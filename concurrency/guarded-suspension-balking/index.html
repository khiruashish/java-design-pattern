    Concurrency Intermediate

    Guarded Suspension & Balking¶

    🟡 Intermediate Concurrency Interview frequency ⭐⭐⭐⭐

    TL;DR

    Both patterns handle "a method can only run when a condition (the guard) is true". Guarded Suspension waits until the guard becomes true; Balking gives up immediately if it isn't. Wait when the condition will soon be true and the caller needs the result (a rider waiting for a packed order). Balk when the work is already being done or isn't needed (a second "run settlement" click).

    See It in Motion¶

    Press Play to watch the calls travel between threads, or step through with Next and Back. Switch to Without it to see what goes wrong without the pattern. Open the full explorer

    1. Intent & Problem It Solves¶

    The problem in plain English: a rider arrives at the restaurant before the food is ready. Checking in a loop (while (!ready) {}) burns a CPU core; sleeping a fixed second wastes time or misses the moment. Separately, a nightly settlement job is triggered by the scheduler, by an operator and by a retry at the same time. Running it three times means three payouts.

    Definitions (Doug Lea, Concurrent Programming in Java; Mark Grand, Patterns in Java):

    Guarded Suspension: if a precondition for an operation isn't met, suspend the calling thread until it is, then proceed.

    Balking: if an object is not in an appropriate state for an operation, return immediately without doing it.

    Both are the building blocks of every blocking queue, latch, future and "only one at a time" job you'll ever use.

    2. Real-World Analogy¶

    The pickup counter and the lift button

    Guarded suspension: you wait at the pickup counter (not pacing around the kitchen) and the staff call your name when the order is ready. Balking: pressing a lift's call button when it's already lit does nothing. The lift is already coming; a second request is pointless.

    3. Structure¶

    flowchart TB subgraph GS["Guarded Suspension"] A1["synchronized method"] --> G1{"guard true?"} G1 -- no --> W["wait() / await()<br/>releases the lock"] --> G1 G1 -- yes --> R1["do the work"] N["another thread changes state<br/>then notifyAll() / signalAll()"] -.-> W end subgraph BK["Balking"] A2["method"] --> G2{"state OK?<br/>(compareAndSet)"} G2 -- no --> X["return immediately"] G2 -- yes --> R2["do the work, then reset state"] end
    Element Guarded Suspension Balking
    Guard Condition that will become true (item available, order packed) State that makes the call pointless (already running, not dirty)
    When false Block (with a timeout) Return a "not done" result
    Java tools synchronized + wait/notifyAll, Lock + Condition, BlockingQueue, CountDownLatch AtomicBoolean.compareAndSet, tryLock(), a state field

    4. Naive Approach (Without the Pattern)¶

    while (!counter.isPacked(orderId)) { }               // busy-wait: 100% CPU, and maybe never sees the change (no visibility)
while (!counter.isPacked(orderId)) Thread.sleep(1000); // up to 1 s late, and still racy

if (!running) { running = true; settle(); running = false; }   // check-then-act race: two threads both see false
    • Busy waiting wastes CPU and may spin forever without volatile/locks.
    • Sleep-polling adds latency.
    • Check-then-act without atomicity lets duplicates through.

    5. Three Real-World Examples¶

    Example 1: Riders Wait for Packed Orders (Food Delivery)¶

    Scenario: A cloud kitchen hands 1,500 orders an hour to riders. Riders arrive early; each waits for their order. If the kitchen hasn't packed an order within the rider's slot, the rider must be released and reassigned rather than waiting forever. Thousands of waiting riders are modelled as virtual threads.

    Design:

    sequenceDiagram autonumber participant R1 as Rider (ORD-501) participant R2 as Rider (ORD-999) participant C as PickupCounter participant K as Kitchen R1->>C: awaitPickup(501, 2s) → wait() R2->>C: awaitPickup(999, 200ms) → wait() K->>C: markPacked(501, B3) → notifyAll() C-->>R1: shelf B3 Note over R2: guard still false → keeps waiting C-->>R2: timeout → null (reassign)

    Full Code:

    package com.handbook.concurrency.guarded.delivery;

import java.util.HashMap;
import java.util.Map;

/** Guarded Suspension: a rider waits until the guard "order is packed" becomes true. */
public final class PickupCounter {

    private final Map<String, String> packed = new HashMap<>(); // orderId -> shelf

    public synchronized void markPacked(String orderId, String shelf) {
        packed.put(orderId, shelf);
        notifyAll(); // (1)!
    }

    public synchronized String awaitPickup(String orderId, long timeoutMs) throws InterruptedException {
        long deadline = System.nanoTime() + timeoutMs * 1_000_000;
        while (!packed.containsKey(orderId)) { // (2)!
            long remainingMs = (deadline - System.nanoTime()) / 1_000_000;
            if (remainingMs <= 0) {
                return null; // (3)!
            }
            wait(remainingMs);
        }
        return packed.remove(orderId);
    }
}
    1. notifyAll, not notify: riders wait for different orders, so waking just one might wake the wrong one.
    2. The guard is re-checked in a while loop after every wake-up (spurious wake-ups, or another order was packed).
    3. A timeout turns "wait forever" into a decision the caller can act on.
    package com.handbook.concurrency.guarded.delivery;

public class DeliveryDemo {

    public static void main(String[] args) throws Exception {
        System.out.println("=== Food Delivery: Riders Wait at the Counter Until the Order Is Packed ===");
        PickupCounter counter = new PickupCounter();
        String[] result = new String[2];

        Thread rider1 = Thread.ofVirtual().start(() -> {
            try {
                result[0] = counter.awaitPickup("ORD-501", 2_000);
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
            }
        });
        Thread rider2 = Thread.ofVirtual().start(() -> {
            try {
                result[1] = counter.awaitPickup("ORD-999", 200); // kitchen never finishes this one in time
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
            }
        });

        Thread.sleep(100); // kitchen is still cooking; riders are suspended, not spinning
        counter.markPacked("ORD-501", "shelf B3");
        rider1.join();
        rider2.join();
        System.out.println("Rider for ORD-501 picked up from: " + result[0]);
        System.out.println("Rider for ORD-999 got: " + result[1] + " -> timed out, reassigned to another pickup");
    }
}

    Output:

    === Food Delivery: Riders Wait at the Counter Until the Order Is Packed ===
Rider for ORD-501 picked up from: shelf B3
Rider for ORD-999 got: null -> timed out, reassigned to another pickup

    Why guarded suspension here:

    • The rider needs the result and it will usually arrive soon.
    • Waiting threads release the lock and use no CPU.
    • Timeouts keep the system live when the guard never comes true.

    Example 2: Balking Duplicate Settlement Runs (Payments)¶

    Scenario: A payment aggregator settles merchant balances nightly. The scheduler fires at 23:00; operators sometimes click "run now"; the workflow engine retries on a timeout. A second concurrent run would pay merchants twice. Duplicate triggers must return immediately (not queue up and run again afterwards).

    Design:

    flowchart LR S[Scheduler 23:00] --> J{compareAndSet false→true} O[Ops: Run now] --> J W[Workflow retry] --> J J -- won --> RUN[Settle batch] J -- lost --> B[Balk: return false] RUN --> RESET[running = false]

    Full Code:

    package com.handbook.concurrency.guarded.settlement;

import java.util.concurrent.CountDownLatch;
import java.util.concurrent.atomic.AtomicBoolean;
import java.util.concurrent.atomic.AtomicInteger;

/** Balking: if the job is already running, a new trigger returns immediately instead of waiting. */
public final class SettlementJob {

    private final AtomicBoolean running = new AtomicBoolean(false);
    private final AtomicInteger batchesSettled = new AtomicInteger();
    private final CountDownLatch holdOpen;

    public SettlementJob(CountDownLatch holdOpen) {
        this.holdOpen = holdOpen;
    }

    /** @return true if this call ran the settlement, false if it balked. */
    public boolean trigger() throws InterruptedException {
        if (!running.compareAndSet(false, true)) { // (1)!
            return false;
        }
        try {
            holdOpen.await(); // simulates a long settlement run
            batchesSettled.incrementAndGet();
            return true;
        } finally {
            running.set(false); // (2)!
        }
    }

    public boolean isRunning() {
        return running.get();
    }

    public int batchesSettled() {
        return batchesSettled.get();
    }
}
    1. Atomic check-and-set: exactly one caller can flip false → true. Everyone else balks.
    2. Reset in finally, so a failed run doesn't block every future run.
    package com.handbook.concurrency.guarded.settlement;

import java.util.ArrayList;
import java.util.List;
import java.util.concurrent.CountDownLatch;
import java.util.concurrent.Executors;
import java.util.concurrent.Future;

public class SettlementDemo {

    public static void main(String[] args) throws Exception {
        System.out.println("=== Payments: Balking Duplicate Settlement Triggers ===");
        CountDownLatch release = new CountDownLatch(1);
        SettlementJob job = new SettlementJob(release);

        try (var pool = Executors.newVirtualThreadPerTaskExecutor()) {
            Future<Boolean> cron = pool.submit(job::trigger);   // scheduler fires at 23:00
            while (!job.isRunning()) {
                Thread.onSpinWait();                             // wait until the scheduled run has started
            }
            List<Future<Boolean>> others = new ArrayList<>();
            others.add(pool.submit(job::trigger));               // ops clicks "run now"
            others.add(pool.submit(job::trigger));               // a retry from the orchestrator
            int balked = 0;
            for (Future<Boolean> f : others) {
                balked += f.get() ? 0 : 1;                       // they return at once, no waiting
            }
            System.out.println("While running: " + balked + " duplicate triggers balked immediately");
            release.countDown();
            System.out.println("Scheduled run settled? " + cron.get());
        }
        System.out.println("Batches settled: " + job.batchesSettled() + " (never twice: no double payouts)");
        System.out.println("Next night's trigger runs again: " + new SettlementJob(new CountDownLatch(0)).trigger());
    }
}

    Output:

    === Payments: Balking Duplicate Settlement Triggers ===
While running: 2 duplicate triggers balked immediately
Scheduled run settled? true
Batches settled: 1 (never twice: no double payouts)
Next night's trigger runs again: true

    Why balking here:

    • A second run adds no value and real risk (double payouts).
    • Callers get an instant answer ("already running") instead of piling up.
    • Across several instances, the same idea becomes a distributed lock or leader election.

    Example 3: Start Playback When Enough Is Buffered (Streaming)¶

    Scenario: A video player must not start until 6 seconds are buffered, or viewers see stalls in the first seconds, which is the biggest churn driver. On a weak network the player waits at most 150 ms before switching to a lower bitrate. The network thread appends 2-second segments as they arrive.

    Design:

    flowchart LR N[Network thread] -->|"append(2s) + signalAll"| B[(PlaybackBuffer)] P[Player] -->|"awaitPlayable(6s, timeout)"| B B -->|true| Play[Start playback] B -->|false| Drop[Lower bitrate, retry]

    Full Code:

    package com.handbook.concurrency.guarded.buffer;

import java.util.concurrent.TimeUnit;
import java.util.concurrent.locks.Condition;
import java.util.concurrent.locks.ReentrantLock;

/** Guarded suspension with Lock/Condition: playback waits until enough seconds are buffered. */
public final class PlaybackBuffer {

    private final ReentrantLock lock = new ReentrantLock();
    private final Condition enoughBuffered = lock.newCondition(); // (1)!
    private int bufferedSeconds;

    public void append(int seconds) {
        lock.lock();
        try {
            bufferedSeconds += seconds;
            enoughBuffered.signalAll();
        } finally {
            lock.unlock();
        }
    }

    /** @return true if playback can start, false if we should show a spinner / drop quality. */
    public boolean awaitPlayable(int neededSeconds, long timeoutMs) throws InterruptedException {
        lock.lock();
        try {
            long nanos = TimeUnit.MILLISECONDS.toNanos(timeoutMs);
            while (bufferedSeconds < neededSeconds) {
                if (nanos <= 0) {
                    return false;
                }
                nanos = enoughBuffered.awaitNanos(nanos); // (2)!
            }
            return true;
        } finally {
            lock.unlock();
        }
    }
}
    1. A Condition is a named wait set. One lock can have several (notFull, notEmpty), so you signal only the threads that care.
    2. awaitNanos returns the time remaining, which makes correct timeouts inside a while loop easy.
    package com.handbook.concurrency.guarded.buffer;

public class BufferDemo {

    public static void main(String[] args) throws Exception {
        System.out.println("=== Streaming: Start Playback Only When 6 Seconds Are Buffered ===");
        PlaybackBuffer good = new PlaybackBuffer();
        Thread network = Thread.ofVirtual().start(() -> {
            for (int i = 0; i < 4; i++) {
                good.append(2); // 2-second segments arriving
                try {
                    Thread.sleep(20);
                } catch (InterruptedException e) {
                    return;
                }
            }
        });
        System.out.println("Fast network: playable within 2s? " + good.awaitPlayable(6, 2_000));
        network.join();

        PlaybackBuffer slow = new PlaybackBuffer();
        slow.append(2); // only one segment before the network drops
        boolean playable = slow.awaitPlayable(6, 150);
        System.out.println("Weak network: playable within 150ms? " + playable + " -> switch to 480p and retry");
    }
}

    Output:

    === Streaming: Start Playback Only When 6 Seconds Are Buffered ===
Fast network: playable within 2s? true
Weak network: playable within 150ms? false -> switch to 480p and retry

    Why guarded suspension here:

    • The player should react the moment the guard is met, not on the next polling tick.
    • The timeout encodes a product decision (degrade quality rather than stall).
    • Lock/Condition work well with virtual threads, which don't pin a carrier while waiting.
    Unit Tests: GuardedSuspensionTest.java 
    package com.handbook.concurrency.guarded;

import com.handbook.concurrency.guarded.buffer.PlaybackBuffer;
import com.handbook.concurrency.guarded.delivery.PickupCounter;
import com.handbook.concurrency.guarded.settlement.SettlementJob;
import org.junit.jupiter.api.Test;

import java.util.concurrent.CountDownLatch;
import java.util.concurrent.Executors;
import java.util.concurrent.Future;

import static org.assertj.core.api.Assertions.assertThat;

class GuardedSuspensionTest {

    @Test
    void riderReceivesShelfOnceOrderIsPacked() throws Exception {
        PickupCounter counter = new PickupCounter();
        Thread kitchen = Thread.ofVirtual().start(() -> counter.markPacked("O", "A1"));
        assertThat(counter.awaitPickup("O", 5_000)).isEqualTo("A1");
        kitchen.join();
    }

    @Test
    void waitingTimesOut() throws Exception {
        assertThat(new PickupCounter().awaitPickup("never", 50)).isNull();
        assertThat(new PlaybackBuffer().awaitPlayable(1, 50)).isFalse();
    }

    @Test
    void concurrentTriggersBalk() throws Exception {
        CountDownLatch release = new CountDownLatch(1);
        SettlementJob job = new SettlementJob(release);
        try (var pool = Executors.newVirtualThreadPerTaskExecutor()) {
            Future<Boolean> first = pool.submit(job::trigger);
            while (!job.isRunning()) {
                Thread.onSpinWait();
            }
            assertThat(pool.submit(job::trigger).get()).isFalse();
            release.countDown();
            assertThat(first.get()).isTrue();
        }
        assertThat(job.batchesSettled()).isEqualTo(1);
    }
}

    6. Variations & Modern Java Take¶

    Variation Notes
    wait/notifyAll Built in; one wait set per object; must hold the monitor
    Lock + Condition Several wait sets, awaitNanos, interruptible and fair options
    Ready-made guarded objects BlockingQueue.take/poll(timeout), CountDownLatch.await, CompletableFuture.get(timeout), Semaphore.acquire
    Balking with tryLock() if (!lock.tryLock()) return; for "skip if busy" sections
    Balking with state if (!dirty) return; (autosave), if (closed) return; (idempotent close())
    Virtual threads (Java 21+) Waiting is cheap, so blocking designs scale again; prefer ReentrantLock over synchronized around long waits until JDK 24's fix for monitor pinning

    7. Where It Lives in Real Frameworks¶

    Where Guarded Suspension / Balking
    JDK ArrayBlockingQueue (two Conditions: notEmpty, notFull), FutureTask.get, CountDownLatch, Thread.join
    JDK balking AtomicBoolean.compareAndSet idioms, Closeable.close() "has no effect if already closed", ExecutorService.shutdown()
    Spring @Scheduled with ShedLock (@SchedulerLock) balks duplicate runs across instances
    Kafka KafkaConsumer.poll(timeout) guarded waiting; consumer wakeup()
    Netty / OkHttp Connection pools wait for a free connection with a timeout

    8. Pros, Cons & Trade-offs¶

    ✅ Pros ❌ Cons
    No CPU wasted while waiting Easy to get wrong (if vs while, notify vs notifyAll, missed signals)
    Reacts immediately when the guard changes Waiting forever without timeouts causes hangs
    Balking prevents duplicate, harmful work Balking can silently drop requests that should have run later
    Foundation of all blocking concurrency utilities Hand-rolled versions are rarely better than JDK ones

    9. Pitfalls & Anti-Patterns¶

    if instead of while

    After waking, another thread may already have consumed what you were waiting for, or the wake-up was spurious. Always re-check the guard in a loop (coding challenge).

    Waiting without a timeout

    If the notifier crashes, waiters hang forever. Use wait(ms), awaitNanos or poll(timeout) and handle the "not ready" outcome.

    notify() with different guards

    notify wakes one arbitrary waiter. If waiters wait for different things, the wrong one may wake and go back to sleep: a missed signal. Use notifyAll or separate Conditions.

    Balking that should have been queuing

    If a skipped request carries new data (a new file to process), balking loses it. Then you want "run again once afterwards" (a dirty flag) or a queue.

    10. Senior / Architect Deep Dive (10–15 yrs)¶

    Why the lock is released. wait() atomically releases the monitor and suspends; on wake-up it re-acquires the monitor before returning. That atomicity is what prevents a lost wake-up between "check guard" and "start waiting". Hand-rolled alternatives with volatile flags and sleep reintroduce exactly that race.

    Balking across machines. A JVM-local AtomicBoolean only balks within one instance. With three replicas, use a database row lock (SELECT ... FOR UPDATE SKIP LOCKED), a lease in Redis/ZooKeeper, ShedLock, or a Kubernetes CronJob with concurrencyPolicy: Forbid. And still make the job idempotent, because leases can expire mid-run.

    Observability. Track how long threads wait on guards and how often callers balk or time out. A rising balk rate means a job is overrunning its schedule; rising wait times are an early capacity signal.

    War story: double payouts on a Friday night

    A payments team protected settlement with if (!running) { running = true; ... } on a plain boolean. When the scheduler and an operator's "run now" arrived within a millisecond, both threads saw false. 1,200 merchants were paid twice; recovering the money took three weeks. Fix: AtomicBoolean.compareAndSet locally, ShedLock across instances, and an idempotency key per merchant per settlement date in the payout table. Lesson: balking needs an atomic check-and-set, and money movement needs idempotency as a second line of defence.

    11. Related Patterns & Comparisons¶

    Guarded Suspension Balking Producer-Consumer Double-Checked Locking
    Guard false → Wait Return Producer/consumer wait on full/empty Lock, check again
    Typical guard "Data ready" "Already running / nothing to do" Buffer capacity "Already initialized"
    Relationship Basis of blocking queues Basis of idempotent triggers Two guarded suspensions Balking on the fast path

    12. Interview Corner¶

    Q1. What is guarded suspension?

    Waiting (without using CPU) until a condition becomes true, then continuing.

    Q2. What is balking?

    Returning immediately when the object isn't in the right state, e.g. a job that's already running.

    Q3. Why must wait() be called inside synchronized?

    It releases and re-acquires the object's monitor; calling it without holding the monitor throws IllegalMonitorStateException.

    Q4. wait() vs sleep()?

    wait releases the lock and waits for a notification; sleep keeps any locks and just pauses.

    Q5. notify vs notifyAll?

    notify wakes one waiter, notifyAll wakes all. Prefer notifyAll unless all waiters wait for the same thing.

    Q1. Why re-check the guard in a while loop?

    Spurious wake-ups and competing threads: the condition may no longer be true when you wake.

    Q2. Condition vs wait/notify?

    Several conditions per lock, timed and interruptible waits, works with ReentrantLock.

    Q3. How do you balk safely?

    Atomic check-and-set: AtomicBoolean.compareAndSet(false, true) or tryLock(), and reset in finally.

    Q4. How do you add a timeout correctly?

    Compute a deadline; in the loop, wait for the remaining time and return a "not ready" result when it reaches zero.

    Q5. Which JDK classes implement guarded suspension?

    BlockingQueue, CountDownLatch, CyclicBarrier, Semaphore, FutureTask, Exchanger.

    Q1. "Implement a bounded blocking queue."

    One lock, two conditions (notFull, notEmpty), while loops for both guards, signal the opposite condition after each put/take.

    Q2. "Make a cron job run at most once across 5 replicas."

    Lease-based lock (DB row/Redis/ZooKeeper) with expiry, or Kubernetes CronJob Forbid; plus idempotent processing keyed by business date.

    Q3. "What is a lost wake-up?"

    A notification sent between a thread's guard check and its call to wait, so it waits forever. wait() inside the same monitor as the state change prevents it.

    Q4. "Balk or queue?"

    Balk when a later run would cover the skipped request anyway; queue (or set a 'run again' flag) when each request carries distinct work.

    Q5. "How do virtual threads change these patterns?"

    Blocking becomes cheap, so guarded waits on millions of threads are fine; avoid synchronized around long blocking calls on older JDKs (pinning) and prefer ReentrantLock.

    Problem: Two consumers wait on an empty mailbox; a producer adds one item and calls notifyAll. Show what happens with if (empty) wait() versus while (empty) wait().

    package com.handbook.concurrency.guarded.ifwhile;

import java.util.ArrayDeque;
import java.util.ArrayList;
import java.util.Collections;
import java.util.List;
import java.util.Queue;

/** Coding challenge: why the guard must be re-checked in a WHILE loop, not an IF. */
public class IfVersusWhileDemo {

    static final class Mailbox {
        private final Queue<String> items = new ArrayDeque<>();
        private final boolean useWhile;

        Mailbox(boolean useWhile) {
            this.useWhile = useWhile;
        }

        synchronized void put(String item) {
            items.add(item);
            notifyAll();
        }

        synchronized String take() throws InterruptedException {
            if (useWhile) {
                while (items.isEmpty()) {
                    wait();
                }
            } else {
                if (items.isEmpty()) {
                    wait(); // BUG: after waking, another consumer may already have taken the item
                }
            }
            return items.poll();
        }
    }

    static List<String> run(boolean useWhile) throws InterruptedException {
        Mailbox box = new Mailbox(useWhile);
        List<String> got = Collections.synchronizedList(new ArrayList<>());
        Thread a = Thread.ofPlatform().start(() -> take(box, got));
        Thread b = Thread.ofPlatform().start(() -> take(box, got));
        while (a.getState() != Thread.State.WAITING || b.getState() != Thread.State.WAITING) {
            Thread.onSpinWait(); // make sure both consumers are waiting
        }
        box.put("job-1"); // ONE item, notifyAll wakes BOTH consumers
        Thread.sleep(100);
        if (useWhile) {
            box.put("job-2"); // the second consumer is still (correctly) waiting
        }
        a.join();
        b.join();
        List<String> sorted = new ArrayList<>(got);
        sorted.sort((x, y) -> String.valueOf(x).compareTo(String.valueOf(y)));
        return sorted;
    }

    static void take(Mailbox box, List<String> got) {
        try {
            got.add(String.valueOf(box.take()));
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        }
    }

    public static void main(String[] args) throws InterruptedException {
        System.out.println("=== Challenge: if (guard) wait() vs while (guard) wait() ===");
        System.out.println("if   : consumers got " + run(false) + "  <- one woke up to an empty queue");
        System.out.println("while: consumers got " + run(true) + "  <- the guard was re-checked after waking");
    }
}

    Output:

    === Challenge: if (guard) wait() vs while (guard) wait() ===
if   : consumers got [job-1, null]  <- one woke up to an empty queue
while: consumers got [job-1, job-2]  <- the guard was re-checked after waking

    Key points to say: notifyAll wakes both consumers; with if, both proceed and one reads an empty queue (null, or an exception with remove()). With while, the loser re-checks, sees the queue empty and goes back to waiting until the next item arrives.

    Behavioural tie-in (STAR) for experienced candidates

    • S: Merchants were paid twice when two settlement triggers raced on a plain boolean flag.
    • T: Guarantee one settlement per night across all replicas.
    • A: Replaced the flag with compareAndSet, added ShedLock for cross-instance balking, and added an idempotency key per merchant and date in the payouts table.
    • R: No duplicate payouts in 18 months; overlapping runs now show up as a balk metric and alert.

    13. Quick Revision Card¶

    Remember in 30 seconds

    • Guarded suspension: guard false → wait (in a while loop, with a timeout).
    • Balking: guard false → return (atomic compareAndSet).
    • notifyAll unless all waiters share one guard; or use separate Conditions.
    • Prefer JDK utilities: BlockingQueue, CountDownLatch, CompletableFuture.
    • Across machines: leases/locks plus idempotency.
    synchronized T take() throws InterruptedException { while (q.isEmpty()) wait(); return q.poll(); }
