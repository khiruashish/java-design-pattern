    Intermediate Principles

    Design Principles Beyond SOLID¶

    🟢 Beginner 🟡 Intermediate Interview frequency ⭐⭐⭐⭐

    TL;DR

    SOLID tells you how to shape classes and dependencies. These seven principles keep the result simple, honest and safe: don't repeat knowledge (DRY), don't be clever (KISS), don't build for imaginary futures (YAGNI), prefer composition to inheritance, talk only to your friends (Law of Demeter), tell objects what to do instead of asking for their data, and fail fast on invalid input.

    # Principle One-liner Smell when violated Pattern/tool that helps
    1 DRY One authoritative place for each piece of knowledge The same rule copy-pasted and drifting Value objects, Template Method
    2 KISS The simplest solution that works Clever code nobody can review Standard library
    3 YAGNI Build it when it's needed, not before Unused interfaces, flags, plug-in points Refactoring later
    4 Composition over Inheritance Has-a beats is-a for reuse Fragile base class, deep trees Decorator, Strategy
    5 Law of Demeter Only talk to your immediate friends a.getB().getC().doX() Facade, Tell-Don't-Ask
    6 Tell, Don't Ask Send commands, don't pull data and decide Logic in callers; anemic models Rich domain model
    7 Fail Fast Reject invalid state immediately, loudly Wrong results far from the cause Validating constructors

    1. DRY: Don't Repeat Yourself¶

    "Every piece of knowledge must have a single, unambiguous, authoritative representation within a system." (Andy Hunt & Dave Thomas, The Pragmatic Programmer, 1999)

    Key point: DRY is about knowledge, not about text. Two identical-looking lines that represent different rules are not duplication. One rule written in two different ways is.

    package com.handbook.principles.other.dry;

/** VIOLATES DRY: the same email rule is copy-pasted, and the copies have already drifted apart. */
public class SignupBefore {
    public boolean canRegister(String email) {
        return email != null && email.contains("@") && email.indexOf('@') > 0;
    }

    public boolean canInvite(String email) {
        return email != null && email.contains("@");          // drifted: accepts "@nobody"
    }
}

    package com.handbook.principles.other.dry;

import java.util.Locale;
import java.util.regex.Pattern;

/** DRY: the single, authoritative representation of "a valid email". Every caller reuses it. */
public record EmailAddress(String value) {
    private static final Pattern SHAPE = Pattern.compile("^[^@\\s]+@[^@\\s]+\\.[^@\\s]+$");

    public EmailAddress {
        if (value == null || !SHAPE.matcher(value.strip()).matches()) {
            throw new IllegalArgumentException("invalid email: " + value);
        }
        value = value.strip().toLowerCase(Locale.ROOT);
    }

    public static boolean isValid(String raw) {
        try {
            new EmailAddress(raw);
            return true;
        } catch (IllegalArgumentException e) {
            return false;
        }
    }

    public String domain() { return value.substring(value.indexOf('@') + 1); }
}

    package com.handbook.principles.other.dry;

public class DryDemo {
    public static void main(String[] args) {
        SignupBefore before = new SignupBefore();
        String bad = "@nobody";
        System.out.println("before: register(" + bad + ")=" + before.canRegister(bad) + ", invite(" + bad + ")=" + before.canInvite(bad)
                + "  <-- two copies, two answers");
        System.out.println("after : isValid(" + bad + ")=" + EmailAddress.isValid(bad));
        EmailAddress ok = new EmailAddress("  Ana@Example.COM ");
        System.out.println("after : normalised=" + ok.value() + ", domain=" + ok.domain());
    }
}

    before: register(@nobody)=false, invite(@nobody)=true  <-- two copies, two answers
after : isValid(@nobody)=false
after : normalised=ana@example.com, domain=example.com
    ✅ Pros ⚠️ Cons / Trade-offs
    A rule change is one edit, so copies can't drift Wrong abstraction: merging code that only looks alike couples unrelated features. "Duplication is far cheaper than the wrong abstraction" (Sandi Metz)
    Bugs are fixed once Cross-service DRY (shared libraries) couples deploys. Microservices often prefer some duplication
    Creates meaningful types (EmailAddress) Over-DRY tests become hard to read. Prefer DAMP (Descriptive And Meaningful Phrases) in tests

    Rule of three: tolerate the second copy, and extract on the third, once you know what really varies.

    2. KISS: Keep It Simple¶

    "Keep it simple, stupid." (attributed to Kelly Johnson, Lockheed Skunk Works, 1960s)

    Key point: prefer the solution that is easiest to read, review and change, even if it's less general or less "elegant". Simplicity is about how much a reader has to keep in their head, not about line count.

    package com.handbook.principles.other.kiss;

import java.util.Collections;
import java.util.List;
import java.util.function.BinaryOperator;
import java.util.function.Function;
import java.util.function.Supplier;

/** KISS: the same requirement ("is this year a leap year? what is the max?"), solved clever vs simple. */
public final class KissExamples {
    private KissExamples() { }

    // ---- too clever: a generic "strategy factory" for a one-line rule
    public static boolean isLeapClever(int year) {
        Supplier<Function<Integer, BinaryOperator<Boolean>>> factory =
                () -> divisor -> (acc, unused) -> acc && year % divisor == 0;
        boolean by4 = factory.get().apply(4).apply(true, true);
        boolean by100 = factory.get().apply(100).apply(true, true);
        boolean by400 = factory.get().apply(400).apply(true, true);
        return by4 && (!by100 || by400);
    }

    // ---- simple: reads like the rule itself
    public static boolean isLeapSimple(int year) {
        return (year % 4 == 0 && year % 100 != 0) || year % 400 == 0;
    }

    // ---- hand-rolled loop vs the library: the library is simpler AND already tested
    public static int maxHandRolled(List<Integer> values) {
        int max = Integer.MIN_VALUE;
        for (int i = 0; i < values.size(); i++) {
            if (values.get(i) > max) max = values.get(i);
        }
        return max;
    }

    public static int maxSimple(List<Integer> values) {
        return Collections.max(values);
    }
}

    package com.handbook.principles.other.kiss;

import java.util.List;

public class KissDemo {
    public static void main(String[] args) {
        for (int year : new int[]{1900, 2000, 2024, 2026}) {
            System.out.println(year + " leap? clever=" + KissExamples.isLeapClever(year) + " simple=" + KissExamples.isLeapSimple(year));
        }
        List<Integer> values = List.of(3, 9, 4);
        System.out.println("max: hand-rolled=" + KissExamples.maxHandRolled(values) + " library=" + KissExamples.maxSimple(values));
    }
}

    1900 leap? clever=false simple=false
2000 leap? clever=true simple=true
2024 leap? clever=true simple=true
2026 leap? clever=false simple=false
max: hand-rolled=9 library=9
    ✅ Pros ⚠️ Cons / Trade-offs
    Faster onboarding and code review "Simple" is subjective. Agree on team conventions
    Fewer bugs hide in simple code Too simple can mean naive (O(n²) loops, no error handling)
    Easier to optimise later, once you've measured Sometimes the simple local choice adds global complexity, such as duplicated logic

    Signs of violation: generic frameworks written for one use case, reflection or metaprogramming where a method call would do, deeply nested streams, one-letter names, "clever" bit tricks without a measured need.

    3. YAGNI: You Aren't Gonna Need It¶

    "Always implement things when you actually need them, never when you just foresee that you need them." (Ron Jeffries, Extreme Programming, late 1990s)

    Key point: speculative features have a cost you pay now: building them, testing them, carrying them along and delaying other work. They usually turn out wrong, because the real requirement differs from the one you guessed.

    package com.handbook.principles.other.yagni;

import java.util.Map;

/** YAGNI: the requirement today is "convert INR to USD at a configured rate". */
public final class YagniExamples {
    private YagniExamples() { }

    /** Speculative: plugin registry, provider SPI, caching hooks, multi-hop conversion... none of it requested. */
    public interface RateProvider { double rate(String from, String to); }

    public interface RateCache { Double lookup(String pair); void store(String pair, double rate); }

    public interface ConversionListener { void converted(String from, String to, long in, long out); }

    public static final class OverEngineeredConverter {
        private final Map<String, RateProvider> providers;
        private final RateCache cache;
        private final ConversionListener listener;

        public OverEngineeredConverter(Map<String, RateProvider> providers, RateCache cache, ConversionListener listener) {
            this.providers = providers;
            this.cache = cache;
            this.listener = listener;
        }

        public long convert(String providerName, String from, String to, long minorUnits) {
            String pair = from + "->" + to;
            Double rate = cache.lookup(pair);
            if (rate == null) {
                rate = providers.get(providerName).rate(from, to);
                cache.store(pair, rate);
            }
            long out = Math.round(minorUnits * rate);
            listener.converted(from, to, minorUnits, out);
            return out;
        }
    }

    /** Just enough: one rate, one method. Easy to extend WHEN a real second requirement appears. */
    public record InrToUsd(long usdCentsPerHundredRupees) {
        public long convertPaise(long paise) {
            return Math.round(paise * (double) usdCentsPerHundredRupees / 10_000);
        }
    }
}

    package com.handbook.principles.other.yagni;

import java.util.HashMap;
import java.util.Map;

public class YagniDemo {
    public static void main(String[] args) {
        Map<String, Double> cacheStore = new HashMap<>();
        var heavy = new YagniExamples.OverEngineeredConverter(
                Map.of("fixed", (from, to) -> 0.012),
                new YagniExamples.RateCache() {
                    public Double lookup(String pair) { return cacheStore.get(pair); }
                    public void store(String pair, double rate) { cacheStore.put(pair, rate); }
                },
                (from, to, in, out) -> { });
        System.out.println("over-engineered: 10000 paise -> " + heavy.convert("fixed", "INR", "USD", 10_000)
                + " USD cents (3 interfaces + 1 class to wire)");
        System.out.println("just enough    : 10000 paise -> " + new YagniExamples.InrToUsd(120).convertPaise(10_000)
                + " USD cents (1 record)");
    }
}

    over-engineered: 10000 paise -> 120 USD cents (3 interfaces + 1 class to wire)
just enough    : 10000 paise -> 120 USD cents (1 record)
    ✅ Pros ⚠️ Cons / Trade-offs
    Ship sooner, with less code to maintain Some decisions are expensive to reverse (public APIs, data formats, security, i18n). Design those up front
    The design follows real requirements Needs good tests and a refactoring habit, or "add it later" turns into "rewrite later"
    Fewer unused abstractions, which serves KISS Can be misused as an excuse for no design at all

    YAGNI vs OCP: OCP says "make it easy to extend". YAGNI says "don't add the extension point until it's needed". Together: write simple code now, and refactor to an abstraction when the second variant actually arrives.

    4. Composition over Inheritance¶

    "Favor object composition over class inheritance." (Gang of Four, Design Patterns, 1994)

    Key point: inheritance gives white-box reuse: the child sees and depends on the parent's internals. Composition gives black-box reuse: you hold a reference to an interface and forward calls to it. You can change it at run time, combine several behaviours, and never depend on how the delegate works internally.

    package com.handbook.principles.other.composition;

import java.util.Collection;
import java.util.HashSet;

/**
 * BROKEN by inheritance (Effective Java, Item 18): HashSet.addAll() internally calls add(),
 * so every element added through addAll() is counted twice. The subclass depends on a
 * self-use implementation detail of its parent: the "fragile base class" problem.
 */
public class InstrumentedHashSet<E> extends HashSet<E> {
    private int addCount = 0;

    @Override
    public boolean add(E e) {
        addCount++;
        return super.add(e);
    }

    @Override
    public boolean addAll(Collection<? extends E> c) {
        addCount += c.size();
        return super.addAll(c);
    }

    public int addCount() { return addCount; }
}

    package com.handbook.principles.other.composition;

import java.util.Collection;
import java.util.Iterator;
import java.util.Set;

/**
 * FIXED by composition: wrap ANY Set and forward to it. We no longer care how the wrapped set
 * implements addAll, and the same wrapper works for HashSet, TreeSet, LinkedHashSet...
 */
public class InstrumentedSet<E> implements Set<E> {
    private final Set<E> delegate;
    private int addCount = 0;

    public InstrumentedSet(Set<E> delegate) { this.delegate = delegate; }

    public int addCount() { return addCount; }

    @Override public boolean add(E e) { addCount++; return delegate.add(e); }
    @Override public boolean addAll(Collection<? extends E> c) { addCount += c.size(); return delegate.addAll(c); }

    // ---- plain forwarding
    @Override public int size() { return delegate.size(); }
    @Override public boolean isEmpty() { return delegate.isEmpty(); }
    @Override public boolean contains(Object o) { return delegate.contains(o); }
    @Override public Iterator<E> iterator() { return delegate.iterator(); }
    @Override public Object[] toArray() { return delegate.toArray(); }
    @Override public <T> T[] toArray(T[] a) { return delegate.toArray(a); }
    @Override public boolean remove(Object o) { return delegate.remove(o); }
    @Override public boolean containsAll(Collection<?> c) { return delegate.containsAll(c); }
    @Override public boolean retainAll(Collection<?> c) { return delegate.retainAll(c); }
    @Override public boolean removeAll(Collection<?> c) { return delegate.removeAll(c); }
    @Override public void clear() { delegate.clear(); }
    @Override public boolean equals(Object o) { return delegate.equals(o); }
    @Override public int hashCode() { return delegate.hashCode(); }
    @Override public String toString() { return delegate.toString(); }
}

    package com.handbook.principles.other.composition;

import java.util.List;
import java.util.TreeSet;

public class CompositionDemo {
    public static void main(String[] args) {
        InstrumentedHashSet<String> inherited = new InstrumentedHashSet<>();
        inherited.addAll(List.of("a", "b", "c"));
        System.out.println("inheritance: added 3, addCount = " + inherited.addCount() + "  <-- double counted");

        InstrumentedSet<String> composed = new InstrumentedSet<>(new TreeSet<>());
        composed.addAll(List.of("a", "b", "c"));
        System.out.println("composition: added 3, addCount = " + composed.addCount() + "  (wrapping a TreeSet: " + composed + ")");
    }
}

    inheritance: added 3, addCount = 6  <-- double counted
composition: added 3, addCount = 3  (wrapping a TreeSet: [a, b, c])
    classDiagram direction LR class Set~E~ { <<interface>> } class InstrumentedSet~E~ { -Set~E~ delegate -int addCount } Set <|.. InstrumentedSet InstrumentedSet o-- Set : wraps any Set HashSet <|-- InstrumentedHashSet : fragile
    ✅ Pros ⚠️ Cons / Trade-offs
    Immune to the parent's self-use changes Boilerplate forwarding methods (Lombok @Delegate and Kotlin by help)
    Works with any implementation of the interface Identity: wrapper != delegate, which matters for equals and callbacks (the "SELF problem")
    Behaviour can be swapped or stacked at run time (Decorator) More objects and indirection

    When inheritance is still right: a real "is-a" relationship, inside one package or team, with a parent designed and documented for extension (AbstractList, Template Method bases, sealed hierarchies of data types).

    5. Law of Demeter (Principle of Least Knowledge)¶

    "Only talk to your immediate friends." (Ian Holland, Northeastern University, Demeter project, 1987)

    Key point: a method m of object O should only call methods on: O itself, m's parameters, objects m creates, and O's direct fields. Chained calls into someone else's internals (customer.getWallet().setCents(...)) couple you to the whole structure.

    Paperboy.java (before vs after)
    package com.handbook.principles.other.demeter;

public class Paperboy {
    private long collected;

    /** VIOLATES LoD: reaches through customer into the wallet ("train wreck" a.getB().getC()). */
    public void collectBefore(Customer customer, long due) {
        Wallet wallet = customer.getWallet();
        if (wallet.getCents() >= due) {
            wallet.setCents(wallet.getCents() - due);
            collected += due;
        }
    }

    /** FOLLOWS LoD: only talks to its direct collaborator. */
    public void collectAfter(Customer customer, long due) {
        collected += customer.pay(due);
    }

    public long collected() { return collected; }
}
    Customer.java
    package com.handbook.principles.other.demeter;

/** Exposes its wallet (Before) AND offers a behaviour that hides it (After). */
public class Customer {
    private final String name;
    private final Wallet wallet;

    public Customer(String name, Wallet wallet) {
        this.name = name;
        this.wallet = wallet;
    }

    public String name() { return name; }

    /** Before-style accessor: leaks the internal structure. */
    public Wallet getWallet() { return wallet; }

    /** After: the customer decides how to pay; callers only talk to their direct friend. */
    public long pay(long cents) {
        if (wallet.getCents() < cents) throw new IllegalStateException(name + " cannot pay " + cents);
        wallet.setCents(wallet.getCents() - cents);
        return cents;
    }
}

    package com.handbook.principles.other.demeter;

public class DemeterDemo {
    public static void main(String[] args) {
        Customer ana = new Customer("Ana", new Wallet(1_000));
        Paperboy boy = new Paperboy();
        boy.collectBefore(ana, 300);
        System.out.println("before: paperboy rummaged in the wallet, wallet now " + ana.getWallet().getCents());
        boy.collectAfter(ana, 300);
        System.out.println("after : customer paid, wallet now " + ana.getWallet().getCents() + ", collected " + boy.collected());
        try {
            boy.collectAfter(ana, 5_000);
        } catch (IllegalStateException e) {
            System.out.println("after : the rule lives with the data -> " + e.getMessage());
        }
    }
}

    before: paperboy rummaged in the wallet, wallet now 700
after : customer paid, wallet now 400, collected 600
after : the rule lives with the data -> Ana cannot pay 5000
    ✅ Pros ⚠️ Cons / Trade-offs
    Internal structure can change without breaking callers Can lead to many small wrapper methods on the middle object
    Rules live with the data (the "insufficient funds" check is in one place) Fluent APIs and streams are fine: list.stream().map().filter() returns the same kind of object and isn't a violation
    Easier mocking: one collaborator, not a chain Data-transfer objects and records are meant to be navigated

    6. Tell, Don't Ask¶

    "Rather than asking an object for data and acting on that data, we should instead tell an object what to do." (Andy Hunt & Dave Thomas, IEEE Software, 2003; popularised by Martin Fowler)

    Key point: if the caller does if (obj.getX() …) obj.setY(…), the decision belongs inside obj. That keeps behaviour next to the data it depends on (encapsulation) and stops callers from re-implementing the rule differently.

    package com.handbook.principles.other.telldontask;

/** The object that owns the data also owns the decision. */
public class Thermostat {
    private final int targetCelsius;
    private boolean heating;

    public Thermostat(int targetCelsius) { this.targetCelsius = targetCelsius; }

    // ---- ASK style: getters let callers pull the data and make the decision outside
    public int getTargetCelsius() { return targetCelsius; }

    public void setHeating(boolean heating) { this.heating = heating; }

    public boolean isHeating() { return heating; }

    // ---- TELL style: give the object the new fact; it decides what that means
    public void onTemperatureReading(int currentCelsius) {
        heating = currentCelsius < targetCelsius - 1;     // 1 degree hysteresis, in ONE place
    }
}

    package com.handbook.principles.other.telldontask;

public class TellDontAskDemo {
    public static void main(String[] args) {
        // ASK: the caller duplicates the rule (and here forgets the hysteresis)
        Thermostat asked = new Thermostat(21);
        int reading = 20;
        if (reading < asked.getTargetCelsius()) asked.setHeating(true);
        System.out.println("ask : reading " + reading + " -> heating " + asked.isHeating() + "  (rule re-implemented by the caller)");

        // TELL: the thermostat applies its own rule
        Thermostat told = new Thermostat(21);
        told.onTemperatureReading(reading);
        System.out.println("tell: reading " + reading + " -> heating " + told.isHeating() + " (thermostat's own 1-degree hysteresis)");
        told.onTemperatureReading(18);
        System.out.println("tell: reading 18 -> heating " + told.isHeating());
    }
}

    ask : reading 20 -> heating true  (rule re-implemented by the caller)
tell: reading 20 -> heating false (thermostat's own 1-degree hysteresis)
tell: reading 18 -> heating true
    ✅ Pros ⚠️ Cons / Trade-offs
    Rich domain model; one place for each rule Queries are still needed for display, reports and serialization. CQS (separate commands from queries) is the balance
    Fewer getters/setters, which fights the anemic domain model Taken to extremes, objects collect unrelated behaviour (an SRP violation)
    Simpler callers, easier to test the rule Some logic really spans several objects. Put it in a domain service

    7. Fail Fast¶

    "Fail fast… makes failures immediate and visible." (Jim Shore, IEEE Software, 2004)

    Key point: detect invalid input or state at the earliest point, usually the constructor or method entry, and throw a clear exception. A failure far from its cause, like a negative invoice three services later, is much harder to diagnose.

    package com.handbook.principles.other.failfast;

import java.time.LocalDate;
import java.time.temporal.ChronoUnit;

/** FAIL SLOW: accepts anything; the error surfaces much later as a wrong number, far from its cause. */
public class LenientReservation {
    private final LocalDate checkIn;
    private final LocalDate checkOut;

    public LenientReservation(LocalDate checkIn, LocalDate checkOut) {
        this.checkIn = checkIn;
        this.checkOut = checkOut;
    }

    public long priceCents(long perNightCents) {
        return ChronoUnit.DAYS.between(checkIn, checkOut) * perNightCents;   // negative nights -> negative invoice
    }
}

    package com.handbook.principles.other.failfast;

import java.time.LocalDate;
import java.util.Objects;

/** FAIL FAST: an invalid Reservation can never exist, so nothing downstream has to re-check it. */
public record Reservation(String guest, LocalDate checkIn, LocalDate checkOut, int guests) {
    public Reservation {
        Objects.requireNonNull(guest, "guest");
        Objects.requireNonNull(checkIn, "checkIn");
        Objects.requireNonNull(checkOut, "checkOut");
        if (guest.isBlank()) throw new IllegalArgumentException("guest must not be blank");
        if (!checkOut.isAfter(checkIn)) throw new IllegalArgumentException("checkOut " + checkOut + " must be after checkIn " + checkIn);
        if (guests < 1 || guests > 8) throw new IllegalArgumentException("guests must be 1..8 but was " + guests);
    }

    public long nights() { return checkIn.until(checkOut).getDays(); }
}

    package com.handbook.principles.other.failfast;

import java.time.LocalDate;

public class FailFastDemo {
    public static void main(String[] args) {
        LocalDate in = LocalDate.of(2025, 3, 10);
        LocalDate out = LocalDate.of(2025, 3, 7);       // typo: before check-in

        System.out.println("fail slow: price = " + new LenientReservation(in, out).priceCents(5_000) + " cents  <-- refund by accident");
        try {
            new Reservation("Ana", in, out, 2);
        } catch (IllegalArgumentException e) {
            System.out.println("fail fast: " + e.getMessage());
        }
        System.out.println("valid    : " + new Reservation("Ana", in, in.plusDays(3), 2).nights() + " nights");
    }
}

    ✅ Pros ⚠️ Cons / Trade-offs
    Bugs surface near their cause, with a precise message Not always right at system edges. A UI or batch job may prefer to collect all errors (Notification pattern / Bean Validation)
    Invalid objects can't exist, so downstream code needn't re-check Fragile if over-applied to optional or noisy data (for example parsing third-party feeds)
    Spring Boot does it at startup (@ConfigurationProperties + @Validated) Needs good error handling and translation at the boundary (RFC 9457 ProblemDetail)

    JDK examples: Objects.requireNonNull, fail-fast iterators (ConcurrentModificationException), List.of rejecting null, and record compact constructors.

    8. Interview Q&A¶

    DRY vs WET vs AHA, and when is duplication OK?

    WET means "Write Everything Twice" (a violation). AHA means "Avoid Hasty Abstractions" (Kent C. Dodds), and it supports the rule of three. Duplication is fine when the copies represent different knowledge that happens to look the same today, or across service boundaries where a shared library would couple deploys.

    Doesn't YAGNI conflict with OCP?

    They are balanced against each other: write the simplest code now, and when a real second variant arrives, refactor to an abstraction (OCP). Good tests make that refactoring cheap. Design up front only for decisions that are expensive to reverse.

    Is method chaining always a Law of Demeter violation?

    No. LoD is about reaching into the structure of other objects. Fluent builders, streams and Optional chains return the same or a related abstraction, so they don't expose structure. order.getCustomer().getAddress().getCity() does.

    Give a real example where composition beat inheritance.

    java.util.Collections.synchronizedList and unmodifiableList wrap any List instead of subclassing each implementation. Spring's TransactionAwareDataSourceProxy and Java I/O streams (BufferedInputStream(new FileInputStream(...))) work the same way, as Decorators.

    Fail fast vs defensive programming?

    Defensive programming tolerates bad input and tries to continue. Fail fast refuses bad input loudly. Inside your own code, fail fast (invariants, preconditions). At untrusted boundaries, validate everything, collect the errors, and respond gracefully.

    9. Quick Revision Card¶

    Remember in 30 seconds

    • DRY: one home for each piece of knowledge; rule of three; avoid the wrong abstraction.
    • KISS: optimise for the reader; use the standard library.
    • YAGNI: build what's needed now; refactor when the need is real.
    • Composition > inheritance: wrap an interface; avoid fragile base classes.
    • LoD: no train wrecks; fluent chains are fine.
    • Tell, Don't Ask: put the decision where the data is.
    • Fail fast: validate in constructors; collect errors only at UX edges.
