    S: Single Responsibility Principle (SRP)¶

    🟢 Beginner SOLID Interview frequency ⭐⭐⭐⭐⭐

    TL;DR

    A class should have one, and only one, reason to change. Put together the things that change for the same reason, and keep apart the things that change for different reasons.

    1. Definition & Origin¶

    "A module should be responsible to one, and only one, actor." (Robert C. Martin, Clean Architecture, 2017)

    Robert C. Martin coined SRP in the early 2000s, building on the older ideas of cohesion (Tom DeMarco, Meilir Page-Jones) and separation of concerns (Dijkstra). People often misread it as "a class should do one thing". The precise version is about reasons to change: who asks for changes to this code? If finance asks for tax changes, marketing asks for invoice layout changes and ops asks for storage changes, one class serving all three has three reasons to change.

    2. The Problem It Solves¶

    • Merge conflicts and accidental breakage. Two teams editing one class for unrelated reasons step on each other.
    • Fragile tests. To test the tax rule you have to set up printing and a database.
    • No reuse. You can't reuse the printing without dragging the persistence along.
    • Shotgun redeploys. A one-line tax change redeploys printing and storage code that didn't change.

    3. Key Features & How to Spot a Violation¶

    Signal What it tells you
    The class name contains And / Manager / Util / Processor The class has no single concept behind it
    Imports from many unrelated layers (SQL + HTTP + PDF + mail) It touches several actors' concerns
    Methods fall into groups that never use each other's fields Low cohesion: the groups want to be separate classes
    You describe it with "…and…and…" Each "and" is a candidate responsibility
    Unrelated change requests keep landing in the same file That's the textbook symptom

    4. Generic Example: an Invoice¶

    package com.handbook.principles.solid.srp.before;

import com.handbook.principles.solid.srp.LineItem;

import java.util.List;
import java.util.Map;

/**
 * VIOLATES SRP: this class has three reasons to change.
 *   1. the tax rule changes          (business / finance team)
 *   2. the printed layout changes    (UI / reporting team)
 *   3. the storage technology changes (infrastructure team)
 */
public class Invoice {
    private final String number;
    private final List<LineItem> items;

    public Invoice(String number, List<LineItem> items) {
        this.number = number;
        this.items = List.copyOf(items);
    }

    // Responsibility 1: business calculation
    public long totalCents() {
        long subtotal = items.stream().mapToLong(LineItem::totalCents).sum();
        return subtotal + subtotal * 18 / 100;              // 18% tax hard-coded here
    }

    // Responsibility 2: presentation
    public String print() {
        StringBuilder sb = new StringBuilder("INVOICE " + number + "\n");
        for (LineItem i : items) {
            sb.append(String.format("  %-10s x%d  %8.2f%n", i.description(), i.quantity(), i.totalCents() / 100.0));
        }
        return sb.append(String.format("  TOTAL (incl. tax) %8.2f", totalCents() / 100.0)).toString();
    }

    // Responsibility 3: persistence
    public void save(Map<String, String> database) {
        database.put(number, print());                    // storage format coupled to the print layout!
    }
}
    Invoice.java (data + subtotal only)
    package com.handbook.principles.solid.srp.after;

import com.handbook.principles.solid.srp.LineItem;

import java.util.List;

/** Data and the rules that belong to the invoice itself. Its only reason to change: what an invoice IS. */
public record Invoice(String number, List<LineItem> items) {
    public Invoice {
        items = List.copyOf(items);
    }

    public long subtotalCents() {
        return items.stream().mapToLong(LineItem::totalCents).sum();
    }
}
    TaxCalculator.java (changes when finance changes the tax rule)
    package com.handbook.principles.solid.srp.after;

/** Reason to change: the tax rule. */
public class TaxCalculator {
    private final int ratePercent;

    public TaxCalculator(int ratePercent) {
        this.ratePercent = ratePercent;
    }

    public long totalWithTaxCents(Invoice invoice) {
        long subtotal = invoice.subtotalCents();
        return subtotal + subtotal * ratePercent / 100;
    }
}
    InvoicePrinter.java + TextInvoicePrinter.java + CsvInvoicePrinter.java (changes when the layout changes)
    package com.handbook.principles.solid.srp.after;

/** Reason to change: how an invoice looks. A new format means a new printer, not edits to Invoice. */
public interface InvoicePrinter {
    String print(Invoice invoice, long totalCents);
}

    package com.handbook.principles.solid.srp.after;

import com.handbook.principles.solid.srp.LineItem;

/** Added later for the finance team. Invoice, TaxCalculator and the repository were not touched. */
public class CsvInvoicePrinter implements InvoicePrinter {
    @Override
    public String print(Invoice invoice, long totalCents) {
        StringBuilder sb = new StringBuilder("number,description,quantity,line_total_cents\n");
        for (LineItem i : invoice.items()) {
            sb.append(invoice.number()).append(',').append(i.description()).append(',')
              .append(i.quantity()).append(',').append(i.totalCents()).append('\n');
        }
        return sb.append(invoice.number()).append(",TOTAL,,").append(totalCents).toString();
    }
}
    InvoiceRepository.java (changes when storage changes)
    package com.handbook.principles.solid.srp.after;

import java.util.HashMap;
import java.util.Map;
import java.util.Optional;

/** Reason to change: how invoices are stored. Stores the data, not a printed layout. */
public class InvoiceRepository {
    private final Map<String, Invoice> store = new HashMap<>();

    public void save(Invoice invoice) {
        store.put(invoice.number(), invoice);
    }

    public Optional<Invoice> find(String number) {
        return Optional.ofNullable(store.get(number));
    }
}

    package com.handbook.principles.solid.srp;

import com.handbook.principles.solid.srp.after.CsvInvoicePrinter;
import com.handbook.principles.solid.srp.after.InvoicePrinter;
import com.handbook.principles.solid.srp.after.InvoiceRepository;
import com.handbook.principles.solid.srp.after.TaxCalculator;
import com.handbook.principles.solid.srp.after.TextInvoicePrinter;

import java.util.HashMap;
import java.util.List;
import java.util.Map;

public class SrpDemo {
    public static void main(String[] args) {
        List<LineItem> items = List.of(new LineItem("Keyboard", 1, 4_500), new LineItem("Mouse", 2, 1_250));

        System.out.println("--- Before: one class does everything ---");
        var before = new com.handbook.principles.solid.srp.before.Invoice("INV-1", items);
        Map<String, String> db = new HashMap<>();
        before.save(db);
        System.out.println(before.print());
        System.out.println("stored value is the printed text: " + db.get("INV-1").startsWith("INVOICE"));

        System.out.println();
        System.out.println("--- After: one reason to change per class ---");
        var invoice = new com.handbook.principles.solid.srp.after.Invoice("INV-1", items);
        var tax = new TaxCalculator(18);
        var repository = new InvoiceRepository();
        repository.save(invoice);
        long total = tax.totalWithTaxCents(invoice);
        for (InvoicePrinter printer : List.of(new TextInvoicePrinter(), new CsvInvoicePrinter())) {
            System.out.println(printer.print(invoice, total));
            System.out.println();
        }
        System.out.println("tax rule changed to 5%: " + new TaxCalculator(5).totalWithTaxCents(invoice)
                + " cents (no printer or repository edited)");
    }
}

    5. Pros¶

    • High cohesion, low coupling. Each class is small and easy to understand.
    • Cheap, focused tests. You can test TaxCalculator with no printer and no database.
    • Safer change. A change for one actor can't break another actor's feature.
    • Reuse. CsvInvoicePrinter can be used anywhere an Invoice exists.
    • Parallel work. Different people can own different classes without merge conflicts.

    6. Cons & Trade-offs¶

    • More classes and files. Over-applied, you get "class explosion" and have to jump through five files to follow one flow.
    • Indirection. Someone has to wire the pieces together, usually a small service or the DI container.
    • Judgement is needed. "Reason to change" isn't mechanical. Splitting by technical step (validate/save/send) rather than by actor can scatter one business concept across many classes.
    • Premature splitting violates YAGNI. If only one actor ever changes this code, one class is fine.

    7. When to Apply / When Not To¶

    Apply SRP when… Hold off when…
    Different stakeholders change different parts It's a small script or prototype with one owner
    A class has grown past a few hundred lines with method clusters The "responsibilities" always change together
    Tests need unrelated setup Splitting would just move code between files with no independent reason to change

    8. Related Patterns & Frameworks¶

    • Facade puts a single entry point over many single-responsibility classes.
    • Strategy (InvoicePrinter) pulls a varying responsibility out into its own type.
    • Repository isolates persistence. Command gives one action one class.
    • Spring stereotypes (@Controller / @Service / @Repository) are SRP at the layer level.
    • At the architecture level, SRP is the Common Closure Principle and the basis of microservice boundaries.

    9. Interview Q&A¶

    What does 'one reason to change' actually mean?

    One actor (a person, team or stakeholder role) whose requests drive changes to the class. A class with three methods is fine if one actor owns all of them. A class with one method can still violate SRP if two actors fight over it.

    Doesn't SRP lead to too many tiny classes?

    It can, if you split by verb instead of by actor. Split when you see independent change, not in advance. A cohesive class with ten methods for one actor beats ten one-method classes.

    How do you refactor a God class towards SRP?

    1) Group methods by the fields they use (a cohesion analysis). 2) Write characterization tests. 3) Use Extract Class for each group and leave a delegating method behind. 4) Point callers at the new classes. 5) Delete the delegates.

    How does SRP relate to microservices?

    It's the same idea at a larger scale. A service should be owned by one team or bounded context and change for one business reason. Otherwise you get a distributed monolith, where every feature needs coordinated deploys.

    10. Quick Revision Card¶

    Remember in 30 seconds

    • One actor, one reason to change, not "one method".
    • Smells: *Manager/*Util, mixed imports, "and" in the description, unrelated changes in the same file.
    • Fix: Extract Class by actor, then wire the pieces with a thin service or DI.
    • Don't over-split. Wait for real, independent change.
