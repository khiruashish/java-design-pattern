    I: Interface Segregation Principle (ISP)¶

    🟢 Beginner SOLID Interview frequency ⭐⭐⭐⭐

    TL;DR

    Clients should not be forced to depend on methods they do not use. Prefer several small, role-based interfaces to one "fat" interface.

    1. Definition & Origin¶

    "Clients should not be forced to depend upon interfaces that they do not use." (Robert C. Martin, 1996)

    Martin came up with ISP while consulting for Xerox. A single Job class served print, staple and fax jobs, so every small change recompiled and redeployed everything. Splitting it into role interfaces, one per client need, fixed that. ISP is SRP applied to interfaces: SRP is cohesion from the implementer's side, ISP is cohesion from the client's side.

    2. The Problem It Solves¶

    • Implementers forced to stub methods with throw new UnsupportedOperationException(). That's also an LSP violation.
    • Unnecessary coupling. A client that only prints still depends on fax() and is affected when it changes.
    • Bloated test doubles. A mock of a 20-method interface for a test that uses one method.
    • Unclear capabilities. The type system says "can scan" when the object can't.

    3. Key Features & How to Spot a Violation¶

    Signal Fix
    Implementations full of UnsupportedOperationException / empty methods Split the interface by capability
    Each client uses a different subset of methods One interface per client role
    Interfaces named *Service with 15+ unrelated methods Group by use case: OrderReader, OrderWriter…
    Mocks that stub one method out of many The client only needs a narrow role interface

    4. Generic Example: Office Machines¶

    OfficeMachine.java
    package com.handbook.principles.solid.isp.before;

/** VIOLATES ISP: a "fat" interface. Every implementer must provide every capability. */
public interface OfficeMachine {
    String print(String document);

    String scan(String document);

    String fax(String document, String number);
}
    BasicPrinter.java (forced to fake two capabilities)
    package com.handbook.principles.solid.isp.before;

/** A cheap printer is forced to "implement" scanning and faxing it can't do. */
public class BasicPrinter implements OfficeMachine {
    public String print(String document) { return "printed " + document; }

    public String scan(String document) { throw new UnsupportedOperationException("BasicPrinter cannot scan"); }

    public String fax(String document, String number) { throw new UnsupportedOperationException("BasicPrinter cannot fax"); }
}
    Printer / Scanner / Fax
    package com.handbook.principles.solid.isp.after;

public interface Printer {
    String print(String document);
}

    package com.handbook.principles.solid.isp.after;

public interface Scanner {
    String scan(String document);
}

    package com.handbook.principles.solid.isp.after;

public interface Fax {
    String fax(String document, String number);
}
    BasicPrinter.java / MultiFunctionDevice.java
    package com.handbook.principles.solid.isp.after;

/** Implements only what it can actually do. No UnsupportedOperationException anywhere. */
public class BasicPrinter implements Printer {
    public String print(String document) { return "printed " + document; }
}

    package com.handbook.principles.solid.isp.after;

/** A device that really does everything simply implements all the small interfaces. */
public class MultiFunctionDevice implements Printer, Scanner, Fax {
    public String print(String document) { return "printed " + document; }

    public String scan(String document) { return "scanned " + document; }

    public String fax(String document, String number) { return "faxed " + document + " to " + number; }
}
    PrintJob.java (a client that needs only Printer)
    package com.handbook.principles.solid.isp.after;

import java.util.List;

/** A client that only prints depends only on Printer, so it accepts any device that can print. */
public class PrintJob {
    public String run(Printer printer, List<String> documents) {
        return String.join(", ", documents.stream().map(printer::print).toList());
    }
}

    package com.handbook.principles.solid.isp;

import com.handbook.principles.solid.isp.after.BasicPrinter;
import com.handbook.principles.solid.isp.after.MultiFunctionDevice;
import com.handbook.principles.solid.isp.after.PrintJob;
import com.handbook.principles.solid.isp.after.Scanner;

import java.util.List;

public class IspDemo {
    public static void main(String[] args) {
        System.out.println("--- Before: one fat interface ---");
        com.handbook.principles.solid.isp.before.OfficeMachine machine = new com.handbook.principles.solid.isp.before.BasicPrinter();
        System.out.println(machine.print("report.pdf"));
        try {
            machine.scan("photo.jpg");       // compiles fine, fails at runtime
        } catch (UnsupportedOperationException e) {
            System.out.println("runtime surprise: " + e.getMessage());
        }

        System.out.println();
        System.out.println("--- After: small role interfaces ---");
        PrintJob job = new PrintJob();
        System.out.println("basic printer: " + job.run(new BasicPrinter(), List.of("a.pdf", "b.pdf")));
        System.out.println("MFD          : " + job.run(new MultiFunctionDevice(), List.of("a.pdf")));
        Scanner scanner = new MultiFunctionDevice();
        System.out.println("scanner role : " + scanner.scan("photo.jpg"));
        System.out.println("(asking a BasicPrinter to scan is now a compile error, not a runtime exception)");
    }
}

BasicPrinter Printer <|.. MultiFunctionDevice Scanner <|.. MultiFunctionDevice Fax <|.. MultiFunctionDevice PrintJob ..> Printer : needs only

    Output:

    --- Before: one fat interface ---
printed report.pdf
runtime surprise: BasicPrinter cannot scan

--- After: small role interfaces ---
basic printer: printed a.pdf, printed b.pdf
MFD          : printed a.pdf
scanner role : scanned photo.jpg
(asking a BasicPrinter to scan is now a compile error, not a runtime exception)

    5. Pros¶

    • Errors move from runtime to compile time. You can't call scan() on something that can't scan.
    • Less coupling. Clients recompile and retest only when their role changes.
    • Simple test doubles. A one-method interface is a lambda.
    • Clearer intent. Method parameters say exactly what capability they need (Printer, not OfficeMachine).

    6. Cons & Trade-offs¶

    • Interface proliferation. Too many one-method interfaces fragment the model and make it harder to discover.
    • Implementations still have to be coherent. A class implementing 8 small interfaces may be breaking SRP instead.
    • API stability. For a public library, a broader, stable interface can be easier to evolve, using default methods.
    • Aggregation is sometimes handy. You can keep interface OfficeMachine extends Printer, Scanner, Fax {} for clients that really need all three.

    7. When to Apply / When Not To¶

    Split an interface when different clients use different subsets or when implementers start stubbing methods. Don't split a cohesive interface that every client uses entirely (such as Iterator's hasNext/next).

    8. Related Patterns & Frameworks¶

    • Adapter can expose a narrow role over a wide class. Facade is the client-side aggregation of roles.
    • Proxy and Decorator are easier to write over small interfaces.
    • JDK: Readable/Appendable/Closeable/AutoCloseable, java.util.function.*, Comparable.
    • Spring Data: Repository → CrudRepository → ListCrudRepository. You can extend just Repository and declare only the methods you need.
    • CQRS applies ISP at the architecture level: read and write models are separate interfaces.

    9. Interview Q&A¶

    ISP vs SRP?

    SRP: an implementation should have one reason to change. ISP: a client shouldn't depend on methods it doesn't use. They often lead to the same split, seen from opposite sides.

    How do default methods affect ISP?

    default methods let you add to an interface without breaking implementers, which helps library evolution. But they can hide fat interfaces. A default that throws UnsupportedOperationException is still an ISP/LSP smell.

    Show ISP in a Spring codebase.

    Split a huge UserService into UserQueries (read) and UserCommands (write). One bean implements both. The read-only controller injects UserQueries, so it can't call a mutating method by accident, and its test needs only a read stub.

    10. Quick Revision Card¶

    Remember in 30 seconds

    • No client should depend on methods it doesn't use.
    • Smell: UnsupportedOperationException stubs; fat *Service interfaces; huge mocks.
    • Fix: role interfaces, implemented together where needed.
    • Don't go too far: avoid fragmenting a cohesive interface.
