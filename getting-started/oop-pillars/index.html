    Beginner OOP

    The Four Pillars of OOP¶

    🟢 Beginner Foundations Interview frequency ⭐⭐⭐⭐⭐

    TL;DR

    Encapsulation protects state, Abstraction hides complexity behind a contract, Inheritance reuses and specialises behaviour, and Polymorphism lets one call do different things depending on the object. Every design pattern in this handbook is a combination of these four.

    flowchart LR E[🔒 Encapsulation<br/>protect invariants] --> A[🎭 Abstraction<br/>depend on what, not how] A --> P[🔀 Polymorphism<br/>one call, many behaviours] I[🧬 Inheritance<br/>is-a reuse] --> P P --> DP[Design patterns<br/>Strategy, State, Decorator, …]
    Pillar Question it answers Java tools Overuse risk
    Encapsulation Who can change this state, and how? private, validated methods, immutable records, defensive copies Getter/setter-only classes (anemic)
    Abstraction What does the caller need to know? interface, abstract class, modules Abstractions with one implementation forever
    Inheritance What is shared, and what is specialised? extends, abstract, final, sealed Fragile base classes, deep hierarchies
    Polymorphism Which behaviour runs for this object? Overriding, overloading, generics, switch patterns Clever dispatch that's hard to follow

    1. Encapsulation¶

    Definition. Bundle data with the operations on it, and hide the internal state so it can only change through methods that enforce the object's rules (its invariants). Encapsulation is about protecting invariants, not just about making fields private and adding getters and setters.

    Key features: private fields; behaviour methods instead of setters; validation in the constructor and methods; immutable or read-only views of internal collections (List.copyOf, unmodifiableList); package-private helpers.

    package com.handbook.principles.oop.encapsulation;

import java.util.ArrayList;
import java.util.Collections;
import java.util.List;

/**
 * Encapsulation: state is private and can only change through methods that protect the invariant
 * "balance is never negative". Callers cannot reach in and set the balance directly.
 */
public class BankAccount {
    private final String id;
    private long balanceCents;
    private final List<String> history = new ArrayList<>();

    public BankAccount(String id, long openingCents) {
        if (openingCents < 0) throw new IllegalArgumentException("opening balance must be >= 0");
        this.id = id;
        this.balanceCents = openingCents;
        history.add("open " + openingCents);
    }

    public void deposit(long cents) {
        if (cents <= 0) throw new IllegalArgumentException("deposit must be positive");
        balanceCents += cents;
        history.add("deposit " + cents);
    }

    public void withdraw(long cents) {
        if (cents <= 0) throw new IllegalArgumentException("withdrawal must be positive");
        if (cents > balanceCents) throw new IllegalStateException("insufficient funds: balance " + balanceCents + ", requested " + cents);
        balanceCents -= cents;
        history.add("withdraw " + cents);
    }

    public long balanceCents() { return balanceCents; }

    public String id() { return id; }

    /** Read-only view: callers can look at the history but cannot rewrite it. */
    public List<String> history() { return Collections.unmodifiableList(history); }
}

    package com.handbook.principles.oop.encapsulation;

public class EncapsulationDemo {
    public static void main(String[] args) {
        BankAccount account = new BankAccount("ACC-1", 10_000);
        account.deposit(2_500);
        account.withdraw(4_000);
        System.out.println("balance = " + account.balanceCents());
        try {
            account.withdraw(1_000_000);
        } catch (IllegalStateException e) {
            System.out.println("rejected: " + e.getMessage());
        }
        try {
            account.history().add("withdraw 999999");
        } catch (UnsupportedOperationException e) {
            System.out.println("history is read-only to callers");
        }
        System.out.println("history = " + account.history());
    }
}

    balance = 8500
rejected: insufficient funds: balance 8500, requested 1000000
history is read-only to callers
history = [open 10000, deposit 2500, withdraw 4000]
    ✅ Pros ⚠️ Cons / Trade-offs
    Invariants can't be broken from outside, so there are fewer "impossible" states More methods to write than with public fields
    You can change the internal representation without affecting callers Too much hiding can make debugging and serialization awkward
    One place to add validation, logging or thread-safety Frameworks (JPA, Jackson) sometimes want no-arg constructors or setters, so you have to balance purity against tooling

    Pitfall: leaking mutable internals

    public List<String> getHistory() { return history; } lets callers change the list and bypass every rule. Return an unmodifiable view or a copy, and copy incoming mutable arguments.

    2. Abstraction¶

    Definition. Expose what something does and hide how it does it. Callers depend on a simplified model (an interface or abstract class), and the complexity lives behind it.

    Key features: interfaces or abstract classes as contracts; names in the caller's language (put, get), not the implementation's (gzipThenWriteToBucket); implementations you can swap.

    FileStorage.java
    package com.handbook.principles.oop.abstraction;

import java.util.Optional;

/** Abstraction: callers see WHAT storage does, not HOW (disk, memory, S3...). */
public interface FileStorage {
    void put(String key, byte[] content);

    Optional<byte[]> get(String key);

    String describe();
}
    ReportArchiver.java (client knows only the abstraction)
    package com.handbook.principles.oop.abstraction;

import java.nio.charset.StandardCharsets;

/** Client written against the abstraction only. */
public class ReportArchiver {
    private final FileStorage storage;

    public ReportArchiver(FileStorage storage) { this.storage = storage; }

    public String archiveAndReadBack(String name, String body) {
        storage.put(name, body.getBytes(StandardCharsets.UTF_8));
        return storage.get(name).map(b -> new String(b, StandardCharsets.UTF_8)).orElse("<missing>");
    }
}
    InMemoryStorage.java
    package com.handbook.principles.oop.abstraction;

import java.util.HashMap;
import java.util.Map;
import java.util.Optional;

public class InMemoryStorage implements FileStorage {
    private final Map<String, byte[]> files = new HashMap<>();

    public void put(String key, byte[] content) { files.put(key, content.clone()); }

    public Optional<byte[]> get(String key) { return Optional.ofNullable(files.get(key)).map(byte[]::clone); }

    public String describe() { return "in-memory (" + files.size() + " files)"; }
}
    CompressingStorage.java
    package com.handbook.principles.oop.abstraction;

import java.io.ByteArrayInputStream;
import java.io.ByteArrayOutputStream;
import java.io.IOException;
import java.io.UncheckedIOException;
import java.util.Optional;
import java.util.zip.GZIPInputStream;
import java.util.zip.GZIPOutputStream;

/** A very different implementation hidden behind the same abstraction: gzip on the way in, gunzip on the way out. */
public class CompressingStorage implements FileStorage {
    private final FileStorage delegate;

    public CompressingStorage(FileStorage delegate) { this.delegate = delegate; }

    public void put(String key, byte[] content) {
        ByteArrayOutputStream out = new ByteArrayOutputStream();
        try (GZIPOutputStream gz = new GZIPOutputStream(out)) {
            gz.write(content);
        } catch (IOException e) {
            throw new UncheckedIOException(e);
        }
        delegate.put(key, out.toByteArray());
    }

    public Optional<byte[]> get(String key) {
        return delegate.get(key).map(bytes -> {
            try (GZIPInputStream gz = new GZIPInputStream(new ByteArrayInputStream(bytes))) {
                return gz.readAllBytes();
            } catch (IOException e) {
                throw new UncheckedIOException(e);
            }
        });
    }

    public String describe() { return "gzip over " + delegate.describe(); }
}

    package com.handbook.principles.oop.abstraction;

public class AbstractionDemo {
    public static void main(String[] args) {
        String body = "Q3 revenue report. ".repeat(3);
        for (FileStorage storage : new FileStorage[]{new InMemoryStorage(), new CompressingStorage(new InMemoryStorage())}) {
            String readBack = new ReportArchiver(storage).archiveAndReadBack("q3.txt", body);
            System.out.println(storage.describe() + " -> round trip ok: " + readBack.equals(body));
        }
    }
}

    in-memory (1 files) -> round trip ok: true
gzip over in-memory (1 files) -> round trip ok: true
    ✅ Pros ⚠️ Cons / Trade-offs
    Callers stay simple and stable Every abstraction leaks eventually (Joel Spolsky's "Law of Leaky Abstractions"), for example the latency of remote storage
    Implementations can be swapped (memory, disk, S3, compressed) Too many layers make the code hard to follow
    Enables DIP and testing with fakes A poor abstraction is worse than none: it constrains every implementation

    Encapsulation vs Abstraction: encapsulation hides data to protect it; abstraction hides complexity to simplify use. BankAccount is mainly encapsulation; FileStorage is mainly abstraction.

    3. Inheritance¶

    Definition. A subclass reuses and specialises a parent class (an "is-a" relationship). The subclass inherits fields and methods, can override behaviour, and can be used wherever the parent is expected (see LSP).

    Key features: extends (a single class), abstract hooks, protected members for subclasses, final to forbid overriding, sealed to restrict who may extend, and super(...) constructor chaining.

    Vehicle.java (template method + abstract hook)
    package com.handbook.principles.oop.inheritance;

/**
 * Inheritance: shared state and behaviour live in the base class; subclasses specialise.
 * The template method describe() is final so subclasses can't break the format, only fill in the hook.
 */
public abstract class Vehicle {
    private final String plate;
    private final int wheels;

    protected Vehicle(String plate, int wheels) {
        this.plate = plate;
        this.wheels = wheels;
    }

    /** Hook that subclasses must provide. */
    protected abstract long tollCents();

    public final String describe() {
        return getClass().getSimpleName() + " " + plate + " (" + wheels + " wheels) toll=" + tollCents();
    }
}

    package com.handbook.principles.oop.inheritance;

public class Car extends Vehicle {
    public Car(String plate) { super(plate, 4); }

    @Override
    protected long tollCents() { return 250; }
}

    package com.handbook.principles.oop.inheritance;

public class Truck extends Vehicle {
    private final int axles;

    public Truck(String plate, int axles) {
        super(plate, axles * 2 + 2);
        this.axles = axles;
    }

    @Override
    protected long tollCents() { return 400L * axles; }   // specialised rule
}

    package com.handbook.principles.oop.inheritance;

import java.util.List;

public class InheritanceDemo {
    public static void main(String[] args) {
        List<Vehicle> lane = List.of(new Car("KA-01-1234"), new Truck("MH-12-9876", 3));
        lane.forEach(v -> System.out.println(v.describe()));
    }
}

    Car KA-01-1234 (4 wheels) toll=250
Truck MH-12-9876 (8 wheels) toll=1200
    classDiagram class Vehicle { <<abstract>> -String plate -int wheels #tollCents()* long +describe() String } Vehicle <|-- Car Vehicle <|-- Truck class Truck { -int axles }
    ✅ Pros ⚠️ Cons / Trade-offs
    Shared code is written once Tight coupling. Subclasses depend on parent internals (the fragile base class problem)
    Natural for true "is-a" taxonomies Single inheritance only; deep trees become rigid
    Template Method gives controlled extension points Easy to break LSP; changes in the parent ripple to every child

    Pitfall: the fragile base class

    A subclass that overrides methods the parent calls internally depends on implementation details. The classic case is InstrumentedHashSet extends HashSet, which counts elements twice because addAll calls add. See the runnable demo under Composition over Inheritance. Design for inheritance (document self-use, make hooks protected abstract, make the rest final) or forbid it.

    4. Polymorphism¶

    Definition. "Many forms": the same call produces different behaviour depending on the type.

    Kind Resolved at Java mechanism
    Subtype (runtime) Run time (dynamic dispatch) Overriding methods from an interface or superclass
    Ad-hoc (compile time) Compile time Method overloading: same name, different parameter types
    Parametric Compile time Generics (List<T>)
    Pattern-based (Java 21) Run time, checked at compile time switch with type patterns over a sealed hierarchy
    Payment.java (sealed, each subtype overrides feeCents)
    package com.handbook.principles.oop.polymorphism;

/** Sealed hierarchy: the compiler knows every subtype, enabling exhaustive switch (Java 21). */
public sealed interface Payment permits Payment.Card, Payment.Upi, Payment.Cash {

    long amountCents();

    /** Runtime (subtype) polymorphism: each subtype overrides fee(). */
    long feeCents();

    record Card(long amountCents, String last4) implements Payment {
        public long feeCents() { return amountCents * 2 / 100; }       // 2%
    }

    record Upi(long amountCents, String vpa) implements Payment {
        public long feeCents() { return 0; }
    }

    record Cash(long amountCents) implements Payment {
        public long feeCents() { return 0; }
    }
}
    Receipt.java (overloading + exhaustive switch)
    package com.handbook.principles.oop.polymorphism;

/** Compile-time (ad-hoc) polymorphism: overloading picks a method by the static argument types. */
public final class Receipt {
    private Receipt() { }

    public static String line(String label, long cents) { return label + ": " + cents + " cents"; }

    public static String line(String label, double percent) { return label + ": " + percent + "%"; }

    /** Pattern-matching switch over a sealed type: no default branch needed, adding a subtype is a compile error here. */
    public static String channel(Payment p) {
        return switch (p) {
            case Payment.Card c -> "card ending " + c.last4();
            case Payment.Upi u -> "UPI " + u.vpa();
            case Payment.Cash cash -> "cash";
        };
    }
}

    package com.handbook.principles.oop.polymorphism;

import java.util.List;

public class PolymorphismDemo {
    public static void main(String[] args) {
        List<Payment> payments = List.of(new Payment.Card(10_000, "4242"), new Payment.Upi(5_000, "ana@bank"), new Payment.Cash(700));
        for (Payment p : payments) {
            System.out.println(Receipt.channel(p) + " | " + Receipt.line("amount", p.amountCents()) + " | " + Receipt.line("fee", p.feeCents()));
        }
        System.out.println(Receipt.line("card fee rate", 2.0));
    }
}

    card ending 4242 | amount: 10000 cents | fee: 200 cents
UPI ana@bank | amount: 5000 cents | fee: 0 cents
cash | amount: 700 cents | fee: 0 cents
card fee rate: 2.0%
    ✅ Pros ⚠️ Cons / Trade-offs
    Removes if/else type checks, which enables OCP Behaviour is spread across classes, so "what runs here?" needs an IDE
    New subtypes plug in without changing callers Overloading combined with autoboxing or varargs can pick surprising methods
    A sealed + switch makes the compiler check every case Virtual dispatch is slightly slower (the JIT usually removes it)

    5. Interview Q&A¶

    Encapsulation vs abstraction: what's the difference?

    Encapsulation is about hiding data and enforcing invariants (private fields plus validated methods). Abstraction is about hiding complexity behind a contract (an interface). A class can show both: FileStorage abstracts how files are stored; BankAccount encapsulates its balance.

    Is a class with private fields and public getters/setters encapsulated?

    Barely. If every field has a setter, any caller can put the object in an invalid state. Real encapsulation exposes behaviour (withdraw, deposit) that keeps the invariants, and avoids unconditional setters.

    Overloading vs overriding?

    Overloading means the same name with different parameters in the same class, chosen at compile time from static types. Overriding means the same signature in a subclass, chosen at run time from the object's real type. Static, private and final methods can't be overridden.

    Why is 'favour composition over inheritance' so common?

    Inheritance couples the child to the parent's implementation and fixes the relationship at compile time. Composition couples only to an interface, can be changed at run time, and can combine several behaviours. Use inheritance for real "is-a" relationships that you designed for extension.

    Abstract class vs interface in modern Java?

    Interfaces can have default, static and private methods but no instance state. Abstract classes can hold state and constructors and protected members, but a class can extend only one. Use an interface for a capability or contract, and an abstract class for a partial implementation that shares state, such as a Template Method base.

    6. Quick Revision Card¶

    Remember in 30 seconds

    • Encapsulation: protect invariants; expose behaviour, not setters; avoid leaking mutable internals.
    • Abstraction: depend on what, not how; interfaces at boundaries.
    • Inheritance: real "is-a" only; design for it or mark it final; beware the fragile base class.
    • Polymorphism: overriding (runtime), overloading (compile time), generics, sealed + switch (exhaustive).
