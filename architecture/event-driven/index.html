    Architecture Intermediate

    Event-Driven Architecture¶

    🟡 Intermediate Architecture Interview frequency ⭐⭐⭐⭐⭐

    TL;DR

    Components communicate by producing and reacting to events (facts about something that happened: OrderPlaced, MeterReading, CardSwiped) through a broker, instead of calling each other directly. Producers don't know their consumers, so new reactions can be added without touching existing code, and work happens asynchronously and in parallel. The cost: eventual consistency, harder debugging, and the need for idempotency, ordering and error-handling strategies.

    1. Intent & Problem It Solves¶

    The problem in plain English: after an order is placed, the order service synchronously calls inventory, loyalty, email, analytics and the recommendation engine. Every new feature adds a call; if the email service is slow, checkout is slow; if analytics is down, orders fail. The order service has become a coordinator of things that aren't its business.

    Definition (Martin Fowler, "What do you mean by Event-Driven?"): event-driven covers several distinct patterns:

    Style What the event carries Example
    Event notification "Something happened" + an ID; consumers call back if they need more OrderPlaced{orderId}
    Event-carried state transfer The data consumers need, so they don't call back CustomerAddressChanged{id, address}
    Event sourcing Events are the system of record Account ledger (see Event Sourcing)
    CQRS Events feed read models See CQRS

    Topologies: broker (choreography: everyone publishes and subscribes) vs. mediator (an orchestrator routes events through steps).

    2. Real-World Analogy¶

    A newspaper vs. phone calls

    The order team could phone every department after each sale (synchronous calls). Instead it publishes a newsletter (event); every department subscribes and decides what to do. New departments subscribe without the order team even knowing. If a department is on holiday, the newsletters wait in its mailbox.

    3. Structure¶

    flowchart LR
    P[Order service<br/>producer] -->|OrderPlaced| T[[orders topic]]
    T --> G1[inventory group]
    T --> G2[loyalty group]
    T --> G3[email group<br/>2 instances]
    T --> G4[analytics group<br/>added later]
    Concept Meaning
    Event Immutable fact, past tense, with ID and timestamp
    Topic / channel Named stream of events
    Consumer group Each group receives every event; members of a group share the work
    Partition / key Ordering scope (all events for an order in one partition)
    Dead-letter queue Where events go after repeated processing failures

    4. Naive Approach (Without the Pattern)¶

    public Order placeOrder(Cart cart) {
    Order order = orders.save(Order.from(cart));
    inventoryClient.reserve(order);        // slow? checkout is slow
    loyaltyClient.addPoints(order);        // down? checkout fails
    emailClient.sendReceipt(order);
    analyticsClient.track(order);          // every new feature = change here + redeploy
    return order;
}

    5. Three Real-World Examples¶

    Example 1: OrderPlaced Fan-Out with Consumer Groups (Grocery)¶

    Scenario: The order service publishes OrderPlaced. Inventory, loyalty and email each have their own consumer group; the email group has two instances sharing the work (competing consumers). Later the analytics team adds a group, and the order service doesn't change at all.

    Full Code:

    package com.handbook.architecture.eventdriven.broker;

import java.util.ArrayList;
import java.util.LinkedHashMap;
import java.util.List;
import java.util.Map;
import java.util.function.Consumer;

/**
 * A tiny in-process broker with Kafka-like consumer groups: every GROUP receives every event
 * (publish-subscribe), and within a group the events are spread across its members (competing
 * consumers). Synchronous for readability; real brokers are asynchronous and durable.
 */
public final class MiniBroker {

    private record Group(List<Consumer<Object>> members, int[] next) {
    }

    private final Map<String, Map<String, Group>> topics = new LinkedHashMap<>();

    @SuppressWarnings("unchecked")
    public <E> void subscribe(String topic, String group, Consumer<E> member) {
        topics.computeIfAbsent(topic, t -> new LinkedHashMap<>())
                .computeIfAbsent(group, g -> new Group(new ArrayList<>(), new int[1]))
                .members().add(e -> member.accept((E) e));
    }

    public void publish(String topic, Object event) {
        System.out.println("[" + topic + "] " + event);
        topics.getOrDefault(topic, Map.of()).forEach((groupName, g) -> {
            int i = g.next()[0]++ % g.members().size(); // (1)!
            g.members().get(i).accept(event);
        });
    }
}
    1. Within a group, events are spread across members (Kafka assigns partitions; here, round-robin). Across groups, everyone gets every event.
    package com.handbook.architecture.eventdriven.grocery;

import com.handbook.architecture.eventdriven.broker.MiniBroker;

public class OrderEventsDemo {

    record OrderPlaced(String orderId, String customerId, long totalPaise) {
    }

    public static void main(String[] args) {
        MiniBroker broker = new MiniBroker();

        // Each consumer group owns its own reaction. The producer knows none of them.
        broker.<OrderPlaced>subscribe("orders", "inventory", e -> System.out.println("    inventory     : reserve stock for " + e.orderId()));
        broker.<OrderPlaced>subscribe("orders", "loyalty", e -> System.out.println("    loyalty       : +" + e.totalPaise() / 10_000 + " points to " + e.customerId()));
        broker.<OrderPlaced>subscribe("orders", "email", e -> System.out.println("    email-1       : receipt for " + e.orderId()));
        broker.<OrderPlaced>subscribe("orders", "email", e -> System.out.println("    email-2       : receipt for " + e.orderId()));

        System.out.println("=== Grocery: OrderPlaced fan-out to independent consumers ===");
        broker.publish("orders", new OrderPlaced("ORD-1", "CUST-42", 144_700));
        broker.publish("orders", new OrderPlaced("ORD-2", "CUST-77", 64_900));

        System.out.println("-- analytics team adds a consumer; the order service is not touched --");
        broker.<OrderPlaced>subscribe("orders", "analytics", e -> System.out.println("    analytics     : basket value " + e.totalPaise() / 100));
        broker.publish("orders", new OrderPlaced("ORD-3", "CUST-42", 12_900));
    }
}

    Why event-driven here:

    • Decoupling: the producer doesn't know or wait for consumers.
    • Extensibility: new consumers without changing the producer.
    • Scalability: add instances to a group to process faster.

    Example 2: Windowed Stream Processing of Smart Meters (Energy)¶

    Scenario: Millions of smart meters stream power readings. The platform computes 5-minute tumbling windows per meter by event time (when the reading was taken, not when it arrived), so a late reading still lands in the right window. When the watermark passes a window's end, the window closes, its average is emitted, and an overload alert fires above 6 kW.

    Full Code:

    package com.handbook.architecture.eventdriven.iot;

import java.util.ArrayList;
import java.util.List;
import java.util.Map;
import java.util.TreeMap;

/**
 * Stream processing on smart-meter readings: group events into 5-minute tumbling windows per meter
 * (by EVENT time, not arrival time), emit the average when a window closes, and raise an alert
 * when the average crosses a threshold.
 */
public final class MeterWindowing {

    public record Reading(String meter, long epochSecond, double kw) {
    }

    public record WindowResult(String meter, long windowStart, double avgKw, boolean alert) {
    }

    private final long windowSeconds;
    private final double alertKw;
    private final Map<String, TreeMap<Long, List<Double>>> open = new TreeMap<>();

    public MeterWindowing(long windowSeconds, double alertKw) {
        this.windowSeconds = windowSeconds;
        this.alertKw = alertKw;
    }

    public void accept(Reading r) {
        long windowStart = r.epochSecond() - r.epochSecond() % windowSeconds; // (1)!
        open.computeIfAbsent(r.meter(), m -> new TreeMap<>())
                .computeIfAbsent(windowStart, w -> new ArrayList<>()).add(r.kw());
    }

    /** Close every window that ended before the watermark (how far event time has progressed). */
    public List<WindowResult> advanceWatermark(long watermark) { // (2)!
        List<WindowResult> closed = new ArrayList<>();
        open.forEach((meter, windows) -> {
            while (!windows.isEmpty() && windows.firstKey() + windowSeconds <= watermark) {
                var w = windows.pollFirstEntry();
                double avg = w.getValue().stream().mapToDouble(Double::doubleValue).average().orElse(0);
                closed.add(new WindowResult(meter, w.getKey(), Math.round(avg * 100) / 100.0, avg > alertKw));
            }
        });
        return closed;
    }
}
    1. The window is chosen from the event's own timestamp, which is what makes late arrivals land correctly.
    2. The watermark says "no more events older than this are expected"; windows that end before it are final.
    package com.handbook.architecture.eventdriven.iot;

import com.handbook.architecture.eventdriven.iot.MeterWindowing.Reading;

import java.time.Instant;
import java.time.ZoneOffset;
import java.util.List;

public class SmartMeterDemo {

    public static void main(String[] args) {
        long t0 = Instant.parse("2026-10-14T18:00:00Z").getEpochSecond();
        var stream = new MeterWindowing(300, 6.0);

        List<Reading> readings = List.of(
                new Reading("M-17", t0 + 10, 2.1), new Reading("M-17", t0 + 130, 2.5),
                new Reading("M-42", t0 + 40, 5.8), new Reading("M-42", t0 + 200, 7.4),
                new Reading("M-17", t0 + 320, 3.0),
                new Reading("M-17", t0 + 250, 2.3),   // arrives late, but belongs to the first window
                new Reading("M-42", t0 + 410, 4.2));

        System.out.println("=== Energy: 5-minute windows over smart-meter events ===");
        readings.forEach(stream::accept);
        for (long watermark : new long[] {t0 + 300, t0 + 600}) {
            System.out.println("watermark " + time(watermark) + ":");
            stream.advanceWatermark(watermark).forEach(w -> System.out.printf("  %s window %s avg %.2f kW%s%n",
                    w.meter(), time(w.windowStart()), w.avgKw(), w.alert() ? "  ALERT: possible overload" : ""));
        }
    }

    private static String time(long epochSecond) {
        return Instant.ofEpochSecond(epochSecond).atOffset(ZoneOffset.UTC).toLocalTime().toString();
    }
}

    Example 3: Real-Time Fraud Detection (Banking)¶

    Scenario: Complex event processing (CEP) looks for patterns across events. Per card, the detector remembers the last swipe; a swipe in a different city within 60 minutes triggers an "impossible travel" alert in real time, before the next transaction is approved.

    Full Code:

    package com.handbook.architecture.eventdriven.fraud;

import java.time.Duration;
import java.time.Instant;
import java.util.HashMap;
import java.util.Map;
import java.util.Optional;

/**
 * Complex event processing: look for a PATTERN across events for the same card. Two transactions in
 * different cities within a short time is "impossible travel", a classic fraud signal.
 */
public final class ImpossibleTravelDetector {

    public record CardSwiped(String card, String city, Instant at, long paise) {
    }

    private final Duration window;
    private final Map<String, CardSwiped> lastByCard = new HashMap<>(); // (1)!

    public ImpossibleTravelDetector(Duration window) {
        this.window = window;
    }

    public Optional<String> onEvent(CardSwiped e) {
        CardSwiped previous = lastByCard.put(e.card(), e);
        if (previous != null && !previous.city().equals(e.city())
                && Duration.between(previous.at(), e.at()).compareTo(window) < 0) { // (2)!
            return Optional.of("FRAUD ALERT " + e.card() + ": " + previous.city() + " then " + e.city()
                    + " within " + Duration.between(previous.at(), e.at()).toMinutes() + " min");
        }
        return Optional.empty();
    }
}
    1. Per-key state: with Kafka Streams this is a state store, partitioned by card number so each instance holds the state for its cards.
    2. The pattern: different city + short time gap.
    package com.handbook.architecture.eventdriven.fraud;

import com.handbook.architecture.eventdriven.fraud.ImpossibleTravelDetector.CardSwiped;

import java.time.Duration;
import java.time.Instant;
import java.util.List;

public class FraudDetectionDemo {

    public static void main(String[] args) {
        var detector = new ImpossibleTravelDetector(Duration.ofMinutes(60));
        Instant t = Instant.parse("2026-10-14T09:00:00Z");

        System.out.println("=== Banking: real-time fraud detection on card events ===");
        for (CardSwiped e : List.of(
                new CardSwiped("CARD-1", "Bengaluru", t, 45_000),
                new CardSwiped("CARD-2", "Mumbai", t.plusSeconds(60), 120_000),
                new CardSwiped("CARD-1", "Bengaluru", t.plusSeconds(600), 9_900),
                new CardSwiped("CARD-1", "Delhi", t.plusSeconds(1_500), 2_499_900),
                new CardSwiped("CARD-2", "Pune", t.plusSeconds(4 * 3_600), 30_000))) {
            String verdict = detector.onEvent(e).orElse("ok");
            System.out.printf("%s %-9s %s ₹%,d -> %s%n", e.card(), e.city(), e.at().toString().substring(11, 16),
                    e.paise() / 100, verdict);
        }
    }
}

    Output:

    === Banking: real-time fraud detection on card events ===
CARD-1 Bengaluru 09:00 ₹450 -> ok
CARD-2 Mumbai    09:01 ₹1,200 -> ok
CARD-1 Bengaluru 09:10 ₹99 -> ok
CARD-1 Delhi     09:25 ₹24,999 -> FRAUD ALERT CARD-1: Bengaluru then Delhi within 15 min

    • Fraud must be caught in seconds; batch analysis the next day is too late.
    • New fraud rules are new consumers of the same card-event stream.

    Kafka Durable log, partitions, consumer groups, replay; the default for event streaming
    RabbitMQ Flexible routing (exchanges), per-message acks; great for work queues
    Cloud (SNS/SQS, EventBridge, Pub/Sub, Event Hubs) Managed brokers and routing
    Kafka Streams / Flink Stateful stream processing, windows, joins
    CloudEvents Standard event envelope (id, source, type, time)
    Spring Cloud Stream Binder abstraction over Kafka/RabbitMQ

    7. Where It Lives in Real Frameworks¶

    Where Event-driven
    Spring ApplicationEventPublisher / @EventListener In-process events
    Spring Kafka, Spring AMQP, Spring Cloud Stream Broker-based messaging
    Kafka Streams, Apache Flink Stream processing and CEP
    Debezium Database changes as events
    UI frameworks (Swing, JavaFX, browsers) Event loops and listeners (Observer)

    8. Pros, Cons & Trade-offs¶

    ✅ Pros ❌ Cons
    Loose coupling between producers and consumers Eventual consistency; harder to reason about
    Easy to add consumers; replay history (Kafka) Debugging flows across services needs tracing
    Absorbs load spikes (queues buffer) Duplicates, ordering and poison messages must be handled
    Natural fit for real-time analytics Schema evolution of events is a long-term commitment

    9. Pitfalls & Anti-Patterns¶

    Event-driven spaghetti

    Dozens of services reacting to each other's events with no one owning end-to-end flows. Document event flows, give business processes owners, and use orchestration for complex workflows (see Saga).

    Poison messages blocking a partition

    One event that always fails, retried forever, stops everything behind it. Bounded retries + a dead-letter queue (see the coding challenge).

    Commands disguised as events

    SendEmailToCustomer isn't a fact; it's an instruction to one recipient. Use events for facts ("OrderShipped") and commands for requests, and be explicit.

    No schema governance

    Changing an event's fields breaks consumers you didn't know about. Use a schema registry with compatibility rules (Avro/Protobuf/JSON Schema).

    10. Senior / Architect Deep Dive (10–15 yrs)¶

    Delivery guarantees. Kafka gives at-least-once by default; design consumers to be idempotent and producers to publish via the outbox. Ordering holds per partition only, so choose keys (order ID, card number) to match your ordering needs.

    Notification vs. state transfer. Thin notifications cause callback storms ("event, then 10 services call GET /orders/{id}"); fat events reduce coupling at runtime but increase schema coupling. Choose per event, and version deliberately.

    Observability. Track consumer lag per group, DLQ sizes, processing latency (event time → processed time), and trace across async hops via message headers (see Distributed Tracing).

    Explain it in 2 minutes (system design / architecture round)¶

    "When an order is placed, the order service writes it and an OrderPlaced event to its outbox; a relay publishes to Kafka keyed by order ID. Inventory, loyalty, notifications and analytics each have their own consumer group, scale by partitions, and process idempotently. Failures retry with backoff and go to a dead-letter topic after N attempts, with alerts. Events have Avro schemas in a registry with backward compatibility. Real-time features like fraud detection and live dashboards run on Kafka Streams with event-time windows. We monitor consumer lag and trace across async hops."

    War story: the poison pill

    A retailer's invoicing consumer hit an event with a malformed price ("12,50" from a new country's checkout). The consumer retried forever; Kafka offsets stopped advancing; 400,000 invoices queued behind it over a weekend. Monday's finance reports were empty. Fix: bounded retries with backoff, a dead-letter topic with an alert and a replay tool, schema validation at the producer, and a lag alert per consumer group. Lesson: in event-driven systems, one bad event can stop a whole stream. Plan for it.

    12. Interview Corner¶

    Q1. What is event-driven architecture?

    Components communicate by publishing and consuming events through a broker, instead of calling each other directly.

    Q2. What is an event?

    An immutable record of something that happened, named in the past tense (OrderPlaced).

    Q3. Name some message brokers.

    Apache Kafka, RabbitMQ, ActiveMQ, AWS SNS/SQS, Google Pub/Sub, Azure Service Bus.

    Q4. What is a consumer group in Kafka?

    A set of consumers sharing a topic's partitions; each group gets all events, and each partition is read by one member of the group.

    Q5. Main advantage?

    Loose coupling: producers don't know consumers, and new consumers can be added without changes.

    Q1. Event notification vs. event-carried state transfer?

    Notification carries an ID (consumers call back for details); state transfer carries the data consumers need.

    Q2. How is ordering guaranteed in Kafka?

    Only within a partition; events with the same key go to the same partition.

    Q3. What is a dead-letter queue?

    A topic/queue where messages go after failing processing repeatedly, so they don't block others and can be inspected or replayed.

    Q4. Event time vs. processing time?

    Event time is when it happened; processing time is when it's processed. Windows by event time handle late data correctly.

    Q5. How do you handle duplicate events?

    Idempotent consumers (dedupe by event ID, idempotent operations).

    Q1. "Design a real-time notification system for 10M users."

    Domain events → Kafka (keyed by user) → notification service consumer groups by channel (push/SMS/email), preference service lookup (cached), rate limits per user, idempotency per notification key, DLQs, provider adapters with retries, delivery status events back for analytics.

    Q2. "How do you evolve event schemas safely?"

    Schema registry with compatibility (backward/forward), additive changes, new event versions or topics for breaking changes, consumers as tolerant readers, and deprecation windows.

    Q3. "When would you NOT use event-driven?"

    When the user needs an immediate answer that depends on the result (a synchronous query/command), for simple CRUD, or when the team lacks the operational maturity for brokers.

    Q4. "Broker vs. mediator topology?"

    Broker: choreography, maximum decoupling, harder to see flows. Mediator: an orchestrator controls steps, easier to manage complex workflows and errors.

    Q5. "Consumer lag is growing. What do you check?"

    Throughput per partition vs. produce rate, slow downstream calls in handlers, rebalancing storms, poison messages, partition skew (hot keys), and whether more partitions/instances or batching are needed.

    Problem: A poison message must not block the stream. Retry each event up to 3 times; transient failures should succeed on retry, but an event that keeps failing goes to a dead-letter queue with its error, and processing continues.

    Solution 
    package com.handbook.architecture.eventdriven.dlq;

import java.util.ArrayList;
import java.util.List;
import java.util.function.Consumer;

/**
 * Coding challenge: a poison message must not block the partition forever. Retry a few times; if
 * it still fails, park it on a dead-letter queue with the error, and move on to the next message.
 */
public final class RetryingConsumer<E> {

    public record DeadLetter<E>(E event, String error, int attempts) {
    }

    private final Consumer<E> handler;
    private final int maxAttempts;
    private final List<DeadLetter<E>> deadLetters = new ArrayList<>();

    public RetryingConsumer(Consumer<E> handler, int maxAttempts) {
        this.handler = handler;
        this.maxAttempts = maxAttempts;
    }

    public void consume(List<E> partition) {
        for (E event : partition) {
            for (int attempt = 1; ; attempt++) {
                try {
                    handler.accept(event);
                    break;
                } catch (RuntimeException e) {
                    if (attempt == maxAttempts) {
                        deadLetters.add(new DeadLetter<>(event, e.getMessage(), attempt));
                        System.out.println("    -> DLQ after " + attempt + " attempts: " + event);
                        break;
                    }
                    System.out.println("    attempt " + attempt + " failed for " + event + ": " + e.getMessage());
                }
            }
        }
    }

    public List<DeadLetter<E>> deadLetters() {
        return List.copyOf(deadLetters);
    }
}

    package com.handbook.architecture.eventdriven.dlq;

import java.util.ArrayList;
import java.util.List;

public class DeadLetterDemo {

    public static void main(String[] args) {
        List<String> invoiced = new ArrayList<>();
        int[] flakyFailures = {1};
        var consumer = new RetryingConsumer<String>(event -> {
            if (event.contains("amount=abc")) {
                throw new IllegalArgumentException("cannot parse amount"); // poison: will never succeed
            }
            if (event.startsWith("ORD-3") && flakyFailures[0]-- > 0) {
                throw new IllegalStateException("invoice DB timeout"); // transient: succeeds on retry
            }
            invoiced.add(event.substring(0, 5));
        }, 3);

        System.out.println("=== Challenge: retries + dead-letter queue for poison messages ===");
        consumer.consume(List.of("ORD-1 amount=1447", "ORD-2 amount=abc", "ORD-3 amount=129", "ORD-4 amount=399"));
        System.out.println("invoiced: " + invoiced);
        System.out.println("dead letters: " + consumer.deadLetters());
    }
}

    Output:

    === Challenge: retries + dead-letter queue for poison messages ===
    attempt 1 failed for ORD-2 amount=abc: cannot parse amount
    attempt 2 failed for ORD-2 amount=abc: cannot parse amount
    -> DLQ after 3 attempts: ORD-2 amount=abc
    attempt 1 failed for ORD-3 amount=129: invoice DB timeout
invoiced: [ORD-1, ORD-3, ORD-4]
dead letters: [DeadLetter[event=ORD-2 amount=abc, error=cannot parse amount, attempts=3]]

    Key points to say: distinguish transient (retry with backoff) from permanent (DLQ immediately) errors when you can; keep the original event and error in the DLQ for replay after a fix; Spring Kafka's DefaultErrorHandler + DeadLetterPublishingRecoverer implements exactly this.

    13. Quick Revision Card¶

    Remember in 30 seconds

    • Events = facts; producers don't know consumers.
    • Consumer groups: pub/sub across groups, competing consumers within a group.
    • Ordering per partition key; at-least-once → idempotent consumers.
    • Event time + watermarks for streams; CEP for patterns.
    • Retries + DLQ, schema registry, lag monitoring, tracing.
