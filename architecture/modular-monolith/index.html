    Architecture Intermediate

    Modular Monolith¶

    🟡 Intermediate Architecture Interview frequency ⭐⭐⭐⭐

    TL;DR

    One deployable application, split internally into modules along business capabilities. Each module has a small public API, hides its internals, owns its data, and talks to other modules through APIs or in-process events. You get most of the design benefits of microservices (clear boundaries, team ownership) without the operational cost of distributed systems, and modules can be extracted into services later if needed.

    1. Intent & Problem It Solves¶

    The problem in plain English: a classic monolith turned into a "big ball of mud": any class calls any other, the billing code reads the catalog's tables, and a change anywhere can break anything. The usual reaction, "let's do microservices", trades that for network failures, distributed transactions and 30 deployment pipelines, often before anyone knows where the right boundaries are.

    Definition (Simon Brown; Spring Modulith documentation):

    A modular monolith is a monolith that is built with well-defined, loosely coupled modules that align with business domains, enforced so that the modules don't depend on each other's internals.

    Rule How it's enforced
    Modules follow business capabilities Package structure by domain (catalog, ordering, billing)
    Modules expose a small public API Package-private internals, Java modules (JPMS), Spring Modulith
    No access to other modules' internals or tables ArchUnit / Spring Modulith verification; schema per module
    Communication via API calls or events In-process events, ideally transactional
    Acyclic module dependencies Verified in CI (see the coding challenge)

    2. Real-World Analogy¶

    A department store vs. a mall

    A department store (modular monolith) has separate departments, each with its own staff, stock room and manager, under one roof with one entrance and one checkout system. A mall (microservices) has independent shops with their own doors, tills and opening hours. The department store is cheaper to run; a department can later move out and become its own shop if it grows enough.

    4. Naive Approach (Without the Pattern)¶

    // billing code in a big-ball-of-mud monolith
var product = productRepository.findById(sku);          // reaches into catalog internals
var order = em.createQuery("SELECT o FROM Order o JOIN Customer c ...");  // joins across domains
orderService.markInvoiced(order);                        // billing mutates ordering's state

    5. Three Real-World Examples¶

    Example 1: Catalog, Ordering and Billing with Enforced Boundaries (Grocery)¶

    Scenario: Each module is a Java package with one public API and package-private internals: code in other packages literally cannot reference CatalogService or ProductTable, because the compiler forbids it. Ordering calls CatalogApi.priceOf() and publishes OrderPlaced; billing reacts to the event and never depends on ordering.

    Full Code:

    package com.handbook.architecture.modular.shop.catalog;

import java.util.Optional;

/** The catalog module's ONLY public surface. Everything else in this package is package-private. */
public interface CatalogApi {

    Optional<Long> priceOf(String sku);

    static CatalogApi create() { // (1)!
        return new CatalogService(new ProductTable());
    }
}
    1. A factory on the API: the only way for other modules to get a catalog, without seeing its implementation.
    package com.handbook.architecture.modular.shop.catalog;

import java.util.Optional;

/** Package-private: other modules cannot even name this class. */
class CatalogService implements CatalogApi {

    private final ProductTable table;

    CatalogService(ProductTable table) {
        this.table = table;
    }

    @Override
    public Optional<Long> priceOf(String sku) {
        return table.find(sku).filter(ProductTable.Row::active).map(ProductTable.Row::pricePaise);
    }
}

    package com.handbook.architecture.modular.shop.catalog;

import java.util.Map;
import java.util.Optional;

/** Package-private: the catalog's own tables (its own schema in the shared database). */
class ProductTable {

    record Row(String sku, long pricePaise, boolean active) {
    }

    private final Map<String, Row> rows = Map.of(
            "MANGO-1KG", new Row("MANGO-1KG", 39_900, true),
            "RICE-5KG", new Row("RICE-5KG", 64_900, true),
            "OLD-SKU", new Row("OLD-SKU", 1_000, false));

    Optional<Row> find(String sku) {
        return Optional.ofNullable(rows.get(sku));
    }
}

    package com.handbook.architecture.modular.shop.ordering;

import com.handbook.architecture.modular.shop.catalog.CatalogApi;
import com.handbook.architecture.modular.shop.shared.ModuleEvents;

import java.util.Map;

/** The ordering module's public API. It depends on the catalog's API, never on its internals. */
public interface OrderingApi {

    String placeOrder(String customerId, Map<String, Integer> items);

    static OrderingApi create(CatalogApi catalog, ModuleEvents events) {
        return new OrderingService(catalog, events);
    }
}

    package com.handbook.architecture.modular.shop.ordering;

import com.handbook.architecture.modular.shop.catalog.CatalogApi;
import com.handbook.architecture.modular.shop.shared.ModuleEvents;
import com.handbook.architecture.modular.shop.shared.OrderPlaced;

import java.util.Map;

class OrderingService implements OrderingApi {

    private final CatalogApi catalog;
    private final ModuleEvents events;
    private int nextId = 1;

    OrderingService(CatalogApi catalog, ModuleEvents events) {
        this.catalog = catalog;
        this.events = events;
    }

    @Override
    public String placeOrder(String customerId, Map<String, Integer> items) {
        long total = 0;
        for (var item : items.entrySet()) {
            long price = catalog.priceOf(item.getKey()) // (1)!
                    .orElseThrow(() -> new IllegalArgumentException("not for sale: " + item.getKey()));
            total += price * item.getValue();
        }
        String id = "ORD-" + nextId++;
        events.publish(new OrderPlaced(id, customerId, total)); // (2)!
        return id;
    }
}
    1. Ordering depends on catalog's API, never its tables.
    2. Downstream reactions happen via an event, so ordering doesn't know billing exists.
    package com.handbook.architecture.modular.shop.billing;

import com.handbook.architecture.modular.shop.shared.ModuleEvents;
import com.handbook.architecture.modular.shop.shared.OrderPlaced;

import java.util.ArrayList;
import java.util.List;

/** Billing reacts to OrderPlaced. It doesn't depend on the ordering module at all. */
public final class BillingModule {

    private final List<String> invoices = new ArrayList<>();

    public BillingModule(ModuleEvents events) {
        events.on(OrderPlaced.class, this::invoice); // (1)!
    }

    private void invoice(OrderPlaced e) {
        long gst = e.totalPaise() * 5 / 100;
        invoices.add(String.format("INV-%s %s ₹%.2f + GST ₹%.2f", e.orderId(), e.customerId(),
                e.totalPaise() / 100.0, gst / 100.0));
    }

    public List<String> invoices() {
        return List.copyOf(invoices);
    }
}
    1. Billing subscribes to the published event type; ArchUnit verifies billing never imports ordering.
    package com.handbook.architecture.modular.shop.shared;

import java.util.ArrayList;
import java.util.LinkedHashMap;
import java.util.List;
import java.util.Map;
import java.util.function.Consumer;

/** In-process event bus shared by modules (Spring's ApplicationEventPublisher in a real app). */
public final class ModuleEvents {

    private final Map<Class<?>, List<Consumer<Object>>> listeners = new LinkedHashMap<>();

    @SuppressWarnings("unchecked")
    public <E> void on(Class<E> type, Consumer<E> listener) {
        listeners.computeIfAbsent(type, t -> new ArrayList<>()).add(e -> listener.accept((E) e));
    }

    public void publish(Object event) {
        listeners.getOrDefault(event.getClass(), List.of()).forEach(l -> l.accept(event));
    }
}

    package com.handbook.architecture.modular.shop.shared;

/** A published event: part of the ordering module's public contract. */
public record OrderPlaced(String orderId, String customerId, long totalPaise) {
}

    package com.handbook.architecture.modular.shop;

import com.handbook.architecture.modular.shop.billing.BillingModule;
import com.handbook.architecture.modular.shop.catalog.CatalogApi;
import com.handbook.architecture.modular.shop.ordering.OrderingApi;
import com.handbook.architecture.modular.shop.shared.ModuleEvents;

import java.util.LinkedHashMap;
import java.util.Map;

public class ModularShopDemo {

    public static void main(String[] args) {
        ModuleEvents events = new ModuleEvents();
        CatalogApi catalog = CatalogApi.create();
        OrderingApi ordering = OrderingApi.create(catalog, events);
        BillingModule billing = new BillingModule(events);

        System.out.println("=== Grocery: one deployable, three modules with enforced boundaries ===");
        Map<String, Integer> basket = new LinkedHashMap<>();
        basket.put("MANGO-1KG", 2);
        basket.put("RICE-5KG", 1);
        System.out.println("ordering.placeOrder -> " + ordering.placeOrder("CUST-42", basket));
        try {
            ordering.placeOrder("CUST-42", Map.of("OLD-SKU", 1));
        } catch (IllegalArgumentException e) {
            System.out.println("ordering.placeOrder -> rejected: " + e.getMessage());
        }
        System.out.println("billing invoices    -> " + billing.invoices());
        System.out.println("(new CatalogService() from the ordering package would not compile: it is package-private)");
    }
}

    Output:

    === Grocery: one deployable, three modules with enforced boundaries ===
ordering.placeOrder -> ORD-1
ordering.placeOrder -> rejected: not for sale: OLD-SKU
billing invoices    -> [INV-ORD-1 CUST-42 ₹1447.00 + GST ₹72.35]
(new CatalogService() from the ordering package would not compile: it is package-private)

    Why a modular monolith here:

    • Boundaries are enforced by the compiler, not by good intentions.
    • One deployment, one database transaction where needed, simple debugging.
    • Each module could become a service later, because its interactions are already explicit.

    Example 2: Extraction-Ready Events (HR & Payroll)¶

    Scenario: HR publishes EmployeeHired through an EventPublisher port. In the monolith, the publisher delivers in-process to payroll. When payroll is extracted into its own service (different scaling, compliance and release needs), the same HR module class is wired with an outbox publisher instead. Only wiring changes.

    Full Code:

    package com.handbook.architecture.modular.payroll;

import java.util.ArrayList;
import java.util.List;
import java.util.function.Consumer;

/**
 * HR and Payroll modules communicate only through an EventPublisher port. Today it's in-process;
 * when payroll is extracted into its own service, only the publisher implementation changes.
 */
public final class PayrollModules {

    private PayrollModules() {
    }

    public record EmployeeHired(String employeeId, String name, long monthlySalaryPaise) {
    }

    public interface EventPublisher {
        void publish(EmployeeHired event);
    }

    /** Wiring today: a direct in-process call to the subscriber. */
    public static EventPublisher inProcess(Consumer<EmployeeHired> subscriber) {
        return subscriber::accept;
    }

    /** Wiring after extraction: events go to an outbox table and Kafka (here: a list). */
    public static EventPublisher outbox(List<String> outboxTable) {
        return e -> outboxTable.add("topic=hr.employee-hired key=" + e.employeeId() + " payload=" + e);
    }

    /** HR module: hires people and announces it. Unchanged across both wirings. */
    public static final class HrModule {
        private final EventPublisher publisher;

        public HrModule(EventPublisher publisher) {
            this.publisher = publisher;
        }

        public void hire(String id, String name, long monthlySalaryPaise) {
            // ...HR's own records, contracts, onboarding tasks...
            publisher.publish(new EmployeeHired(id, name, monthlySalaryPaise)); // (1)!
        }
    }

    /** Payroll module: keeps its own copy of what it needs. */
    public static final class PayrollModule {
        private final List<String> payees = new ArrayList<>();

        public void on(EmployeeHired e) {
            payees.add(e.employeeId() + " " + String.format("₹%,d/month", e.monthlySalaryPaise() / 100));
        }

        public List<String> payees() {
            return List.copyOf(payees);
        }
    }
}
    1. HR publishes a fact; it doesn't know whether the subscriber is in the same JVM or behind Kafka.
    package com.handbook.architecture.modular.payroll;

import com.handbook.architecture.modular.payroll.PayrollModules.HrModule;
import com.handbook.architecture.modular.payroll.PayrollModules.PayrollModule;

import java.util.ArrayList;
import java.util.List;

public class ExtractionReadyDemo {

    public static void main(String[] args) {
        System.out.println("=== HR & Payroll: modules today, services tomorrow ===");

        PayrollModule payroll = new PayrollModule();
        HrModule hr = new HrModule(PayrollModules.inProcess(payroll::on));
        hr.hire("EMP-101", "Meera Nair", 9_500_000);
        hr.hire("EMP-102", "Arjun Das", 7_200_000);
        System.out.println("Modular monolith, in-process events -> payroll has " + payroll.payees());

        List<String> outbox = new ArrayList<>();
        HrModule extractedHr = new HrModule(PayrollModules.outbox(outbox)); // same HrModule class
        extractedHr.hire("EMP-103", "Sara Khan", 8_100_000);
        System.out.println("After extracting payroll, HR writes to the outbox:");
        outbox.forEach(row -> System.out.println("  " + row));
    }
}

    Output:

    === HR & Payroll: modules today, services tomorrow ===
Modular monolith, in-process events -> payroll has [EMP-101 ₹95,000/month, EMP-102 ₹72,000/month]
After extracting payroll, HR writes to the outbox:
  topic=hr.employee-hired key=EMP-103 payload=EmployeeHired[employeeId=EMP-103, name=Sara Khan, monthlySalaryPaise=8100000]

    Why design for extraction:

    • You don't have to decide now which modules become services.
    • Event-based integration between modules already looks like integration between services.

    Example 3: Verifying Module Boundaries in CI (Education platform)¶

    Scenario: An LMS has modules courses, enrollment, certificates and payments, each declaring the modules it may depend on. A verifier (like Spring Modulith's ApplicationModules.verify()) checks dependencies found in the code against the declarations and flags undeclared dependencies and access to internal packages. The build fails until they're fixed.

    Full Code:

    package com.handbook.architecture.modular.verify;

import java.util.ArrayList;
import java.util.List;
import java.util.Map;
import java.util.Set;

/**
 * Like Spring Modulith's ApplicationModules.verify(): compares the dependencies a module DECLARES
 * with the ones found in the code (from bytecode analysis), and flags access to another module's
 * internal packages.
 */
public final class ModuleVerifier {

    /** A type reference found in the code: from module + type, to module + package. */
    public record Reference(String fromModule, String fromType, String toModule, String toPackage) {
    }

    private final Map<String, Set<String>> declared;

    public ModuleVerifier(Map<String, Set<String>> declaredDependencies) {
        this.declared = declaredDependencies;
    }

    public List<String> verify(List<Reference> references) {
        List<String> problems = new ArrayList<>();
        for (Reference r : references) {
            if (r.fromModule().equals(r.toModule())) {
                continue;
            }
            if (!declared.getOrDefault(r.fromModule(), Set.of()).contains(r.toModule())) {
                problems.add(r.fromType() + ": undeclared dependency " + r.fromModule() + " -> " + r.toModule());
            } else if (r.toPackage().contains(".internal")) {
                problems.add(r.fromType() + ": uses internal package " + r.toPackage());
            }
        }
        return problems;
    }
}

    package com.handbook.architecture.modular.verify;

import com.handbook.architecture.modular.verify.ModuleVerifier.Reference;

import java.util.List;
import java.util.Map;
import java.util.Set;

public class ModuleVerifyDemo {

    public static void main(String[] args) {
        var verifier = new ModuleVerifier(Map.of(
                "enrollment", Set.of("courses"),
                "certificates", Set.of("enrollment"),
                "payments", Set.of()));

        List<Reference> found = List.of(
                new Reference("enrollment", "EnrollmentService", "courses", "lms.courses"),
                new Reference("certificates", "CertificateIssuer", "enrollment", "lms.enrollment"),
                new Reference("certificates", "CertificatePdf", "courses", "lms.courses"),
                new Reference("enrollment", "SeatChecker", "courses", "lms.courses.internal.jpa"),
                new Reference("payments", "RefundPolicy", "enrollment", "lms.enrollment"));

        System.out.println("=== Education platform: verifying module boundaries in CI ===");
        List<String> problems = verifier.verify(found);
        problems.forEach(p -> System.out.println("FAIL " + p));
        System.out.println(problems.isEmpty() ? "All module boundaries respected" : problems.size() + " violations: build fails");
    }
}

    Output:

    === Education platform: verifying module boundaries in CI ===
FAIL CertificatePdf: undeclared dependency certificates -> courses
FAIL SeatChecker: uses internal package lms.courses.internal.jpa
FAIL RefundPolicy: undeclared dependency payments -> enrollment
3 violations: build fails

    Why verification matters:

    • Without automated checks, module boundaries erode within months.
    • Declared dependencies double as documentation of the architecture.

    }

    @Test
    void billingModuleDoesNotDependOnOrdering() {
        noClasses().that().resideInAPackage("..modular.shop.billing..")
                .should().dependOnClassesThat().resideInAPackage("..modular.shop.ordering..")

    }
}

    6. Variations & Modern Java Take¶

    // Spring Modulith (reference): each top-level package under the main package is a module
@SpringBootApplication
class ShopApplication { }

class ModularityTests {
    @Test
    void verifiesModuleStructure() {
        ApplicationModules.of(ShopApplication.class).verify();   // fails on cycles and internal access
    }
}

// In ordering: publish within the transaction
@Transactional
public String placeOrder(...) { ...; events.publishEvent(new OrderPlaced(id, customer, total)); }

// In billing: handled after commit, asynchronously, with a persisted event publication log
@ApplicationModuleListener
void on(OrderPlaced event) { invoices.create(event); }
    Option Notes
    Package-private + ArchUnit Works everywhere; simplest
    Spring Modulith Module detection, verification, event publication registry, module integration tests, documentation
    Java Platform Module System module-info.java with exports; strongest encapsulation, more friction with frameworks
    Multi-module Maven/Gradle Separate build modules per business module; compile-time boundaries
    Schema per module Each module owns its tables; no cross-module joins

    7. Where It Lives in Real Frameworks¶

    Where Modular monolith
    Spring Modulith ApplicationModules, @ApplicationModuleListener, @ApplicationModuleTest
    Shopify's Rails monolith Componentized into domain components with enforced boundaries (Packwerk)
    JPMS module-info.java exports/requires
    ArchUnit / jMolecules Rules for slices and cycles (slices().should().beFreeOfCycles())

    8. Pros, Cons & Trade-offs¶

    ✅ Pros ❌ Cons
    Simple operations: one deploy, one runtime, local calls Shared fate: one memory leak or bad deploy affects all modules
    Clear boundaries, team ownership Scaling is per application, not per module
    Local transactions where needed One technology stack for all modules
    Easy refactoring of boundaries before they harden Requires discipline and tooling to keep boundaries
    Extraction to services is straightforward Build and test times grow with size

    9. Pitfalls & Anti-Patterns¶

    Modules by technical layer

    controllers, services, repositories modules aren't business modules. Modules should be capabilities (catalog, ordering), with layers inside.

    Shared tables

    If billing queries ordering's tables, the modules are coupled through the database, and extraction later becomes a data migration project. One owner per table.

    A giant 'common' module

    Everything "shared" ends up in common, which everything depends on. Keep shared kernels tiny (IDs, money types, event contracts).

    Synchronous chains between modules

    A → B → C → D calls inside one request recreate a distributed monolith in-process. Prefer events for reactions.

    10. Senior / Architect Deep Dive (10–15 yrs)¶

    "Monolith first." Martin Fowler and others observe that many successful microservice systems started as monoliths whose boundaries were discovered over time. A modular monolith is how you do that deliberately: cheap to change boundaries while you learn the domain.

    When to extract a module. Different scaling profile, different release cadence, different team, different compliance needs, or a different technology need. If none apply, keep it in.

    Transactional events. Publishing events within the business transaction and handling them after commit, with a persisted publication log (Spring Modulith's event publication registry), gives outbox-like reliability inside the monolith, and makes the later switch to Kafka trivial.

    Explain it in 2 minutes (system design / architecture round)¶

    "For a new product with one or two teams, I'd start with a modular monolith in Spring Boot: modules per business capability (catalog, ordering, billing, customers), each with a small public API and package-private internals, owning its own schema. Modules integrate through APIs for queries and events for reactions, using Spring Modulith's transactional event publication. CI verifies module boundaries and forbids cycles. When a module needs independent scaling or a separate team, we extract it: its API becomes REST, its events go to Kafka via the outbox."

    War story: microservices on day one

    A startup split its MVP into 14 microservices before launch, with 4 engineers. Most features changed 3–5 services at once; local development needed 20 containers; a third of the engineering time went into infrastructure. Boundaries turned out to be wrong: "pricing" and "promotions" were constantly called together. What they did: merged into a modular monolith with 6 modules, enforced boundaries with ArchUnit, and later extracted only search (different scaling) and payments (compliance). Lesson: you can't design good service boundaries before you understand the domain. Modules let you learn cheaply.

    12. Interview Corner¶

    Q1. What is a modular monolith?

    A single deployable application divided into well-defined business modules with enforced boundaries.

    Q2. How is it different from a normal monolith?

    A normal monolith often has no enforced boundaries (any code calls any code); a modular monolith restricts modules to each other's public APIs.

    Q3. Why not start with microservices?

    Microservices add network, deployment and data-consistency complexity; boundaries are hard to get right early. A modular monolith keeps things simple while boundaries are learned.

    Q4. How do modules communicate?

    Through public APIs (method calls) and in-process events.

    Q5. What is Spring Modulith?

    A Spring project that detects, verifies, tests and documents modules in a Spring Boot application, and supports reliable module events.

    Q1. How do you enforce module boundaries in Java?

    Package-private internals, ArchUnit/Spring Modulith verification, separate build modules, or JPMS.

    Q2. How do you handle data in a modular monolith?

    Each module owns its tables (ideally its own schema); no cross-module joins; other modules use its API or events.

    Q3. When do you extract a module into a service?

    When it needs independent scaling, deployment cadence, team ownership, technology or compliance isolation.

    Q4. How do module events differ from Kafka events?

    They're in-process (and can be transactional); with an event publication registry they're reliable. Semantically they should look like integration events so extraction is easy.

    Q5. What's a sign of a bad module boundary?

    Most changes touch several modules together, or modules call each other in long synchronous chains.

    Q1. "A CTO wants to move a 1M-line monolith to microservices. Your advice?"

    First modularize in place: map capabilities, enforce boundaries, split data ownership, then extract only modules with a clear reason, using the strangler approach. Measure benefits along the way.

    Q2. "How do you handle a cross-module transaction?"

    Within the monolith, a local transaction is allowed if both modules agree, but prefer events with eventual consistency to keep extraction possible.

    Q3. "How would you test module boundaries and behaviour?"

    Verification tests (Spring Modulith verify()), module-slice integration tests (@ApplicationModuleTest) that bootstrap one module with mocks for others, plus scenario tests that publish events.

    Q4. "How does Conway's law apply?"

    Module boundaries should match team boundaries; one team per module (or a few modules) reduces coordination.

    Q5. "What tooling would you put in CI?"

    Module verification, cycle checks, ArchUnit rules for internal packages, schema access checks, and generated module documentation (C4/PlantUML from Spring Modulith).

    Problem: Modules must form a DAG. Detect a dependency cycle and print it, or, if there's none, compute a valid build/initialization order with dependencies first.

    Solution 
    package com.handbook.architecture.modular.cycles;

import java.util.ArrayDeque;
import java.util.ArrayList;
import java.util.Deque;
import java.util.LinkedHashMap;
import java.util.List;
import java.util.Map;
import java.util.Optional;
import java.util.TreeMap;
import java.util.TreeSet;

/**
 * Coding challenge: modules must form a DAG. Find a dependency cycle if there is one (DFS with
 * colours); otherwise return a valid build/initialization order (dependencies first).
 */
public final class ModuleGraph {

    private final Map<String, TreeSet<String>> edges = new TreeMap<>();

    public ModuleGraph dependsOn(String module, String... dependencies) {
        edges.computeIfAbsent(module, m -> new TreeSet<>()).addAll(List.of(dependencies));
        for (String d : dependencies) {
            edges.computeIfAbsent(d, m -> new TreeSet<>());
        }
        return this;
    }

    public Optional<List<String>> findCycle() {
        Map<String, Integer> colour = new LinkedHashMap<>(); // 0 = new, 1 = on stack, 2 = done
        Deque<String> path = new ArrayDeque<>();
        for (String start : edges.keySet()) {
            List<String> cycle = dfs(start, colour, path);
            if (cycle != null) {
                return Optional.of(cycle);
            }
        }
        return Optional.empty();
    }

    private List<String> dfs(String node, Map<String, Integer> colour, Deque<String> path) {
        int c = colour.getOrDefault(node, 0);
        if (c == 2) {
            return null;
        }
        if (c == 1) { // back edge: the path from node to here is a cycle
            List<String> cycle = new ArrayList<>();
            boolean in = false;
            for (var it = path.descendingIterator(); it.hasNext(); ) {
                String n = it.next();
                in |= n.equals(node);
                if (in) {
                    cycle.add(n);
                }
            }
            cycle.add(node);
            return cycle;
        }
        colour.put(node, 1);
        path.push(node);
        for (String next : edges.get(node)) {
            List<String> cycle = dfs(next, colour, path);
            if (cycle != null) {
                return cycle;
            }
        }
        path.pop();
        colour.put(node, 2);
        return null;
    }

    /** Dependencies before dependents (post-order DFS). Call only when there is no cycle. */
    public List<String> buildOrder() {
        List<String> order = new ArrayList<>();
        Map<String, Boolean> seen = new TreeMap<>();
        for (String m : edges.keySet()) {
            visit(m, seen, order);
        }
        return order;
    }

    private void visit(String m, Map<String, Boolean> seen, List<String> order) {
        if (seen.putIfAbsent(m, true) != null) {
            return;
        }
        edges.get(m).forEach(d -> visit(d, seen, order));
        order.add(m);
    }
}

    package com.handbook.architecture.modular.cycles;

public class CycleDemo {

    public static void main(String[] args) {
        System.out.println("=== Challenge: detect module cycles, compute a build order ===");
        ModuleGraph healthy = new ModuleGraph()
                .dependsOn("ordering", "catalog", "customers")
                .dependsOn("billing", "customers")
                .dependsOn("shipping", "ordering");
        System.out.println("cycle: " + healthy.findCycle().map(Object::toString).orElse("none")
                + ", build order: " + healthy.buildOrder());

        ModuleGraph tangled = new ModuleGraph()
                .dependsOn("ordering", "catalog", "billing")
                .dependsOn("billing", "customers", "shipping")
                .dependsOn("shipping", "ordering");
        System.out.println("cycle: " + tangled.findCycle().map(c -> String.join(" -> ", c)).orElse("none")
                + "  (break it with an event or by moving the shared concept)");
    }
}

    Output:

    === Challenge: detect module cycles, compute a build order ===
cycle: none, build order: [customers, billing, catalog, ordering, shipping]
cycle: billing -> shipping -> ordering -> billing  (break it with an event or by moving the shared concept)

    Key points to say: DFS with three colours finds back edges (cycles) in O(V + E); post-order DFS gives a topological order. To break a cycle, invert one dependency with an event or move the shared concept into its own module.

    Behavioural tie-in (STAR) for experienced candidates

    • S: Our 600k-line monolith had 3 teams constantly breaking each other; leadership proposed a full microservices rewrite.
    • T: Restore team autonomy with less risk than a rewrite.
    • A: Proposed modularizing first: defined 7 modules with the teams, introduced module APIs, Spring Modulith verification with a shrinking violation baseline, and schema-per-module; extracted one module (search) that needed different scaling.
    • R: Cross-team breakages fell by 80% in two quarters; the rewrite was cancelled, saving an estimated 18 months.

    13. Quick Revision Card¶

    Remember in 30 seconds

    • One deployable, many business modules with enforced boundaries.
    • Public API + hidden internals + own data per module.
    • APIs for queries, events for reactions; no cycles.
    • Verify in CI (Spring Modulith, ArchUnit).
    • Extract to services only when there's a reason.
