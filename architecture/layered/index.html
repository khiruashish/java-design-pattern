    Architecture Beginner

    Layered Architecture¶

    🟢 Beginner Architecture Interview frequency ⭐⭐⭐⭐⭐

    TL;DR

    Organize code into horizontal layers (presentation → business/service → persistence), where each layer has one kind of responsibility and depends only on the layers below it. It's the default architecture of most Spring Boot applications (@Controller → @Service → @Repository): easy to learn and to staff, but it can turn into "pass-through" layers and database-centric designs if you're not careful.

    1. Intent & Problem It Solves¶

    The problem in plain English: without structure, a grocery app's HTTP handler parses JSON, checks stock, calculates discounts, writes SQL and formats the response, all in one 400-line method. Changing the database means touching UI code; testing a discount rule needs a web server and a database.

    Definition (Mark Richards, Software Architecture Patterns):

    Components within the layered architecture pattern are organized into horizontal layers, each layer performing a specific role within the application.

    Layer Responsibility Spring stereotype
    Presentation HTTP/UI: parse input, call the service, format output @RestController
    Business / Service Use cases, validation, rules, transaction boundaries @Service + @Transactional
    Persistence Load/save data @Repository (JPA/JDBC)
    Database Storage PostgreSQL, etc.

    Closed vs. open layers: a closed layer must be passed through (presentation can't skip the service layer); an open layer may be skipped. Relaxed layering allows calling any lower layer; strict allows only the one directly below.

    2. Real-World Analogy¶

    A restaurant: waiter, kitchen, pantry

    The waiter (presentation) takes orders and serves plates, but never cooks. The kitchen (business) decides how dishes are made and refuses impossible orders. The pantry (persistence) stores and hands out ingredients. Customers never walk into the pantry, and the pantry never talks to customers.

    3. Structure¶

    flowchart TB
    W["Presentation<br/>OrderController"] --> S["Business<br/>OrderService"]
    S --> R["Persistence<br/>OrderRepository"]
    R --> DB[(Database)]
    W -.->|❌ skip| R
    R -.->|❌ upward| W

    4. Naive Approach (Without the Pattern)¶

    @PostMapping("/orders")
public String post(@RequestBody Map<String, String> form) throws SQLException {
    int qty = Integer.parseInt(form.get("qty"));                                    // parsing
    if (qty > 20) return "{\"error\":\"too many\"}";                                 // business rule
    try (var c = DriverManager.getConnection(URL)) {                                // persistence
        c.createStatement().executeUpdate("INSERT INTO orders VALUES (...)");
    }
    return "{\"ok\":true}";                                                         // formatting
}

    5. Three Real-World Examples¶

    Example 1: Placing an Order Through Three Layers (Grocery)¶

    Scenario: POST /orders flows through the controller (parses the form, maps errors to 400/422), the service (validates the 20-item limit, prices items, creates the order; this is the transaction boundary), and the repository (stores it). Each layer logs when it's involved, so you can see that invalid input never reaches the service, and invalid orders never reach the repository.

    Design:

    sequenceDiagram
    participant W as OrderController
    participant S as OrderService
    participant R as OrderRepository
    W->>W: parse form (400 if not numbers)
    W->>S: placeOrder(customer, quantities)
    S->>R: priceOf(sku)
    S->>S: rules (422 if violated)
    S->>R: save(order)
    W-->>W: 201 + response DTO

    Full Code:

    package com.handbook.architecture.layered.grocery.web;

import com.handbook.architecture.layered.grocery.domain.Order;
import com.handbook.architecture.layered.grocery.service.OrderService;

import java.util.LinkedHashMap;
import java.util.Map;

/**
 * Presentation layer: translates HTTP input into a service call and the result into a response.
 * No business rules here, and no direct access to the repository.
 */
public class OrderController {

    /** The response DTO: what the API exposes, decoupled from the domain object. */
    public record OrderResponse(int status, String body) {
    }

    private final OrderService service;

    public OrderController(OrderService service) {
        this.service = service;
    }

    /** POST /orders with form fields like {@code customer=CUST-42&MANGO-1KG=2}. */
    public OrderResponse post(Map<String, String> form) {
        System.out.println("    [web] POST /orders " + form);
        Map<String, Integer> quantities = new LinkedHashMap<>();
        try {
            form.forEach((k, v) -> {
                if (!k.equals("customer")) {
                    quantities.put(k, Integer.parseInt(v)); // (1)!
                }
            });
        } catch (NumberFormatException e) {
            return new OrderResponse(400, "quantities must be numbers");
        }
        try {
            Order order = service.placeOrder(form.get("customer"), quantities);
            return new OrderResponse(201, order.id() + " total ₹" + order.totalPaise() / 100); // (2)!
        } catch (OrderService.InvalidOrderException e) {
            return new OrderResponse(422, e.getMessage()); // (3)!
        }
    }
}
    1. Input translation is the presentation layer's job: strings to numbers.
    2. A response DTO: the API's shape is decoupled from the domain object.
    3. Business errors map to HTTP status codes here, not in the service.
    package com.handbook.architecture.layered.grocery.service;

import com.handbook.architecture.layered.grocery.domain.Order;
import com.handbook.architecture.layered.grocery.repository.OrderRepository;

import java.util.ArrayList;
import java.util.List;
import java.util.Map;

/** Business layer: use cases, validation and transaction boundaries. Calls only the layer below. */
public class OrderService {

    public static final class InvalidOrderException extends RuntimeException {
        InvalidOrderException(String message) {
            super(message);
        }
    }

    private final OrderRepository repository;
    private int nextId = 1;

    public OrderService(OrderRepository repository) {
        this.repository = repository;
    }

    /** In Spring this method would be @Transactional: the use case is one unit of work. */
    public Order placeOrder(String customerId, Map<String, Integer> quantities) { // (1)!
        System.out.println("    [service] validating and pricing " + quantities.keySet());
        if (quantities.values().stream().mapToInt(Integer::intValue).sum() > 20) {
            throw new InvalidOrderException("max 20 items per order");
        }
        List<Order.Line> lines = new ArrayList<>();
        quantities.forEach((sku, qty) -> lines.add(new Order.Line(sku, qty,
                repository.priceOf(sku).orElseThrow(() -> new InvalidOrderException("unknown product " + sku)))));
        Order order = new Order("ORD-" + nextId++, customerId, List.copyOf(lines));
        repository.save(order);
        return order;
    }
}
    1. The use case: validation, pricing, creation, persistence, as one unit of work (@Transactional in Spring).
    package com.handbook.architecture.layered.grocery.repository;

import com.handbook.architecture.layered.grocery.domain.Order;

import java.util.LinkedHashMap;
import java.util.Map;
import java.util.Optional;

/** Persistence layer: stores and loads domain objects. A JPA/JdbcTemplate repository in a real app. */
public class OrderRepository {

    private final Map<String, Order> orders = new LinkedHashMap<>();
    private final Map<String, Long> prices = Map.of("MANGO-1KG", 39_900L, "RICE-5KG", 64_900L);

    public Optional<Long> priceOf(String sku) {
        return Optional.ofNullable(prices.get(sku));
    }

    public void save(Order order) {
        System.out.println("    [repository] INSERT order " + order.id());
        orders.put(order.id(), order);
    }

    public int count() {
        return orders.size();
    }
}

    package com.handbook.architecture.layered.grocery.domain;

import java.util.List;

/** Domain layer: plain data and rules about orders. Knows nothing about HTTP or storage. */
public record Order(String id, String customerId, List<Line> lines) {

    public record Line(String sku, int qty, long unitPaise) {
        public long totalPaise() {
            return qty * unitPaise;
        }
    }

    public long totalPaise() {
        return lines.stream().mapToLong(Line::totalPaise).sum();
    }
}

    package com.handbook.architecture.layered.grocery;

import com.handbook.architecture.layered.grocery.repository.OrderRepository;
import com.handbook.architecture.layered.grocery.service.OrderService;
import com.handbook.architecture.layered.grocery.web.OrderController;

import java.util.LinkedHashMap;
import java.util.Map;

public class LayeredOrderDemo {

    public static void main(String[] args) {
        OrderRepository repository = new OrderRepository();
        OrderController controller = new OrderController(new OrderService(repository)); // wiring = Spring's job

        System.out.println("=== Grocery: one request through three layers ===");
        System.out.println("-> " + controller.post(form("customer", "CUST-42", "MANGO-1KG", "2", "RICE-5KG", "1")));
        System.out.println("-> " + controller.post(form("customer", "CUST-42", "MANGO-1KG", "two")));
        System.out.println("-> " + controller.post(form("customer", "CUST-42", "SAFFRON-1G", "1")));
        System.out.println("-> " + controller.post(form("customer", "CUST-42", "RICE-5KG", "25")));
        System.out.println("Orders stored: " + repository.count());
    }

    private static Map<String, String> form(String... kv) {
        Map<String, String> m = new LinkedHashMap<>();
        for (int i = 0; i < kv.length; i += 2) {
            m.put(kv[i], kv[i + 1]);
        }
        return m;
    }
}

    Why layers here:

    • Each concern has an obvious home; new developers know where to look.
    • The service can be unit-tested without HTTP; the controller with a mocked service.

    Example 2: One Service, Two Front Ends (Clinic booking)¶

    Scenario: Patients book online; receptionists use a kiosk that accepts "10:30" for today. Both front ends call the same BookingService, which owns the rules: clinic hours, no double-booking a doctor, at most 2 appointments per patient per day. Because the rules live in the service layer, the kiosk can't accidentally allow what the website forbids.

    Full Code:

    package com.handbook.architecture.layered.clinic.service;

import com.handbook.architecture.layered.clinic.data.AppointmentDao;
import com.handbook.architecture.layered.clinic.data.AppointmentDao.AppointmentRow;

import java.time.LocalDateTime;

/**
 * The booking rules live here, ONCE. Every front end (web, reception desk, kiosk, phone bot)
 * calls this service, so the rules can't diverge between channels.
 */
public class BookingService {

    private final AppointmentDao dao;

    public BookingService(AppointmentDao dao) {
        this.dao = dao;
    }

    public String book(String patient, String doctor, LocalDateTime slot) {
        if (slot.getHour() < 9 || slot.getHour() >= 17) { // (1)!
            return "REJECTED: outside clinic hours";
        }
        if (dao.slotTaken(doctor, slot)) {
            return "REJECTED: " + doctor + " is already booked at " + slot.toLocalTime();
        }
        if (dao.countForPatientOn(patient, slot.toLocalDate()) >= 2) {
            return "REJECTED: max 2 appointments per patient per day";
        }
        dao.insert(new AppointmentRow(patient, doctor, slot));
        return "CONFIRMED: " + patient + " with " + doctor + " at " + slot.toLocalTime();
    }
}
    1. Rules in one place. If they lived in the web controller, the kiosk would need a copy, and the copies would drift.
    package com.handbook.architecture.layered.clinic.presentation;

import com.handbook.architecture.layered.clinic.service.BookingService;

import java.time.LocalDateTime;

/** Web front end: parses the ISO date-time from the form and shows a green or red banner. */
public class WebBookingPage {

    private final BookingService service;

    public WebBookingPage(BookingService service) {
        this.service = service;
    }

    public String submit(String patient, String doctor, String isoSlot) {
        String result = service.book(patient, doctor, LocalDateTime.parse(isoSlot));
        return (result.startsWith("CONFIRMED") ? "[green] " : "[red] ") + result;
    }
}

    package com.handbook.architecture.layered.clinic.presentation;

import com.handbook.architecture.layered.clinic.service.BookingService;

import java.time.LocalDate;
import java.time.LocalDateTime;
import java.time.LocalTime;

/** Reception kiosk: staff type "10:30" for today's date. Different input, same rules. */
public class ReceptionKiosk {

    private final BookingService service;
    private final LocalDate today;

    public ReceptionKiosk(BookingService service, LocalDate today) {
        this.service = service;
        this.today = today;
    }

    public String enter(String patient, String doctor, String hhmm) {
        return "KIOSK> " + service.book(patient, doctor, LocalDateTime.of(today, LocalTime.parse(hhmm)));
    }
}

    package com.handbook.architecture.layered.clinic.data;

import java.time.LocalDate;
import java.time.LocalDateTime;
import java.util.ArrayList;
import java.util.List;

/** Data layer: simple queries over stored appointments. */
public class AppointmentDao {

    public record AppointmentRow(String patient, String doctor, LocalDateTime slot) {
    }

    private final List<AppointmentRow> rows = new ArrayList<>();

    public boolean slotTaken(String doctor, LocalDateTime slot) {
        return rows.stream().anyMatch(r -> r.doctor().equals(doctor) && r.slot().equals(slot));
    }

    public long countForPatientOn(String patient, LocalDate day) {
        return rows.stream().filter(r -> r.patient().equals(patient) && r.slot().toLocalDate().equals(day)).count();
    }

    public void insert(AppointmentRow row) {
        rows.add(row);
    }
}

    Example 3: Closed vs. Open Layers for Reports (Banking)¶

    Scenario: A statement report is a pure read. With strictly closed layers, the presentation calls a service method that just forwards to the query: the architecture sinkhole anti-pattern. Marking the read-only query layer as open lets presentation read it directly, while writes (transfers) still must go through the service layer and its rules.

    Full Code:

    package com.handbook.architecture.layered.reporting;

import java.util.List;
import java.util.Map;
import java.util.function.Supplier;

/**
 * Closed vs. open layers for a read-only report. In strict (closed) layering every call passes
 * through the service layer, even when it adds nothing: the "architecture sinkhole".
 * Marking a query layer as OPEN lets the presentation layer read it directly.
 */
public final class StatementLayers {

    public record Txn(String date, String description, long paise) {
    }

    /** Data layer: a read-optimized query (in a real app, a SQL view or a reporting replica). */
    public static final class StatementQueries {
        private final Map<String, List<Txn>> data = Map.of("ACC-1", List.of(
                new Txn("2026-10-01", "Salary", 5_000_000),
                new Txn("2026-10-03", "Rent", -1_250_000),
                new Txn("2026-10-07", "Groceries", -89_900)));

        public List<Txn> forAccount(String account) {
            return data.getOrDefault(account, List.of());
        }
    }

    /** Service layer method that only forwards: no rules, no transaction, no transformation. */
    public static final class StatementService {
        private final StatementQueries queries;
        int passThroughCalls;

        public StatementService(StatementQueries queries) {
            this.queries = queries;
        }

        public List<Txn> statement(String account) {
            passThroughCalls++; // (1)!
            return queries.forAccount(account);
        }
    }

    public static String render(Supplier<List<Txn>> source) {
        StringBuilder sb = new StringBuilder();
        for (Txn t : source.get()) {
            sb.append(String.format("  %s %-10s %,12.2f%n", t.date(), t.description(), t.paise() / 100.0));
        }
        return sb.toString();
    }

    private StatementLayers() {
    }
}
    1. A layer that only forwards adds code, tests and indirection with no value. If most requests look like this, the layering is too strict.
    package com.handbook.architecture.layered.reporting;

import com.handbook.architecture.layered.reporting.StatementLayers.StatementQueries;
import com.handbook.architecture.layered.reporting.StatementLayers.StatementService;

public class OpenLayerDemo {

    public static void main(String[] args) {
        StatementQueries queries = new StatementQueries();
        StatementService service = new StatementService(queries);

        System.out.println("=== Banking: statement report through closed vs. open layers ===");
        System.out.println("Closed layering (presentation -> service -> queries):");
        System.out.print(StatementLayers.render(() -> service.statement("ACC-1")));
        System.out.println("service methods that only forwarded: " + service.passThroughCalls);

        System.out.println("Open query layer (presentation -> queries, read-only):");
        System.out.print(StatementLayers.render(() -> queries.forAccount("ACC-1")));
        System.out.println("Same output, one less layer to maintain for a pure read.");
        System.out.println("Writes (transfers, payments) still go through the service layer and its rules.");
    }
}

    Output:

    === Banking: statement report through closed vs. open layers ===
Closed layering (presentation -> service -> queries):
  2026-10-01 Salary        50,000.00
  2026-10-03 Rent         -12,500.00
  2026-10-07 Groceries       -899.00
service methods that only forwarded: 1
Open query layer (presentation -> queries, read-only):
  2026-10-01 Salary        50,000.00
  2026-10-03 Rent         -12,500.00
  2026-10-07 Groceries       -899.00
Same output, one less layer to maintain for a pure read.
Writes (transfers, payments) still go through the service layer and its rules.

    Why it matters:

    • Mark Richards' rule of thumb: if more than about 20% of requests are simple pass-throughs, consider opening some layers.
    • Open layers must be explicit and documented, or every shortcut becomes a precedent.
    Unit and ArchUnit Tests 
    package com.handbook.architecture;

import com.tngtech.archunit.core.domain.JavaClasses;
import com.tngtech.archunit.core.importer.ClassFileImporter;
import com.tngtech.archunit.core.importer.ImportOption;
import org.junit.jupiter.api.Test;

import static com.tngtech.archunit.lang.syntax.ArchRuleDefinition.noClasses;
import static com.tngtech.archunit.library.Architectures.layeredArchitecture;

/** The architecture of the examples, enforced by ArchUnit on every build. */
class ArchitectureRulesTest {

    private final JavaClasses classes = new ClassFileImporter()
            .withImportOption(ImportOption.Predefined.DO_NOT_INCLUDE_TESTS)
            .importPackages("com.handbook.architecture");

    @Test
    void groceryLayersOnlyCallDownwards() {
        layeredArchitecture().consideringOnlyDependenciesInLayers()
                .layer("Web").definedBy("..layered.grocery.web..")
                .layer("Service").definedBy("..layered.grocery.service..")
                .layer("Repository").definedBy("..layered.grocery.repository..")
                .whereLayer("Web").mayNotBeAccessedByAnyLayer()
                .whereLayer("Service").mayOnlyBeAccessedByLayers("Web")
                .whereLayer("Repository").mayOnlyBeAccessedByLayers("Service")
                .check(classes);
    }

    @Test
    void hexagonCoreNeverDependsOnAdapters() {
        noClasses().that().resideInAPackage("..hexagonal.checkout.domain..")
                .should().dependOnClassesThat().resideInAPackage("..hexagonal.checkout.adapter..")
                .check(classes);
        noClasses().that().resideInAPackage("..hexagonal.checkout.port..")
                .should().dependOnClassesThat().resideInAPackage("..hexagonal.checkout.adapter..")
                .check(classes);
    }

    @Test
    void cleanArchitectureDependencyRulePointsInwards() {
        noClasses().that().resideInAPackage("..clean.coupon.entities..")
                .should().dependOnClassesThat().resideInAnyPackage("..clean.coupon.usecase..", "..clean.coupon.adapters..")
                .check(classes);
        noClasses().that().resideInAPackage("..clean.coupon.usecase..")
                .should().dependOnClassesThat().resideInAPackage("..clean.coupon.adapters..")
                .check(classes);
    }

    @Test
    void billingModuleDoesNotDependOnOrdering() {
        noClasses().that().resideInAPackage("..modular.shop.billing..")
                .should().dependOnClassesThat().resideInAPackage("..modular.shop.ordering..")
                .check(classes);
    }

    6. Variations & Modern Java Take¶

    • Package by layer (controller/, service/, repository/) vs. package by feature (orders/, customers/ with layers inside each). Package by feature scales better and leads naturally to a modular monolith.
    • Enforce layers with ArchUnit (layeredArchitecture(), see the tests above) or Java modules (JPMS).
    • DTO mapping between layers with records and MapStruct; keep JPA entities out of API responses.
    • Evolve towards Hexagonal or Clean when the domain logic grows and you want it independent of persistence.

    7. Where It Lives in Real Frameworks¶

    Where Layering
    Spring MVC / Spring Boot @Controller → @Service → @Repository stereotypes
    Jakarta EE JAX-RS resources → EJB/CDI services → JPA
    OSI / TCP-IP network stacks Each layer uses only the one below
    Classic enterprise apps (n-tier) Web tier, application tier, data tier on separate servers

    8. Pros, Cons & Trade-offs¶

    ✅ Pros ❌ Cons
    Simple, universally understood Tends to become database-centric (design starts from tables)
    Clear separation of technical concerns Changes often cut through all layers (a new field touches every one)
    Easy to test layers in isolation Sinkhole layers that only forward
    Good default for CRUD-heavy apps Business logic leaks into controllers or repositories

    9. Pitfalls & Anti-Patterns¶

    Fat controllers

    Rules in controllers can't be reused by other channels (Example 2) and are hard to test. Controllers translate; services decide.

    Anemic domain with transaction scripts everywhere

    Services full of if statements over data-only entities. Fine for simple CRUD; for rich domains, move rules into domain objects (see Clean Architecture).

    Leaking persistence types upward

    Returning JPA entities from controllers couples your API to your schema and triggers lazy-loading surprises. Map to DTOs.

    Upward dependencies

    A repository importing a web DTO creates cycles and breaks layering. Catch it automatically (see the coding challenge and ArchUnit).

    10. Senior / Architect Deep Dive (10–15 yrs)¶

    Layers are technical, not business, boundaries. They tell you how code is organized, not what it does. In large systems, slice by business capability first (modules or services), then layer inside each slice.

    Where layered architecture breaks down. When the core logic is complex, the dependency of business on persistence (service → repository implementation) makes the domain hard to test and evolve. Dependency inversion (the service owns a repository interface) is the first step toward Hexagonal/Clean.

    Governance. Write the rules down (closed/open layers, allowed dependencies) and enforce them with ArchUnit in CI. Unenforced rules decay within months.

    Explain it in 2 minutes (system design / architecture round)¶

    "For a CRUD-heavy internal app, I'd use classic layering: REST controllers translate HTTP, services hold use cases and transaction boundaries, repositories handle persistence. I'd package by feature with layers inside, map entities to DTOs at the edge, and enforce layer rules with ArchUnit. Read-only reporting can use an open query layer to avoid pass-through services. If the domain logic grows complex, I'd invert the persistence dependency and move toward hexagonal."

    War story: the controller that knew too much

    An insurance portal's quote controller contained 1,100 lines of pricing logic. When the company launched a broker API, a developer copied the logic into a second controller. Six months later the two channels quoted different prices for the same customer, because a tax change had only been applied to one copy. A regulator asked why. Fix: pricing moved to a QuoteService used by both controllers; ArchUnit rule "controllers may not contain classes ending in Calculator"; a test comparing both channels' quotes. Lesson: business rules live in the business layer, once.

    12. Interview Corner¶

    Q1. What is layered architecture?

    Organizing an application into layers (presentation, business, persistence) where each layer depends only on layers below it.

    Q2. What does each Spring stereotype represent?

    @Controller/@RestController: presentation; @Service: business logic; @Repository: data access (with exception translation).

    Q3. Why shouldn't controllers contain business logic?

    It can't be reused by other channels, is hard to test, and mixes HTTP concerns with rules.

    Q4. What is a DTO and why use one?

    A Data Transfer Object shapes data for the API, decoupling it from internal entities.

    Q5. Where does @Transactional usually go?

    On service-layer methods, because a use case is one unit of work.

    Q1. Closed vs. open layers?

    Closed layers must be passed through; open layers can be skipped. Opening read-only layers avoids pass-through services.

    Q2. What is the architecture sinkhole anti-pattern?

    Requests passing through layers that add no logic, just forwarding.

    Q3. Package by layer vs. package by feature?

    By layer groups all controllers together; by feature groups everything for "orders" together. Feature packaging scales better and keeps related code close.

    Q4. How do you enforce layering?

    ArchUnit tests in CI (or JPMS modules / Maven modules).

    Q5. What's wrong with returning JPA entities from controllers?

    Couples the API to the schema, risks lazy-loading exceptions and over-exposure of fields (and mass-assignment issues on input).

    Q1. "When would you choose layered over hexagonal?"

    Simple CRUD domains, small teams, short-lived apps, or where the framework's conventions give most value. Hexagonal pays off with complex logic and many integrations.

    Q2. "A change to add a field touches 7 files across layers. Problem?"

    It's typical of layered designs (shotgun surgery). Mitigate with package by feature, fewer mapping layers for simple reads, or generated mappers; question whether all layers add value.

    Q3. "How do layers relate to tiers?"

    Layers are logical code organization; tiers are physical deployment units. Several layers can run in one tier.

    Q4. "How would you migrate a big layered monolith toward modules?"

    Re-package by feature, identify module boundaries, introduce module APIs, forbid cross-module access to internals with ArchUnit, then split data ownership.

    Q5. "What's the dependency inversion step from layered to hexagonal?"

    The service defines repository/gateway interfaces it needs; persistence implements them. Now business code doesn't depend on persistence code.

    Problem: Given layer definitions (package prefixes, top to bottom) and a list of class dependencies, report every dependency that goes upward (lower layer depending on a higher one). Downward skips are allowed (relaxed layering).

    Solution 
    package com.handbook.architecture.layered.rules;

import java.util.ArrayList;
import java.util.LinkedHashMap;
import java.util.List;
import java.util.Map;

/**
 * Coding challenge: a tiny version of what ArchUnit's layeredArchitecture() checks. Layers are
 * ordered top to bottom; a class may depend only on its own layer or the layers below it.
 */
public final class LayerRules {

    public record Dependency(String fromClass, String toClass) {
    }

    private final Map<String, Integer> layerRank = new LinkedHashMap<>(); // package prefix → rank

    public LayerRules layer(String packagePrefix) {
        layerRank.put(packagePrefix, layerRank.size());
        return this;
    }

    public List<String> violations(List<Dependency> dependencies) {
        List<String> violations = new ArrayList<>();
        for (Dependency d : dependencies) {
            Integer from = rank(d.fromClass());
            Integer to = rank(d.toClass());
            if (from != null && to != null && to < from) {
                violations.add(simple(d.fromClass()) + " -> " + simple(d.toClass())
                        + " (lower layer depends on a higher one)");
            }
        }
        return violations;
    }

    private Integer rank(String className) {
        return layerRank.entrySet().stream()
                .filter(e -> className.startsWith(e.getKey()))
                .map(Map.Entry::getValue)
                .findFirst().orElse(null);
    }

    private static String simple(String className) {
        return className.substring(className.lastIndexOf('.', className.lastIndexOf('.') - 1) + 1);
    }
}

    package com.handbook.architecture.layered.rules;

import com.handbook.architecture.layered.rules.LayerRules.Dependency;

import java.util.List;

public class LayerRulesDemo {

    public static void main(String[] args) {
        LayerRules rules = new LayerRules().layer("app.web").layer("app.service").layer("app.repository");

        List<Dependency> deps = List.of(
                new Dependency("app.web.OrderController", "app.service.OrderService"),
                new Dependency("app.service.OrderService", "app.repository.OrderRepository"),
                new Dependency("app.web.OrderController", "app.repository.OrderRepository"), // skips a layer
                new Dependency("app.repository.OrderRepository", "app.web.OrderResponse"),   // upward!
                new Dependency("app.service.PricingService", "app.web.Pagination"));         // upward!

        System.out.println("=== Challenge: detect layer violations ===");
        List<String> violations = rules.violations(deps);
        violations.forEach(v -> System.out.println("VIOLATION " + v));
        System.out.println(violations.size() + " violations; skipping a layer downward is allowed in relaxed layering.");
    }
}

    Output:

    === Challenge: detect layer violations ===
VIOLATION repository.OrderRepository -> web.OrderResponse (lower layer depends on a higher one)
VIOLATION service.PricingService -> web.Pagination (lower layer depends on a higher one)
2 violations; skipping a layer downward is allowed in relaxed layering.

    Key points to say: rank layers by order; a dependency is a violation if rank(to) < rank(from). Real tools (ArchUnit, jQAssistant) extract dependencies from bytecode; this exercise focuses on the rule.

    • S: A 6-year-old Spring app had business rules spread across controllers, services and SQL stored procedures; onboarding took months.
    • T: Make the codebase predictable without a rewrite.

    13. Quick Revision Card¶

    Remember in 30 seconds

    • Presentation → Business → Persistence; dependencies point down.
    • Controllers translate; services decide (and own transactions); repositories store.
    • Closed vs. open layers; avoid sinkholes.
    • Package by feature; DTOs at the edge; ArchUnit to enforce.
    • Next step for complex domains: invert dependencies (Hexagonal/Clean).
