    Hexagonal Architecture (Ports & Adapters)¶

    🟡 Intermediate Architecture Interview frequency ⭐⭐⭐⭐⭐

    TL;DR

    Put the application's core (domain + use cases) in the middle and let everything else plug in through ports (interfaces the core owns) and adapters (implementations for HTTP, databases, message brokers, external APIs). Driving adapters call the core; driven adapters are called by it. The core depends on nothing technical, so it can be tested without infrastructure and adapters can be swapped freely.

    1. Intent & Problem It Solves¶

    The problem in plain English: checkout logic is tangled with Spring MVC, JPA and the payment provider's SDK. Switching payment providers means editing business code; testing a checkout rule requires a database and a sandbox account; a nightly batch import can't reuse the logic because it's buried in a controller.

    Definition (Alistair Cockburn, 2005):

    Allow an application to equally be driven by users, programs, automated test or batch scripts, and to be developed and tested in isolation from its eventual run-time devices and databases.

    Term Meaning Example
    Core Domain model + application logic CheckoutService
    Driving (primary) port What the app offers PlaceOrderUseCase
    Driven (secondary) port What the app needs, in its own terms PaymentPort, OrderRepositoryPort
    Driving adapter Calls a driving port REST controller, CLI, message listener, test
    Driven adapter Implements a driven port JPA repository, PayFast HTTP client, SMS sender, fake

    2. Real-World Analogy¶

    A laptop's ports

    The laptop (core) defines USB-C and HDMI ports. You can plug in any monitor, charger or keyboard that fits, from any brand, and swap them anytime. The laptop's design doesn't change when you buy a new monitor; you just need the right adapter.

    The dependency rule: source-code dependencies always point into the hexagon. Adapters depend on ports; the core never imports an adapter.

    5. Three Real-World Examples¶

    Example 1: Checkout with Two Driving and Three Driven Adapters (Grocery)¶

    Scenario: The same CheckoutService is driven by a REST adapter (JSON with rupee amounts) and a CLI used by phone-order staff (amounts in paise). It needs a payment provider, a repository and a notifier, defined as ports in its own terms. The PayFast adapter translates to PayFast's language (rupee strings, merchant key, CAPTURED/DECLINED_LIMIT).

    Full Code:

    package com.handbook.architecture.hexagonal.checkout.domain;

import com.handbook.architecture.hexagonal.checkout.port.in.PlaceOrderUseCase;
import com.handbook.architecture.hexagonal.checkout.port.out.NotificationPort;
import com.handbook.architecture.hexagonal.checkout.port.out.OrderRepositoryPort;
import com.handbook.architecture.hexagonal.checkout.port.out.PaymentPort;

/**
 * The hexagon's core: implements the driving port, depends only on driven PORTS (interfaces it
 * owns), never on adapters. It can run in a unit test, a web app or a CLI unchanged.
 */
public class CheckoutService implements PlaceOrderUseCase {

    private final PaymentPort payments;
    private final OrderRepositoryPort orders;
    private final NotificationPort notifications;
    private int nextId = 1;

    public CheckoutService(PaymentPort payments, OrderRepositoryPort orders, NotificationPort notifications) {
        this.payments = payments; // (1)!
        this.orders = orders;
        this.notifications = notifications;
    }

    @Override
    public Order placeOrder(PlaceOrderCommand cmd) {
        String id = "ORD-" + nextId++;
        boolean paid = payments.charge(cmd.customerId(), cmd.totalPaise(), id);
        Order order = new Order(id, cmd.customerId(), cmd.totalPaise(),
                paid ? Order.Status.PAID : Order.Status.PAYMENT_DECLINED);
        orders.save(order);
        notifications.notify(cmd.phone(), paid ? "Order " + id + " confirmed" : "Payment for " + id + " declined");
        return order;
    }
}
    1. Constructor injection of ports. The core has no idea whether payments go to PayFast, a fake, or a test double.
    package com.handbook.architecture.hexagonal.checkout.port.in;

import com.handbook.architecture.hexagonal.checkout.domain.Order;

/** Driving (primary) port: what the application offers to the outside world. */
public interface PlaceOrderUseCase {

    record PlaceOrderCommand(String customerId, String phone, long totalPaise) {
        public PlaceOrderCommand {
            if (totalPaise <= 0) {
                throw new IllegalArgumentException("total must be positive");
            }
        }
    }

    Order placeOrder(PlaceOrderCommand command);
}

/** Driven (secondary) port: what the core needs from a payment provider, in the core's terms. */

}

import com.handbook.architecture.hexagonal.checkout.domain.Order;

/** Driven port for persistence. */
public interface OrderRepositoryPort {
    void save(Order order);

    int count();
}

/** Driven port for telling the customer something. SMS, push or e-mail is an adapter decision. */

}

    package com.handbook.architecture.hexagonal.checkout.adapter.out;

import com.handbook.architecture.hexagonal.checkout.port.out.PaymentPort;

import java.util.Map;
import java.util.function.Function;

/**
 * Driven adapter for a (fictional) payment provider "PayFast". It speaks PayFast's language:
 * rupee strings, a merchant key, and status codes, and translates back to the port's boolean.
 */
public class PayFastPaymentAdapter implements PaymentPort {

    private final Function<Map<String, String>, Map<String, String>> payFastApi; // the HTTP client

    public PayFastPaymentAdapter(Function<Map<String, String>, Map<String, String>> payFastApi) {
        this.payFastApi = payFastApi;
    }

    @Override
    public boolean charge(String customerId, long amountPaise, String reference) {
        Map<String, String> response = payFastApi.apply(Map.of(
                "merchant_key", "MK-GROCERY", // (1)!
                "amount", String.format("%d.%02d", amountPaise / 100, amountPaise % 100),
                "customer_ref", customerId,
                "txn_ref", reference));
        return "CAPTURED".equals(response.get("status")); // (2)!
    }
}
    1. Vendor-specific details (merchant key, rupee strings) live only in the adapter.
    2. The vendor's status codes are translated into the port's simple contract.
    package com.handbook.architecture.hexagonal.checkout.adapter.in;

import com.handbook.architecture.hexagonal.checkout.domain.Order;
import com.handbook.architecture.hexagonal.checkout.port.in.PlaceOrderUseCase;
import com.handbook.architecture.hexagonal.checkout.port.in.PlaceOrderUseCase.PlaceOrderCommand;

import java.util.Map;

/** Driving adapter: HTTP/JSON → command → use case → HTTP response. (A @RestController in Spring.) */
public class RestCheckoutAdapter {

    private final PlaceOrderUseCase useCase;

    public RestCheckoutAdapter(PlaceOrderUseCase useCase) {
        this.useCase = useCase;
    }

    public String post(Map<String, String> json) {
        try {
            Order o = useCase.placeOrder(new PlaceOrderCommand(json.get("customerId"), json.get("phone"),
                    Math.round(Double.parseDouble(json.get("totalRupees")) * 100)));
            return (o.status() == Order.Status.PAID ? "201 " : "402 ") + o;
        } catch (IllegalArgumentException e) {
            return "400 " + e.getMessage();
        }
    }
}

    package com.handbook.architecture.hexagonal.checkout.adapter.in;

import com.handbook.architecture.hexagonal.checkout.port.in.PlaceOrderUseCase;
import com.handbook.architecture.hexagonal.checkout.port.in.PlaceOrderUseCase.PlaceOrderCommand;

/** Another driving adapter: support staff place phone orders from a terminal. Same use case. */
public class CliCheckoutAdapter {

    private final PlaceOrderUseCase useCase;

    public CliCheckoutAdapter(PlaceOrderUseCase useCase) {
        this.useCase = useCase;
    }

    /** Input like: {@code order CUST-77 +91-98450-22222 64900} (amount in paise). */
    public String run(String commandLine) {
        String[] p = commandLine.split(" ");
        return "cli> " + useCase.placeOrder(new PlaceOrderCommand(p[1], p[2], Long.parseLong(p[3]))).status();
    }
}

    package com.handbook.architecture.hexagonal.checkout.adapter.out;

import com.handbook.architecture.hexagonal.checkout.domain.Order;
import com.handbook.architecture.hexagonal.checkout.port.out.OrderRepositoryPort;

import java.util.ArrayList;
import java.util.List;

/** Driven adapter for persistence. A JPA or JDBC adapter would implement the same port. */
public class InMemoryOrderRepository implements OrderRepositoryPort {

    private final List<Order> orders = new ArrayList<>();

    @Override
    public void save(Order order) {
        orders.add(order);
    }

    @Override
    public int count() {
        return orders.size();
    }
}

    package com.handbook.architecture.hexagonal.checkout.adapter.out;

import com.handbook.architecture.hexagonal.checkout.port.out.NotificationPort;

/** Driven adapter: sends an SMS (printed here instead of calling an SMS gateway). */
public class SmsNotificationAdapter implements NotificationPort {

    @Override

        System.out.println("    sms to " + phone + ": " + message);

}

import com.handbook.architecture.hexagonal.checkout.adapter.in.CliCheckoutAdapter;
import com.handbook.architecture.hexagonal.checkout.adapter.in.RestCheckoutAdapter;
import com.handbook.architecture.hexagonal.checkout.adapter.out.InMemoryOrderRepository;
import com.handbook.architecture.hexagonal.checkout.adapter.out.PayFastPaymentAdapter;
import com.handbook.architecture.hexagonal.checkout.adapter.out.SmsNotificationAdapter;
import com.handbook.architecture.hexagonal.checkout.domain.CheckoutService;

import java.util.Map;
import java.util.TreeMap;

public class HexagonalCheckoutDemo {

    public static void main(String[] args) {
        // Fake PayFast HTTP API: declines amounts over ₹5,000.
        var payFast = new PayFastPaymentAdapter(request -> {
            System.out.println("    PayFast API <- " + new TreeMap<>(request));
            boolean ok = Double.parseDouble(request.get("amount")) <= 5_000;
            return Map.of("status", ok ? "CAPTURED" : "DECLINED_LIMIT");
        });
        var repository = new InMemoryOrderRepository();
        var core = new CheckoutService(payFast, repository, new SmsNotificationAdapter()); // composition root

        var rest = new RestCheckoutAdapter(core);
        var cli = new CliCheckoutAdapter(core);

        System.out.println("=== Grocery: one core, two driving adapters, three driven adapters ===");
        System.out.println(rest.post(Map.of("customerId", "CUST-42", "phone", "+91-98450-11111", "totalRupees", "1447.00")));
        System.out.println(cli.run("order CUST-77 +91-98450-22222 899000"));
        System.out.println(rest.post(Map.of("customerId", "CUST-42", "phone", "+91-98450-11111", "totalRupees", "-5")));
        System.out.println("Orders saved: " + repository.count());
    }
}

    Why hexagonal here:

    • Switching payment providers = writing one new adapter.
    • The core is unit-tested with lambdas as adapters (see the tests); no Spring context, no database.

    Example 2: Swappable Routing for Fares (Ride-hailing)¶

    Scenario: The fare core needs a route (km, minutes). The GeoMaps adapter calls an online API that returns meters and seconds; an offline adapter estimates from straight-line distance. A composite fallback adapter tries GeoMaps and falls back offline when it's down. The fare rules never change.

    Full Code:

    package com.handbook.architecture.hexagonal.fare;

import java.util.Map;
import java.util.function.Function;

/** The fare core and its driven port for routing, with three interchangeable adapters. */
public final class FareHexagon {

    private FareHexagon() {
    }

    public record Point(double lat, double lon) {
    }

    public record Route(double km, int minutes, String source) {
    }

    /** Driven port, owned by the core and expressed in its units (km, minutes). */
    public interface RoutePort {
        Route route(Point from, Point to);
    }

    /** The core: fare rules only. */
    public static final class FareCalculator {
        private final RoutePort routes;

        public FareCalculator(RoutePort routes) {
            this.routes = routes;
        }

        public String quote(Point from, Point to) {
            Route r = routes.route(from, to);
            long paise = 5_000 + Math.round(r.km() * 1_200) + r.minutes() * 150L; // base + per km + per minute
            return String.format("₹%d.%02d for %.1f km / %d min (route from %s)",
                    paise / 100, paise % 100, r.km(), r.minutes(), r.source());
        }
    }

    /** Adapter for a (fictional) online maps API returning meters and seconds as JSON-ish maps. */
    public static final class GeoMapsAdapter implements RoutePort {
        private final Function<String, Map<String, Long>> api;

        public GeoMapsAdapter(Function<String, Map<String, Long>> api) {
            this.api = api;
        }

        @Override
        public Route route(Point from, Point to) {
            Map<String, Long> json = api.apply(from.lat() + "," + from.lon() + ";" + to.lat() + "," + to.lon());
            return new Route(json.get("distance_m") / 1000.0, (int) (json.get("duration_s") / 60), "GeoMaps traffic"); // (1)!
        }
    }

    /** Adapter that needs no network: straight-line distance × detour factor, average city speed. */
    public static final class OfflineEstimateAdapter implements RoutePort {
        @Override
        public Route route(Point from, Point to) {
            double dLat = StrictMath.toRadians(to.lat() - from.lat());
            double dLon = StrictMath.toRadians(to.lon() - from.lon());
            double a = StrictMath.pow(StrictMath.sin(dLat / 2), 2) + StrictMath.cos(StrictMath.toRadians(from.lat()))
                    * StrictMath.cos(StrictMath.toRadians(to.lat())) * StrictMath.pow(StrictMath.sin(dLon / 2), 2);
            double km = 6371 * 2 * StrictMath.atan2(StrictMath.sqrt(a), StrictMath.sqrt(1 - a)) * 1.3; // (2)!
            return new Route(km, (int) Math.ceil(km / 22 * 60), "offline estimate");
        }
    }

    /** Adapters compose: try the primary, fall back to the secondary. The core never knows. */
    public static final class FallbackRouteAdapter implements RoutePort {
        private final RoutePort primary;
        private final RoutePort fallback;

        public FallbackRouteAdapter(RoutePort primary, RoutePort fallback) {
            this.primary = primary;
            this.fallback = fallback;
        }

        @Override
        public Route route(Point from, Point to) {
            try {
                return primary.route(from, to);
            } catch (RuntimeException e) {
                return fallback.route(from, to); // (3)!
            }
        }
    }
}
    1. The adapter converts the API's units (meters, seconds) into the port's units (km, minutes).
    2. Haversine distance × 1.3 detour factor. StrictMath keeps results identical on every platform.
    3. Adapters can be composed (a Decorator/Composite of ports) for resilience, invisible to the core.
    package com.handbook.architecture.hexagonal.fare;

import com.handbook.architecture.hexagonal.fare.FareHexagon.FallbackRouteAdapter;
import com.handbook.architecture.hexagonal.fare.FareHexagon.FareCalculator;
import com.handbook.architecture.hexagonal.fare.FareHexagon.GeoMapsAdapter;
import com.handbook.architecture.hexagonal.fare.FareHexagon.OfflineEstimateAdapter;
import com.handbook.architecture.hexagonal.fare.FareHexagon.Point;

import java.util.Map;

public class FareDemo {

    public static void main(String[] args) {
        Point koramangala = new Point(12.9352, 77.6245);
        Point airport = new Point(13.1986, 77.7066);
        boolean[] mapsUp = {true};
        var geoMaps = new GeoMapsAdapter(query -> {
            if (!mapsUp[0]) {
                throw new IllegalStateException("GeoMaps 503");
            }
            return Map.of("distance_m", 38_400L, "duration_s", 4_020L);
        });

        System.out.println("=== Ride-hailing: same fare core, swappable routing adapters ===");
        System.out.println("GeoMaps adapter  : " + new FareCalculator(geoMaps).quote(koramangala, airport));
        System.out.println("Offline adapter  : " + new FareCalculator(new OfflineEstimateAdapter()).quote(koramangala, airport));

        var resilient = new FareCalculator(new FallbackRouteAdapter(geoMaps, new OfflineEstimateAdapter()));
        mapsUp[0] = false;
        System.out.println("GeoMaps down     : " + resilient.quote(koramangala, airport));
    }
}

    Output:

    === Ride-hailing: same fare core, swappable routing adapters ===
GeoMaps adapter  : ₹611.30 for 38.4 km / 67 min (route from GeoMaps traffic)
Offline adapter  : ₹691.00 for 39.8 km / 109 min (route from offline estimate)
GeoMaps down     : ₹691.00 for 39.8 km / 109 min (route from offline estimate)

    Why hexagonal here:

    • External dependencies are replaceable and composable.
    • Each adapter can be tested against recorded API responses; the core against a trivial fake.

    Example 3: One Use Case, Event and Batch Channels (Insurance)¶

    Scenario: Claims come from the mobile app (as events on a topic) and from a partner garage network (as a nightly CSV). Two driving adapters parse their formats and call the same SubmitClaim port, so validation and triage rules are identical for every channel.

    Full Code:

    package com.handbook.architecture.hexagonal.claims;

import java.util.ArrayList;
import java.util.List;

/** The claims core with ONE driving port used by two very different driving adapters. */
public final class ClaimsHexagon {

    private ClaimsHexagon() {
    }

    public record Claim(String policy, String type, long amountPaise) {
    }

    /** Driving port. */
    public interface SubmitClaim {
        String submit(Claim claim);
    }

    /** The core: validation and a simple triage rule. */
    public static final class ClaimsCore implements SubmitClaim {
        private final List<Claim> accepted = new ArrayList<>();

        @Override
        public String submit(Claim c) {
            if (!c.policy().matches("POL-\\d{4}")) {
                return "REJECTED " + c.policy() + ": invalid policy number";
            }
            if (c.amountPaise() <= 0) {
                return "REJECTED " + c.policy() + ": amount must be positive";
            }
            accepted.add(c);
            String route = c.amountPaise() > 5_000_000 ? "manual review" : "fast track"; // (1)!
            return "ACCEPTED " + c.policy() + " " + c.type() + " -> " + route;
        }

        public int acceptedCount() {
            return accepted.size();
        }
    }

    /** Driving adapter 1: an event from the mobile app arrives on a message topic. */
    public static final class MobileClaimListener {
        private final SubmitClaim port;

        public MobileClaimListener(SubmitClaim port) {
            this.port = port;
        }

        public String onMessage(String json) { // {"policy":"POL-1234","type":"MOTOR","amount":"12500.00"}
            String body = json.replaceAll("[{}\"]", "");
            String policy = null;
            String type = null;
            long paise = 0;
            for (String field : body.split(",")) {
                String[] kv = field.split(":");
                switch (kv[0]) {
                    case "policy" -> policy = kv[1];
                    case "type" -> type = kv[1];
                    case "amount" -> paise = Math.round(Double.parseDouble(kv[1]) * 100);
                    default -> { }
                }
            }
            return "[topic] " + port.submit(new Claim(policy, type, paise));
        }
    }

    /** Driving adapter 2: a nightly CSV file from a partner garage network. */
    public static final class GarageCsvImporter {
        private final SubmitClaim port;

        public GarageCsvImporter(SubmitClaim port) {
            this.port = port;
        }

        public List<String> importFile(List<String> lines) {
            return lines.stream().skip(1) // header
                    .map(l -> l.split(";"))
                    .map(f -> "[csv]   " + port.submit(new Claim(f[0].trim(), "MOTOR", Long.parseLong(f[1].trim()))))
                    .toList();
        }
    }
}
    1. Triage is a core decision; neither adapter knows the ₹50,000 threshold.
    package com.handbook.architecture.hexagonal.claims;

import com.handbook.architecture.hexagonal.claims.ClaimsHexagon.ClaimsCore;
import com.handbook.architecture.hexagonal.claims.ClaimsHexagon.GarageCsvImporter;
import com.handbook.architecture.hexagonal.claims.ClaimsHexagon.MobileClaimListener;

import java.util.List;

public class ClaimsDemo {

    public static void main(String[] args) {
        ClaimsCore core = new ClaimsCore();
        var listener = new MobileClaimListener(core);
        var importer = new GarageCsvImporter(core);

        System.out.println("=== Insurance: claims arrive by event and by nightly file, one core ===");
        System.out.println(listener.onMessage("{\"policy\":\"POL-1234\",\"type\":\"MOTOR\",\"amount\":\"12500.00\"}"));
        System.out.println(listener.onMessage("{\"policy\":\"PX-99\",\"type\":\"HEALTH\",\"amount\":\"800.00\"}"));
        importer.importFile(List.of(
                "policy;amount_paise",
                "POL-5678; 7500000",
                "POL-9012; 0")).forEach(System.out::println);
        System.out.println("Accepted claims: " + core.acceptedCount() + " (same rules for every channel)");
    }
}

    === Insurance: claims arrive by event and by nightly file, one core ===

    Why hexagonal here:

    • Driving adapters are as replaceable as driven ones: an API, a topic, a file, or a test.
    • No more "the batch import has slightly different rules".

    6. Variations & Modern Java Take¶

    checkout/
├── domain/            Order, CheckoutService          ← no framework imports
├── port/in/           PlaceOrderUseCase
├── port/out/          PaymentPort, OrderRepositoryPort, NotificationPort
├── adapter/in/web/    CheckoutController (@RestController)
├── adapter/in/cli/    CliCheckoutAdapter
├── adapter/out/jpa/   OrderJpaAdapter (@Repository, JPA entities live here)
├── adapter/out/payfast/ PayFastPaymentAdapter
└── config/            @Configuration wiring adapters to ports
    • Spring wiring: the core classes stay annotation-free; a @Configuration class creates them as beans with adapters injected.
    • JPA entities live in the adapter, mapped to domain objects, so the domain isn't shaped by ORM needs. (A pragmatic variant allows JPA annotations in the domain; decide consciously.)
    • Testing pyramid: core unit tests with fakes; adapter integration tests (Testcontainers for DB, WireMock for HTTP); a few end-to-end tests.
    • Contract tests for ports keep fakes honest (see the coding challenge).

    7. Where It Lives in Real Frameworks¶

    Where Ports & adapters
    Spring Boot apps structured as hexagons Core + @Configuration wiring; ArchUnit's onionArchitecture() checks it
    jMolecules Annotations (@Port, @Adapter) and ArchUnit rules for architecture concepts
    Micronaut / Quarkus apps Same structure; frameworks only in adapters
    Testcontainers / WireMock Test driven adapters against real dependencies

    8. Pros, Cons & Trade-offs¶

    ✅ Pros ❌ Cons
    Core testable without infrastructure More interfaces and mapping code
    Adapters swappable (vendor, DB, channel) Overkill for simple CRUD
    Multiple channels share one use case Team discipline needed to keep frameworks out of the core
    Postpone technology decisions Mapping between domain and persistence models takes effort

    9. Pitfalls & Anti-Patterns¶

    Ports shaped like the vendor's API

    A PaymentPort with merchantKey and PayFastStatus defeats the purpose. Define ports in the core's language.

    Framework annotations creeping into the core

    @Transactional, @Entity and @JsonProperty in domain classes bind the core to frameworks. Keep them in adapters or configuration.

    One port per method, interfaces everywhere

    Ports should be cohesive, per capability (payments, orders), not one interface per method or per class "just in case".

    Fakes that lie

    A fake adapter that behaves differently from the real one makes core tests pass while production fails. Run the same contract tests against both.

    10. Senior / Architect Deep Dive (10–15 yrs)¶

    Hexagonal vs. Clean vs. Onion. All three apply the dependency rule (dependencies point inward to the domain). Hexagonal emphasizes ports and adapters, symmetric for driving and driven sides; Onion emphasizes concentric layers (domain model, domain services, application services); Clean adds named circles (entities, use cases, interface adapters, frameworks) and presenters. In practice, teams mix their vocabulary.

    Transactions and cross-cutting concerns. Use-case boundaries are natural transaction boundaries; apply them with decorators or Spring AOP around port implementations, keeping the core annotation-free if you want strict purity.

    When the hexagon pays off. Several integrations, long lifespan, changing vendors, or heavy testing needs. For a two-table CRUD admin app, a layered design is cheaper.

    Explain it in 2 minutes (system design / architecture round)¶

    "I'd structure the checkout service as a hexagon. The core holds the domain model and use cases, with driving ports like PlaceOrderUseCase and driven ports like PaymentPort and OrderRepositoryPort, all in business terms. Adapters on the outside: a REST controller and a Kafka listener drive it; a JPA adapter, a payment-provider client and an SMS client implement the driven ports. Spring wiring lives in configuration. Core tests run in milliseconds with fakes, contract tests keep fakes honest, and ArchUnit fails the build if the core imports an adapter. Changing payment provider is one new adapter."

    War story: the payment provider migration

    A food-delivery company had to switch payment providers within 8 weeks after a pricing dispute. The old provider's SDK types appeared in 140 classes, including discount and refund logic. The migration took 5 months and caused two incidents where refunds were issued in the wrong currency unit. Fix (for the next migration): a PaymentPort in business terms; all provider specifics in one adapter per provider; contract tests run against both adapters; a feature flag to route by merchant. Lesson: vendor types inside the core turn a vendor change into a rewrite.

    12. Interview Corner¶

    Q1. What is hexagonal architecture?

    An architecture where the business core is isolated and talks to the outside world only through ports (interfaces), with adapters implementing them for specific technologies.

    Q2. What is a port? What is an adapter?

    A port is an interface owned by the core (what it offers or needs); an adapter is a concrete implementation for a technology (REST, JPA, Kafka, a vendor API).

    Q3. Driving vs. driven adapters?

    Driving adapters call into the core (controllers, listeners, tests); driven adapters are called by the core (databases, external APIs).

    Q4. Main benefit?

    The core can be tested and changed without infrastructure, and technologies can be swapped by writing new adapters.

    Q5. Why "hexagon"?

    Just a drawing convention showing many sides (ports); the number six has no meaning.

    Q1. Where do JPA entities go?

    In the persistence adapter, mapped to domain objects, or pragmatically in the domain if the team accepts the coupling.

    Q2. How do you wire it in Spring?

    Keep core classes free of annotations and create them as beans in a @Configuration class, injecting adapters for the ports.

    Q3. How do you test each part?

    Core: unit tests with fakes. Adapters: integration tests (Testcontainers, WireMock). Plus contract tests per port and a few end-to-end tests.

    Q4. Hexagonal vs. layered?

    Layered has business depending on persistence; hexagonal inverts that so both depend on ports owned by the core.

    Q5. How do you enforce the rules?

    ArchUnit (onionArchitecture() or custom noClasses() rules), separate Maven/Gradle modules, or jMolecules.

    Q1. "When is hexagonal not worth it?"

    Small CRUD apps or short-lived prototypes, where mapping and extra interfaces cost more than they save.

    Q2. "How do transactions work across ports?"

    The use case is the transaction boundary; the transaction manager is applied around it (AOP/decorator), and repository adapters join it. Cross-system consistency needs sagas/outbox.

    Q3. "How do hexagons relate to microservices?"

    Each service can be a hexagon; inter-service clients are driven adapters and API endpoints/listeners are driving adapters. An ACL is a special driven adapter.

    Q4. "Hexagonal vs. Clean: real differences?"

    Clean adds explicit circles and the presenter/output-boundary idea; hexagonal is simpler and symmetric. Both enforce inward dependencies.

    Q5. "How do you prevent port explosion?"

    Group by capability, keep ports coarse-grained around use cases, and only introduce a port where you need substitution or isolation.

    Problem: Fakes make core tests fast, but only if they behave like the real adapter. Write a contract that any PaymentPort adapter must pass, and run it against the real PayFast adapter (with a stubbed HTTP API), a correct fake, and a buggy fake.

    Solution 
    package com.handbook.architecture.hexagonal.contract;

import com.handbook.architecture.hexagonal.checkout.port.out.PaymentPort;

import java.util.ArrayList;
import java.util.List;

/**
 * Coding challenge: a contract every PaymentPort adapter must satisfy, run against the real adapter
 * (with a stubbed HTTP API) and the in-memory test adapter. If both pass, tests of the core that use
 * the fake are trustworthy.
 */
public final class PaymentPortContract {

    private PaymentPortContract() {
    }

    /** Assumes the adapter's environment accepts amounts up to ₹5,000 and declines above. */
    public static List<String> verify(String name, PaymentPort adapter) {
        List<String> results = new ArrayList<>();
        check(results, name, "small payment is captured", adapter.charge("C1", 10_000, "R1"));
        check(results, name, "payment above the limit is declined", !adapter.charge("C1", 900_000, "R2"));
        check(results, name, "boundary ₹5,000.00 is captured", adapter.charge("C1", 500_000, "R3"));
        return results;
    }

    private static void check(List<String> results, String adapter, String rule, boolean ok) {
        results.add((ok ? "PASS " : "FAIL ") + adapter + ": " + rule);
    }
}

    package com.handbook.architecture.hexagonal.contract;

import com.handbook.architecture.hexagonal.checkout.adapter.out.PayFastPaymentAdapter;
import com.handbook.architecture.hexagonal.checkout.port.out.PaymentPort;

import java.util.Map;

public class ContractDemo {

    public static void main(String[] args) {
        PaymentPort payFast = new PayFastPaymentAdapter(req ->
                Map.of("status", Double.parseDouble(req.get("amount")) <= 5_000 ? "CAPTURED" : "DECLINED_LIMIT"));
        PaymentPort fake = (customer, paise, ref) -> paise <= 500_000;
        PaymentPort buggyFake = (customer, paise, ref) -> paise < 500_000; // off-by-one at the boundary

        System.out.println("=== Challenge: one contract test suite for every PaymentPort adapter ===");
        PaymentPortContract.verify("PayFastAdapter", payFast).forEach(System.out::println);
        PaymentPortContract.verify("InMemoryFake", fake).forEach(System.out::println);
        PaymentPortContract.verify("BuggyFake", buggyFake).forEach(System.out::println);
    }
}

    Output:

    === Challenge: one contract test suite for every PaymentPort adapter ===
PASS PayFastAdapter: small payment is captured
PASS PayFastAdapter: payment above the limit is declined
PASS PayFastAdapter: boundary ₹5,000.00 is captured
PASS InMemoryFake: small payment is captured
PASS InMemoryFake: payment above the limit is declined
PASS InMemoryFake: boundary ₹5,000.00 is captured
PASS BuggyFake: small payment is captured
PASS BuggyFake: payment above the limit is declined
FAIL BuggyFake: boundary ₹5,000.00 is captured

    Key points to say: the contract encodes the port's behavioural expectations (including boundaries); in JUnit, write it as an abstract test class with one subclass per adapter. The buggy fake fails the boundary case, which would otherwise let core tests pass incorrectly.

    • S: Our order service's tests took 25 minutes because every test booted Spring and a database; developers stopped running them.
    • T: Fast, reliable feedback on business logic.
    • A: Refactored the core into a hexagon: ports for persistence, payments and notifications; moved JPA and vendor SDKs into adapters; added contract tests; kept a slim set of Testcontainers integration tests.
    • R: 900 core tests ran in 8 seconds; the full suite dropped to 4 minutes; a later payment-provider switch took 2 weeks.

    13. Quick Revision Card¶

    Remember in 30 seconds

    • Core in the middle; ports (owned by the core) at the edge; adapters outside.
    • Driving adapters call in; driven adapters are called out.
    • Dependencies point inward; frameworks and vendors only in adapters.
    • Test the core with fakes; keep fakes honest with contract tests.
    • Swap vendors and add channels by writing adapters.
