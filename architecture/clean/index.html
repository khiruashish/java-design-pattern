    Advanced Architecture

    Clean Architecture¶

    🔴 Advanced Architecture Interview frequency ⭐⭐⭐⭐

    TL;DR

    Arrange code in concentric circles: entities (enterprise rules) → use cases (application rules) → interface adapters (controllers, presenters, gateways) → frameworks and drivers (web, DB, UI). Source-code dependencies may only point inward. Business rules don't know about the web, the database or the framework, so those can change, and the rules can be tested in isolation.

    1. Intent & Problem It Solves¶

    The problem in plain English: the coupon rules of a grocery app are written inside a Spring controller, read data via JPA entities, and return a JSON map. Adding a mobile app with a different response shape means duplicating the rules; upgrading Spring breaks business logic; nobody can say where "the rules" actually are.

    Definition (Robert C. Martin, Clean Architecture):

    The Dependency Rule: source code dependencies must point only inward, toward higher-level policies. Nothing in an inner circle can know anything at all about something in an outer circle.

    Circle Contains Example
    Entities Enterprise-wide business rules Coupon.evaluate(), Account.withdraw()
    Use cases Application-specific rules; input/output boundaries; request/response models; gateway interfaces ApplyCoupon.Interactor
    Interface adapters Controllers, presenters, gateway implementations; convert data between use cases and the outside CouponController, WebPresenter
    Frameworks & drivers Web framework, DB, UI, devices Spring MVC, PostgreSQL, Android

    2. Real-World Analogy¶

    A country's constitution, laws and offices

    The constitution (entities) changes rarely and doesn't mention any specific government office. Laws (use cases) build on the constitution. Government offices and forms (adapters) implement the laws for citizens, and the buildings and computers (frameworks) can be replaced without changing a single law.

    sequenceDiagram
    participant C as Controller (adapter)
    participant I as Interactor (use case)
    participant G as Gateway (interface in use-case circle)
    participant En as Entity
    participant P as Presenter (adapter)
    C->>I: Request model
    I->>G: load data
    I->>En: apply rules
    I->>P: Response model (via output boundary)
    P->>P: build view model

    Flow of control vs. dependencies: control flows outward (interactor → presenter), but the interactor only knows the output boundary interface defined in its own circle; the presenter implements it. That's dependency inversion.

    4. Naive Approach (Without the Pattern)¶

    @PostMapping("/cart/{id}/coupon")
Map<String, Object> apply(@PathVariable String id, @RequestParam String code) {
    CartEntity cart = cartJpaRepo.findById(id).orElseThrow();
    CouponEntity c = couponJpaRepo.findByCode(code.toUpperCase());
    if (c.getExpires().isBefore(LocalDate.now())) return Map.of("error", "expired");   // rule + clock
    long discount = Math.min(c.getMax(), cart.getSubtotal() * c.getPercent() / 100);   // rule
    return Map.of("total", "₹" + (cart.getSubtotal() - discount) / 100);              // formatting
}

    5. Three Real-World Examples¶

    Example 1: Apply a Coupon, Two Presenters (Grocery)¶

    Scenario: The Coupon entity knows the rules (expiry, minimum basket, percentage, cap). The ApplyCoupon interactor loads data through gateway interfaces and reports a response model through an output boundary. A web presenter turns it into a detailed JSON view model; a mobile presenter into a one-line toast. The calendar is a gateway too, so the use case is deterministic in tests.

    Full Code:

    package com.handbook.architecture.clean.coupon.entities;

import java.time.LocalDate;

/**
 * Entity (innermost circle): enterprise-wide business rules that would exist even without this app.
 * No dependencies on anything outside this circle.
 */
public record Coupon(String code, int percentOff, long minSubtotalPaise, long maxDiscountPaise, LocalDate expires) {

    public sealed interface Outcome permits Discount, NotApplicable {
    }

    public record Discount(long paise) implements Outcome {
    }

    public record NotApplicable(String reason) implements Outcome {
    }

    public Outcome evaluate(long subtotalPaise, LocalDate today) {
        if (today.isAfter(expires)) {
            return new NotApplicable("coupon expired on " + expires);
        }
        if (subtotalPaise < minSubtotalPaise) {
            return new NotApplicable("add ₹" + (minSubtotalPaise - subtotalPaise) / 100 + " more to use " + code);
        }
        return new Discount(Math.min(maxDiscountPaise, subtotalPaise * percentOff / 100));
    }
}

    package com.handbook.architecture.clean.coupon.usecase;

import com.handbook.architecture.clean.coupon.entities.Coupon;

import java.time.LocalDate;
import java.util.Optional;

/**
 * Use-case circle: the boundaries (input/output ports), request/response models, the gateways the
 * use case needs, and the interactor. It depends only on entities.
 */
public final class ApplyCoupon {

    private ApplyCoupon() {
    }

    public record Request(String cartId, String couponCode) { // (1)!
    }

    public record Response(boolean applied, long subtotalPaise, long discountPaise, String message) {
    }

    public interface InputBoundary {
        void apply(Request request, OutputBoundary presenter);
    }

    public interface OutputBoundary { // (2)!
        void present(Response response);
    }

    public interface CartGateway {
        Optional<Long> subtotalOf(String cartId);
    }

    public interface CouponGateway {
        Optional<Coupon> find(String code);
    }

    public interface Calendar {
        LocalDate today();
    }

    public static final class Interactor implements InputBoundary {
        private final CartGateway carts;
        private final CouponGateway coupons;
        private final Calendar calendar;

        public Interactor(CartGateway carts, CouponGateway coupons, Calendar calendar) {
            this.carts = carts;
            this.coupons = coupons;
            this.calendar = calendar;
        }

        @Override
        public void apply(Request request, OutputBoundary presenter) {
            long subtotal = carts.subtotalOf(request.cartId()).orElse(0L);
            Optional<Coupon> coupon = coupons.find(request.couponCode().trim().toUpperCase());
            if (coupon.isEmpty()) {
                presenter.present(new Response(false, subtotal, 0, "unknown coupon " + request.couponCode()));
                return;
            }
            switch (coupon.get().evaluate(subtotal, calendar.today())) { // (3)!
                case Coupon.Discount d -> presenter.present(new Response(true, subtotal, d.paise(), "coupon applied"));
                case Coupon.NotApplicable n -> presenter.present(new Response(false, subtotal, 0, n.reason()));
            }
        }
    }
}
    1. Request model: plain data crossing the boundary; no HTTP types.
    2. Output boundary: implemented by presenters in the outer circle (dependency inversion).
    3. The entity's sealed Outcome lets the compiler check that every case is handled.
    package com.handbook.architecture.clean.coupon.adapters;

import com.handbook.architecture.clean.coupon.entities.Coupon;
import com.handbook.architecture.clean.coupon.usecase.ApplyCoupon;

import java.time.LocalDate;
import java.util.Map;
import java.util.Optional;

/**
 * Interface-adapters circle: controllers turn web/app input into request models, presenters turn
 * response models into view models, gateways implement the use case's data interfaces.
 */
public final class CouponAdapters {

    private CouponAdapters() {
    }

    /** Controller: knows the HTTP shape of the input, nothing about rules. */
    public static final class CouponController {
        private final ApplyCoupon.InputBoundary useCase;

        public CouponController(ApplyCoupon.InputBoundary useCase) {
            this.useCase = useCase;
        }

        public void post(Map<String, String> form, ApplyCoupon.OutputBoundary presenter) {
            useCase.apply(new ApplyCoupon.Request(form.get("cart"), form.getOrDefault("code", "")), presenter);
        }
    }

    /** Web presenter: a detailed view model with rupee strings for the desktop basket page. */
    public static final class WebPresenter implements ApplyCoupon.OutputBoundary {
        public String viewModel;

        @Override
        public void present(ApplyCoupon.Response r) { // (1)!
            viewModel = String.format("{\"ok\":%s,\"subtotal\":\"₹%,.2f\",\"discount\":\"-₹%,.2f\",\"total\":\"₹%,.2f\",\"note\":\"%s\"}",
                    r.applied(), r.subtotalPaise() / 100.0, r.discountPaise() / 100.0,
                    (r.subtotalPaise() - r.discountPaise()) / 100.0, r.message());
        }
    }

    /** Mobile presenter: one short line for a toast message. */
    public static final class MobileToastPresenter implements ApplyCoupon.OutputBoundary {
        public String viewModel;

        @Override
        public void present(ApplyCoupon.Response r) {
            viewModel = r.applied() ? "🎉 You saved ₹" + r.discountPaise() / 100 : "⚠ " + r.message();
        }
    }

    /** Gateways: in-memory here; JPA, Redis or a remote API in production. */
    public static ApplyCoupon.CartGateway carts(Map<String, Long> subtotals) {
        return id -> Optional.ofNullable(subtotals.get(id));
    }

    public static ApplyCoupon.CouponGateway coupons(Map<String, Coupon> byCode) {
        return code -> Optional.ofNullable(byCode.get(code));
    }

    public static ApplyCoupon.Calendar fixedCalendar(LocalDate date) {
        return () -> date;
    }
}
    1. The presenter owns formatting: currency, wording, JSON shape. The use case never formats.
    package com.handbook.architecture.clean.coupon;

import com.handbook.architecture.clean.coupon.adapters.CouponAdapters;
import com.handbook.architecture.clean.coupon.adapters.CouponAdapters.CouponController;
import com.handbook.architecture.clean.coupon.adapters.CouponAdapters.MobileToastPresenter;
import com.handbook.architecture.clean.coupon.adapters.CouponAdapters.WebPresenter;
import com.handbook.architecture.clean.coupon.entities.Coupon;
import com.handbook.architecture.clean.coupon.usecase.ApplyCoupon;

import java.time.LocalDate;
import java.util.Map;

public class CleanCouponDemo {

    public static void main(String[] args) {
        // "Main" component: the only place that knows every concrete class.
        var useCase = new ApplyCoupon.Interactor(
                CouponAdapters.carts(Map.of("CART-1", 144_700L, "CART-2", 39_900L)),
                CouponAdapters.coupons(Map.of(
                        "MANGO20", new Coupon("MANGO20", 20, 50_000, 20_000, LocalDate.of(2026, 10, 31)),
                        "DIWALI10", new Coupon("DIWALI10", 10, 0, 50_000, LocalDate.of(2025, 11, 5)))),

        var controller = new CouponController(useCase);

        System.out.println("=== Grocery: one use case, two presenters ===");
        WebPresenter web = new WebPresenter();
        controller.post(Map.of("cart", "CART-1", "code", "mango20"), web);
        System.out.println("web    CART-1 MANGO20  -> " + web.viewModel);

        MobileToastPresenter mobile = new MobileToastPresenter();
        controller.post(Map.of("cart", "CART-1", "code", "MANGO20"), mobile);
        System.out.println("mobile CART-1 MANGO20  -> " + mobile.viewModel);
        controller.post(Map.of("cart", "CART-2", "code", "MANGO20"), mobile);
        System.out.println("mobile CART-2 MANGO20  -> " + mobile.viewModel);
        controller.post(Map.of("cart", "CART-1", "code", "DIWALI10"), mobile);
        System.out.println("mobile CART-1 DIWALI10 -> " + mobile.viewModel);
    }
}

    === Grocery: one use case, two presenters ===

    Why Clean here:

    • Rules live in one place (entity), application flow in another (interactor), formatting in presenters.
    • A new channel = a new presenter; no rule changes.
    • Fully testable without Spring or a database (ArchUnit enforces the dependency rule in the tests).

    Example 2: Transfer Funds, One Response for Two Audiences (Banking)¶

    Scenario: The Account entity enforces balance and daily-limit rules. The interactor orchestrates the transfer and produces one response model. The API presenter shows customer-friendly messages with HTTP codes; the audit presenter writes a detailed compliance line. Both receive the same facts.

    Full Code:

    package com.handbook.architecture.clean.transfer;

import java.util.HashMap;
import java.util.Map;

/**
 * Banking transfer in Clean Architecture terms. The entity enforces account rules; the interactor
 * orchestrates; TWO presenters render the same response model for different audiences.
 */
public final class TransferFunds {

    private TransferFunds() {
    }

    /** Entity: rules that hold for every application the bank builds. */
    public static final class Account {
        private final String id;
        private long balance;
        private long withdrawnToday;
        private final long dailyLimit;

        public Account(String id, long balance, long dailyLimit) {
            this.id = id;
            this.balance = balance;
            this.dailyLimit = dailyLimit;
        }

        void withdraw(long paise) {
            if (paise > balance) {
                throw new IllegalStateException("insufficient funds");
            }
            if (withdrawnToday + paise > dailyLimit) {
                throw new IllegalStateException("daily transfer limit exceeded");
            }
            balance -= paise;
            withdrawnToday += paise;
        }

        void deposit(long paise) {
            balance += paise;
        }

        public long balance() {
            return balance;
        }

        public String id() {
            return id;
        }
    }

    public record Request(String from, String to, long paise, String channel) {
    }

    public record Response(boolean ok, String from, String to, long paise, String reason, long fromBalanceAfter) {
    }

    public interface Presenter {
        void present(Response response);
    }

    public interface AccountGateway {
        Account load(String id);

        void save(Account account);
    }

    /** Interactor: application-specific orchestration. Knows nothing about HTTP or logs. */
    public static final class Interactor {
        private final AccountGateway accounts;

        public Interactor(AccountGateway accounts) {
            this.accounts = accounts;
        }

        public void transfer(Request r, Presenter presenter) {
            Account from = accounts.load(r.from());
            Account to = accounts.load(r.to());
            try {
                from.withdraw(r.paise()); // (1)!
                to.deposit(r.paise());
                accounts.save(from);
                accounts.save(to);
                presenter.present(new Response(true, r.from(), r.to(), r.paise(), "", from.balance()));
            } catch (IllegalStateException rule) {
                presenter.present(new Response(false, r.from(), r.to(), r.paise(), rule.getMessage(), from.balance()));
            }
        }
    }

    /** Presenter 1: the mobile API, with HTTP status and customer-friendly text. */
    public static final class ApiPresenter implements Presenter {
        public String output;

        @Override
        public void present(Response r) {
            output = r.ok() ? "200 {\"message\":\"Sent ₹" + r.paise() / 100 + "\"}"
                    : "422 {\"message\":\"Transfer failed: " + r.reason() + "\"}";
        }
    }

    /** Presenter 2: the compliance audit log, with everything an auditor needs. */
    public static final class AuditPresenter implements Presenter {
        public String output;

        @Override
        public void present(Response r) {
            output = String.format("AUDIT result=%s from=%s to=%s amount=%d reason=%s balance_after=%d",
                    r.ok() ? "OK" : "REJECTED", r.from(), r.to(), r.paise(), r.reason().isEmpty() ? "-" : r.reason(),
                    r.fromBalanceAfter());
        }
    }

    /** Gateway implementation (interface-adapters circle). */
    public static final class InMemoryAccounts implements AccountGateway {
        private final Map<String, Account> accounts = new HashMap<>();

        public InMemoryAccounts with(Account a) {
            accounts.put(a.id(), a);
            return this;
        }

        @Override
        public Account load(String id) {
            return accounts.get(id);
        }

        @Override
        public void save(Account account) {
            accounts.put(account.id(), account);
        }
    }
}
    1. Rules are enforced by the entity; the interactor only coordinates and reports.
    package com.handbook.architecture.clean.transfer;

import com.handbook.architecture.clean.transfer.TransferFunds.Account;
import com.handbook.architecture.clean.transfer.TransferFunds.ApiPresenter;
import com.handbook.architecture.clean.transfer.TransferFunds.AuditPresenter;
import com.handbook.architecture.clean.transfer.TransferFunds.InMemoryAccounts;
import com.handbook.architecture.clean.transfer.TransferFunds.Interactor;
import com.handbook.architecture.clean.transfer.TransferFunds.Presenter;
import com.handbook.architecture.clean.transfer.TransferFunds.Request;
import com.handbook.architecture.clean.transfer.TransferFunds.Response;

public class TransferDemo {

    public static void main(String[] args) {
        var accounts = new InMemoryAccounts()
                .with(new Account("A-1", 10_000_000, 5_000_000))
                .with(new Account("B-2", 0, 5_000_000));
        var interactor = new Interactor(accounts);

        System.out.println("=== Banking: one interactor, a response model rendered twice ===");
        for (long paise : new long[] {2_000_000, 4_000_000, 20_000_000}) {
            ApiPresenter api = new ApiPresenter();
            AuditPresenter audit = new AuditPresenter();
            interactor.transfer(new Request("A-1", "B-2", paise, "app"), both(api, audit));
            System.out.println(api.output);
            System.out.println("  " + audit.output);
        }
    }

    private static Presenter both(Presenter a, Presenter b) {
        return (Response r) -> {
            a.present(r);
            b.present(r);
        };
    }
}

    === Banking: one interactor, a response model rendered twice ===

  AUDIT result=REJECTED from=A-1 to=B-2 amount=4000000 reason=daily transfer limit exceeded balance_after=8000000

    Why Clean here:

    • Customer messaging and compliance logging evolve independently, without touching rules.
    • Entities are reusable across apps (branch system, mobile app, batch).

    Example 3: Prescription Refills with a Sealed Result (Healthcare)¶

    Scenario: A modern-Java variation: instead of an output-boundary callback, the use case returns a sealed Result (Approved, NeedsDoctor, Rejected). The outermost web layer maps each case to an HTTP status with an exhaustive switch. Controlled substances always go to the doctor; expired prescriptions too; other patients' prescriptions are invisible.

    Full Code:

    package com.handbook.architecture.clean.refill;

import java.time.LocalDate;
import java.util.Map;

/**
 * A modern-Java variation: instead of an output boundary, the use case returns a sealed Result.
 * The web layer (outermost circle) maps each case to HTTP. Same dependency rule: inner code never
 * mentions HTTP.
 */
public final class RefillPrescription {

    private RefillPrescription() {
    }

    public record Prescription(String id, String patient, String drug, int refillsLeft, LocalDate validUntil,
                               boolean controlledSubstance) {
    }

    public sealed interface Result permits Approved, NeedsDoctor, Rejected {
    }

    public record Approved(String drug, int refillsLeft) implements Result {
    }

    public record NeedsDoctor(String reason) implements Result {
    }

    public record Rejected(String reason) implements Result {
    }

    public interface Prescriptions {
        Prescription find(String id);
    }

    /** Use case: pure rules + gateway calls; trivially unit-testable. */
    public static Result refill(Prescriptions repo, String prescriptionId, String patient, LocalDate today) {
        Prescription p = repo.find(prescriptionId);
        if (p == null || !p.patient().equals(patient)) {
            return new Rejected("no such prescription for this patient"); // (1)!
        }
        if (today.isAfter(p.validUntil())) {
            return new NeedsDoctor("prescription expired on " + p.validUntil());
        }
        if (p.controlledSubstance()) {
            return new NeedsDoctor("controlled substance: doctor must approve each refill");
        }
        if (p.refillsLeft() == 0) {
            return new NeedsDoctor("no refills left");
        }
        return new Approved(p.drug(), p.refillsLeft() - 1);
    }

    /** Outermost circle: the web controller maps results to HTTP. */
    public static String httpResponse(Result result) {
        return switch (result) { // (2)!
            case Approved a -> "200 refill approved: " + a.drug() + " (" + a.refillsLeft() + " left)";
            case NeedsDoctor n -> "202 sent to your doctor: " + n.reason();
            case Rejected r -> "404 " + r.reason();
        };
    }

    public static Prescriptions inMemory(Map<String, Prescription> data) {
        return data::get;
    }
}
    1. The same answer for "doesn't exist" and "belongs to someone else", so the API doesn't leak which prescriptions exist.
    2. An exhaustive switch over a sealed type: add a new result and the compiler shows every place to update.
    package com.handbook.architecture.clean.refill;

import com.handbook.architecture.clean.refill.RefillPrescription.Prescription;

import java.time.LocalDate;
import java.util.Map;

public class RefillDemo {

    public static void main(String[] args) {
        var repo = RefillPrescription.inMemory(Map.of(
                "RX-1", new Prescription("RX-1", "PAT-5", "Metformin 500 mg", 3, LocalDate.of(2027, 3, 1), false),
                "RX-2", new Prescription("RX-2", "PAT-5", "Alprazolam 0.25 mg", 2, LocalDate.of(2027, 3, 1), true),
                "RX-3", new Prescription("RX-3", "PAT-5", "Atorvastatin 10 mg", 1, LocalDate.of(2026, 9, 30), false)));
        LocalDate today = LocalDate.of(2026, 10, 14);

        System.out.println("=== Healthcare: refill use case returning a sealed Result ===");
        for (String[] req : new String[][] {{"RX-1", "PAT-5"}, {"RX-2", "PAT-5"}, {"RX-3", "PAT-5"}, {"RX-1", "PAT-9"}}) {
            var result = RefillPrescription.refill(repo, req[0], req[1], today);
            System.out.printf("%s by %s -> %s%n", req[0], req[1], RefillPrescription.httpResponse(result));
        }
    }
}

    Output:

    === Healthcare: refill use case returning a sealed Result ===
RX-1 by PAT-5 -> 200 refill approved: Metformin 500 mg (2 left)
RX-2 by PAT-5 -> 202 sent to your doctor: controlled substance: doctor must approve each refill
RX-3 by PAT-5 -> 202 sent to your doctor: prescription expired on 2026-09-30
RX-1 by PAT-9 -> 404 no such prescription for this patient

    Why this variation:

    • Simpler than presenters when there's one consumer; still no HTTP in the use case.
    • Sealed results make error handling explicit and type-checked (no exceptions for expected outcomes).

    6. Variations & Modern Java Take¶

    • Output boundary vs. return values: presenters (Example 1–2) suit multiple outputs or streaming; returning a sealed Result (Example 3) is simpler and idiomatic in Java 21.
    • Records for request/response models; sealed interfaces for outcomes; pattern matching in adapters.
    • Screaming architecture: top-level packages named after use cases and domain (coupons/, transfers/), not frameworks (controllers/).
    • Spring at the edge: controllers and @Configuration live in the outer circle; use cases are plain classes registered as beans in configuration.
    • Cross-cutting concerns (transactions, security, logging) as decorators around use cases (see the coding challenge).

    8. Pros, Cons & Trade-offs¶

    ✅ Pros ❌ Cons
    Business rules independent of frameworks, UI, DB Boilerplate: boundaries, request/response models, presenters
    Very testable; fast tests Indirection can confuse newcomers
    Long-lived systems survive framework changes Overkill for CRUD
    Clear place for every kind of code Risk of "ceremony over substance"

    9. Pitfalls & Anti-Patterns¶

    Entities that are just JPA rows

    If entities have only getters/setters and all rules are in interactors, you have an anemic model with extra layers. Put invariants in entities.

    Use cases returning view models or HTTP codes

    Then they depend on the outer circle. Return response models (or sealed results); let presenters/controllers decide formats and status codes.

    Mapping everything three times by default

    Request → entity → response → view model for a trivial read is ceremony. Be pragmatic about reads; apply full rigour to complex writes.

    Frameworks imported 'just for annotations'

    @Transactional in a use case looks harmless but couples it to Spring. Prefer decorators/AOP configured in the outer circle if strict independence matters to you.

    10. Senior / Architect Deep Dive (10–15 yrs)¶

    Policy vs. detail. Martin's core idea: high-level policy (rules) shouldn't depend on low-level detail (I/O). Every inward dependency arrow you protect buys the freedom to postpone or replace a detail.

    Where to be pragmatic. Many teams allow JPA annotations on entities, or skip presenters and return DTOs, to reduce mapping. That's fine if it's a deliberate, documented decision enforced by tests, not an accident.

    Use cases as the unit of design. Name them after what users do (ApplyCoupon, TransferFunds); each one is a transaction boundary, a test suite and a security boundary. This also maps neatly onto API endpoints and messages.

    Explain it in 2 minutes (system design / architecture round)¶

    "I'd organize the service around use cases. Entities hold invariants (account limits, coupon rules). Each use case is a plain class with request and response models and gateway interfaces for data it needs. Controllers translate HTTP into requests; presenters or the controller translate responses into views and status codes. Spring, JPA and Kafka live only in the outer circle. ArchUnit enforces that dependencies point inward. Cross-cutting concerns like transactions and authorization are applied as decorators around use cases in configuration."

    War story: the framework upgrade that rewrote the business

    A logistics firm's routing rules lived in Struts actions and EJB session beans. When the platform reached end of life, migrating to Spring meant rewriting 600 classes, including the rules, because rules and framework code were interleaved. The migration took two years, and several rules changed by accident. What they did next time: entities and use cases as plain Java with 2,000 fast tests; frameworks only in adapters. The next migration (Spring Boot 2 → 3, javax → jakarta) touched only adapters and took three weeks. Lesson: frameworks come and go; protect the rules from them.

    12. Interview Corner¶

    Q1. What is Clean Architecture?

    An architecture of concentric circles (entities, use cases, interface adapters, frameworks) where dependencies only point inward.

    Q2. What is the Dependency Rule?

    Inner circles must not know anything about outer circles: no imports, no names, no data formats.

    Q3. Entity vs. use case?

    Entities hold enterprise-wide rules; use cases hold application-specific workflows that use entities.

    Q4. What does a presenter do?

    Converts the use case's response model into a view model for a specific UI or API.

    Q5. Why is it testable?

    Business rules don't depend on frameworks, databases or UIs, so they can be tested with plain unit tests.

    Q1. How does the interactor call the presenter without depending on it?

    Through an output boundary interface defined in the use-case circle and implemented by the presenter (dependency inversion).

    Q2. Where do Spring annotations go?

    In the outer circles: controllers, configuration, gateway implementations. Use cases are wired as beans from configuration.

    Q3. Clean vs. Hexagonal?

    Same dependency principle; Clean names more circles and adds presenters and request/response models; Hexagonal focuses on ports/adapters.

    Q4. What is "screaming architecture"?

    The top-level structure shows what the system does (use cases, domain) rather than which framework it uses.

    Q5. How do you handle validation?

    Input format validation in controllers/request models; business invariants in entities; use-case preconditions in interactors.

    Q1. "Clean Architecture for a CRUD admin panel: yes or no?"

    No: the ceremony costs more than it saves. Use it where rules are complex and long-lived.

    Q2. "How do you avoid mapping fatigue?"

    Pragmatic shortcuts for reads (query services returning DTOs directly), MapStruct for mechanical mapping, and full rigour for complex write paths.

    Q3. "Where does the transaction boundary go?"

    Around the use case, applied from outside (decorator/AOP) so the interactor stays framework-free.

    Q4. "How do you introduce Clean Architecture into an existing system?"

    Pick a high-value, high-change area; extract entities and use cases with tests; move framework code outward; enforce with ArchUnit for that package; expand gradually.

    Q5. "Sealed results vs. exceptions for business outcomes?"

    Sealed results make expected outcomes explicit and compiler-checked; exceptions are for unexpected failures. Java 21 pattern matching makes results ergonomic.

    Problem: Add transactions, logging and role checks to use cases without putting any of that code inside the interactors. Use a generic UseCase<I, O> interface and decorators applied in the composition root.

    Solution 
    package com.handbook.architecture.clean.crosscutting;

import java.util.ArrayList;
import java.util.List;
import java.util.function.Supplier;

/**
 * Coding challenge: add transactions, logging and authorization to every use case WITHOUT putting
 * framework code in the interactors. Each concern is a decorator around a generic UseCase interface,
 * applied in the composition root (the outermost circle).
 */
public final class UseCaseDecorators {

    private UseCaseDecorators() {
    }

    @FunctionalInterface
    public interface UseCase<I, O> {
        O execute(I input);
    }

    /** Stands in for a database transaction manager. */
    public static final class TxManager {
        public final List<String> log = new ArrayList<>();

        void begin() {
            log.add("BEGIN");
        }

        void commit() {
            log.add("COMMIT");
        }

        void rollback() {
            log.add("ROLLBACK");
        }
    }

    public static <I, O> UseCase<I, O> transactional(UseCase<I, O> inner, TxManager tx) {
        return input -> {
            tx.begin();
            try {
                O out = inner.execute(input);
                tx.commit();
                return out;
            } catch (RuntimeException e) {
                tx.rollback();
                throw e;
            }
        };
    }

    public static <I, O> UseCase<I, O> logged(String name, UseCase<I, O> inner) {
        return input -> {
            System.out.println("    -> " + name + "(" + input + ")");
            O out = inner.execute(input);
            System.out.println("    <- " + name + " = " + out);
            return out;
        };
    }

    public static <I, O> UseCase<I, O> requiresRole(String role, Supplier<String> currentRole,
                                                   UseCase<I, O> inner) {
        return input -> {
            if (!role.equals(currentRole.get())) {
                throw new SecurityException("role " + role + " required");
            }
            return inner.execute(input);
        };
    }
}

    package com.handbook.architecture.clean.crosscutting;

import com.handbook.architecture.clean.crosscutting.UseCaseDecorators.TxManager;
import com.handbook.architecture.clean.crosscutting.UseCaseDecorators.UseCase;

public class DecoratorsDemo {

    public static void main(String[] args) {
        // The interactor: pure business logic, no transactions, no logging, no security.
        UseCase<Long, String> issueRefund = paise -> {
            if (paise > 500_000) {
                throw new IllegalArgumentException("refunds over ₹5,000 need a manager");
            }
            return "refund of ₹" + paise / 100 + " issued";
        };

        TxManager tx = new TxManager();
        String[] role = {"SUPPORT_AGENT"};
        UseCase<Long, String> wired = UseCaseDecorators.logged("IssueRefund",
                UseCaseDecorators.requiresRole("SUPPORT_AGENT", () -> role[0],
                        UseCaseDecorators.transactional(issueRefund, tx)));

        System.out.println("=== Challenge: cross-cutting concerns as decorators at the edge ===");
        wired.execute(29_900L);
        try {
            wired.execute(900_000L);
        } catch (IllegalArgumentException e) {
            System.out.println("    failed: " + e.getMessage());
        }
        role[0] = "WAREHOUSE";
        try {
            wired.execute(10_000L);
        } catch (SecurityException e) {
            System.out.println("    denied: " + e.getMessage());
        }
        System.out.println("transaction log: " + tx.log);
    }
}

    Output:

    === Challenge: cross-cutting concerns as decorators at the edge ===
    -> IssueRefund(29900)
    <- IssueRefund = refund of ₹299 issued
    -> IssueRefund(900000)
    failed: refunds over ₹5,000 need a manager
    -> IssueRefund(10000)
    denied: role SUPPORT_AGENT required
transaction log: [BEGIN, COMMIT, BEGIN, ROLLBACK]

    Key points to say: decorator order matters (authorization before opening a transaction; logging outermost); the failed refund rolls back, and the denied call never opens a transaction. Spring AOP (@Transactional, @PreAuthorize) does the same with proxies.
