    Test Doubles (Dummy, Stub, Spy, Mock, Fake)¶

    🟢 Beginner → 🟡 Intermediate Testing Interview frequency ⭐⭐⭐⭐⭐

    TL;DR

    A test double stands in for a real dependency so a unit test is fast, deterministic and focused. Dummies fill parameters, stubs return canned answers, spies record calls, mocks verify expected calls, and fakes are working lightweight implementations. Prefer fakes and state-based assertions; use mocks only for side effects you can't observe any other way.

    See It in Motion¶

    Press Play to watch the calls travel between objects, or step through with Next and Back. Switch to Without it to see what goes wrong without the pattern. Open the full explorer with all 75 patterns

    1. Intent & Problem It Solves¶

    The problem in plain English: the slot-reminder service checks a delivery-slot API, looks up the customer in PostgreSQL and sends an SMS. A test that uses the real things is slow, flaky (the slot API changes every minute), costs money (SMS), and can't easily reproduce rare paths like "API timed out twice".

    Definition (Gerard Meszaros, xUnit Test Patterns):

    A Test Double is any object that replaces a real component (the depended-on component, DOC) for testing purposes.

    Double What it does Assertion style Example
    Dummy Passed but never used — null or new Object() for an unused parameter
    Stub Returns canned answers State (check the result) Slot API that always returns "Today 19:00"
    Spy A stub that also records calls State of the spy SMS sender that keeps a list of sent messages
    Mock Pre-programmed expectations, verified at the end Behaviour (were the right calls made?) "gateway.refund(pay_2, 5000) exactly once"
    Fake A working, simplified implementation State In-memory repository, fake clock, fake payment gateway

    Martin Fowler calls the two styles state verification ("is the outcome right?") and behaviour verification ("did it call the right things?").

    2. Real-World Analogy¶

    Film stunt doubles and props

    A dummy is the mannequin thrown off a building. A stub is a prop phone that always shows the same text. A spy is a hidden camera recording what the actor does. A mock is the director with a script checking each line is said in order. A fake is a real-but-cheap set: the café works, but it's plywood.

    3. Structure¶

    classDiagram class SlotReminderService { +remind(customerId) } class SlotApi { <<interface>> } class Sms { <<interface>> } class CustomerRepository { <<interface>> } class StubSlots { canned answer } class SpySms { +List sent } class FakeCustomerRepository { in-memory Map } SlotReminderService --> SlotApi SlotReminderService --> Sms SlotReminderService --> CustomerRepository StubSlots ..|> SlotApi SpySms ..|> Sms FakeCustomerRepository ..|> CustomerRepository
    Participant Responsibility
    System under test (SUT) The class whose behaviour the test checks
    Depended-on components Interfaces the SUT uses (inject them: Dependency Injection)
    Doubles Test-only implementations chosen for each dependency
    Test Arranges doubles, acts on the SUT, asserts on results/state (or verifies calls)

    4. Naive Approach (Without the Pattern)¶

    @Test void remindsCustomer() {
    var service = new SlotReminderService(new HttpSlotApi("https://slots.prod"), new TwilioSms(KEY), new JdbcCustomerRepository(prodLikeDb));
    assertThat(service.remind("C1")).startsWith("reminded");   // depends on the real slot calendar right now
}
    • Slow (network, DB) and flaky (real data changes).
    • Side effects (real SMS, real charges).
    • Rare paths (timeouts, sold out) can't be triggered on demand.

    5. Three Real-World Examples¶

    Example 1: Stub, Spy and Fake for Slot Reminders (Grocery)¶

    Scenario: A grocery app texts customers when a delivery slot opens, but only if they opted in and only when a slot exists. The test stubs the slot API (fixed answer), uses an in-memory fake for customers, and a spy SMS sender to check exactly which messages would have gone out.

    Design:

    flowchart LR T[Test] --> S[SlotReminderService] S --> St["Stub SlotApi<br/>'Today 19:00-20:00' or empty"] S --> F["Fake CustomerRepository<br/>HashMap"] S --> Sp["Spy Sms<br/>records messages"] T -->|assert| Sp

    Full Code:

    package com.handbook.testing.doubles.grocery;

import java.util.ArrayList;
import java.util.HashMap;
import java.util.List;
import java.util.Map;
import java.util.Optional;

/** Production code under test, plus the three doubles a test needs: a stub, a spy and a fake. */
public final class SlotReminderService {

    public interface SlotApi { Optional<String> nextFreeSlot(String pincode); }

    public interface Sms { void send(String phone, String text); }

    public interface CustomerRepository {
        void save(Customer c);
        Optional<Customer> find(String id);
    }

    public record Customer(String id, String phone, String pincode, boolean optedIn) { }

    private final SlotApi slots;
    private final Sms sms;
    private final CustomerRepository customers;

    public SlotReminderService(SlotApi slots, Sms sms, CustomerRepository customers) {
        this.slots = slots;
        this.sms = sms;
        this.customers = customers;
    }

    public String remind(String customerId) {
        Customer c = customers.find(customerId).orElseThrow();
        if (!c.optedIn()) {
            return "skipped (opted out)";
        }
        return slots.nextFreeSlot(c.pincode()).map(slot -> {
            sms.send(c.phone(), "A delivery slot just opened: " + slot);
            return "reminded for " + slot;
        }).orElse("no slot, no SMS");
    }

    // ---------- Test doubles ----------

    /** STUB: returns canned answers; has no logic and records nothing. */
    public static SlotApi stubSlots(String answer) { // (1)!
        return pincode -> Optional.ofNullable(answer);
    }

    /** SPY: a real-enough implementation that RECORDS how it was used, for assertions afterwards. */
    public static final class SpySms implements Sms { // (2)!
        public final List<String> sent = new ArrayList<>();

        public void send(String phone, String text) {
            sent.add(phone + " <- " + text);
        }
    }

    /** FAKE: a working, simplified implementation (in-memory instead of PostgreSQL). */
    public static final class FakeCustomerRepository implements CustomerRepository { // (3)!
        private final Map<String, Customer> rows = new HashMap<>();

        public void save(Customer c) { rows.put(c.id(), c); }

        public Optional<Customer> find(String id) { return Optional.ofNullable(rows.get(id)); }
    }
}
    1. A stub is often just a lambda returning a fixed value.
    2. A spy records interactions so the test can assert on them afterwards (state of the spy).
    3. A fake really works (save, then find), just without PostgreSQL. Keep fakes honest with contract tests.
    package com.handbook.testing.doubles.grocery;

import com.handbook.testing.doubles.grocery.SlotReminderService.Customer;
import com.handbook.testing.doubles.grocery.SlotReminderService.FakeCustomerRepository;
import com.handbook.testing.doubles.grocery.SlotReminderService.SpySms;

public class DoublesDemo {

    public static void main(String[] args) {
        System.out.println("=== Grocery: Testing Slot Reminders with a Stub, a Spy and a Fake ===");
        FakeCustomerRepository customers = new FakeCustomerRepository();
        customers.save(new Customer("C1", "+919845000001", "560034", true));
        customers.save(new Customer("C2", "+919845000002", "560034", false));

        SpySms sms = new SpySms();
        SlotReminderService withSlot = new SlotReminderService(SlotReminderService.stubSlots("Today 19:00-20:00"), sms, customers);
        System.out.println("C1 with a free slot : " + withSlot.remind("C1"));
        System.out.println("C2 opted out        : " + withSlot.remind("C2"));

        SlotReminderService noSlot = new SlotReminderService(SlotReminderService.stubSlots(null), sms, customers);
        System.out.println("C1 with no slot     : " + noSlot.remind("C1"));
        System.out.println("Spy recorded        : " + sms.sent);
        System.out.println("No network, no database, no SMS bill: the test needs nothing but the JVM.");
    }
}

    Output:

    === Grocery: Testing Slot Reminders with a Stub, a Spy and a Fake ===
C1 with a free slot : reminded for Today 19:00-20:00
C2 opted out        : skipped (opted out)
C1 with no slot     : no slot, no SMS
Spy recorded        : [+919845000001 <- A delivery slot just opened: Today 19:00-20:00]
No network, no database, no SMS bill: the test needs nothing but the JVM.

    Why these doubles here:

    • Each double matches what the test needs: answers (stub), observations (spy), behaviour (fake).
    • All three business paths are covered deterministically.
    • No mocking framework needed: interfaces + constructor injection make hand-rolled doubles trivial.

    Example 2: A Mock for Refund Calls (Payments)¶

    Scenario: When items are missing from a grocery delivery, the refund service refunds their value, capped at what's still refundable. The only observable effect is a call to the payment gateway, so behaviour verification is appropriate: the test sets an expectation and verifies it, including "no call at all" when everything has been refunded already.

    Design:

    sequenceDiagram autonumber participant T as Test participant M as MockGateway participant S as RefundService T->>M: expect refund(pay_2, 5000) T->>S: refundMissingItems(pay_2, captured 1200, refunded 1150, missing 150) S->>M: refund(pay_2, 5000) T->>M: verify() → expected == actual

    Full Code:

    package com.handbook.testing.doubles.payments;

import java.util.ArrayList;
import java.util.List;

/** A hand-rolled MOCK: expectations are set up front and verified at the end (what Mockito automates). */
public final class MockGateway implements RefundService.Gateway {

    private final List<String> expected = new ArrayList<>();
    private final List<String> actual = new ArrayList<>();

    public MockGateway expect(String call) { // (1)!
        expected.add(call);
        return this;
    }

    @Override
    public void refund(String paymentId, long paise) {
        actual.add("refund(" + paymentId + ", " + paise + ")");
    }

    @Override
    public void capture(String paymentId, long paise) {
        actual.add("capture(" + paymentId + ", " + paise + ")");
    }

    public String verify() { // (2)!
        return expected.equals(actual) ? "verified " + actual : "FAILED: expected " + expected + " but got " + actual;
    }
}
    1. Expectations are declared before the action.
    2. verify compares expected and actual calls, exactly what Mockito.verify(...) and verifyNoMoreInteractions(...) do.
    package com.handbook.testing.doubles.payments;

/** Partial refunds: refund only what's left, never more than was captured. */
public final class RefundService {

    public interface Gateway {
        void refund(String paymentId, long paise);
        void capture(String paymentId, long paise);
    }

    private final Gateway gateway;

    public RefundService(Gateway gateway) {
        this.gateway = gateway;
    }

    public void refundMissingItems(String paymentId, long capturedPaise, long alreadyRefundedPaise, long missingItemsPaise) {
        long refundable = capturedPaise - alreadyRefundedPaise;
        long amount = Math.min(refundable, missingItemsPaise);
        if (amount > 0) {
            gateway.refund(paymentId, amount);
        }
    }
}

    package com.handbook.testing.doubles.payments;

public class MockDemo {

    public static void main(String[] args) {
        System.out.println("=== Payments: Verifying Calls to the Gateway with a Mock ===");
        MockGateway mock = new MockGateway().expect("refund(pay_1, 15000)");
        new RefundService(mock).refundMissingItems("pay_1", 120_000, 0, 15_000);
        System.out.println("Missing curd (INR 150)        : " + mock.verify());

        MockGateway capped = new MockGateway().expect("refund(pay_2, 5000)");
        new RefundService(capped).refundMissingItems("pay_2", 120_000, 115_000, 15_000);
        System.out.println("Only INR 50 left to refund    : " + capped.verify());

        MockGateway none = new MockGateway();
        new RefundService(none).refundMissingItems("pay_3", 120_000, 120_000, 15_000);
        System.out.println("Fully refunded already        : " + none.verify() + " (no gateway call at all)");
        System.out.println("Mockito equivalent: verify(gateway).refund(\"pay_2\", 5000L); verifyNoMoreInteractions(gateway);");
    }
}

    Output:

    === Payments: Verifying Calls to the Gateway with a Mock ===
Missing curd (INR 150)        : verified [refund(pay_1, 15000)]
Only INR 50 left to refund    : verified [refund(pay_2, 5000)]
Fully refunded already        : verified [] (no gateway call at all)
Mockito equivalent: verify(gateway).refund("pay_2", 5000L); verifyNoMoreInteractions(gateway);

    Why a mock here:

    • The outcome is an outgoing call to an external system: there's no state to inspect.
    • "Exactly this call, nothing else" is the business rule (never over-refund).
    • With Mockito: verify(gateway).refund("pay_2", 5_000L); verifyNoMoreInteractions(gateway);

    Example 3: A Fault-Injecting Fake (Travel)¶

    Scenario: A hotel-booking service retries timeouts up to 3 times but must not retry "sold out". The partner's sandbox never times out on demand. A fake hotel API can be scripted to fail in specific ways, so every retry path gets a fast, deterministic test.

    Design:

    flowchart LR T["Test: failNext(TIMEOUT)"] --> F[FaultyFakeGateway] S[BookingService] -->|"hold() #1"| F F -->|"throws timeout"| S S -->|"hold() #2"| F F -->|"HOLD-2"| S

    Full Code:

    package com.handbook.testing.doubles.travel;

import java.util.ArrayDeque;
import java.util.Deque;
import java.util.HashMap;
import java.util.Map;

/** A FAKE with fault injection: behaves like the real hotel API but can be told to fail in specific ways. */
public final class FaultyFakeGateway implements BookingService.HotelApi {

    public enum Fault { TIMEOUT, SOLD_OUT }

    private final Deque<Fault> scripted = new ArrayDeque<>();
    private final Map<String, String> holds = new HashMap<>();
    private int calls;

    public FaultyFakeGateway failNext(Fault fault) { // (1)!
        scripted.add(fault);
        return this;
    }

    @Override
    public String hold(String hotel, String night) {
        calls++;
        Fault f = scripted.poll();
        if (f == Fault.TIMEOUT) {
            throw new IllegalStateException("timeout");
        }
        if (f == Fault.SOLD_OUT) {
            return null;
        }
        String id = "HOLD-" + calls;
        holds.put(id, hotel + "@" + night);
        return id;
    }

    @Override
    public void release(String holdId) {
        holds.remove(holdId);
    }

    public int calls() {
        return calls;
    }

    public Map<String, String> activeHolds() {
        return Map.copyOf(holds);
    }
}
    1. Scripted faults: the test decides exactly which call fails and how. Combine with a fake clock for timeouts and backoff.
    package com.handbook.testing.doubles.travel;

/** Retries timeouts up to 3 times; reports sold-out immediately. */
public final class BookingService {

    public interface HotelApi {
        String hold(String hotel, String night);
        void release(String holdId);
    }

    private final HotelApi api;

    public BookingService(HotelApi api) {
        this.api = api;
    }

    public String book(String hotel, String night) {
        for (int attempt = 1; attempt <= 3; attempt++) {
            try {
                String hold = api.hold(hotel, night);
                return hold == null ? "sold out" : "held " + hold + " after " + attempt + " attempt(s)";
            } catch (IllegalStateException timeout) {
                // retry
            }
        }
        return "gave up after 3 timeouts";
    }
}

    package com.handbook.testing.doubles.travel;

import com.handbook.testing.doubles.travel.FaultyFakeGateway.Fault;

public class FaultInjectionDemo {

    public static void main(String[] args) {
        System.out.println("=== Travel: Testing Retry Paths with a Fault-Injecting Fake ===");
        FaultyFakeGateway oneTimeout = new FaultyFakeGateway().failNext(Fault.TIMEOUT);
        System.out.println("1 timeout   -> " + new BookingService(oneTimeout).book("Sea Breeze Goa", "2026-12-24")
                + ", calls=" + oneTimeout.calls());

        FaultyFakeGateway soldOut = new FaultyFakeGateway().failNext(Fault.SOLD_OUT);
        System.out.println("sold out    -> " + new BookingService(soldOut).book("Sea Breeze Goa", "2026-12-24")
                + ", calls=" + soldOut.calls() + " (not retried)");

        FaultyFakeGateway down = new FaultyFakeGateway().failNext(Fault.TIMEOUT).failNext(Fault.TIMEOUT).failNext(Fault.TIMEOUT);
        System.out.println("3 timeouts  -> " + new BookingService(down).book("Sea Breeze Goa", "2026-12-24")
                + ", calls=" + down.calls() + ", holds=" + down.activeHolds());
        System.out.println("These paths are almost impossible to trigger reliably against the real partner sandbox.");
    }
}

    Output:

    === Travel: Testing Retry Paths with a Fault-Injecting Fake ===
1 timeout   -> held HOLD-2 after 2 attempt(s), calls=2
sold out    -> sold out, calls=1 (not retried)
3 timeouts  -> gave up after 3 timeouts, calls=3, holds={}
These paths are almost impossible to trigger reliably against the real partner sandbox.

    Why a fake here:

    • Error paths are where production bugs live, and the hardest to reach with real systems.
    • The fake keeps state (active holds), so tests can check that nothing leaked.
    • One fake serves many tests; mocks would need re-scripting in each.
    Unit Tests: TestDoublesTest.java 
    package com.handbook.testing;

import com.handbook.testing.doubles.grocery.SlotReminderService;
import com.handbook.testing.doubles.grocery.SlotReminderService.Customer;
import com.handbook.testing.doubles.grocery.SlotReminderService.FakeCustomerRepository;
import com.handbook.testing.doubles.grocery.SlotReminderService.SpySms;
import com.handbook.testing.doubles.payments.MockGateway;
import com.handbook.testing.doubles.payments.RefundService;
import com.handbook.testing.doubles.travel.BookingService;
import com.handbook.testing.doubles.travel.FaultyFakeGateway;
import com.handbook.testing.doubles.travel.FaultyFakeGateway.Fault;
import org.junit.jupiter.api.BeforeEach;
import org.junit.jupiter.api.Test;

import static org.assertj.core.api.Assertions.assertThat;

class TestDoublesTest {

    FakeCustomerRepository customers;
    SpySms sms;

    @BeforeEach
    void setUp() {
        customers = new FakeCustomerRepository();
        sms = new SpySms();
    }

    @Test
    void optedInCustomerGetsExactlyOneSms() {
        customers.save(new Customer("C", "+91", "560001", true));
        new SlotReminderService(SlotReminderService.stubSlots("18:00"), sms, customers).remind("C");
        assertThat(sms.sent).containsExactly("+91 <- A delivery slot just opened: 18:00");
    }

    @Test
    void optedOutCustomerGetsNothing() {
        customers.save(new Customer("C", "+91", "560001", false));
        new SlotReminderService(SlotReminderService.stubSlots("18:00"), sms, customers).remind("C");
        assertThat(sms.sent).isEmpty();
    }

    @Test
    void refundIsCappedAtWhatRemains() {
        MockGateway mock = new MockGateway().expect("refund(p, 100)");
        new RefundService(mock).refundMissingItems("p", 1_000, 900, 500);
        assertThat(mock.verify()).startsWith("verified");
    }

    @Test
    void timeoutsAreRetriedButSoldOutIsNot() {
        FaultyFakeGateway api = new FaultyFakeGateway().failNext(Fault.TIMEOUT).failNext(Fault.SOLD_OUT);
        assertThat(new BookingService(api).book("h", "n")).isEqualTo("sold out");
        assertThat(api.calls()).isEqualTo(2);
    }
}

    6. Variations & Modern Java Take¶

    @ExtendWith(MockitoExtension.class)
class RefundServiceTest {
    @Mock RefundService.Gateway gateway;          // mock
    @InjectMocks RefundService service;

    @Test void capsRefund() {
        service.refundMissingItems("pay_2", 120_000, 115_000, 15_000);
        verify(gateway).refund("pay_2", 5_000L);
        verifyNoMoreInteractions(gateway);
    }
}
// stub:  when(slotApi.nextFreeSlot("560034")).thenReturn(Optional.of("Today 19:00"));
// spy:   ArgumentCaptor<String> text = ArgumentCaptor.forClass(String.class); verify(sms).send(eq(phone), text.capture());
    Variation Notes
    Lambdas as stubs Single-method interfaces make stubs one-liners (pincode -> Optional.of("19:00"))
    Mockito mock, when/thenReturn, verify, ArgumentCaptor, spy(realObject) (partial mock)
    Spring Boot @MockitoBean replaces a bean in the test context (Boot 3.4+; replaced @MockBean)
    WireMock / MockServer HTTP-level stubs and fault injection for clients
    Testcontainers Real infrastructure (PostgreSQL, Kafka) instead of fakes for integration tests
    Fake clocks / ids Clock.fixed, seeded Random, injected id generators for determinism

    7. Where It Lives in Real Frameworks¶

    Where Test doubles
    Mockito / EasyMock / MockK Mocks, stubs, spies, argument captors
    Spring @MockitoBean, @MockitoSpyBean, MockMvc, MockRestServiceServer (HTTP client stub)
    JDK java.time.Clock.fixed, Clock.offset; HttpClient can be wrapped behind an interface
    HTTP WireMock, MockWebServer (OkHttp)
    Data H2 / embedded Kafka as fakes; Testcontainers for the real thing

    8. Pros, Cons & Trade-offs¶

    ✅ Pros ❌ Cons
    Fast, deterministic, isolated unit tests Doubles can drift from real behaviour
    Any path (errors, timeouts) can be tested on demand Over-mocking couples tests to implementation details
    No side effects or costs Mock-heavy tests are hard to read
    Forces good design (interfaces, DI) False confidence if integration tests are missing

    9. Pitfalls & Anti-Patterns¶

    Mocking everything

    Verifying every internal call makes tests fail on harmless refactors (coding challenge) and pass on broken behaviour. Assert outcomes; mock only true external side effects.

    Mocking types you don't own

    Mocking RestTemplate, JdbcTemplate or an SDK encodes your assumptions about it. Wrap third-party APIs behind your own interface (an adapter) and double that; test the adapter against the real thing.

    Fakes without contract tests

    An in-memory repository that behaves differently from PostgreSQL (no unique constraints, no copies) hides bugs. Run the same contract test suite against fake and real (Repository).

    Partial mocks (spies on real objects)

    spy(realService) with some methods stubbed usually means the class does too much. Split it instead.

    10. Senior / Architect Deep Dive (10–15 yrs)¶

    The test pyramid in practice. Many fast unit tests with stubs/fakes; fewer integration tests with Testcontainers for adapters (DB, Kafka, HTTP clients); a thin layer of contract tests between services; very few end-to-end tests. Doubles live at the ports of a hexagonal service; adapters are tested against real infrastructure.

    London vs Chicago schools. "Mockist" (London) TDD mocks collaborators and drives design through interactions; "classicist" (Chicago) uses real objects and fakes and asserts state. Most robust codebases lean classicist for domain logic and mockist only at boundaries with side effects.

    Determinism. Flaky tests usually come from hidden dependencies: time, randomness, threads, network, ordering of HashMap. Inject them and replace with doubles: Clock.fixed, seeded Random, synchronous executors.

    War story: green tests, broken refunds

    A payments team's refund tests mocked RestTemplate and asserted it was called with a URL. The PSP changed its API to require an idempotency header; the mocks didn't care, tests stayed green, and production refunds failed for six hours. Fix: a PspClient adapter interface with fakes for unit tests; the adapter itself tested against WireMock recordings and the PSP sandbox; a contract test in CI. Lesson: don't mock what you don't own. Wrap it, then double your wrapper.

    12. Interview Corner¶

    Q1. What is a mock?

    A test double with expectations about how it will be called, verified at the end of the test.

    Q2. Stub vs mock?

    A stub returns canned data (you check the result); a mock checks the calls made to it.

    Q3. What is a fake?

    A working simplified implementation, like an in-memory repository.

    Q4. What do @Mock and @InjectMocks do?

    @Mock creates a Mockito mock; @InjectMocks creates the class under test and injects the mocks into it.

    Q5. Why use test doubles?

    Speed, isolation, determinism, and the ability to test error paths without side effects.

    Q1. When should you use a mock vs a fake?

    Mock when the only observable effect is a call to an external system; fake when the dependency holds state you can inspect.

    Q2. What does "don't mock what you don't own" mean?

    Wrap third-party APIs in your own interfaces and double those; test the wrappers against the real thing.

    Q3. What is ArgumentCaptor for?

    Capturing arguments passed to a mock so you can assert on them in detail.

    Q4. Why are over-mocked tests brittle?

    They encode implementation details (call order, internal methods), so refactors break them even when behaviour is unchanged.

    Q5. @MockitoBean vs @Mock?

    @MockitoBean replaces a bean in the Spring context (slower, integration-style); @Mock is plain Mockito with no Spring.

    Q1. "How do you keep fakes trustworthy?"

    Shared contract test suites run against the fake and the real adapter (Testcontainers), and consumer-driven contracts for remote services.

    Q2. "Design the test strategy for a hexagonal payments service."

    Domain: pure unit tests, no doubles needed. Application: fakes for repositories, mocks for outbound side effects. Adapters: Testcontainers / WireMock. Between services: contract tests. A few E2E smoke tests.

    Q3. "How do you test retry and timeout logic deterministically?"

    Fault-injecting fakes plus a fake clock/scheduler; never real sleeps.

    Q4. "A test suite takes 40 minutes. Where do doubles help?"

    Replace Spring-context and network-heavy tests with plain unit tests on fakes; keep a small integration layer; parallelize.

    Q5. "London vs Chicago school?"

    Mockist vs classicist; prefer classicist for domain logic (refactor-friendly), mockist at side-effect boundaries.

    Problem: A restock routine is refactored from two save() calls to one saveAll(). Show that an interaction-based test fails while a state-based test with a fake passes, even though behaviour didn't change.

    Solution 
    package com.handbook.testing.doubles.overmocking;

import java.util.ArrayList;
import java.util.HashMap;
import java.util.List;
import java.util.Map;

/** Coding challenge: an interaction-heavy test breaks on a harmless refactor; a state-based test with a fake doesn't. */
public class OverMockingDemo {

    interface StockStore {
        void save(String sku, int qty);
        void saveAll(Map<String, Integer> batch);
    }

    /** Records calls (like a strict mock) and also keeps state (like a fake). */
    static final class RecordingStore implements StockStore {
        final List<String> calls = new ArrayList<>();
        final Map<String, Integer> state = new HashMap<>();

        public void save(String sku, int qty) {
            calls.add("save(" + sku + ")");
            state.put(sku, qty);
        }

        public void saveAll(Map<String, Integer> batch) {
            calls.add("saveAll(" + batch.size() + ")");
            state.putAll(batch);
        }
    }

    /** Version 1: one save per SKU. */
    static void restockV1(StockStore store) {
        store.save("MILK", 50);
        store.save("EGGS", 30);
    }

    /** Version 2 (refactor for performance): one batched call. Same behaviour. */
    static void restockV2(StockStore store) {
        Map<String, Integer> batch = new java.util.TreeMap<>(Map.of("MILK", 50, "EGGS", 30));
        store.saveAll(batch);
    }


    public static void main(String[] args) {
        System.out.println("=== Challenge: Over-Mocking vs State-Based Tests ===");
        for (String version : new String[] {"v1", "v2"}) {
            RecordingStore store = new RecordingStore();
            if (version.equals("v1")) {
                restockV1(store);
            } else {
                restockV2(store);
            }
            boolean interactionPass = store.calls.equals(List.of("save(MILK)", "save(EGGS)")); // verify(store).save(...) x2
            boolean statePass = store.state.equals(Map.of("MILK", 50, "EGGS", 30));             // assert the outcome
            System.out.printf("%s calls=%s -> interaction test %s, state test %s%n", version, store.calls,
                    interactionPass ? "PASS" : "FAIL", statePass ? "PASS" : "FAIL");
        }
        System.out.println("Assert on outcomes with fakes; reserve mocks for side effects you can only observe as calls.");
    }
}

    Output:

    === Challenge: Over-Mocking vs State-Based Tests ===
v1 calls=[save(MILK), save(EGGS)] -> interaction test PASS, state test PASS
v2 calls=[saveAll(2)] -> interaction test FAIL, state test PASS
Assert on outcomes with fakes; reserve mocks for side effects you can only observe as calls.

    Key points to say: the interaction test verified how the code worked, not what it achieved. A fake with state lets the test assert the outcome (stock levels), so refactors stay green and real regressions still fail.

    Behavioural tie-in (STAR) for experienced candidates

    • S: Refund tests mocked RestTemplate, so an upstream API change broke production refunds while CI stayed green.
    • T: Make the test suite catch integration breakages without slowing it down.
    • A: Introduced adapter interfaces with fakes for unit tests, WireMock-based adapter tests, contract tests against the PSP sandbox, and banned mocking third-party types via a review checklist.
    • R: Two later API changes were caught in CI; unit tests got 3× faster after removing Spring contexts from them.
