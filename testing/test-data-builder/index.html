    Test Data Builder & Object Mother¶

    🟢 Beginner → 🟡 Intermediate Testing Interview frequency ⭐⭐⭐

    TL;DR

    A Test Data Builder creates test objects with sensible defaults, so each test sets only the fields that matter to it (anOrder().express().build()). An Object Mother adds named, realistic personas on top (aYoungDriverInMumbai()). Use them whenever test setup is longer than the test, or when adding a constructor parameter breaks dozens of tests.

    1. Intent & Problem It Solves¶

    The problem in plain English: Order has nine fields. A delivery-fee test only cares about the subtotal and "express", but has to write new Order("O1", "C1", "560034", "18:00", "UPI", true, false, List.of(...), null). A reader can't tell which values matter. When a tenth field is added, 140 tests stop compiling.

    Definitions:

    Test Data Builder (Nat Pryce; Growing Object-Oriented Software, Guided by Tests): a builder with safe default values for every field, and methods to override just the ones a test cares about.

    Object Mother (Peter Schuh & Stephanie Punke, ThoughtWorks): a factory of example objects, each representing a meaningful, named scenario.

    Test Data Builder Object Mother
    Gives you Defaults + fluent overrides Named, ready-made personas
    Flexibility High: any combination Low on its own (fixed shapes)
    Readability "What's different in this test" "Which business scenario this is"
    Best together The mother returns builders, so tests can tweak a persona

    2. Real-World Analogy¶

    Ordering a thali

    The restaurant's standard thali (defaults) comes with dal, rice, two sabzis and a roti. You only say what's different: "extra roti, no sweet" (overrides). The menu also lists named thalis, "Gujarati", "Punjabi" (the Object Mother's personas), which you can still customise.

    3. Structure¶

    classDiagram class Order { <<record>> 9 fields } class OrderBuilder { -defaults for every field +anOrder()$ OrderBuilder +express() OrderBuilder +withSubtotal(paise) OrderBuilder +build() Order } class Drivers { <<object mother>> +aYoungDriverInMumbai()$ DriverBuilder +aHighRiskDriver()$ DriverBuilder } OrderBuilder ..> Order : builds Drivers ..> DriverBuilder : returns pre-configured
    Participant Responsibility
    Builder Valid defaults for every field; intention-revealing withX/asY methods; build()
    Static entry point anOrder(), aCustomer(): reads like English in tests
    Object Mother Named personas that return builders
    Test Overrides only what matters, asserts on behaviour

    4. Naive Approach (Without the Pattern)¶

    @Test void expressSmallOrderFee() {
    Order o = new Order("O1", "C1", "560034", "Today 18:00-19:00", "UPI", true, false,
                        List.of(new Line("BASKET", 1, 30_000)), null);      // which of these matter?
    assertThat(o.deliveryFeePaise()).isEqualTo(5_500);
}
    • Noise hides the one or two values the test is about.
    • Every constructor change breaks every test.
    • Copy-pasted setups drift and carry irrelevant, sometimes invalid, values.

    5. Three Real-World Examples¶

    Example 1: Delivery-Fee Tests with a Builder (Grocery)¶

    Scenario: Delivery fee rules: INR 25 below INR 499, free above it, +INR 30 for express, and always free for a customer's first order. Each test should state its case in one line. The builder supplies a valid customer, pincode, slot, payment method and basket by default.

    Design:

    flowchart LR D["defaults: CUST-1, 560034, UPI, MILK-1L…"] --> B[OrderBuilder] T1["withSubtotal(30_000)"] --> B T2["express()"] --> B T3["firstOrder()"] --> B B --> O[Order]

    Full Code:

    package com.handbook.testing.testdata.grocery;

import com.handbook.testing.testdata.grocery.Order.Line;

import java.util.ArrayList;
import java.util.List;

/** Test Data Builder: every field has a sensible default; tests override only what matters to them. */
public final class OrderBuilder {

    private String id = "ORD-1";
    private String customerId = "CUST-1";
    private String pincode = "560034";
    private String slot = "Today 18:00-19:00";
    private String paymentMethod = "UPI";
    private boolean express = false;
    private boolean firstOrder = false;
    private final List<Line> lines = new ArrayList<>(List.of(new Line("MILK-1L", 1, 6_800))); // (1)!
    private String coupon = null;

    public static OrderBuilder anOrder() { // (2)!
        return new OrderBuilder();
    }

    public OrderBuilder express() { this.express = true; return this; }

    public OrderBuilder firstOrder() { this.firstOrder = true; return this; }

    public OrderBuilder withSubtotal(long paise) { // (3)!
        lines.clear();
        lines.add(new Line("BASKET", 1, paise));
        return this;
    }

    public OrderBuilder withCoupon(String code) { this.coupon = code; return this; }

    public Order build() {
        return new Order(id, customerId, pincode, slot, paymentMethod, express, firstOrder, List.copyOf(lines), coupon);
    }
}
    1. Valid defaults for every field: an order built with no overrides is a realistic, valid order.
    2. A static entry point so tests read as sentences: anOrder().express().build().
    3. Domain-level overrides (withSubtotal) rather than raw setters for every field.
    package com.handbook.testing.testdata.grocery;

import java.util.List;

/** Production type with many fields, most irrelevant to any single test. */
public record Order(String id, String customerId, String pincode, String slot, String paymentMethod,
                    boolean expressDelivery, boolean firstOrder, List<Line> lines, String couponCode) {

    public record Line(String sku, int qty, long unitPaise) { }

    public long subtotalPaise() {
        return lines.stream().mapToLong(l -> l.qty() * l.unitPaise()).sum();
    }

    /** The rule under test: delivery fee. */
    public long deliveryFeePaise() {
        if (firstOrder) {
            return 0;
        }
        long base = subtotalPaise() >= 49_900 ? 0 : 2_500;
        return base + (expressDelivery ? 3_000 : 0);
    }
}

    package com.handbook.testing.testdata.grocery;

import static com.handbook.testing.testdata.grocery.OrderBuilder.anOrder;

public class BuilderDemo {

    public static void main(String[] args) {
        System.out.println("=== Grocery: Delivery-Fee Tests That Say Only What Matters ===");
        print("small order           ", anOrder().withSubtotal(30_000).build());
        print("order above INR 499   ", anOrder().withSubtotal(50_000).build());
        print("small + express       ", anOrder().withSubtotal(30_000).express().build());
        print("first order + express ", anOrder().withSubtotal(30_000).express().firstOrder().build());
        System.out.println("Each case sets 1-3 fields; the other 6 fields of Order come from defaults.");
    }

    private static void print(String label, Order o) {
        System.out.println(label + "-> fee INR " + o.deliveryFeePaise() / 100);
    }
}

    Output:

    === Grocery: Delivery-Fee Tests That Say Only What Matters ===
small order           -> fee INR 25
order above INR 499   -> fee INR 0
small + express       -> fee INR 55
first order + express -> fee INR 0
Each case sets 1-3 fields; the other 6 fields of Order come from defaults.

    Why a builder here:

    • Each test shows only its difference from a normal order.
    • Adding a field to Order means changing one builder, not 140 tests.
    • Defaults are valid, so tests don't accidentally exercise validation paths.

    Example 2: Driver Personas with an Object Mother (Insurance)¶

    Scenario: Underwriters talk about "young drivers in metro cities", "experienced safe drivers" and "high-risk drivers". Premium tests use those exact personas, so business people can read them. Because each persona returns a builder, a test can still tweak one detail ("young driver in Mumbai, with one claim").

    Design:

    flowchart LR M["Drivers (object mother)"] --> Y["aYoungDriverInMumbai()"] M --> S["anExperiencedSafeDriver()"] M --> H["aHighRiskDriver()"] Y -->|".claims(1)"| Y1["young driver, 1 claim"]

    Full Code:

    package com.handbook.testing.testdata.insurance;

import java.time.LocalDate;

/** Object Mother: named, realistic personas for the domain, built on top of a builder. */
public final class Drivers {

    public record Driver(String name, LocalDate born, String city, int claimsLast3Years, int yearsLicensed, String vehicle) { }

    public static final class DriverBuilder {
        private String name = "Test Driver";
        private LocalDate born = LocalDate.of(1990, 1, 1);
        private String city = "Pune";
        private int claims = 0;
        private int yearsLicensed = 10;
        private String vehicle = "hatchback";

        public DriverBuilder born(LocalDate d) { born = d; return this; }
        public DriverBuilder city(String c) { city = c; return this; }
        public DriverBuilder claims(int n) { claims = n; return this; }
        public DriverBuilder yearsLicensed(int y) { yearsLicensed = y; return this; }
        public DriverBuilder vehicle(String v) { vehicle = v; return this; }
        public DriverBuilder named(String n) { name = n; return this; }
        public Driver build() { return new Driver(name, born, city, claims, yearsLicensed, vehicle); }
    }

    // ---- The mother: personas the business team actually talks about ----

    public static DriverBuilder aYoungDriverInMumbai() { // (1)!
        return new DriverBuilder().named("Young driver").born(LocalDate.of(2005, 6, 1)).city("Mumbai").yearsLicensed(1);
    }

    public static DriverBuilder anExperiencedSafeDriver() {
        return new DriverBuilder().named("Safe driver").born(LocalDate.of(1978, 3, 9)).yearsLicensed(25);
    }

    public static DriverBuilder aHighRiskDriver() {
        return new DriverBuilder().named("High-risk driver").claims(3).vehicle("sports");
    }

    private Drivers() {
    }
}
    1. Personas return a builder, not a finished object, which avoids the classic Object Mother problem of dozens of near-duplicate factory methods.
    package com.handbook.testing.testdata.insurance;

import com.handbook.testing.testdata.insurance.Drivers.Driver;

import java.time.LocalDate;
import java.time.Period;

public final class PremiumCalculator {

    public static long annualPremiumPaise(Driver d, LocalDate today) {
        long premium = 900_000; // INR 9,000 base
        int age = Period.between(d.born(), today).getYears();
        if (age < 25) premium += 450_000;
        if (d.yearsLicensed() >= 20) premium -= 150_000;
        premium += d.claimsLast3Years() * 300_000L;
        if (d.city().equals("Mumbai") || d.city().equals("Delhi")) premium += 120_000;
        if (d.vehicle().equals("sports")) premium += 500_000;
        return premium;
    }

    private PremiumCalculator() {
    }
}

    package com.handbook.testing.testdata.insurance;

import com.handbook.testing.testdata.insurance.Drivers.Driver;

import java.time.LocalDate;

import static com.handbook.testing.testdata.insurance.Drivers.aHighRiskDriver;
import static com.handbook.testing.testdata.insurance.Drivers.aYoungDriverInMumbai;
import static com.handbook.testing.testdata.insurance.Drivers.anExperiencedSafeDriver;

public class PersonasDemo {

    public static void main(String[] args) {
        System.out.println("=== Insurance: Premium Tests Written with Personas ===");
        LocalDate today = LocalDate.of(2026, 11, 1);
        for (Driver d : new Driver[] {
                aYoungDriverInMumbai().build(),
                anExperiencedSafeDriver().build(),
                aHighRiskDriver().build(),
                aYoungDriverInMumbai().claims(1).named("Young driver, 1 claim").build()}) { // persona + tweak
            System.out.printf("%-22s -> INR %,d%n", d.name(), PremiumCalculator.annualPremiumPaise(d, today) / 100);
        }
        System.out.println("Personas read like the underwriting guide; builders let a test tweak one detail.");
    }
}

    Output:

    === Insurance: Premium Tests Written with Personas ===
Young driver           -> INR 14,700
Safe driver            -> INR 7,500
High-risk driver       -> INR 23,000
Young driver, 1 claim  -> INR 17,700
Personas read like the underwriting guide; builders let a test tweak one detail.

    Why an object mother here:

    • Tests speak the business vocabulary, which makes them reviewable by domain experts.
    • Persona definitions live in one place; when underwriting redefines "young", one method changes.
    • Builders keep the mother small and flexible.

    Example 3: Generated, Reproducible Data (Banking)¶

    Scenario: A ledger must satisfy one invariant: money is never created or destroyed, so all balances sum to zero. Hand-written examples miss edge cases, so the test generates 10,000 random valid transfers from a seed. A buggy version that rounds large credits down is caught, and the seed is printed so the exact failing data can be replayed.

    Design:

    flowchart LR S["seed 20261101"] --> G["RandomTransfers.generate(seed, 10_000)"] G --> L1["correct ledger: Σ = 0 ✅"] G --> L2["buggy ledger: Σ = −2532 ❌ → replay with the same seed"]

    Full Code:

    package com.handbook.testing.testdata.ledger;

import java.util.ArrayList;
import java.util.List;
import java.util.Random;

/** Generated test data: many random-but-valid transfers from a SEED, so any failure can be replayed exactly. */
public final class RandomTransfers {

    public record Transfer(String from, String to, long paise) { }

    public static List<Transfer> generate(long seed, int count, List<String> accounts) {
        Random r = new Random(seed); // (1)!
        List<Transfer> out = new ArrayList<>();
        for (int i = 0; i < count; i++) {
            String from = accounts.get(r.nextInt(accounts.size()));
            String to;
            do {
                to = accounts.get(r.nextInt(accounts.size()));
            } while (to.equals(from)); // (2)!
            out.add(new Transfer(from, to, 100 + r.nextInt(1_000_000)));
        }
        return out;
    }

    private RandomTransfers() {
    }
}
    1. Seeded randomness: the same seed always produces the same data, so a failure is reproducible.
    2. Generated data must still be valid (no self-transfers), or failures are noise.
    package com.handbook.testing.testdata.ledger;

import com.handbook.testing.testdata.ledger.RandomTransfers.Transfer;

import java.util.HashMap;
import java.util.List;
import java.util.Map;

public class LedgerPropertyDemo {

    /** System under test, with a bug: credits above INR 5,000 are rounded down to an even paisa, leaking money. */
    static Map<String, Long> apply(List<Transfer> transfers, boolean buggy) {
        Map<String, Long> balances = new HashMap<>();
        for (Transfer t : transfers) {
            long credited = buggy && t.paise() > 500_000 ? t.paise() - (t.paise() % 2) : t.paise();
            balances.merge(t.from(), -t.paise(), Long::sum);
            balances.merge(t.to(), credited, Long::sum);
        }
        return balances;
    }

    public static void main(String[] args) {
        System.out.println("=== Banking: A Ledger Invariant Checked on 10,000 Generated Transfers ===");
        List<String> accounts = List.of("A", "B", "C", "D", "E");
        long seed = 20261101L;
        List<Transfer> transfers = RandomTransfers.generate(seed, 10_000, accounts);
        for (boolean buggy : new boolean[] {false, true}) {
            long sum = apply(transfers, buggy).values().stream().mapToLong(Long::longValue).sum();
            System.out.println((buggy ? "buggy ledger  " : "correct ledger") + ": sum of all balances = " + sum
                    + (sum == 0 ? " -> invariant holds" : " -> INVARIANT BROKEN, replay with seed " + seed));
        }
        System.out.println("Same seed, same 10,000 transfers: first transfer is always " + transfers.get(0));
    }
}

    Output:

    === Banking: A Ledger Invariant Checked on 10,000 Generated Transfers ===
correct ledger: sum of all balances = 0 -> invariant holds
buggy ledger  : sum of all balances = -2532 -> INVARIANT BROKEN, replay with seed 20261101
Same seed, same 10,000 transfers: first transfer is always Transfer[from=E, to=C, paise=67735]

    Why generated data here:

    • Invariants ("sum is zero", "balance never negative") are best tested across many inputs.
    • Edge cases (large amounts, repeated pairs) appear without anyone thinking of them.
    • This is the idea behind property-based testing tools like jqwik, which also shrink failures to minimal examples.
    Unit Tests: TestDataBuilderTest.java 
    package com.handbook.testing;

import com.handbook.testing.testdata.insurance.PremiumCalculator;
import com.handbook.testing.testdata.ledger.RandomTransfers;
import org.junit.jupiter.api.Test;

import java.time.LocalDate;
import java.util.List;

import static com.handbook.testing.testdata.grocery.OrderBuilder.anOrder;
import static com.handbook.testing.testdata.insurance.Drivers.aHighRiskDriver;
import static com.handbook.testing.testdata.insurance.Drivers.anExperiencedSafeDriver;
import static org.assertj.core.api.Assertions.assertThat;

class TestDataBuilderTest {

    @Test
    void freeDeliveryAboveThreshold() {
        assertThat(anOrder().withSubtotal(49_900).build().deliveryFeePaise()).isZero();
    }

    @Test
    void expressAddsThirtyRupees() {
        assertThat(anOrder().withSubtotal(49_900).express().build().deliveryFeePaise()).isEqualTo(3_000);
    }

    @Test
    void firstOrderIsAlwaysFree() {
        assertThat(anOrder().express().firstOrder().build().deliveryFeePaise()).isZero();
    }

    @Test
    void highRiskPaysMoreThanSafe() {
        LocalDate today = LocalDate.of(2026, 1, 1);
        assertThat(PremiumCalculator.annualPremiumPaise(aHighRiskDriver().build(), today))
                .isGreaterThan(PremiumCalculator.annualPremiumPaise(anExperiencedSafeDriver().build(), today));
    }

    @Test
    void generatedDataIsReproducibleAndValid() {
        var a = RandomTransfers.generate(42, 500, List.of("X", "Y", "Z"));
        assertThat(a).isEqualTo(RandomTransfers.generate(42, 500, List.of("X", "Y", "Z")));
        assertThat(a).allSatisfy(t -> assertThat(t.from()).isNotEqualTo(t.to()));
    }
}

    6. Variations & Modern Java Take¶

    @Property
void moneyIsConserved(@ForAll("transfers") List<Transfer> transfers) {
    assertThat(ledger.apply(transfers).values().stream().mapToLong(Long::longValue).sum()).isZero();
}

@Provide
Arbitrary<List<Transfer>> transfers() {
    Arbitrary<String> acct = Arbitraries.of("A", "B", "C", "D");
    return Combinators.combine(acct, acct, Arbitraries.longs().between(100, 1_000_000))
            .filter((f, t, p) -> !f.equals(t)).as(Transfer::new).list().ofMaxSize(500);
}
    Variation Notes
    Record + wither builders Immutable builders as records (withBalance(...) returns a new builder), safe to share (coding challenge)
    Lombok @Builder(toBuilder = true) Generates builders; add a test-only factory with defaults on top
    Instancio / EasyRandom Populate objects with random values automatically; override the fields under test
    Property-based testing jqwik generates inputs and shrinks failing cases
    Fixtures in SQL/JSON For integration tests; keep them small and named, and prefer builders + repositories

    Where Test data
    JUnit 5 @ParameterizedTest with @MethodSource feeding builders
    jqwik @Property, Arbitraries, shrinking
    Instancio Instancio.of(Order.class).set(field(Order::express), true).create()

    Testcontainers Seed data per test with builders + repositories rather than shared dumps

    8. Pros, Cons & Trade-offs¶

    ✅ Pros ❌ Cons
    Tests show only what matters Another class per important type to maintain
    Constructor changes touch one place Hidden defaults can surprise ("why is the customer in Bengaluru?")
    Personas speak the business language Object Mothers grow into god classes if unmanaged
    Generated data finds edge cases Random data without seeds causes unreproducible failures

    9. Pitfalls & Anti-Patterns¶

    Shared mutable builders

    A builder stored in a static field and modified by one test leaks state into the next, making results depend on test order (coding challenge). Create a fresh builder per test, or make builders immutable.

    Relying on a default in an assertion

    If a test asserts the fee for pincode 560034 but never sets the pincode, a change to the default breaks it mysteriously. Set explicitly every value you assert on.

    Object Mother explosion

    aYoungDriverInMumbaiWithOneClaimAndASportsCar(): dozens of factory methods. Return builders and let tests compose.

    Unseeded randomness

    new Random() in test data makes failures impossible to reproduce. Always seed and print the seed.

    10. Senior / Architect Deep Dive (10–15 yrs)¶

    Builders as a design signal. If building a valid object for a test needs 15 lines even with a builder, the production type probably has too many responsibilities, or invariants aren't enforced in the constructor. Use the pain to drive design.

    Shared test fixtures module. In a multi-module build, put builders and mothers in a test-fixtures artefact (Gradle's java-test-fixtures plugin) so other modules' tests reuse the same, maintained definitions instead of copying them.

    Integration tests. Build with builders, persist through the real repository (Testcontainers database), and clean up per test (transaction rollback or truncation). Avoid large shared SQL dumps: nobody knows which rows a test depends on.

    War story: tests that passed only alphabetically

    A banking team's test class kept one AccountBuilder in a static field. testA_frozenAccount set frozen = true; every later test then built frozen accounts. Tests passed in IntelliJ (alphabetical order) but failed randomly on CI once JUnit 5 ran methods in a different order and later in parallel. The team lost a week to "flaky CI". Fix: immutable record-based builders and a fresh base per test; JUnit's random method order enabled to surface hidden coupling. Lesson: test data must be independent per test, and builders are data.

    12. Interview Corner¶

    Q1. What is a Test Data Builder?

    A builder used in tests that has default values for every field, so tests only set the fields they care about.

    Q2. What is an Object Mother?

    A class that creates ready-made example objects for common scenarios.

    Q3. Why not just use constructors in tests?

    Long constructors hide what matters and break every test when a parameter is added.

    Q4. How is it different from the GoF Builder?

    Same mechanics, but the test version focuses on defaults and readability.

    Q5. Name a library that helps.

    Lombok @Builder, Instancio, jqwik.

    Q1. Builder vs Object Mother: when to use which?

    Builders for flexibility; mothers for named business scenarios; best combined (mothers return builders).

    Q2. Why should defaults be valid?

    So tests only fail for the reason they're testing, not because of an unrelated invalid field.

    Q3. How do you make random test data reproducible?

    Seed the generator and log the seed on failure.

    Q4. What's wrong with a static shared builder?

    Mutations leak across tests; results depend on order and parallelism.

    Q5. Where do builders live in a multi-module project?

    In a shared test-fixtures module/artefact.

    Q1. "Our test setup is longer than our tests. What do you do?"

    Introduce builders/mothers, move shared ones to test fixtures, and treat the remaining pain as feedback on production design.

    Q2. "When would you use property-based testing?"

    For invariants over large input spaces: money conservation, serialization round-trips, idempotency, sorting.

    Q3. "How do you manage test data for integration tests against a real DB?"

    Builders + real repositories per test, isolated by transaction rollback or unique ids; no shared dumps.

    Q4. "How do you keep an Object Mother from becoming a god class?"

    Few personas, each returning a builder; split mothers per aggregate; delete unused personas.

    Q5. "How do builders interact with immutable domain types?"

    The builder collects values and calls the canonical constructor once, so domain invariants are still enforced.

    Problem: A test class shares one mutable AccountBuilder in a static field. Show how one test's change leaks into the next, and fix it with an immutable builder.

    Solution 
    package com.handbook.testing.testdata.sharedbuilder;

/** Coding challenge: a shared mutable builder leaks changes between tests. Fix: fresh or immutable builders. */
public class SharedBuilderDemo {

    record Account(String type, long balancePaise, boolean frozen) { }

    static final class MutableBuilder {
        String type = "SAVINGS";
        long balance = 100_000;
        boolean frozen = false;
        MutableBuilder frozen() { frozen = true; return this; }
        MutableBuilder balance(long b) { balance = b; return this; }
        Account build() { return new Account(type, balance, frozen); }
    }

    /** Immutable builder: every "with" returns a NEW builder, so a shared base can't be corrupted. */
    record ImmutableBuilder(String type, long balance, boolean frozen) {
        static ImmutableBuilder anAccount() { return new ImmutableBuilder("SAVINGS", 100_000, false); }
        ImmutableBuilder asFrozen() { return new ImmutableBuilder(type, balance, true); }
        ImmutableBuilder withBalance(long b) { return new ImmutableBuilder(type, b, frozen); }
        Account build() { return new Account(type, balance, frozen); }
    }

    static final MutableBuilder SHARED = new MutableBuilder(); // "to save typing" in a test class
    static final ImmutableBuilder BASE = ImmutableBuilder.anAccount();

    public static void main(String[] args) {
        System.out.println("=== Challenge: The Shared Builder That Froze Every Account ===");
        Account a = SHARED.frozen().build();              // testFrozenAccountCannotWithdraw
        Account b = SHARED.balance(500_000).build();      // testLargeBalanceEarnsBonus, runs next
        System.out.println("mutable shared  : test 1 " + a + "\n                  test 2 " + b + "  <- frozen leaked in");

        Account c = BASE.asFrozen().build();
        Account d = BASE.withBalance(500_000).build();
        System.out.println("immutable base  : test 1 " + c + "\n                  test 2 " + d);
        System.out.println("Test order or parallel runs no longer change results.");
    }
}

    Output:

    === Challenge: The Shared Builder That Froze Every Account ===
mutable shared  : test 1 Account[type=SAVINGS, balancePaise=100000, frozen=true]
                  test 2 Account[type=SAVINGS, balancePaise=500000, frozen=true]  <- frozen leaked in
immutable base  : test 1 Account[type=SAVINGS, balancePaise=100000, frozen=true]
                  test 2 Account[type=SAVINGS, balancePaise=500000, frozen=false]
Test order or parallel runs no longer change results.

    Key points to say: the mutable builder is shared state across tests; an immutable builder returns a new instance from every withX, so a common base is safe to reuse. Simpler still: call anAccount() fresh in every test.

    Behavioural tie-in (STAR) for experienced candidates

    • S: CI failed randomly for a week because tests shared a mutable builder and JUnit changed method order.
    • T: Make the suite deterministic and easier to read.
    • A: Replaced ad-hoc setup with immutable record builders and a small Object Mother of business personas, moved them to a test-fixtures module, and enabled random test ordering in CI.
    • R: Zero order-dependent failures since; average test length dropped from 28 to 9 lines; adding a field to Account now touches one file.

    Remember in 30 seconds

    • Builder: valid defaults, override only what matters.
    • Object Mother: named personas that return builders.
    • Set explicitly anything you assert on.
    • Fresh or immutable builders per test; never shared mutable ones.
    • Generated data: always seeded, always valid.
