    Intermediate Testing

    Contract Testing¶

    🟡 Intermediate → 🔴 Advanced Testing Interview frequency ⭐⭐⭐⭐

    TL;DR

    A contract test checks that a provider's API (or event) still satisfies what each consumer actually relies on. Consumers write the expectations; the provider verifies them in its own CI; a broker answers "can I deploy this version?". Use it between services owned by different teams, instead of slow, flaky end-to-end test environments. Match on shape and type, not exact values.

    1. Intent & Problem It Solves¶

    The problem in plain English: the inventory team renames available to availableQty in a "harmless cleanup". Their unit tests pass. The order service's unit tests pass too (they use a stub with the old field). Both deploy, and order placement breaks in production. The usual fix, a shared end-to-end environment, is slow, flaky and always on the wrong versions.

    Definition (Martin Fowler / Ian Robinson, Consumer-Driven Contracts):

    Each consumer captures its expectations of a provider in a contract. The provider runs all consumers' contracts as part of its build, so it knows immediately when a change would break a consumer.

    What a contract covers:

    Kind Consumer expectation Provider verification
    HTTP "GET /stock/MILK-1L returns 200 with sku (string), available (integer)" Replay the request against the real provider app, check the response
    Messages "payment.captured has paymentId, amountPaise (long)" Check the producer's schema/sample against every consumer's needs
    Provider states "Given SKU MILK-1L has stock" Set up that data before replaying

    2. Real-World Analogy¶

    A plug and a socket

    An appliance maker (consumer) states, "my plug has three round pins, 5 A". The building's electrician (provider) checks every socket against the plugs actually in use before renovating. Nobody needs to plug in every appliance in the building to know the renovation is safe.

    3. Structure¶

    sequenceDiagram autonumber participant C as Consumer CI (order-service) participant B as Contract broker participant P as Provider CI (inventory-service) participant D as Deploy pipeline C->>C: consumer tests against a mock built from the contract C->>B: publish contract (order-service 3.4.0) P->>B: fetch contracts for inventory-service P->>P: verify each interaction against the real app P->>B: publish results (inventory 1.9 vs order 3.4.0: FAIL) D->>B: can-i-deploy inventory 1.9 to prod? B-->>D: NO
    Participant Responsibility
    Consumer Writes interactions (request + expected response shape + provider state); tests itself against a generated stub
    Contract Versioned artefact (Pact JSON, Spring Cloud Contract DSL, AsyncAPI/Avro schema)
    Provider Verifies all consumers' contracts in its build, with provider-state setup
    Broker Stores contracts and verification results; answers can-i-deploy per environment

    4. Naive Approach (Without the Pattern)¶

    Shared "integration" environment with 40 services
→ deploy your branch, run 600 end-to-end tests (45 minutes)
→ 7 fail because another team's service is broken today
→ re-run; 3 different failures; merge anyway
    • Slow and flaky; failures are often someone else's.
    • Tests the versions that happen to be deployed, not the ones going to prod.
    • Stubs in consumer unit tests silently drift from the real provider.

    5. Three Real-World Examples¶

    Example 1: Order Service ↔ Inventory Service (Grocery)¶

    Scenario: The order service calls GET /stock/{sku} before reserving stock. Its team writes a contract with two interactions: a known SKU (needs sku, available as an integer, updatedAt as an ISO timestamp) and an unknown SKU (404). The inventory team verifies the contract in CI. When v1.9 renames available, verification fails in their pipeline.

    Design:

    flowchart LR O["order-service team<br/>writes contract"] --> K[(Contract)] K --> V1["inventory v1.8 verification: PASS"] K --> V2["inventory v1.9 verification: FAIL<br/>missing field 'available'"]

    Full Code:

    package com.handbook.testing.contract.core;

import java.util.ArrayList;
import java.util.List;
import java.util.Map;
import java.util.function.Consumer;
import java.util.function.Function;
import java.util.regex.Pattern;

/** A tiny Pact-like consumer-driven contract: interactions written by the consumer, verified against the provider. */
public final class Contract {

    /** Match by TYPE or pattern, not by exact value, so provider test data can differ. */
    public sealed interface Matcher permits AnyString, AnyInteger, Regex, Exactly {
        boolean matches(Object actual);
    }

    public record AnyString() implements Matcher {
        public boolean matches(Object a) { return a instanceof String; }
        public String toString() { return "a string"; }
    }

    public record AnyInteger() implements Matcher {
        public boolean matches(Object a) { return a instanceof Integer || a instanceof Long; }
        public String toString() { return "an integer"; }
    }

    public record Regex(String pattern) implements Matcher {
        public boolean matches(Object a) { return a instanceof String s && Pattern.matches(pattern, s); }
        public String toString() { return "matching /" + pattern + "/"; }
    }

    public record Exactly(Object value) implements Matcher {
        public boolean matches(Object a) { return value.equals(a); }
        public String toString() { return "exactly " + value; }
    }

    public record Interaction(String description, String providerState, String path, int status, Map<String, Matcher> body) { }

    private final String consumer;
    private final String provider;
    private final List<Interaction> interactions = new ArrayList<>();

    public Contract(String consumer, String provider) {
        this.consumer = consumer;
        this.provider = provider;
    }

    public Contract uponReceiving(Interaction i) {
        interactions.add(i);
        return this;
    }

    public record Response(int status, Map<String, Object> body) { }

    /** Provider-side verification: set up each provider state, replay the request, check the response. */
    public List<String> verify(Consumer<String> setUpState, Function<String, Response> providerApp) {
        List<String> report = new ArrayList<>();
        for (Interaction i : interactions) {
            setUpState.accept(i.providerState()); // (1)!
            Response r = providerApp.apply(i.path());
            List<String> problems = new ArrayList<>();
            if (r.status() != i.status()) {
                problems.add("status " + r.status() + " != " + i.status());
            }
            new java.util.TreeMap<>(i.body()).forEach((field, matcher) -> { // (2)!
                Object actual = r.body().get(field);
                if (actual == null) {
                    problems.add("missing field '" + field + "'");
                } else if (!matcher.matches(actual)) {
                    problems.add("'" + field + "' = " + actual + " is not " + matcher);
                }
            });
            report.add((problems.isEmpty() ? "PASS " : "FAIL ") + consumer + " -> " + provider + ": " + i.description()
                    + (problems.isEmpty() ? "" : " " + problems));
        }
        return report;
    }
}
    1. Provider states let each interaction set up the data it needs ("SKU MILK-1L has stock"), so contracts don't depend on whatever happens to be in a shared database.
    2. Each field is checked with a matcher: present, right type or pattern. Fields the consumer doesn't mention can change freely.
    package com.handbook.testing.contract.grocery;

import com.handbook.testing.contract.core.Contract;
import com.handbook.testing.contract.core.Contract.AnyInteger;
import com.handbook.testing.contract.core.Contract.AnyString;
import com.handbook.testing.contract.core.Contract.Interaction;
import com.handbook.testing.contract.core.Contract.Regex;
import com.handbook.testing.contract.core.Contract.Response;

import java.util.HashMap;
import java.util.LinkedHashMap;
import java.util.Map;
import java.util.function.Function;

public class InventoryContractDemo {

    static final Map<String, Integer> STOCK = new HashMap<>();

    public static void main(String[] args) {
        System.out.println("=== Grocery: Order Service's Contract with the Inventory Service ===");
        Contract contract = new Contract("order-service", "inventory-service") // written by the ORDER team
                .uponReceiving(new Interaction("stock for a known SKU", "SKU MILK-1L has stock",
                        "/stock/MILK-1L", 200, Map.of("sku", new AnyString(), "available", new AnyInteger(),
                        "updatedAt", new Regex("\\d{4}-\\d{2}-\\d{2}T.*Z"))))
                .uponReceiving(new Interaction("unknown SKU", "SKU NOPE does not exist", "/stock/NOPE", 404, Map.of()));

        System.out.println("Provider v1.8 (current):");
        contract.verify(InventoryContractDemo::state, provider("available")).forEach(l -> System.out.println("  " + l));
        System.out.println("Provider v1.9 (renames 'available' to 'availableQty' in a 'harmless cleanup'):");
        contract.verify(InventoryContractDemo::state, provider("availableQty")).forEach(l -> System.out.println("  " + l));
        System.out.println("v1.9 fails in the INVENTORY team's CI, before it can break order placement in production.");
    }

    static void state(String providerState) { // provider states set up the data each interaction needs
        STOCK.clear();
        if (providerState.equals("SKU MILK-1L has stock")) {
            STOCK.put("MILK-1L", 37);
        }
    }

    static Function<String, Response> provider(String quantityField) {
        return path -> {
            String sku = path.substring("/stock/".length());
            Integer qty = STOCK.get(sku);
            if (qty == null) {
                return new Response(404, Map.of("error", "unknown sku"));
            }
            Map<String, Object> body = new LinkedHashMap<>();
            body.put("sku", sku);
            body.put(quantityField, qty);
            body.put("updatedAt", "2026-10-02T09:15:00Z");
            return new Response(200, body);
        };
    }
}

    Output:

    === Grocery: Order Service's Contract with the Inventory Service ===
Provider v1.8 (current):
  PASS order-service -> inventory-service: stock for a known SKU
  PASS order-service -> inventory-service: unknown SKU
Provider v1.9 (renames 'available' to 'availableQty' in a 'harmless cleanup'):
  FAIL order-service -> inventory-service: stock for a known SKU [missing field 'available']
  PASS order-service -> inventory-service: unknown SKU
v1.9 fails in the INVENTORY team's CI, before it can break order placement in production.

    Why contract testing here:

    • The breaking change is caught before merge, in the team that made it.
    • Only fields the consumer uses are protected; providers can add or change the rest.
    • Runs in seconds against the provider app, no shared environment.

    Example 2: Evolving a Payment Event (Payments)¶

    Scenario: payments.payment.captured.v1 is consumed by the ledger, notifications and analytics. The payments team wants to add the payment method, and later someone proposes renaming amountPaise to amount (decimal). Each consumer declares the fields it reads; the producer's new schema is checked against all of them before release.

    Design:

    flowchart LR S2["v2: + method (optional)"] --> C{Check against consumers} S3["v3: amountPaise → amount (decimal)"] --> C C -->|v2| OK["compatible"] C -->|v3| BR["BREAKING: ledger, analytics"]

    Full Code:

    package com.handbook.testing.contract.messages;

import java.util.ArrayList;
import java.util.List;
import java.util.Map;

/** Message contracts: can every existing consumer still read what the new producer schema emits? */
public final class SchemaCompatibility {

    public record Field(String type, boolean required) { }

    /** What a consumer actually reads from the event (its contract). */
    public record ConsumerNeeds(String consumer, Map<String, String> fields) { }

    public static List<String> check(Map<String, Field> producerSchema, List<ConsumerNeeds> consumers) {
        List<String> problems = new ArrayList<>();
        for (ConsumerNeeds c : consumers) {
            new java.util.TreeMap<>(c.fields()).forEach((name, type) -> {
                Field f = producerSchema.get(name);
                if (f == null) {
                    problems.add(c.consumer() + " reads '" + name + "' which no longer exists"); // (1)!
                } else if (!f.type().equals(type)) {
                    problems.add(c.consumer() + " expects '" + name + "' as " + type + " but it is " + f.type()); // (2)!
                } else if (!f.required()) {
                    problems.add(c.consumer() + " relies on '" + name + "' which is now optional");
                }
            });
        }
        return problems;
    }
}
    1. A field a consumer reads has disappeared: breaking.
    2. A field changed type: breaking (even if the name is the same).
    package com.handbook.testing.contract.messages;

import com.handbook.testing.contract.messages.SchemaCompatibility.ConsumerNeeds;
import com.handbook.testing.contract.messages.SchemaCompatibility.Field;

import java.util.LinkedHashMap;
import java.util.List;
import java.util.Map;

public class PaymentEventDemo {

    public static void main(String[] args) {
        System.out.println("=== Payments: Evolving the payments.payment.captured.v1 Event Safely ===");
        List<ConsumerNeeds> consumers = List.of(
                new ConsumerNeeds("ledger", Map.of("paymentId", "string", "amountPaise", "long", "currency", "string")),
                new ConsumerNeeds("notifications", Map.of("paymentId", "string", "customerId", "string")),
                new ConsumerNeeds("analytics", Map.of("paymentId", "string", "amountPaise", "long")));

        Map<String, Field> v1 = schema("amountPaise", new Field("long", true), null, null);
        Map<String, Field> v2AddOptional = schema("amountPaise", new Field("long", true), "method", new Field("string", false));
        Map<String, Field> v3Breaking = new LinkedHashMap<>(schema("amount", new Field("decimal", true), null, null));

        report("v1 (today)", v1, consumers);
        report("v2 adds optional 'method'", v2AddOptional, consumers);
        report("v3 'amountPaise' -> 'amount' as decimal", v3Breaking, consumers);
        System.out.println("Breaking changes go to a NEW topic/version (...captured.v2), published alongside v1 during migration.");
    }

    static Map<String, Field> schema(String amountName, Field amount, String extraName, Field extra) {
        Map<String, Field> s = new LinkedHashMap<>();
        s.put("paymentId", new Field("string", true));
        s.put("customerId", new Field("string", true));
        s.put(amountName, amount);
        s.put("currency", new Field("string", true));
        if (extraName != null) {
            s.put(extraName, extra);
        }
        return s;
    }

    static void report(String label, Map<String, Field> schema, List<ConsumerNeeds> consumers) {
        List<String> problems = SchemaCompatibility.check(schema, consumers);
        System.out.println(label + " -> " + (problems.isEmpty() ? "compatible with all 3 consumers" : "BREAKING: " + problems));
    }
}

    Output:

    === Payments: Evolving the payments.payment.captured.v1 Event Safely ===
v1 (today) -> compatible with all 3 consumers
v2 adds optional 'method' -> compatible with all 3 consumers
v3 'amountPaise' -> 'amount' as decimal -> BREAKING: [ledger reads 'amountPaise' which no longer exists, analytics reads 'amountPaise' which no longer exists]
Breaking changes go to a NEW topic/version (...captured.v2), published alongside v1 during migration.

    Why message contracts here:

    • Events have no request/response cycle, so breakages surface late (in a consumer's logs, hours later).
    • Schema registries (Avro/Protobuf with BACKWARD compatibility) enforce the generic rules; consumer contracts add "what each consumer actually reads".
    • Breaking changes become a planned new version, not an incident.

    Example 3: "Can I Deploy?" for the Accounts API (Banking)¶

    Scenario: The accounts API is consumed by the mobile BFF, statements and loans. Version 9.0.0 removes branchCode. Loans 1.3.0 (in prod) still reads it; loans 1.4.0 (fixed) isn't in prod yet. The broker records which consumer versions each provider version was verified against, and the deploy pipeline asks whether 9.0.0 is safe for the versions actually in prod.

    Design:

    flowchart LR M["Verification matrix<br/>accounts 9.0.0 × mobile-bff 4.2.0 ✅<br/>× statements 2.7.1 ✅<br/>× loans 1.3.0 ❌<br/>× loans 1.4.0 ✅"] --> Q{"prod runs loans 1.3.0"} Q --> N["can-i-deploy: NO"] Q -. "after loans 1.4.0 ships" .-> Y["can-i-deploy: YES"]

    Full Code:

    package com.handbook.testing.contract.broker;

import java.util.ArrayList;
import java.util.HashMap;
import java.util.List;
import java.util.Map;

/** The "can I deploy?" question: is this provider version verified against every consumer version in that environment? */
public final class ContractBroker {

    public record Verification(String consumer, String consumerVersion, String provider, String providerVersion, boolean passed) { }

    private final List<Verification> results = new ArrayList<>();
    private final Map<String, Map<String, String>> deployed = new HashMap<>(); // env -> app -> version

    public void record(Verification v) {
        results.add(v);
    }

    public void deployed(String env, String app, String version) {
        deployed.computeIfAbsent(env, e -> new HashMap<>()).put(app, version);
    }

    public String canIDeploy(String provider, String version, String env, List<String> consumers) {
        List<String> blockers = new ArrayList<>();
        for (String consumer : consumers) {
            String consumerVersion = deployed.getOrDefault(env, Map.of()).get(consumer); // (1)!
            boolean ok = results.stream().anyMatch(r -> r.consumer().equals(consumer) && r.consumerVersion().equals(consumerVersion)
                    && r.provider().equals(provider) && r.providerVersion().equals(version) && r.passed());
            if (!ok) {
                blockers.add(consumer + "@" + consumerVersion);
            }
        }
        return blockers.isEmpty() ? "YES" : "NO, not verified against " + blockers; // (2)!
    }
}
    1. The check uses the consumer versions deployed in the target environment, not the latest ones.
    2. The answer names the blockers, so the provider team knows who to coordinate with.
    package com.handbook.testing.contract.broker;

import com.handbook.testing.contract.broker.ContractBroker.Verification;

import java.util.List;

public class CanIDeployDemo {

    public static void main(String[] args) {
        System.out.println("=== Banking: 'Can I Deploy?' for the Accounts API ===");
        ContractBroker broker = new ContractBroker();
        broker.deployed("prod", "mobile-bff", "4.2.0");
        broker.deployed("prod", "statements", "2.7.1");
        broker.deployed("prod", "loans", "1.3.0");

        broker.record(new Verification("mobile-bff", "4.2.0", "accounts-api", "9.0.0", true));
        broker.record(new Verification("statements", "2.7.1", "accounts-api", "9.0.0", true));
        broker.record(new Verification("loans", "1.3.0", "accounts-api", "9.0.0", false)); // loans still reads 'branchCode'
        broker.record(new Verification("loans", "1.4.0", "accounts-api", "9.0.0", true));  // fixed, but not in prod yet

        List<String> consumers = List.of("mobile-bff", "statements", "loans");
        System.out.println("accounts-api 9.0.0 -> prod? " + broker.canIDeploy("accounts-api", "9.0.0", "prod", consumers));
        broker.deployed("prod", "loans", "1.4.0");
        System.out.println("after loans 1.4.0 ships -> prod? " + broker.canIDeploy("accounts-api", "9.0.0", "prod", consumers));
    }
}

    Output:

    === Banking: 'Can I Deploy?' for the Accounts API ===
accounts-api 9.0.0 -> prod? NO, not verified against [loans@1.3.0]
after loans 1.4.0 ships -> prod? YES

    Why a broker here:

    • Independent deploys need a precise answer for this environment's versions.
    • Coordination becomes explicit: ship the consumer fix first, then the provider.
    • Pact Broker / PactFlow provide exactly this matrix and the can-i-deploy CLI.
    Unit Tests: ContractTestingTest.java 
    package com.handbook.testing;

import com.handbook.testing.contract.broker.ContractBroker;
import com.handbook.testing.contract.broker.ContractBroker.Verification;
import com.handbook.testing.contract.core.Contract;
import com.handbook.testing.contract.core.Contract.AnyInteger;
import com.handbook.testing.contract.core.Contract.Interaction;
import com.handbook.testing.contract.core.Contract.Response;
import com.handbook.testing.contract.messages.SchemaCompatibility;
import com.handbook.testing.contract.messages.SchemaCompatibility.ConsumerNeeds;
import com.handbook.testing.contract.messages.SchemaCompatibility.Field;
import org.junit.jupiter.api.Test;

import java.util.List;
import java.util.Map;

import static org.assertj.core.api.Assertions.assertThat;

class ContractTestingTest {

    @Test
    void missingFieldFailsVerification() {
        Contract c = new Contract("a", "b").uponReceiving(new Interaction("x", "s", "/x", 200, Map.of("n", new AnyInteger())));
        assertThat(c.verify(s -> { }, p -> new Response(200, Map.of("m", 1)))).singleElement().asString().startsWith("FAIL");
        assertThat(c.verify(s -> { }, p -> new Response(200, Map.of("n", 5)))).singleElement().asString().startsWith("PASS");
    }

    @Test
    void addingAnOptionalFieldIsCompatibleRemovingOneIsNot() {
        List<ConsumerNeeds> consumers = List.of(new ConsumerNeeds("c", Map.of("id", "string")));
        assertThat(SchemaCompatibility.check(Map.of("id", new Field("string", true), "extra", new Field("int", false)), consumers)).isEmpty();
        assertThat(SchemaCompatibility.check(Map.of("ident", new Field("string", true)), consumers)).hasSize(1);
    }

    @Test
    void cannotDeployWithoutVerificationAgainstDeployedConsumers() {
        ContractBroker b = new ContractBroker();
        b.deployed("prod", "c", "1");
        b.record(new Verification("c", "2", "p", "9", true));
        assertThat(b.canIDeploy("p", "9", "prod", List.of("c"))).startsWith("NO");
        b.deployed("prod", "c", "2");
        assertThat(b.canIDeploy("p", "9", "prod", List.of("c"))).isEqualTo("YES");
    }
}

    @ExtendWith(PactConsumerTestExt.class)
@PactTestFor(providerName = "inventory-service")
class InventoryClientPactTest {
    @Pact(consumer = "order-service")
    V4Pact stock(PactDslWithProvider builder) {
        return builder.given("SKU MILK-1L has stock")
            .uponReceiving("stock for a known SKU").path("/stock/MILK-1L").method("GET")
            .willRespondWith().status(200)
            .body(new PactDslJsonBody().stringType("sku").integerType("available").datetime("updatedAt"))
            .toPact(V4Pact.class);
    }

    @Test void readsStock(MockServer server) {
        assertThat(new InventoryClient(server.getUrl()).available("MILK-1L")).isGreaterThanOrEqualTo(0);
    }
}

    8. Pros, Cons & Trade-offs¶

    ✅ Pros ❌ Cons
    Catches integration breaks in seconds, before merge Teams must adopt it on both sides
    Replaces most slow, flaky E2E tests Contracts cover the interface, not end-to-end business flows
    Providers know exactly which fields consumers use Provider-state setup takes effort
    Enables safe independent deploys (can-i-deploy) Another piece of infrastructure (broker) to run

    9. Pitfalls & Anti-Patterns¶

    Exact-value contracts

    Asserting pricePaise == 28500 fails whenever the provider's test data changes, which teaches teams to ignore failures (coding challenge). Contract the shape; test values in unit tests.

    Using contracts as functional tests

    "Order total is correct after a 10% coupon" is business behaviour; test it in the provider's own tests. Contracts check that the conversation is understood.

    Consumers over-specifying

    Listing every field "just in case" freezes the provider's API. Include only what the consumer reads.

    Skipping can-i-deploy

    Verifying contracts but deploying without checking the matrix for the target environment still lets incompatible versions meet in production.

    10. Senior / Architect Deep Dive (10–15 yrs)¶

    Where it fits. Unit tests with doubles inside a service; integration tests with Testcontainers for adapters; contract tests between services; a handful of E2E smoke tests for critical journeys. Contracts are what keep the consumer's stubs honest.

    Versioning and branches. Tag contracts and verifications with git SHA and branch; use "pending pacts" so a new consumer expectation doesn't break the provider's main build before the feature is implemented; use "WIP pacts" to verify feature branches.

    Events at scale. Combine a schema registry (generic compatibility rules) with consumer contracts (actual field usage). Treat a breaking change as a new event version published in parallel during migration, then retire the old one when no consumer contracts reference it.

    War story: the field nobody knew was used

    A banking platform removed branchCode from the accounts API because "no one uses it any more". The loans service used it to route documents. Shared-environment E2E tests didn't cover that path. Loan document generation failed for three days before anyone noticed. Fix: consumer-driven contracts for all 14 consumers of the accounts API, verification in the provider's CI, and can-i-deploy as a required pipeline step. Lesson: only consumers know what they depend on. Let them write it down.

    12. Interview Corner¶

    Q1. What is contract testing?

    Testing that a provider's API matches what its consumers expect, without running both systems end to end.

    Q2. What is consumer-driven contract testing?

    Consumers define the expectations; the provider verifies them in its build.

    Q3. Name tools for it.

    Pact, Spring Cloud Contract, schema registries for events.

    Q4. How is it different from an integration test?

    Integration tests run a service with real infrastructure; contract tests check the agreement between two services' interfaces.

    Q5. What is a provider state?

    Data the provider sets up before verifying an interaction (e.g. "account 123 exists").

    Q1. Why match by type instead of exact values?

    So contracts don't break when test data changes; they should protect the shape the consumer depends on.

    Q2. Pact vs Spring Cloud Contract?

    Pact is consumer-driven and polyglot, with a broker; Spring Cloud Contract is provider-driven, JVM-centric, generating tests and WireMock stubs.

    Q3. What does can-i-deploy do?

    Checks the broker's verification matrix to see if a version is compatible with the versions deployed in the target environment.

    Q4. How do you contract-test Kafka events?

    Message pacts or schema contracts: consumers declare fields they read; the producer verifies samples/schemas against them.

    Q5. Is adding a field breaking?

    Usually not for consumers (tolerant readers), as long as it's optional for them; removing or retyping a field is breaking.

    Q1. "Replace a 2-hour E2E suite for 30 services."

    Contract tests on every service boundary, Testcontainers integration tests per service, can-i-deploy gating, and 10–20 E2E smoke tests for critical journeys.

    Q2. "How do you handle a breaking change you must make?"

    Expand/contract: add the new field/version, migrate consumers (their contracts change), verify, then remove the old once no contract references it.

    Q3. "How do contracts work with feature branches?"

    Tag by branch, use pending/WIP pacts so new expectations don't break the provider's main build prematurely.

    Q4. "Public API with unknown consumers?"

    Contracts can't cover unknown consumers; use OpenAPI diff checks, versioned endpoints, deprecation headers and long sunset periods.

    Q5. "What do contracts not catch?"

    Semantic changes with the same shape (units, meaning), performance, and multi-service workflow bugs.

    Problem: A contract asserts exact values (pricePaise == 28500). The provider changes its seeded test price; the API is unchanged. Show the failure and fix the contract with type matchers.

    Solution 
    package com.handbook.testing.contract.matching;

import com.handbook.testing.contract.core.Contract;
import com.handbook.testing.contract.core.Contract.AnyInteger;
import com.handbook.testing.contract.core.Contract.AnyString;
import com.handbook.testing.contract.core.Contract.Exactly;
import com.handbook.testing.contract.core.Contract.Interaction;
import com.handbook.testing.contract.core.Contract.Response;

import java.util.Map;

/** Coding challenge: exact-value contracts break when the provider's test data changes; type matchers don't. */
public class ExactVsTypeDemo {

    public static void main(String[] args) {
        System.out.println("=== Challenge: Exact Values vs Type Matchers in a Contract ===");
        Contract exact = new Contract("checkout", "pricing").uponReceiving(new Interaction("price of a SKU", "SKU exists",
                "/price/ATTA-5KG", 200, Map.of("sku", new Exactly("ATTA-5KG"), "pricePaise", new Exactly(28_500))));
        Contract byType = new Contract("checkout", "pricing").uponReceiving(new Interaction("price of a SKU", "SKU exists",
                "/price/ATTA-5KG", 200, Map.of("sku", new Exactly("ATTA-5KG"), "pricePaise", new AnyInteger(),
                "currency", new AnyString())));

        // The pricing team's test fixture changed the seeded price from 285.00 to 279.00. Nothing about the API changed.
        java.util.function.Function<String, Response> pricing = path ->
                new Response(200, Map.of("sku", "ATTA-5KG", "pricePaise", 27_900, "currency", "INR"));

        exact.verify(state -> { }, pricing).forEach(l -> System.out.println("exact values : " + l));
        byType.verify(state -> { }, pricing).forEach(l -> System.out.println("type matcher : " + l));
        System.out.println("Contract the SHAPE the consumer depends on; assert specific values in the consumer's own unit tests.");
    }
}

    Output:

    === Challenge: Exact Values vs Type Matchers in a Contract ===
exact values : FAIL checkout -> pricing: price of a SKU ['pricePaise' = 27900 is not exactly 28500]
type matcher : PASS checkout -> pricing: price of a SKU
Contract the SHAPE the consumer depends on; assert specific values in the consumer's own unit tests.

    Key points to say: exact values make contracts fail for reasons unrelated to compatibility; use type/regex matchers for data and exact matching only for values that are part of the protocol (enums, the requested id).

    • S: Removing an "unused" API field broke loan document generation for three days; E2E tests didn't cover it.
    • T: Let 14 consumer teams and the provider deploy independently without breakages.
    • A: Introduced Pact consumer contracts, provider verification in CI with provider states, a Pact Broker, and can-i-deploy as a required pipeline gate; trimmed the shared E2E suite to smoke tests.
