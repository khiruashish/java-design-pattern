    System Design Patterns¶

    System design rounds ask you to design a large system (a URL shortener, a feed, checkout, ride-hailing) in 45–60 minutes. Interviewers don't expect a perfect design; they look for a structured approach, sound building blocks, numbers, and trade-offs. This page collects the building blocks and shows how the microservices and architecture patterns from this handbook combine in classic designs.

    1. A framework for the round¶

    Step Time What to do
    1. Requirements 5 min Functional (core use cases only), non-functional (scale, latency, availability, consistency), out of scope
    2. Estimates 5 min Users, requests/s (average and peak), storage per day/year, bandwidth, read:write ratio
    3. API 5 min Key endpoints or events with request/response shapes
    4. Data model 5 min Entities, keys, access patterns → choice of store
    5. High-level design 10 min Clients → edge → services → data; draw the main flow
    6. Deep dives 15 min The 2–3 hardest parts: hot keys, consistency, fan-out, failure handling
    7. Wrap-up 5 min Bottlenecks, monitoring, what you'd do next, trade-offs you made

    Say the trade-off out loud

    "I'll use cache-aside with a 60-second TTL. That means a price change can show for up to a minute on product pages, but checkout re-reads from the database, so customers are never charged a stale price."

    2. Building blocks¶

    Block What it solves Key trade-offs Handbook link
    Load balancer Spread traffic, remove unhealthy instances L4 vs. L7; sticky sessions hurt scaling Service Discovery
    API gateway Single entry: auth, rate limits, routing Must be HA; no business logic API Gateway
    Cache Fast reads, less DB load Staleness, invalidation, stampedes LRU Cache, Proxy
    CDN Static/media content near users Cache invalidation, cost —
    Replication Read scaling, availability Replication lag → stale reads CQRS
    Sharding Write and storage scaling Hot shards, cross-shard queries, resharding Consistent hashing
    Message queue / log Async work, decoupling, buffering spikes At-least-once, ordering per partition Event-Driven, Producer-Consumer
    Search index Full-text and faceted search Eventual consistency with the source of truth CQRS
    Object storage Files, images, video Latency; use with CDN —
    Rate limiter Protect from abuse/overload Global vs. local counters Rate Limiter
    Idempotency Safe retries Storage of keys Idempotent Consumer
    Saga / outbox Cross-service consistency Eventual consistency, compensations Saga, Outbox
    Circuit breaker, timeouts, bulkheads Contain failures Tuning, fallbacks Circuit Breaker
    Tracing & metrics See what's happening Cost, sampling Distributed Tracing

    Caching strategies¶

    Strategy How Good for Watch out for
    Cache-aside (lazy loading) App reads cache; on miss, reads DB and fills cache Most read-heavy data Stale data until TTL; stampede on hot key expiry (use locks or early refresh)
    Read-through Cache library loads from DB on miss Same, less app code Same as cache-aside
    Write-through Write to cache and DB synchronously Read-after-write consistency Slower writes
    Write-behind Write to cache, flush to DB asynchronously Very write-heavy counters Data loss on cache failure
    Refresh-ahead Refresh hot keys before expiry Predictable hot keys Wasted refreshes

    Invalidation: delete the key on writes (not update) to avoid races; use short TTLs as a safety net; version keys (product:42:v7) for bulk changes.

    Consistent hashing¶

    Spreading keys across cache or database nodes with hash(key) % N moves almost every key when N changes. Consistent hashing places nodes and keys on a ring; adding a node moves only about 1/N of the keys. Virtual nodes even out the distribution.

    package com.handbook.lld.systemdesign;

import java.nio.charset.StandardCharsets;
import java.security.MessageDigest;
import java.security.NoSuchAlgorithmException;
import java.util.Map;
import java.util.SortedMap;
import java.util.TreeMap;

/**
 * Consistent hashing with virtual nodes: keys and nodes are hashed onto a ring; a key belongs to
 * the first node clockwise. Adding or removing a node moves only about 1/N of the keys, instead of
 * nearly all of them with {@code hash(key) % N}.
 */
public final class ConsistentHashRing {

    private final TreeMap<Long, String> ring = new TreeMap<>();
    private final int virtualNodes;

    public ConsistentHashRing(int virtualNodes) {
        this.virtualNodes = virtualNodes;
    }

    public void addNode(String node) {
        for (int i = 0; i < virtualNodes; i++) {
            ring.put(hash(node + "#" + i), node);
        }
    }

    public void removeNode(String node) {
        for (int i = 0; i < virtualNodes; i++) {
            ring.remove(hash(node + "#" + i));
        }
    }

    public String nodeFor(String key) {
        SortedMap<Long, String> tail = ring.tailMap(hash(key));
        return tail.isEmpty() ? ring.firstEntry().getValue() : tail.get(tail.firstKey());
    }

    /** First 8 bytes of MD5: stable across JVMs and well distributed (not for security). */
    static long hash(String s) {
        try {
            byte[] d = MessageDigest.getInstance("MD5").digest(s.getBytes(StandardCharsets.UTF_8));
            long h = 0;
            for (int i = 0; i < 8; i++) {
                h = (h << 8) | (d[i] & 0xff);
            }
            return h;
        } catch (NoSuchAlgorithmException e) {
            throw new IllegalStateException(e);
        }
    }

    public static Map<String, Integer> distribution(ConsistentHashRing ring, int keys) {
        Map<String, Integer> counts = new TreeMap<>();
        for (int i = 0; i < keys; i++) {
            counts.merge(ring.nodeFor("cart:" + i), 1, Integer::sum);
        }
        return counts;
    }
}

    package com.handbook.lld.systemdesign;

public class ConsistentHashingDemo {

    public static void main(String[] args) {
        int keys = 100_000;
        var ring = new ConsistentHashRing(200);
        for (String n : new String[] {"cache-1", "cache-2", "cache-3", "cache-4"}) {
            ring.addNode(n);
        }
        String[] before = new String[keys];
        for (int i = 0; i < keys; i++) {
            before[i] = ring.nodeFor("cart:" + i);
        }

        System.out.println("=== System design: consistent hashing for a cart cache cluster ===");
        System.out.println("4 nodes, 200 virtual nodes each: " + ConsistentHashRing.distribution(ring, keys));

        ring.addNode("cache-5");
        int moved = 0;
        for (int i = 0; i < keys; i++) {
            if (!ring.nodeFor("cart:" + i).equals(before[i])) {
                moved++;
            }
        }
        System.out.printf("add cache-5 -> %.1f%% of keys moved (ideal 1/5 = 20%%)%n", moved * 100.0 / keys);

        int movedModulo = 0;
        for (int i = 0; i < keys; i++) {
            int h = Math.floorMod(("cart:" + i).hashCode(), 4);
            int h5 = Math.floorMod(("cart:" + i).hashCode(), 5);
            if (h != h5) {
                movedModulo++;
            }
        }
        System.out.printf("with hash %% N instead: %.1f%% of keys would move%n", movedModulo * 100.0 / keys);
    }
}

    === System design: consistent hashing for a cart cache cluster ===
4 nodes, 200 virtual nodes each: {cache-1=25169, cache-2=23658, cache-3=24689, cache-4=26484}
add cache-5 -> 21.5% of keys moved (ideal 1/5 = 20%)
with hash % N instead: 80.1% of keys would move

    Used by: Cassandra and DynamoDB-style partitioning, Memcached clients, load balancers with session affinity, CDNs.

    Other patterns worth naming¶

    Pattern One-liner
    Leader election One instance does a job (lease in etcd/ZooKeeper/DB) with fencing tokens so a stale leader can't write
    Back-pressure Bounded queues; slow consumers push back instead of collapsing (Producer-Consumer)
    Write-ahead log Append before applying; recover by replaying (databases, Kafka, Event Sourcing)
    Bloom filter Probabilistic "definitely not present" checks to skip disk/DB lookups
    Snowflake IDs 64-bit time-ordered IDs: timestamp + machine ID + sequence; no central counter
    Fan-out on write vs. read Precompute feeds for most users; compute on read for celebrities with millions of followers
    Hedged requests Send a backup request after p95 latency to cut tail latency (reads only)
    Geo-partitioning Keep users' data in their region for latency and data residency

    3. Classic designs and the patterns inside them¶

    URL shortener¶

    flowchart LR
    C[Client] --> GW[API Gateway<br/>rate limit per key]
    GW --> W[Write service<br/>ID gen + base62]
    GW --> R[Redirect service]
    R --> CA[(Cache<br/>cache-aside)]
    CA -.miss.-> DB[(KV store<br/>sharded by code)]
    W --> DB
    R -->|click event| Q[[Kafka]] --> AN[Analytics]
    • Estimates: 100M new URLs/month ≈ 40 writes/s; reads 100× → 4,000/s, cache hit rate > 90%.
    • Patterns: rate limiter, cache-aside, consistent hashing for the KV store, event-driven analytics, 302 (trackable) vs. 301 (cacheable) redirects.

    E-commerce checkout¶

    flowchart LR
    App --> GW[Gateway] --> BFF[Mobile BFF] --> CO[Checkout service]
    CO -->|saga| INV[Inventory]
    CO -->|saga| PAY[Payment]
    CO -->|saga| DEL[Delivery]
    CO -->|outbox| K[[Kafka]]
    K --> N[Notifications]
    K --> RM[Order history<br/>CQRS read model]
    • Patterns: BFF, Saga with a pivot at payment, Outbox, Idempotency keys, CQRS for order history, Circuit Breaker on payment, flash-sale stock with atomic conditional updates.
    • See the Capstone for a runnable version.

    News feed / timeline¶

    flowchart LR
    P[Post service] -->|PostCreated| K[[Kafka]]
    K --> FO[Fan-out workers]
    FO --> FC[(Feed cache per user<br/>Redis lists)]
    U[User] --> FS[Feed service] --> FC
    FS -.celebrity posts.-> PS[(Posts store)]
    • Patterns: fan-out on write for normal users, on read for celebrities (hybrid), Producer-Consumer workers, cache per user, ranking as a Strategy, pagination with cursors.

    Ride-hailing (matching and tracking)¶

    flowchart LR
    D[Driver app<br/>location every 4s] --> LS[Location service] --> GEO[(Geo index<br/>geohash/H3 cells)]
    R[Rider app] --> M[Matching service] --> GEO
    M --> T[Trip service<br/>state machine]
    T -->|TripCompleted| K[[Kafka]] --> B[Billing]
    M --> ETA[ETA service<br/>circuit breaker + fallback]
    • Patterns: State for trips, geo-sharding, Circuit Breaker with estimate fallback, event-driven billing, idempotent fare charging, tracing across async hops.

    Notification platform¶

    flowchart LR
    S[Domain services] -->|events| K[[Kafka]] --> NS[Notification service]
    NS --> PREF[(Preferences)]
    NS --> D{Dedupe + rate limit}
    D --> Q1[[email queue]] --> E[Email provider]
    D --> Q2[[sms queue]] --> SMS[SMS provider]
    D --> Q3[[push queue]] --> PU[Push provider]
    Q1 & Q2 & Q3 -.failures.-> DLQ[[DLQ]]
    • Patterns: Strategy per channel, Template Method for messages, idempotent dedupe, rate limiting per user, bulkheads per provider, DLQs. See the Notification LLD.

    Chat / messaging¶

    • Patterns: WebSocket gateways with session routing (consistent hashing by user), messages persisted per conversation (partitioned by conversation ID for ordering), delivery receipts as events, offline push via the notification platform, idempotent client message IDs to avoid duplicates on reconnect.

    Distributed rate limiter, cache, or job scheduler¶

    • Rate limiter: token buckets in Redis with Lua, local fallback (Rate Limiter).
    • Distributed cache: consistent hashing, replication for hot keys, eviction (LRU), cache-aside.
    • Job scheduler: jobs table with SELECT ... FOR UPDATE SKIP LOCKED, leader election for the scheduler loop, idempotent jobs, retries with backoff, DLQ.

    4. Numbers worth remembering¶

    Operation Order of magnitude
    L1 cache / main memory reference ~1 ns / ~100 ns
    Read 1 MB sequentially from memory ~10 µs (varies by hardware)
    SSD random read ~16–100 µs
    Round trip within a data centre ~0.5 ms
    Redis GET over the network ~0.5–1 ms
    Simple indexed DB query ~1–10 ms
    Round trip across continents ~100–150 ms
    Quick math Value
    1 day ≈ 86,400 s ≈ 10⁵ s
    1M requests/day ≈ 12 requests/s average; plan peaks at 2–10×
    1 KB × 1B records ≈ 1 TB

    Estimation example: grocery orders

    5M orders/day → ~58 orders/s average; evening peak 5× → ~300/s. Each order ~2 KB with lines → 10 GB/day → ~3.6 TB/year (before indexes and replicas). Order-history reads 10× writes → ~3,000 reads/s at peak: a CQRS read model plus cache handles it comfortably.
