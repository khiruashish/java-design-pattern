    Google: Design Patterns in Interviews¶

    Commonly reported, not official

    This page summarizes publicly shared candidate experiences and Google's own general hiring guidance. Formats vary by role, level and location and change over time. Confirm the details of your loop with your recruiter.

    What the process commonly looks like¶

    • Coding interviews dominate for software engineers: data structures and algorithms, written in a shared doc or editor, with emphasis on correctness, complexity and clear code.
    • System design is commonly added for experienced (roughly L5+) candidates.
    • Behavioral / "Googleyness & leadership" conversations explore collaboration, ambiguity and impact.
    • Google's careers site describes evaluating general cognitive ability, role-related knowledge, leadership and "Googleyness". Feedback is typically reviewed by a hiring committee rather than decided by one interviewer.

    Where design patterns show up¶

    Google interviews rarely ask "define the Visitor pattern". Patterns show up implicitly:

    Situation Pattern knowledge that helps
    A coding problem with extensible rules ("now support a new type of discount") Strategy, Factory Method, open/closed design
    Iterating complex structures lazily Iterator, generators, Composite
    Designing an API or library Builder, Immutable Object, Facade
    Concurrency follow-ups Producer-Consumer, Thread Pool, Read-Write Lock
    System design Rate Limiter, caching, sharding, CQRS, Circuit Breaker

    What interviewers look for¶

    Signal What strong looks like
    Problem solving Clarifies, explores examples, chooses a sound approach, states complexity
    Code quality Readable names, small functions, correct edge cases, no over-engineering
    Testing Walks through examples, finds own bugs, mentions test cases
    Communication Thinks aloud, takes hints well, explains trade-offs
    Design (senior) Requirements → API → data model → scaling → failure modes, with numbers

    Pattern advice for Google-style coding rounds

    Use patterns only when they simplify the solution. An interface plus two implementations for an extensibility follow-up is great; a factory of builders for a 30-line problem is not. Say why you chose the structure.

    15 practice questions (with model answers)¶

    1. Design an iterator that flattens a nested list of integers lazily.

    Keep a stack of iterators; hasNext() advances until the top iterator yields an integer, pushing nested lists as you meet them. O(1) amortized per element, O(depth) memory. This is Iterator over a Composite.

    2. Implement an LRU cache with O(1) get and put. How would you make it thread-safe?

    HashMap + doubly linked list (or LinkedHashMap with accessOrder=true and removeEldestEntry). Thread safety: a single lock is simplest; for high concurrency, shard into N segments by key hash. See the LRU Cache LLD.

    3. A pricing function grows a new if every sprint. Refactor it.

    Extract each rule into a PricingRule Strategy (or Specification + action), register rules in a list or map, and test each independently. New rules don't touch existing code.

    4. Design a rate limiter for an API used by millions of clients.

    Token bucket per key, Redis with atomic Lua scripts for global limits, local buckets for hot paths, 429 with Retry-After. See Rate Limiter.

    5. Make an expensive, immutable configuration object available everywhere, loaded once.

    Lazy holder idiom or an enum singleton; better, dependency injection with a single instance. Immutable, so no locking after construction. See Singleton and Immutable Object.

    6. Implement an event system where components subscribe to typed events.

    Map<Class<?>, List<Consumer<?>>>, type-safe subscribe/publish, copy-on-write lists for concurrent publishing, and unsubscribe handles to avoid leaks. See Observer.

    7. Design a bounded blocking queue without java.util.concurrent collections.

    Array + head/tail indices + ReentrantLock with two Conditions (notFull, notEmpty); always wait in a while loop. See Producer-Consumer.

    8. Design a text editor's undo/redo.

    Command objects with execute/undo on two stacks, or Memento snapshots for complex state; merge consecutive typing commands.

    9. How would you parse and evaluate expressions like price > 100 AND category = 'fruit'?

    Tokenize → recursive-descent parser → AST of composite nodes → evaluate with an Interpreter or Visitor. Discuss precedence and error messages.

    10. Design a URL shortener. Which parts would you cache and how?

    ID generation (counter + base62 or random with collision check), key-value store sharded by key, cache-aside for hot links with TTL, 301 vs 302 trade-off, analytics via async events. See System design patterns.

    11. A service calls three backends; p99 latency is too high. What do you do?

    Call in parallel (Future/Promise), add per-call timeouts and hedged requests for idempotent reads, cache, and make optional calls degradable. See BFF.

    12. How do you guarantee only one instance runs a scheduled job across a cluster?

    Leader election (lease in a DB/etcd/ZooKeeper with fencing tokens), or a DB row lock (SELECT ... FOR UPDATE SKIP LOCKED), not a JVM singleton.

    13. Builder vs. telescoping constructors vs. static factories: when each?

    Static factories for simple named creation; builders for many optional parameters and validation across fields; avoid telescoping constructors. See Builder.

    14. Design a thread-safe counter used by 64 threads at very high rate.

    LongAdder (striped cells) beats AtomicLong under contention; reads sum the cells. Explain the trade-off (reads are not atomic snapshots).

    15. Tell me about a time you simplified an over-engineered design.

    STAR: what the abstraction cost (onboarding, bugs), the evidence you gathered, how you removed it safely (tests first), the measurable result. See the anti-patterns page: Anti-Patterns.

    4-week plan¶

    Week Do
    1 30 algorithm problems (arrays, hashing, two pointers, trees, graphs); code cleanly with small helper classes
    2 20 more problems + 4 design-flavoured coding problems (iterator, LRU, rate limiter, event bus) from this handbook
    3 Concurrency patterns; 2 system design mocks (URL shortener, news feed) using System design patterns
    4 Mock interviews with a timer; 5 STAR stories; revise the cheat sheet
