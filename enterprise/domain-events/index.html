    Domain Events¶

    🟡 Intermediate Enterprise / DDD Interview frequency ⭐⭐⭐⭐

    TL;DR

    A Domain Event is an immutable record of something that happened in the business (OrderPlaced, PolicyLapsed), raised by an aggregate and handled by whoever cares, after the change is committed. Use it to keep aggregates small and decoupled: the order says what happened, and loyalty, SMS and the warehouse decide what to do about it.

    See It in Motion¶

    Press Play to watch the calls travel between objects, or step through with Next and Back. Switch to Without it to see what goes wrong without the pattern. Open the full explorer with all 75 patterns

    1. Intent & Problem It Solves¶

    The problem in plain English: placeOrder() starts simple, then grows: award loyalty points, send an SMS, tell the warehouse, update analytics, notify the fraud team. Each addition makes the order module depend on another module, the transaction gets longer, and a failing SMS gateway now blocks orders.

    Definition (Eric Evans; Vaughn Vernon, Implementing DDD):

    Something that happened in the domain that domain experts care about, modelled as an immutable fact in the past tense. Aggregates publish events; other parts of the system subscribe and react, usually eventually consistent.

    Domain event vs integration event:

    Domain event Integration event
    Audience Same service / bounded context, in-process Other services, over a broker
    Shape Rich, can change with the model Public contract: versioned, minimal, stable
    Delivery After commit, in memory Through the Transactional Outbox

    2. Real-World Analogy¶

    A hospital PA announcement

    When a baby is born, the nurse doesn't personally phone the paediatrician, the records office, the billing desk and the family. She announces "baby born in room 12". Each team knows what to do when it hears that. The nurse's job stays the same no matter how many teams start listening.

    3. Structure¶

    sequenceDiagram autonumber participant UC as Use case participant O as Order (aggregate) participant Repo as Repository participant D as Dispatcher participant H1 as Loyalty handler participant H2 as SMS handler UC->>O: place() O->>O: record(OrderPlaced) UC->>Repo: save(order) (transaction) Note over UC,Repo: COMMIT UC->>D: dispatch(order.pullEvents()) D->>H1: OrderPlaced D->>H2: OrderPlaced
    Participant Responsibility
    Event Immutable record, past-tense name, ids + the facts handlers need, occurredAt
    Aggregate Records events as part of a state change; doesn't know the handlers
    Dispatcher / publisher Delivers events to handlers after commit (Spring ApplicationEventPublisher)
    Handlers React: update another aggregate, send notifications, write an outbox row

    4. Naive Approach (Without the Pattern)¶

    @Transactional
public void placeOrder(Order o) {
    orders.save(o);
    loyaltyService.addPoints(o.customerId(), o.total() / 100);   // order module depends on loyalty
    smsClient.send(o.phone(), "Order confirmed");                  // network call inside the transaction
    warehouseClient.startPicking(o.id());                          // another one
    analytics.track("order_placed", o);                            // and another
}
    • High coupling: every new reaction edits the order module.
    • Long, fragile transactions: an SMS timeout rolls back the order.
    • Side effects can happen even if the commit later fails.

    5. Three Real-World Examples¶

    Example 1: Order Raises Events, Modules React (Grocery)¶

    Scenario: A grocery modular monolith has ordering, loyalty, notifications and warehouse modules. When an order is placed, loyalty awards 1 point per INR 100, notifications send an SMS and the warehouse starts picking. On cancellation only the warehouse cares. New listeners (analytics, referral bonus) are added every quarter, and the ordering team doesn't want to touch their code each time.

    Design:

    flowchart LR O[Order.place] -->|OrderPlaced| D{Dispatcher} D --> L[Loyalty] D --> S[SMS] D --> W[Warehouse] C[Order.cancel] -->|OrderCancelled| D

    Full Code:

    package com.handbook.enterprise.domainevents.grocery;

import java.util.ArrayList;
import java.util.LinkedHashMap;
import java.util.List;
import java.util.Map;
import java.util.function.Consumer;

/** Aggregates RECORD events; the application layer DISPATCHES them after a successful commit. */
public final class DomainEvents {

    public sealed interface Event permits OrderPlaced, OrderCancelled { } // (1)!

    public record OrderPlaced(String orderId, String customerId, long totalPaise) implements Event { }

    public record OrderCancelled(String orderId, String reason) implements Event { }

    /** Base class for roots: collects events in memory while the transaction runs. */
    public abstract static class AggregateRoot {
        private final List<Event> pending = new ArrayList<>();

        protected void record(Event e) { pending.add(e); } // (2)!

        public List<Event> pullEvents() {
            List<Event> out = List.copyOf(pending);
            pending.clear();
            return out;
        }
    }

    /** In-process publisher: handlers subscribe by event type. */
    public static final class Dispatcher {
        private final Map<Class<?>, List<Consumer<Event>>> handlers = new LinkedHashMap<>();

        public <E extends Event> Dispatcher on(Class<E> type, Consumer<E> handler) {
            handlers.computeIfAbsent(type, k -> new ArrayList<>()).add(e -> handler.accept(type.cast(e)));
            return this;
        }

        public void dispatch(List<Event> events) {
            for (Event e : events) {
                handlers.getOrDefault(e.getClass(), List.of()).forEach(h -> h.accept(e));
            }
        }
    }

    private DomainEvents() {
    }
}
    1. A sealed hierarchy lists every event this context can raise; records make each one an immutable fact.
    2. The aggregate only records events in memory; publishing is the application layer's job. Spring Data's AbstractAggregateRoot.registerEvent works the same way.
    package com.handbook.enterprise.domainevents.grocery;

import com.handbook.enterprise.domainevents.grocery.DomainEvents.AggregateRoot;
import com.handbook.enterprise.domainevents.grocery.DomainEvents.OrderCancelled;
import com.handbook.enterprise.domainevents.grocery.DomainEvents.OrderPlaced;

/** The aggregate states WHAT happened; it doesn't know who cares (loyalty, SMS, stock). */
public final class Order extends AggregateRoot {

    private final String id;
    private final String customerId;
    private final long totalPaise;
    private String status = "NEW";

    public Order(String id, String customerId, long totalPaise) {
        this.id = id;
        this.customerId = customerId;
        this.totalPaise = totalPaise;
    }

    public void place() {
        status = "PLACED";
        record(new OrderPlaced(id, customerId, totalPaise));
    }

    public void cancel(String reason) {
        if (!status.equals("PLACED")) {
            throw new IllegalStateException("only placed orders can be cancelled");
        }
        status = "CANCELLED";
        record(new OrderCancelled(id, reason));
    }
}

    package com.handbook.enterprise.domainevents.grocery;

import com.handbook.enterprise.domainevents.grocery.DomainEvents.Dispatcher;
import com.handbook.enterprise.domainevents.grocery.DomainEvents.OrderCancelled;
import com.handbook.enterprise.domainevents.grocery.DomainEvents.OrderPlaced;

public class GroceryEventsDemo {

    public static void main(String[] args) {
        System.out.println("=== Grocery: Order Raises Events, Other Modules React ===");
        Dispatcher dispatcher = new Dispatcher()
                .on(OrderPlaced.class, e -> System.out.println("  [loyalty]   +" + e.totalPaise() / 10_000 + " points for " + e.customerId()))
                .on(OrderPlaced.class, e -> System.out.println("  [sms]       'Order " + e.orderId() + " confirmed' -> " + e.customerId()))
                .on(OrderPlaced.class, e -> System.out.println("  [warehouse] start picking " + e.orderId()))
                .on(OrderCancelled.class, e -> System.out.println("  [warehouse] stop picking " + e.orderId() + " (" + e.reason() + ")"));

        Order order = new Order("ORD-31", "CUST-5", 1_245_000);
        order.place();
        System.out.println("Use case: order.place() then save in a transaction... committed. Dispatching:");
        dispatcher.dispatch(order.pullEvents()); // (1)!

        order.cancel("customer changed mind");
        System.out.println("Use case: order.cancel() committed. Dispatching:");
        dispatcher.dispatch(order.pullEvents());
        System.out.println("Events left after dispatch: " + order.pullEvents().size());
    }
}
    1. Events are pulled from the aggregate and dispatched after the commit. If the transaction had failed, they'd be discarded with it.

    Output:

    === Grocery: Order Raises Events, Other Modules React ===
Use case: order.place() then save in a transaction... committed. Dispatching:
  [loyalty]   +124 points for CUST-5
  [sms]       'Order ORD-31 confirmed' -> CUST-5
  [warehouse] start picking ORD-31
Use case: order.cancel() committed. Dispatching:
  [warehouse] stop picking ORD-31 (customer changed mind)
Events left after dispatch: 0

    Why domain events here:

    • Order has zero dependencies on loyalty, SMS or warehouse.
    • New reactions are new handlers; the order module is closed for modification (OCP).
    • Each handler can later move to its own service by switching to integration events.

    Example 2: Lab Results and Critical Values (Healthcare)¶

    Scenario: A hospital lab system records 40,000 results a day. A potassium value below 2.5 or above 6.0 mmol/L is critical and must page the on-call doctor within minutes; normal values just go on the patient timeline. Amended results (e.g., a haemolysed sample re-run) must be flagged for review. Events carry the time they happened for the audit trail.

    Design:

    flowchart LR L[LabOrder.recordPotassium] --> R1["ResultRecorded(critical=false)"] --> T[Timeline] L --> R2["ResultRecorded(critical=true)"] --> P[Page on-call doctor] L --> A["ResultAmended"] --> V[Timeline + reviewer]

    Full Code:

    package com.handbook.enterprise.domainevents.healthcare;

import java.time.Clock;
import java.time.Instant;
import java.util.ArrayList;
import java.util.List;

/** Events as immutable facts in past tense, with when they happened, handled via pattern matching. */
public final class LabEvents {

    public sealed interface LabEvent permits ResultRecorded, ResultAmended {
        String patientId();
        Instant occurredAt();
    }

    public record ResultRecorded(String patientId, String test, double value, boolean critical, Instant occurredAt)
            implements LabEvent { }

    public record ResultAmended(String patientId, String test, double oldValue, double newValue, Instant occurredAt)
            implements LabEvent { }

    /** The aggregate: a lab order that knows the critical thresholds. */
    public static final class LabOrder {
        private final String patientId;
        private final Clock clock;
        private final List<LabEvent> events = new ArrayList<>();
        private Double potassium;

        public LabOrder(String patientId, Clock clock) {
            this.patientId = patientId;
            this.clock = clock;
        }

        public void recordPotassium(double mmolPerL) {
            boolean critical = mmolPerL < 2.5 || mmolPerL > 6.0; // (1)!
            if (potassium == null) {
                events.add(new ResultRecorded(patientId, "K+", mmolPerL, critical, clock.instant()));
            } else {
                events.add(new ResultAmended(patientId, "K+", potassium, mmolPerL, clock.instant()));
            }
            potassium = mmolPerL;
        }

        public List<LabEvent> pullEvents() {
            List<LabEvent> out = List.copyOf(events);
            events.clear();
            return out;
        }
    }

    /** Handler with an exhaustive switch: adding a new event type breaks compilation until handled. */
    public static String describe(LabEvent e) {
        return switch (e) { // (2)!
            case ResultRecorded r when r.critical() -> "PAGE on-call doctor: " + r.test() + "=" + r.value() + " for " + r.patientId();
            case ResultRecorded r -> "timeline: " + r.test() + "=" + r.value();
            case ResultAmended a -> "timeline: " + a.test() + " amended " + a.oldValue() + " -> " + a.newValue() + " (notify reviewer)";
        };
    }

    private LabEvents() {
    }
}
    1. The aggregate decides what is critical; the event carries that decision as a fact, so handlers don't re-implement clinical rules.
    2. An exhaustive switch over a sealed interface: add a new event type and every handler that doesn't handle it stops compiling.
    package com.handbook.enterprise.domainevents.healthcare;

import com.handbook.enterprise.domainevents.healthcare.LabEvents.LabOrder;

import java.time.Clock;
import java.time.Instant;
import java.time.ZoneOffset;

public class LabEventsDemo {

    public static void main(String[] args) {
        System.out.println("=== Healthcare: Lab Results as Domain Events ===");
        Clock clock = Clock.fixed(Instant.parse("2026-02-10T03:15:00Z"), ZoneOffset.UTC);
        LabOrder ward = new LabOrder("PAT-17", clock);
        ward.recordPotassium(4.1);
        LabOrder icu = new LabOrder("PAT-88", clock);
        icu.recordPotassium(6.8);
        icu.recordPotassium(5.9); // re-run after haemolysed sample

        for (LabOrder order : new LabOrder[] {ward, icu}) {
            order.pullEvents().forEach(e -> System.out.println(e.occurredAt() + " " + LabEvents.describe(e)));
        }
    }
}

    Output:

    === Healthcare: Lab Results as Domain Events ===
2026-02-10T03:15:00Z timeline: K+=4.1
2026-02-10T03:15:00Z PAGE on-call doctor: K+=6.8 for PAT-88
2026-02-10T03:15:00Z timeline: K+ amended 6.8 -> 5.9 (notify reviewer)

    Why domain events here:

    • Events are facts with timestamps, which is exactly what clinical audit needs.
    • Paging, timelines and review queues evolve independently of the lab model.
    • Pattern matching keeps handlers explicit and complete.

    Example 3: Domain Event to Integration Event (Insurance)¶

    Scenario: When a policy lapses (three missed premiums), the policy service's own modules react in-process (renewals schedules a win-back call, claims blocks new claims). Other services (CRM, marketing, the data lake) also need to know, but must not see underwriter notes or internal risk scores, and they need a stable, versioned contract. The integration event is written to the outbox in the same transaction.

    Design:

    flowchart LR P[Policy aggregate] -->|"PolicyLapsed: rich, internal"| H[In-process handlers] P --> M[Mapper] -->|"PolicyLapsedV1: public"| OB[(Outbox row)] --> K[[Kafka: insurance.policy.lapsed.v1]]

    Full Code:

    package com.handbook.enterprise.domainevents.insurance;

import java.time.LocalDate;
import java.util.Map;

/** Domain events stay internal and rich; integration events are a public, versioned contract. */
public final class PolicyEvents {

    /** Internal: can change freely with the model. Contains data other teams must not depend on. */
    public record PolicyLapsed(String policyId, String customerId, LocalDate lapsedOn, int missedPremiums,
                               String underwriterNotes, double internalRiskScore) { }

    /** Public: what other services may rely on. Stable names, a schema version, no internals. */
    public record PolicyLapsedV1(int schemaVersion, String eventType, String policyId, String customerId, String lapsedOn) { }

    public static PolicyLapsedV1 toIntegrationEvent(PolicyLapsed e) { // (1)!
        return new PolicyLapsedV1(1, "insurance.policy.lapsed.v1", e.policyId(), e.customerId(), e.lapsedOn().toString());
    }

    public static Map<String, String> outboxRow(PolicyLapsedV1 e) { // (2)!
        return Map.of("topic", "insurance.policy.lapsed.v1", "key", e.policyId(),
                "payload", "{\"schemaVersion\":1,\"policyId\":\"" + e.policyId() + "\",\"customerId\":\"" + e.customerId()
                        + "\",\"lapsedOn\":\"" + e.lapsedOn() + "\"}");
    }

    private PolicyEvents() {
    }
}
    1. An explicit mapping from the internal event to the public contract: anything not copied stays private.
    2. The integration event is stored as an outbox row in the same transaction; a relay publishes it to the broker.
    package com.handbook.enterprise.domainevents.insurance;

import com.handbook.enterprise.domainevents.insurance.PolicyEvents.PolicyLapsed;
import com.handbook.enterprise.domainevents.insurance.PolicyEvents.PolicyLapsedV1;

import java.time.LocalDate;
import java.util.Map;
import java.util.TreeMap;

public class PolicyEventsDemo {

    public static void main(String[] args) {
        System.out.println("=== Insurance: Domain Event -> Integration Event -> Outbox ===");
        PolicyLapsed internal = new PolicyLapsed("POL-2207", "CUST-41", LocalDate.of(2026, 4, 1), 3,
                "Customer called twice about premium hike", 0.82);
        System.out.println("In-process handlers see : " + internal);
        System.out.println("  [renewals] schedule win-back call; [claims] block new claims on POL-2207");

        PolicyLapsedV1 published = PolicyEvents.toIntegrationEvent(internal);
        System.out.println("Other services receive  : " + published);
        Map<String, String> row = new TreeMap<>(PolicyEvents.outboxRow(published));
        System.out.println("Outbox row (same DB transaction as the lapse): " + row);
        System.out.println("Notes and risk score never leave the policy service.");
    }
}

    Output:

    === Insurance: Domain Event -> Integration Event -> Outbox ===
In-process handlers see : PolicyLapsed[policyId=POL-2207, customerId=CUST-41, lapsedOn=2026-04-01, missedPremiums=3, underwriterNotes=Customer called twice about premium hike, internalRiskScore=0.82]
  [renewals] schedule win-back call; [claims] block new claims on POL-2207
Other services receive  : PolicyLapsedV1[schemaVersion=1, eventType=insurance.policy.lapsed.v1, policyId=POL-2207, customerId=CUST-41, lapsedOn=2026-04-01]
Outbox row (same DB transaction as the lapse): {key=POL-2207, payload={"schemaVersion":1,"policyId":"POL-2207","customerId":"CUST-41","lapsedOn":"2026-04-01"}, topic=insurance.policy.lapsed.v1}
Notes and risk score never leave the policy service.

    Why two kinds of event here:

    • The internal model can evolve without breaking other teams.
    • Sensitive data is never published by accident.
    • The outbox makes cross-service delivery reliable without distributed transactions.

    package com.handbook.enterprise.domainevents;

import java.time.LocalDate;

import java.util.List;

import static org.assertj.core.api.Assertions.assertThat;

class DomainEventsTest {

    @Test
    void aggregateRecordsEventsAndPullClearsThem() {
        Order o = new Order("O", "C", 100);
        o.place();
        assertThat(o.pullEvents()).containsExactly(new OrderPlaced("O", "C", 100));
        assertThat(o.pullEvents()).isEmpty();
    }

    @Test
    void dispatcherRoutesByType() {
        List<String> seen = new ArrayList<>();
        Order o = new Order("O", "C", 100);
        o.place();
        o.cancel("x");
        new Dispatcher().on(OrderPlaced.class, e -> seen.add(e.orderId())).dispatch(o.pullEvents());
        assertThat(seen).containsExactly("O");
    }

    @Test
    void criticalResultsPageTheDoctor() {
        LabOrder lab = new LabOrder("P", Clock.systemUTC());
        lab.recordPotassium(2.0);
        var event = lab.pullEvents().get(0);
        assertThat(event).isInstanceOf(ResultRecorded.class);
        assertThat(LabEvents.describe(event)).startsWith("PAGE");
    }

    @Test
    void integrationEventDropsInternalFields() {
        var v1 = PolicyEvents.toIntegrationEvent(new PolicyLapsed("P", "C", LocalDate.EPOCH, 3, "secret", 0.9));
        assertThat(v1.toString()).doesNotContain("secret").doesNotContain("0.9");
        assertThat(v1.schemaVersion()).isEqualTo(1);
    }
}

    6. Variations & Modern Java Take¶

    Variation Notes
    Record & dispatch after commit (Example 1) Aggregate collects; application dispatches after save commits
    Static DomainEvents.raise(...) Udi Dahan's original style: convenient but hidden global state; harder to test
    Spring @TransactionalEventListener(phase = AFTER_COMMIT) Handler runs only if the transaction commits; @Async to decouple further
    Spring Modulith @ApplicationModuleListener + an event publication registry (persisted, retried) between modules
    Event sourcing Domain events are the state (Event Sourcing)
    Sealed + records + pattern matching Exhaustive, type-safe event handling (Example 2)

    7. Where It Lives in Real Frameworks¶

    Where Domain events
    Spring ApplicationEventPublisher, @EventListener, @TransactionalEventListener, Spring Data AbstractAggregateRoot / @DomainEvents
    Spring Modulith Module-to-module events with an outbox-like publication log, Scenario testing API
    Axon AggregateLifecycle.apply(event), event handlers, sagas
    Jakarta CDI Event<T>.fire(), @Observes(during = TransactionPhase.AFTER_SUCCESS)
    Debezium / outbox Integration events leave the database via CDC

    8. Pros, Cons & Trade-offs¶

    ✅ Pros ❌ Cons
    Decouples the aggregate from its consequences Flow is harder to follow ("who handles this?")
    Small transactions; side effects outside them Eventual consistency between aggregates
    Natural audit trail and integration point Handler failures need retries and monitoring
    Easy to add reactions (OCP) Event schemas become contracts to version

    9. Pitfalls & Anti-Patterns¶

    Publishing before commit

    Sending the SMS inside the transaction means a later commit failure leaves the customer with a confirmation for an order that doesn't exist (coding challenge). Dispatch after commit, or use an outbox.

    Leaking internal events to other services

    Publishing domain events straight to Kafka turns every internal refactor into a breaking change and may leak sensitive fields. Map to integration events.

    Command disguised as an event

    SendSmsEvent is a command with one intended receiver. Events describe what happened (OrderPlaced), not what someone should do.

    Fat events vs thin events

    Thin events ({orderId}) force every handler to call back for data; fat events (full order) couple consumers to your model. Include what consumers need to act, plus ids.

    10. Senior / Architect Deep Dive (10–15 yrs)¶

    Delivery guarantees in-process. @TransactionalEventListener(AFTER_COMMIT) runs after commit, but if the JVM crashes in between, the event is lost. For must-not-lose reactions inside one service, persist the event (Spring Modulith's publication registry, or your own outbox table) and retry until handlers succeed.

    Ordering and idempotency. Handlers should tolerate duplicates (an at-least-once relay) and out-of-order arrival. Include the aggregate id and a sequence/version so consumers can detect gaps or stale events.

    Events as the integration backbone. Once integration events flow through a broker, they become the API between teams: give each a schema in a registry (Avro/Protobuf/JSON Schema), a topic naming convention (<context>.<aggregate>.<event>.v1) and compatibility rules (backward-compatible changes only).

    War story: the confirmation for a phantom order

    A grocery checkout sent the "order confirmed" SMS from inside the @Transactional method. On busy evenings, a unique-constraint violation on the invoice number occasionally failed the commit after the SMS was sent. About 200 customers a week waited for orders that didn't exist and then called support. Fix: the aggregate records OrderPlaced; the SMS handler became an @TransactionalEventListener(AFTER_COMMIT) reading from a persisted publication log. Lesson: side effects follow the commit, never precede it.

    Domain Event Observer Integration Event Command
    Meaning A business fact "Something changed" callback Business fact as a public contract A request to do something
    Coupling Aggregate doesn't know handlers Subject holds observer list Producer doesn't know consumers Sender knows the receiver

    Domain events are the domain-level form of Observer; across services they travel via Transactional Outbox to Idempotent Consumers.

    12. Interview Corner¶

    Q1. What is a domain event?

    An immutable record of something meaningful that happened in the business, named in the past tense, like OrderPlaced.

    Q2. Why past tense?

    Because it's a fact that already happened; handlers can't reject it, only react.

    Q3. How do you publish events in Spring?

    ApplicationEventPublisher.publishEvent(event) and handle with @EventListener or @TransactionalEventListener.

    Q4. What's in an event?

    Ids, the relevant facts, and when it happened (occurredAt).

    Q5. Event vs command?

    A command asks for something to be done (may be rejected); an event reports something that was done.

    Q1. @EventListener vs @TransactionalEventListener?

    The first runs immediately when published (inside the transaction); the second waits for a transaction phase, usually after commit.

    Q2. Domain vs integration events?

    Domain events are internal and can change freely; integration events are a versioned public contract sent through a broker.

    Q3. How do you make handler side effects reliable?

    Persist events (outbox / publication registry), retry handlers, make them idempotent.

    Q4. Where should events be raised?

    In aggregate methods that change state, so an event can't exist without the state change.

    Q5. How do you test events?

    Call the aggregate method and assert on pullEvents(); test handlers separately with a given event.

    Q1. "Design event-driven integration between ordering, payments and inventory."

    Each service publishes integration events via an outbox; consumers are idempotent; a saga coordinates the multi-step flow; schemas in a registry with compatibility checks.

    Q2. "How do you version events?"

    Additive changes stay in v1 (optional fields); breaking changes get a new type/topic (v2) published alongside v1 during migration.

    Q3. "Fat vs thin events?"

    Trade-off between consumer autonomy and coupling; a common middle ground is "event-carried state transfer" for data consumers need, plus ids.

    Q4. "Handlers are slow and delay the response."

    Make them async after commit, move them out of process via the broker, or give them their own thread pool/bulkhead.

    Q5. "How do you keep the flow understandable?"

    Event catalogue (AsyncAPI), tracing across handlers, Spring Modulith's documentation generation, and naming conventions.

    Problem: A use case sends a confirmation SMS while saving the order. The commit sometimes fails. Show the bug and fix it by recording the event and publishing after commit.

    Solution 
    package com.handbook.enterprise.domainevents.timing;

import java.util.ArrayList;
import java.util.List;

/** Coding challenge: an SMS for an order that never existed. Publish AFTER commit. */
public class PublishTimingDemo {

    static final List<String> SMS_SENT = new ArrayList<>();

    static void sendSms(String text) { SMS_SENT.add(text); }

    /** Simulated transaction: runs the body, then the commit can fail (e.g., unique key, deadlock). */
    static void inTransaction(boolean commitFails, Runnable body, Runnable afterCommit) {
        body.run();
        if (commitFails) {
            System.out.println("  COMMIT failed -> rolled back");
            return;
        }
        System.out.println("  COMMIT ok");
        afterCommit.run();
    }

    /** Events recorded during the transaction live and die with it. */
    static void placeOrder(String orderId, boolean commitFails) {
        List<String> pending = new ArrayList<>();
        inTransaction(commitFails, () -> pending.add(orderId + " confirmed"), () -> pending.forEach(PublishTimingDemo::sendSms));
    }

    public static void main(String[] args) {
        System.out.println("=== Challenge: When Should Events Be Published? ===");
        System.out.println("Publishing immediately inside the use case:");
        inTransaction(true, () -> sendSms("ORD-77 confirmed"), () -> { });
        System.out.println("  SMS sent: " + SMS_SENT + "  <- customer told about an order that doesn't exist");

        SMS_SENT.clear();
        System.out.println("Recording, then publishing after commit:");
        placeOrder("ORD-77", true);
        System.out.println("  SMS sent: " + SMS_SENT);
        placeOrder("ORD-78", false);
        System.out.println("  SMS sent: " + SMS_SENT);
        System.out.println("In Spring: @TransactionalEventListener(phase = AFTER_COMMIT), or an outbox row for other services.");
    }
}

    Output:

    === Challenge: When Should Events Be Published? ===
Publishing immediately inside the use case:
  COMMIT failed -> rolled back
  SMS sent: [ORD-77 confirmed]  <- customer told about an order that doesn't exist
Recording, then publishing after commit:
  COMMIT failed -> rolled back
  SMS sent: []
  COMMIT ok
  SMS sent: [ORD-78 confirmed]
In Spring: @TransactionalEventListener(phase = AFTER_COMMIT), or an outbox row for other services.

    Key points to say: side effects that can't be rolled back (SMS, email, HTTP calls) must happen after commit. Recorded events live and die with the transaction. For other services, write an outbox row in the same transaction instead.

    Behavioural tie-in (STAR) for experienced candidates

    • S: Around 200 customers a week got confirmations for orders that had rolled back.
    • T: Guarantee notifications only for committed orders, without slowing checkout.
    • A: Introduced domain events recorded by the Order aggregate, moved notifications to after-commit listeners backed by a persisted publication log, and added retries with idempotency keys.
    • R: Phantom confirmations dropped to zero; checkout p95 improved by 120 ms because the SMS call left the transaction.

    13. Quick Revision Card¶

    Remember in 30 seconds

    • Past-tense, immutable business facts raised by aggregates.
    • Record during the change; dispatch after commit.
    • Handlers decouple consequences from the aggregate.
    • Domain events internal; integration events public, versioned, via outbox.
    • Handlers idempotent; events carry ids and occurredAt.
