    Aggregate¶

    🟡 Intermediate → 🔴 Advanced Enterprise / DDD Interview frequency ⭐⭐⭐⭐

    TL;DR

    An Aggregate is a cluster of objects (a root entity plus the entities and values inside it) that is loaded, changed and saved as one unit, so its business rules are always true. Outsiders may only talk to the root. Use it to decide what must be consistent immediately (inside one aggregate, one transaction) versus eventually (between aggregates, via events).

    1. Intent & Problem It Solves¶

    The problem in plain English: an order has lines. A rule says "max 4 dozen mangoes per order during the flash sale" and "COD orders can't exceed INR 20,000". If any code can grab order.getLines() and add to it, or update order_line rows directly, those rules are only as strong as the most careless caller. In the other direction, if you make the boundary too big (a Customer that contains every order ever), every new order loads thousands of objects and two phones ordering at once conflict.

    Definition (Eric Evans, DDD; Vaughn Vernon, Effective Aggregate Design):

    A cluster of associated objects treated as a unit for the purpose of data changes. Each aggregate has a root and a boundary. Outside objects may hold references only to the root. Invariants within the boundary are enforced on every change.

    Vernon's four rules of thumb:

    1. Model true invariants inside the boundary (rules that must hold at the end of every transaction).
    2. Design small aggregates.
    3. Reference other aggregates by identity only.
    4. Use eventual consistency (domain events) between aggregates.

    2. Real-World Analogy¶

    A sealed tiffin box

    A tiffin (lunch box) has several compartments, but you hand over, carry and wash it as one thing. Nobody reaches in to swap the dal while it's in the delivery bag. The dabbawala doesn't carry your whole kitchen, just the tiffin (small aggregate), and the label on it is your address, not your house (reference by id).

    3. Structure¶

    classDiagram direction LR class Order { <<aggregate root>> -OrderId id -CustomerId customerId -List~Line~ lines -Status status +add(sku, price, qty) +markPacked() +total() } class Line { <<entity, internal>> -sku -qty } class Quantity { <<value>> } class Customer { <<another aggregate>> } Order "1" *-- "many" Line : owns Line --> Quantity Order ..> Customer : by id only
    Concept Responsibility
    Aggregate root The only entry point; public methods enforce all invariants
    Internal entities / values Can't be referenced or modified from outside (no public constructors, read-only views)
    Boundary One transaction changes one aggregate; one repository per root
    References to other aggregates By id (CustomerId), never by object

    4. Naive Approach (Without the Pattern)¶

    Order order = orderRepo.findById(id);
order.getLines().add(new OrderLine("ALPHONSO-1DZ", 5));   // bypasses the flash-sale limit
orderLineRepo.save(new OrderLine(orderId, "TV-32", 1));    // bypasses the COD cap, and the order total is now wrong
    • Invariants checked "somewhere", so in practice nowhere.
    • Repositories per table let anyone change part of the cluster.
    • No clear transaction boundary, so concurrent changes interleave.

    5. Three Real-World Examples¶

    Example 1: The Order Aggregate (Grocery)¶

    Scenario: During the Alphonso mango sale, each order may have at most 4 dozen, cash-on-delivery orders are capped at INR 20,000, and nothing can be added once the order is packed. Orders are edited by the customer app, customer-support tools and the substitutions service; all of them must obey the rules.

    Design:

    flowchart LR App[Customer app] --> R Support[Support tool] --> R Subs[Substitution service] --> R subgraph Aggregate boundary R["Order (root)<br/>add / markPacked"] --> L1[Line] R --> L2[Line] end

    Full Code:

    package com.handbook.enterprise.aggregate.grocery;

import java.util.ArrayList;
import java.util.Collections;
import java.util.List;
import java.util.Objects;

/** Aggregate root. The ONLY way to change lines is through Order, so its rules always hold. */
public final class Order {

    public enum Status { OPEN, PACKED }

    /** Entity inside the aggregate: identified by SKU within this order, never shared. */
    public static final class Line {
        private final String sku;
        private final long unitPaise;
        private int qty;

        private Line(String sku, long unitPaise, int qty) { // (1)!
            this.sku = sku;
            this.unitPaise = unitPaise;
            this.qty = qty;
        }

        public String sku() { return sku; }
        public int qty() { return qty; }
        public long subtotal() { return unitPaise * qty; }
        public String toString() { return sku + " x" + qty; }
    }

    static final int FLASH_SALE_LIMIT_PER_SKU = 4;
    static final long MAX_ORDER_PAISE = 2_000_000; // INR 20,000 cash-on-delivery cap

    private final String id;
    private final String customerId; // (2)!
    private final List<Line> lines = new ArrayList<>();
    private Status status = Status.OPEN;

    public Order(String id, String customerId) {
        this.id = Objects.requireNonNull(id);
        this.customerId = Objects.requireNonNull(customerId);
    }

    public void add(String sku, long unitPaise, int qty) { // (3)!
        if (status != Status.OPEN) {
            throw new IllegalStateException("order " + id + " is " + status + "; cannot add " + sku);
        }
        Line line = lines.stream().filter(l -> l.sku.equals(sku)).findFirst().orElse(null);
        int newQty = (line == null ? 0 : line.qty) + qty;
        if (newQty > FLASH_SALE_LIMIT_PER_SKU) {
            throw new IllegalArgumentException("max " + FLASH_SALE_LIMIT_PER_SKU + " of " + sku + " per order");
        }
        if (total() + unitPaise * qty > MAX_ORDER_PAISE) {
            throw new IllegalArgumentException("order total would exceed INR 20,000 COD cap");
        }
        if (line == null) {
            lines.add(new Line(sku, unitPaise, qty));
        } else {
            line.qty = newQty;
        }
    }

    public void markPacked() {
        if (lines.isEmpty()) {
            throw new IllegalStateException("cannot pack an empty order");
        }
        status = Status.PACKED;
    }

    public long total() { return lines.stream().mapToLong(Line::subtotal).sum(); }
    public List<Line> lines() { return Collections.unmodifiableList(lines); } // (4)!
    public Status status() { return status; }
    public String customerId() { return customerId; }
}
    1. Line's constructor is private: only Order can create lines.
    2. The customer is another aggregate, so it's referenced by id.
    3. Every invariant is checked in the root's command method, against the whole aggregate's state.
    4. Callers get a read-only view; they can look but not touch.
    package com.handbook.enterprise.aggregate.grocery;

public class OrderAggregateDemo {

    public static void main(String[] args) {
        System.out.println("=== Grocery: The Order Aggregate Guards Its Own Rules ===");
        Order order = new Order("ORD-9", "CUST-7");
        order.add("ALPHONSO-1DZ", 89_900, 2);
        order.add("ALPHONSO-1DZ", 89_900, 2);
        order.add("MILK-1L", 6_800, 3);
        System.out.println("Lines " + order.lines() + ", total INR " + order.total() / 100);
        attempt("5th dozen of mangoes", () -> order.add("ALPHONSO-1DZ", 89_900, 1));
        attempt("INR 18,000 TV in a grocery order", () -> order.add("TV-32", 1_800_000, 1));
        attempt("edit lines from outside", () -> order.lines().clear());
        order.markPacked();
        attempt("add after packing", () -> order.add("BREAD", 4_500, 1));
        System.out.println("Final: " + order.status() + " " + order.lines() + ", total INR " + order.total() / 100);
    }

    private static void attempt(String what, Runnable r) {
        try {
            r.run();
            System.out.println("  " + what + ": allowed?!");
        } catch (RuntimeException e) {
            System.out.println("  " + what + ": rejected (" + (e.getMessage() == null ? e.getClass().getSimpleName() : e.getMessage()) + ")");
        }
    }
}

    Output:

    === Grocery: The Order Aggregate Guards Its Own Rules ===
Lines [ALPHONSO-1DZ x4, MILK-1L x3], total INR 3800
  5th dozen of mangoes: rejected (max 4 of ALPHONSO-1DZ per order)
  INR 18,000 TV in a grocery order: rejected (order total would exceed INR 20,000 COD cap)
  edit lines from outside: rejected (UnsupportedOperationException)
  add after packing: rejected (order ORD-9 is PACKED; cannot add BREAD)
Final: PACKED [ALPHONSO-1DZ x4, MILK-1L x3], total INR 3800

    Why an aggregate here:

    • Rules that span lines (per-SKU limit, total cap) need the whole cluster to evaluate.
    • One root means one place to read the rules, and one place to test them.
    • The repository saves Order as a unit, so lines and totals never diverge.

    Example 2: Card Account with Holds (Banking)¶

    Scenario: A credit card with a INR 50,000 limit receives pre-authorisations (hotel, fuel), captures (often for less than the hold) and reversals. The invariant is posted balance + open holds ≤ limit, and it must hold even with authorisations arriving from different payment networks at the same moment. The account and its holds therefore form one aggregate, saved with a version number.

    Design:

    stateDiagram-v2 [*] --> Held : authorise (if available) Held --> Posted : capture (≤ hold) Held --> Released : release / expiry Posted --> [*] Released --> [*]

    Full Code:

    package com.handbook.enterprise.aggregate.banking;

import java.util.LinkedHashMap;
import java.util.Map;

/** Invariant: balance + all open holds <= credit limit. Holds are internal to the aggregate. */
public final class CardAccount {

    private final String cardId;
    private final long limitPaise;
    private long postedPaise;
    private final Map<String, Long> holds = new LinkedHashMap<>(); // authCode -> amount
    private long version;

    public CardAccount(String cardId, long limitPaise) {
        this.cardId = cardId;
        this.limitPaise = limitPaise;
    }

    public long available() {
        return limitPaise - postedPaise - holds.values().stream().mapToLong(Long::longValue).sum();
    }

    public boolean authorise(String authCode, long paise) { // (1)!
        if (paise > available()) {
            return false;
        }
        holds.put(authCode, paise);
        version++;
        return true;
    }

    public void capture(String authCode, long finalPaise) { // (2)!
        Long held = holds.remove(authCode);
        if (held == null) {
            throw new IllegalStateException("unknown or already settled auth " + authCode);
        }
        if (finalPaise > held) {
            holds.put(authCode, held);
            throw new IllegalArgumentException("capture " + finalPaise + " exceeds hold " + held);
        }
        postedPaise += finalPaise;
        version++;
    }

    public void release(String authCode) {
        if (holds.remove(authCode) != null) {
            version++;
        }
    }

    public long version() { return version; }

    @Override
    public String toString() {
        return cardId + "[posted=" + postedPaise / 100 + ", holds=" + holds.size() + ", available=" + available() / 100 + "]";
    }
}
    1. The limit check uses posted amounts and all open holds, which is only possible because the holds live inside the aggregate.
    2. Capture moves money from a hold to posted; it can't exceed the hold.
    package com.handbook.enterprise.aggregate.banking;

public class CardAccountDemo {

    public static void main(String[] args) {
        System.out.println("=== Banking: Credit Card Account as One Consistency Boundary ===");
        CardAccount card = new CardAccount("CARD-4111", 5_000_000); // INR 50,000 limit
        System.out.println("Hotel pre-auth 30,000 : " + card.authorise("A1", 3_000_000) + " -> " + card);
        System.out.println("Fuel pre-auth 2,000   : " + card.authorise("A2", 200_000) + " -> " + card);
        System.out.println("Laptop 25,000         : " + card.authorise("A3", 2_500_000) + " -> " + card);
        card.capture("A1", 2_400_000);   // final hotel bill lower than the hold
        System.out.println("Hotel captured 24,000 -> " + card);
        card.release("A2");              // fuel station sent a reversal
        System.out.println("Fuel released         -> " + card);
        System.out.println("Laptop retried        : " + card.authorise("A3", 2_500_000) + " -> " + card);
        System.out.println("Version after 5 state changes: " + card.version() + " (used for optimistic locking on save)");
    }
}

    Output:

    === Banking: Credit Card Account as One Consistency Boundary ===
Hotel pre-auth 30,000 : true -> CARD-4111[posted=0, holds=1, available=20000]
Fuel pre-auth 2,000   : true -> CARD-4111[posted=0, holds=2, available=18000]
Laptop 25,000         : false -> CARD-4111[posted=0, holds=2, available=18000]
Hotel captured 24,000 -> CARD-4111[posted=24000, holds=1, available=24000]
Fuel released         -> CARD-4111[posted=24000, holds=0, available=26000]
Laptop retried        : true -> CARD-4111[posted=24000, holds=1, available=1000]
Version after 5 state changes: 5 (used for optimistic locking on save)

    Why an aggregate here:

    • The invariant spans several objects (account + holds), so they belong together.
    • The version makes concurrent authorisations on the same card serialize via optimistic locking: one wins, the other reloads and re-checks.
    • Statements and rewards are separate aggregates that react to events, so they don't bloat this one.

    Example 3: Seats in a Show (Entertainment)¶

    Scenario: A ticketing platform sells seats for 12,000 shows a day; a blockbuster's first-day shows sell out in minutes. A booking for several seats must be all-or-nothing (a family of four doesn't want three seats), no seat may be sold twice, and a show can't exceed capacity. Customers and payments are separate aggregates referenced by id.

    Design:

    flowchart LR subgraph "Show aggregate (one per show)" S[Show root] --> Seats["seat → CustomerId"] end S -.->|by id| C[(Customer aggregate)] S -.->|event: SeatsBooked| P[(Payment aggregate)]

    Full Code:

    package com.handbook.enterprise.aggregate.cinema;

import java.util.Map;
import java.util.TreeMap;

/** A small aggregate: one show's seats. Customers and payments are referenced by ID only. */
public final class Show {

    public record ShowId(String value) { }

    public record CustomerId(String value) { }

    private final ShowId id;
    private final int capacity;
    private final Map<String, CustomerId> bookedSeats = new TreeMap<>(); // seat -> customer id (1)!

    public Show(ShowId id, int capacity) {
        this.id = id;
        this.capacity = capacity;
    }

    public void book(CustomerId customer, String... seats) { // (2)!
        for (String seat : seats) {
            if (bookedSeats.containsKey(seat)) {
                throw new IllegalStateException("seat " + seat + " already taken; nothing booked");
            }
        }
        if (bookedSeats.size() + seats.length > capacity) {
            throw new IllegalStateException("show " + id.value() + " is full");
        }
        for (String seat : seats) {
            bookedSeats.put(seat, customer);
        }
    }

    public Map<String, CustomerId> bookedSeats() { return Map.copyOf(bookedSeats); }

    @Override
    public String toString() {
        return id.value() + " " + bookedSeats.keySet() + " (" + bookedSeats.size() + "/" + capacity + ")";
    }
}
    1. The aggregate stores ids of other aggregates, never Customer objects.
    2. Check everything first, then mutate: a multi-seat booking is atomic within the aggregate.
    package com.handbook.enterprise.aggregate.cinema;

import com.handbook.enterprise.aggregate.cinema.Show.CustomerId;
import com.handbook.enterprise.aggregate.cinema.Show.ShowId;

public class ShowDemo {

    public static void main(String[] args) {
        System.out.println("=== Entertainment: Booking Seats in a Show Aggregate ===");
        Show show = new Show(new ShowId("STARLIGHT-AUDI3-2026-05-01-21:00"), 4);
        show.book(new CustomerId("C-1"), "F7", "F8");
        System.out.println("C-1 booked      -> " + show);
        try {
            show.book(new CustomerId("C-2"), "F9", "F8"); // F8 is taken
        } catch (IllegalStateException e) {
            System.out.println("C-2 F9+F8       -> " + e.getMessage() + " -> " + show);
        }
        show.book(new CustomerId("C-2"), "F9", "F10");
        System.out.println("C-2 F9+F10      -> " + show);
        try {
            show.book(new CustomerId("C-3"), "A1");
        } catch (IllegalStateException e) {
            System.out.println("C-3 A1          -> " + e.getMessage());
        }
    }
}

    Output:

    === Entertainment: Booking Seats in a Show Aggregate ===
C-1 booked      -> STARLIGHT-AUDI3-2026-05-01-21:00 [F7, F8] (2/4)
C-2 F9+F8       -> seat F8 already taken; nothing booked -> STARLIGHT-AUDI3-2026-05-01-21:00 [F7, F8] (2/4)
C-2 F9+F10      -> STARLIGHT-AUDI3-2026-05-01-21:00 [F10, F7, F8, F9] (4/4)
C-3 A1          -> show STARLIGHT-AUDI3-2026-05-01-21:00 is full

    Why an aggregate here:

    • "No double booking" is a true invariant of one show, so one show is the boundary.
    • Different shows never contend: the platform scales by spreading shows across shards.
    • Payment happens afterwards, driven by a SeatsBooked domain event; if it fails, a compensating action releases the seats.
    Unit Tests: AggregateTest.java 
    package com.handbook.enterprise.aggregate;

import com.handbook.enterprise.aggregate.banking.CardAccount;
import com.handbook.enterprise.aggregate.cinema.Show;
import com.handbook.enterprise.aggregate.cinema.Show.CustomerId;
import com.handbook.enterprise.aggregate.cinema.Show.ShowId;
import com.handbook.enterprise.aggregate.grocery.Order;
import org.junit.jupiter.api.Test;

import static org.assertj.core.api.Assertions.assertThat;
import static org.assertj.core.api.Assertions.assertThatThrownBy;

class AggregateTest {

    @Test
    void orderEnforcesPerSkuLimitAcrossAdds() {
        Order o = new Order("O", "C");
        o.add("A", 100, 3);
        assertThatThrownBy(() -> o.add("A", 100, 2)).hasMessageContaining("max 4");
        assertThat(o.lines()).singleElement().extracting(Order.Line::qty).isEqualTo(3);
    }

    @Test
    void linesCannotBeModifiedFromOutside() {
        Order o = new Order("O", "C");
        o.add("A", 100, 1);
        assertThatThrownBy(() -> o.lines().clear()).isInstanceOf(UnsupportedOperationException.class);
    }

    @Test
    void cardNeverExceedsLimitIncludingHolds() {
        CardAccount card = new CardAccount("C", 1_000);
        assertThat(card.authorise("a", 700)).isTrue();
        assertThat(card.authorise("b", 400)).isFalse();
        card.capture("a", 500);
        assertThat(card.authorise("b", 400)).isTrue();
        assertThat(card.available()).isEqualTo(100);
    }

    @Test
    void bookingIsAllOrNothing() {
        Show show = new Show(new ShowId("S"), 10);
        show.book(new CustomerId("1"), "A1");
        assertThatThrownBy(() -> show.book(new CustomerId("2"), "A2", "A1")).isInstanceOf(IllegalStateException.class);
        assertThat(show.bookedSeats()).containsOnlyKeys("A1");
    }
}

    6. Variations & Modern Java Take¶

    Variation Notes
    Mutable root, private internals Classic OO style (Examples 1–3) with JPA @Entity + @OneToMany(cascade = ALL, orphanRemoval = true)
    Immutable aggregates Records with methods returning a new aggregate version; repository saves the new version
    Event-sourced aggregates State rebuilt from events; commands emit new events after checking invariants (Event Sourcing)
    Sealed state types sealed interface OrderState permits Open, Packed, Delivered: illegal transitions don't compile
    Spring Data AbstractAggregateRoot registerEvent(...) inside the root; events published on save()
    jMolecules @AggregateRoot, @Entity, @ValueObject annotations + ArchUnit rules to verify DDD structure

    7. Where It Lives in Real Frameworks¶

    Where Aggregates
    Spring Data One repository per aggregate root; AbstractAggregateRoot, @DomainEvents; Spring Data JDBC is explicitly aggregate-oriented (saves the whole aggregate)
    JPA Cascades and orphanRemoval approximate the boundary; @Version for concurrency
    Axon Framework @Aggregate, @CommandHandler, @EventSourcingHandler
    Event stores One stream per aggregate instance (order-ORD-9), with expected-version appends

    8. Pros, Cons & Trade-offs¶

    ✅ Pros ❌ Cons
    Invariants enforced in one place, always Choosing boundaries is hard and domain-specific
    Clear transaction and locking unit Cross-aggregate rules become eventually consistent
    Small aggregates scale and rarely conflict More events and coordination code
    Maps naturally to microservices, shards and event streams ORMs push toward big object graphs; you must resist

    9. Pitfalls & Anti-Patterns¶

    Giant aggregates

    Customer containing all orders, addresses, payments and reviews: slow loads, huge saves and constant optimistic-lock conflicts. See the coding challenge.

    Exposing internals

    Returning a mutable List<Line> or public setters on internal entities lets callers break invariants. Return read-only views and expose intention-revealing commands.

    Modifying two aggregates in one transaction

    Tempting and sometimes acceptable inside one service, but it hides coupling and fails across services. Prefer one aggregate per transaction plus domain events.

    Object references across aggregates

    @ManyToOne Customer customer inside Order invites lazy-loading and cascades across boundaries. Store CustomerId.

    10. Senior / Architect Deep Dive (10–15 yrs)¶

    Finding the boundary. Ask: "Which rules must be true at the end of this transaction, and which can be true a few seconds later?" Only the first group justifies putting objects together. "Show can't be double-booked" is immediate; "customer gets a confirmation email" can be eventual.

    Concurrency is the real test. If two users regularly modify the same aggregate at the same time and get version conflicts, the aggregate is too big or the operations should be commutative. Seat booking per show is fine; "one aggregate for the whole cinema chain" is not.

    Aggregates and services. An aggregate never spans services. A service usually owns a few aggregate types; each is a natural unit for sharding (by aggregate id), for event streams and for idempotency keys.

    War story: the shopping cart that couldn't take two items

    A grocery app modelled Customer as one aggregate containing carts, orders, addresses and wallet. When households shared an account, two phones adding items at the same time hit optimistic-lock failures on Customer; the app retried silently and dropped items. Order placement for long-time customers took 1.8 s because it loaded five years of history. Fix: Cart, Order, Wallet became separate aggregates referencing CustomerId; the wallet balance update moved to an event handler. Lesson: small aggregates, references by id, events in between.

    12. Interview Corner¶

    Q1. What is an aggregate root?

    The single entity through which a cluster of objects is accessed and changed, e.g. Order for its lines.

    Q2. Why can't other code modify order lines directly?

    The root enforces rules that involve all lines (limits, totals); direct changes would bypass them.

    Q3. How many repositories does an aggregate have?

    One, for its root.

    Q4. How should an Order refer to its Customer?

    By CustomerId, not by holding the Customer object.

    Q5. Give an example invariant.

    "Order total must equal the sum of its lines" or "a seat can't be booked twice for the same show".

    Q1. How do you pick aggregate boundaries?

    Group objects that share a true invariant needing immediate consistency; keep everything else separate and connect with events.

    Q2. Why keep aggregates small?

    Faster loads, smaller transactions and fewer concurrency conflicts.

    Q3. How do you handle concurrent changes to one aggregate?

    Optimistic locking with a version on the root; on conflict, reload and re-run the command.

    Q4. A rule spans two aggregates. What now?

    Rethink the boundary, or accept eventual consistency: one aggregate emits an event, the other reacts, with compensations if needed.

    Q5. How does JPA support aggregates?

    Cascades, orphanRemoval, @Version, and only exposing a repository for the root.

    Q1. "Design aggregates for a ride-hailing trip."

    Trip (states, fare, driver/rider ids), Driver (availability), Payment separate. Matching changes Driver and creates Trip via an event-driven saga, not one transaction.

    Q2. "Hot aggregate: a flash-sale product's stock receives 5,000 writes per second."

    Split stock into buckets (sharded counters), reserve via a queue/single writer, or move to an atomic Redis counter with reconciliation. One aggregate row can't take that rate.

    Q3. "How do aggregates map to event sourcing?"

    One event stream per aggregate instance; commands validated against state rebuilt from that stream; appends with expected version.

    Q4. "Two aggregates in one transaction inside one service: ever OK?"

    Pragmatically, sometimes (same database, rare, low contention). Document it; it becomes a problem when you split the service or scale writes.

    Q5. "How do you enforce aggregate rules in a large codebase?"

    Package-private internals, no public setters, jMolecules/ArchUnit rules (repositories only for roots, no cross-aggregate object references).

    Problem: A Customer aggregate holds a list of every past order. Show the cost of placing one order for a loyal customer, and redesign the boundary.

    Solution 
    package com.handbook.enterprise.aggregate.sizing;

import java.util.ArrayList;
import java.util.List;

/** Coding challenge: a Customer aggregate that contains every order, and the fix. */
public class AggregateSizeDemo {

    static int objectsLoaded;

    record PastOrder(String id, long totalPaise) {
        PastOrder {
            objectsLoaded++;
        }
    }

    /** Too big: placing one order loads (and locks, and re-saves) the whole history. */
    static final class CustomerWithOrders {
        final String id;
        final List<PastOrder> orders = new ArrayList<>();
        CustomerWithOrders(String id, int history) {
            this.id = id;
            objectsLoaded++;
            for (int i = 0; i < history; i++) {
                orders.add(new PastOrder("O" + i, 50_000));
            }
        }
        void placeOrder(String orderId, long paise) { orders.add(new PastOrder(orderId, paise)); }
    }

    /** Right-sized: Order is its own aggregate that references the customer by ID. */
    record CustomerId(String value) { }

    record NewOrder(String id, CustomerId customer, long totalPaise) {
        NewOrder {
            objectsLoaded++;
        }
    }

    public static void main(String[] args) {
        System.out.println("=== Challenge: Finding the Right Aggregate Boundary ===");
        objectsLoaded = 0;
        CustomerWithOrders loyal = new CustomerWithOrders("CUST-1", 5_000); // 5 years of weekly orders
        loyal.placeOrder("O-NEW", 75_000);
        System.out.println("Customer-contains-orders: objects loaded to place 1 order = " + objectsLoaded);

        objectsLoaded = 0;
        NewOrder order = new NewOrder("O-NEW", new CustomerId("CUST-1"), 75_000);
        System.out.println("Order-references-customer-id: objects loaded = " + objectsLoaded + " (" + order.id() + ")");
        System.out.println("Two devices ordering at once no longer conflict on one giant Customer version.");
    }
}

    Output:

    === Challenge: Finding the Right Aggregate Boundary ===
Customer-contains-orders: objects loaded to place 1 order = 5002
Order-references-customer-id: objects loaded = 1 (O-NEW)
Two devices ordering at once no longer conflict on one giant Customer version.

    Key points to say: there's no invariant that needs all orders and the customer in one transaction, so Order is its own aggregate referencing CustomerId. Lists like "order history" become queries (or a read model), not aggregate contents.

    Behavioural tie-in (STAR) for experienced candidates

    • S: Shared household accounts lost cart items and order placement took 1.8 s for loyal customers.
    • T: Remove the conflicts and the latency without a rewrite.
    • A: Split the Customer mega-aggregate into Cart, Order and Wallet aggregates referenced by id; moved wallet updates to domain events; added a "no cross-aggregate references" ArchUnit rule.
    • R: Lock conflicts dropped 99%; order placement p95 went from 1.8 s to 140 ms.

    13. Quick Revision Card¶

    Remember in 30 seconds

    • Cluster + root + boundary; outsiders talk to the root only.
    • Boundary = true invariants that must hold at commit.
    • Small; reference other aggregates by id.
    • One aggregate per transaction; events between aggregates.
    • One repository per root; @Version on the root.
