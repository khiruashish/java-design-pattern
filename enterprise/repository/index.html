    Repository¶

    🟡 Intermediate Enterprise Interview frequency ⭐⭐⭐⭐⭐

    TL;DR

    A Repository looks like an in-memory collection of domain objects (save, findBySku, lowStock) and hides how they are stored. Use it whenever business logic needs to load or save aggregates, so the logic never contains SQL, JPA queries or HTTP calls to a storage service.

    See It in Motion¶

    Press Play to watch the calls travel between objects, or step through with Next and Back. Switch to Without it to see what goes wrong without the pattern. Open the full explorer

    1. Intent & Problem It Solves¶

    The problem in plain English: when a restock rule contains SELECT ... WHERE stock < ? and ResultSet mapping, three things go wrong. You can't unit-test the rule without a database; changing the schema means editing business code; and the same query gets copy-pasted into five services with five slightly different bugs.

    Definition (Martin Fowler, PoEAA; Eric Evans, DDD):

    Mediates between the domain and data mapping layers using a collection-like interface for accessing domain objects. In DDD, there is one repository per aggregate root.

    In a hexagonal service the repository interface is a port in the domain layer; the JDBC/JPA class is an adapter in infrastructure.

    Repository vs DAO: a DAO mirrors a table (insertRow, updateColumn) and lives in the data layer. A Repository speaks the domain's language (overdue(asOf), lowStock(threshold)), returns whole aggregates, and its interface belongs to the domain. A repository is often implemented with one or more DAOs.

    2. Real-World Analogy¶

    A library's front desk

    You ask the librarian for "the latest edition of Clean Code". You don't care whether it's on shelf 4B, in the basement archive or on loan from another branch. The desk (repository) speaks in books and editions, not in shelf coordinates (tables and rows).

    Participant Responsibility
    Aggregate root (Product) The domain object that is loaded and saved as a unit
    Repository interface Domain-language operations; owned by the domain/application layer
    Repository implementation SQL/JPA/NoSQL/HTTP details, mapping rows ↔ objects, optimistic locking
    Client (RestockService) Business logic that only sees the interface

    4. Naive Approach (Without the Pattern)¶

    public List<String> restockLowItems(int threshold) throws SQLException {
    try (var c = dataSource.getConnection();
         var ps = c.prepareStatement("SELECT sku, stock FROM product WHERE stock < ?")) {   // SQL in business code
        ps.setInt(1, threshold);
        var rs = ps.executeQuery();
        while (rs.next()) { /* mapping + business rule + UPDATE, all tangled */ }
    }
}
    • Business rule untestable without a database.
    • SRP violation: persistence and policy in one method.
    • Queries duplicated wherever products are needed.

    5. Three Real-World Examples¶

    Example 1: One Restock Service, Two Adapters (Grocery)¶

    Scenario: A dark store tracks 8,000 SKUs. Every 15 minutes a job tops up anything below 10 units. The rule must be unit-tested in milliseconds and run against PostgreSQL in production. Both adapters must behave identically, so a single contract test runs against each.

    Design:

    flowchart LR S[RestockService] --> P{{ProductRepository port}} P -.-> M[InMemoryProductRepository<br/>unit tests, demos] P -.-> J[JdbcProductRepository<br/>H2 / PostgreSQL]

    Full Code:

    package com.handbook.enterprise.repository.grocery;

import java.util.List;
import java.util.Optional;

/** The port: a collection-like interface in the language of the domain. */
public interface ProductRepository { // (1)!

    void save(Product product);

    Optional<Product> findBySku(String sku);

    List<Product> lowStock(int threshold); // (2)!
}
    1. The interface speaks domain language and returns domain objects. No ResultSet, no EntityManager.
    2. An intention-revealing finder. Prefer lowStock(threshold) over a generic findBy(String where).
    package com.handbook.enterprise.repository.grocery;

import javax.sql.DataSource;
import java.sql.Connection;
import java.sql.PreparedStatement;
import java.sql.ResultSet;
import java.sql.SQLException;
import java.util.ArrayList;
import java.util.List;
import java.util.Optional;

/** Adapter #2: real SQL (H2 here, PostgreSQL in production). All mapping lives here. */
public final class JdbcProductRepository implements ProductRepository {

    private final DataSource ds;

    public JdbcProductRepository(DataSource ds) {
        this.ds = ds;
    }

    public void save(Product p) {
        sql("MERGE INTO product (sku, name, category, price_paise, stock) KEY (sku) VALUES (?, ?, ?, ?, ?)", ps -> { // (1)!
            ps.setString(1, p.sku());
            ps.setString(2, p.name());
            ps.setString(3, p.category());
            ps.setLong(4, p.pricePaise());
            ps.setInt(5, p.stock());
            ps.executeUpdate();
            return null;
        });
    }

    public Optional<Product> findBySku(String sku) {
        return sql("SELECT * FROM product WHERE sku = ?", ps -> {
            ps.setString(1, sku);
            List<Product> found = map(ps.executeQuery());
            return found.stream().findFirst();
        });
    }

    public List<Product> lowStock(int threshold) {
        return sql("SELECT * FROM product WHERE stock < ? ORDER BY sku", ps -> {
            ps.setInt(1, threshold);
            return map(ps.executeQuery());
        });
    }

    private static List<Product> map(ResultSet rs) throws SQLException { // (2)!
        List<Product> out = new ArrayList<>();
        while (rs.next()) {
            out.add(new Product(rs.getString("sku"), rs.getString("name"), rs.getString("category"),
                    rs.getLong("price_paise"), rs.getInt("stock")));
        }
        return out;
    }

    private interface Body<T> { T run(PreparedStatement ps) throws SQLException; }

    private <T> T sql(String sql, Body<T> body) {
        try (Connection c = ds.getConnection(); PreparedStatement ps = c.prepareStatement(sql)) {
            return body.run(ps);
        } catch (SQLException e) {
            throw new IllegalStateException(e);
        }
    }
}
    1. save is an upsert: callers think "put it in the collection", not "insert vs update".
    2. All row ↔ object mapping is here. Schema changes stop at this file.
    package com.handbook.enterprise.repository.grocery;

import java.util.Comparator;
import java.util.List;
import java.util.Map;
import java.util.Optional;
import java.util.concurrent.ConcurrentHashMap;

/** Adapter #1: for unit tests and local demos. */
public final class InMemoryProductRepository implements ProductRepository {

    private final Map<String, Product> rows = new ConcurrentHashMap<>();

    public void save(Product product) { rows.put(product.sku(), product); }

    public Optional<Product> findBySku(String sku) { return Optional.ofNullable(rows.get(sku)); }

    public List<Product> lowStock(int threshold) {
        return rows.values().stream().filter(p -> p.stock() < threshold)
                .sorted(Comparator.comparing(Product::sku)).toList();
    }
}

    package com.handbook.enterprise.repository.grocery;

import java.util.List;

/** Application logic written once against the port; works with any adapter. */
public final class RestockService {

    private final ProductRepository products;

    public RestockService(ProductRepository products) {
        this.products = products;
    }

    public List<String> restockLowItems(int threshold, int topUpTo) {
        return products.lowStock(threshold).stream().map(p -> {
            products.save(p.withStock(topUpTo));
            return p.sku() + " " + p.stock() + "->" + topUpTo;
        }).toList();
    }
}

    package com.handbook.enterprise.repository.grocery;

/** Domain object. Knows nothing about SQL. */
public record Product(String sku, String name, String category, long pricePaise, int stock) {

    public Product withStock(int newStock) {
        return new Product(sku, name, category, pricePaise, newStock);
    }
}

    package com.handbook.enterprise.repository.grocery;

import org.h2.jdbcx.JdbcDataSource;

import java.sql.Connection;
import java.sql.SQLException;
import java.util.List;

public class GroceryRepositoryDemo {

    public static void main(String[] args) throws SQLException {
        System.out.println("=== Grocery: One Restock Service, Two Repository Adapters ===");
        JdbcDataSource ds = new JdbcDataSource();
        ds.setURL("jdbc:h2:mem:catalog;DB_CLOSE_DELAY=-1");
        try (Connection c = ds.getConnection()) {
            c.createStatement().execute("CREATE TABLE product (sku VARCHAR PRIMARY KEY, name VARCHAR, category VARCHAR,"
                    + " price_paise BIGINT, stock INT)");
        }
        for (ProductRepository repo : List.of(new InMemoryProductRepository(), new JdbcProductRepository(ds))) {
            repo.save(new Product("MILK-1L", "Toned Milk 1L", "dairy", 6_800, 4));
            repo.save(new Product("ATTA-5KG", "Wheat Atta 5kg", "staples", 28_500, 40));
            repo.save(new Product("EGG-12", "Eggs (12)", "dairy", 9_000, 2));
            List<String> restocked = new RestockService(repo).restockLowItems(10, 50);
            System.out.printf("%-26s restocked %s, MILK-1L stock now %d%n", repo.getClass().getSimpleName(), restocked,
                    repo.findBySku("MILK-1L").orElseThrow().stock());
        }
        System.out.println("RestockService has no SQL and no Map: storage is a detail behind the port.");
    }
}

    Output:

    === Grocery: One Restock Service, Two Repository Adapters ===
InMemoryProductRepository  restocked [EGG-12 2->50, MILK-1L 4->50], MILK-1L stock now 50
JdbcProductRepository      restocked [EGG-12 2->50, MILK-1L 4->50], MILK-1L stock now 50
RestockService has no SQL and no Map: storage is a detail behind the port.

    Why a repository here:

    • The restock rule is tested against the in-memory adapter in microseconds.
    • The same contract test (see Unit Tests) runs against both adapters, so the fake can't drift from reality.
    • Switching PostgreSQL for DynamoDB touches one class.

    Example 2: Optimistic Locking in the Repository (Banking)¶

    Scenario: A savings account has INR 10,000. The customer withdraws INR 8,000 at an ATM while a UPI payment of INR 7,000 is in flight. Both channels loaded the same balance. Without protection, the second save overwrites the first and the bank loses INR 7,000 (a lost update). The repository rejects stale writes using a version number, like UPDATE account SET ... WHERE id = ? AND version = ?.

    Design:

    sequenceDiagram autonumber participant ATM participant UPI participant R as AccountRepository ATM->>R: findById (v1, 10,000) UPI->>R: findById (v1, 10,000) ATM->>R: save(balance 2,000, v1) ✅ now v2 UPI->>R: save(balance 3,000, v1) ❌ stale UPI->>R: findById (v2, 2,000) → withdraw 7,000 → insufficient funds

    Full Code:

    package com.handbook.enterprise.repository.banking;

import java.util.ConcurrentModificationException;
import java.util.HashMap;
import java.util.Map;
import java.util.Optional;

/** Repository that protects aggregates with optimistic locking (a version column). */
public final class AccountRepository {

    public record Account(String id, long balancePaise, long version) {
        public Account withdraw(long paise) {
            if (paise > balancePaise) {
                throw new IllegalArgumentException("insufficient funds");
            }
            return new Account(id, balancePaise - paise, version);
        }
    }

    private final Map<String, Account> table = new HashMap<>();

    public synchronized Optional<Account> findById(String id) {
        return Optional.ofNullable(table.get(id));
    }

    /** Saves only if nobody else saved since we loaded: UPDATE ... WHERE id = ? AND version = ? */
    public synchronized Account save(Account changed) { // (1)!
        Account current = table.get(changed.id());
        long expected = current == null ? 0 : current.version();
        if (changed.version() != expected) {
            throw new ConcurrentModificationException("Account " + changed.id() + " was modified (expected v"
                    + changed.version() + ", found v" + expected + ")");
        }
        Account stored = new Account(changed.id(), changed.balancePaise(), expected + 1);
        table.put(stored.id(), stored);
        return stored;
    }
}
    1. The repository enforces optimistic concurrency: the save succeeds only if the stored version equals the version the caller loaded. JPA does this with @Version.
    package com.handbook.enterprise.repository.banking;

import com.handbook.enterprise.repository.banking.AccountRepository.Account;

import java.util.ConcurrentModificationException;

public class BankingRepositoryDemo {

    public static void main(String[] args) {
        System.out.println("=== Banking: Repository with Optimistic Locking ===");
        AccountRepository accounts = new AccountRepository();
        accounts.save(new Account("SB-501", 1_000_000, 0));

        Account atm = accounts.findById("SB-501").orElseThrow();    // two channels load v1
        Account upi = accounts.findById("SB-501").orElseThrow();
        System.out.println("ATM and UPI both loaded " + atm);

        System.out.println("ATM saves  -> " + accounts.save(atm.withdraw(800_000)));
        try {
            accounts.save(upi.withdraw(700_000));                   // based on the stale balance
        } catch (ConcurrentModificationException e) {
            System.out.println("UPI rejected: " + e.getMessage());
            Account fresh = accounts.findById("SB-501").orElseThrow(); // (1)!
            try {
                accounts.save(fresh.withdraw(700_000));
            } catch (IllegalArgumentException again) {
                System.out.println("UPI retried on fresh state: " + again.getMessage() + " (no overdraft)");
            }
        }
    }
}
    1. The correct reaction to a version conflict: reload and re-run the business rule on fresh state, never blindly retry the same write.

    Output:

    === Banking: Repository with Optimistic Locking ===
ATM and UPI both loaded Account[id=SB-501, balancePaise=1000000, version=1]
ATM saves  -> Account[id=SB-501, balancePaise=200000, version=2]
UPI rejected: Account SB-501 was modified (expected v1, found v2)
UPI retried on fresh state: insufficient funds (no overdraft)

    Why a repository here:

    • Concurrency control belongs with persistence, so every caller gets it for free.
    • The aggregate (Account) still enforces its own invariant (no overdraft).
    • Callers work with whole aggregates, never with half-updated rows.

    Example 3: Domain Finders and a Caching Decorator (Logistics)¶

    Scenario: A courier's tracking page is refreshed about 1,000 times per parcel on delivery day. Ops also run an "overdue shipments" report. The tracking lookup should be cached; the report must always be fresh. Because callers depend on the ShipmentRepository interface, caching is added as a decorator without touching them.

    Design:

    flowchart LR T[Tracking page] --> C[CachingShipmentRepository] O[Ops report] --> C C -->|"byAwb: cache miss only"| D[DbShipmentRepository] C -->|"overdue: always"| D

    Full Code:

    package com.handbook.enterprise.repository.logistics;

import java.time.LocalDate;
import java.util.HashMap;
import java.util.List;
import java.util.Map;
import java.util.Optional;

/** Intention-revealing finders plus a caching decorator over the repository port. */
public final class Shipments {

    public record Shipment(String awb, String city, LocalDate promised, boolean delivered) {
    }

    public interface ShipmentRepository {
        Optional<Shipment> byAwb(String awb);
        List<Shipment> overdue(LocalDate asOf); // (1)!
    }

    /** Pretend database that counts round trips. */
    public static final class DbShipmentRepository implements ShipmentRepository {
        private final Map<String, Shipment> rows = new HashMap<>();
        public int queries;

        public DbShipmentRepository add(Shipment s) {
            rows.put(s.awb(), s);
            return this;
        }

        public Optional<Shipment> byAwb(String awb) {
            queries++;
            return Optional.ofNullable(rows.get(awb));
        }

        public List<Shipment> overdue(LocalDate asOf) {
            queries++;
            return rows.values().stream().filter(s -> !s.delivered() && s.promised().isBefore(asOf))
                    .sorted(java.util.Comparator.comparing(Shipment::awb)).toList();
        }
    }

    /** Decorator: same port, adds a read-through cache for hot tracking lookups. */
    public static final class CachingShipmentRepository implements ShipmentRepository { // (2)!
        private final ShipmentRepository inner;
        private final Map<String, Optional<Shipment>> cache = new HashMap<>();

        public CachingShipmentRepository(ShipmentRepository inner) {
            this.inner = inner;
        }

        public Optional<Shipment> byAwb(String awb) { return cache.computeIfAbsent(awb, inner::byAwb); }

        public List<Shipment> overdue(LocalDate asOf) { return inner.overdue(asOf); } // reports always go to the DB
    }

    private Shipments() {
    }
}
    1. A domain question as a method (overdue(asOf)), not findByDeliveredFalseAndPromisedBefore. Spring Data can generate either; the domain name reads better at call sites.
    2. A decorator implementing the same port: callers can't tell it's there.
    package com.handbook.enterprise.repository.logistics;

import com.handbook.enterprise.repository.logistics.Shipments.CachingShipmentRepository;
import com.handbook.enterprise.repository.logistics.Shipments.DbShipmentRepository;
import com.handbook.enterprise.repository.logistics.Shipments.Shipment;
import com.handbook.enterprise.repository.logistics.Shipments.ShipmentRepository;

import java.time.LocalDate;

public class LogisticsRepositoryDemo {

    public static void main(String[] args) {
        System.out.println("=== Logistics: Domain Finders and a Caching Repository ===");
        DbShipmentRepository db = new DbShipmentRepository()
                .add(new Shipment("AWB-1", "Pune", LocalDate.of(2026, 3, 1), true))
                .add(new Shipment("AWB-2", "Delhi", LocalDate.of(2026, 3, 2), false))
                .add(new Shipment("AWB-3", "Chennai", LocalDate.of(2026, 3, 9), false));
        ShipmentRepository repo = new CachingShipmentRepository(db);

        for (int i = 0; i < 1_000; i++) {
            repo.byAwb("AWB-2"); // customers refreshing the tracking page
        }
        System.out.println("1,000 tracking lookups -> DB queries: " + db.queries);
        System.out.println("Overdue as of 2026-03-05: " + repo.overdue(LocalDate.of(2026, 3, 5)).stream()
                .map(s -> s.awb() + " (" + s.city() + ")").toList());
        System.out.println("DB queries after report: " + db.queries);
    }
}

    Output:

    === Logistics: Domain Finders and a Caching Repository ===
1,000 tracking lookups -> DB queries: 1
Overdue as of 2026-03-05: [AWB-2 (Delhi)]
DB queries after report: 2

    Why a repository here:

    • An interface gives you a seam for cross-cutting concerns (caching, metrics, tenant filters).
    • Finder names document the business questions the system answers.
    • The cached and uncached paths are explicit, not hidden in an ORM's second-level cache.
    Unit Tests: RepositoryTest.java 
    package com.handbook.enterprise.repository;

import com.handbook.enterprise.repository.banking.AccountRepository;
import com.handbook.enterprise.repository.banking.AccountRepository.Account;
import com.handbook.enterprise.repository.grocery.InMemoryProductRepository;
import com.handbook.enterprise.repository.grocery.JdbcProductRepository;
import com.handbook.enterprise.repository.grocery.Product;
import com.handbook.enterprise.repository.grocery.ProductRepository;
import com.handbook.enterprise.repository.logistics.Shipments.CachingShipmentRepository;
import com.handbook.enterprise.repository.logistics.Shipments.DbShipmentRepository;
import com.handbook.enterprise.repository.logistics.Shipments.Shipment;
import org.h2.jdbcx.JdbcDataSource;
import org.junit.jupiter.params.ParameterizedTest;
import org.junit.jupiter.params.provider.MethodSource;
import org.junit.jupiter.api.Test;

import java.sql.Connection;
import java.time.LocalDate;
import java.util.ConcurrentModificationException;
import java.util.List;
import java.util.UUID;

import static org.assertj.core.api.Assertions.assertThat;
import static org.assertj.core.api.Assertions.assertThatThrownBy;

class RepositoryTest {

    static List<ProductRepository> adapters() throws Exception {
        JdbcDataSource ds = new JdbcDataSource();
        ds.setURL("jdbc:h2:mem:" + UUID.randomUUID() + ";DB_CLOSE_DELAY=-1");
        try (Connection c = ds.getConnection()) {
            c.createStatement().execute("CREATE TABLE product (sku VARCHAR PRIMARY KEY, name VARCHAR, category VARCHAR,"
                    + " price_paise BIGINT, stock INT)");
        }
        return List.of(new InMemoryProductRepository(), new JdbcProductRepository(ds));
    }

    /** One contract, every adapter: the in-memory fake can't drift from the real one. */
    @ParameterizedTest
    @MethodSource("adapters")
    void everyAdapterHonoursTheSameContract(ProductRepository repo) {
        repo.save(new Product("A", "a", "x", 100, 1));
        repo.save(new Product("B", "b", "x", 100, 99));
        repo.save(new Product("A", "a", "x", 100, 5)); // upsert
        assertThat(repo.findBySku("A")).get().extracting(Product::stock).isEqualTo(5);
        assertThat(repo.findBySku("missing")).isEmpty();
        assertThat(repo.lowStock(10)).extracting(Product::sku).containsExactly("A");
    }

    @Test
    void staleWritesAreRejected() {
        AccountRepository repo = new AccountRepository();
        repo.save(new Account("X", 100, 0));
        Account a = repo.findById("X").orElseThrow();
        repo.save(a.withdraw(10));
        assertThatThrownBy(() -> repo.save(a.withdraw(20))).isInstanceOf(ConcurrentModificationException.class);
        assertThat(repo.findById("X").orElseThrow().balancePaise()).isEqualTo(90);
    }

    @Test
    void cachingDecoratorHitsTheDatabaseOnce() {
        DbShipmentRepository db = new DbShipmentRepository().add(new Shipment("A", "P", LocalDate.EPOCH, false));
        CachingShipmentRepository repo = new CachingShipmentRepository(db);
        repo.byAwb("A");
        repo.byAwb("A");
        assertThat(db.queries).isEqualTo(1);
    }
}

    6. Variations & Modern Java Take¶

    Variation Notes
    Spring Data repositories interface ProductRepository extends JpaRepository<Product, String>: derived queries, @Query, paging. Fast to write; leaks JPA types into callers unless you wrap it
    Port + adapter (hexagonal) Your own interface in domain; a Spring Data repository used inside the adapter. Keeps the domain framework-free
    Specification-based findAll(Specification<T>) for dynamic filters (see Specification)
    Read-only query repositories For CQRS read models: return DTOs/projections, not aggregates
    Records as aggregates Immutable records + withX methods; the repository saves the new version

    7. Where It Lives in Real Frameworks¶

    Where Repository
    Spring Data CrudRepository, JpaRepository, MongoRepository, R2dbcRepository, @Repository (also translates exceptions to DataAccessException)
    Jakarta Data (EE 11) @Repository interfaces with @Find, @Insert, @Query
    Hibernate / JPA EntityManager is the Unit of Work underneath; @Version for optimistic locking
    Micronaut Data Compile-time generated repositories
    Axon / event-sourced systems Repository<Aggregate> that loads by replaying events

    8. Pros, Cons & Trade-offs¶

    ✅ Pros ❌ Cons
    Business logic is storage-agnostic and unit-testable Another layer of interfaces and mapping code
    Queries live in one place, named by intent Easy to over-generalize into a leaky "generic repository"
    Seam for caching, auditing, multi-tenancy, optimistic locking Hides query cost: an innocent findAll() can load a million rows
    One repository per aggregate enforces consistency boundaries Mapping domain ↔ entity is extra work in rich domains

    9. Pitfalls & Anti-Patterns¶

    Generic repository with findBy(String where)

    Repository<T>.query(String sql) pushes SQL back into business code and makes every caller depend on the schema. Expose named, typed finders.

    Returning IQueryable-style builders or JPA entities everywhere

    If callers build CriteriaQuery or touch lazy-loaded @Entity graphs, the repository hides nothing. Lazy-loading outside a transaction becomes LazyInitializationException in a controller.

    One repository per table

    Repositories are per aggregate root. An OrderLineRepository lets code modify lines without going through Order, bypassing its invariants.

    In-memory fakes that don't copy

    A HashMap that hands out stored objects lets tests "save" without calling save(). See the coding challenge.

    10. Senior / Architect Deep Dive (10–15 yrs)¶

    Where transactions go. The repository does not open transactions per call; the application service (use case) owns the transaction boundary (@Transactional) so several repository calls commit together. That's the Unit of Work.

    Performance. Design finders for the access patterns you actually have: lowStock(threshold) can use an index on stock; a generic findAll().stream().filter(...) can't. Watch for N+1 queries when aggregates contain collections; use fetch joins or batch loading inside the adapter.

    Contract tests for adapters. Write one abstract test suite for the port and run it against the in-memory and the real adapter (Testcontainers PostgreSQL in CI). That is what keeps fakes honest.

    War story: the fake that hid a lost update

    A team's checkout tests used an in-memory InventoryRepository backed by a HashMap that returned stored objects directly. A refactor dropped a save() call; tests still passed because the mutated object was the stored one. In production with JPA in a read-only transaction, stock never decreased and the store oversold 400 units of mangoes during a sale. Fix: the fake now copies in and out, and the same contract suite runs against the JPA adapter with Testcontainers. Lesson: a fake repository must behave like a database, not like a shared object.

    12. Interview Corner¶

    Q1. What is the Repository pattern?

    A collection-like interface (save, findById) that hides how domain objects are stored.

    Q2. What does Spring's @Repository do?

    Marks a persistence bean and enables translation of vendor exceptions to Spring's DataAccessException hierarchy.

    Q3. CrudRepository vs JpaRepository?

    JpaRepository extends it with JPA-specific features: flush, batch deletes, findAll(Sort), paging via PagingAndSortingRepository.

    Q4. Repository vs DAO?

    DAO is table-oriented; Repository is aggregate- and domain-oriented. Repositories often use DAOs internally.

    Q5. How do you test a service that uses a repository?

    Pass an in-memory implementation or a mock into its constructor.

    Q1. Why one repository per aggregate root?

    So all changes go through the root, which enforces invariants (an order total can't diverge from its lines).

    Q2. What is optimistic locking and where does it live?

    A version column checked on update; a mismatch means someone else changed the row. In the repository/ORM (@Version).

    Q3. How do you avoid N+1 queries?

    Fetch joins / entity graphs, batch fetching, or purpose-built read models.

    Q4. Should repositories return Optional?

    Yes for single lookups (findById), so "not found" is explicit.

    Q5. Where should @Transactional go?

    On the application service/use case, not on each repository method.

    Q1. "Spring Data in the domain, or your own interface?"

    For CRUD services Spring Data directly is fine. For rich domains, define a domain port and implement it with Spring Data inside an adapter; the domain then doesn't depend on Spring or JPA.

    Q2. "How do you keep in-memory fakes honest?"

    A shared contract test suite run against every adapter, including the real database via Testcontainers.

    Q3. "A report query is slow and joins five aggregates."

    Don't bend the aggregate repositories. Add a read model (SQL view, materialized view or CQRS projection) with its own query repository.

    Q4. "How do repositories work with event sourcing?"

    load(id) replays the aggregate's events (plus snapshot); save appends new events with an expected-version check.

    Q5. "Multi-tenant data: where do you enforce tenant isolation?"

    In the repository adapter (or with PostgreSQL row-level security), never trusting callers to add WHERE tenant_id = ?.

    Problem: An in-memory CartRepository is used in tests. Show how it can make a test pass even when the code forgets to call save(), and fix it.

    Solution 
    package com.handbook.enterprise.repository.copies;

import java.util.ArrayList;
import java.util.HashMap;
import java.util.List;
import java.util.Map;

/** Coding challenge: an in-memory repository must not let callers change stored state without save(). */
public class LeakyRepositoryDemo {

    static final class Cart { // mutable on purpose, like a JPA entity
        final String id;
        final List<String> items = new ArrayList<>();
        Cart(String id) { this.id = id; }
        Cart copy() {
            Cart c = new Cart(id);
            c.items.addAll(items);
            return c;
        }
    }

    static final class LeakyCartRepository {
        private final Map<String, Cart> store = new HashMap<>();
        void save(Cart c) { store.put(c.id, c); }
        Cart find(String id) { return store.get(id); } // hands out the stored object itself
    }

    static final class SafeCartRepository {
        private final Map<String, Cart> store = new HashMap<>();
        void save(Cart c) { store.put(c.id, c.copy()); } // copy in
        Cart find(String id) { return store.get(id).copy(); } // copy out
    }

    public static void main(String[] args) {
        System.out.println("=== Challenge: An In-Memory Repository That Behaves Like a Database ===");
        LeakyCartRepository leaky = new LeakyCartRepository();
        leaky.save(new Cart("C1"));
        leaky.find("C1").items.add("Mango"); // forgot to call save()
        System.out.println("Leaky repo after unsaved change: " + leaky.find("C1").items + "  <- tests pass, prod loses it");

        SafeCartRepository safe = new SafeCartRepository();
        safe.save(new Cart("C1"));
        safe.find("C1").items.add("Mango");
        System.out.println("Safe repo after unsaved change : " + safe.find("C1").items);
        Cart c = safe.find("C1");
        c.items.add("Mango");
        safe.save(c);
        System.out.println("Safe repo after save()         : " + safe.find("C1").items);
    }
}

    Output:

    === Challenge: An In-Memory Repository That Behaves Like a Database ===
Leaky repo after unsaved change: [Mango]  <- tests pass, prod loses it
Safe repo after unsaved change : []
Safe repo after save()         : [Mango]

    Key points to say: a real database stores a copy; your fake must too (copy in on save, copy out on find), or use immutable aggregates. Then back it with a contract test against the real adapter.

    • T: Make repository fakes trustworthy and prevent the regression.
    • A: Rewrote fakes to copy in/out, created one contract test suite per port, and ran it against PostgreSQL in Testcontainers in CI.
