    Value Object¶

    🟢 Beginner → 🟡 Intermediate Enterprise / DDD Interview frequency ⭐⭐⭐⭐

    TL;DR

    A Value Object is a small immutable type defined only by its values (Quantity, PhoneNumber, StayPeriod), with no identity of its own. It validates itself and carries the rules that belong to that concept. Use one whenever a primitive (String, long, LocalDate pair) has rules, units or a format. In Java 21 this is usually a record.

    See It in Motion¶

    Press Play to watch the calls travel between objects, or step through with Next and Back. Switch to Without it to see what goes wrong without the pattern. Open the full explorer

    1. Intent & Problem It Solves¶

    The problem in plain English: long quantity doesn't say whether it means grams, kilograms or pieces. String phone accepts "098450-12345" and "+91 98450 12345" as two different customers. LocalDate from, LocalDate to lets someone create a stay that ends before it starts. Every service re-implements (slightly differently) the same checks. This is called primitive obsession.

    Definition (Eric Evans, Domain-Driven Design):

    An object that describes some characteristic or attribute but carries no concept of identity. Value objects are immutable, compared by value (two Quantity(2 kg) are interchangeable), and should be self-validating and side-effect free.

    Value Object vs Entity: an entity (Customer, Order) has an identity that persists while its attributes change. A value (Address, Money, Quantity) is replaced, not modified. Ask: "If every field is equal, are these the same thing?" If yes, it's a value.

    This page is the domain modelling view. For the thread-safety view of the same idea, see Immutable Object.

    2. Real-World Analogy¶

    Banknotes

    You don't care which ₹500 note you get back, only that it's ₹500: banknotes are compared by value. A forged ₹700 note can't exist (validation). And you never "edit" a note; you exchange it for different ones (immutability). Your bank account, on the other hand, is an entity: it's still your account when the balance changes.

    3. Structure¶

    classDiagram class Quantity { <<record, value object>> +long amount +Unit unit +plus(Quantity) Quantity +priceFor(long) long } class OrderLine { <<entity part>> +Sku sku +Quantity quantity } OrderLine --> Quantity : holds by value note for Quantity "Validated in the compact constructor;\nequals/hashCode by value; no setters"
    Property How in Java
    Immutable record (final fields), withers return new instances
    Equal by value Records generate equals/hashCode from components; normalise first so equal values compare equal
    Self-validating Compact constructor throws on invalid input; invalid values can't exist
    Behaviour-rich Methods like plus, overlaps, masked live on the value, not in services

    4. Naive Approach (Without the Pattern)¶

    void addToCart(String sku, long qty, String unit) { ... }            // "kg"? "KG"? "Kilogram"?
boolean bedFree(LocalDate from, LocalDate to, LocalDate from2, LocalDate to2) { ... }  // overlap logic copy-pasted
customerRepo.findByPhone(rawInput);                                 // "098450-12345" ≠ "+919845012345"
    • Validation scattered across controllers, services and SQL.
    • Easy to mix units, swap arguments and duplicate records.
    • The domain's vocabulary is invisible in the code.

    5. Three Real-World Examples¶

    Example 1: Quantity with Units (Grocery)¶

    Scenario: A grocery app sells loose vegetables by weight (g/kg) and eggs by count (pieces/dozen). Carts merge quantities from re-orders and substitutions. A past bug added "6 pieces" of eggs to "2 kg" of potatoes in a picking summary. Prices are per kg or per piece, in integer paise.

    Design:

    flowchart LR A["Quantity(500, GRAM)"] --> P["plus"] B["Quantity(1, KILOGRAM) → normalised to 1000 g"] --> P P --> C["Quantity(1500 g)"] D["Quantity(6, PIECE)"] -.->|different dimension| X["IllegalArgumentException"]

    Full Code:

    package com.handbook.enterprise.valueobject.grocery;

import java.util.Objects;

/** A quantity of something, with its unit. Equal by value; normalised to the smallest unit. */
public record Quantity(long amount, Unit unit) {

    public enum Unit {
        GRAM(Dimension.MASS, 1), KILOGRAM(Dimension.MASS, 1000), PIECE(Dimension.COUNT, 1), DOZEN(Dimension.COUNT, 12);

        final Dimension dimension;
        final long factor;

        Unit(Dimension dimension, long factor) {
            this.dimension = dimension;
            this.factor = factor;
        }
    }

    enum Dimension { MASS, COUNT }

    public Quantity { // (1)!
        Objects.requireNonNull(unit, "unit");
        if (amount < 0) {
            throw new IllegalArgumentException("quantity cannot be negative: " + amount);
        }
        long base = Math.multiplyExact(amount, unit.factor);
        amount = base;
        unit = unit.dimension == Dimension.MASS ? Unit.GRAM : Unit.PIECE;
    }

    public static Quantity of(long amount, Unit unit) {
        return new Quantity(amount, unit);
    }

    public Quantity plus(Quantity other) { // (2)!
        if (unit.dimension != other.unit.dimension) {
            throw new IllegalArgumentException("cannot add " + other + " to " + this);
        }
        return new Quantity(amount + other.amount, unit);
    }

    /** Price for this quantity, given a price per kg or per piece, in paise (rounded half-up). */
    public long priceFor(long paisePerKgOrPiece) {
        long divisor = unit == Unit.GRAM ? 1000 : 1;
        return (amount * paisePerKgOrPiece + divisor / 2) / divisor;
    }

    @Override
    public String toString() {
        if (unit == Unit.GRAM) {
            return amount % 1000 == 0 ? amount / 1000 + " kg" : amount + " g";
        }
        return amount + " pc";
    }
}
    1. The compact constructor validates and normalises (1 kg becomes 1000 g, 1 dozen becomes 12 pieces), so record equality works across units.
    2. Operations return new values and enforce the rule "only add like with like".
    package com.handbook.enterprise.valueobject.grocery;

import static com.handbook.enterprise.valueobject.grocery.Quantity.Unit.DOZEN;
import static com.handbook.enterprise.valueobject.grocery.Quantity.Unit.GRAM;
import static com.handbook.enterprise.valueobject.grocery.Quantity.Unit.KILOGRAM;
import static com.handbook.enterprise.valueobject.grocery.Quantity.Unit.PIECE;

public class QuantityDemo {

    public static void main(String[] args) {
        System.out.println("=== Grocery: Quantity as a Value Object ===");
        Quantity basket = Quantity.of(500, GRAM).plus(Quantity.of(1, KILOGRAM)).plus(Quantity.of(500, GRAM));
        System.out.println("500 g + 1 kg + 500 g = " + basket);
        System.out.println("1 kg equals 1000 g? " + Quantity.of(1, KILOGRAM).equals(Quantity.of(1000, GRAM)));
        System.out.println("1 dozen equals 12 pc? " + Quantity.of(1, DOZEN).equals(Quantity.of(12, PIECE)));
        System.out.println("Tomatoes 750 g at INR 40/kg = " + Quantity.of(750, GRAM).priceFor(4_000) + " paise");
        try {
            Quantity.of(2, KILOGRAM).plus(Quantity.of(6, PIECE));
        } catch (IllegalArgumentException e) {
            System.out.println("Rejected: " + e.getMessage());
        }
        try {
            Quantity.of(-1, PIECE);
        } catch (IllegalArgumentException e) {
            System.out.println("Rejected: " + e.getMessage());
        }
    }
}

    Output:

    === Grocery: Quantity as a Value Object ===
500 g + 1 kg + 500 g = 2 kg
1 kg equals 1000 g? true
1 dozen equals 12 pc? true
Tomatoes 750 g at INR 40/kg = 3000 paise
Rejected: cannot add 6 pc to 2 kg
Rejected: quantity cannot be negative: -1

    Why a value object here:

    • Units become part of the type, not a comment.
    • Pricing and addition rules live in one place.
    • Quantity.of(1, KILOGRAM).equals(Quantity.of(1000, GRAM)), so dedupe and comparisons just work.

    Example 2: StayPeriod for Bed Allocation (Healthcare)¶

    Scenario: A hospital's bed manager assigns 600 beds. A stay runs from the admission date until the discharge date; a new patient can be admitted to the same bed on the discharge day. Overlap checks were duplicated across four services, and two of them treated the discharge day as occupied, leaving beds empty for a night.

    Design:

    gantt dateFormat YYYY-MM-DD title Bed 7 section Stays Current stay [10, 14) :a, 2026-03-10, 4d Next patient [14, 16) :b, 2026-03-14, 2d

    Full Code:

    package com.handbook.enterprise.valueobject.healthcare;

import java.time.LocalDate;
import java.time.temporal.ChronoUnit;
import java.util.Objects;

/** A half-open date range [admitted, discharged). Rules about stays live here, not in services. */
public record StayPeriod(LocalDate admitted, LocalDate discharged) {

    public StayPeriod {
        Objects.requireNonNull(admitted);
        Objects.requireNonNull(discharged);
        if (!discharged.isAfter(admitted)) {
            throw new IllegalArgumentException("discharge " + discharged + " must be after admission " + admitted);
        }
    }

    public long nights() {
        return ChronoUnit.DAYS.between(admitted, discharged);
    }

    public boolean overlaps(StayPeriod other) { // (1)!
        return admitted.isBefore(other.discharged) && other.admitted.isBefore(discharged);
    }

    public StayPeriod extendTo(LocalDate newDischarge) { // (2)!
        return new StayPeriod(admitted, newDischarge);
    }
}
    1. One correct overlap rule for half-open ranges [start, end), used by everyone.
    2. "Changing" a stay produces a new value; anything holding the old one is unaffected.
    package com.handbook.enterprise.valueobject.healthcare;

import java.time.LocalDate;

public class StayPeriodDemo {

    public static void main(String[] args) {
        System.out.println("=== Healthcare: Bed Allocation with a StayPeriod Value Object ===");
        StayPeriod current = new StayPeriod(LocalDate.of(2026, 3, 10), LocalDate.of(2026, 3, 14));
        StayPeriod nextPatient = new StayPeriod(LocalDate.of(2026, 3, 14), LocalDate.of(2026, 3, 16));
        System.out.println("Bed 7 current stay: " + current.nights() + " nights");
        System.out.println("Next patient admitted on discharge day overlaps? " + current.overlaps(nextPatient));

        StayPeriod extended = current.extendTo(LocalDate.of(2026, 3, 15));
        System.out.println("Doctor extends stay -> " + extended.nights() + " nights; now overlaps? " + extended.overlaps(nextPatient));
        System.out.println("Original value unchanged: " + current.nights() + " nights");
        try {
            new StayPeriod(LocalDate.of(2026, 3, 12), LocalDate.of(2026, 3, 12));
        } catch (IllegalArgumentException e) {
            System.out.println("Rejected: " + e.getMessage());
        }
    }
}

    Output:

    === Healthcare: Bed Allocation with a StayPeriod Value Object ===
Bed 7 current stay: 4 nights
Next patient admitted on discharge day overlaps? false
Doctor extends stay -> 5 nights; now overlaps? true
Original value unchanged: 4 nights
Rejected: discharge 2026-03-12 must be after admission 2026-03-12

    Why a value object here:

    • Date-range logic is notoriously easy to get wrong; centralise it once.
    • An invalid stay (discharge on or before admission) can't be constructed.
    • Services ask the domain question (overlaps, nights) instead of comparing dates.

    Example 3: PhoneNumber Normalisation (Telecom)¶

    Scenario: A telecom's sign-up funnel collects numbers from web, app, retail stores and partner kiosks: "+91 98450 12345", "098450-12345", "9845012345". Stored as raw strings, one person became three subscribers with three SIM KYC records. Logs must never print a full number.

    Design:

    flowchart LR R1["+91 98450 12345"] --> P["PhoneNumber.parse"] R2["098450-12345"] --> P R3["9845012345"] --> P P --> E["PhoneNumber(+919845012345)"] E --> M["masked() → +9198*****345"]

    Full Code:

    package com.handbook.enterprise.valueobject.telecom;

/** An Indian mobile number in canonical E.164 form. Parsing normalises every accepted spelling. */
public record PhoneNumber(String e164) {

    public PhoneNumber {
        if (!e164.matches("\\+91[6-9]\\d{9}")) {
            throw new IllegalArgumentException("not a canonical Indian mobile number: " + e164);
        }
    }

    public static PhoneNumber parse(String raw) { // (1)!
        String digits = raw.replaceAll("[^0-9]", "");
        if (digits.length() == 12 && digits.startsWith("91")) {
            digits = digits.substring(2);
        } else if (digits.length() == 11 && digits.startsWith("0")) {
            digits = digits.substring(1);
        }
        if (digits.length() != 10) {
            throw new IllegalArgumentException("cannot parse '" + raw + "'");
        }
        return new PhoneNumber("+91" + digits);
    }

    public String masked() {
        return e164.substring(0, 5) + "*****" + e164.substring(10);
    }
}
    1. A factory that accepts the messy real-world formats and produces one canonical value. The constructor only accepts canonical form, so every PhoneNumber is valid.
    package com.handbook.enterprise.valueobject.telecom;

import java.util.LinkedHashSet;
import java.util.List;
import java.util.Set;

public class PhoneNumberDemo {

    public static void main(String[] args) {
        System.out.println("=== Telecom: De-duplicating Subscribers by PhoneNumber ===");
        List<String> signups = List.of("+91 98450 12345", "098450-12345", "9845012345", "91-9845012345", "+91 70221 99887");
        Set<PhoneNumber> unique = new LinkedHashSet<>();
        for (String raw : signups) {
            unique.add(PhoneNumber.parse(raw));
        }
        System.out.println(signups.size() + " raw sign-ups -> " + unique.size() + " subscribers: " + unique.stream().map(PhoneNumber::e164).toList());
        System.out.println("Masked for SMS logs: " + unique.stream().map(PhoneNumber::masked).toList());
        for (String bad : List.of("12345", "+91 12345 67890")) {
            try {
                PhoneNumber.parse(bad);
            } catch (IllegalArgumentException e) {
                System.out.println("Rejected: " + e.getMessage());
            }
        }
    }
}

    Output:

    === Telecom: De-duplicating Subscribers by PhoneNumber ===
5 raw sign-ups -> 2 subscribers: [+919845012345, +917022199887]
Masked for SMS logs: [+9198*****345, +9170*****887]
Rejected: cannot parse '12345'
Rejected: not a canonical Indian mobile number: +911234567890

    Why a value object here:

    • Canonical form makes equality, sets and database uniqueness constraints correct.
    • Privacy rules (masked) travel with the value.
    • Parsing happens once at the edge; the rest of the system trusts the type.
    Unit Tests: ValueObjectTest.java 
    package com.handbook.enterprise.valueobject;

import com.handbook.enterprise.valueobject.grocery.Quantity;
import com.handbook.enterprise.valueobject.healthcare.StayPeriod;
import com.handbook.enterprise.valueobject.telecom.PhoneNumber;
import org.junit.jupiter.api.Test;
import org.junit.jupiter.params.ParameterizedTest;
import org.junit.jupiter.params.provider.ValueSource;

import java.time.LocalDate;

import static com.handbook.enterprise.valueobject.grocery.Quantity.Unit.GRAM;
import static com.handbook.enterprise.valueobject.grocery.Quantity.Unit.KILOGRAM;
import static com.handbook.enterprise.valueobject.grocery.Quantity.Unit.PIECE;
import static org.assertj.core.api.Assertions.assertThat;
import static org.assertj.core.api.Assertions.assertThatThrownBy;

class ValueObjectTest {

    @Test
    void quantitiesAreEqualByValueAcrossUnits() {
        assertThat(Quantity.of(2, KILOGRAM)).isEqualTo(Quantity.of(2000, GRAM)).hasSameHashCodeAs(Quantity.of(2000, GRAM));
        assertThatThrownBy(() -> Quantity.of(1, KILOGRAM).plus(Quantity.of(1, PIECE))).isInstanceOf(IllegalArgumentException.class);
        assertThat(Quantity.of(250, GRAM).priceFor(6_000)).isEqualTo(1_500);
    }

    @Test
    void halfOpenStaysDoNotOverlapOnTheSameDay() {
        StayPeriod a = new StayPeriod(LocalDate.of(2026, 1, 1), LocalDate.of(2026, 1, 3));
        assertThat(a.overlaps(new StayPeriod(LocalDate.of(2026, 1, 3), LocalDate.of(2026, 1, 4)))).isFalse();
        assertThat(a.overlaps(new StayPeriod(LocalDate.of(2026, 1, 2), LocalDate.of(2026, 1, 4)))).isTrue();
    }

    @ParameterizedTest
    @ValueSource(strings = {"+91 98450 12345", "098450-12345", "9845012345", "919845012345"})
    void everySpellingNormalisesToTheSameNumber(String raw) {
        assertThat(PhoneNumber.parse(raw)).isEqualTo(new PhoneNumber("+919845012345"));
    }
}

    6. Variations & Modern Java Take¶

    Variation Notes
    Records (Java 16+) The natural fit: final fields, value equality, compact constructors
    Typed IDs record OrderId(UUID value) instead of UUID everywhere (coding challenge)
    Enums Values with a closed set (Unit, Currency)
    Sealed interfaces of records Values with variants: sealed interface Discount permits Percent, Flat
    JPA mapping @Embeddable classes (records supported as embeddables since Hibernate 6.2), or AttributeConverter<PhoneNumber, String>
    Jackson Records (de)serialise via their canonical constructor; @JsonValue/@JsonCreator for single-field values
    Project Valhalla (future) value class will give values without identity at the JVM level (no headers, flattening)

    Where Value objects
    JDK LocalDate, Instant, Duration, BigDecimal, UUID, Currency, URI, Optional

    JPA @Embeddable / @Embedded, AttributeConverter

    8. Pros, Cons & Trade-offs¶

    ✅ Pros ❌ Cons
    Invalid states can't be represented More types and small files
    Rules live in one place, close to the data Mapping to DB columns/JSON needs converters
    Thread-safe and shareable (immutable) Over-wrapping trivial strings adds ceremony
    Code reads like the domain language Allocation per operation (negligible in practice)

    9. Pitfalls & Anti-Patterns¶

    Equality without normalisation

    record Quantity(long amount, Unit unit) without normalising makes 1 kg ≠ 1000 g. Normalise in the compact constructor, or write equals yourself.

    Mutable value objects

    A value with setters shared by two orders means changing one order's address changes the other's. Values must be immutable.

    Records holding mutable components

    record Basket(List<Item> items) is only shallowly immutable. List.copyOf in the constructor.

    Validation in the controller only

    If new PhoneNumber(...) accepts anything, every other code path (batch imports, Kafka consumers) can create invalid values. Validate in the constructor.

    10. Senior / Architect Deep Dive (10–15 yrs)¶

    Parse, don't validate. Convert raw input to value objects at the system edge (controllers, message consumers). After that, code receives PhoneNumber, not String, so the type itself is proof of validation. This removes defensive checks from deep inside services.

    Persistence. Map values as embedded columns (quantity_amount, quantity_unit) or converters to one column. Keep the canonical form in the database too, with a unique index (UNIQUE (phone_e164)), so duplicates are impossible at both layers.

    APIs and events. Value objects make great contract types: {"amount": 1500, "unit": "GRAM"} is unambiguous. Version them carefully: changing a value's canonical form (e.g., kg → g) is a breaking change for consumers.

    War story: three subscribers, one person

    A telecom stored raw phone strings from five channels. The fraud team found customers with up to four active SIM KYC profiles because "098450-12345" and "+91 98450 12345" never matched. Regulators asked for a cleanup within 30 days. Fix: a PhoneNumber value object with canonical E.164 form, used by every channel; a migration normalised 18 million rows and merged 410,000 duplicates; a unique index prevents recurrence. Lesson: if a value has a canonical form, make it a type.

    Value Object Entity Immutable Object DTO
    Identity None (equal by value) Yes (id) N/A None

    Purpose Model a concept precisely Track something over time Thread safety Move data across boundaries

    12. Interview Corner¶

    Q1. What is a value object?

    An immutable object defined by its values, with no identity, like Money or Address.

    Q2. Value object vs entity?

    An entity has an identity that stays the same while attributes change (Customer #42). A value object is equal to any other with the same values.

    Q3. Why are records good for value objects?

    Final fields, generated value-based equals/hashCode/toString, and compact constructors for validation.

    Q4. Give JDK examples.

    String, LocalDate, BigDecimal, UUID, Duration.

    Q5. What is primitive obsession?

    Using primitives (String, int) for domain concepts that have rules, which scatters validation and allows mix-ups.

    Q1. How do you persist a value object with JPA?

    @Embeddable (embedded columns) or an AttributeConverter to a single column.

    Q2. Why normalise in the constructor?

    So that semantically equal values are also equals()-equal and hash the same.

    Q3. How do typed IDs help?

    The compiler stops you passing a CustomerId where an OrderId is expected, or swapping arguments.

    Q4. Where should parsing happen?

    At the edges (HTTP, messaging, files): "parse, don't validate".

    Q5. Can a value object reference an entity?

    It can hold an entity's id, but shouldn't hold the mutable entity itself.

    Q1. "Model money for a multi-currency marketplace."

    Money(long minorUnits, Currency); operations only within one currency; explicit ExchangeRate value for conversions; allocation that preserves totals; persisted as two columns.

    Q2. "How do you evolve a value object used in events?"

    Treat its JSON shape as a contract: add optional fields, never change meaning in place; introduce a new event version for breaking changes.

    Q3. "When is a value object overkill?"

    When the primitive has no rules and no ambiguity (a free-text note). Introduce types where bugs or duplication actually appear.

    Q4. "Values vs entities in an Order aggregate?"

    Order (entity, root), OrderLine (entity inside, identified within the order), Quantity, Money, Address, Sku (values).

    Q5. "What will Valhalla change?"

    Value classes without identity let the JVM flatten them in arrays and fields, removing the allocation/indirection cost of small values.

    Problem: transfer(String from, String to, long paise) was called with swapped arguments in production. Redesign it so this can't compile, and so negative amounts can't exist.

    Solution 
    package com.handbook.enterprise.valueobject.ids;

import java.util.TreeMap;
import java.util.Map;

/** Coding challenge: cure primitive obsession in transfer(String, String, long). */
public class TypedIdsDemo {

    static final Map<String, Long> BALANCES = new TreeMap<>();

    // Before: three primitives; nothing stops callers from swapping them.
    static void transferRaw(String fromAccount, String toAccount, long paise) {
        BALANCES.merge(fromAccount, -paise, Long::sum);
        BALANCES.merge(toAccount, paise, Long::sum);
    }

    // After: each concept is its own type with its own rules.
    record AccountId(String value) {
        AccountId {
            if (!value.matches("ACC-\\d{4}")) {
                throw new IllegalArgumentException("bad account id " + value);
            }
        }
    }

    record Paise(long value) {
        Paise {
            if (value <= 0) {
                throw new IllegalArgumentException("transfer amount must be positive: " + value);
            }
        }
    }

    static void transfer(AccountId from, AccountId to, Paise amount) {
        transferRaw(from.value(), to.value(), amount.value());
    }

    public static void main(String[] args) {
        System.out.println("=== Challenge: Typed IDs Instead of Strings ===");
        BALANCES.put("ACC-1001", 50_000L);
        BALANCES.put("ACC-2002", 0L);
        String customer = "ACC-1001";
        String merchant = "ACC-2002";
        transferRaw(merchant, customer, 10_000); // swapped by mistake: compiles fine
        System.out.println("Raw strings, swapped args : " + BALANCES);

        BALANCES.put("ACC-1001", 50_000L);
        BALANCES.put("ACC-2002", 0L);
        transfer(new AccountId("ACC-1001"), new AccountId("ACC-2002"), new Paise(10_000));
        System.out.println("Typed values, correct call: " + BALANCES);
        try {
            transfer(new AccountId("ACC-1001"), new AccountId("ACC-2002"), new Paise(-500));
        } catch (IllegalArgumentException e) {
            System.out.println("Rejected: " + e.getMessage());
        }
        System.out.println("transfer(paise, from, to) would not compile: the types make the order part of the API.");
    }
}

    Output:

    === Challenge: Typed IDs Instead of Strings ===
Raw strings, swapped args : {ACC-1001=60000, ACC-2002=-10000}
Typed values, correct call: {ACC-1001=40000, ACC-2002=10000}
Rejected: transfer amount must be positive: -500
transfer(paise, from, to) would not compile: the types make the order part of the API.

    Key points to say: distinct types (AccountId, Paise) move mistakes from runtime to compile time; validation lives in the constructor; the method signature documents itself. Two AccountId parameters can still be swapped, so name them clearly or use a Transfer(from, to, amount) value.

    13. Quick Revision Card¶

    Remember in 30 seconds

    • No identity; equal by value; immutable; self-validating.
    • Use a record with a compact constructor that validates and normalises.
    • Put the rules (plus, overlaps, masked) on the value.
    • Parse at the edge; pass types, not strings, inside.
    • Entity = identity over time; value = replace, don't modify.
