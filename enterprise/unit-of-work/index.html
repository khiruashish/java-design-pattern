    Unit of Work & Identity Map¶

    🟡 Intermediate → 🔴 Advanced Enterprise Interview frequency ⭐⭐⭐⭐

    TL;DR

    A Unit of Work tracks every object a business transaction creates, changes or deletes, and writes them all in one database transaction at the end. An Identity Map makes sure each record is loaded into exactly one object per unit of work. You use both every day: JPA's EntityManager / Hibernate's Session is a unit of work with an identity map (the persistence context).

    See It in Motion¶

    Press Play to watch the calls travel between objects, or step through with Next and Back. Switch to Without it to see what goes wrong without the pattern. Open the full explorer

    1. Intent & Problem It Solves¶

    The problem in plain English: placing a grocery order inserts an order row, inserts several line rows and decrements stock for each product. If every repository call commits on its own and the third write fails, you're left with an order that has no lines, or stock taken for an order that doesn't exist. Separately, if two parts of the same request load the same booking, they get two different objects; one changes the seat, the other still has the old one and may save it back.

    Definitions (Martin Fowler, PoEAA):

    Unit of Work: maintains a list of objects affected by a business transaction and coordinates the writing out of changes and the resolution of concurrency problems.

    Identity Map: ensures that each object gets loaded only once by keeping every loaded object in a map. Looks up objects using the map when referring to them.

    2. Real-World Analogy¶

    A supermarket trolley and the checkout counter

    You walk the aisles adding and removing items (registering changes), but nothing is paid for until the checkout (commit). If your card is declined, the whole trolley is rejected, not half of it. And there's only one trolley per shopper: you don't push two trolleys holding different versions of your shopping (identity map).

    3. Structure¶

    classDiagram class UseCase { +place(order) } class UnitOfWork { -List pending +registerNew(obj) +registerDirty(obj) +registerRemoved(obj) +commit() } class IdentityMap~K,V~ { -Map loaded +get(K) V } class Mapper~T~ { <<interface>> +insert() +update() +delete() } UseCase --> UnitOfWork UnitOfWork --> Mapper UnitOfWork --> IdentityMap
    Participant Responsibility
    Unit of Work Tracks new / dirty / removed objects; opens one transaction on commit; rolls back on failure
    Identity Map One in-memory object per database identity within the unit of work
    Mapper Knows how to write one kind of object (SQL); the unit of work orders and calls them
    Use case / application service Starts a unit of work, runs business logic, commits

    4. Naive Approach (Without the Pattern)¶

    orderRepo.insert(order);            // auto-commit #1
for (Line l : lines) {
    lineRepo.insert(l);             // auto-commit #2, #3
    stockRepo.decrement(l.sku(), l.qty());   // auto-commit #4 ... throws: stock would go negative
}
// The order and some lines are already committed. Manual cleanup code? Hope?
    • No atomicity: partial writes survive failures.
    • Many round trips and commits instead of one.
    • Duplicate objects for the same row → lost updates inside one request.

    5. Three Real-World Examples¶

    Example 1: Order + Lines + Stock, All or Nothing (Grocery)¶

    Scenario: During a mango-season flash sale, a dark store receives 200 orders a minute for a product with limited stock. Placing an order writes the order, its lines and the stock decrements. The database has CHECK (on_hand >= 0). If any write fails, none of them may persist: no orphan orders, no stock taken for a failed order.

    Design:

    sequenceDiagram autonumber participant U as OrderPlacement participant W as UnitOfWork participant DB U->>W: registerNew(order), registerNew(line x2), registerDirty(stock x2) U->>W: commit() W->>DB: BEGIN, INSERT order, INSERT lines, UPDATE stock ... alt all succeed W->>DB: COMMIT else CHECK constraint fails W->>DB: ROLLBACK (nothing persists) end

    Full Code:

    package com.handbook.enterprise.unitofwork.grocery;

import javax.sql.DataSource;
import java.sql.Connection;
import java.sql.SQLException;
import java.util.ArrayList;
import java.util.List;

/** Collects new/changed/removed objects during a use case and writes them in ONE transaction. */
public final class UnitOfWork {

    /** How to write one kind of object. The unit of work doesn't know SQL itself. */
    public interface Mapper<T> {
        void insert(Connection c, T obj) throws SQLException;
        void update(Connection c, T obj) throws SQLException;
    }

    private record Pending<T>(String kind, T obj, Mapper<T> mapper) {
        void apply(Connection c) throws SQLException {
            if (kind.equals("INSERT")) {
                mapper.insert(c, obj);
            } else {
                mapper.update(c, obj);
            }
        }
    }

    private final DataSource ds;
    private final List<Pending<?>> pending = new ArrayList<>();

    public UnitOfWork(DataSource ds) {
        this.ds = ds;
    }

    public <T> void registerNew(T obj, Mapper<T> mapper) { pending.add(new Pending<>("INSERT", obj, mapper)); } // (1)!

    public <T> void registerDirty(T obj, Mapper<T> mapper) { pending.add(new Pending<>("UPDATE", obj, mapper)); }

    public int commit() {
        try (Connection c = ds.getConnection()) {
            c.setAutoCommit(false); // (2)!
            try {
                for (Pending<?> p : pending) {
                    p.apply(c);
                }
                c.commit();
                return pending.size();
            } catch (SQLException e) {
                c.rollback(); // (3)!
                throw new IllegalStateException("Rolled back " + pending.size() + " changes (SQLState " + e.getSQLState() + ")", e);
            } finally {
                pending.clear();
            }
        } catch (SQLException e) {
            throw new IllegalStateException(e);
        }
    }
}
    1. Business code registers changes; nothing is written yet. Hibernate does the same when you persist() or modify a managed entity.
    2. One connection, one transaction, for every pending change.
    3. Any failure rolls back everything, so the database never sees a half-placed order.
    package com.handbook.enterprise.unitofwork.grocery;

import java.sql.Connection;
import java.sql.PreparedStatement;
import java.sql.SQLException;
import java.util.List;

/** Use case: create an order, its lines and the stock decrements, all-or-nothing. */
public final class OrderPlacement {

    public record Order(String id, String customer) { }

    public record Line(String orderId, String sku, int qty) { }

    public record Stock(String sku, int onHand) { }

    static final UnitOfWork.Mapper<Order> ORDERS = new UnitOfWork.Mapper<>() {
        public void insert(Connection c, Order o) throws SQLException {
            exec(c, "INSERT INTO orders (id, customer) VALUES (?, ?)", o.id(), o.customer());
        }
        public void update(Connection c, Order o) { throw new UnsupportedOperationException(); }
    };

    static final UnitOfWork.Mapper<Line> LINES = new UnitOfWork.Mapper<>() {
        public void insert(Connection c, Line l) throws SQLException {
            exec(c, "INSERT INTO order_line (order_id, sku, qty) VALUES (?, ?, ?)", l.orderId(), l.sku(), l.qty());
        }
        public void update(Connection c, Line l) { throw new UnsupportedOperationException(); }
    };

    static final UnitOfWork.Mapper<Stock> STOCK = new UnitOfWork.Mapper<>() {
        public void insert(Connection c, Stock s) { throw new UnsupportedOperationException(); }
        public void update(Connection c, Stock s) throws SQLException {
            exec(c, "UPDATE stock SET on_hand = ? WHERE sku = ?", s.onHand(), s.sku());
        }
    };

    private final UnitOfWork uow;

    public OrderPlacement(UnitOfWork uow) {
        this.uow = uow;
    }

    /** Business logic only registers changes; nothing touches the database until commit. */
    public int place(Order order, List<Line> lines, List<Stock> currentStock) {
        uow.registerNew(order, ORDERS);
        for (Line line : lines) {
            uow.registerNew(line, LINES);
            Stock s = currentStock.stream().filter(x -> x.sku().equals(line.sku())).findFirst().orElseThrow();
            uow.registerDirty(new Stock(s.sku(), s.onHand() - line.qty()), STOCK);
        }
        return uow.commit();
    }

    private static void exec(Connection c, String sql, Object... args) throws SQLException {
        try (PreparedStatement ps = c.prepareStatement(sql)) {
            for (int i = 0; i < args.length; i++) {
                ps.setObject(i + 1, args[i]);
            }
            ps.executeUpdate();
        }
    }
}

    package com.handbook.enterprise.unitofwork.grocery;

import com.handbook.enterprise.unitofwork.grocery.OrderPlacement.Line;
import com.handbook.enterprise.unitofwork.grocery.OrderPlacement.Order;
import com.handbook.enterprise.unitofwork.grocery.OrderPlacement.Stock;
import org.h2.jdbcx.JdbcDataSource;

import java.sql.Connection;
import java.sql.ResultSet;
import java.sql.SQLException;
import java.util.List;

public class GroceryUowDemo {

    public static void main(String[] args) throws SQLException {
        System.out.println("=== Grocery: Order + Lines + Stock in One Unit of Work ===");
        JdbcDataSource ds = new JdbcDataSource();
        ds.setURL("jdbc:h2:mem:uow_grocery;DB_CLOSE_DELAY=-1");
        try (Connection c = ds.getConnection()) {
            c.createStatement().execute("CREATE TABLE orders (id VARCHAR PRIMARY KEY, customer VARCHAR)");
            c.createStatement().execute("CREATE TABLE order_line (order_id VARCHAR, sku VARCHAR, qty INT)");
            c.createStatement().execute("CREATE TABLE stock (sku VARCHAR PRIMARY KEY, on_hand INT CHECK (on_hand >= 0))");
            c.createStatement().execute("INSERT INTO stock VALUES ('MANGO-1KG', 3), ('CURD-400G', 10)");
        }

        int written = new OrderPlacement(new UnitOfWork(ds)).place(new Order("O-1", "riya"),
                List.of(new Line("O-1", "MANGO-1KG", 2), new Line("O-1", "CURD-400G", 1)),
                List.of(new Stock("MANGO-1KG", 3), new Stock("CURD-400G", 10)));
        System.out.println("O-1 committed " + written + " changes -> " + snapshot(ds));

        try {
            new OrderPlacement(new UnitOfWork(ds)).place(new Order("O-2", "arjun"),
                    List.of(new Line("O-2", "CURD-400G", 2), new Line("O-2", "MANGO-1KG", 5)), // only 1 mango left
                    List.of(new Stock("MANGO-1KG", 1), new Stock("CURD-400G", 9)));
        } catch (IllegalStateException e) {
            System.out.println("O-2 failed: " + e.getMessage() + ": stock would go negative");
        }
        System.out.println("After O-2 -> " + snapshot(ds) + " (no orphan order, curd untouched)");
    }

    private static String snapshot(JdbcDataSource ds) throws SQLException {
        try (Connection c = ds.getConnection()) {
            ResultSet o = c.createStatement().executeQuery("SELECT COUNT(*) FROM orders");
            o.next();
            ResultSet l = c.createStatement().executeQuery("SELECT COUNT(*) FROM order_line");
            l.next();
            ResultSet s = c.createStatement().executeQuery("SELECT LISTAGG(sku || '=' || on_hand, ', ') WITHIN GROUP (ORDER BY sku) FROM stock");
            s.next();
            return "orders=" + o.getInt(1) + ", lines=" + l.getInt(1) + ", stock[" + s.getString(1) + "]";
        }
    }
}

    Output:

    === Grocery: Order + Lines + Stock in One Unit of Work ===
O-1 committed 5 changes -> orders=1, lines=2, stock[CURD-400G=9, MANGO-1KG=1]
O-2 failed: Rolled back 5 changes (SQLState 23513): stock would go negative
After O-2 -> orders=1, lines=2, stock[CURD-400G=9, MANGO-1KG=1] (no orphan order, curd untouched)

    Why a unit of work here:

    • One business action = one atomic database transaction.
    • The use case contains no commit/rollback plumbing.
    • Writes are batched at the end, so there are fewer round trips and locks are held for less time.

    Example 2: Identity Map in a Check-in Session (Travel)¶

    Scenario: An airline's web check-in page renders several widgets in one request: seat map, baggage, meal choice. Each widget loads the booking. Without an identity map there are three database reads and three separate Booking objects. When the seat widget upgrades the passenger to 3A, the baggage widget still holds 14C and prints the wrong boarding-pass zone.

    Design:

    flowchart LR S[Seat widget] --> M[(Identity map<br/>PNR-42 → Booking@1)] B[Baggage widget] --> M M -->|first lookup only| DB[(bookings)]

    Full Code:

    package com.handbook.enterprise.unitofwork.travel;

import java.util.HashMap;
import java.util.Map;
import java.util.function.Function;

/** Ensures each record is loaded once per session: one id -> one in-memory object. */
public final class IdentityMap<K, V> {

    private final Map<K, V> loaded = new HashMap<>();
    private final Function<K, V> loader;

    public IdentityMap(Function<K, V> loader) {
        this.loader = loader;
    }

    public V get(K id) {
        return loaded.computeIfAbsent(id, loader); // (1)!
    }

    public int size() {
        return loaded.size();
    }
}
    1. Load on first access, then always return the same instance. This is why em.find(Booking.class, id) == em.find(Booking.class, id) is true inside one JPA transaction.
    package com.handbook.enterprise.unitofwork.travel;

import java.util.HashMap;
import java.util.Map;

public class TravelIdentityMapDemo {

    /** A mutable booking, like a JPA entity. */
    static final class Booking {
        final String pnr;
        String seat;
        Booking(String pnr, String seat) { this.pnr = pnr; this.seat = seat; }
    }

    static final Map<String, String> SEATS_TABLE = new HashMap<>(Map.of("PNR-42", "14C"));
    static int dbReads = 0;

    static Booking loadFromDb(String pnr) {
        dbReads++;
        return new Booking(pnr, SEATS_TABLE.get(pnr));
    }

    public static void main(String[] args) {
        System.out.println("=== Travel: Identity Map in a Check-in Session ===");

        dbReads = 0;
        Booking forSeatMap = loadFromDb("PNR-42");    // seat-map widget
        Booking forBaggage = loadFromDb("PNR-42");    // baggage widget, same request
        forSeatMap.seat = "3A";                         // passenger upgrades
        System.out.println("Without map: reads=" + dbReads + ", same object=" + (forSeatMap == forBaggage)
                + ", baggage widget still sees seat " + forBaggage.seat + " (stale copy)");

        dbReads = 0;
        IdentityMap<String, Booking> session = new IdentityMap<>(TravelIdentityMapDemo::loadFromDb);
        Booking a = session.get("PNR-42");
        Booking b = session.get("PNR-42");
        a.seat = "3A";
        System.out.println("With map   : reads=" + dbReads + ", same object=" + (a == b) + ", baggage widget sees seat " + b.seat);
    }
}

    Output:

    === Travel: Identity Map in a Check-in Session ===
Without map: reads=2, same object=false, baggage widget still sees seat 14C (stale copy)
With map   : reads=1, same object=true, baggage widget sees seat 3A

    Why an identity map here:

    • Consistency inside a request: everyone sees the same booking state.
    • Fewer reads: the second lookup is free (a first-level cache).
    • Needed by the unit of work to know which object to write for a given row.

    Example 3: Dirty Checking for an Appraisal Batch (SaaS / ERP)¶

    Scenario: An HR system's appraisal job loads 5,000 employee records, but only about 10% get a raise or transfer. Writing back all 5,000 rows would bloat the audit log and contend with other jobs. The unit of work snapshots each object when loaded and, at flush, issues an UPDATE only for objects whose fields actually changed, and only for those columns.

    Design:

    flowchart LR L["find(E1..E5)"] --> Snap["snapshot of each on load"] Code["appraisal logic mutates E2, E4"] --> F["flush(): compare current vs snapshot"] F --> U2["UPDATE E2 salary"] F --> U4["UPDATE E4 department"] F -.->|unchanged| X["E1, E3, E5: no SQL"]

    Full Code:

    package com.handbook.enterprise.unitofwork.erp;

import java.util.ArrayList;
import java.util.LinkedHashMap;
import java.util.List;
import java.util.Map;

/** Hibernate-style dirty checking: snapshot on load, compare on flush, UPDATE only what changed. */
public final class DirtyCheckingSession {

    public static final class Employee { // mutable "managed entity"
        public final String id;
        public String department;
        public long salaryPaise;

        public Employee(String id, String department, long salaryPaise) {
            this.id = id;
            this.department = department;
            this.salaryPaise = salaryPaise;
        }
    }

    private record Snapshot(String department, long salaryPaise) {
        static Snapshot of(Employee e) { return new Snapshot(e.department, e.salaryPaise); }
    }

    private final Map<String, Employee> table;
    private final Map<String, Employee> managed = new LinkedHashMap<>(); // identity map
    private final Map<String, Snapshot> snapshots = new LinkedHashMap<>();

    public DirtyCheckingSession(Map<String, Employee> table) {
        this.table = table;
    }

    public Employee find(String id) {
        return managed.computeIfAbsent(id, k -> {
            Employee row = table.get(k);
            Employee copy = new Employee(row.id, row.department, row.salaryPaise);
            snapshots.put(k, Snapshot.of(copy)); // (1)!
            return copy;
        });
    }

    /** Returns the SQL it would issue. */
    public List<String> flush() {
        List<String> sql = new ArrayList<>();
        for (Employee e : managed.values()) {
            Snapshot before = snapshots.get(e.id);
            List<String> sets = new ArrayList<>();
            if (!before.department().equals(e.department)) {
                sets.add("department='" + e.department + "'");
            }
            if (before.salaryPaise() != e.salaryPaise) {
                sets.add("salary_paise=" + e.salaryPaise);
            }
            if (!sets.isEmpty()) { // (2)!
                sql.add("UPDATE employee SET " + String.join(", ", sets) + " WHERE id='" + e.id + "'");
                table.put(e.id, new Employee(e.id, e.department, e.salaryPaise));
                snapshots.put(e.id, Snapshot.of(e));
            }
        }
        return sql;
    }
}
    1. The snapshot taken at load time, exactly what Hibernate keeps in its persistence context ("loaded state").
    2. Only changed objects produce SQL. Setting a field to its existing value is not a change.
    package com.handbook.enterprise.unitofwork.erp;

import com.handbook.enterprise.unitofwork.erp.DirtyCheckingSession.Employee;

import java.util.HashMap;
import java.util.Map;

public class ErpDirtyCheckingDemo {

    public static void main(String[] args) {
        System.out.println("=== ERP: Annual Appraisal with Dirty Checking ===");
        Map<String, Employee> table = new HashMap<>();
        for (int i = 1; i <= 5; i++) {
            table.put("E" + i, new Employee("E" + i, "Finance", 1_200_000_00L));
        }
        DirtyCheckingSession session = new DirtyCheckingSession(table);
        for (int i = 1; i <= 5; i++) {
            Employee e = session.find("E" + i);
            if (i == 2) {
                e.salaryPaise = 1_320_000_00L;            // 10% raise
            }
            if (i == 4) {
                e.department = "Treasury";                 // transfer
                e.salaryPaise = e.salaryPaise;             // "set" to same value: not a change
            }
        }
        System.out.println("Loaded 5 employees, flush issues:");
        session.flush().forEach(s -> System.out.println("  " + s));
        System.out.println("Second flush with no changes issues " + session.flush().size() + " statements");
    }
}

    Output:

    === ERP: Annual Appraisal with Dirty Checking ===
Loaded 5 employees, flush issues:
  UPDATE employee SET salary_paise=132000000 WHERE id='E2'
  UPDATE employee SET department='Treasury' WHERE id='E4'
Second flush with no changes issues 0 statements

    Why dirty checking here:

    • Business code just changes objects; it never calls update().
    • Minimal writes: fewer locks, smaller audit trail, less replication traffic.
    • Explains JPA behaviour that surprises people: modifying a managed entity is a save.

import com.handbook.enterprise.unitofwork.erp.DirtyCheckingSession.Employee;

import com.handbook.enterprise.unitofwork.grocery.UnitOfWork;
import com.handbook.enterprise.unitofwork.travel.IdentityMap;
import org.h2.jdbcx.JdbcDataSource;
import org.junit.jupiter.api.Test;

import java.sql.Connection;
import java.sql.ResultSet;
import java.util.HashMap;
import java.util.List;

import java.util.concurrent.atomic.AtomicInteger;

import static org.assertj.core.api.Assertions.assertThat;
import static org.assertj.core.api.Assertions.assertThatThrownBy;

class UnitOfWorkTest {

    @Test
    void failedCommitLeavesNothingBehind() throws Exception {
        JdbcDataSource ds = new JdbcDataSource();
        ds.setURL("jdbc:h2:mem:" + UUID.randomUUID() + ";DB_CLOSE_DELAY=-1");
        try (Connection c = ds.getConnection()) {
            c.createStatement().execute("CREATE TABLE orders (id VARCHAR PRIMARY KEY, customer VARCHAR)");
            c.createStatement().execute("CREATE TABLE order_line (order_id VARCHAR, sku VARCHAR, qty INT)");
            c.createStatement().execute("CREATE TABLE stock (sku VARCHAR PRIMARY KEY, on_hand INT CHECK (on_hand >= 0))");
            c.createStatement().execute("INSERT INTO stock VALUES ('A', 1)");
        }
        assertThatThrownBy(() -> new OrderPlacement(new UnitOfWork(ds))
                .place(new Order("O", "c"), List.of(new Line("O", "A", 2)), List.of(new Stock("A", 1))))
                .hasMessageContaining("Rolled back 3 changes");
        try (Connection c = ds.getConnection()) {
            ResultSet rs = c.createStatement().executeQuery("SELECT COUNT(*) FROM orders");
            rs.next();
            assertThat(rs.getInt(1)).isZero();
        }
    }

    @Test
    void identityMapLoadsOncePerId() {
        AtomicInteger loads = new AtomicInteger();
        IdentityMap<String, Object> map = new IdentityMap<>(id -> {
            loads.incrementAndGet();
            return new Object();
        });
        assertThat(map.get("x")).isSameAs(map.get("x"));
        assertThat(loads).hasValue(1);
    }

    @Test
    void dirtyCheckingUpdatesOnlyChangedColumns() {
        Map<String, Employee> table = new HashMap<>(Map.of("E1", new Employee("E1", "HR", 100), "E2", new Employee("E2", "HR", 100)));
        DirtyCheckingSession s = new DirtyCheckingSession(table);
        s.find("E1").salaryPaise = 200;
        s.find("E2");
        assertThat(s.flush()).containsExactly("UPDATE employee SET salary_paise=200 WHERE id='E1'");
        assertThat(s.flush()).isEmpty();
        assertThat(table.get("E1").salaryPaise).isEqualTo(200);
    }
}

    6. Variations & Modern Java Take¶

    Variation Notes
    Caller registration (Example 1) Code explicitly calls registerNew/Dirty. Simple and explicit
    Object registration / dirty checking (Example 3) The unit of work snapshots on load and detects changes. Hibernate, EclipseLink
    Spring @Transactional Declares the unit-of-work boundary on a use-case method; the persistence context lives for that transaction
    Immutable aggregates With records, you save(newVersion) explicitly and the unit of work just batches those calls
    Event-sourced unit of work Collect new events from several aggregates and append them atomically with expected versions
    Outbox in the same unit of work Write the outbox row in the same transaction as the business change (Transactional Outbox)

    7. Where It Lives in Real Frameworks¶

    Where Unit of Work / Identity Map
    JPA / Hibernate EntityManager / Session = unit of work; the persistence context = identity map + snapshots; flush(), FlushMode
    Spring @Transactional, TransactionTemplate, PlatformTransactionManager; Open-Session-in-View (and why to disable it)
    jOOQ / JDBC No automatic unit of work: DSLContext.transaction(...) gives atomicity, you track changes yourself
    .NET EF Core DbContext + SaveChanges(): the same pattern, and a common interview comparison
    Kafka Producer transactions group writes to several partitions into one atomic unit

    8. Pros, Cons & Trade-offs¶

    ✅ Pros ❌ Cons
    Atomic business operations Long units of work hold memory and, if not careful, locks
    Fewer, batched writes; minimal UPDATEs with dirty checking "Magic" saves: changing a managed entity writes it, sometimes surprisingly
    Identity map: consistency within a request + first-level cache Dirty checking costs CPU proportional to managed objects
    Business code free of transaction plumbing Doesn't span services: across services you need a Saga

    9. Pitfalls & Anti-Patterns¶

    Units of work that span user think-time

    Keeping a transaction (or JPA persistence context) open while the user fills a form holds locks and connections. Load, close, then use optimistic locking (a version) when the user submits.

    Open Session in View

    Spring Boot enables it by default (with a warning). Lazy loading in controllers/views fires queries outside your use case, causing N+1 and surprising writes. Set spring.jpa.open-in-view=false.

    Global identity maps

    An identity map guarantees identity, not freshness. Shared across requests it becomes a stale, thread-unsafe cache (coding challenge). Scope it to one unit of work.

    Batch jobs with one giant persistence context

    Loading 1 million entities in one session exhausts memory and makes every flush slower. Process in chunks: flush() + clear() every N items.

    10. Senior / Architect Deep Dive (10–15 yrs)¶

    Write ordering. A real unit of work orders writes to satisfy foreign keys: inserts parent-first, deletes child-first. Hibernate uses an action queue sorted by entity type; with hibernate.order_inserts=true and JDBC batching, it groups statements into batches.

    Flush vs commit. flush() sends SQL but stays in the transaction; commit() makes it durable. JPQL queries trigger an auto-flush so queries see pending changes (FlushModeType.AUTO), a frequent source of "why did it run an UPDATE before my SELECT?".

    Consistency beyond one database. A unit of work is a local transaction. Once a business action spans services, replace "one transaction" with a saga plus an outbox written in the same local unit of work, and idempotent consumers on the other side.

    War story: the orphaned orders

    A grocery platform's order service used Spring Data repositories without @Transactional on the use case. Each save() committed on its own. During a sale, a stock CHECK constraint failed after the order and two lines were committed: 3,100 orders appeared in customer apps with no items and no payment. Support refunded nothing (nothing was charged) but spent two days explaining "empty orders". Fix: @Transactional on the application service (one unit of work per use case) and an integration test asserting no rows survive a failed placement. Lesson: a repository is not a transaction boundary. The use case is.

    12. Interview Corner¶

    Q1. What is a Unit of Work?

    An object that tracks all changes during a business operation and commits them together in one transaction.

    Q2. What is the persistence context in JPA?

    The set of managed entities in an EntityManager: an identity map plus change tracking.

    Q3. What does @Transactional do?

    Starts a transaction before the method and commits after (or rolls back on a runtime exception), via a proxy.

    Q4. Why does modifying an entity without calling save() update the database?

    Because it's managed: dirty checking at flush detects the change.

    Q5. What is the first-level cache in Hibernate?

    The identity map of the session: repeated find for the same id returns the same instance without a query.

    Q1. flush() vs commit()?

    Flush sends pending SQL within the transaction; commit ends the transaction and makes changes durable.

    Q2. Why is Open Session in View considered harmful?

    It extends the persistence context into the web layer: hidden lazy-loading queries, N+1, connections held longer.

    Q3. How do you process a million rows with JPA?

    Chunk: page through, flush() and clear() every N, or use JDBC/stateless sessions for bulk work.

    Q4. Why does @Transactional on a private method not work?

    Spring's proxy only intercepts calls that come through the proxy from outside; self-invocation and private methods bypass it.

    Q5. Which exceptions roll back by default?

    Unchecked (RuntimeException, Error). Checked exceptions commit unless you set rollbackFor.

    Q1. "Design the transaction boundaries for checkout across order, payment and inventory services."

    One local unit of work per service (business change + outbox row); an orchestrated saga connects them; consumers are idempotent; compensations undo on failure.

    Q2. "Why might dirty checking hurt performance?"

    Comparing snapshots of thousands of managed entities at every flush. Use read-only transactions/queries (@Transactional(readOnly = true), Session.setDefaultReadOnly), DTO projections or smaller contexts.

    Q3. "How does Hibernate order inserts and deletes?"

    An action queue: inserts, updates, collection changes, then deletes; with order_inserts/updates it groups by entity for JDBC batching while respecting FK order.

    Q4. "Is an identity map a cache?"

    It's a per-unit-of-work map that guarantees identity. It acts like a cache inside the transaction but must never be shared across transactions or threads.

    Q5. "How do you get atomicity with immutable aggregates?"

    Collect save(newVersion) calls (plus domain events) in a unit of work and commit together, with optimistic version checks per aggregate.

    Problem: A developer made the identity map a static singleton "to save queries". Show what goes wrong when another process updates a price, and fix it.

    Solution 
    package com.handbook.enterprise.unitofwork.scope;

import com.handbook.enterprise.unitofwork.travel.IdentityMap;

import java.util.HashMap;
import java.util.Map;

/** Coding challenge: why an identity map must be scoped to one session/transaction, not global. */
public class ScopeDemo {

    record Price(String sku, long paise) { }

    static final Map<String, Long> PRICE_TABLE = new HashMap<>(Map.of("ONION-1KG", 4_000L));

    public static void main(String[] args) {
        System.out.println("=== Challenge: Identity Map Scope ===");
        IdentityMap<String, Price> global = new IdentityMap<>(sku -> new Price(sku, PRICE_TABLE.get(sku)));

        System.out.println("Request 1 (global map)     : " + global.get("ONION-1KG"));
        PRICE_TABLE.put("ONION-1KG", 9_000L); // pricing team updates after a supply shock
        System.out.println("Request 2 (global map)     : " + global.get("ONION-1KG") + "  <- stale forever");

        IdentityMap<String, Price> perRequest = new IdentityMap<>(sku -> new Price(sku, PRICE_TABLE.get(sku)));
        System.out.println("Request 2 (per-request map): " + perRequest.get("ONION-1KG"));
        System.out.println("An identity map guarantees identity, not freshness: scope it to one unit of work.");
    }
}

    Output:

    === Challenge: Identity Map Scope ===
Request 1 (global map)     : Price[sku=ONION-1KG, paise=4000]
Request 2 (global map)     : Price[sku=ONION-1KG, paise=4000]  <- stale forever
Request 2 (per-request map): Price[sku=ONION-1KG, paise=9000]
An identity map guarantees identity, not freshness: scope it to one unit of work.

    Key points to say: an identity map has no expiry and no invalidation; it's also not thread-safe for concurrent requests. Scope it to one unit of work. If you need cross-request caching, use a real cache with TTL and invalidation (Cache-Aside).

    13. Quick Revision Card¶

    Remember in 30 seconds

    • Unit of Work: register changes, then one atomic commit (or rollback).
    • Identity Map: one object per row per unit of work; identity, not freshness.
    • JPA EntityManager = both; @Transactional on the use case sets the boundary.
    • Modifying a managed entity is a save (dirty checking).
    • Across services, use a saga + outbox instead.
    @Transactional public void place(Order o) { orders.save(o); stock.decrement(o.lines()); } // one unit of work
