    Advanced Data Microservices

    Event Sourcing¶

    🔴 Advanced Microservices Interview frequency ⭐⭐⭐⭐

    TL;DR

    Instead of storing the current state and overwriting it, store every change as an immutable event in an append-only log. The current state is derived by replaying the events (sped up with snapshots). You get a complete audit trail, time travel ("what was the state on 1 March?"), and the ability to build new views from history, at the cost of more complexity (schema evolution, replays, eventual consistency of read models).

    1. Intent & Problem It Solves¶

    The problem in plain English: a CRUD accounts table says the balance is ₹11,200. How did it get there? Which deposit was reversed? What was the balance at month-end for the regulator? The UPDATE destroyed that information. Bolting on audit tables later is error-prone (they drift from reality).

    Definition (Martin Fowler):

    Event Sourcing ensures that all changes to application state are stored as a sequence of events. Not just can we query these events, we can also use the event log to reconstruct past states.

    Core mechanics:

    Concept Meaning
    Event An immutable fact in the past tense: Deposited(₹100)
    Stream All events of one aggregate, in order (account-ACC-1)
    Rehydration Rebuilding state by applying events in order
    Snapshot Saved state at version N, so replay starts there
    Optimistic concurrency Append only if the stream is still at the expected version
    Projection A read model built from events (see CQRS)

    2. Real-World Analogy¶

    Your bank passbook vs. a whiteboard

    A whiteboard shows only today's balance; erase and rewrite. A passbook lists every deposit and withdrawal; the balance is the sum. You can check any past balance, find a wrong entry, and correct it with a new entry (a reversal), never by tearing out a page. Accountants have worked this way for centuries.

    3. Structure¶

    flowchart LR
    C[Command: withdraw ₹25] --> L[Load: snapshot + later events]
    L --> A[Aggregate checks rules]
    A -->|new events| S[(Event store<br/>append-only)]
    S --> P1[Projection: balance view]
    S --> P2[Projection: statement]
    S --> P3[Projection: fraud analytics]
    Participant Responsibility
    Aggregate Rebuilds state from events; decides which new events a command produces
    Event store Appends events per stream with version checks; reads streams
    Snapshot store Optional; periodic state copies to bound replay time
    Projections Read models, rebuildable from the log

    4. Naive Approach (Without the Pattern)¶

    UPDATE accounts SET balance = balance - 2500 WHERE id = 'ACC-1';
-- History lost. Audit table added later:
INSERT INTO account_audit ...   -- forgotten in one code path → audit no longer matches reality

    5. Three Real-World Examples¶

    Example 1: Event-Sourced Bank Account (Banking)¶

    Scenario: An account stream with Opened, Deposited and Withdrawn events. The repository loads the latest snapshot (taken every 4 events) and replays only later events. Two tellers load version 6 at the same time; teller A withdraws first; teller B's append is rejected by optimistic concurrency, reloads, and the rule check now correctly refuses the withdrawal: no double spend.

    Design:

    sequenceDiagram
    participant A as Teller A
    participant B as Teller B
    participant S as Event store
    A->>S: load (v6)
    B->>S: load (v6)
    A->>S: append Withdrawn(10000), expected v6 ✔ → v7
    B->>S: append Withdrawn(10000), expected v6 ✘ (now v7)
    B->>S: reload v7 → balance 1200 → insufficient funds

    Full Code:

    package com.handbook.microservices.eventsourcing.account;

import java.util.List;

/**
 * An event-sourced aggregate. State is never stored directly: it is the result of applying every
 * event in order. Commands check rules against that state and return NEW events.
 */
public final class Account {

    public sealed interface Event permits Opened, Deposited, Withdrawn {
    }

    public record Opened(String owner) implements Event {
    }

    public record Deposited(long paise) implements Event {
    }

    public record Withdrawn(long paise) implements Event {
    }

    /** A snapshot: the state as of a version, so replay can start there. */
    public record Snapshot(long version, String owner, long balance) {
    }

    private String owner;
    private long balance;
    private long version;

    public static Account replay(Snapshot snapshot, List<Event> laterEvents) {
        Account a = new Account();
        if (snapshot != null) {
            a.owner = snapshot.owner();
            a.balance = snapshot.balance();
            a.version = snapshot.version();
        }
        laterEvents.forEach(a::apply); // (1)!
        return a;
    }

    private void apply(Event e) { // (2)!
        switch (e) {
            case Opened o -> owner = o.owner();
            case Deposited d -> balance += d.paise();
            case Withdrawn w -> balance -= w.paise();
        }
        version++;
    }

    public List<Event> deposit(long paise) { // (3)!
        if (paise <= 0) {
            throw new IllegalArgumentException("amount must be positive");
        }
        return List.of(new Deposited(paise));
    }

    public List<Event> withdraw(long paise) {
        if (paise > balance) {
            throw new IllegalStateException("insufficient funds");
        }
        return List.of(new Withdrawn(paise));
    }

    public Snapshot snapshot() {
        return new Snapshot(version, owner, balance);
    }

    public long version() {
        return version;
    }

    public long balance() {
        return balance;
    }
}
    1. State = fold of events, starting from a snapshot if there is one.
    2. apply only changes state; it never validates (past events are facts, even if today's rules differ).
    3. Commands validate and return new events; they don't mutate state directly.
    package com.handbook.microservices.eventsourcing.account;

import java.util.ArrayList;
import java.util.HashMap;
import java.util.List;
import java.util.Map;

/**
 * An append-only store of events per stream (one stream per aggregate). Appends carry the version
 * the writer last saw; if someone else appended first, the write is rejected (optimistic locking).
 */
public final class EventStore<E> {

    public static final class ConcurrencyException extends RuntimeException {
        ConcurrencyException(String stream, long expected, long actual) {
            super(stream + ": expected version " + expected + " but was " + actual);
        }
    }

    private final Map<String, List<E>> streams = new HashMap<>();
    private int reads;

    public synchronized void append(String stream, long expectedVersion, List<E> events) {
        List<E> existing = streams.computeIfAbsent(stream, k -> new ArrayList<>());
        if (existing.size() != expectedVersion) { // (1)!
            throw new ConcurrencyException(stream, expectedVersion, existing.size());
        }
        existing.addAll(events);
    }

    /** Events with version greater than {@code afterVersion} (versions start at 1). */
    public synchronized List<E> read(String stream, long afterVersion) {
        List<E> all = streams.getOrDefault(stream, List.of());
        reads += all.size() - (int) afterVersion;
        return List.copyOf(all.subList((int) afterVersion, all.size()));
    }

    public synchronized int eventsReadSoFar() {
        return reads;
    }
}
    1. Optimistic concurrency: the append fails if someone else appended since we loaded.
    package com.handbook.microservices.eventsourcing.account;

import com.handbook.microservices.eventsourcing.account.Account.Event;
import com.handbook.microservices.eventsourcing.account.Account.Snapshot;

import java.util.HashMap;
import java.util.List;
import java.util.Map;
import java.util.function.Function;

/** Loads aggregates from snapshot + later events, and saves new events with optimistic locking. */
public final class AccountRepository {

    private final EventStore<Event> store;
    private final Map<String, Snapshot> snapshots = new HashMap<>();
    private final int snapshotEvery;

    public AccountRepository(EventStore<Event> store, int snapshotEvery) {
        this.store = store;
        this.snapshotEvery = snapshotEvery;
    }

    public Account load(String id) {
        Snapshot snap = snapshots.get(id);
        return Account.replay(snap, store.read(id, snap == null ? 0 : snap.version()));
    }

    /** Load, run the command, append its events at the version we loaded. */
    public void execute(String id, Function<Account, List<Event>> command) {
        Account account = load(id);
        List<Event> events = command.apply(account);
        store.append(id, account.version(), events);
        Account after = Account.replay(account.snapshot(), events);
        if (after.version() / snapshotEvery > account.version() / snapshotEvery) { // (1)!
            snapshots.put(id, after.snapshot());
        }
    }
}
    1. Take a snapshot when the version crosses a multiple of snapshotEvery.
    package com.handbook.microservices.eventsourcing.account;

import com.handbook.microservices.eventsourcing.account.Account.Event;
import com.handbook.microservices.eventsourcing.account.Account.Opened;

import java.util.List;

public class AccountEventSourcingDemo {

    public static void main(String[] args) {
        EventStore<Event> store = new EventStore<>();
        var repo = new AccountRepository(store, 4);

        System.out.println("=== Banking: an event-sourced account ===");
        store.append("ACC-1", 0, List.of(new Opened("Asha")));
        repo.execute("ACC-1", a -> a.deposit(10_000));
        repo.execute("ACC-1", a -> a.withdraw(2_500));
        repo.execute("ACC-1", a -> a.deposit(4_000));
        repo.execute("ACC-1", a -> a.withdraw(1_000));
        repo.execute("ACC-1", a -> a.deposit(700));

        System.out.println("Event stream : " + store.read("ACC-1", 0));
        int before = store.eventsReadSoFar();
        Account loaded = repo.load("ACC-1");
        System.out.println("Balance " + loaded.balance() + " at version " + loaded.version()
                + ", rebuilt by replaying " + (store.eventsReadSoFar() - before) + " event(s) after the snapshot at v4");

        System.out.println("-- two tellers load v6 at the same time --");
        Account tellerA = repo.load("ACC-1");
        Account tellerB = repo.load("ACC-1");
        store.append("ACC-1", tellerA.version(), tellerA.withdraw(10_000));
        System.out.println("Teller A withdrew 10000 -> balance " + repo.load("ACC-1").balance());
        try {
            store.append("ACC-1", tellerB.version(), tellerB.withdraw(10_000));
        } catch (EventStore.ConcurrencyException e) {
            System.out.println("Teller B rejected: " + e.getMessage() + " -> reload and retry");
            try {
                repo.execute("ACC-1", a -> a.withdraw(10_000));
            } catch (IllegalStateException retryFailed) {
                System.out.println("Retry on fresh state: " + retryFailed.getMessage() + " (no double spend)");
            }
        }
    }
}

    Output:

    === Banking: an event-sourced account ===
Event stream : [Opened[owner=Asha], Deposited[paise=10000], Withdrawn[paise=2500], Deposited[paise=4000], Withdrawn[paise=1000], Deposited[paise=700]]
Balance 11200 at version 6, rebuilt by replaying 2 event(s) after the snapshot at v4
-- two tellers load v6 at the same time --
Teller A withdrew 10000 -> balance 1200
Teller B rejected: ACC-1: expected version 6 but was 7 -> reload and retry
Retry on fresh state: insufficient funds (no double spend)

    Why event sourcing here:

    • The ledger is the history; audits and disputes read it directly.
    • Concurrency is handled per stream without row locks.
    • Snapshots keep loading fast as streams grow.

    Example 2: What the Cart Table Forgets (E-commerce)¶

    Scenario: A CRUD cart table shows only what's in each cart now. The event log also knows what was added and removed. Replaying it reveals that avocados are removed right before checkout in carts that still get bought, a signal about price or stock reliability that CRUD would have deleted.

    Full Code:

    package com.handbook.microservices.eventsourcing.cart;

import java.util.ArrayList;
import java.util.HashMap;
import java.util.List;
import java.util.Map;
import java.util.TreeMap;

/** Cart events, the current cart derived from them, and an insight a CRUD table would have lost. */
public final class CartEvents {

    public sealed interface Event permits ItemAdded, ItemRemoved, CheckedOut {
        String cartId();
    }

    public record ItemAdded(String cartId, String sku) implements Event {
    }

    public record ItemRemoved(String cartId, String sku) implements Event {
    }

    public record CheckedOut(String cartId) implements Event {
    }

    private CartEvents() {
    }

    /** Current state: what a CRUD "cart_items" table would hold. */
    public static Map<String, List<String>> currentCarts(List<Event> log) {
        Map<String, List<String>> carts = new TreeMap<>();
        for (Event e : log) {
            switch (e) {
                case ItemAdded a -> carts.computeIfAbsent(a.cartId(), k -> new ArrayList<>()).add(a.sku());
                case ItemRemoved r -> carts.get(r.cartId()).remove(r.sku());
                case CheckedOut c -> { }
            }
        }
        return carts;
    }

    /** History-based insight: items removed from carts that were later checked out anyway. */
    public static Map<String, Integer> removedBeforeCheckout(List<Event> log) {
        Map<String, List<String>> removedPerCart = new HashMap<>();
        Map<String, Integer> counts = new TreeMap<>();
        for (Event e : log) {
            switch (e) {
                case ItemRemoved r -> removedPerCart.computeIfAbsent(r.cartId(), k -> new ArrayList<>()).add(r.sku());
                case CheckedOut c -> removedPerCart.getOrDefault(c.cartId(), List.of())
                        .forEach(sku -> counts.merge(sku, 1, Integer::sum)); // (1)!
                case ItemAdded a -> { }
            }
        }
        return counts;
    }
}
    1. A new question asked of old data: no schema change, just a new fold over the events.
    package com.handbook.microservices.eventsourcing.cart;

import com.handbook.microservices.eventsourcing.cart.CartEvents.CheckedOut;
import com.handbook.microservices.eventsourcing.cart.CartEvents.Event;

import com.handbook.microservices.eventsourcing.cart.CartEvents.ItemRemoved;

import java.util.List;

public class CartHistoryDemo {

    public static void main(String[] args) {
        List<Event> log = List.of(
                new ItemAdded("C1", "MANGO-1KG"), new ItemAdded("C1", "AVOCADO-2"), new ItemRemoved("C1", "AVOCADO-2"),
                new CheckedOut("C1"),
                new ItemAdded("C2", "AVOCADO-2"), new ItemAdded("C2", "RICE-5KG"), new ItemRemoved("C2", "AVOCADO-2"),
                new CheckedOut("C2"),
                new ItemAdded("C3", "MILK-1L"), new ItemAdded("C3", "BREAD"), new ItemRemoved("C3", "BREAD"));

        System.out.println("=== E-commerce: what the cart table shows vs. what the events know ===");
        System.out.println("Current carts (CRUD view)          : " + CartEvents.currentCarts(log));
        System.out.println("Removed, yet the cart was bought   : " + CartEvents.removedBeforeCheckout(log));

    Output:

    === E-commerce: what the cart table shows vs. what the events know ===
Current carts (CRUD view)          : {C1=[MANGO-1KG], C2=[RICE-5KG], C3=[MILK-1L]}

    Why event sourcing here:

    • Business questions nobody thought of at design time can be answered retroactively.
    • Analytics and ML features come from the same source of truth as the app.

    Example 3: Temporal Queries on a Shipment (Logistics)¶

    Scenario: A customer disputes a late delivery and blames the courier. Replaying the shipment's scans up to a point in time shows exactly what the system knew then: at 14:00 the parcel was in transit at Pune; by midnight it was flagged with a weather delay.

    Full Code:

    package com.handbook.microservices.eventsourcing.shipment;

import java.time.Instant;
import java.util.List;

/** Shipment events with timestamps support "what did we know at time T?" queries. */
public final class ShipmentHistory {

    public record Scanned(Instant at, String location, String status) {
    }

    public record State(String location, String status) {
    }

    private final List<Scanned> events;

    public ShipmentHistory(List<Scanned> events) {
        this.events = List.copyOf(events);
    }

    public State current() {
        return stateAt(Instant.MAX);
    }

    public State stateAt(Instant when) { // (1)!
        State state = new State("-", "CREATED");
        for (Scanned e : events) {
            if (e.at().isAfter(when)) {
                break;
            }
            state = new State(e.location(), e.status());
        }
        return state;
    }
}
    1. Time travel: replay only events up to when.
    package com.handbook.microservices.eventsourcing.shipment;

import com.handbook.microservices.eventsourcing.shipment.ShipmentHistory.Scanned;

import java.time.Instant;
import java.util.List;

public class ShipmentTemporalDemo {

    public static void main(String[] args) {
        var history = new ShipmentHistory(List.of(
                new Scanned(Instant.parse("2026-10-12T06:10:00Z"), "Mumbai hub", "PICKED_UP"),
                new Scanned(Instant.parse("2026-10-12T13:45:00Z"), "Pune sort centre", "IN_TRANSIT"),
                new Scanned(Instant.parse("2026-10-12T18:20:00Z"), "Pune sort centre", "DELAYED_WEATHER"),
                new Scanned(Instant.parse("2026-10-13T09:05:00Z"), "Bengaluru hub", "IN_TRANSIT"),
                new Scanned(Instant.parse("2026-10-13T15:30:00Z"), "Koramangala", "DELIVERED")));

        System.out.println("=== Logistics: temporal queries on a shipment ===");
        System.out.println("Now                         : " + history.current());
        System.out.println("At 2026-10-12 14:00 UTC     : " + history.stateAt(Instant.parse("2026-10-12T14:00:00Z")));
        System.out.println("At 2026-10-12 23:59 UTC     : " + history.stateAt(Instant.parse("2026-10-12T23:59:00Z")));
        System.out.println("Customer says: \"the delay was the courier's fault\" -> the history shows a weather delay at Pune, 18:20.");
    }
}

    Output:

    === Logistics: temporal queries on a shipment ===

At 2026-10-12 14:00 UTC     : State[location=Pune sort centre, status=IN_TRANSIT]

    • "As of" queries are natural; with CRUD they need bitemporal tables.

import java.util.Map;

import static org.assertj.core.api.Assertions.assertThatThrownBy;

class EventSourcingTest {

    @Test
    void stateIsRebuiltFromEventsWithOrWithoutSnapshots() {
        EventStore<Event> store = new EventStore<>();
        store.append("A", 0, List.of(new Opened("x")));

    @Test
    void upcasterConvertsRupeeStringsToPaise() {
        Map<String, Object> v1 = new java.util.LinkedHashMap<>(Map.of("type", "PriceSet", "version", 1, "price", "1.05"));
        assertThat(Upcaster.upcast(v1)).containsEntry("amountPaise", 105L).containsEntry("version", 2);

    6. Variations & Modern Java Take¶

    // Axon Framework (reference): an event-sourced aggregate
@Aggregate
class AccountAggregate {
    @AggregateIdentifier String id;
    long balance;

    @CommandHandler
    void handle(WithdrawCommand cmd) {
        if (cmd.amount() > balance) throw new IllegalStateException("insufficient funds");
        AggregateLifecycle.apply(new Withdrawn(cmd.accountId(), cmd.amount())); // stored + applied
    }

    @EventSourcingHandler
    void on(Withdrawn e) { balance -= e.amount(); }  // used for rehydration
}
    Option Notes
    EventStoreDB (Kurrent) Purpose-built event store: streams, subscriptions, optimistic concurrency
    Axon Framework + Axon Server Java CQRS/ES framework with snapshots and sagas
    PostgreSQL table events(stream_id, version, type, payload, PRIMARY KEY(stream_id, version)): the unique key enforces concurrency
    Kafka Great for distributing events, but weak as the store for per-aggregate loads and optimistic concurrency
    Java records + sealed interfaces Ideal for events: immutable, exhaustive switch in apply

    7. Where It Lives in Real Frameworks¶

    Where Event sourcing
    Axon Framework @EventSourcingHandler, snapshots, upcasters
    EventStoreDB Streams with expected-version appends
    Git Commits are events; a checkout is a replay
    Database WAL / Kafka log compaction Log-first storage underneath many systems
    Accounting ledgers Double-entry bookkeeping is event sourcing on paper

    8. Pros, Cons & Trade-offs¶

    ✅ Pros ❌ Cons
    Complete audit trail by design Steep learning curve; unfamiliar to most teams
    Temporal queries and debugging by replay Event schema evolution is hard (events are forever)
    New read models from old data Queries need projections (CQRS)
    Natural fit with event-driven integration GDPR "right to be forgotten" in an immutable log needs crypto-shredding
    No lost updates (optimistic concurrency per stream) Replays can be slow without snapshots

    9. Pitfalls & Anti-Patterns¶

    Event sourcing the whole system

    Use it for aggregates where history matters (ledgers, orders, workflows), not for user profiles or reference data. Mixing styles per service is normal.

    Using events as a message bus between services without contracts

    Internal domain events (fine-grained, private) are different from integration events (public, stable). Publishing internal events couples other services to your internals.

    Validating in apply

    If rules change, old events would fail to replay. apply must accept every historical event; validate in command handlers.

    Changing or deleting stored events

    Fix mistakes with compensating events (DepositReversed). For schema changes, use upcasting (see the coding challenge) or copy-and-transform migrations.

    10. Senior / Architect Deep Dive (10–15 yrs)¶

    Schema evolution strategies. Weak schemas (tolerant readers ignoring unknown fields), upcasters that convert old versions on read, versioned event types, or copy-transform migrations of whole streams. Keep events small and business-focused to limit change.

    GDPR and immutability. Encrypt personal data in events with a per-subject key and delete the key on erasure (crypto-shredding), or keep PII out of events and reference it.

    Snapshot policy. Snapshot every N events or when load time exceeds a threshold; snapshots are a cache, so they can be discarded and rebuilt after model changes.

    When it pays off. Domains with inherent history (finance, logistics, compliance), complex workflows, or heavy analytics needs. When it doesn't: CRUD-heavy domains, small teams, tight deadlines.

    Production checklist¶

    • Clear reason (audit, temporal queries, complex domain), scoped to specific aggregates.
    • Event store with per-stream optimistic concurrency (unique (stream, version)).
    • Snapshot policy; replay performance measured.
    • Versioned events + upcasters; tolerant readers.
    • Separate internal domain events from published integration events.
    • PII strategy (crypto-shredding); retention and archival plan.
    • Projections idempotent with checkpoints; rebuild procedure tested.

    Explain it in 2 minutes (system design round)¶

    "For the wallet ledger I'd use event sourcing: each wallet is a stream of Credited/Debited/Reversed events in a PostgreSQL events table with a unique (wallet_id, version) constraint for optimistic concurrency. Commands load a snapshot plus recent events, check the balance rule and append. Events go to Kafka via the outbox and feed projections: balance, statements and fraud features. Corrections are new events, never updates. Snapshots every 100 events keep loads fast, upcasters handle schema changes, and personal data is encrypted per user for erasure."

    War story: the event nobody could replay

    A logistics company renamed a field in ParcelScanned and deployed. Old events still had the old field name; the next projection rebuild failed halfway through 400 million events, and the tracking page served stale data for 9 hours while engineers wrote an emergency upcaster. Fix: schema-compatibility checks in CI (every historical event version must deserialize), upcasters registered for every change, and a nightly replay of a sample of old streams. Lesson: in event sourcing, old events are part of your API forever. Test them like an API.

    12. Interview Corner¶

    Q1. What is event sourcing?

    Storing every change as an immutable event and deriving current state by replaying events, instead of storing and overwriting the current state.

    Q2. Give a real-life example.

    A bank passbook or accounting ledger; Git commits.

    Q3. What is a snapshot?

    A saved copy of state at a version, so you don't have to replay all events from the beginning.

    Q4. Can you delete or edit an event?

    No. You append a corrective event (e.g. PaymentReversed).

    Q5. What's the relation to CQRS?

    Event sourcing gives you events; CQRS projections turn them into query-friendly read models. They're often used together.

    Q1. How is concurrency handled?

    Optimistic concurrency: append with the expected stream version; if another writer appended first, reload and retry.

    Q2. How do you query "all accounts with balance > X"?

    Not from the event store; build a projection (read model) and query it.

    Q3. How do you change an event's schema?

    Version the event and add an upcaster that converts old versions when reading, or use tolerant readers for additive changes.

    Q4. Domain events vs. integration events?

    Domain events are internal and fine-grained; integration events are stable, public contracts published to other services.

    Q5. What makes replay slow, and how do you fix it?

    Long streams; fix with snapshots, and for projections, parallel replay per partition.

    Q1. "How do you handle GDPR erasure with an immutable log?"

    Crypto-shredding: encrypt PII per subject and delete the key; or keep PII out of events (reference IDs) and store it in a deletable store.

    Q2. "Would you use Kafka as the event store?"

    Usually not as the only store: no efficient per-aggregate reads or expected-version appends. Use a DB/EventStoreDB as the store and Kafka for distribution.

    Q3. "Design a ledger for a wallet with 10M users and audit requirements."

    Per-wallet streams, a unique (wallet, version) constraint, commands with balance checks, snapshots, outbox to Kafka, projections for balances and statements, reversals as events, crypto-shredding, nightly reconciliation of projections against streams.

    Q4. "A bug produced wrong events last week. What do you do?"

    Never edit history: append compensating events per affected stream (a scripted migration), fix the code, and rebuild affected projections. Document it for audit.

    Q5. "When would you advise against event sourcing?"

    CRUD-dominant domains, teams new to DDD, no audit/temporal needs, or tight deadlines. Consider an outbox + audit log instead.

    Problem: Version 1 of PriceSet stored the price as a rupee string ("399.00"). Version 2 stores integer paise and a currency. Old events can't be changed. Write an upcaster so the application only ever sees v2.

    Solution 
    package com.handbook.microservices.eventsourcing.upcasting;

import java.math.BigDecimal;
import java.util.LinkedHashMap;
import java.util.Map;

/**
 * Coding challenge: stored events are immutable, but schemas evolve. Version 1 of PriceSet stored
 * the price as a rupee string ("399.00"); version 2 stores integer paise and a currency.
 * An upcaster converts old events on read, so the domain code only ever sees the latest version.
 */
public final class Upcaster {

    private Upcaster() {
    }

    public static Map<String, Object> upcast(Map<String, Object> stored) {
        Map<String, Object> e = new LinkedHashMap<>(stored);
        if ("PriceSet".equals(e.get("type")) && Integer.valueOf(1).equals(e.get("version"))) {
            long paise = new BigDecimal((String) e.remove("price")).movePointRight(2).longValueExact();
            e.put("version", 2);
            e.put("amountPaise", paise);
            e.put("currency", "INR"); // v1 only ever existed in the Indian store
        }
        return e;
    }
}

    package com.handbook.microservices.eventsourcing.upcasting;

import java.util.LinkedHashMap;
import java.util.List;
import java.util.Map;

public class UpcastingDemo {

    public static void main(String[] args) {
        List<Map<String, Object>> stored = List.of(
                event("PriceSet", 1, "sku", "MANGO-1KG", "price", "399.00"),
                event("PriceSet", 1, "sku", "RICE-5KG", "price", "649.50"),
                event("PriceSet", 2, "sku", "MANGO-1KG", "amountPaise", 34_900L, "currency", "INR"));

        System.out.println("=== Challenge: upcasting old event versions on read ===");
        for (Map<String, Object> e : stored) {
            System.out.println("stored  " + e);
            System.out.println("  read  " + Upcaster.upcast(e));
        }
    }

    private static Map<String, Object> event(String type, int version, Object... kv) {
        Map<String, Object> e = new LinkedHashMap<>();
        e.put("type", type);
        e.put("version", version);
        for (int i = 0; i < kv.length; i += 2) {
            e.put((String) kv[i], kv[i + 1]);
        }
        return e;
    }
}

    13. Quick Revision Card¶

    Remember in 30 seconds

    • State = replay of immutable events; snapshots for speed.
    • Commands validate → new events; apply never validates.
    • Optimistic concurrency per stream (expected version).
    • Corrections are new events; upcasters for schema changes.
    • Pair with CQRS projections for queries.
