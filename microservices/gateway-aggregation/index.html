    Gateway Aggregation¶

    🟡 Intermediate Microservices Interview frequency ⭐⭐⭐⭐

    TL;DR

    Gateway Aggregation combines several backend calls into one client request: the client asks once, the gateway fans out (in parallel where possible), merges the results and returns a single response, within a latency budget and with partial results when a backend is slow or down. Use it when clients (especially mobile) would otherwise make many round trips. Keep it to composition: no business rules.

    See It in Motion¶

    Press Play to watch the calls travel between components, or step through with Next and Back. Open the full explorer with all 66 patterns

    1. Intent & Problem It Solves¶

    The problem in plain English: a travel app's trip screen needs flight status, the hotel, the cab and the weather, from four services. On a 4G connection each round trip costs ~300 ms, so the screen takes over a second, drains the battery and breaks when any one call fails. Every client (iOS, Android, web) re-implements the same fan-out.

    Definition (Azure Architecture Center, Gateway Aggregation pattern):

    Use a gateway to aggregate multiple individual requests into a single request. The gateway receives one request from the client, dispatches requests to the various backend systems, aggregates the results and sends them back to the requesting client.

    Where this page fits: the BFF page shows who owns aggregation (one backend per client experience). This page is about how to aggregate well: declarative composition, field-driven fan-out, latency budgets with partial results, and dependency-ordered calls.

    2. Real-World Analogy¶

    A travel agent

    Instead of calling the airline, the hotel, the cab company and checking the weather yourself, you call one travel agent who makes those calls in parallel and gives you one itinerary. If the cab company doesn't answer in time, the agent still sends the itinerary with "cab: to be confirmed", rather than making you wait all day.

    3. Structure¶

    sequenceDiagram autonumber participant App as Mobile app participant G as Gateway / aggregator participant F as Flights participant H as Hotels participant C as Cabs App->>G: GET /itinerary/TRIP-9 par fan-out G->>F: status G->>H: booking G->>C: pickup end F-->>G: 120 ms H-->>G: 90 ms C-->>G: 60 ms G-->>App: one merged response (≈ slowest call)
    Participant Responsibility
    Client One request per screen/use case
    Aggregator (gateway, BFF, GraphQL server) Fan-out, per-call timeouts, overall budget, merge, partial-result handling
    Backend services Own their data; unaware of aggregation
    Composition spec Which backends and fields make up the response (code or configuration)

    4. Naive Approach (Without the Pattern)¶

    // Android client
val flight = api.flight(tripId)      // 300 ms
val hotel  = api.hotel(tripId)       // 300 ms
val cab    = api.cab(tripId)         // 300 ms
val wx     = api.weather(city)       // 300 ms  → 1.2 s, four failure points, repeated on iOS and web
    • Latency adds up over slow networks.
    • Each client duplicates orchestration and error handling.
    • Internal service boundaries leak into public APIs.

    5. Three Real-World Examples¶

    Example 1: Declarative Itinerary Composition (Travel)¶

    Scenario: A travel app's trip screen combines four services. The API team keeps the composition in configuration ("gate comes from flights.gate"), so adding a field is a config change reviewed like code, and the gateway calls all four backends in parallel. Latency becomes the slowest backend (120 ms) instead of four mobile round trips.

    Design:

    flowchart LR App -->|"GET /itinerary"| G["Aggregation spec<br/>flight ← flights.status<br/>gate ← flights.gate<br/>hotel ← hotels.name<br/>..."] G --> F[flights] & H[hotels] & C[cabs] & W[weather]

    Full Code:

    package com.handbook.microservices.aggregation.declarative;

import com.handbook.microservices.aggregation.core.SimCall;

import java.util.LinkedHashMap;
import java.util.List;
import java.util.Map;

/** Aggregation as configuration: which backends to call and which fields to copy into the response. */
public final class AggregationSpec {

    /** "itinerary.flight <- flights.pnrStatus" style mapping. */
    public record FieldMapping(String responseField, String backend, String backendField) { }

    private final List<FieldMapping> mappings;

    public AggregationSpec(List<FieldMapping> mappings) {
        this.mappings = mappings;
    }

    /** Calls every backend in parallel once, then copies mapped fields; latency is the slowest call. */
    public Map<String, Object> execute(Map<String, SimCall> backends, StringBuilder timeline) {
        Map<String, Object> response = new LinkedHashMap<>();
        long slowest = 0;
        for (SimCall call : backends.values()) { // (1)!
            slowest = Math.max(slowest, call.latencyMs());
        }
        for (FieldMapping m : mappings) { // (2)!
            response.put(m.responseField(), backends.get(m.backend()).result().get(m.backendField()));
        }
        timeline.append(backends.size()).append(" backends in parallel, total ").append(slowest).append(" ms");
        return response;
    }
}
    1. Each backend is called once, in parallel: total latency is the maximum, not the sum.
    2. The response shape is driven by mappings, not hand-written merging code.
    package com.handbook.microservices.aggregation.declarative;

import com.handbook.microservices.aggregation.core.SimCall;
import com.handbook.microservices.aggregation.declarative.AggregationSpec.FieldMapping;

import java.util.LinkedHashMap;
import java.util.List;
import java.util.Map;

public class ItineraryDemo {

    public static void main(String[] args) {
        System.out.println("=== Travel: One /itinerary Call Instead of Four from the Mobile App ===");
        AggregationSpec spec = new AggregationSpec(List.of( // would live in gateway YAML, owned by the API team
                new FieldMapping("flight", "flights", "status"),
                new FieldMapping("gate", "flights", "gate"),
                new FieldMapping("hotel", "hotels", "name"),
                new FieldMapping("checkIn", "hotels", "checkIn"),
                new FieldMapping("cab", "cabs", "pickup"),
                new FieldMapping("weather", "weather", "summary")));

        Map<String, SimCall> backends = new LinkedHashMap<>();
        backends.put("flights", SimCall.ok("flights", 120, Map.of("status", "6E-2134 on time", "gate", "B12")));
        backends.put("hotels", SimCall.ok("hotels", 90, Map.of("name", "Sea Breeze, Goa", "checkIn", "14:00")));
        backends.put("cabs", SimCall.ok("cabs", 60, Map.of("pickup", "GOI T1, 11:20")));
        backends.put("weather", SimCall.ok("weather", 40, Map.of("summary", "31C, humid")));

        StringBuilder timeline = new StringBuilder();
        Map<String, Object> itinerary = spec.execute(backends, timeline);
        System.out.println("Response: " + itinerary);
        System.out.println("Gateway: " + timeline + "; the app on 4G would have made 4 round trips (~4 x 300 ms).");
    }
}

    package com.handbook.microservices.aggregation.core;

import java.util.Map;

/** A backend call with a known latency, so aggregation timelines are deterministic (virtual milliseconds). */
public record SimCall(String backend, long latencyMs, Map<String, Object> result, boolean fails) {

    public static SimCall ok(String backend, long latencyMs, Map<String, Object> result) {
        return new SimCall(backend, latencyMs, result, false);
    }

    public static SimCall failing(String backend, long latencyMs) {
        return new SimCall(backend, latencyMs, Map.of(), true);
    }
}

    Output:

    === Travel: One /itinerary Call Instead of Four from the Mobile App ===
Response: {flight=6E-2134 on time, gate=B12, hotel=Sea Breeze, Goa, checkIn=14:00, cab=GOI T1, 11:20, weather=31C, humid}
Gateway: 4 backends in parallel, total 120 ms; the app on 4G would have made 4 round trips (~4 x 300 ms).

    Why aggregation here:

    • One round trip over the slow network; the fan-out happens on the fast data-centre network.
    • Composition is visible, reviewable configuration.
    • Backends stay unaware of the screen they serve.

    Example 2: Field-Driven Fan-Out (E-commerce)¶

    Scenario: The search-results tile shows only name and price; the product page shows name, price, stock, rating and delivery ETA. The reviews service is slow (180 ms). With a fixed "product" endpoint, every search tile would wait for reviews it never displays. With GraphQL-style field selection, the aggregator calls only the backends that own the requested fields.

    Design:

    flowchart LR T["Search tile: {name, price}"] --> A{Field → owner} P["Product page: {name, price, stock, rating, eta}"] --> A A -->|tile| C[catalog] & PR[pricing] A -->|page| C & PR & I[inventory] & R[reviews] & D[delivery]

    Full Code:

    package com.handbook.microservices.aggregation.fields;

import com.handbook.microservices.aggregation.core.SimCall;

import java.util.LinkedHashMap;
import java.util.LinkedHashSet;
import java.util.List;
import java.util.Map;
import java.util.Set;

/** GraphQL-style: the client names the fields it needs; only the backends that own those fields are called. */
public final class FieldDrivenAggregator {

    private final Map<String, String> fieldOwner; // field -> backend
    private final Map<String, SimCall> backends;

    public FieldDrivenAggregator(Map<String, String> fieldOwner, Map<String, SimCall> backends) {
        this.fieldOwner = fieldOwner;
        this.backends = backends;
    }

    public record Result(Map<String, Object> data, Set<String> backendsCalled, long latencyMs) { }

    public Result query(List<String> fields) {
        Set<String> needed = new LinkedHashSet<>();
        for (String f : fields) {
            needed.add(fieldOwner.get(f)); // (1)!
        }
        long latency = needed.stream().mapToLong(b -> backends.get(b).latencyMs()).max().orElse(0);
        Map<String, Object> data = new LinkedHashMap<>();
        for (String f : fields) {
            data.put(f, backends.get(fieldOwner.get(f)).result().get(f));
        }
        return new Result(data, needed, latency);
    }
}
    1. Resolve each requested field to its owning backend; the set of backends to call is derived from the query. This is how GraphQL resolvers and Netflix's federated graph avoid over-fetching.
    package com.handbook.microservices.aggregation.fields;

import com.handbook.microservices.aggregation.core.SimCall;
import com.handbook.microservices.aggregation.fields.FieldDrivenAggregator.Result;

import java.util.List;
import java.util.Map;

public class ProductFieldsDemo {

    public static void main(String[] args) {
        System.out.println("=== E-commerce: Each Screen Asks Only for the Fields It Shows ===");
        FieldDrivenAggregator gateway = new FieldDrivenAggregator(
                Map.of("name", "catalog", "price", "pricing", "stock", "inventory", "rating", "reviews", "eta", "delivery"),
                Map.of("catalog", SimCall.ok("catalog", 30, Map.of("name", "Noise-cancelling earbuds")),
                        "pricing", SimCall.ok("pricing", 25, Map.of("price", "INR 3,999")),
                        "inventory", SimCall.ok("inventory", 40, Map.of("stock", "In stock")),
                        "reviews", SimCall.ok("reviews", 180, Map.of("rating", "4.3 (2,140)")),
                        "delivery", SimCall.ok("delivery", 70, Map.of("eta", "Tomorrow"))));

        Result listTile = gateway.query(List.of("name", "price"));
        System.out.println("Search tile   " + listTile.data() + " -> called " + listTile.backendsCalled() + ", " + listTile.latencyMs() + " ms");
        Result detail = gateway.query(List.of("name", "price", "stock", "rating", "eta"));
        System.out.println("Product page  -> called " + detail.backendsCalled().size() + " backends, " + detail.latencyMs() + " ms (reviews is the slow one)");
        System.out.println("A fixed 'product' endpoint would make every search tile wait 180 ms for reviews it doesn't show.");
    }
}

    Output:

    === E-commerce: Each Screen Asks Only for the Fields It Shows ===
Search tile   {name=Noise-cancelling earbuds, price=INR 3,999} -> called [catalog, pricing], 30 ms
Product page  -> called 5 backends, 180 ms (reviews is the slow one)
A fixed 'product' endpoint would make every search tile wait 180 ms for reviews it doesn't show.

    Why field-driven aggregation here:

    • Each screen pays only for the data it shows (30 ms vs 180 ms for search tiles).
    • Fewer backend calls under load: search pages are 10× more common than product pages.
    • One endpoint serves many screens without bespoke versions.

    Example 3: Latency Budget with Partial Results (Insurance)¶

    Scenario: An insurance marketplace shows car-insurance quotes from 5 insurers. Most answer in under 700 ms; one partner API often takes 2 seconds; another sometimes errors. Product's rule: show the page within 800 ms with whatever quotes are available, sorted by price, and list who's missing, rather than fail or make everyone wait for the slowest insurer.

    Design:

    gantt dateFormat x axisFormat %L ms title Fan-out with an 800 ms budget section Insurers Suraksha General (220) :0, 220 Bharat Shield (640) :0, 640 Raksha Direct (410) :0, 410 Kavach Insure (1900, cut) :crit, 0, 800 Monsoon Mutual (error) :crit, 0, 150

    Full Code:

    package com.handbook.microservices.aggregation.budget;

import com.handbook.microservices.aggregation.core.SimCall;

import java.util.ArrayList;
import java.util.Comparator;
import java.util.List;

/** Fan out to every insurer, keep whatever answers within the latency budget, and say what's missing. */
public final class QuoteAggregator {

    public record Quote(String insurer, long premiumPaise) { }

    public record Page(List<Quote> quotes, List<String> missing, long respondedAtMs) { }

    private final long budgetMs;

    public QuoteAggregator(long budgetMs) {
        this.budgetMs = budgetMs;
    }

    public Page aggregate(List<SimCall> insurers) {
        List<Quote> quotes = new ArrayList<>();
        List<String> missing = new ArrayList<>();
        long latest = 0;
        for (SimCall call : insurers) {
            if (call.fails()) {
                missing.add(call.backend() + " (error)"); // (1)!
            } else if (call.latencyMs() > budgetMs) {
                missing.add(call.backend() + " (timed out at " + budgetMs + " ms)"); // (2)!
            } else {
                quotes.add(new Quote(call.backend(), (Long) call.result().get("premium")));
                latest = Math.max(latest, call.latencyMs());
            }
        }
        boolean anyMissing = !missing.isEmpty();
        quotes.sort(Comparator.comparingLong(Quote::premiumPaise));
        return new Page(quotes, missing, anyMissing ? budgetMs : latest); // (3)!
    }
}
    1. A failing backend becomes a missing section, not a failed page.
    2. A backend slower than the budget is cut off (completeOnTimeout / orTimeout in real code).
    3. The response time is bounded by the budget whenever anything is missing.
    package com.handbook.microservices.aggregation.budget;

import com.handbook.microservices.aggregation.budget.QuoteAggregator.Page;
import com.handbook.microservices.aggregation.core.SimCall;

import java.util.List;
import java.util.Map;

public class QuotesDemo {

    public static void main(String[] args) {
        System.out.println("=== Insurance: Car Insurance Quotes from 5 Insurers within 800 ms ===");
        List<SimCall> insurers = List.of(
                SimCall.ok("Suraksha General", 220, Map.of("premium", 1_245_000L)),
                SimCall.ok("Bharat Shield", 640, Map.of("premium", 1_189_900L)),
                SimCall.ok("Kavach Insure", 1_900, Map.of("premium", 1_099_000L)), // slow partner API
                SimCall.failing("Monsoon Mutual", 150),
                SimCall.ok("Raksha Direct", 410, Map.of("premium", 1_310_500L)));
        Page page = new QuoteAggregator(800).aggregate(insurers);
        page.quotes().forEach(q -> System.out.printf("  %-17s INR %,d%n", q.insurer(), q.premiumPaise() / 100));
        System.out.println("Missing: " + page.missing());
        System.out.println("Page returned at " + page.respondedAtMs() + " ms with partial results, instead of waiting 1,900 ms or failing.");
    }
}

    Output:

    === Insurance: Car Insurance Quotes from 5 Insurers within 800 ms ===
  Bharat Shield     INR 11,899
  Suraksha General  INR 12,450
  Raksha Direct     INR 13,105
Missing: [Kavach Insure (timed out at 800 ms), Monsoon Mutual (error)]
Page returned at 800 ms with partial results, instead of waiting 1,900 ms or failing.

    Why a budget here:

    • The page's latency is decided by product, not by the slowest partner.
    • Partial results are better than no results for comparison shopping.
    • The "missing" list can drive a "more quotes loading" refresh or partner SLAs.

    package com.handbook.microservices;

import com.handbook.microservices.aggregation.budget.QuoteAggregator;
import com.handbook.microservices.aggregation.core.SimCall;
import com.handbook.microservices.aggregation.dag.DependencyAggregator;
import com.handbook.microservices.aggregation.dag.DependencyAggregator.Step;
import com.handbook.microservices.aggregation.fields.FieldDrivenAggregator;
import org.junit.jupiter.api.Test;

import java.util.List;
import java.util.Map;

import static org.assertj.core.api.Assertions.assertThat;

class GatewayAggregationTest {

    @Test
    void onlyBackendsOwningRequestedFieldsAreCalled() {
        FieldDrivenAggregator a = new FieldDrivenAggregator(Map.of("x", "A", "y", "B"),
                Map.of("A", SimCall.ok("A", 10, Map.of("x", 1)), "B", SimCall.ok("B", 99, Map.of("y", 2))));
        var r = a.query(List.of("x"));
        assertThat(r.backendsCalled()).containsExactly("A");
        assertThat(r.latencyMs()).isEqualTo(10);
    }

    @Test
    void slowAndFailingBackendsBecomeMissingNotErrors() {
        var page = new QuoteAggregator(100).aggregate(List.of(
                SimCall.ok("fast", 50, Map.of("premium", 10L)),
                SimCall.ok("slow", 500, Map.of("premium", 5L)),
                SimCall.failing("broken", 10)));
        assertThat(page.quotes()).extracting(QuoteAggregator.Quote::insurer).containsExactly("fast");
        assertThat(page.missing()).hasSize(2);
    }

    @Test
    void criticalPathDeterminesLatency() {
        var finish = DependencyAggregator.schedule(List.of(new Step("a", 10, List.of()), new Step("b", 5, List.of()),
                new Step("c", 7, List.of("a", "b"))));
        assertThat(finish.get("c")).isEqualTo(17);
    }
}

    6. Variations & Modern Java Take¶

    var flights = supplyAsync(() -> flightsClient.status(tripId), vthreads).completeOnTimeout(Flight.UNKNOWN, 300, MILLISECONDS);
var hotels  = supplyAsync(() -> hotelsClient.booking(tripId), vthreads).completeOnTimeout(Hotel.UNKNOWN, 300, MILLISECONDS);
var cabs    = supplyAsync(() -> cabsClient.pickup(tripId), vthreads).exceptionally(e -> Cab.TO_BE_CONFIRMED);
return CompletableFuture.allOf(flights, hotels, cabs)
        .thenApply(v -> new Itinerary(flights.join(), hotels.join(), cabs.join()));

    @QueryMapping Product product(@Argument String id) { return catalog.product(id); }
@SchemaMapping Rating rating(Product p) { return reviews.rating(p.id()); }   // called only if the query asks for rating
@BatchMapping Map<Product, Stock> stock(List<Product> ps) { return inventory.stockFor(ps); }   // avoids N+1
    Variation Notes
    Hand-written aggregator A BFF or gateway endpoint with CompletableFuture/virtual threads; full control
    GraphQL / federation Clients choose fields; resolvers fan out; @BatchMapping/DataLoader batch per request
    Declarative gateways KrakenD, Kong/Apigee policies, Spring Cloud Gateway with custom filters
    Structured concurrency StructuredTaskScope (preview in Java 21–25) gives clean cancellation of sibling calls
    Hedged requests Send a duplicate request to another replica if the first exceeds p95, to cut tail latency (idempotent reads only)

    7. Where It Lives in Real Frameworks¶

    Where Aggregation
    Spring Spring for GraphQL (@SchemaMapping, @BatchMapping), Spring Cloud Gateway custom filters, WebFlux Mono.zip
    GraphQL ecosystem Apollo Federation, Netflix DGS, DataLoader
    API gateways KrakenD (merging backends), Kong and Apigee policies, AWS AppSync

    8. Pros, Cons & Trade-offs¶

    ✅ Pros ❌ Cons
    One round trip for the client: lower latency, less battery The aggregator is a new hop and a potential bottleneck
    Centralised fan-out, timeouts and fallbacks Couples the aggregator to many backends' APIs
    Partial results instead of all-or-nothing Risk of business logic creeping into the gateway
    Hides internal service boundaries from public APIs Harder to cache than single-resource endpoints

    9. Pitfalls & Anti-Patterns¶

    Sequential calls in the aggregator

    Calling backends one after another just moves the latency problem to the server. Parallelize everything that doesn't depend on something else (coding challenge).

    No per-call timeouts

    Without timeouts, the slowest backend sets the page's latency, and a hung backend exhausts the aggregator's threads.

    Business rules in the gateway

    Discount calculation or eligibility checks in aggregation code create a hidden monolith. Push rules into the owning service.

    N+1 fan-out

    Fetching ratings for 50 products with 50 calls. Use batch endpoints (@BatchMapping, DataLoader).

    10. Senior / Architect Deep Dive (10–15 yrs)¶

    Latency math. Parallel latency ≈ max(calls); with dependencies it's the critical path. Tail latency compounds: if each of 5 backends has a 1% chance of a 1-second response, the aggregate is slow ~5% of the time. Budgets, hedging and optional sections keep the tail under control.

    Failure semantics are a product decision. For each section: required (fail the page), optional (omit with a marker), or stale-acceptable (serve cached). Write it down per endpoint and test each degraded mode.

    Ownership. If one team owns a generic aggregation gateway for everyone, it becomes a bottleneck for every client change. Prefer BFFs owned by client teams, or GraphQL federation where each domain team owns its part of the schema.

    War story: the home screen that waited for recommendations

    A grocery app's home endpoint aggregated banners, orders, offers and recommendations, with no per-call timeouts. When the recommendations service degraded to 4-second responses, the whole home screen took 4 seconds; app-open conversion dropped 22% in an hour. Fix: 250 ms timeouts per optional section, recommendations made optional with a cached fallback, and a 600 ms overall budget. Lesson: an aggregator is only as fast as its slowest required dependency, so make most dependencies optional.

    12. Interview Corner¶

    Q1. What is gateway aggregation?

    The gateway combines several backend calls into one client request and returns a merged response.

    Q2. Why is it useful for mobile apps?

    Fewer round trips over slow networks: faster screens and less battery use.

    Q3. Should calls be sequential or parallel?

    Parallel, unless one call needs another's result.

    Q4. What happens if one backend fails?

    Return the rest with that section missing or defaulted, if it's optional.

    Q5. Gateway aggregation vs BFF?

    The BFF is one way to implement it: an aggregating backend owned by and tailored to one client type.

    Q1. How do you implement timeouts per call in Java?

    CompletableFuture.orTimeout or completeOnTimeout with a fallback value; or client-level timeouts.

    Q2. How does GraphQL relate?

    Clients choose fields; resolvers fetch only what's needed, which is field-driven aggregation.

    Q3. How do you avoid N+1 calls?

    Batch endpoints and DataLoader/@BatchMapping.

    Q4. How do you cache aggregated responses?

    Cache per section (each backend's piece) rather than the whole response, or cache only optional sections.

    Q5. How do you test degraded modes?

    Contract tests per backend and tests that inject timeouts/errors for each section.

    Q1. "Design the home-screen API for 20M daily users."

    BFF per platform; parallel fan-out with per-section timeouts; optional sections with cached fallbacks; overall budget; per-section metrics; CDN for static banners.

    Q2. "How do you reduce tail latency?"

    Budgets, hedged requests for idempotent reads, optional sections, caching, and removing the slowest dependency from the critical path.

    Q3. "Aggregation vs precomputed read models?"

    Aggregate live for freshness and low volume; precompute (materialized views) when the same composition is read very often or must survive backend outages.

    Q4. "Who owns aggregation code?"

    Client-facing teams (BFF) or domain teams via federated GraphQL subgraphs; avoid a central team bottleneck.

    Q5. "How do you stop the aggregator becoming a monolith?"

    No business rules, thin mapping only, contract tests, ownership per client, and moving shared logic into domain services.

    Problem: The order-details page needs order, customer, shipment (needs order), products (needs order), driver (needs shipment) and refundRules (needs products and customer). Compute the fastest possible completion time if independent calls run in parallel.

    Solution 
    package com.handbook.microservices.aggregation.dag;

import java.util.LinkedHashMap;
import java.util.List;
import java.util.Map;

/** Coding challenge: some calls need another call's output. Run each call as soon as its inputs are ready. */
public final class DependencyAggregator {

    public record Step(String name, long latencyMs, List<String> dependsOn) { }

    /** @return finish time (virtual ms) of each step when independent steps run in parallel. */
    public static Map<String, Long> schedule(List<Step> steps) {
        Map<String, Long> finish = new LinkedHashMap<>();
        for (Step s : steps) { // steps are listed in a valid (topological) order
            long start = s.dependsOn().stream().mapToLong(finish::get).max().orElse(0);
            finish.put(s.name(), start + s.latencyMs());
        }
        return finish;
    }

    public static long sequential(List<Step> steps) {
        return steps.stream().mapToLong(Step::latencyMs).sum();
    }
}

    package com.handbook.microservices.aggregation.dag;

import com.handbook.microservices.aggregation.dag.DependencyAggregator.Step;

import java.util.List;
import java.util.Map;

public class OrderPageDagDemo {

    public static void main(String[] args) {
        System.out.println("=== Challenge: Order-Details Page with Dependent Calls ===");
        List<Step> steps = List.of(
                new Step("order", 50, List.of()),
                new Step("customer", 40, List.of()),
                new Step("shipment", 80, List.of("order")),     // needs order.shipmentId
                new Step("products", 60, List.of("order")),     // needs order.skus
                new Step("driver", 30, List.of("shipment")),    // needs shipment.driverId
                new Step("refundRules", 20, List.of("products", "customer")));
        Map<String, Long> finish = DependencyAggregator.schedule(steps);
        finish.forEach((name, t) -> System.out.println("  " + name + " done at " + t + " ms"));
        System.out.println("Parallel where possible: " + finish.values().stream().mapToLong(Long::longValue).max().orElseThrow()
                + " ms; one call after another: " + DependencyAggregator.sequential(steps) + " ms");
    }
}

    Key points to say: each call starts when its last dependency finishes; total latency is the critical path (order → shipment → driver = 160 ms), not the sum (280 ms). In code: thenCompose for dependent calls, allOf/thenCombine for independent ones.

    13. Quick Revision Card¶

    Remember in 30 seconds

    • One client request → parallel fan-out → merged response.
    • Latency = slowest call (or critical path), so parallelize and add timeouts.
    • Overall budget + optional sections = partial results, not failures.
    • Field-driven fan-out avoids over-fetching; batch to avoid N+1.
    • Composition only: no business rules.
    allOf(a, b, c).thenApply(v -> merge(a.join(), b.join(), c.join()));
