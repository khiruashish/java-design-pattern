    Health Check (Liveness & Readiness)¶

    🟢 Beginner → 🟡 Intermediate Microservices Interview frequency ⭐⭐⭐⭐⭐

    TL;DR

    A service exposes health endpoints that the platform polls: liveness ("is this process broken and needs a restart?") and readiness ("can it take traffic right now?"). Load balancers route only to ready instances; orchestrators restart only non-live ones. Every service needs both, and they must check different things: dependencies belong in readiness, never in liveness.

    See It in Motion¶

    Press Play to watch the calls travel between components, or step through with Next and Back. Switch to Without it to see what goes wrong without the pattern. Open the full explorer

    1. Intent & Problem It Solves¶

    The problem in plain English: a pod is "running" but its thread pool is deadlocked, so it returns nothing and the load balancer keeps sending it customers. Another pod is still warming its cache and gets traffic too early, timing out the first thousand requests. And when the database blips, a naïve health check makes Kubernetes restart every pod at once, turning a 1-minute blip into a 5-minute outage.

    Definition (microservices.io, Health Check API):

    A service has a health check API endpoint (e.g. /health) that returns the health of the service. A monitoring service, service registry or load balancer periodically invokes the endpoint to check the instance and route requests accordingly.

    Probe Question Failure means Typical checks
    Liveness Is the process alive and making progress? Restart the container Event loop / thread pool responsive, no deadlock
    Readiness Should this instance receive traffic now? Stop routing to it (no restart) Started, caches warm, critical dependencies reachable, not overloaded
    Startup Has it finished starting? Keep waiting (don't run liveness yet) Initialization done

    2. Real-World Analogy¶

    A shop's lights and its OPEN sign

    The lights being on tells you someone's inside (liveness). The OPEN sign tells you they're ready to serve (readiness). During stock-taking, the lights stay on but the sign is flipped to CLOSED; nobody calls an ambulance just because the shop is closed for an hour. If the shopkeeper collapses (deadlock), that's when you call for help (restart).

    3. Structure¶

    flowchart LR K[kubelet] -->|"/actuator/health/liveness"| P[Pod] K -->|"/actuator/health/readiness"| P LB[Service / load balancer] -.->|"routes only if ready"| P P --> D1[(Database)] P --> D2[Cache] P --> D3[Optional: recommendations] K -->|"liveness failed N times"| R[Restart container]
    Participant Responsibility
    Health indicators One per component (DB, cache, broker, disk), each UP/DOWN with details
    Health groups Liveness and readiness are different groups of indicators
    Prober kubelet, load balancer, service registry, monitoring
    Policy Thresholds, periods, timeouts; what to do on failure (restart vs remove from rotation)

    4. Naive Approach (Without the Pattern)¶

    @GetMapping("/health")
public String health() {
    jdbcTemplate.queryForObject("SELECT 1", Integer.class);   // used for BOTH liveness and readiness
    restTemplate.getForObject("http://recommendations/health", String.class);  // optional dependency
    return "OK";
}
    • A database blip fails liveness → every pod restarts → cold caches → longer outage.
    • An optional dependency makes the whole service "unhealthy".
    • Every probe from every prober hits the database.

    5. Three Real-World Examples¶

    Example 1: Liveness vs Readiness Through a Pod's Life (Grocery)¶

    Scenario: The grocery catalog service warms an in-memory cache of 200,000 SKUs for 40 seconds at startup. Later, the database fails over for 30 seconds. Later still, a bug deadlocks its worker pool. The probes must keep the cold pod out of rotation, keep pods alive (but out of rotation) during the failover, and restart only the deadlocked pod.

    Design:

    stateDiagram-v2 [*] --> Starting: container starts Starting --> Serving: cache warm (ready=200) Serving --> OutOfRotation: DB failover (ready=503, live=200) OutOfRotation --> Serving: DB back Serving --> Restarting: deadlock (live=503) Restarting --> Starting

    Full Code:

    package com.handbook.microservices.healthcheck.probes;

import java.util.function.BooleanSupplier;

/** Liveness: "am I broken beyond repair?" Readiness: "can I serve traffic right now?" They answer different questions. */
public final class GroceryProbes {

    private final BooleanSupplier eventLoopResponsive;
    private final BooleanSupplier databaseReachable;
    private final BooleanSupplier catalogCacheWarm;

    public GroceryProbes(BooleanSupplier eventLoopResponsive, BooleanSupplier databaseReachable, BooleanSupplier catalogCacheWarm) {
        this.eventLoopResponsive = eventLoopResponsive;
        this.databaseReachable = databaseReachable;
        this.catalogCacheWarm = catalogCacheWarm;
    }

    public int liveness() { // (1)!
        return eventLoopResponsive.getAsBoolean() ? 200 : 503;
    }

    public int readiness() { // (2)!
        return eventLoopResponsive.getAsBoolean() && databaseReachable.getAsBoolean() && catalogCacheWarm.getAsBoolean() ? 200 : 503;
    }

    /** What the platform does with the two answers. */
    public static String kubernetesAction(int liveness, int readiness) {
        if (liveness != 200) {
            return "RESTART container";
        }
        return readiness == 200 ? "send traffic" : "remove from Service endpoints (no restart)";
    }
}
    1. Liveness checks only the process itself. A restart can fix a deadlock; it can't fix the database.
    2. Readiness includes dependencies and warm-up, because those decide whether this instance should get requests now.
    package com.handbook.microservices.healthcheck.probes;

public class ProbesDemo {

    public static void main(String[] args) {
        System.out.println("=== Grocery: Liveness vs Readiness Through a Pod's Life ===");
        boolean[] loop = {true};
        boolean[] db = {true};
        boolean[] cache = {false};
        GroceryProbes probes = new GroceryProbes(() -> loop[0], () -> db[0], () -> cache[0]);

        String[] phases = {"starting, cache cold", "cache warmed", "database failover (30s)", "database back", "thread deadlock"};
        for (String phase : phases) {
            switch (phase) {
                case "cache warmed" -> cache[0] = true;
                case "database failover (30s)" -> db[0] = false;
                case "database back" -> db[0] = true;
                case "thread deadlock" -> loop[0] = false;
                default -> { }
            }
            int live = probes.liveness();
            int ready = probes.readiness();
            System.out.printf("%-24s live=%d ready=%d -> %s%n", phase, live, ready, GroceryProbes.kubernetesAction(live, ready));
        }
    }
}

    Output:

    === Grocery: Liveness vs Readiness Through a Pod's Life ===
starting, cache cold     live=200 ready=503 -> remove from Service endpoints (no restart)
cache warmed             live=200 ready=200 -> send traffic
database failover (30s)  live=200 ready=503 -> remove from Service endpoints (no restart)
database back            live=200 ready=200 -> send traffic
thread deadlock          live=503 ready=503 -> RESTART container

    Why two probes here:

    • Cold pods never get traffic; they join only when ready.
    • Dependency problems remove pods from rotation without restarting them.
    • Genuine process failures still get the restart they need.

    Example 2: Composite Health by Criticality (Payments)¶

    Scenario: A payment service depends on its ledger database and primary PSP (critical), plus a fraud-scoring service and an email-receipt service (optional, with fallbacks: rule-based fraud checks, receipts queued for later). The health endpoint must report DEGRADED when an optional dependency fails (still serving, but page the on-call) and DOWN only when a critical one fails.

    Design:

    flowchart TB H["/health → overall status"] --> L["ledgerDb (critical)"] H --> P["primaryPsp (critical)"] H --> F["fraudScoring (optional)"] H --> E["emailReceipts (optional)"] L & P -->|any DOWN| D[DOWN: stop traffic] F & E -->|any DOWN| G[DEGRADED: serve + alert]

    Full Code:

    package com.handbook.microservices.healthcheck.composite;

import java.util.LinkedHashMap;
import java.util.List;
import java.util.Map;

/** Aggregate component health by criticality: a broken optional dependency degrades, a broken critical one is DOWN. */
public final class CompositeHealth {

    public enum Status { UP, DEGRADED, DOWN }

    public record Component(String name, boolean critical, boolean healthy) { }

    public record Report(Status status, Map<String, String> details) { }

    public static Report evaluate(List<Component> components) {
        Map<String, String> details = new LinkedHashMap<>();
        Status overall = Status.UP;
        for (Component c : components) {
            details.put(c.name(), c.healthy() ? "UP" : "DOWN" + (c.critical() ? "" : " (optional)"));
            if (!c.healthy() && c.critical()) {
                overall = Status.DOWN; // (1)!
            } else if (!c.healthy() && overall == Status.UP) {
                overall = Status.DEGRADED; // (2)!
            }
        }
        return new Report(overall, details);
    }
}
    1. Any critical component down makes the service DOWN (not ready).
    2. An optional component down only degrades it: the service keeps serving with a fallback.
    package com.handbook.microservices.healthcheck.composite;

import com.handbook.microservices.healthcheck.composite.CompositeHealth.Component;
import com.handbook.microservices.healthcheck.composite.CompositeHealth.Report;

import java.util.List;

public class PaymentsHealthDemo {

    public static void main(String[] args) {
        System.out.println("=== Payments: One Health Endpoint, Components with Different Criticality ===");
        print("Normal day", List.of(new Component("ledgerDb", true, true), new Component("primaryPsp", true, true),
                new Component("fraudScoring", false, true), new Component("emailReceipts", false, true)));
        print("Fraud scorer down", List.of(new Component("ledgerDb", true, true), new Component("primaryPsp", true, true),
                new Component("fraudScoring", false, false), new Component("emailReceipts", false, true)));
        print("Ledger DB down", List.of(new Component("ledgerDb", true, false), new Component("primaryPsp", true, true),
                new Component("fraudScoring", false, true), new Component("emailReceipts", false, false)));
        System.out.println("DEGRADED stays ready (fallback: rule-based fraud check) but pages the on-call; DOWN stops traffic.");
    }

    private static void print(String scenario, List<Component> components) {
        Report r = CompositeHealth.evaluate(components);
        System.out.printf("%-18s -> %-8s %s%n", scenario, r.status(), r.details());
    }
}

    Output:

    === Payments: One Health Endpoint, Components with Different Criticality ===
Normal day         -> UP       {ledgerDb=UP, primaryPsp=UP, fraudScoring=UP, emailReceipts=UP}
Fraud scorer down  -> DEGRADED {ledgerDb=UP, primaryPsp=UP, fraudScoring=DOWN (optional), emailReceipts=UP}
Ledger DB down     -> DOWN     {ledgerDb=DOWN, primaryPsp=UP, fraudScoring=UP, emailReceipts=DOWN (optional)}
DEGRADED stays ready (fallback: rule-based fraud check) but pages the on-call; DOWN stops traffic.

    Why composite health here:

    • Health reflects business impact, not just "is everything green".
    • Optional failures don't take payments offline.
    • Details per component speed up diagnosis (but restrict them to internal callers).

    Example 3: Cached Deep Checks (Streaming)¶

    Scenario: A streaming catalog service runs 200 pods. Five probers (kubelet, load balancer, mesh, two monitors) hit each pod every second. If every probe ran SELECT 1 against the catalog database, that's 60,000 extra queries a minute just for health. The deep check runs at most once every 10 seconds per pod; probes read the cached result.

    Design:

    sequenceDiagram autonumber participant Pr as 5 probers (every 1s) participant C as CachedHealthCheck participant DB as Catalog DB Pr->>C: healthy? C->>DB: SELECT 1 (only if last check > 10 s ago) DB-->>C: ok C-->>Pr: cached result Pr->>C: healthy? (×49 more within 10 s) C-->>Pr: cached result (no DB call)

    Full Code:

    package com.handbook.microservices.healthcheck.cached;

import java.time.Clock;
import java.time.Duration;
import java.time.Instant;
import java.util.function.BooleanSupplier;

/** Run the expensive dependency check at most once per interval; probes read the cached result. */
public final class CachedHealthCheck {

    private final BooleanSupplier expensiveCheck;
    private final Clock clock;
    private final Duration interval;
    private Instant checkedAt = Instant.MIN;
    private boolean lastResult;
    private int executions;

    public CachedHealthCheck(BooleanSupplier expensiveCheck, Clock clock, Duration interval) {
        this.expensiveCheck = expensiveCheck;
        this.clock = clock;
        this.interval = interval;
    }

    public synchronized boolean healthy() {
        Instant now = clock.instant();
        if (checkedAt == Instant.MIN || !now.isBefore(checkedAt.plus(interval))) { // (1)!
            lastResult = expensiveCheck.getAsBoolean();
            checkedAt = now;
            executions++;
        }
        return lastResult;
    }

    public int executions() {
        return executions;
    }
}
    1. The expensive check runs only when the cached result is older than the interval; probes always get an instant answer.
    package com.handbook.microservices.healthcheck.cached;

import com.handbook.microservices.support.FakeClock;

import java.time.Duration;

public class CachedHealthDemo {

    public static void main(String[] args) {
        System.out.println("=== Streaming: Probes Every Second, Database Checked Every 10 Seconds ===");
        FakeClock clock = FakeClock.at("2026-11-01T20:00:00Z");
        int[] dbQueries = {0};
        CachedHealthCheck check = new CachedHealthCheck(() -> {
            dbQueries[0]++;
            return true; // SELECT 1 against the catalog DB
        }, clock, Duration.ofSeconds(10));

        int probes = 0;
        for (int second = 0; second < 60; second++) {
            for (int source = 0; source < 5; source++) { // kubelet + load balancer + mesh + 2 monitors
                check.healthy();
                probes++;
            }
            clock.advance(Duration.ofSeconds(1));
        }
        System.out.println("Health probes in one minute: " + probes);
        System.out.println("Queries the database actually received: " + dbQueries[0]);
        System.out.println("Across 200 pods: " + probes * 200 + " probes -> " + dbQueries[0] * 200 + " DB queries per minute");
    }
}

    Output:

    === Streaming: Probes Every Second, Database Checked Every 10 Seconds ===
Health probes in one minute: 300
Queries the database actually received: 6
Across 200 pods: 60000 probes -> 1200 DB queries per minute

    Why caching here:

    • Health checks must never become a load problem for the dependencies they check.
    • Probe responses stay fast (well under the probe timeout).
    • In production, run the check on a background schedule and have probes only read the result.
    Unit Tests: HealthCheckTest.java 
    package com.handbook.microservices;

import com.handbook.microservices.healthcheck.cached.CachedHealthCheck;
import com.handbook.microservices.healthcheck.composite.CompositeHealth;
import com.handbook.microservices.healthcheck.composite.CompositeHealth.Component;
import com.handbook.microservices.healthcheck.composite.CompositeHealth.Status;
import com.handbook.microservices.healthcheck.probes.GroceryProbes;
import com.handbook.microservices.support.FakeClock;
import org.junit.jupiter.api.Test;

import java.time.Duration;
import java.util.List;

import static org.assertj.core.api.Assertions.assertThat;

class HealthCheckTest {

    @Test
    void databaseOutageAffectsReadinessOnly() {
        GroceryProbes p = new GroceryProbes(() -> true, () -> false, () -> true);
        assertThat(p.liveness()).isEqualTo(200);
        assertThat(p.readiness()).isEqualTo(503);
    }

    @Test
    void optionalFailureDegradesCriticalFailureIsDown() {
        assertThat(CompositeHealth.evaluate(List.of(new Component("a", true, true), new Component("b", false, false))).status())
                .isEqualTo(Status.DEGRADED);
        assertThat(CompositeHealth.evaluate(List.of(new Component("a", true, false), new Component("b", false, true))).status())
                .isEqualTo(Status.DOWN);
    }

    @Test
    void expensiveCheckRunsOncePerInterval() {
        FakeClock clock = FakeClock.at("2026-01-01T00:00:00Z");
        CachedHealthCheck c = new CachedHealthCheck(() -> true, clock, Duration.ofSeconds(10));
        c.healthy();
        clock.advance(Duration.ofSeconds(9));
        c.healthy();
        clock.advance(Duration.ofSeconds(1));
        c.healthy();
        assertThat(c.executions()).isEqualTo(2);
    }
}

    6. Variations & Modern Java Take¶

    management:
  endpoint:
    health:
      probes.enabled: true            # /actuator/health/liveness and /readiness
      show-details: when-authorized

    Variation Notes
    Custom HealthIndicator @Component class PspHealth implements HealthIndicator { Health health() { ... } }
    Availability state AvailabilityChangeEvent.publish(ctx, ReadinessState.REFUSING_TRAFFIC) during shutdown or maintenance
    Graceful shutdown server.shutdown=graceful: readiness goes down first, in-flight requests finish
    gRPC health protocol grpc.health.v1.Health/Check, supported by Kubernetes grpc probes
    Synthetic checks External probes that run a real user journey (search → add to cart)

    Where Health checks

    8. Pros, Cons & Trade-offs¶

    ✅ Pros ❌ Cons
    Automatic recovery from stuck processes Wrong probe design causes restart storms
    Traffic only reaches instances that can serve it Probes add load if they do deep checks
    Zero-downtime deploys and graceful shutdown Health "green" doesn't guarantee correct behaviour
    Clear operational signal per component Details endpoints can leak internals if exposed publicly

    9. Pitfalls & Anti-Patterns¶

    Dependencies in liveness

    If the database is down, restarting every pod can't fix it; it just adds cold starts, connection storms and longer recovery (coding challenge). Put dependencies in readiness.

    Shared dependency failing every pod's readiness

    If all pods depend on the same database, readiness also drops all of them, and the service returns load-balancer errors instead of graceful ones. For a shared hard dependency, consider staying ready and serving a degraded response or fast 503s with a clear message.

    No startup probe for slow starters

    Without one, liveness kills slow-starting JVMs before they finish booting: crash loop.

    Exposing health details publicly

    show-details: always on a public endpoint reveals versions, hosts and dependency names. Restrict details to authenticated or internal callers.

    10. Senior / Architect Deep Dive (10–15 yrs)¶

    Readiness is a load-shedding tool. Failing readiness under overload (queue too deep, latency too high) moves traffic to healthier pods. But if every pod reaches the same state, readiness empties the pool: combine it with backpressure and autoscaling instead of relying on it alone.

    Liveness should be boring. The most useful liveness checks detect conditions only a restart fixes: deadlocked worker pools, a stuck event loop, an exhausted heap that GC can't recover. If you can't name such a condition, a basic "process responds" check is enough.

    Health ≠ correctness. A service can be green and serving wrong prices. Pair probes with SLO-based alerting on real traffic (error rate, latency, business KPIs) and synthetic journeys.

    War story: the database blip that became a 12-minute outage

    A payments platform's liveness probe ran SELECT 1. A 70-second database failover failed liveness on all 60 pods; Kubernetes restarted them together. Each JVM took 50 seconds to start and then opened 40 connections at once, overloading the freshly promoted database. Pods failed liveness again. The cycle lasted 12 minutes. Fix: liveness = process only; readiness = DB + PSP; a startup probe for the JVM boot; connection-pool warm-up with jitter. Lesson: restarts fix processes, not dependencies.

    Health Check Circuit Breaker Service Discovery Distributed Tracing

    12. Interview Corner¶

    Q1. What is a health check?

    An endpoint that reports whether a service instance is healthy, polled by load balancers and orchestrators.

    Q2. Liveness vs readiness?

    Liveness: should the process be restarted? Readiness: should it receive traffic now?

    Q3. What does Spring Boot provide?

    Actuator's /actuator/health with liveness and readiness groups and built-in indicators (DB, Redis, Kafka, disk).

    Q4. What happens when readiness fails in Kubernetes?

    The pod is removed from the Service's endpoints; it is not restarted.

    Q5. What is a startup probe?

    A probe that gives slow-starting apps time to boot before liveness checks begin.

    Q1. Why not check the database in liveness?

    A DB outage would restart every pod, which can't fix the DB and slows recovery.

    Q2. How do you write a custom health indicator?

    Implement HealthIndicator (or ReactiveHealthIndicator) and return Health.up()/down().withDetail(...).

    Q3. How does readiness support graceful shutdown?

    On SIGTERM, readiness flips to refusing traffic, the load balancer drains the pod, then in-flight requests finish.

    Q4. How do you avoid probes overloading dependencies?

    Cache deep checks, run them on a schedule, and keep probes cheap.

    Q5. What's DEGRADED?

    A status meaning the service works but with reduced functionality (an optional dependency is down).

    Q1. "Design health checks for a service with one critical shared database."

    Liveness = process only; readiness = warm-up + DB with a short cached check; on DB outage, consider staying ready and failing fast with explicit errors so the platform doesn't empty the pool; alert on SLOs.

    Q2. "Probes passed but customers saw errors. Why?"

    Health checks test the wrong thing (shallow), or a dependency path not covered; add SLO alerts and synthetic journeys.

    Q3. "How do health checks interact with autoscaling and rollouts?"

    Rollouts wait for readiness before shifting traffic; autoscaling should use load metrics, not health.

    Q4. "Passive vs active health checking?"

    Active = probes; passive = observing real traffic (Envoy outlier detection ejecting hosts with 5xx bursts). Use both.

    Q5. "What should never be in a health endpoint?"

    Expensive queries, calls to optional services in liveness, secrets or sensitive details on public routes.

    Problem: Simulate 20 pods, a 45-second startup and a liveness probe (every 10 s, 3 failures to restart) during a 100-second database outage. Compare putting the database check in liveness vs readiness.

    Solution 
    package com.handbook.microservices.healthcheck.storm;

/** Coding challenge: put the database in the LIVENESS probe and watch a 100s outage become a restart storm. */
public class RestartStormDemo {

    static final int PODS = 20;
    static final int STARTUP_SECONDS = 45; // JVM start + cache warm-up
    static final int FAILURE_THRESHOLD = 3; // probe every 10s, restart after 3 failures

    static String simulate(boolean databaseInLiveness) {
        int restarts = 0;
        int servingAtT120 = 0;
        int[] restartedAt = new int[PODS];
        java.util.Arrays.fill(restartedAt, -1_000);
        int[] failures = new int[PODS];
        for (int t = 0; t <= 120; t += 10) {
            boolean dbUp = t < 10 || t >= 110; // outage from t=10s to t=110s
            for (int p = 0; p < PODS; p++) {
                boolean starting = t - restartedAt[p] < STARTUP_SECONDS;
                boolean liveFails = databaseInLiveness && !dbUp;
                if (starting) {
                    continue;
                }
                failures[p] = liveFails ? failures[p] + 1 : 0;
                if (failures[p] >= FAILURE_THRESHOLD) {
                    restarts++;
                    restartedAt[p] = t;
                    failures[p] = 0;
                }
            }
        }
        for (int p = 0; p < PODS; p++) {
            if (120 - restartedAt[p] >= STARTUP_SECONDS) {
                servingAtT120++;
            }
        }
        return "restarts=" + restarts + ", pods able to serve at t=120s (DB back since t=110s): " + servingAtT120 + "/" + PODS;
    }

    public static void main(String[] args) {
        System.out.println("=== Challenge: The Database Belongs in Readiness, Not Liveness ===");
        System.out.println("DB in liveness : " + simulate(true));
        System.out.println("DB in readiness: " + simulate(false));
        System.out.println("Restarting can't fix a dependency; it only adds cold starts when the dependency returns.");
    }
}

    Output:

    === Challenge: The Database Belongs in Readiness, Not Liveness ===
DB in liveness : restarts=40, pods able to serve at t=120s (DB back since t=110s): 0/20
DB in readiness: restarts=0, pods able to serve at t=120s (DB back since t=110s): 20/20
Restarting can't fix a dependency; it only adds cold starts when the dependency returns.

    Key points to say: with the DB in liveness, every pod restarts, twice, and when the database comes back no pod can serve because they're all still booting. With the DB only in readiness, pods stay warm and serve as soon as the database returns.

    Behavioural tie-in (STAR) for experienced candidates

    • S: A 70-second DB failover turned into a 12-minute outage because liveness checked the database.
    • T: Make dependency failures recover as fast as the dependency.
    • A: Split probes (liveness = process, readiness = DB/PSP with cached checks), added startup probes and graceful shutdown, and jittered connection-pool warm-up.
    • R: The next failover caused 75 seconds of degraded service and zero restarts.

    13. Quick Revision Card¶

    Remember in 30 seconds

    • Liveness → restart; readiness → stop traffic; startup → wait.
    • Dependencies in readiness, never liveness.
    • Critical vs optional: DOWN vs DEGRADED.
    • Cache deep checks; keep probes cheap and fast.
    • Green health ≠ correct: also alert on SLOs.
