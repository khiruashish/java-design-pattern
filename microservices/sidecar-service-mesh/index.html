    Advanced Microservices Platform

    Sidecar & Service Mesh¶

    🔴 Advanced Microservices Interview frequency ⭐⭐⭐⭐

    TL;DR

    A sidecar is a helper process deployed next to each service instance (same pod), adding capabilities such as mTLS, retries, metrics and tracing without changing the service's code. A service mesh is a fleet of sidecar proxies (the data plane) configured centrally by a control plane. Network concerns move out of every application and library into shared infrastructure.

    1. Intent & Problem It Solves¶

    The problem in plain English: 80 services in Java, Go, Node and one PHP legacy app. Each needs encryption between services (mTLS), "who may call whom" rules, retries, timeouts, canary routing, metrics and tracing. Implementing these in every language's libraries means 4× the work, inconsistent behaviour and painful upgrades across all services. And security teams want guarantees that don't depend on every team getting it right.

    Definitions:

    Sidecar (Azure Architecture Center): Deploy components of an application into a separate process or container to provide isolation and encapsulation.

    Service mesh: A dedicated infrastructure layer for service-to-service communication, made of proxies deployed alongside services (data plane) and a control plane that configures them.

    Plane What it does Examples
    Data plane Proxies intercept all traffic: mTLS, routing, retries, metrics Envoy, linkerd2-proxy, ztunnel
    Control plane Distributes config, certificates, service discovery Istiod, Linkerd control plane, Consul

    2. Real-World Analogy¶

    A motorcycle sidecar, or a diplomat's interpreter

    The rider (your service) focuses on driving. The sidecar carries the extra equipment. A diplomat doesn't learn every language; an interpreter next to them handles communication, checks credentials at the door, and keeps a log, and every diplomat gets one from the same agency (the control plane) with the same rules.

    4. Naive Approach (Without the Pattern)¶

    Java services:    Resilience4j + Spring Security mTLS config + Micrometer + OpenTelemetry agent
Go services:      different retry library, hand-rolled TLS, Prometheus client
Node services:    yet another set; PHP legacy: nothing at all
→ inconsistent retries, some traffic unencrypted, metrics with different names,
  and upgrading the TLS library means 80 pull requests.

    5. Three Real-World Examples¶

    Example 1: Zero-Trust mTLS + Authorization (Grocery payments)¶

    Scenario: Only checkout may create charges on payment-service; reporting may read reports but not charge; a compromised pod without a mesh certificate is rejected. Each sidecar presents its workload's SPIFFE identity outbound and checks the caller's identity inbound. The payment app contains no security code.

    Design:

    sequenceDiagram
    participant C as checkout app
    participant CS as checkout sidecar
    participant PS as payment sidecar
    participant P as payment app
    C->>CS: POST /charges (plain HTTP to localhost)
    CS->>PS: mTLS, identity spiffe://.../sa/checkout
    PS->>PS: policy: /charges allows checkout ✔
    PS->>P: POST /charges

    Full Code:

    package com.handbook.microservices.sidecar.mtls;

import com.handbook.microservices.support.Http.Request;
import com.handbook.microservices.support.Http.Response;

import java.util.Map;
import java.util.Set;
import java.util.function.Function;

/**
 * Runs next to the app (same pod) and intercepts all its traffic. Inbound, it checks the caller's
 * workload identity (from the mTLS certificate, simulated here by a header the mesh sets) against an
 * authorization policy. The app itself contains no security code.
 */
public final class SidecarProxy {

    private final String myIdentity;
    private final Map<String, Set<String>> allowedCallersByPath; // path prefix → SPIFFE IDs
    private final Function<Request, Response> app;

    public SidecarProxy(String myIdentity, Map<String, Set<String>> allowedCallersByPath,
                        Function<Request, Response> app) {
        this.myIdentity = myIdentity;
        this.allowedCallersByPath = allowedCallersByPath;
        this.app = app;
    }

    public Response inbound(Request request) {
        String peer = request.header("x-peer-spiffe-id"); // (1)!
        if (peer == null) {
            return Response.of(403, "rejected: no mTLS client certificate"); // (2)!
        }
        boolean allowed = allowedCallersByPath.entrySet().stream()
                .filter(e -> request.path().startsWith(e.getKey()))
                .anyMatch(e -> e.getValue().contains(peer)); // (3)!
        if (!allowed) {
            return Response.of(403, "RBAC: " + shortName(peer) + " may not call " + request.path());
        }
        return app.apply(request);
    }

    /** Outbound: the sidecar presents this workload's identity to the next hop. */
    public Request outbound(Request request) {
        return request.withHeader("x-peer-spiffe-id", myIdentity);
    }

    private static String shortName(String spiffeId) {
        return spiffeId.substring(spiffeId.lastIndexOf('/') + 1);
    }
}
    1. In a real mesh, identity comes from the peer's mTLS certificate (issued and rotated by the control plane), not from a header; the header stands in for the TLS handshake here.
    2. No certificate means the caller is outside the mesh: reject.
    3. Authorization policy per path, like Istio's AuthorizationPolicy.
    package com.handbook.microservices.sidecar.mtls;

import com.handbook.microservices.support.Http.Request;
import com.handbook.microservices.support.Http.Response;

import java.util.Map;
import java.util.Set;

public class ZeroTrustDemo {

    static final String CHECKOUT = "spiffe://shop.local/ns/prod/sa/checkout";
    static final String REPORTING = "spiffe://shop.local/ns/prod/sa/reporting";
    static final String PAYMENT = "spiffe://shop.local/ns/prod/sa/payment";

    public static void main(String[] args) {
        // The payment app only knows business logic.
        var paymentSidecar = new SidecarProxy(PAYMENT, Map.of(
                "/charges", Set.of(CHECKOUT),
                "/reports", Set.of(REPORTING, CHECKOUT)),
                r -> Response.of(200, "payment-app handled " + r.method() + " " + r.path()));

        var checkoutSidecar = new SidecarProxy(CHECKOUT, Map.of(), r -> Response.of(200, "checkout"));
        var reportingSidecar = new SidecarProxy(REPORTING, Map.of(), r -> Response.of(200, "reporting"));

        System.out.println("=== Grocery: zero-trust calls to payment-service through sidecars ===");
        Request charge = new Request("POST", "/charges", Map.of(), "{order: ORD-1}");
        System.out.println("checkout  -> POST /charges : " + paymentSidecar.inbound(checkoutSidecar.outbound(charge)));
        System.out.println("reporting -> POST /charges : " + paymentSidecar.inbound(reportingSidecar.outbound(charge)));
        System.out.println("reporting -> GET /reports  : "
                + paymentSidecar.inbound(reportingSidecar.outbound(Request.get("/reports/daily", Map.of()))));
        System.out.println("attacker pod (no cert)     : " + paymentSidecar.inbound(charge));
    }
}

    Output:

    === Grocery: zero-trust calls to payment-service through sidecars ===
checkout  -> POST /charges : 200 payment-app handled POST /charges
reporting -> POST /charges : 403 RBAC: reporting may not call /charges
reporting -> GET /reports  : 200 payment-app handled GET /reports/daily
attacker pod (no cert)     : 403 rejected: no mTLS client certificate

    Why a sidecar here:

    • Zero trust: being inside the network isn't enough; every call is authenticated and authorized.
    • Security rules are enforced uniformly, in every language, and audited centrally.
    • Certificates rotate automatically (hours, not years).

    Example 2: Canary Traffic Split + Retries (Streaming)¶

    Scenario: The recommendations team ships v2. The mesh routes 10% of calls to v2, then 50%. v2 fails about 5% of requests; the client sidecar retries once, and most failures disappear (partly by retrying on v1). The calling app just calls "recommendations"; weights and retries are configuration.

    Full Code:

    package com.handbook.microservices.sidecar.traffic;

import java.util.Map;
import java.util.Random;
import java.util.TreeMap;
import java.util.function.Function;

/**
 * The client-side sidecar (Envoy) applies routing rules pushed by the mesh control plane:
 * weighted subsets for canaries, and retries for failed calls. The calling app just calls "recommendations".
 */
public final class TrafficSplitSidecar {

    private final TreeMap<Integer, String> cumulativeWeights = new TreeMap<>();
    private final Map<String, Function<String, String>> subsets;
    private final int retries;
    private final Random random;
    private int total;

    public TrafficSplitSidecar(Map<String, Integer> weights, Map<String, Function<String, String>> subsets,
                               int retries, Random random) {
        weights.forEach((subset, w) -> {
            total += w;
            cumulativeWeights.put(total, subset); // (1)!
        });
        this.subsets = subsets;
        this.retries = retries;
        this.random = random;
    }

    public String call(String request) {
        RuntimeException last = null;
        for (int attempt = 0; attempt <= retries; attempt++) { // (2)!
            String subset = cumulativeWeights.higherEntry(random.nextInt(total)).getValue();
            try {
                return subsets.get(subset).apply(request);
            } catch (RuntimeException e) {
                last = e;
            }
        }
        throw last;
    }
}
    1. Weighted subsets, as in Istio VirtualService route weights. Seeded random keeps the demo reproducible.
    2. Retries in the proxy. Configure them for idempotent requests only, with a retry budget.
    package com.handbook.microservices.sidecar.traffic;

import java.util.LinkedHashMap;
import java.util.Map;
import java.util.Random;
import java.util.TreeMap;
import java.util.function.Function;

public class TrafficSplitDemo {

    public static void main(String[] args) {
        Map<String, Function<String, String>> subsets = Map.of(
                "v1", req -> "v1",
                "v2", req -> {
                    if (req.hashCode() % 20 == 0) {
                        throw new IllegalStateException("v2 503");
                    }
                    return "v2";
                });

        System.out.println("=== Streaming: canary of recommendations v2 via mesh routing rules ===");
        for (int v2Weight : new int[] {10, 50}) {
            Map<String, Integer> weights = new LinkedHashMap<>();
            weights.put("v1", 100 - v2Weight);
            weights.put("v2", v2Weight);
            var sidecar = new TrafficSplitSidecar(weights, subsets, 1, new Random(42));
            Map<String, Integer> served = new TreeMap<>();
            int failed = 0;
            for (int i = 0; i < 10_000; i++) {
                try {
                    served.merge(sidecar.call("profile-" + i), 1, Integer::sum);
                } catch (IllegalStateException e) {
                    failed++;
                }
            }
            System.out.println("weights v1=" + (100 - v2Weight) + "/v2=" + v2Weight + " -> served " + served
                    + ", failed after retry: " + failed);
        }
        System.out.println("The app code never changed: weights and retries are mesh configuration.");
    }
}

    Output:

    === Streaming: canary of recommendations v2 via mesh routing rules ===
weights v1=90/v2=10 -> served {v1=9035, v2=959}, failed after retry: 6
weights v1=50/v2=50 -> served {v1=5046, v2=4825}, failed after retry: 129
The app code never changed: weights and retries are mesh configuration.

    Why the mesh here:

    • Progressive delivery without touching application code or the client.
    • Weights change in seconds; combined with metrics, tools like Flagger/Argo Rollouts automate promotion.

    Example 3: Golden Signals for a Legacy App (Ride-hailing)¶

    Scenario: The fare service is an old app with no metrics and no tracing. Its sidecar records traffic, errors and latency per route (normalizing IDs so /fares/TRIP-11 and /fares/TRIP-12 are one route), and starts a trace for requests without one. Dashboards and alerts work on day one, with zero code changes.

    Full Code:

    package com.handbook.microservices.sidecar.telemetry;

import com.handbook.microservices.support.Http.Request;
import com.handbook.microservices.support.Http.Response;

import java.time.Clock;
import java.util.Map;
import java.util.TreeMap;
import java.util.function.Function;

/**
 * Records golden-signal metrics (traffic, errors, latency) for every request, for any app in any
 * language, without changing the app. Also starts a trace if the request has none.
 */
public final class TelemetrySidecar {

    private record Stats(int count, int errors, long totalMillis, long maxMillis) {
    }

    private final Function<Request, Response> app;
    private final Clock clock;
    private final Map<String, Stats> byRoute = new TreeMap<>();
    private int nextTrace = 1;

    public TelemetrySidecar(Function<Request, Response> app, Clock clock) {
        this.app = app;
        this.clock = clock;
    }

    public Response handle(Request request) {
        Request traced = request.header("traceparent") != null ? request // (1)!
                : request.withHeader("traceparent", String.format("00-%032x-%016x-01", nextTrace, nextTrace++));
        long start = clock.millis();
        Response response = app.apply(traced);
        long took = clock.millis() - start;
        String route = request.method() + " " + request.path().replaceAll("/[A-Z]+-\\d+", "/{id}"); // (2)!
        byRoute.merge(route, new Stats(1, response.status() >= 500 ? 1 : 0, took, took),
                (a, b) -> new Stats(a.count() + 1, a.errors() + b.errors(), a.totalMillis() + b.totalMillis(),
                        Math.max(a.maxMillis(), b.maxMillis())));
        return response;
    }

    public void printMetrics() {
        byRoute.forEach((route, s) -> System.out.printf("  %-22s requests=%d errors=%d avg=%dms max=%dms%n",
                route, s.count(), s.errors(), s.totalMillis() / s.count(), s.maxMillis()));
    }
}
    1. Start a trace if the caller didn't send one; otherwise continue it (see Distributed Tracing).
    2. Normalize IDs out of paths; otherwise each trip ID becomes its own metric series (cardinality explosion).
    package com.handbook.microservices.sidecar.telemetry;

import com.handbook.microservices.support.FakeClock;
import com.handbook.microservices.support.Http.Request;
import com.handbook.microservices.support.Http.Response;

import java.util.Map;

public class TelemetryDemo {

    public static void main(String[] args) {
        FakeClock clock = FakeClock.at("2026-10-13T08:00:00Z");
        // A legacy fare service (imagine it's written in PHP): no metrics, no tracing.
        var sidecar = new TelemetrySidecar(request -> {
            boolean surge = request.path().contains("surge");
            clock.advanceMillis(surge ? 180 : 40);
            if (request.path().endsWith("TRIP-13")) {
                return Response.of(500, "fare table missing");
            }
            return Response.of(200, "fare ok, trace-id ..." + request.header("traceparent").substring(27, 35));
        }, clock);

        System.out.println("=== Ride-hailing: golden signals from a sidecar, zero app changes ===");
        for (String trip : new String[] {"TRIP-11", "TRIP-12", "TRIP-13"}) {
            System.out.println("GET /fares/" + trip + " -> " + sidecar.handle(Request.get("/fares/" + trip, Map.of())));
        }
        System.out.println("GET /fares/surge/TRIP-14 -> " + sidecar.handle(Request.get("/fares/surge/TRIP-14", Map.of())));
        System.out.println("Metrics exported to Prometheus:");
        sidecar.printMetrics();
    }
}

    Output:

    === Ride-hailing: golden signals from a sidecar, zero app changes ===
GET /fares/TRIP-11 -> 200 fare ok, trace-id ...00000001
GET /fares/TRIP-12 -> 200 fare ok, trace-id ...00000002
GET /fares/TRIP-13 -> 500 fare table missing
GET /fares/surge/TRIP-14 -> 200 fare ok, trace-id ...00000004
Metrics exported to Prometheus:
  GET /fares/surge/{id}  requests=1 errors=0 avg=180ms max=180ms
  GET /fares/{id}        requests=3 errors=1 avg=40ms max=40ms

    Why a sidecar here:

    • Uniform observability across all languages, including apps nobody wants to modify.
    • Same metric names and labels everywhere, so dashboards and SLOs are standard.
    Unit Tests: SidecarTest.java 
    package com.handbook.microservices;

import com.handbook.microservices.sidecar.mtls.SidecarProxy;
import com.handbook.microservices.sidecar.outlier.OutlierDetector;
import com.handbook.microservices.support.FakeClock;
import com.handbook.microservices.support.Http.Request;
import com.handbook.microservices.support.Http.Response;
import org.junit.jupiter.api.Test;

import java.time.Duration;
import java.util.List;
import java.util.Map;
import java.util.Set;

import static org.assertj.core.api.Assertions.assertThat;

class SidecarTest {

    @Test
    void onlyAllowedIdentitiesReachTheApp() {
        var sidecar = new SidecarProxy("me", Map.of("/x", Set.of("good")), r -> Response.of(200, "ok"));
        assertThat(sidecar.inbound(Request.get("/x", Map.of("x-peer-spiffe-id", "good"))).status()).isEqualTo(200);
        assertThat(sidecar.inbound(Request.get("/x", Map.of("x-peer-spiffe-id", "evil"))).status()).isEqualTo(403);
        assertThat(sidecar.inbound(Request.get("/x", Map.of())).status()).isEqualTo(403);
    }

    @Test
    void outlierIsEjectedThenReturns() {
        FakeClock clock = FakeClock.at("2026-01-01T00:00:00Z");
        var detector = new OutlierDetector(List.of("a", "b"), 2, Duration.ofSeconds(10), 50, clock);
        detector.record("a", 500);
        detector.record("a", 500);
        assertThat(detector.healthyHosts()).containsExactly("b");
        clock.advance(Duration.ofSeconds(10));
        assertThat(detector.healthyHosts()).containsExactly("a", "b");
    }
}

    6. Variations & Modern Java Take¶

    Istio configuration for the examples (reference):

    apiVersion: security.istio.io/v1
kind: AuthorizationPolicy
metadata: { name: payment-charges, namespace: prod }
spec:
  selector: { matchLabels: { app: payment } }
  action: ALLOW
  rules:
    - from: [ { source: { principals: ["shop.local/ns/prod/sa/checkout"] } } ]
      to:   [ { operation: { paths: ["/charges*"], methods: ["POST"] } } ]
---
apiVersion: networking.istio.io/v1
kind: VirtualService
metadata: { name: recommendations }
spec:
  hosts: [ recommendations ]
  http:
    - route:
        - { destination: { host: recommendations, subset: v1 }, weight: 90 }
        - { destination: { host: recommendations, subset: v2 }, weight: 10 }
      retries: { attempts: 1, perTryTimeout: 300ms, retryOn: "5xx,reset,connect-failure" }
    Variation Notes
    Sidecar mesh (Istio classic, Linkerd) One proxy per pod; most features; per-pod resource cost
    Sidecar-less / ambient (Istio ambient, Cilium) Per-node L4 proxy (ztunnel) + optional L7 waypoint proxies; lower overhead
    Library approach (Resilience4j, gRPC xDS, Spring Cloud) No extra hop; per-language
    Other sidecars Log shippers (Fluent Bit), secret fetchers (Vault Agent), Dapr runtime, config reloaders
    Ambassador A sidecar specialized for outbound calls of a legacy app (retries, routing)

    7. Where It Lives in Real Frameworks¶

    Where Sidecar / mesh
    Istio, Linkerd, Consul Connect, Kuma Service meshes
    Envoy The most common data-plane proxy (xDS API)
    Dapr Sidecar runtime providing pub/sub, state, bindings via HTTP/gRPC
    Kubernetes Native sidecar containers (restartPolicy: Always init containers, stable since 1.33)
    SPIFFE/SPIRE Workload identity used by meshes

    8. Pros, Cons & Trade-offs¶

    ✅ Pros ❌ Cons
    Language-agnostic cross-cutting features Operational complexity: a distributed system to run the distributed system
    Uniform mTLS, policy, telemetry Extra latency (two proxy hops per call, often ~1 ms or less) and resources per pod
    Changes via config, not redeploys Debugging gets harder (is it the app or the proxy?)
    Gradual delivery and traffic control Version upgrades of the mesh are significant projects

    9. Pitfalls & Anti-Patterns¶

    Retries in the app AND the mesh

    Resilience4j retries 3×, the sidecar retries 3× → 9 attempts per call, and more across hops. Decide which layer owns retries.

    Adopting a mesh for 5 services

    The mesh's operational cost only pays off at scale or with strict security requirements. Libraries or the platform's built-ins may be enough.

    Treating mTLS as full authorization

    mTLS proves which workload is calling, not which user. User-level authorization (JWT claims) still belongs in the app.

    Startup/shutdown ordering

    The app starts before its sidecar is ready (calls fail), or the sidecar exits before the app drains. Use native sidecar containers or holdApplicationUntilProxyStarts, and graceful drain settings.

    10. Senior / Architect Deep Dive (10–15 yrs)¶

    Mesh vs. libraries. A homogeneous Spring estate with good platform libraries may not need a mesh; a polyglot estate with zero-trust requirements usually benefits. Many orgs adopt mTLS + telemetry from the mesh and keep business-aware resilience (fallbacks) in the app.

    North-south vs. east-west. The API gateway handles client traffic; the mesh handles service-to-service traffic. Meshes often provide an ingress gateway too.

    Cost and performance. Sidecars consume CPU/memory per pod (sizable at thousands of pods). Ambient/sidecar-less modes reduce this; measure p99 latency overhead under real load.

    Production checklist¶

    • Clear reason (zero trust, polyglot, traffic management) and an owning platform team.
    • STRICT mTLS with automatic certificate rotation; default-deny authorization policies.
    • One layer owns retries/timeouts; budgets configured.
    • Telemetry: standard metrics, tracing propagation (apps still forward headers!), access logs.
    • Sidecar lifecycle (startup/drain) handled; resource requests sized.
    • Mesh upgrade runbooks and canaries for mesh config changes.

    Explain it in 2 minutes (system design round)¶

    "Service-to-service traffic goes through a mesh (Istio or Linkerd). Each pod's proxy gets a SPIFFE identity from the control plane, so all traffic is mutually authenticated and encrypted, and authorization policies say which services may call which endpoints, deny by default. The mesh also gives uniform metrics and tracing, timeouts, limited retries, outlier detection, and weighted routing for canaries. Business-aware fallbacks stay in the apps. If sidecar overhead becomes an issue, ambient mode moves L4 to per-node proxies."

    War story: the retry storm in the mesh

    An e-commerce company enabled mesh retries (3 attempts on 5xx) globally while several Java services still had Resilience4j retries (3 attempts). During a database slowdown, one user click produced up to 9 attempts at each of 3 hops. The database load multiplied, and a 2-minute slowdown became a 40-minute outage. Fix: retries removed from the apps; mesh retries limited to idempotent routes with a retry budget of 20%; per-try timeouts aligned to the request deadline. Lesson: a mesh adds behaviour between your services. Audit how it combines with what's already in your code.

    12. Interview Corner¶

    Q1. What is a sidecar?

    A helper container that runs next to the main application container in the same pod, adding features (proxying, logging, security) without changing the app.

    Q2. What is a service mesh?

    An infrastructure layer of sidecar proxies plus a control plane that handles service-to-service communication: mTLS, routing, retries, telemetry.

    Q3. Name a service mesh and its proxy.

    Istio (Envoy proxy), Linkerd (linkerd2-proxy), Consul Connect.

    Q4. What is mTLS?

    Mutual TLS: both client and server present certificates, so each side verifies the other's identity, and traffic is encrypted.

    Q5. Gateway vs. service mesh?

    The gateway handles traffic from clients into the system; the mesh handles traffic between services.

    Q1. What are the data plane and control plane?

    The data plane is the proxies handling traffic; the control plane configures them (routes, policies, certificates).

    Q2. How does a mesh do canary releases?

    Weighted routing between service subsets (e.g. 90/10), adjusted gradually, often automated with metrics analysis.

    Q3. Does a mesh give you distributed tracing automatically?

    It creates spans per hop, but apps must forward trace headers from inbound to outbound requests, or traces break into pieces.

    Q4. Downsides of sidecars?

    Per-pod CPU/memory, extra latency, operational complexity, lifecycle ordering issues.

    Q5. What's the Ambassador pattern?

    A sidecar that handles outbound connections for an app (routing, retries, TLS), useful for legacy apps you can't modify.

    Q1. "Would you introduce a mesh? Make the case for or against."

    For: polyglot services, zero-trust/compliance, need for uniform telemetry and traffic control, a platform team to run it. Against: small, homogeneous estates; no platform capacity; latency-critical paths where libraries suffice.

    Q2. "Explain how workload identity works in a mesh."

    The control plane (SPIFFE/SPIRE or Istiod) issues short-lived X.509 certificates bound to the Kubernetes service account; proxies use them for mTLS; authorization policies refer to these identities.

    Q3. "Sidecar vs. ambient mesh?"

    Sidecar: per-pod proxies, full L7 features everywhere, higher resource cost. Ambient: per-node L4 (mTLS, telemetry) plus optional per-namespace L7 waypoints; lower overhead, simpler upgrades.

    Q4. "Outlier detection vs. circuit breaker?"

    Outlier detection ejects individual misbehaving hosts from the pool; circuit breakers stop calls to a whole dependency and offer fallbacks. The mesh does the former well; apps do the latter.

    Q5. "How do you roll out mesh config changes safely?"

    GitOps, validation (istioctl analyze), canary namespaces, staged rollout, monitoring error rates, and quick revert, just like application deploys.

    Problem: Implement Envoy-style outlier detection: after 3 consecutive 5xx from a host, eject it for 30 s, but never eject more than 50% of hosts (or a bad dependency could eject everyone).

    Solution 
    package com.handbook.microservices.sidecar.outlier;

import java.time.Clock;
import java.time.Duration;
import java.time.Instant;
import java.util.HashMap;
import java.util.List;
import java.util.Map;

/**
 * Coding challenge: Envoy-style outlier detection. After N consecutive 5xx from one host, eject it
 * from the load-balancing pool for a while, but never eject more than a maximum share of hosts.
 */
public final class OutlierDetector {

    private final List<String> hosts;
    private final int consecutive5xx;
    private final Duration ejectionTime;
    private final int maxEjectionPercent;
    private final Clock clock;
    private final Map<String, Integer> failures = new HashMap<>();
    private final Map<String, Instant> ejectedUntil = new HashMap<>();

    public OutlierDetector(List<String> hosts, int consecutive5xx, Duration ejectionTime,
                           int maxEjectionPercent, Clock clock) {
        this.hosts = List.copyOf(hosts);
        this.consecutive5xx = consecutive5xx;
        this.ejectionTime = ejectionTime;
        this.maxEjectionPercent = maxEjectionPercent;
        this.clock = clock;
    }

    public List<String> healthyHosts() {
        Instant now = clock.instant();
        ejectedUntil.values().removeIf(until -> !now.isBefore(until));
        return hosts.stream().filter(h -> !ejectedUntil.containsKey(h)).toList();
    }

    public void record(String host, int status) {
        if (status < 500) {
            failures.remove(host);
            return;
        }
        int n = failures.merge(host, 1, Integer::sum);
        boolean underCap = (ejectedUntil.size() + 1) * 100 / hosts.size() <= maxEjectionPercent;
        if (n >= consecutive5xx && underCap && !ejectedUntil.containsKey(host)) {
            ejectedUntil.put(host, clock.instant().plus(ejectionTime));
            failures.remove(host);
            System.out.println("    ejected " + host + " for " + ejectionTime.toSeconds() + "s");
        }
    }
}

    package com.handbook.microservices.sidecar.outlier;

import com.handbook.microservices.support.FakeClock;

import java.time.Duration;
import java.util.List;

public class OutlierDemo {

    public static void main(String[] args) {
        FakeClock clock = FakeClock.at("2026-10-13T12:00:00Z");
        var detector = new OutlierDetector(List.of("pod-a", "pod-b", "pod-c", "pod-d"), 3,
                Duration.ofSeconds(30), 50, clock);

        System.out.println("=== Challenge: outlier detection (3 consecutive 5xx, max 50% ejected) ===");
        System.out.println("healthy: " + detector.healthyHosts());
        for (int i = 0; i < 3; i++) {
            detector.record("pod-b", 503); // pod-b has a corrupted cache
        }
        System.out.println("healthy: " + detector.healthyHosts());
        for (String pod : List.of("pod-c", "pod-d")) {
            for (int i = 0; i < 3; i++) {
                detector.record(pod, 503); // a bad dependency makes more pods fail
            }
        }
        System.out.println("healthy: " + detector.healthyHosts() + "  (pod-d kept: ejecting it would exceed 50%)");
        clock.advance(Duration.ofSeconds(30));
        System.out.println("30 s later healthy: " + detector.healthyHosts());
    }
}

    Output:

    === Challenge: outlier detection (3 consecutive 5xx, max 50% ejected) ===
healthy: [pod-a, pod-b, pod-c, pod-d]
    ejected pod-b for 30s
healthy: [pod-a, pod-c, pod-d]
    ejected pod-c for 30s
healthy: [pod-a, pod-d]  (pod-d kept: ejecting it would exceed 50%)
30 s later healthy: [pod-a, pod-b, pod-c, pod-d]

    Key points to say: consecutive failures (not a rate) keep it simple; the max ejection percent protects against a shared-dependency failure ejecting all hosts; ejected hosts return automatically after the ejection time (Envoy also increases ejection time for repeat offenders).

    Remember in 30 seconds

    • Sidecar = helper container next to the app; mesh = sidecars + control plane.
    • Gives mTLS identity, authorization, retries/timeouts, traffic splitting, telemetry.
    • East-west (mesh) vs. north-south (gateway).
    • Apps still forward trace headers and own business fallbacks.
    • Watch retry layering, overhead, lifecycle ordering.
