    Advanced Microservices

    Decomposition (by Business Capability / Subdomain)¶

    🔴 Advanced Microservices Interview frequency ⭐⭐⭐⭐⭐

    TL;DR

    Split a system into services along business capabilities (what the business does) or DDD subdomains, so each service owns its data and can change and deploy independently. The test of a good boundary: most use cases write inside one service. If a common use case must update data in two services at once, the boundary is probably wrong.

    1. Intent & Problem It Solves¶

    The problem in plain English: a grocery monolith has catalog, inventory, orders, payments and delivery in one codebase and one database. Every team deploys together, a bad inventory query slows checkout, and a change to the products table breaks four teams. Microservices promise independent teams and deployments, but only if the boundaries are right. Split badly (by technical layer, or by today's org chart) and you get a distributed monolith: all the network problems, none of the independence.

    Definitions (microservices.io / DDD):

    • Decompose by business capability: a service per thing the business does (catalog, inventory, ordering, billing), stable over time even as technology and org charts change.
    • Decompose by subdomain (DDD): model the domain, find bounded contexts where a term has one meaning ("Trip" in dispatch vs. billing), and align services with them.
    Subdomain type Meaning Strategy
    Core Where you compete (pricing, matching, recommendations) Build in-house, best engineers
    Supporting Necessary, specific to you (catalog admin) Build simply, or customize
    Generic Same for everyone (auth, email, payments gateway) Buy or use a SaaS

    2. Real-World Analogy¶

    A hospital's departments

    A hospital isn't organized by "people who use computers" and "people who use phones". It's organized by capability: emergency, radiology, pharmacy, billing. Each department has its own records and staff, and they coordinate through well-defined requests (a lab order, a discharge summary). A reorganization of managers doesn't move the pharmacy.

    3. Structure¶

    flowchart LR
    subgraph Monolith["Before: one deployable, one DB"]
        M[Catalog + Inventory + Orders + Payments] --> DB[(Shared DB)]
    end
    subgraph Services["After: services by business capability"]
        C[Catalog] --> CDB[(catalog DB)]
        I[Inventory] --> IDB[(inventory DB)]
        O[Ordering] --> ODB[(orders DB)]
        O -- "API: canFulfil?" --> I
        O -- "event: OrderPlaced" --> I
        I -- "event: StockLow" --> C
    end
    Rule Why
    Each service owns its data No shared tables, so services can change their schema independently
    Integrate via APIs and events Explicit contracts instead of hidden coupling
    Most use cases write in one service Avoids distributed transactions
    A team owns each service end to end Conway's Law: the architecture mirrors communication paths

    4. Naive Approach (Without the Pattern)¶

    Split by technical layer:      web-service, business-service, data-service    <- every feature touches all three
Split by current teams:        Registration, Doctors, Scheduling, Billing, Payments  <- org chart changes yearly
Split by entities (nouns):     CustomerService, ProductService, OrderService   <- "entity services": chatty, anemic
Shared database:               everyone reads/writes the same tables           <- distributed monolith
    • Every feature spans several services: coordinated deployments.
    • Distributed transactions for common use cases.
    • Chatty calls between services that should have been one.

    5. Three Real-World Examples¶

    Example 1: Grocery Monolith Split by Business Capability (Grocery)¶

    Scenario: A quick-commerce company splits its monolith into Catalog (what we sell and how it's shown), Inventory (units in each dark store) and Ordering (the order lifecycle). Ordering checks stock through Inventory's API, never its tables; Inventory announces events (StockLow) that Catalog uses to update the "only 1 left" badge. Each service could now be deployed, scaled and changed by its own team.

    Design:

    sequenceDiagram
    autonumber
    participant O as Ordering
    participant I as Inventory
    participant C as Catalog
    O->>I: canFulfil(MANGO-1KG, 2)? (API)
    I-->>O: yes
    O-)I: OrderPlaced (event)
    I->>I: reserve 2, 1 left
    I-)C: StockLow(left=1) (event)
    C->>C: badge "only 1 left"

    Full Code:

    package com.handbook.microservices.decomposition.grocery;

import com.handbook.microservices.support.EventBus;

import java.util.HashMap;
import java.util.List;
import java.util.Map;

/**
 * Three services split by BUSINESS CAPABILITY. Each owns its data (a private map standing in
 * for its own database) and talks to the others only through APIs and events.
 */
public final class GroceryServices {

    private GroceryServices() {
    }

    public record OrderPlaced(String orderId, String sku, int qty) {
    }

    public record StockLow(String sku, int left) {
    }

    /** Catalog: what we sell, how it's described, whether to show it as available. */
    public static class CatalogService {
        private final Map<String, String> products = new HashMap<>(Map.of("MANGO-1KG", "Alphonso mangoes, 1 kg"));
        private final Map<String, Boolean> showAsAvailable = new HashMap<>(Map.of("MANGO-1KG", true));

        public CatalogService(EventBus bus) {
            bus.<StockLow>subscribe("inventory.stock-low", e -> { // (1)!
                showAsAvailable.put(e.sku(), e.left() > 0);
                System.out.println("  [catalog] " + e.sku() + " badge -> " + (e.left() > 0 ? "only " + e.left() + " left" : "out of stock"));
            });
        }

        public String describe(String sku) {
            return products.get(sku) + (showAsAvailable.get(sku) ? "" : " (out of stock)");
        }
    }

    /** Inventory: how many units each dark store physically has. */
    public static class InventoryService {
        private final Map<String, Integer> stock = new HashMap<>(Map.of("MANGO-1KG", 3));
        private final EventBus bus;

        public InventoryService(EventBus bus) {
            this.bus = bus;
            bus.<OrderPlaced>subscribe("orders.placed", e -> {
                int left = stock.merge(e.sku(), -e.qty(), Integer::sum);
                System.out.println("  [inventory] reserved " + e.qty() + " x " + e.sku() + ", " + left + " left");
                if (left <= 1) {
                    bus.publish("inventory.stock-low", new StockLow(e.sku(), left));
                }
            });
        }

        public boolean canFulfil(String sku, int qty) { // a synchronous API other services may call
            return stock.getOrDefault(sku, 0) >= qty;
        }
    }

    /** Ordering: the order lifecycle. It asks Inventory through its API, never reads its tables. */
    public static class OrderService {
        private final InventoryService inventoryApi;
        private final EventBus bus;
        private int next = 1;

        public OrderService(InventoryService inventoryApi, EventBus bus) {
            this.inventoryApi = inventoryApi;
            this.bus = bus;
        }

        public String place(String sku, int qty) {
            if (!inventoryApi.canFulfil(sku, qty)) { // (2)!
                return "rejected: not enough " + sku;
            }
            String id = "ORD-" + next++;
            bus.publish("orders.placed", new OrderPlaced(id, sku, qty)); // (3)!
            return "accepted " + id;
        }
    }

    public static List<String> ownership() {
        return List.of(
                "Catalog   owns: product names, descriptions, images, availability badge",
                "Inventory owns: units per dark store, reservations",
                "Ordering  owns: orders, order lifecycle");
    }
}
    1. Catalog reacts to Inventory's events instead of reading Inventory's tables. It keeps its own copy of what it needs (the badge).
    2. A synchronous API call for a question that needs a fresh answer before accepting the order.
    3. An event for something that already happened. Inventory decides what reservation means.
    package com.handbook.microservices.support;

import java.util.ArrayList;
import java.util.LinkedHashMap;
import java.util.List;
import java.util.Map;
import java.util.function.Consumer;

/**
 * A tiny, synchronous, in-memory stand-in for a message broker (Kafka, RabbitMQ).
 * Real brokers are asynchronous and at-least-once; the examples call that out where it matters.
 */
public final class EventBus {

    private final Map<String, List<Consumer<Object>>> subscribers = new LinkedHashMap<>();
    private final boolean log;

    public EventBus(boolean log) {
        this.log = log;
    }

    @SuppressWarnings("unchecked")
    public <T> void subscribe(String topic, Consumer<T> handler) {
        subscribers.computeIfAbsent(topic, t -> new ArrayList<>()).add(e -> handler.accept((T) e));
    }

    public void publish(String topic, Object event) {
        if (log) {
            System.out.println("  [bus] " + topic + " <- " + event);
        }
        for (Consumer<Object> s : subscribers.getOrDefault(topic, List.of())) {
            s.accept(event);
        }
    }
}

    package com.handbook.microservices.decomposition.grocery;

import com.handbook.microservices.decomposition.grocery.GroceryServices.*;
import com.handbook.microservices.support.EventBus;

public class GroceryDecompositionDemo {

    public static void main(String[] args) {
        System.out.println("=== Grocery: Monolith Split by Business Capability ===");
        GroceryServices.ownership().forEach(System.out::println);
        EventBus bus = new EventBus(true);
        CatalogService catalog = new CatalogService(bus);
        InventoryService inventory = new InventoryService(bus);
        OrderService orders = new OrderService(inventory, bus);

        System.out.println("Customer 1 orders 2 mangoes:");
        System.out.println("  -> " + orders.place("MANGO-1KG", 2));
        System.out.println("Customer 2 orders 2 mangoes:");
        System.out.println("  -> " + orders.place("MANGO-1KG", 2));
        System.out.println("Customer 3 orders 1 mango:");
        System.out.println("  -> " + orders.place("MANGO-1KG", 1));
        System.out.println("Catalog page now shows: " + catalog.describe("MANGO-1KG"));
    }
}

    Output (happy path and failure path):

    === Grocery: Monolith Split by Business Capability ===
Catalog   owns: product names, descriptions, images, availability badge
Inventory owns: units per dark store, reservations
Ordering  owns: orders, order lifecycle
Customer 1 orders 2 mangoes:
  [bus] orders.placed <- OrderPlaced[orderId=ORD-1, sku=MANGO-1KG, qty=2]
  [inventory] reserved 2 x MANGO-1KG, 1 left
  [bus] inventory.stock-low <- StockLow[sku=MANGO-1KG, left=1]
  [catalog] MANGO-1KG badge -> only 1 left
  -> accepted ORD-1
Customer 2 orders 2 mangoes:
  -> rejected: not enough MANGO-1KG
Customer 3 orders 1 mango:
  [bus] orders.placed <- OrderPlaced[orderId=ORD-2, sku=MANGO-1KG, qty=1]
  [inventory] reserved 1 x MANGO-1KG, 0 left
  [bus] inventory.stock-low <- StockLow[sku=MANGO-1KG, left=0]
  [catalog] MANGO-1KG badge -> out of stock
  -> accepted ORD-2
Catalog page now shows: Alphonso mangoes, 1 kg (out of stock)

    Why this boundary:

    • Each capability has its own data and rules (reservation logic stays in Inventory).
    • Catalog stays fast and available even if Inventory is slow: it uses its own copy of the badge.
    • Teams map one-to-one to services.

    Example 2: One Word, Two Bounded Contexts (Ride-hailing)¶

    Scenario: In a ride-hailing company, Dispatch thinks of a trip as a driver, a pickup location, an ETA and a status. Billing thinks of a trip as base fare, distance fare, time fare and surge. A single shared Trip class (and table) would grow 60 columns, couple both teams, and make every change risky. Instead, each bounded context has its own Trip model, and Dispatch publishes a small, stable TripCompleted event that Billing translates into its model.

    Design:

    flowchart LR
    subgraph Dispatch["Dispatch context"]
        DT["Trip: driverId, pickup lat/lng, etaMinutes, status"]
    end
    subgraph Billing["Billing context"]
        BT["Trip: baseFare, distanceFare, timeFare, surge, total"]
    end
    DT -- "TripCompleted(tripId, riderId, km, minutes, city)" --> BT

    Full Code:

    package com.handbook.microservices.decomposition.ridehailing;

import java.util.ArrayList;
import java.util.List;
import java.util.function.Consumer;

/**
 * The word "Trip" means different things in two bounded contexts. Each context has its OWN model;
 * they integrate through a published event, not a shared Trip class or shared table.
 */
public final class TripContexts {

    private TripContexts() {
    }

    // ---------- Dispatch context: moving cars around the city ----------
    public static final class Dispatch {
        public record Trip(String id, String driverId, double pickupLat, double pickupLng, int etaMinutes, String status) { // (1)!
        }

        /** The public contract Dispatch publishes. Deliberately small and stable. */
        public record TripCompleted(String tripId, String riderId, double distanceKm, int durationMin, String city) { // (2)!
        }

        private final List<Consumer<TripCompleted>> listeners = new ArrayList<>();

        public void onTripCompleted(Consumer<TripCompleted> l) {
            listeners.add(l);
        }

        public void complete(Trip trip, String riderId, double km, int minutes) {
            System.out.println("  [dispatch] " + trip.id() + " completed by driver " + trip.driverId() + " (ETA was " + trip.etaMinutes() + " min)");
            listeners.forEach(l -> l.accept(new TripCompleted(trip.id(), riderId, km, minutes, "Bengaluru")));
        }
    }

    // ---------- Billing context: charging riders ----------
    public static final class Billing {
        public record Trip(String id, String riderId, int baseFare, int distanceFare, int timeFare, int surge, int totalInr) { // (3)!
        }

        private final List<Trip> invoiced = new ArrayList<>();

        public void handle(Dispatch.TripCompleted e) { // translate THEIR language into OURS
            int base = 50;
            int distance = (int) Math.round(e.distanceKm() * 14);
            int time = e.durationMin() * 2;
            int surge = e.city().equals("Bengaluru") ? 20 : 0;
            Trip t = new Trip(e.tripId(), e.riderId(), base, distance, time, surge, base + distance + time + surge);
            invoiced.add(t);
            System.out.println("  [billing] invoice " + t);
        }

        public List<Trip> invoiced() {
            return invoiced;
        }
    }
}
    1. Dispatch's model: what matters for moving cars.
    2. The published contract between contexts: small, explicit, versioned. It's not either side's internal model.
    3. Billing's model: what matters for charging money. Same word, different concept.
    package com.handbook.microservices.decomposition.ridehailing;

import com.handbook.microservices.decomposition.ridehailing.TripContexts.Billing;
import com.handbook.microservices.decomposition.ridehailing.TripContexts.Dispatch;

public class TripContextsDemo {

    public static void main(String[] args) {
        System.out.println("=== Ride-hailing: One Word, Two Bounded Contexts ===");
        Dispatch dispatch = new Dispatch();
        Billing billing = new Billing();
        dispatch.onTripCompleted(billing::handle);

        Dispatch.Trip trip = new Dispatch.Trip("TRIP-77", "DRV-12", 12.9352, 77.6245, 4, "IN_PROGRESS");
        dispatch.complete(trip, "RIDER-5", 8.4, 23);
        System.out.println("Dispatch's Trip has GPS + ETA; Billing's Trip has fare components. Neither knows the other's model.");
    }
}

    Output:

    === Ride-hailing: One Word, Two Bounded Contexts ===
  [dispatch] TRIP-77 completed by driver DRV-12 (ETA was 4 min)
  [billing] invoice Trip[id=TRIP-77, riderId=RIDER-5, baseFare=50, distanceFare=118, timeFare=46, surge=20, totalInr=234]
Dispatch's Trip has GPS + ETA; Billing's Trip has fare components. Neither knows the other's model.

    Why bounded contexts here:

    • The ubiquitous language differs between teams; forcing one model makes both worse.
    • The event is the boundary: each side can evolve its internals freely.
    • Billing can add surge rules without touching Dispatch, and vice versa.

    Example 3: Checking Candidate Splits Against Use Cases (Healthcare)¶

    Scenario: A hospital IT department wants to break up its patient-management system. One architect proposes splitting by current teams (Registration, Doctors, Scheduling, Billing, Payments); another by business capability (PatientRecords, Scheduling, Billing). Before writing code, they check each split against the real use cases: which ones would have to write data owned by two services in one transaction?

    Design:

    flowchart TB
    U[Use cases + tables they write/read] --> C{BoundaryChecker}
    S1[Split A: by teams] --> C
    S2[Split B: by capability] --> C
    C --> R1["Split A: 3 cross-service writes"]
    C --> R2["Split B: 1 cross-service write"]

    Full Code:

    package com.handbook.microservices.decomposition.healthcare;

import java.util.LinkedHashMap;
import java.util.List;
import java.util.Map;
import java.util.Set;
import java.util.TreeSet;

/**
 * Checks a proposed service split against the system's use cases: a use case that must WRITE
 * data owned by two services in one transaction is a warning sign (distributed transaction).
 */
public final class BoundaryChecker {

    public record UseCase(String name, Set<String> writes, Set<String> reads) {
    }

    private BoundaryChecker() {
    }

    public static Map<String, String> check(Map<String, String> tableOwner, List<UseCase> useCases) {
        Map<String, String> report = new LinkedHashMap<>();
        for (UseCase uc : useCases) {
            Set<String> writeOwners = new TreeSet<>();
            uc.writes().forEach(t -> writeOwners.add(tableOwner.get(t)));
            Set<String> readOwners = new TreeSet<>();
            uc.reads().forEach(t -> readOwners.add(tableOwner.get(t)));
            readOwners.removeAll(writeOwners);
            String verdict;
            if (writeOwners.size() > 1) {
                verdict = "WARN writes span " + writeOwners + " -> needs a saga or a different boundary"; // (1)!
            } else if (!readOwners.isEmpty()) {
                verdict = "ok   (reads from " + readOwners + ": API calls or a read model)";
            } else {
                verdict = "ok   (inside " + writeOwners + ")";
            }
            report.put(uc.name(), verdict);
        }
        return report;
    }
}
    1. The heuristic: writes across services in one use case mean a saga (complex) or a wrong boundary. Reads across services are normal (API calls or a local read model).
    package com.handbook.microservices.decomposition.healthcare;

import com.handbook.microservices.decomposition.healthcare.BoundaryChecker.UseCase;

import java.util.List;
import java.util.Map;
import java.util.Set;

public class BoundaryDemo {

    static final List<UseCase> USE_CASES = List.of(
            new UseCase("Book appointment", Set.of("appointments", "slots"), Set.of("patients", "doctors")),
            new UseCase("Check in patient", Set.of("appointments"), Set.of("patients")),
            new UseCase("Close consultation + bill", Set.of("appointments", "invoices"), Set.of("tariffs")),
            new UseCase("Pay invoice", Set.of("invoices", "payments"), Set.of()),
            new UseCase("Update allergies", Set.of("patients"), Set.of()));

    public static void main(String[] args) {
        System.out.println("=== Hospital: Checking Two Candidate Service Splits ===");
        Map<String, String> splitByTeam = Map.of( // split along today's org chart
                "patients", "Registration", "appointments", "Scheduling", "slots", "Doctors",
                "doctors", "Doctors", "invoices", "Billing", "payments", "Payments", "tariffs", "Billing");
        Map<String, String> splitByCapability = Map.of( // split along business capabilities
                "patients", "PatientRecords", "appointments", "Scheduling", "slots", "Scheduling",
                "doctors", "Scheduling", "invoices", "Billing", "payments", "Billing", "tariffs", "Billing");

        for (var split : List.of(Map.entry("Split A (by current teams)", splitByTeam),
                Map.entry("Split B (by business capability)", splitByCapability))) {
            System.out.println(split.getKey() + ":");
            BoundaryChecker.check(split.getValue(), USE_CASES)
                    .forEach((uc, verdict) -> System.out.printf("  %-26s %s%n", uc, verdict));
        }
    }
}

    Output:

    === Hospital: Checking Two Candidate Service Splits ===
Split A (by current teams):
  Book appointment           WARN writes span [Doctors, Scheduling] -> needs a saga or a different boundary
  Check in patient           ok   (reads from [Registration]: API calls or a read model)
  Close consultation + bill  WARN writes span [Billing, Scheduling] -> needs a saga or a different boundary
  Pay invoice                WARN writes span [Billing, Payments] -> needs a saga or a different boundary
  Update allergies           ok   (inside [Registration])
Split B (by business capability):
  Book appointment           ok   (reads from [PatientRecords]: API calls or a read model)
  Check in patient           ok   (reads from [PatientRecords]: API calls or a read model)
  Close consultation + bill  WARN writes span [Billing, Scheduling] -> needs a saga or a different boundary
  Pay invoice                ok   (inside [Billing])
  Update allergies           ok   (inside [PatientRecords])

    The capability-based split leaves one warning, "Close consultation + bill". That's acceptable if Scheduling publishes ConsultationClosed and Billing creates the invoice asynchronously: the invoice doesn't need to exist in the same transaction. Making that decision explicitly is the point of the exercise.

    Why this check:

    • Turns "where should the boundary be?" from opinion into evidence from use cases.
    • Splitting by org chart produced three cross-service writes: a distributed monolith in the making.
    • Cheap to run before writing any service code.
    Unit Tests: DecompositionTest.java 
    package com.handbook.microservices;

import com.handbook.microservices.decomposition.grocery.GroceryServices.*;
import com.handbook.microservices.decomposition.healthcare.BoundaryChecker;
import com.handbook.microservices.decomposition.ridehailing.TripContexts;
import com.handbook.microservices.support.EventBus;
import org.junit.jupiter.api.Test;

import java.util.List;
import java.util.Map;
import java.util.Set;

import static org.assertj.core.api.Assertions.assertThat;

class DecompositionTest {

    @Test
    void servicesCollaborateOnlyThroughApisAndEvents() {
        EventBus bus = new EventBus(false);
        CatalogService catalog = new CatalogService(bus);
        OrderService orders = new OrderService(new InventoryService(bus), bus);
        assertThat(orders.place("MANGO-1KG", 3)).startsWith("accepted");
        assertThat(catalog.describe("MANGO-1KG")).endsWith("(out of stock)");
        assertThat(orders.place("MANGO-1KG", 1)).startsWith("rejected");
    }

    @Test
    void billingTranslatesDispatchEventIntoItsOwnModel() {
        var dispatch = new TripContexts.Dispatch();
        var billing = new TripContexts.Billing();
        dispatch.onTripCompleted(billing::handle);
        dispatch.complete(new TripContexts.Dispatch.Trip("T", "D", 0, 0, 1, "X"), "R", 10, 10);
        assertThat(billing.invoiced()).singleElement().extracting(TripContexts.Billing.Trip::totalInr).isEqualTo(50 + 140 + 20 + 20);
    }

    @Test
    void crossServiceWritesAreFlagged() {
        var report = BoundaryChecker.check(Map.of("a", "S1", "b", "S2"),
                List.of(new BoundaryChecker.UseCase("uc", Set.of("a", "b"), Set.of())));
        assertThat(report.get("uc")).startsWith("WARN");
    }
}

    6. Variations & Modern Java Take¶

    • Modular monolith first. Many teams start with one deployable split into strict modules (Java modules, Spring Modulith, ArchUnit rules), then extract services when a module needs independent scaling or deployment. See Modular Monolith.
    • Event storming workshops to discover domain events, aggregates and bounded contexts with domain experts.
    • Context mapping between bounded contexts: customer/supplier, conformist, anti-corruption layer, open-host service, published language.
    • Strangler fig to extract services from an existing monolith incrementally. See Strangler Fig.

    8. Pros, Cons & Trade-offs¶

    ✅ Pros ❌ Cons
    Independent deployment and scaling per capability Distributed system costs: network failures, latency, eventual consistency
    Team autonomy: one team, one service, one database Cross-service queries need API composition or read models
    Failures isolated to one capability Operational overhead: CI/CD, monitoring, on-call per service
    Each service can use the right technology Wrong boundaries are expensive to fix later

    9. Pitfalls & Anti-Patterns¶

    Splitting by technical layer or by entity

    ProductService, CustomerService, OrderService as CRUD wrappers ("entity services") create chatty, anemic services where every feature changes three of them.

    Shared database

    Services that share tables are one system with extra network hops. Each service must own its data; others get it through APIs or events.

    Too many, too small

    50 services for 8 engineers means more time on infrastructure than features. Size services to teams and capabilities, not to lines of code.

    Splitting before understanding the domain

    Boundaries are hardest to get right early. Start with a modular monolith and extract when the seams are clear.

    10. Senior / Architect Deep Dive (10–15 yrs)¶

    Conway's Law and the Inverse Conway Maneuver. Systems mirror the communication structure of the organizations that build them. Design team boundaries deliberately to get the architecture you want (Team Topologies: stream-aligned teams owning services end to end, platform teams providing paved roads).

    Data ownership decides boundaries. Ask "who is allowed to change this data, and what invariants protect it?" An invariant that spans data in two services ("an appointment can't be booked unless the slot is free") belongs inside one service, or it needs a saga and accepts eventual consistency.

    Migration path. Strangler fig: put a routing layer in front of the monolith, extract one capability at a time (start with one that has clear data and low coupling), replicate data with CDC during the transition, and delete the monolith code once traffic has moved.

    Production checklist¶

    • Each service has one owning team and an on-call rotation.
    • Each service has its own database (or schema with enforced access control).
    • Integration contracts (APIs, events) are versioned and covered by contract tests.
    • The most common use cases write in a single service.
    • Cross-service flows have explicit consistency strategies (sagas, events, read models).
    • Observability: distributed tracing, per-service SLOs and dashboards.
    • Independent CI/CD pipelines; a service can deploy without others.

    Explain it in 2 minutes (system design round)¶

    "I'd split by business capability: catalog, inventory, ordering, payments, delivery. Each owns its data; no shared tables. Ordering checks stock through Inventory's API for decisions that must be fresh, and publishes events like OrderPlaced that Inventory and Notifications consume. I'd validate the boundaries against core use cases: placing an order should write mostly within Ordering, with reservation and payment handled by a saga. I'd start as a modular monolith if the team is small, and extract services as scaling or team boundaries require."

    War story: the twelve services that always deployed together

    A fintech split its monolith into 12 services along its database tables (Customer, Account, Card, Transaction...). Every feature needed changes in 4–6 services, deployed in a strict order. Releases took a full day, and a failed deploy of one service broke the others. They had built a distributed monolith. Fix: re-drew boundaries around capabilities (Onboarding, Cards, Payments, Lending), merged services that always changed together, and introduced events for cross-capability flows. Deploys became independent and went from weekly to 30 per day. Lesson: services that change together belong together. Draw boundaries around change and data ownership, not nouns.

    12. Interview Corner¶

    Q1. What are microservices?

    An architecture where an application is built as a set of small, independently deployable services, each owning a business capability and its data, communicating over the network (HTTP/gRPC, messaging).

    Q2. How do you decide service boundaries?

    By business capability or DDD subdomain/bounded context, not by technical layer. Each service should own its data and handle most of its use cases on its own.

    Q3. Monolith vs. microservices?

    Monolith: one deployable, simple to develop and test, harder to scale teams. Microservices: independent deployment and scaling, at the cost of distributed-system complexity.

    Q4. What is a bounded context?

    A boundary within which a domain model and its terms have one consistent meaning ("Trip" in Dispatch vs. Billing).

    Q5. Should microservices share a database?

    No. Each service owns its data; others access it through APIs or events.

    Q1. What's a distributed monolith?

    Services that must be deployed together or share a database: all the costs of microservices, none of the independence.

    Q2. How do services get data they don't own?

    Synchronous API calls for fresh decisions; events to keep local read copies for display and queries.

    Q3. What's wrong with "entity services"?

    CRUD services per noun make features span many services, causing chatty calls and coordinated deployments.

    Q4. How do you handle a use case that writes to two services?

    Reconsider the boundary first; otherwise use a saga with compensations or make one part asynchronous via events.

    Q5. Core vs. supporting vs. generic subdomains?

    Core: competitive advantage, build it well. Supporting: needed, build simply. Generic: buy or use SaaS (auth, email).

    Q1. "Decompose a food-delivery platform." (classic)

    Capabilities: Customer, Restaurant/Menu, Ordering, Payments, Delivery (rider assignment, tracking), Notifications, Pricing/Promotions, Search. Each owns its data; order placement runs a saga (reserve → pay → assign rider); events feed search and analytics. Discuss team ownership, scaling hotspots (tracking, search), and starting as a modular monolith.

    Q2. "How do you validate boundaries before building?"

    Event storming, mapping use cases to data writes (like Example 3), checking change history (files that change together), and team topology. Prototype as modules and enforce boundaries with ArchUnit or Spring Modulith before splitting deployables.

    Q3. "When should you NOT use microservices?"

    Small teams, unclear domains, early-stage products, no mature CI/CD and observability. Start with a well-structured monolith.

    Q4. "How do you migrate a large monolith?"

    Strangler fig, extracting capabilities with clear seams first, an anti-corruption layer around legacy models, CDC for data during transition, and decommissioning milestones. Measure deploy frequency and lead time to show progress.

    Q5. "How does Conway's Law affect your design?"

    The architecture mirrors team communication. Align services with teams (inverse Conway maneuver); avoid services that need several teams to change together.

    Problem: Propose a service split for a food-delivery app (restaurants, menus, dishes, customers, orders, riders, assignments, rider locations, payments) such that no use case writes across services. Verify it with the BoundaryChecker.

    Solution 
    package com.handbook.microservices.decomposition.fooddelivery;

import com.handbook.microservices.decomposition.healthcare.BoundaryChecker;
import com.handbook.microservices.decomposition.healthcare.BoundaryChecker.UseCase;

import java.util.List;
import java.util.Map;
import java.util.Set;

/** Challenge solution: a food-delivery split where no use case writes across services. */
public class FoodDeliverySplitDemo {

    public static void main(String[] args) {
        List<UseCase> useCases = List.of(
                new UseCase("Update menu", Set.of("menus", "dishes"), Set.of("restaurants")),
                new UseCase("Place order", Set.of("orders", "order_lines"), Set.of("dishes", "customers")),
                new UseCase("Assign rider", Set.of("assignments"), Set.of("riders", "orders")),
                new UseCase("Rider location ping", Set.of("rider_locations"), Set.of()),
                new UseCase("Capture payment", Set.of("payments"), Set.of("orders")));

        Map<String, String> split = Map.ofEntries(
                Map.entry("restaurants", "Restaurant"), Map.entry("menus", "Restaurant"), Map.entry("dishes", "Restaurant"),
                Map.entry("customers", "Customer"),
                Map.entry("orders", "Ordering"), Map.entry("order_lines", "Ordering"),
                Map.entry("riders", "Delivery"), Map.entry("assignments", "Delivery"), Map.entry("rider_locations", "Delivery"),
                Map.entry("payments", "Payments"));

        BoundaryChecker.check(split, useCases).forEach((uc, v) -> System.out.printf("%-20s %s%n", uc, v));
    }
}

    Output:

    Update menu          ok   (inside [Restaurant])
Place order          ok   (reads from [Customer, Restaurant]: API calls or a read model)
Assign rider         ok   (reads from [Ordering]: API calls or a read model)
Rider location ping  ok   (inside [Delivery])
Capture payment      ok   (reads from [Ordering]: API calls or a read model)

    Key points to say: every write stays inside one capability; cross-service reads are fine (Ordering reads menus through an API or a cached read model; Delivery and Payments learn about orders through OrderPlaced events). Placing an order end to end (reserve, pay, assign) still spans services, so it becomes a Saga.

    Behavioural tie-in (STAR) for experienced candidates

    • S: Our 12 entity-based services always deployed together; releases took a day.
    • T: Restore independent delivery without a rewrite.
    • A: Mapped use cases to data writes, redrew boundaries around four capabilities, merged services that always changed together, and replaced synchronous chains with events.
    • R: Deploy frequency went from weekly to about 30 per day; cross-team deployment coordination dropped to near zero.

    13. Quick Revision Card¶

    Remember in 30 seconds

    • Split by business capability / bounded context, not by layer, entity or org chart.
    • Each service owns its data; integrate with APIs (fresh decisions) and events (facts).
    • Test: common use cases write inside one service.
    • Same word, different models across contexts; integrate with published events.
    • Small team or unclear domain? Start with a modular monolith.
    Catalog | Inventory | Ordering | Payments | Delivery   — each with its own DB, team and pipeline
