    Intermediate Messaging Microservices

    Competing Consumers¶

    🟡 Intermediate Microservices Interview frequency ⭐⭐⭐⭐

    TL;DR

    Several identical consumers read from the same queue; each message is delivered to only one of them. Add consumers to add throughput. Use it for background work that arrives faster than one worker can handle (PDFs, emails, webhooks, image processing). Pair it with acknowledgements, visibility timeouts, idempotency and a dead-letter queue.

    See It in Motion¶

    Press Play to watch the calls travel between components, or step through with Next and Back. Open the full explorer with all 66 patterns

    1. Intent & Problem It Solves¶

    The problem in plain English: every order needs an invoice PDF. At 5 pm a single worker can render 50 per second, but orders arrive at 200 per second; the backlog grows all evening. Running the renderer inside the checkout request makes checkout slow. You want to put the work on a queue and add workers until the queue keeps up, and you want a crashed worker's job to be picked up by someone else.

    Definition (Hohpe & Woolf, Enterprise Integration Patterns):

    Create multiple Competing Consumers on a single channel so that the consumers can process multiple messages concurrently. The messaging system ensures each message is delivered to only one consumer.

    Two broker models:

    Queue (SQS, RabbitMQ, JMS) Log with consumer groups (Kafka, Kinesis)
    Unit of competition Each message Each partition (one owner at a time)
    Ordering None across consumers (FIFO queues: per group id) Per partition (per key)
    Max parallelism Number of consumers Number of partitions
    Redelivery Visibility timeout / nack Uncommitted offsets re-read after rebalance

    2. Real-World Analogy¶

    Bank counters with a token display

    Customers take a token and wait in one shared queue. Whichever counter is free calls the next token. Opening more counters serves more customers; if a clerk leaves mid-transaction, the customer is called again by another counter.

    3. Structure¶

    flowchart LR P1[Checkout] --> Q[["invoice-jobs queue"]] P2[Re-issue tool] --> Q Q --> C1[Worker 1] Q --> C2[Worker 2] Q --> C3[Worker 3] Q -. "after N failures" .-> DLQ[["DLQ"]]
    Participant Responsibility
    Producers Put messages on the queue; don't know who processes them
    Queue / topic Stores messages; hands each to one consumer; redelivers unacked ones
    Consumers Identical, stateless workers; ack on success; idempotent
    Dead-letter queue Holds messages that keep failing, for inspection and replay
    Autoscaler Adds/removes consumers based on queue depth or lag (KEDA, HPA on lag)

    4. Naive Approach (Without the Pattern)¶

    @PostMapping("/orders")
public Order place(...) {
    Order o = orders.save(...);
    pdfRenderer.render(o);      // 400 ms inside the request
    emailClient.send(o);        // another 300 ms, and a failure fails the order
    return o;
}
    • Request latency includes slow background work.
    • Spikes overload the service instead of building a queue.
    • A crash loses the work; there's no retry.

    5. Three Real-World Examples¶

    Example 1: Invoice PDFs with a Worker Pool (Grocery)¶

    Scenario: A grocery platform renders 400 invoice PDFs for a batch of evening orders. Four identical workers pull from one queue. Each invoice must be rendered exactly once, and adding a fifth worker should need no code changes, just another instance. Workers stop gracefully when the queue drains (poison-pill shutdown).

    Design:

    flowchart LR O["400 orders"] --> Q[["LinkedBlockingQueue"]] Q -->|take| W1[worker 1] Q -->|take| W2[worker 2] Q -->|take| W3[worker 3] Q -->|take| W4[worker 4]

    Full Code:

    package com.handbook.microservices.competingconsumers.invoices;

import java.util.Map;
import java.util.concurrent.BlockingQueue;
import java.util.concurrent.ConcurrentHashMap;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.LinkedBlockingQueue;
import java.util.concurrent.TimeUnit;
import java.util.concurrent.atomic.AtomicInteger;

/** N identical workers pull from ONE queue; each message goes to exactly one of them. */
public final class InvoiceWorkers {

    private static final String STOP = "__STOP__";

    private final BlockingQueue<String> queue = new LinkedBlockingQueue<>();
    private final Map<String, Integer> processedCount = new ConcurrentHashMap<>();
    private final AtomicInteger inProgress = new AtomicInteger();
    private final AtomicInteger maxParallel = new AtomicInteger();

    public void publish(String orderId) {
        queue.add(orderId);
    }

    public void runWith(int workers) throws InterruptedException {
        try (ExecutorService pool = Executors.newFixedThreadPool(workers)) {
            for (int i = 0; i < workers; i++) {
                queue.add(STOP); // one poison pill per worker, after the real work
            }
            for (int i = 0; i < workers; i++) {
                pool.submit(this::workLoop);
            }
            pool.shutdown();
            pool.awaitTermination(30, TimeUnit.SECONDS);
        }
    }

    private Void workLoop() throws InterruptedException {
        while (true) {
            String orderId = queue.take(); // (1)!
            if (orderId.equals(STOP)) {
                return null;
            }
            int now = inProgress.incrementAndGet();
            maxParallel.accumulateAndGet(now, Math::max);
            Thread.sleep(2); // render the PDF
            processedCount.merge(orderId, 1, Integer::sum);
            inProgress.decrementAndGet();
        }
    }

    public Map<String, Integer> processedCount() {
        return processedCount;
    }

    public int maxParallel() {
        return maxParallel.get();
    }
}
    1. take() removes the message atomically, so two workers can never get the same one. A broker gives the same guarantee across machines.
    package com.handbook.microservices.competingconsumers.invoices;

public class InvoiceDemo {

    public static void main(String[] args) throws Exception {
        System.out.println("=== Grocery: 400 Invoice PDFs Shared by 4 Competing Workers ===");
        InvoiceWorkers workers = new InvoiceWorkers();
        for (int i = 1; i <= 400; i++) {
            workers.publish("ORD-" + i);
        }
        workers.runWith(4);
        long once = workers.processedCount().values().stream().filter(n -> n == 1).count();
        System.out.println("Invoices rendered      : " + workers.processedCount().size());
        System.out.println("Rendered exactly once  : " + once);
        System.out.println("Never more than 4 at a time: " + (workers.maxParallel() <= 4) + " (scale by adding workers, not code)");
    }
}

    Output:

    === Grocery: 400 Invoice PDFs Shared by 4 Competing Workers ===
Invoices rendered      : 400
Rendered exactly once  : 400
Never more than 4 at a time: true (scale by adding workers, not code)

    Why competing consumers here:

    • Work items are independent, so any worker can take any job.
    • Throughput scales linearly with workers until the bottleneck moves (CPU, the PDF service).
    • Checkout just enqueues and returns.

    Example 2: Visibility Timeout and Redelivery (Payments)¶

    Scenario: A payment gateway sends payment.captured webhooks. A worker receives one, starts settling, and its pod is killed by a deploy before it acknowledges. With an SQS-style queue, the message is hidden for 30 seconds rather than deleted; when the timeout passes without an ack, it becomes visible again and another worker processes it. Because the first attempt might have partly run, settlement is idempotent.

    Design:

    sequenceDiagram autonumber participant A as worker-A participant Q as Queue participant B as worker-B A->>Q: receive → evt_91 (hidden 30s) Note over A: crash, no ack B->>Q: receive at +5s → nothing Note over Q: +31s: visibility expired → visible again B->>Q: receive at +36s → evt_91 (attempt 2) B->>B: settle (idempotent by payment id) B->>Q: ack → deleted

    Full Code:

    package com.handbook.microservices.competingconsumers.visibility;

import java.time.Clock;
import java.time.Duration;
import java.time.Instant;
import java.util.ArrayDeque;
import java.util.Deque;
import java.util.HashMap;
import java.util.Map;
import java.util.Optional;

/** SQS-style queue: a received message is hidden, not deleted, until the worker acks it. */
public final class VisibilityQueue {

    public record Message(String id, String body, int receiveCount) { }

    private record InFlight(Message message, Instant visibleAgainAt) { }

    private final Deque<Message> visible = new ArrayDeque<>();
    private final Map<String, InFlight> inFlight = new HashMap<>();
    private final Clock clock;
    private final Duration visibilityTimeout;

    public VisibilityQueue(Clock clock, Duration visibilityTimeout) {
        this.clock = clock;
        this.visibilityTimeout = visibilityTimeout;
    }

    public void send(String id, String body) {
        visible.add(new Message(id, body, 0));
    }

    public Optional<Message> receive() {
        returnExpired();
        Message m = visible.poll();
        if (m == null) {
            return Optional.empty();
        }
        Message delivered = new Message(m.id(), m.body(), m.receiveCount() + 1);
        inFlight.put(m.id(), new InFlight(delivered, clock.instant().plus(visibilityTimeout))); // (1)!
        return Optional.of(delivered);
    }

    public void ack(String id) {
        inFlight.remove(id); // (2)!
    }

    private void returnExpired() {
        inFlight.values().removeIf(f -> {
            if (!clock.instant().isBefore(f.visibleAgainAt())) {
                visible.addFirst(f.message()); // (3)!
                return true;
            }
            return false;
        });
    }
}
    1. Receiving hides the message for the visibility timeout instead of deleting it.
    2. Only an explicit ack deletes it: no ack, no loss.
    3. Expired in-flight messages go back to the front for another consumer.
    package com.handbook.microservices.competingconsumers.visibility;

import com.handbook.microservices.competingconsumers.visibility.VisibilityQueue.Message;
import com.handbook.microservices.support.FakeClock;

import java.time.Duration;
import java.util.HashSet;
import java.util.Set;

public class WebhookDemo {

    public static void main(String[] args) {
        System.out.println("=== Payments: A Worker Crashes Mid-Webhook; Another Finishes It ===");
        FakeClock clock = FakeClock.at("2026-08-15T10:00:00Z");
        VisibilityQueue queue = new VisibilityQueue(clock, Duration.ofSeconds(30));
        queue.send("evt_91", "payment.captured pay_ABC INR 1,499");
        Set<String> settledPayments = new HashSet<>(); // the idempotency record

        Message m1 = queue.receive().orElseThrow();
        System.out.println("worker-A received " + m1.id() + " (attempt " + m1.receiveCount() + ") ... crashed before ack");
        System.out.println("worker-B polls at +5s  : " + queue.receive().map(Message::id).orElse("nothing (message still hidden)"));

        clock.advance(Duration.ofSeconds(31));
        Message m2 = queue.receive().orElseThrow();
        boolean firstTime = settledPayments.add("pay_ABC");
        queue.ack(m2.id());
        System.out.println("worker-B polls at +36s : " + m2.id() + " (attempt " + m2.receiveCount() + "), settled=" + firstTime + ", acked");
        System.out.println("worker-C polls later   : " + queue.receive().map(Message::id).orElse("nothing (done)"));
    }
}

    Output:

    === Payments: A Worker Crashes Mid-Webhook; Another Finishes It ===
worker-A received evt_91 (attempt 1) ... crashed before ack
worker-B polls at +5s  : nothing (message still hidden)
worker-B polls at +36s : evt_91 (attempt 2), settled=true, acked
worker-C polls later   : nothing (done)

    Why this matters:

    • Delivery is at-least-once: crashes cause redelivery, never silent loss.
    • So consumers must be idempotent (here: a set of settled payment ids).
    • The visibility timeout must exceed the normal processing time, or healthy jobs get processed twice.

    Example 3: Kafka Consumer Groups and Rebalancing (Ride-hailing)¶

    Scenario: Trip events are on a Kafka topic with 6 partitions, keyed by trip id so each trip's events stay in order. The trip-processing service autoscales from 1 to 7 pods. Kafka divides partitions among group members; when a pod joins or dies, partitions are rebalanced. With more pods than partitions, the extra pod has nothing to do.

    Design:

    flowchart LR subgraph "trip-events (6 partitions)" P0[p0] & P1[p1] & P2[p2] & P3[p3] & P4[p4] & P5[p5] end P0 & P1 --> A[pod-1] P2 & P3 --> B[pod-2] P4 & P5 --> C[pod-3]

    Full Code:

    package com.handbook.microservices.competingconsumers.groups;

import java.util.ArrayList;
import java.util.LinkedHashMap;
import java.util.List;
import java.util.Map;

/** Kafka-style consumer group: partitions are divided among members; each partition has ONE owner. */
public final class ConsumerGroup {

    private final int partitions;
    private final List<String> members = new ArrayList<>();

    public ConsumerGroup(int partitions) {
        this.partitions = partitions;
    }

    public Map<String, List<Integer>> join(String member) {
        members.add(member);
        return rebalance();
    }

    public Map<String, List<Integer>> leave(String member) {
        members.remove(member);
        return rebalance();
    }

    /** Range assignment, like Kafka's RangeAssignor. */
    private Map<String, List<Integer>> rebalance() { // (1)!
        Map<String, List<Integer>> assignment = new LinkedHashMap<>();
        members.forEach(m -> assignment.put(m, new ArrayList<>()));
        int per = partitions / members.size();
        int extra = partitions % members.size();
        int next = 0;
        for (int i = 0; i < members.size(); i++) {
            int count = per + (i < extra ? 1 : 0); // (2)!
            for (int k = 0; k < count; k++) {
                assignment.get(members.get(i)).add(next++);
            }
        }
        return assignment;
    }

    public static int partitionFor(String key, int partitions) {
        return Math.floorMod(key.hashCode(), partitions); // same key -> same partition -> same consumer, in order
    }
}
    1. Every membership change triggers a rebalance: partitions are reassigned so each has exactly one owner in the group.
    2. Range assignment: the first partitions % members consumers get one extra partition.
    package com.handbook.microservices.competingconsumers.groups;

public class ConsumerGroupDemo {

    public static void main(String[] args) {
        System.out.println("=== Ride-hailing: 'trip-events' (6 partitions) and a Scaling Consumer Group ===");
        ConsumerGroup group = new ConsumerGroup(6);
        System.out.println("pod-1 joins -> " + group.join("pod-1"));
        System.out.println("pod-2 joins -> " + group.join("pod-2"));
        System.out.println("pod-3 joins -> " + group.join("pod-3"));
        group.join("pod-4");
        group.join("pod-5");
        group.join("pod-6");
        System.out.println("pod-7 joins -> " + group.join("pod-7") + "  <- more consumers than partitions: one idles");
        System.out.println("pod-2 dies  -> " + group.leave("pod-2"));
        System.out.println("Trip TRIP-88 always goes to partition " + ConsumerGroup.partitionFor("TRIP-88", 6)
                + ", so its events are processed in order by whoever owns it.");
    }
}

    Output:

    === Ride-hailing: 'trip-events' (6 partitions) and a Scaling Consumer Group ===
pod-1 joins -> {pod-1=[0, 1, 2, 3, 4, 5]}
pod-2 joins -> {pod-1=[0, 1, 2], pod-2=[3, 4, 5]}
pod-3 joins -> {pod-1=[0, 1], pod-2=[2, 3], pod-3=[4, 5]}
pod-7 joins -> {pod-1=[0], pod-2=[1], pod-3=[2], pod-4=[3], pod-5=[4], pod-6=[5], pod-7=[]}  <- more consumers than partitions: one idles
pod-2 dies  -> {pod-1=[0], pod-3=[1], pod-4=[2], pod-5=[3], pod-6=[4], pod-7=[5]}
Trip TRIP-88 always goes to partition 2, so its events are processed in order by whoever owns it.

    Why consumer groups here:

    • Competition happens per partition, which preserves per-trip ordering.
    • Parallelism is capped by the partition count: choose it for peak load up front.
    • Failover is automatic: a dead pod's partitions move to survivors.
    Unit Tests: CompetingConsumersTest.java 
    package com.handbook.microservices;

import com.handbook.microservices.competingconsumers.groups.ConsumerGroup;
import com.handbook.microservices.competingconsumers.invoices.InvoiceWorkers;
import com.handbook.microservices.competingconsumers.visibility.VisibilityQueue;
import com.handbook.microservices.support.FakeClock;
import org.junit.jupiter.api.Test;

import java.time.Duration;
import java.util.List;
import java.util.Map;
import java.util.stream.Collectors;

import static org.assertj.core.api.Assertions.assertThat;

class CompetingConsumersTest {

    @Test
    void everyMessageIsProcessedExactlyOnceByTheGroup() throws Exception {
        InvoiceWorkers w = new InvoiceWorkers();
        for (int i = 0; i < 50; i++) {
            w.publish("O" + i);
        }
        w.runWith(3);
        assertThat(w.processedCount()).hasSize(50).allSatisfy((k, v) -> assertThat(v).isEqualTo(1));
        assertThat(w.maxParallel()).isBetween(1, 3);
    }

    @Test
    void unackedMessageReappearsAfterVisibilityTimeout() {
        FakeClock clock = FakeClock.at("2026-01-01T00:00:00Z");
        VisibilityQueue q = new VisibilityQueue(clock, Duration.ofSeconds(10));
        q.send("m", "x");
        q.receive();
        assertThat(q.receive()).isEmpty();
        clock.advance(Duration.ofSeconds(10));
        assertThat(q.receive()).get().extracting(VisibilityQueue.Message::receiveCount).isEqualTo(2);
    }

    @Test
    void partitionsAreSplitWithoutOverlap() {
        ConsumerGroup g = new ConsumerGroup(5);
        g.join("a");
        Map<String, List<Integer>> a = g.join("b");
        assertThat(a.get("a")).containsExactly(0, 1, 2);
        assertThat(a.get("b")).containsExactly(3, 4);
        assertThat(a.values().stream().flatMap(List::stream).collect(Collectors.toSet())).hasSize(5);
    }
}

    Where Competing consumers

    RabbitMQ Multiple consumers on a queue, basic.qos prefetch, manual acks, DLX

    8. Pros, Cons & Trade-offs¶

    ✅ Pros ❌ Cons
    Horizontal scaling by adding consumers No global ordering across consumers
    Load levelling: spikes become queue depth, not outages At-least-once delivery: duplicates must be handled
    Fault tolerance: unacked work is redelivered Poison messages can loop without a DLQ
    Producers and consumers deploy independently Kafka parallelism capped by partitions; rebalances pause processing

    9. Pitfalls & Anti-Patterns¶

    Non-idempotent consumers

    Redelivery after a crash, a rebalance or a visibility timeout is normal. Without idempotency, customers get two emails, or two refunds.

    No dead-letter queue

    A message that always fails is retried forever, burning capacity and (in Kafka) blocking its partition. Retry a bounded number of times, then dead-letter (coding challenge).

    Visibility timeout shorter than processing time

    A 30 s job with a 20 s timeout gets processed twice, every time. Size the timeout from p99 processing time, or extend it while working.

    Expecting order from a plain queue

    Ten consumers process messages in parallel; message 2 may finish before message 1. Use a key-partitioned log or FIFO groups for per-entity order.

    10. Senior / Architect Deep Dive (10–15 yrs)¶

    Capacity planning. Consumers needed ≈ arrival rate × processing time (Little's law). 200 msg/s × 0.4 s = 80 concurrent jobs. For Kafka, provision partitions for the peak consumer count you'll ever need; increasing partitions later changes key → partition mapping and breaks per-key ordering for in-flight keys.

    Rebalance storms. In Kafka, slow processing beyond max.poll.interval.ms makes the broker think the consumer died, triggering rebalances, redelivery and more slowness. Use smaller max.poll.records, cooperative-sticky assignment, static membership (group.instance.id) and offload slow work.

    Back-pressure to producers. A queue absorbs spikes, not sustained overload. Alert on age of the oldest message (not just depth), and shed or degrade at the producer when the backlog SLO is breached.

    War story: every webhook processed twice

    A team moved webhook handling to SQS with the default 30 s visibility timeout. The handler called a slow bank API (p99 45 s). Every slow message became visible again mid-processing and a second worker settled it too: 2,300 merchants were credited twice in one day. Fix: visibility timeout raised to 5 minutes with periodic extension (ChangeMessageVisibility) for long jobs, an idempotency table keyed by payment id, and a DLQ after 5 receives. Lesson: at-least-once is a promise of duplicates. Size timeouts and make consumers idempotent.

    Scope Across processes/machines Across services In one process In one process

    Kafka does both: consumers in the same group compete; different groups each get every message (pub-sub). See also Producer-Consumer, Idempotent Consumer and Backpressure.

    12. Interview Corner¶

    Q1. What is the competing consumers pattern?

    Multiple consumers read from one queue; each message goes to only one of them, so work is shared.

    Q2. How do you increase throughput?

    Add more consumer instances.

    Q3. What is an acknowledgement?

    The consumer telling the broker the message was processed, so it can be deleted or its offset committed.

    Q4. What is a dead-letter queue?

    A queue for messages that failed processing too many times.

    Q5. Queue vs topic?

    A queue delivers each message to one consumer; a topic delivers it to every subscriber (group).

    Q1. Why must consumers be idempotent?

    Brokers redeliver after crashes, timeouts and rebalances: at-least-once delivery.

    Q2. What's a visibility timeout?

    The time a received SQS message stays hidden; if not deleted by then, it becomes visible again.

    Q3. Why can't you have more Kafka consumers than partitions?

    You can, but each partition has one owner per group, so extra consumers sit idle.

    Q4. How do you keep order per customer?

    Partition by customer id (Kafka) or use FIFO queues with a message group id.

    Q5. What happens during a Kafka rebalance?

    Partitions are reassigned; uncommitted messages may be re-read by the new owner.

    Q1. "Design an email-sending system for 10M emails/hour with retries."

    Producer → queue partitioned by tenant; autoscaled consumers with provider rate limits (token bucket per provider); idempotency by message id; exponential backoff retries; DLQ; metrics on oldest-message age.

    Q2. "How many partitions would you create?"

    Enough for peak parallelism with headroom (peak rate × processing time), considering broker limits; avoid repartitioning live topics with key ordering needs.

    Q3. "Consumer lag keeps growing. Diagnose."

    Check processing time (slow downstream?), rebalances, partition skew (hot keys), consumer CPU/GC, and whether you're at max parallelism (partitions).

    Q4. "Exactly-once processing?"

    Effectively-once: at-least-once delivery + idempotent effects, or Kafka transactions for read-process-write within Kafka.

    Q5. "Poison message in an ordered partition?"

    Retry a bounded number of times, then dead-letter and decide whether later events for that key can proceed (park the key) to avoid inconsistent state.

    Problem: A queue contains an SMS job with an invalid phone number that always fails. Show how bounded retries plus a dead-letter queue keep good messages flowing.

    Solution 
    package com.handbook.microservices.competingconsumers.poison;

import java.util.ArrayDeque;
import java.util.ArrayList;
import java.util.Deque;
import java.util.HashMap;
import java.util.List;
import java.util.Map;

/** Coding challenge: one bad message must not block the queue or loop forever. */
public class PoisonMessageDemo {

    static final int MAX_RECEIVES = 3;

    public static void main(String[] args) {
        System.out.println("=== Challenge: Poison Messages and a Dead-Letter Queue ===");
        Deque<String> queue = new ArrayDeque<>(List.of("sms:+919845000001", "sms:NOT-A-NUMBER", "sms:+919845000002"));
        Map<String, Integer> receives = new HashMap<>();
        List<String> sent = new ArrayList<>();
        List<String> deadLetters = new ArrayList<>();

        while (!queue.isEmpty()) {
            String msg = queue.poll();
            int attempt = receives.merge(msg, 1, Integer::sum);
            try {
                String number = msg.substring(4);
                if (!number.matches("\\+91\\d{10}")) {
                    throw new IllegalArgumentException("invalid number " + number);
                }
                sent.add(number);
            } catch (IllegalArgumentException e) {
                if (attempt >= MAX_RECEIVES) {
                    deadLetters.add(msg + " (" + e.getMessage() + ", " + attempt + " attempts)"); // park it for humans
                } else {
                    queue.addLast(msg); // retry later, behind other work
                }
            }
        }
        System.out.println("Sent        : " + sent);
        System.out.println("Dead letters: " + deadLetters);
        System.out.println("Good messages weren't blocked, and the bad one stopped after " + MAX_RECEIVES + " tries.");
    }
}

    Output:

    === Challenge: Poison Messages and a Dead-Letter Queue ===
Sent        : [+919845000001, +919845000002]
Dead letters: [sms:NOT-A-NUMBER (invalid number NOT-A-NUMBER, 3 attempts)]
Good messages weren't blocked, and the bad one stopped after 3 tries.

    Key points to say: count receives per message (ApproximateReceiveCount, delivery attempts); retry behind other work rather than immediately; dead-letter after N; alert on DLQ depth and provide a replay tool once the bug or data is fixed.

    Behavioural tie-in (STAR) for experienced candidates

    • S: Merchants were credited twice because webhook processing outlived SQS's visibility timeout.
    • T: Stop duplicate credits without slowing webhook handling.
    • A: Sized and extended visibility timeouts from p99 processing time, added an idempotency table keyed by payment id, a DLQ after 5 receives, and autoscaling on oldest-message age.
    • R: Duplicate credits went to zero; backlog during sales stayed under 2 minutes with 3× the traffic.

    13. Quick Revision Card¶

    Remember in 30 seconds

    • One queue, many identical consumers; each message to one.
    • Ack after success; unacked = redelivered (at-least-once).
    • Consumers idempotent; bounded retries → DLQ.
    • Kafka: one owner per partition; parallelism ≤ partitions; key = order.
    • Scale on lag / oldest-message age.
