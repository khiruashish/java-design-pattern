    Intermediate Microservices Resilience

    Circuit Breaker¶

    🟡 Intermediate Microservices Interview frequency ⭐⭐⭐⭐⭐

    TL;DR

    A circuit breaker wraps calls to a dependency and watches the failures. When they cross a threshold it "opens" and fails fast (or serves a fallback) without calling the dependency. After a cool-down it lets a few trial calls through ("half-open") and closes again if they succeed. It stops one sick service from tying up threads everywhere and gives it room to recover.

    1. Intent & Problem It Solves¶

    The problem in plain English: the payment provider starts timing out after 10 seconds. Every checkout thread now waits 10 s, the thread pool fills up, and checkout stops working for everyone, including requests that never touch payments. Meanwhile, the struggling provider is hammered with retries and can't recover. That's a cascading failure.

    Definition (Michael Nygard, Release It!; popularized by Martin Fowler):

    Wrap a protected function call in a circuit breaker object, which monitors for failures. Once the failures reach a certain threshold, the circuit breaker trips, and all further calls return with an error, without the protected call being made at all.

    The state machine:

    stateDiagram-v2
    [*] --> CLOSED
    CLOSED --> OPEN: failure rate ≥ threshold<br/>(over last N calls, after min calls)
    OPEN --> HALF_OPEN: wait duration elapsed
    HALF_OPEN --> CLOSED: trial calls succeed
    HALF_OPEN --> OPEN: a trial call fails

    2. Real-World Analogy¶

    The electrical breaker in your home

    When a faulty heater draws too much current, the breaker trips and cuts power to that circuit before the wiring catches fire. The rest of the house keeps working. After fixing the heater, you flip the breaker back and see whether it holds.

    3. Structure¶

    Participant Responsibility
    Caller Calls through the breaker; supplies a fallback
    Circuit breaker Records outcomes in a sliding window, manages state, fails fast when OPEN
    Protected dependency Remote service, database, third-party API
    Fallback Cached data, a default, a queued request, or a clear error

    Key configuration (Resilience4j names): slidingWindowSize, minimumNumberOfCalls, failureRateThreshold, waitDurationInOpenState, permittedNumberOfCallsInHalfOpenState, plus slowCallDurationThreshold / slowCallRateThreshold.

    4. Naive Approach (Without the Pattern)¶

    public String pay(String orderId) {
    return paymentHttp.post(orderId); // 10 s read timeout
}
// Provider degrades → 200 checkout threads all blocked for 10 s
// → the thread pool is exhausted → browsing and cart APIs on the same service time out too
// → clients retry → even more blocked threads → total outage

    5. Three Real-World Examples¶

    All three examples use the same small breaker, modelled on Resilience4j's count-based state machine:

    package com.handbook.microservices.circuitbreaker.core;

import java.time.Clock;
import java.time.Duration;
import java.time.Instant;
import java.util.ArrayDeque;
import java.util.Deque;
import java.util.function.Function;
import java.util.function.Supplier;

/**
 * A count-based circuit breaker modelled on Resilience4j's state machine.
 * <pre>
 *   CLOSED --(failure rate >= threshold over the last N calls)--> OPEN
 *   OPEN   --(wait duration elapsed)--> HALF_OPEN
 *   HALF_OPEN --(trial calls succeed)--> CLOSED, --(any trial call fails)--> OPEN
 * </pre>
 */
public final class CircuitBreaker {

    public enum State { CLOSED, OPEN, HALF_OPEN }

    public record Config(int windowSize, int minimumCalls, int failureRatePercent,
                         Duration waitInOpen, int trialCalls) {
    }

    public static final class OpenException extends RuntimeException {
        OpenException(String name) {
            super(name + " circuit is OPEN");
        }
    }

    private final String name;
    private final Config config;
    private final Clock clock;
    private final Deque<Boolean> window = new ArrayDeque<>(); // true = failure
    private State state = State.CLOSED;
    private Instant openedAt;
    private int trialSuccesses;

    public CircuitBreaker(String name, Config config, Clock clock) {
        this.name = name;
        this.config = config;
        this.clock = clock;
    }

    public synchronized State state() {
        if (state == State.OPEN && !clock.instant().isBefore(openedAt.plus(config.waitInOpen()))) {
            transition(State.HALF_OPEN); // (1)!
        }
        return state;
    }

    public <T> T call(Supplier<T> action, Function<Throwable, T> fallback) {
        try {
            return call(action);
        } catch (RuntimeException e) {
            return fallback.apply(e); // (2)!
        }
    }

    public <T> T call(Supplier<T> action) {
        if (state() == State.OPEN) {
            throw new OpenException(name); // (3)!
        }
        try {
            T result = action.get();
            record(false);
            return result;
        } catch (RuntimeException e) {
            record(true);
            throw e;
        }
    }

    private synchronized void record(boolean failure) {
        if (state == State.HALF_OPEN) { // (4)!
            if (failure) {
                trip();
            } else if (++trialSuccesses >= config.trialCalls()) {
                window.clear();
                transition(State.CLOSED);
            }
            return;
        }
        window.addLast(failure);
        if (window.size() > config.windowSize()) {
            window.removeFirst();
        }
        long failures = window.stream().filter(f -> f).count();
        if (window.size() >= config.minimumCalls() // (5)!
                && failures * 100 / window.size() >= config.failureRatePercent()) {
            trip();
        }
    }

    private void trip() {
        openedAt = clock.instant();
        transition(State.OPEN);
    }

    private void transition(State to) {
        System.out.println("    [" + name + "] " + state + " -> " + to);
        state = to;
        trialSuccesses = 0;
    }
}
    1. OPEN → HALF_OPEN happens lazily when someone asks for the state after the wait duration.
    2. The fallback receives the exception, so it can tell "circuit open" from "real failure".
    3. Fail fast: no network call, no waiting, so threads are freed immediately.
    4. In HALF_OPEN, one failure re-opens; enough successes close the circuit with a fresh window.
    5. minimumCalls prevents opening on 1 failure out of 1 call (100%) at startup.

    Example 1: Checkout → Payment Provider (Grocery)¶

    Scenario: A window of 4 calls, at least 4 calls before deciding, and a 50% failure threshold. When the provider starts timing out, the breaker opens and orders are queued for retry instead of failing (the customer sees "payment processing"). While OPEN, the provider receives zero calls. After 30 s, a trial call succeeds and the circuit closes.

    Design:

    sequenceDiagram
    participant C as Checkout
    participant B as Breaker
    participant P as Payment provider
    C->>B: ORD-3, ORD-4
    B->>P: calls time out
    Note over B: 2/4 failed = 50% → OPEN
    C->>B: ORD-5, ORD-6
    B-->>C: fail fast → queued
    Note over B: +30 s → HALF_OPEN
    C->>B: ORD-7
    B->>P: trial call OK
    Note over B: 2 trials OK → CLOSED

    Full Code:

    package com.handbook.microservices.circuitbreaker.grocery;

import com.handbook.microservices.circuitbreaker.core.CircuitBreaker;

import java.util.function.Supplier;

/** Checkout calls the payment provider through a breaker; when it's open, orders are queued, not lost. */
public final class PaymentClient {

    private final CircuitBreaker breaker;
    private final Supplier<String> provider;

    public PaymentClient(CircuitBreaker breaker, Supplier<String> provider) {
        this.breaker = breaker;
        this.provider = provider;
    }

    public String pay(String orderId) {
        return breaker.call(
                () -> orderId + " paid (" + provider.get() + ")",
                e -> orderId + " queued for retry: " + e.getMessage()); // (1)!
    }
}
    1. The fallback queues the payment for a background retry. This is a business decision: the order isn't lost, and the customer is told payment is pending.
    package com.handbook.microservices.circuitbreaker.grocery;

import com.handbook.microservices.circuitbreaker.core.CircuitBreaker;
import com.handbook.microservices.circuitbreaker.core.CircuitBreaker.Config;
import com.handbook.microservices.support.FakeClock;

import java.time.Duration;
import java.util.concurrent.atomic.AtomicBoolean;
import java.util.concurrent.atomic.AtomicInteger;

public class PaymentBreakerDemo {

    public static void main(String[] args) {
        FakeClock clock = FakeClock.at("2026-10-13T18:00:00Z");
        AtomicBoolean providerDown = new AtomicBoolean(false);
        AtomicInteger providerCalls = new AtomicInteger();

        var breaker = new CircuitBreaker("payment", new Config(4, 4, 50, Duration.ofSeconds(30), 2), clock);
        var client = new PaymentClient(breaker, () -> {
            providerCalls.incrementAndGet();
            if (providerDown.get()) {
                throw new IllegalStateException("provider timeout");
            }
            return "txn-ok";
        });

        System.out.println("=== Grocery: checkout -> payment provider ===");
        pay(client, "ORD-1");
        pay(client, "ORD-2");
        System.out.println("-- provider starts timing out --");
        providerDown.set(true);
        pay(client, "ORD-3");
        pay(client, "ORD-4");
        int before = providerCalls.get();
        pay(client, "ORD-5");
        pay(client, "ORD-6");
        System.out.println("Provider calls while OPEN: " + (providerCalls.get() - before) + " (fail fast, no waiting)");

        System.out.println("-- 30 s later, provider has recovered --");
        clock.advance(Duration.ofSeconds(30));
        providerDown.set(false);
        pay(client, "ORD-7");
        pay(client, "ORD-8");
        pay(client, "ORD-9");
    }

    private static void pay(PaymentClient client, String orderId) {
        System.out.println(client.pay(orderId));
    }
}

    Output:

    === Grocery: checkout -> payment provider ===
ORD-1 paid (txn-ok)
ORD-2 paid (txn-ok)
-- provider starts timing out --
ORD-3 queued for retry: provider timeout
    [payment] CLOSED -> OPEN
ORD-4 queued for retry: provider timeout
ORD-5 queued for retry: payment circuit is OPEN
ORD-6 queued for retry: payment circuit is OPEN
Provider calls while OPEN: 0 (fail fast, no waiting)
-- 30 s later, provider has recovered --
    [payment] OPEN -> HALF_OPEN
ORD-7 paid (txn-ok)
    [payment] HALF_OPEN -> CLOSED
ORD-8 paid (txn-ok)
ORD-9 paid (txn-ok)

    Why a circuit breaker here:

    • Checkout threads aren't held hostage by a slow provider.
    • The provider gets breathing room to recover.
    • Automatic recovery: no human has to "turn payments back on".

    Example 2: ETA with a Degraded Fallback (Ride-hailing)¶

    Scenario: The traffic-aware routing engine gives accurate ETAs. During its deploy it returns 503s. Riders still need some ETA, so the fallback estimates from straight-line distance. The example also shows a failed trial: HALF_OPEN → OPEN when the engine is still down, then a successful trial 10 s later.

    Full Code:

    package com.handbook.microservices.circuitbreaker.ridehailing;

import com.handbook.microservices.circuitbreaker.core.CircuitBreaker;

import java.util.function.ToIntFunction;

/**
 * The traffic-aware routing engine gives accurate ETAs. If it's unhealthy, the breaker opens and
 * riders get a rougher estimate from straight-line distance instead of an error screen.
 */
public final class EtaService {

    public record Trip(String id, double distanceKm) {
    }

    private final CircuitBreaker breaker;
    private final ToIntFunction<Trip> routingEngine;

    public EtaService(CircuitBreaker breaker, ToIntFunction<Trip> routingEngine) {
        this.breaker = breaker;
        this.routingEngine = routingEngine;
    }

    public String eta(Trip trip) {
        return breaker.call(
                () -> routingEngine.applyAsInt(trip) + " min (live traffic)",
                e -> estimate(trip) + " min (estimate)"); // (1)!
    }

    private static int estimate(Trip trip) {
        return (int) Math.ceil(trip.distanceKm() / 25.0 * 60 * 1.3); // 25 km/h city average, 30% detour
    }
}
    1. A degraded but useful answer, labelled as an estimate so the UI can show "~25 min".
    package com.handbook.microservices.circuitbreaker.ridehailing;

import com.handbook.microservices.circuitbreaker.core.CircuitBreaker;
import com.handbook.microservices.circuitbreaker.core.CircuitBreaker.Config;
import com.handbook.microservices.circuitbreaker.ridehailing.EtaService.Trip;
import com.handbook.microservices.support.FakeClock;

import java.time.Duration;
import java.util.concurrent.atomic.AtomicBoolean;

public class EtaBreakerDemo {

    public static void main(String[] args) {
        FakeClock clock = FakeClock.at("2026-10-13T08:00:00Z");
        AtomicBoolean engineHealthy = new AtomicBoolean(true);
        var breaker = new CircuitBreaker("routing", new Config(5, 3, 60, Duration.ofSeconds(10), 1), clock);
        var eta = new EtaService(breaker, trip -> {
            if (!engineHealthy.get()) {
                throw new IllegalStateException("routing engine 503");
            }
            return (int) Math.round(trip.distanceKm() * 2.4);
        });

        System.out.println("=== Ride-hailing: ETA with a degraded fallback ===");
        System.out.println("trip-1 (5 km):  " + eta.eta(new Trip("trip-1", 5)));
        engineHealthy.set(false);
        System.out.println("-- routing engine fails during a deploy --");
        for (int i = 2; i <= 5; i++) {
            System.out.println("trip-" + i + " (8 km):  " + eta.eta(new Trip("trip-" + i, 8)));
        }
        System.out.println("-- 10 s later: one trial call while the engine is still down --");
        clock.advance(Duration.ofSeconds(10));
        System.out.println("trip-6 (8 km):  " + eta.eta(new Trip("trip-6", 8)));
        System.out.println("-- another 10 s: engine is back --");
        clock.advance(Duration.ofSeconds(10));
        engineHealthy.set(true);
        System.out.println("trip-7 (8 km):  " + eta.eta(new Trip("trip-7", 8)));
        System.out.println("Breaker state: " + breaker.state());
    }
}

    Output:

    === Ride-hailing: ETA with a degraded fallback ===
trip-1 (5 km):  12 min (live traffic)
-- routing engine fails during a deploy --
trip-2 (8 km):  25 min (estimate)
    [routing] CLOSED -> OPEN
trip-3 (8 km):  25 min (estimate)
trip-4 (8 km):  25 min (estimate)
trip-5 (8 km):  25 min (estimate)
-- 10 s later: one trial call while the engine is still down --
    [routing] OPEN -> HALF_OPEN
    [routing] HALF_OPEN -> OPEN
trip-6 (8 km):  25 min (estimate)
-- another 10 s: engine is back --
    [routing] OPEN -> HALF_OPEN
    [routing] HALF_OPEN -> CLOSED
trip-7 (8 km):  19 min (live traffic)
Breaker state: CLOSED

    Why a circuit breaker here:

    • The app keeps working with lower quality instead of failing.
    • A failed trial re-opens immediately, so the engine isn't flooded the moment the wait ends.

    Example 3: Personalised Rows with Layered Fallbacks (Streaming)¶

    Scenario: At Friday 9 pm the recommender is overloaded. The home screen must never fail, so the client falls back to the profile's last good recommendations, then to a global "Popular now" row for profiles with no cache. The open breaker also sheds load from the recommender during its worst moment.

    Full Code:

    package com.handbook.microservices.circuitbreaker.streaming;

import com.handbook.microservices.circuitbreaker.core.CircuitBreaker;

import java.util.List;
import java.util.Map;
import java.util.concurrent.ConcurrentHashMap;
import java.util.function.Function;

/**
 * Personalised rows are nice to have. If the recommender is struggling, fall back to the profile's
 * last good response, then to a global "Popular now" row. The home screen never fails.
 */
public final class RecommendationsClient {

    private final CircuitBreaker breaker;
    private final Function<String, List<String>> recommender;
    private final Map<String, List<String>> lastGood = new ConcurrentHashMap<>();
    private final List<String> popularNow;

    public RecommendationsClient(CircuitBreaker breaker, Function<String, List<String>> recommender,
                                 List<String> popularNow) {
        this.breaker = breaker;
        this.recommender = recommender;
        this.popularNow = popularNow;
    }

    public String row(String profileId) {
        return breaker.call(() -> {
            List<String> titles = recommender.apply(profileId);
            lastGood.put(profileId, titles); // (1)!
            return "For you " + titles;
        }, e -> {
            List<String> cached = lastGood.get(profileId);
            return cached != null ? "For you (cached) " + cached : "Popular now " + popularNow; // (2)!
        });
    }
}
    1. Every success refreshes the last-good cache.
    2. Layered fallback: personal cache → global default. Each layer is cheaper and less personal.
    package com.handbook.microservices.circuitbreaker.streaming;

import com.handbook.microservices.circuitbreaker.core.CircuitBreaker;
import com.handbook.microservices.circuitbreaker.core.CircuitBreaker.Config;
import com.handbook.microservices.support.FakeClock;

import java.time.Duration;
import java.util.List;
import java.util.concurrent.atomic.AtomicBoolean;

public class RecommendationsBreakerDemo {

    public static void main(String[] args) {
        FakeClock clock = FakeClock.at("2026-10-13T21:00:00Z");
        AtomicBoolean overloaded = new AtomicBoolean(false);
        var breaker = new CircuitBreaker("recommender", new Config(4, 2, 50, Duration.ofSeconds(60), 1), clock);
        var client = new RecommendationsClient(breaker, profile -> {
            if (overloaded.get()) {
                throw new IllegalStateException("recommender overloaded");
            }
            return profile.equals("P-1") ? List.of("Monsoon Express", "Spice Route") : List.of("Byte Club");
        }, List.of("City of Rain", "Monsoon Express"));

        System.out.println("=== Streaming: personalised row with layered fallbacks ===");
        System.out.println("P-1: " + client.row("P-1"));
        System.out.println("-- Friday 9 pm peak: recommender overloaded --");
        overloaded.set(true);
        System.out.println("P-1: " + client.row("P-1"));
        System.out.println("P-2: " + client.row("P-2"));
        System.out.println("P-1: " + client.row("P-1") + "   <- breaker open, recommender not called");
        System.out.println("P-3: " + client.row("P-3"));
    }
}

    Output:

    === Streaming: personalised row with layered fallbacks ===
P-1: For you [Monsoon Express, Spice Route]
-- Friday 9 pm peak: recommender overloaded --
    [recommender] CLOSED -> OPEN
P-1: For you (cached) [Monsoon Express, Spice Route]
P-2: Popular now [City of Rain, Monsoon Express]
P-1: For you (cached) [Monsoon Express, Spice Route]   <- breaker open, recommender not called
P-3: Popular now [City of Rain, Monsoon Express]

    Why a circuit breaker here:

    • Optional features degrade invisibly; viewers still get a full home screen.
    • Load shedding during peaks helps the recommender recover faster.
    Unit Tests: CircuitBreakerTest.java 
    package com.handbook.microservices;

import com.handbook.microservices.circuitbreaker.core.CircuitBreaker;
import com.handbook.microservices.circuitbreaker.core.CircuitBreaker.Config;
import com.handbook.microservices.circuitbreaker.core.CircuitBreaker.State;
import com.handbook.microservices.support.FakeClock;
import org.junit.jupiter.api.Test;

import java.time.Duration;
import java.util.function.Supplier;

import static org.assertj.core.api.Assertions.assertThat;
import static org.assertj.core.api.Assertions.assertThatThrownBy;

class CircuitBreakerTest {

    private final FakeClock clock = FakeClock.at("2026-01-01T00:00:00Z");
    private final CircuitBreaker breaker = new CircuitBreaker("t", new Config(4, 4, 50, Duration.ofSeconds(10), 1), clock);
    private final Supplier<String> failing = () -> {
        throw new IllegalStateException("boom");
    };

    @Test
    void opensAtFailureRateAndFailsFast() {
        breaker.call(() -> "ok", e -> "fb");
        breaker.call(() -> "ok", e -> "fb");
        breaker.call(failing, e -> "fb");
        assertThat(breaker.state()).isEqualTo(State.CLOSED); // only 3 calls, minimum is 4
        breaker.call(failing, e -> "fb");
        assertThat(breaker.state()).isEqualTo(State.OPEN);
        assertThatThrownBy(() -> breaker.call(() -> "ok")).isInstanceOf(CircuitBreaker.OpenException.class);
    }

    @Test
    void halfOpenTrialClosesOrReopens() {
        for (int i = 0; i < 4; i++) {
            breaker.call(failing, e -> "fb");
        }
        clock.advance(Duration.ofSeconds(10));
        assertThat(breaker.state()).isEqualTo(State.HALF_OPEN);
        breaker.call(failing, e -> "fb");
        assertThat(breaker.state()).isEqualTo(State.OPEN);
        clock.advance(Duration.ofSeconds(10));
        assertThat(breaker.call(() -> "ok", e -> "fb")).isEqualTo("ok");
        assertThat(breaker.state()).isEqualTo(State.CLOSED);
    }
}

    6. Variations & Modern Java Take¶

    Resilience4j with Spring Boot (the standard choice; Hystrix is in maintenance mode). This class is compiled in the repo's spring-reference module:

    package com.handbook.springref.resilience;

import io.github.resilience4j.bulkhead.annotation.Bulkhead;
import io.github.resilience4j.circuitbreaker.annotation.CircuitBreaker;
import io.github.resilience4j.ratelimiter.annotation.RateLimiter;
import io.github.resilience4j.retry.annotation.Retry;
import org.springframework.stereotype.Component;
import org.springframework.web.client.RestClient;

/**
 * Resilience4j annotations on a Spring bean. Order of decoration (outermost first) by default:
 * Retry ( CircuitBreaker ( RateLimiter ( Bulkhead ( call ) ) ) ).
 * Instances "payment" are configured in application.yml (see the Circuit Breaker page).
 */
@Component
public class PaymentProviderClient {

    private final RestClient http;

    public PaymentProviderClient(RestClient.Builder builder) {
        this.http = builder.baseUrl("https://payments.example.com").build();
    }

    @Retry(name = "payment")
    @CircuitBreaker(name = "payment", fallbackMethod = "queueForLater")
    @RateLimiter(name = "payment")
    @Bulkhead(name = "payment")
    public String charge(String orderId, long amountPaise) {
        return http.post()
                .uri("/charges")
                .header("Idempotency-Key", orderId) // retries must not double-charge
                .body(new ChargeRequest(orderId, amountPaise))
                .retrieve()
                .body(String.class);
    }

    /** Same parameters plus the exception; called when the call fails or the circuit is open. */
    String queueForLater(String orderId, long amountPaise, Throwable cause) {
        return "QUEUED:" + orderId;
    }

    9. Pitfalls & Anti-Patterns¶

    Counting business errors as failures

    "Card declined" (HTTP 402/422) is a correct answer, not an outage. Counting it opens the breaker on a busy shopping day. Use ignoreExceptions / recordExceptions.

    Breaker without timeouts

    A breaker records a failure only when a call ends. Without a timeout, a hung call never ends, so it never counts. Always pair breakers with timeouts.

    Retry outside the breaker hammering an open circuit

    Retrying CallNotPermittedException is pointless. Configure retries to ignore it, and keep retry counts small.

    One breaker for many endpoints

    If /search is down but /orders is fine, a shared breaker blocks both. Use breakers per dependency and per operation where behaviour differs.

    10. Senior / Architect Deep Dive (10–15 yrs)¶

    Composition order. Resilience4j's default aspect order is Retry ( CircuitBreaker ( RateLimiter ( TimeLimiter ( Bulkhead ( call ))))). Retry wraps the breaker, so each retry attempt is counted and an open circuit stops retries quickly. Think about whether that's what you want, and document it.

    Fallback design is product design. Options: cached/stale data, default values, degraded computation, queue for later, or a clear error. Payments → queue; recommendations → popular list; balances → error (stale balances are dangerous). Discuss with product owners.

    Observability. Export state transitions and failure rates (Micrometer → Prometheus). Alert on OPEN for critical dependencies; dashboards show which dependency is sick across all callers.

    Production checklist¶

    • Timeouts on every remote call, inside the breaker.
    • Record only infrastructure failures (5xx, timeouts, connection errors); ignore business errors.
    • Slow-call thresholds for latency-driven failures.
    • A meaningful fallback per use case, agreed with product.
    • Metrics + alerts on state transitions; dashboards per dependency.
    • Chaos tests (inject latency/failures) to verify breakers actually open.

    Explain it in 2 minutes (system design round)¶

    "Every synchronous dependency call goes through Resilience4j: a timeout, a circuit breaker (e.g. 50% failures or 80% slow calls over the last 20 calls, open for 30 s, 3 trial calls), a bulkhead to cap concurrency, and limited retries with jitter for idempotent calls only. Each has a fallback that makes business sense: recommendations fall back to popular items, payments get queued and confirmed asynchronously. Breaker state is exported as metrics with alerts, so a sick dependency is visible in one dashboard."

    War story: the breaker that tripped on success

    A food-delivery checkout counted all exceptions as failures, including PromoCodeExpiredException. During a marketing campaign, thousands of users entered an expired promo code. The breaker around the pricing service opened, and all checkouts for 30 s got the fallback "pricing unavailable" error. It kept re-opening for an hour. Fix: ignoreExceptions for business errors; record only timeouts, connection failures and 5xx. Lesson: a circuit breaker should measure the health of the dependency, not the validity of user input.

    12. Interview Corner¶

    Q1. What is a circuit breaker?

    A wrapper around remote calls that stops calling a failing service for a while (fails fast or uses a fallback), then tests whether it has recovered.

    Q2. Name its three states.

    CLOSED (normal), OPEN (fail fast), HALF_OPEN (a few trial calls).

    Q3. Which library do you use in Spring Boot?

    Resilience4j with @CircuitBreaker(name = "...", fallbackMethod = "..."). Hystrix is legacy.

    Q4. What is a fallback method?

    An alternative response when the call fails or the circuit is open: cached data, a default, or a friendly error. It has the same parameters plus a Throwable.

    Q5. Why is it important in microservices?

    It prevents cascading failures: one slow service can't exhaust threads in all its callers.

    Q1. Count-based vs. time-based sliding window?

    Count-based: the last N calls. Time-based: calls in the last N seconds. Time-based behaves better under very variable traffic.

    Q2. Why minimumNumberOfCalls?

    So 1 failure out of 1 call (100%) after a restart doesn't open the circuit.

    Q3. How do slow calls trip a breaker?

    Calls longer than slowCallDurationThreshold are counted as slow; if the slow-call rate exceeds its threshold, the circuit opens even without errors.

    Q4. Retry + circuit breaker: which wraps which?

    By default in Resilience4j, Retry wraps the CircuitBreaker: each attempt is recorded, and once OPEN, retries fail fast. Don't retry CallNotPermittedException.

    Q5. What should not count as a failure?

    Business/validation errors (4xx), like "insufficient funds". Only infrastructure failures should count.

    Q1. "Design resilience for checkout calling 5 dependencies."

    Classify dependencies (critical: inventory, payment; optional: recommendations, loyalty), a timeout + breaker + bulkhead per dependency, fallbacks per business rules (queue payment, skip loyalty), a deadline for the whole request, and metrics/alerts per breaker.

    Q2. "100 instances each have their own breaker. Problems?"

    Each sees only its own traffic, so they open at different times and low-traffic instances may never reach the minimum. Usually acceptable; alternatives are mesh-level outlier detection or shared state (rarely worth it).

    Q3. "How do you pick thresholds?"

    From SLOs and real traffic: window large enough for statistical meaning, wait duration near typical recovery time, slow-call threshold from the dependency's p99. Validate with chaos experiments and tune from metrics.

    Q4. "When is a fallback dangerous?"

    When stale or default data causes wrong decisions: account balances, stock levels for overselling, prices. Then fail clearly instead.

    Q5. "Circuit breaker vs. outlier detection in a service mesh?"

    App breakers protect per dependency/operation with business-aware fallbacks; mesh outlier detection ejects individual bad hosts from load balancing. They complement each other.

    Problem: Implement a minimal, thread-safe circuit breaker in about 40 lines: it opens after N consecutive failures, stays open for T ms, then lets one trial call through.

    Solution 
    package com.handbook.microservices.circuitbreaker.mini;

import java.util.function.LongSupplier;
import java.util.function.Supplier;

/** Coding challenge: a minimal, thread-safe breaker that opens after N consecutive failures. */
public final class MiniCircuitBreaker {

    private final int failureThreshold;
    private final long openMillis;
    private final LongSupplier nowMillis;
    private int consecutiveFailures;
    private long openedAt = -1;

    public MiniCircuitBreaker(int failureThreshold, long openMillis, LongSupplier nowMillis) {
        this.failureThreshold = failureThreshold;
        this.openMillis = openMillis;
        this.nowMillis = nowMillis;
    }

    public synchronized <T> T call(Supplier<T> action, Supplier<T> fallback) {
        boolean open = openedAt >= 0 && nowMillis.getAsLong() - openedAt < openMillis;
        if (open) {
            return fallback.get();
        }
        // CLOSED, or the open period is over (HALF_OPEN): let this call through as a trial.
        try {
            T result = action.get();
            consecutiveFailures = 0;
            openedAt = -1;
            return result;
        } catch (RuntimeException e) {
            if (++consecutiveFailures >= failureThreshold || openedAt >= 0) {
                openedAt = nowMillis.getAsLong(); // trip, or re-trip after a failed trial
            }
            return fallback.get();
        }
    }

    public synchronized String state() {
        if (openedAt < 0) {
            return "CLOSED";
        }
        return nowMillis.getAsLong() - openedAt < openMillis ? "OPEN" : "HALF_OPEN";
    }
}

    package com.handbook.microservices.circuitbreaker.mini;

import java.util.concurrent.atomic.AtomicLong;

public class MiniBreakerDemo {

    public static void main(String[] args) {
        AtomicLong now = new AtomicLong(0);
        var breaker = new MiniCircuitBreaker(3, 5_000, now::get);
        String[] results = {"ok", "fail", "fail", "fail", "ok", "ok"};

        System.out.println("=== Challenge: minimal circuit breaker (3 consecutive failures, 5 s open) ===");
        for (String r : results) {
            String out = breaker.call(() -> {
                if (r.equals("fail")) {
                    throw new IllegalStateException();
                }
                return "real";
            }, () -> "fallback");
            System.out.printf("t=%4dms service=%-4s -> %-8s state=%s%n", now.get(), r, out, breaker.state());
            now.addAndGet(1_000);
        }
        now.set(9_000);
        String out = breaker.call(() -> "real", () -> "fallback");
        System.out.printf("t=%4dms service=ok   -> %-8s state=%s%n", now.get(), out, breaker.state());
    }
}
