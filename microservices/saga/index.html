    Advanced Data Microservices

    Saga¶

    🔴 Advanced Microservices Interview frequency ⭐⭐⭐⭐⭐

    TL;DR

    A saga keeps data consistent across services without a distributed transaction. It is a sequence of local transactions, one per service. If a step fails, the saga runs compensating transactions that semantically undo the steps already completed. It can be coordinated by an orchestrator (a central "conductor") or by choreography (services reacting to each other's events).

    1. Intent & Problem It Solves¶

    The problem in plain English: placing a grocery order touches inventory (reserve stock), payments (charge the card) and delivery (book a slot). Each service has its own database, so there's no single BEGIN ... COMMIT across them. Two-phase commit (2PC/XA) is slow, couples services' availability, and isn't supported by most brokers and NoSQL stores. Yet "charged but no delivery slot" is unacceptable.

    Definition (Hector Garcia-Molina & Kenneth Salem, 1987; microservices.io):

    A saga is a sequence of local transactions. Each local transaction updates the database and publishes a message or event to trigger the next local transaction. If a local transaction fails, the saga executes a series of compensating transactions that undo the changes made by the preceding local transactions.

    Key vocabulary:

    Term Meaning
    Compensating transaction Semantic undo: refund a charge, release a reservation (not a database rollback)
    Pivot transaction The go/no-go step; after it succeeds, the saga must complete
    Retriable transaction Steps after the pivot; retried until they succeed
    Orchestration A coordinator tells each participant what to do
    Choreography Participants subscribe to events and decide what to do next

    2. Real-World Analogy¶

    Planning a trip with separate bookings

    You book a flight, then a hotel, then try to pay for a tour. The tour is sold out, so you cancel the hotel and cancel the flight, in reverse order, maybe paying a cancellation fee. Nobody "rolls back time"; you perform new actions that undo the effect. That's a saga.

    3. Structure¶

    flowchart LR
    subgraph Orchestration
      O[Order saga<br/>orchestrator] -->|1 reserve| I[Inventory]
      O -->|2 charge| P[Payment]
      O -->|3 schedule| D[Delivery]
      O -.->|undo: refund| P
      O -.->|undo: release| I
    end
    flowchart LR
    subgraph Choreography
      A[Order: OrderCreated] --> B[Inventory: StockReserved]
      B --> C[Payment: PaymentCompleted]
      C --> E[Delivery: SlotBooked]
      C -.->|PaymentFailed| B2[Inventory releases stock]
    end
    Orchestration Choreography
    Flow visible in One class Spread across services
    Coupling Orchestrator knows participants Services know events
    Good for Complex flows, many steps Simple flows, 2–4 steps
    Risk Orchestrator becomes a "god service" Cyclic, hard-to-follow event chains

    4. Naive Approach (Without the Pattern)¶

    @Transactional // only covers order-service's database!
public void placeOrder(Order o) {
    inventoryClient.reserve(o);   // remote call: committed in inventory's DB
    paymentClient.charge(o);      // remote call: committed in payment's DB
    deliveryClient.schedule(o);   // fails → local rollback only
}   // result: stock reserved and card charged for an order that doesn't exist

    5. Three Real-World Examples¶

    All orchestrated examples share one small orchestrator:

    package com.handbook.microservices.saga.core;

import java.util.ArrayDeque;
import java.util.ArrayList;
import java.util.Deque;
import java.util.List;

/**
 * An orchestration-based saga: run local transactions in order; if one fails, run the
 * compensations of the completed steps in reverse order. Steps after the pivot step are
 * retried until they succeed instead of being compensated.
 */
public final class SagaOrchestrator {

    /** A step's action and compensation each call one service's local transaction. */
    public record Step(String name, Runnable action, Runnable compensation, Kind kind) {

        public enum Kind { COMPENSATABLE, PIVOT, RETRIABLE }

        public static Step compensatable(String name, Runnable action, Runnable compensation) {
            return new Step(name, action, compensation, Kind.COMPENSATABLE);
        }

        public static Step pivot(String name, Runnable action) {
            return new Step(name, action, () -> { }, Kind.PIVOT);
        }

        public static Step retriable(String name, Runnable action) {
            return new Step(name, action, () -> { }, Kind.RETRIABLE);
        }
    }

    public enum Outcome { COMPLETED, COMPENSATED }

    private final List<String> log = new ArrayList<>();
    private final int maxRetries;

    public SagaOrchestrator(int maxRetries) {
        this.maxRetries = maxRetries;
    }

    public Outcome run(String sagaId, List<Step> steps) {
        Deque<Step> done = new ArrayDeque<>();
        for (Step step : steps) {
            if (step.kind() == Step.Kind.RETRIABLE) {
                runWithRetries(sagaId, step); // (1)!
                continue;
            }
            try {
                step.action().run();
                record(sagaId, step.name() + " ✔");
                done.push(step); // (2)!
            } catch (RuntimeException e) {
                record(sagaId, step.name() + " ✘ " + e.getMessage());
                compensate(sagaId, done);
                return Outcome.COMPENSATED;
            }
        }
        record(sagaId, "COMPLETED");
        return Outcome.COMPLETED;
    }

    private void compensate(String sagaId, Deque<Step> done) {
        while (!done.isEmpty()) { // (3)!
            Step step = done.pop();
            step.compensation().run();
            record(sagaId, "undo " + step.name() + " ✔");
        }
        record(sagaId, "COMPENSATED");
    }

    private void runWithRetries(String sagaId, Step step) {
        for (int attempt = 1; ; attempt++) {
            try {
                step.action().run();
                record(sagaId, step.name() + " ✔" + (attempt > 1 ? " (attempt " + attempt + ")" : ""));
                return;
            } catch (RuntimeException e) {
                record(sagaId, step.name() + " ✘ " + e.getMessage() + ", will retry");
                if (attempt == maxRetries) {
                    record(sagaId, step.name() + " needs manual attention"); // (4)!
                    return;
                }
            }
        }
    }

    private void record(String sagaId, String entry) {
        log.add(entry);
        System.out.println("  [" + sagaId + "] " + entry);
    }

    public List<String> log() {
        return List.copyOf(log);
    }
}
    1. Retriable steps (after the pivot) are never compensated; they are retried.
    2. Completed steps go on a stack, so compensations run in reverse order.
    3. Compensations themselves must be idempotent and retriable: in production, a failed compensation is retried, not abandoned.
    4. Retries are bounded; exhausted retries go to a human (a dead-letter queue plus an alert).

    Example 1: Place-Order Saga (Grocery, orchestration)¶

    Scenario: Reserve stock → charge payment → schedule delivery. ORD-1 succeeds. ORD-2's pincode has no delivery slots, so the payment is refunded and stock released. ORD-3 fails at the first step, so there's nothing to undo.

    Design:

    sequenceDiagram
    participant S as Order saga
    participant I as Inventory
    participant P as Payment
    participant D as Delivery
    S->>I: reserve ✔
    S->>P: charge ✔
    S->>D: schedule ✘ no slots
    S->>P: refund (compensate)
    S->>I: release (compensate)

    Full Code:

    package com.handbook.microservices.saga.grocery;

import com.handbook.microservices.saga.core.SagaOrchestrator;
import com.handbook.microservices.saga.core.SagaOrchestrator.Outcome;
import com.handbook.microservices.saga.core.SagaOrchestrator.Step;
import com.handbook.microservices.saga.grocery.GroceryServices.DeliveryService;
import com.handbook.microservices.saga.grocery.GroceryServices.InventoryService;
import com.handbook.microservices.saga.grocery.GroceryServices.PaymentService;

import java.util.List;

/** The order service owns this saga and tells each participant what to do. */
public final class PlaceOrderSaga {

    public record Order(String id, String sku, int qty, long paise, String pincode) {
    }

    private final InventoryService inventory;
    private final PaymentService payments;
    private final DeliveryService delivery;

    public PlaceOrderSaga(InventoryService inventory, PaymentService payments, DeliveryService delivery) {
        this.inventory = inventory;
        this.payments = payments;
        this.delivery = delivery;
    }

    public Outcome place(Order o) {
        return new SagaOrchestrator(3).run(o.id(), List.of(
                Step.compensatable("reserve stock",
                        () -> inventory.reserve(o.sku(), o.qty()),
                        () -> inventory.release(o.sku(), o.qty())), // (1)!
                Step.compensatable("charge payment",
                        () -> payments.charge(o.id(), o.paise()),
                        () -> payments.refund(o.id())),
                Step.compensatable("schedule delivery",
                        () -> delivery.schedule(o.id(), o.pincode()),
                        () -> { })));
    }
}
    1. Each action is paired with its compensation right where it's defined, so they can't drift apart.
    package com.handbook.microservices.saga.grocery;

import java.util.HashMap;
import java.util.HashSet;
import java.util.Map;
import java.util.Set;

/** Three services, each with its own database and a local transaction per call. */
public final class GroceryServices {

    private GroceryServices() {
    }

    public static final class InventoryService {
        private final Map<String, Integer> stock = new HashMap<>(Map.of("MANGO-1KG", 10));

        public void reserve(String sku, int qty) {
            int available = stock.getOrDefault(sku, 0);
            if (available < qty) {
                throw new IllegalStateException("out of stock");
            }
            stock.put(sku, available - qty);
        }

        public void release(String sku, int qty) {
            stock.merge(sku, qty, Integer::sum);
        }

        public int available(String sku) {
            return stock.getOrDefault(sku, 0);
        }
    }

    public static final class PaymentService {
        private final Set<String> charged = new HashSet<>();

        public void charge(String orderId, long paise) {
            charged.add(orderId);
        }

        public void refund(String orderId) {
            charged.remove(orderId);
        }

        public boolean isCharged(String orderId) {
            return charged.contains(orderId);
        }
    }

    public static final class DeliveryService {
        private final Set<String> pincodesServed = Set.of("560001", "560034");

        public void schedule(String orderId, String pincode) {
            if (!pincodesServed.contains(pincode)) {
                throw new IllegalStateException("no delivery slots for " + pincode);
            }
        }
    }
}

    package com.handbook.microservices.saga.grocery;

import com.handbook.microservices.saga.grocery.GroceryServices.DeliveryService;
import com.handbook.microservices.saga.grocery.GroceryServices.InventoryService;
import com.handbook.microservices.saga.grocery.GroceryServices.PaymentService;
import com.handbook.microservices.saga.grocery.PlaceOrderSaga.Order;

public class PlaceOrderSagaDemo {

    public static void main(String[] args) {
        var inventory = new InventoryService();
        var payments = new PaymentService();
        var saga = new PlaceOrderSaga(inventory, payments, new DeliveryService());

        System.out.println("=== Grocery: place-order saga (orchestration) ===");
        System.out.println("Outcome: " + saga.place(new Order("ORD-1", "MANGO-1KG", 2, 79_800, "560034")));
        System.out.println("Stock left: " + inventory.available("MANGO-1KG") + ", ORD-1 charged: " + payments.isCharged("ORD-1"));

        System.out.println();
        System.out.println("Outcome: " + saga.place(new Order("ORD-2", "MANGO-1KG", 3, 119_700, "999999")));
        System.out.println("Stock left: " + inventory.available("MANGO-1KG") + ", ORD-2 charged: " + payments.isCharged("ORD-2"));

        System.out.println();
        System.out.println("Outcome: " + saga.place(new Order("ORD-3", "MANGO-1KG", 50, 1_995_000, "560001")));
    }
}

    Output:

    === Grocery: place-order saga (orchestration) ===

  [ORD-1] charge payment ✔
  [ORD-1] schedule delivery ✔
  [ORD-1] COMPLETED
Outcome: COMPLETED
Stock left: 8, ORD-1 charged: true

  [ORD-2] reserve stock ✔

    Why a saga here:

    • Three databases, no distributed transaction, yet no orphaned charges or reservations.
    • The whole flow is readable in one place (orchestration).
    • Ordering tip: put steps that are most likely to fail, or cheapest to undo, first (validate delivery before charging in a real design).

    Example 2: Trip Booking with a Pivot (Travel)¶

    Scenario: Hold a flight and a hotel (both cancellable), then charge the card: the pivot. After payment, the trip is sold; if the airport-cab partner is flaky, the saga retries forward instead of refunding the whole trip. If the hotel is sold out before payment, the flight hold is cancelled.

    Full Code:

    package com.handbook.microservices.saga.travel;

import com.handbook.microservices.saga.core.SagaOrchestrator;
import com.handbook.microservices.saga.core.SagaOrchestrator.Outcome;
import com.handbook.microservices.saga.core.SagaOrchestrator.Step;

import java.util.List;
import java.util.function.Consumer;

/**
 * Flight and hotel holds can be cancelled. Charging the card is the pivot: once it succeeds the
 * trip is sold, so the cab and confirmation e-mail are retried rather than undoing the whole trip.
 */
public final class TripBookingSaga {

    public interface Partners {
        void holdFlight(String trip);

        void cancelFlight(String trip);

        void holdHotel(String trip);

        void cancelHotel(String trip);

        void chargeCard(String trip);

        void bookAirportCab(String trip);

        void sendItinerary(String trip);
    }

    private final Partners p;

    public TripBookingSaga(Partners partners) {
        this.p = partners;
    }

    public Outcome book(String trip) {
        return new SagaOrchestrator(3).run(trip, List.of(
                Step.compensatable("hold flight", run(p::holdFlight, trip), run(p::cancelFlight, trip)),
                Step.compensatable("hold hotel", run(p::holdHotel, trip), run(p::cancelHotel, trip)),
                Step.pivot("charge card", run(p::chargeCard, trip)), // (1)!
                Step.retriable("book airport cab", run(p::bookAirportCab, trip)), // (2)!
                Step.retriable("send itinerary", run(p::sendItinerary, trip))));
    }

    private static Runnable run(Consumer<String> call, String trip) {
        return () -> call.accept(trip);
    }
}
    1. The pivot: the point of no return. Before it, compensate; after it, complete.
    2. Retriable steps must eventually succeed (idempotent calls, retries, a manual fallback).
    package com.handbook.microservices.saga.travel;

import java.util.Set;

public class TripBookingDemo {

    public static void main(String[] args) {
        System.out.println("=== Travel: flight + hotel + cab, with a pivot step ===");
        new TripBookingSaga(new FakePartners(Set.of(), 0)).book("TRIP-1");

        System.out.println();
        System.out.println("-- hotel is sold out: cancel the flight hold --");
        new TripBookingSaga(new FakePartners(Set.of("hotel"), 0)).book("TRIP-2");

        System.out.println();
        System.out.println("-- after payment, the cab partner is flaky: retry forward, don't refund --");
        new TripBookingSaga(new FakePartners(Set.of(), 2)).book("TRIP-3");
    }

    /** Fake partner APIs: some always fail, and the cab API fails its first N calls. */
    private static final class FakePartners implements TripBookingSaga.Partners {
        private final Set<String> failing;
        private int cabFailuresLeft;

        FakePartners(Set<String> failing, int cabFailures) {
            this.failing = failing;
            this.cabFailuresLeft = cabFailures;
        }

        private void maybeFail(String partner, String reason) {
            if (failing.contains(partner)) {
                throw new IllegalStateException(reason);
            }
        }

        @Override public void holdFlight(String trip) { maybeFail("flight", "no seats"); }
        @Override public void cancelFlight(String trip) { }
        @Override public void holdHotel(String trip) { maybeFail("hotel", "sold out"); }
        @Override public void cancelHotel(String trip) { }
        @Override public void chargeCard(String trip) { maybeFail("card", "card declined"); }
        @Override public void sendItinerary(String trip) { }

        @Override
        public void bookAirportCab(String trip) {
            if (cabFailuresLeft-- > 0) {
                throw new IllegalStateException("cab API timeout");
            }
        }
    }
}

  [TRIP-1] send itinerary ✔

    Why a pivot here:

    • Refunding a whole holiday because a cab API timed out is bad business.
    • Making the structure explicit (compensatable → pivot → retriable) forces the right conversation with the product owner.

    Example 3: Inter-Bank Transfer (Banking, choreography)¶

    Scenario: No orchestrator. The debit service reacts to TransferRequested by debiting and publishing AccountDebited. The credit service reacts by crediting, or publishes CreditFailed if the target account is closed. The debit service listens for CreditFailed and refunds (the compensation), then publishes TransferFailed.

    Design:

    sequenceDiagram
    participant Bus as Event bus
    participant A as Debit service (bank A)
    participant B as Credit service (bank B)
    Bus->>A: TransferRequested TX-2
    A->>Bus: AccountDebited
    Bus->>B: AccountDebited
    B->>Bus: CreditFailed (account closed)
    Bus->>A: CreditFailed
    A->>Bus: TransferFailed (refunded)

    Full Code:

    package com.handbook.microservices.saga.banking;

import com.handbook.microservices.support.EventBus;

import java.util.HashMap;
import java.util.Map;
import java.util.Set;

/**
 * A choreography-based saga: no orchestrator. Each service reacts to events and publishes its own.
 * The debit side listens for CreditFailed and refunds, which is the compensation.
 */
public final class TransferChoreography {

    public record TransferRequested(String id, String from, String to, long amount) {
    }

    public record AccountDebited(String id, String from, String to, long amount) {
    }

    public record AccountCredited(String id) {
    }

    public record CreditFailed(String id, String from, long amount, String reason) {
    }

    public record TransferFailed(String id, String reason) {
    }

    /** Owns source accounts (bank A). */
    public static final class DebitService {
        final Map<String, Long> balances = new HashMap<>();

        DebitService(EventBus bus) {
            bus.<TransferRequested>subscribe("transfers", e -> {
                long balance = balances.getOrDefault(e.from(), 0L);
                if (balance < e.amount()) {
                    bus.publish("transfers.failed", new TransferFailed(e.id(), "insufficient funds"));
                    return;
                }
                balances.put(e.from(), balance - e.amount());
                bus.publish("accounts.debited", new AccountDebited(e.id(), e.from(), e.to(), e.amount()));
            });
            bus.<CreditFailed>subscribe("credits.failed", e -> { // (1)!
                balances.merge(e.from(), e.amount(), Long::sum);
                bus.publish("transfers.failed", new TransferFailed(e.id(), e.reason() + ", refunded"));
            });
        }
    }

    /** Owns destination accounts (bank B). */
    public static final class CreditService {
        final Map<String, Long> balances = new HashMap<>();

        CreditService(EventBus bus, Set<String> closedAccounts) {
            bus.<AccountDebited>subscribe("accounts.debited", e -> {
                if (closedAccounts.contains(e.to())) {
                    bus.publish("credits.failed", new CreditFailed(e.id(), e.from(), e.amount(), "account closed"));
                    return;
                }
                balances.merge(e.to(), e.amount(), Long::sum);
                bus.publish("accounts.credited", new AccountCredited(e.id()));
            });
        }
    }

    public final DebitService debit;
    public final CreditService credit;

    public TransferChoreography(EventBus bus, Set<String> closedAccounts) {
        this.debit = new DebitService(bus);
        this.credit = new CreditService(bus, closedAccounts);
    }

    public long balanceA(String account) {
        return debit.balances.getOrDefault(account, 0L);
    }

    public void openA(String account, long balance) {
        debit.balances.put(account, balance);
    }
}
    1. The compensation is triggered by an event, not called by a coordinator.
    package com.handbook.microservices.saga.banking;

import com.handbook.microservices.saga.banking.TransferChoreography.TransferRequested;
import com.handbook.microservices.support.EventBus;

import java.util.Set;

public class TransferChoreographyDemo {

    public static void main(String[] args) {
        EventBus bus = new EventBus(true);
        var transfers = new TransferChoreography(bus, Set.of("B-CLOSED-9"));
        transfers.openA("A-100", 5_000);

        System.out.println("=== Banking: inter-bank transfer as a choreographed saga ===");
        bus.publish("transfers", new TransferRequested("TX-1", "A-100", "B-200", 1_500));
        System.out.println("A-100 balance: " + transfers.balanceA("A-100"));

        System.out.println();
        bus.publish("transfers", new TransferRequested("TX-2", "A-100", "B-CLOSED-9", 2_000));
        System.out.println("A-100 balance: " + transfers.balanceA("A-100") + " (debit compensated by refund)");

        System.out.println();
        bus.publish("transfers", new TransferRequested("TX-3", "A-100", "B-200", 9_999));
        System.out.println("A-100 balance: " + transfers.balanceA("A-100"));
    }
}

    package com.handbook.microservices.support;

import java.util.ArrayList;
import java.util.LinkedHashMap;
import java.util.List;
import java.util.Map;
import java.util.function.Consumer;

/**
 * A tiny, synchronous, in-memory stand-in for a message broker (Kafka, RabbitMQ).
 * Real brokers are asynchronous and at-least-once; the examples call that out where it matters.
 */
public final class EventBus {

    private final Map<String, List<Consumer<Object>>> subscribers = new LinkedHashMap<>();
    private final boolean log;

    public EventBus(boolean log) {
        this.log = log;
    }

    @SuppressWarnings("unchecked")
    public <T> void subscribe(String topic, Consumer<T> handler) {
        subscribers.computeIfAbsent(topic, t -> new ArrayList<>()).add(e -> handler.accept((T) e));
    }

    public void publish(String topic, Object event) {
        if (log) {
            System.out.println("  [bus] " + topic + " <- " + event);
        }
        for (Consumer<Object> s : subscribers.getOrDefault(topic, List.of())) {
            s.accept(event);
        }
    }
}

    A choreography participant with Spring Kafka (compiled in the spring-reference module):

    package com.handbook.springref.saga;

import org.springframework.kafka.annotation.KafkaListener;
import org.springframework.kafka.core.KafkaTemplate;
import org.springframework.stereotype.Component;
import org.springframework.transaction.annotation.Transactional;

/**
 * A choreography participant: payment-service reacts to StockReserved by charging the customer,
 * and publishes PaymentCompleted or PaymentFailed (which inventory-service uses to release stock).
 * Events are plain JSON strings here to keep the snippet short.
 */
@Component
public class PaymentSagaListener {

    private final KafkaTemplate<String, String> kafka;
    private final PaymentRepository payments;

    public PaymentSagaListener(KafkaTemplate<String, String> kafka, PaymentRepository payments) {
        this.kafka = kafka;
        this.payments = payments;
    }

    @KafkaListener(topics = "inventory.stock-reserved", groupId = "payment-service")
    @Transactional
    public void onStockReserved(String orderId) {
        if (payments.alreadyProcessed(orderId)) {
            return; // Kafka is at-least-once: make the handler idempotent
        }
        boolean charged = payments.charge(orderId);
        // In production, write this event to an outbox table in the same transaction instead.
        kafka.send(charged ? "payment.completed" : "payment.failed", orderId, orderId);
    }

    /** The local database access this listener needs. */
    public interface PaymentRepository {
        boolean alreadyProcessed(String orderId);

        boolean charge(String orderId);
    }
}

    Hand-written orchestrator with a saga state table Full control; you build persistence, timeouts, retries
    Temporal / Cadence Durable workflows in Java code: retries, timers and state persisted for you
    Camunda / Zeebe BPMN workflows with compensation events
    Axon Framework @Saga with @SagaEventHandler, in an event-sourced style
    Eventuate Tram Sagas Orchestration sagas over the transactional outbox
    AWS Step Functions Managed state machines with catch/compensate branches

    Countermeasures for missing isolation (sagas are ACD, without the I):

    • Semantic lock: mark records PENDING (order APPROVAL_PENDING) so other flows treat them carefully.
    • Commutative updates: design operations that can be applied in any order (debit/credit amounts, not "set balance").
    • Pessimistic view: order steps to minimize business risk (charge after cheap checks).
    • Reread value: check data hasn't changed before overwriting.

    9. Pitfalls & Anti-Patterns¶

    Non-idempotent steps and compensations

    Messages are redelivered and orchestrators crash and retry. "Refund" executed twice refunds twice. Every step and compensation needs an idempotency key.

    Losing saga state on crash

    An in-memory orchestrator that crashes mid-saga leaves money charged and stock reserved forever. Persist saga state (see the coding challenge), or use a workflow engine.

    Compensations that can't compensate

    You can't "unsend" an email or "unship" a parcel. Move irreversible actions after the pivot, or compensate with a new business action (a correction email, a return label).

    Choreography spaghetti

    Ten services reacting to each other's events with nobody owning the flow. If you need a diagram to understand it, consider orchestration.

    10. Senior / Architect Deep Dive (10–15 yrs)¶

    Orchestration vs. choreography in practice. Most mature teams use orchestration for core business flows (order, payment, onboarding) because the flow is versioned, testable and observable in one place, and use choreography for loose reactions (send email when an order ships). Workflow engines (Temporal) make orchestration durable without writing the state machine yourself.

    Isolation anomalies. Lost updates (saga B overwrites saga A's change), dirty reads (reading a reservation that will be compensated), fuzzy reads. Use semantic locks (PENDING states), version checks and commutative operations. Discuss which anomalies are acceptable for the business.

    Timeouts. A participant may never reply. Sagas need deadlines per step ("payment not confirmed in 15 min → cancel order"), implemented with durable timers (a scheduler table or a workflow engine).

    Production checklist¶

    • Saga state persisted (state table or workflow engine); recovery on restart.
    • Every step and compensation idempotent (idempotency keys, processed-message table).
    • Steps ordered: validations and reversible steps first, irreversible steps after the pivot.
    • Commands and events sent via the transactional outbox.
    • Per-step timeouts with durable timers; dead-letter handling and alerts for stuck sagas.
    • Semantic locks (PENDING states) visible in UIs and APIs.
    • Tracing across all steps (one trace or a correlation ID per saga).

    Explain it in 2 minutes (system design round)¶

    "Order placement spans inventory, payment and delivery, each with its own database, so I'd use an orchestrated saga, owned by the order service or run in Temporal. The order starts as PENDING. Steps: reserve stock, charge payment (the pivot), book delivery (retried until it succeeds). If a step before the pivot fails, compensations run in reverse: refund, release. Saga state is persisted, commands go through the outbox, every handler is idempotent, and each step has a timeout. The customer sees 'processing' until the saga completes, then gets a push notification."

    War story: the refund that ran three times

    A marketplace's payment-failure compensation listened to DeliveryFailed events. During a broker rebalance, the same event was delivered three times, and the handler issued three refunds for one order. Finance found the loss two weeks later. Fix: compensations keyed by (sagaId, step) in a processed-messages table inside the same local transaction; the refund API called with an idempotency key. Lesson: "at-least-once delivery" means your code must make it "exactly-once in effect".

    12. Interview Corner¶

    Q1. What is a saga?

    A sequence of local transactions across services; if one fails, compensating transactions undo the earlier ones.

    Q2. Why not use a normal database transaction?

    Each microservice has its own database; a single transaction can't span them, and distributed transactions (2PC) are slow and reduce availability.

    Q3. Orchestration vs. choreography?

    Orchestration: a central coordinator tells services what to do. Choreography: services listen to events and react, with no central coordinator.

    Q4. What is a compensating transaction? Give an example.

    A business action that semantically undoes a previous step: refund a payment, release reserved stock, cancel a booking.

    Q5. Is a saga ACID?

    No: it's ACD without isolation, and eventually consistent.

    Q1. When would you choose orchestration?

    For complex flows with many steps, conditional logic or timeouts, where seeing the flow in one place matters.

    Q2. What happens if a compensation fails?

    Retry it (it must be idempotent); after repeated failures, alert and send to manual handling. Compensations must eventually succeed.

    Q3. What is a pivot transaction?

    The go/no-go step. Steps before it are compensatable; steps after it are retriable and must complete.

    Q4. How do sagas publish events reliably?

    With the transactional outbox: the local state change and the event are written in one local transaction, then relayed to the broker.

    Q5. Which tools help implement sagas in Java?

    Temporal, Camunda/Zeebe, Axon, Eventuate Tram, or Spring Kafka with a hand-written state machine.

    Q1. "Explain isolation anomalies in sagas and countermeasures."

    Lost updates, dirty reads, non-repeatable reads, because intermediate states are visible. Countermeasures: semantic locks (PENDING), commutative updates, version checks (reread value), and ordering steps by risk.

    Q2. "Design the order saga for a food delivery app, including timeouts."

    States: PENDING → RESTAURANT_ACCEPTED → PAID → COURIER_ASSIGNED → CONFIRMED; compensations: void payment authorization, cancel at restaurant; timeouts: restaurant must accept in 3 min, courier in 10 min (else reassign or cancel and refund); durable timers; outbox; idempotent handlers.

    Q3. "2PC vs. saga: when would you still use 2PC?"

    Within one organization, few XA-capable resources, short transactions, strong consistency required, and lower availability acceptable (e.g. DB + legacy queue in a monolith). Not across microservices.

    Q4. "How do you test sagas?"

    Unit test the orchestrator with fake participants for every failure point; contract tests for messages; chaos tests that crash the orchestrator mid-flow; and verify idempotency by redelivering every message.

    Q5. "How would you migrate a monolith's @Transactional checkout to a saga?"

    Identify steps and compensations, introduce PENDING states and the outbox while still in the monolith, extract one participant at a time behind its API, then move coordination to an orchestrator or workflow engine.

    Problem: The orchestrator pod crashes in the middle of a saga. Persist a saga log so a new pod can find unfinished sagas on startup and compensate the steps that completed.

    Solution 
    package com.handbook.microservices.saga.recovery;

import java.util.ArrayList;
import java.util.LinkedHashMap;
import java.util.List;
import java.util.Map;

/**
 * Coding challenge: an orchestrator that survives a crash. Before and after each step it appends to
 * a durable saga log (a database table in real life). On restart, it reads the log: an unfinished
 * saga is rolled back by compensating every step that completed.
 */
public final class DurableSaga {

    public record Step(String name, Runnable action, Runnable compensation) {
    }

    /** Stands in for a saga_log table: saga id → ordered entries. */
    public static final class SagaLog {
        private final Map<String, List<String>> entries = new LinkedHashMap<>();

        void append(String sagaId, String entry) {
            entries.computeIfAbsent(sagaId, k -> new ArrayList<>()).add(entry);
        }

        public List<String> read(String sagaId) {
            return List.copyOf(entries.getOrDefault(sagaId, List.of()));
        }
    }

    private final SagaLog log;

    public DurableSaga(SagaLog log) {
        this.log = log;
    }

    public void run(String sagaId, List<Step> steps) {
        log.append(sagaId, "STARTED");
        for (Step step : steps) {
            log.append(sagaId, "BEGIN " + step.name());
            step.action().run();
            log.append(sagaId, "DONE " + step.name());
        }
        log.append(sagaId, "FINISHED");
    }

    /** Called on startup for every saga that has no FINISHED or ROLLED_BACK entry. */
    public void recover(String sagaId, List<Step> steps) {
        List<String> entries = log.read(sagaId);
        if (entries.contains("FINISHED") || entries.contains("ROLLED_BACK")) {
            return;
        }
        List<Step> completed = steps.stream().filter(s -> entries.contains("DONE " + s.name())).toList();
        for (int i = completed.size() - 1; i >= 0; i--) {
            Step step = completed.get(i);
            step.compensation().run(); // compensations must be idempotent: we may crash here too
            log.append(sagaId, "UNDONE " + step.name());
        }
        log.append(sagaId, "ROLLED_BACK");
    }
}

public class DurableSagaDemo {

    public static void main(String[] args) {
        SagaLog log = new SagaLog();
        List<Step> steps = List.of(
                new Step("reserve stock", () -> say("inventory: reserved"), () -> say("inventory: released")),

            new DurableSaga(log).run("ORD-7", steps);

            System.out.println("CRASH: " + crash.getMessage());

        System.out.println("-- new pod starts and scans unfinished sagas --");
        new DurableSaga(log).recover("ORD-7", steps);
        System.out.println("Saga log after restart: " + log.read("ORD-7"));
    }

    private static void say(String s) {
        System.out.println("  " + s);
    }
}
