    Cache-Aside (and Other Caching Patterns)¶

    🟡 Intermediate Microservices Interview frequency ⭐⭐⭐⭐⭐

    TL;DR

    Cache-aside: the application checks the cache first; on a miss it reads the database and puts the result in the cache with a TTL; on a write it updates the database and deletes the cache entry. Use it for read-heavy data that tolerates being a few seconds stale (catalogs, profiles, configuration). Add request coalescing for hot keys, and know when write-through or write-behind fit better.

    See It in Motion¶

    Press Play to watch the calls travel between components, or step through with Next and Back. Open the full explorer with all 66 patterns

    1. Intent & Problem It Solves¶

    The problem in plain English: the product page for bananas is viewed 1,000 times a minute during the evening rush, and every view runs the same SELECT. The database's CPU climbs, latency rises for everything else, and you're paying for a bigger database just to answer the same question again and again.

    Definition (Microsoft Azure Architecture Center, Cache-Aside):

    Load data on demand into a cache from a data store. The application is responsible for reading from and writing to the store and keeping the cache consistent.

    The family of caching patterns:

    Pattern Read path Write path Typical use
    Cache-aside (lazy loading) App: cache → miss → DB → fill cache App: write DB, delete cache key Most microservices with Redis
    Read-through Cache library loads from DB on a miss (Usually with write-through) Caffeine LoadingCache, Hazelcast MapLoader
    Write-through From cache Write cache and DB synchronously Data read right after write
    Write-behind (write-back) From cache Write cache; flush to DB asynchronously in batches Counters, metrics, likes
    Refresh-ahead From cache Reload hot keys before they expire Hot keys with expensive loads

    2. Real-World Analogy¶

    The stock of popular items at the billing counter

    A supermarket keeps chewing gum and batteries at the counter (the cache) instead of sending someone to the aisles (the database) each time. When the counter runs out, the cashier fetches more from the aisle (miss → load). When the price changes, the counter stock is relabelled by removing the old tags (invalidate), not by guessing the new price.

    3. Structure¶

    sequenceDiagram autonumber participant App participant Cache as Redis participant DB App->>Cache: GET product:BANANA-6 alt hit Cache-->>App: value else miss App->>DB: SELECT ... DB-->>App: row App->>Cache: SET product:BANANA-6 value EX 600 end Note over App,DB: write path App->>DB: UPDATE price App->>Cache: DEL product:BANANA-6
    Participant Responsibility
    Application Owns the logic: look up, load on miss, fill, invalidate on write
    Cache (Redis, Memcached, Caffeine) Fast key-value store with TTLs and eviction
    Database Source of truth
    TTL Upper bound on staleness and a safety net for missed invalidations

    4. Naive Approach (Without the Pattern)¶

    public Product get(String sku) {
    return jdbc.queryForObject("SELECT * FROM product WHERE sku = ?", mapper, sku);  // every view hits the DB
}
// or, the opposite mistake:
static final Map<String, Product> CACHE = new HashMap<>();   // per-instance, never expires, never invalidated
    • The database carries load that a cache could absorb 1000×.
    • Home-made per-instance maps: inconsistent between pods, unbounded memory, stale forever.
    • No TTL means one missed invalidation is permanent.

    5. Three Real-World Examples¶

    Example 1: Product Pages (Grocery)¶

    Scenario: A grocery app's product pages are viewed tens of thousands of times an hour, but prices change only a few times a day. A 10-minute TTL is acceptable, except that a price drop must show up immediately (marketing has pushed a notification). The write path updates PostgreSQL, then deletes the Redis key.

    Design:

    flowchart LR V["1,000 views"] --> C{"cache hit?"} C -- "999 yes" --> R[(Redis)] C -- "1 miss" --> DB[(PostgreSQL)] --> R U["Price update"] --> DB U -->|DEL key| R

    Full Code:

    package com.handbook.microservices.caching.catalog;

import java.time.Duration;
import java.util.HashMap;
import java.util.Map;

/** Cache-aside: the APPLICATION reads the cache, falls back to the DB, and fills the cache itself. */
public final class ProductCatalog {

    public record Product(String sku, String name, long pricePaise) { }

    private final Map<String, Product> database = new HashMap<>();
    private final TtlCache<Product> cache;
    private int dbReads;

    public ProductCatalog(TtlCache<Product> cache) {
        this.cache = cache;
    }

    public void seed(Product p) {
        database.put(p.sku(), p);
    }

    public Product get(String sku) {
        return cache.get("product:" + sku).orElseGet(() -> { // (1)!
            dbReads++;
            Product fromDb = database.get(sku);
            cache.set("product:" + sku, fromDb, Duration.ofMinutes(10)); // (2)!
            return fromDb;
        });
    }

    public void updatePrice(String sku, long newPaise) {
        Product p = database.get(sku);
        database.put(sku, new Product(sku, p.name(), newPaise)); // 1. write the source of truth
        cache.delete("product:" + sku);                         // 2. invalidate (don't set) (3)!
    }

    public int dbReads() {
        return dbReads;
    }
}
    1. Look in the cache first; only on a miss go to the database.
    2. Fill the cache with a TTL. The TTL bounds staleness even if an invalidation is lost.
    3. Delete, don't set, on writes. Setting the new value from the writer races with concurrent readers and can't handle complex derived values; a delete just forces the next reader to load fresh data.
    package com.handbook.microservices.caching.catalog;

import java.time.Clock;
import java.time.Duration;
import java.time.Instant;
import java.util.Map;
import java.util.Optional;
import java.util.concurrent.ConcurrentHashMap;

/** A minimal Redis stand-in: get / set with TTL / delete. */
public final class TtlCache<V> {

    private record Entry<V>(V value, Instant expiresAt) { }

    private final Map<String, Entry<V>> data = new ConcurrentHashMap<>();
    private final Clock clock;

    public TtlCache(Clock clock) {
        this.clock = clock;
    }

    public Optional<V> get(String key) {
        Entry<V> e = data.get(key);
        if (e == null || !clock.instant().isBefore(e.expiresAt())) {
            data.remove(key);
            return Optional.empty();
        }
        return Optional.of(e.value());
    }

    public void set(String key, V value, Duration ttl) {
        data.put(key, new Entry<>(value, clock.instant().plus(ttl)));
    }

    public void delete(String key) {
        data.remove(key);
    }
}

import com.handbook.microservices.support.FakeClock;

import java.time.Duration;

public class CatalogCacheDemo {

        System.out.println("=== Grocery: Cache-Aside for Product Pages ===");
        FakeClock clock = FakeClock.at("2026-06-01T18:00:00Z");
        ProductCatalog catalog = new ProductCatalog(new TtlCache<>(clock));
        catalog.seed(new Product("BANANA-6", "Robusta Banana (6)", 4_200));

        for (int i = 0; i < 1_000; i++) {
            catalog.get("BANANA-6"); // evening rush on the product page
        }
        System.out.println("1,000 page views -> DB reads: " + catalog.dbReads());

        catalog.updatePrice("BANANA-6", 3_900);
        long paise = catalog.get("BANANA-6").pricePaise();
        System.out.printf("After price drop, next view shows INR %d.%02d (DB reads: %d)%n", paise / 100, paise % 100, catalog.dbReads());

        clock.advance(Duration.ofMinutes(11));

    Output:

    === Grocery: Cache-Aside for Product Pages ===
1,000 page views -> DB reads: 1
After price drop, next view shows INR 39.00 (DB reads: 2)

    Why cache-aside here:

    • Read-heavy, rarely written data: a near-perfect hit rate.
    • The application controls what is cached and for how long.
    • If Redis is down, the app can still read the database (degraded, not broken).

    Example 2: Stampede Protection for a New Release (Streaming)¶

    Scenario: When a new episode drops at 12:00, 500 viewers open it in the same second. The metadata isn't cached yet, so all 500 miss and query the database at once: a cache stampede (thundering herd). The fix is request coalescing (single-flight): the first miss loads; everyone else waits for that same load.

    Design:

    sequenceDiagram autonumber participant V1 as Viewer 1 participant Vn as Viewers 2..500 participant L as SingleFlightLoader participant DB V1->>L: get(ep-2201) → miss, owns in-flight Vn->>L: get(ep-2201) → miss, join in-flight future L->>DB: ONE query DB-->>L: metadata L-->>V1: value L-->>Vn: same value

    Full Code:

    package com.handbook.microservices.caching.singleflight;

import java.util.Map;
import java.util.concurrent.CompletableFuture;
import java.util.concurrent.ConcurrentHashMap;
import java.util.function.Function;

/** Request coalescing: concurrent misses for the same key share ONE load instead of stampeding the DB. */
public final class SingleFlightLoader<V> {

    private final Map<String, V> cache = new ConcurrentHashMap<>();
    private final Map<String, CompletableFuture<V>> inFlight = new ConcurrentHashMap<>();
    private final Function<String, V> loader;

    public SingleFlightLoader(Function<String, V> loader) {
        this.loader = loader;
    }

    public V get(String key) {
        V cached = cache.get(key);
        if (cached != null) {
            return cached;
        }
        CompletableFuture<V> mine = new CompletableFuture<>();
        CompletableFuture<V> existing = inFlight.putIfAbsent(key, mine); // (1)!
        if (existing != null) {
            return existing.join(); // (2)!
        }
        try {
            V value = cache.get(key); // re-check: a load may have finished between our first check and now
            if (value == null) {
                value = loader.apply(key);
            }
            cache.put(key, value);
            mine.complete(value);
            return value;
        } catch (RuntimeException e) {
            mine.completeExceptionally(e);
            throw e;
        } finally {
            inFlight.remove(key);
        }
    }
}
    1. putIfAbsent elects exactly one loader per key; everyone else gets the in-flight future.
    2. Waiters share the result (or the failure) of that single load.
    package com.handbook.microservices.caching.singleflight;

import java.util.ArrayList;
import java.util.List;
import java.util.concurrent.CountDownLatch;
import java.util.concurrent.Executors;
import java.util.concurrent.Future;
import java.util.concurrent.atomic.AtomicInteger;

public class StampedeDemo {

    public static void main(String[] args) throws Exception {
        System.out.println("=== Streaming: 500 Viewers Open a Just-Released Episode ===");
        AtomicInteger dbLoads = new AtomicInteger();
        CountDownLatch slowDb = new CountDownLatch(1);
        SingleFlightLoader<String> metadata = new SingleFlightLoader<>(id -> {
            dbLoads.incrementAndGet();
            try {
                slowDb.await(); // the metadata query takes a while
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
            }
            return id + ": 'The Monsoon Heist' S2E1, 52 min, 4K";
        });

        List<Future<String>> viewers = new ArrayList<>();
        try (var pool = Executors.newVirtualThreadPerTaskExecutor()) {
            for (int i = 0; i < 500; i++) {
                viewers.add(pool.submit(() -> metadata.get("ep-2201")));
            }
            while (dbLoads.get() == 0) {
                Thread.onSpinWait();
            }
            Thread.sleep(100); // let the other 499 requests pile up behind the in-flight load
            slowDb.countDown();
            long served = 0;
            for (Future<String> f : viewers) {
                served += f.get().startsWith("ep-2201") ? 1 : 0;
            }
            System.out.println("Viewers served: " + served);
        }
        System.out.println("Database loads: " + dbLoads.get() + " (without coalescing: up to 500)");
    }
}

    Output:

    === Streaming: 500 Viewers Open a Just-Released Episode ===
Viewers served: 500
Database loads: 1 (without coalescing: up to 500)

    Why coalescing here:

    • Hot keys + cold cache = synchronized misses; this turns N database queries into 1.
    • Caffeine's AsyncLoadingCache does this per JVM; across pods, add a short Redis lock or jittered TTLs.
    • The same idea protects downstream APIs, not just databases.

    Example 3: Write-Behind View Counters (Travel)¶

    Scenario: A travel site shows "1,234 people viewed this hotel today". That's 20,000 increments per second at peak across three hotels in this demo. Writing each to the database is wasteful; counters can tolerate losing a second of data on a crash. Increments go to the cache and are flushed as aggregated deltas once per second.

    Design:

    flowchart LR V["20,000 views/s"] -->|INCR| C[(Cache deltas)] T["every 1 s"] -->|flush| C C -->|"3 UPDATEs: views = views + delta"| DB[(Database)]

    Full Code:

    package com.handbook.microservices.caching.writebehind;

import java.util.HashMap;
import java.util.Map;
import java.util.TreeMap;

/** Write-behind: absorb writes in the cache, flush aggregated deltas to the database in batches. */
public final class WriteBehindCounter {

    private final Map<String, Long> pendingDeltas = new HashMap<>(); // the "cache" side
    private final Map<String, Long> database = new TreeMap<>();
    private int dbWrites;

    public synchronized void increment(String hotelId) {
        pendingDeltas.merge(hotelId, 1L, Long::sum); // (1)!
    }

    public synchronized int flush() { // (2)!
        int rows = pendingDeltas.size();
        pendingDeltas.forEach((id, delta) -> database.merge(id, delta, Long::sum));
        dbWrites += rows;
        pendingDeltas.clear();
        return rows;
    }

    public synchronized long pending() {
        return pendingDeltas.values().stream().mapToLong(Long::longValue).sum();
    }

    public synchronized Map<String, Long> database() {
        return Map.copyOf(database);
    }

    public synchronized int dbWrites() {
        return dbWrites;
    }
}
    1. Writes only touch the in-memory side: microseconds, no DB round trip.
    2. A periodic flush writes one row per key with the aggregated delta.
    package com.handbook.microservices.caching.writebehind;

import java.util.Random;
import java.util.TreeMap;

public class WriteBehindDemo {

    public static void main(String[] args) {
        System.out.println("=== Travel: Hotel Page-View Counters with Write-Behind ===");
        WriteBehindCounter counter = new WriteBehindCounter();
        Random random = new Random(7);
        String[] hotels = {"GOA-BEACH-12", "JAIPUR-FORT-3", "MUNNAR-TEA-8"};

        for (int second = 1; second <= 3; second++) {
            for (int i = 0; i < 20_000; i++) {
                counter.increment(hotels[random.nextInt(hotels.length)]);
            }
            System.out.println("t=" + second + "s flush wrote " + counter.flush() + " rows");
        }
        System.out.println("60,000 views -> " + counter.dbWrites() + " DB writes; totals " + new TreeMap<>(counter.database()));

        for (int i = 0; i < 500; i++) {
            counter.increment("GOA-BEACH-12");
        }
        System.out.println("Crash before the next flush would lose " + counter.pending() + " views: fine for counters, never for money.");
    }
}

    Output:

    === Travel: Hotel Page-View Counters with Write-Behind ===
t=1s flush wrote 3 rows
t=2s flush wrote 3 rows
t=3s flush wrote 3 rows
60,000 views -> 9 DB writes; totals {GOA-BEACH-12=19956, JAIPUR-FORT-3=20009, MUNNAR-TEA-8=20035}
Crash before the next flush would lose 500 views: fine for counters, never for money.

    Why write-behind here:

    • 60,000 increments became 9 database writes.
    • The data is approximate by nature, so a small loss window is acceptable.
    • Never use write-behind for money, orders or anything you can't afford to lose.

    package com.handbook.microservices;

import com.handbook.microservices.caching.catalog.ProductCatalog;
import com.handbook.microservices.caching.catalog.ProductCatalog.Product;

import org.junit.jupiter.api.Test;

import java.time.Duration;
import java.util.concurrent.atomic.AtomicInteger;

import static org.assertj.core.api.Assertions.assertThat;

class CacheAsideTest {

    @Test
    void cacheAsideServesFromCacheAndInvalidatesOnWrite() {
        ProductCatalog c = new ProductCatalog(new TtlCache<>(FakeClock.at("2026-01-01T00:00:00Z")));
        c.seed(new Product("A", "a", 100));
        c.get("A");
        c.get("A");
        assertThat(c.dbReads()).isEqualTo(1);
        c.updatePrice("A", 90);
        assertThat(c.get("A").pricePaise()).isEqualTo(90);
    }

    @Test
    void entriesExpireAfterTtl() {
        FakeClock clock = FakeClock.at("2026-01-01T00:00:00Z");
        TtlCache<String> cache = new TtlCache<>(clock);
        cache.set("k", "v", Duration.ofSeconds(5));
        clock.advance(Duration.ofSeconds(5));
        assertThat(cache.get("k")).isEmpty();
    }

    @Test
    void sequentialMissesAfterFillHitTheCache() {
        AtomicInteger loads = new AtomicInteger();
        SingleFlightLoader<Integer> l = new SingleFlightLoader<>(k -> loads.incrementAndGet());
        l.get("x");
        l.get("x");
        assertThat(loads).hasValue(1);
    }

    @Test
    void writeBehindAggregatesDeltas() {
        WriteBehindCounter c = new WriteBehindCounter();
        for (int i = 0; i < 100; i++) {
            c.increment("h");
        }
        assertThat(c.flush()).isEqualTo(1);
        assertThat(c.database()).containsEntry("h", 100L);
    }
}

@Transactional
public void updatePrice(String sku, long paise) { ... }

    spring:
  cache:
    type: redis

      time-to-live: 10m

    Variation Notes
    Two-level cache Caffeine in-process (L1, ~1 s TTL) + Redis (L2): removes network hops for the hottest keys
    Negative caching Cache "not found" briefly to stop repeated misses for nonexistent keys (and enumeration attacks)
    Jittered TTLs ttl ± random(10%) so keys loaded together don't expire together
    Event-driven invalidation Consume product.price.changed events (or Debezium CDC) to delete keys in every service that caches them
    Versioned keys product:BANANA-6:v42: a new version is a new key; old ones just expire

    7. Where It Lives in Real Frameworks¶

    Where Caching
    Spring @Cacheable, @CachePut, @CacheEvict, CacheManager (Redis, Caffeine, JCache)
    Caffeine LoadingCache, AsyncLoadingCache (coalescing), refreshAfterWrite (refresh-ahead), W-TinyLFU eviction
    Redis SET key value EX ttl NX, DEL, INCRBY, keyspace notifications
    Hibernate Second-level cache (read-through for entities)
    CDNs / HTTP Cache-Control: max-age, stale-while-revalidate: cache-aside at the edge

    8. Pros, Cons & Trade-offs¶

    ✅ Pros ❌ Cons
    Huge read offload; sub-millisecond reads Data can be stale (bounded by TTL and invalidation)
    Cache failure degrades gracefully (fall back to DB) First request after expiry is slow; stampedes on hot keys
    Only requested data is cached Invalidation logic in every writer, in every service
    Simple to add to an existing service Cache and DB can't be updated atomically; races exist

    9. Pitfalls & Anti-Patterns¶

    Updating the cache instead of deleting

    "Write DB, then SET the new value" races with concurrent writers and readers and can leave the older value in the cache. Delete, and let the next read load.

    Caching without a TTL

    One lost DEL (network blip, a bug in another service) makes stale data permanent. Always set a TTL.

    Cache stampede on hot keys

    Popular keys expiring at once flatten the database. Use coalescing, jittered TTLs, refresh-ahead or a short lock.

    Caching per-user or rarely reused data

    A low hit rate means you pay for Redis and serialization for nothing. Measure hit ratio per cache.

    10. Senior / Architect Deep Dive (10–15 yrs)¶

    The stale-set race. Reader misses and loads v1; writer updates the DB to v2 and deletes the key; the slow reader then sets v1. Now the cache is stale until the TTL. Mitigations: short TTLs; versioned sets (only write if the version is newer, coding challenge); "delayed double delete" (delete again after a few hundred ms); or invalidation driven by CDC events, which are ordered per key.

    Sizing and eviction. Measure working-set size and hit ratio; choose maxmemory-policy allkeys-lfu (or Caffeine's W-TinyLFU) for skewed traffic. Watch big keys (a 5 MB JSON blob) and hot keys (one key at 100k ops/s); split or replicate them.

    Consistency budget. Decide per data type how stale is acceptable: product price on a listing page (seconds to minutes), price at checkout (never: read from the source of truth), stock count (show "few left" from cache, but reserve against the database).

    War story: the price that wouldn't go down

    A grocery app set new prices into Redis right after updating the database. During a festival sale, two price updates for the same product raced: the older one's SET landed last. The listing showed INR 120 while checkout (reading the database) charged INR 99, and 6,000 customers abandoned carts thinking the sale was fake. Fix: writers only DEL; reads fill the cache; TTL cut from 24 h to 10 min; checkout always reads the database. Lesson: the cache is a copy. Invalidate it; don't try to keep it in sync by writing to it.

    12. Interview Corner¶

    Q1. What is cache-aside?

    The app checks the cache; on a miss it reads the DB and stores the result in the cache; on writes it updates the DB and removes the cache entry.

    Q2. Why use a TTL?

    To bound how stale data can get and to recover from missed invalidations.

    Q3. What does @Cacheable do?

    Returns the cached value if present; otherwise runs the method and caches the result.

    Q4. Redis vs local cache?

    Redis is shared across instances (consistent, network hop); local caches are faster but per-instance and harder to invalidate.

    Q5. What is a cache hit ratio?

    Hits / total lookups. Low ratios mean the cache isn't helping.

    Q1. Why delete instead of update on write?

    Avoids races where an older value overwrites a newer one, and avoids computing cache values in writers.

    Q2. What's a cache stampede and how do you prevent it?

    Many concurrent misses for the same key hitting the DB. Coalescing, locks, jittered TTLs, refresh-ahead.

    Q3. Write-through vs write-behind?

    Write-through writes DB and cache synchronously (safe, slower writes); write-behind writes the cache and flushes later (fast, can lose data).

    Q4. How do you invalidate a cache in another service?

    Publish an event (or use CDC); the owning service's consumer deletes the keys.

    Q5. What is negative caching?

    Caching "not found" for a short time to avoid repeated misses.

    Q1. "Design caching for a product catalog with 50M SKUs and flash sales."

    CDN for images/static data; Redis cache-aside for product details with jittered TTLs; Caffeine L1 for the top 10k hot SKUs; CDC-driven invalidation; checkout bypasses caches for price and stock.

    Q2. "Explain the stale-set race and fixes."

    Reader loads old value, writer deletes, reader sets old value. Fixes: versioned writes, delayed double delete, short TTL, CDC-ordered invalidation.

    Q3. "Redis is down. What happens?"

    Circuit-break the cache client, serve from the DB with a concurrency limit/bulkhead to protect it, and shed non-critical traffic.

    Q4. "Hot key at 200k reads/s on one Redis shard."

    Local L1 cache with a very short TTL, key replication (key#1..N read randomly), or Redis client-side caching.

    Q5. "When would you not cache?"

    Strongly consistent data (balances, stock reservations), low reuse, or data cheaper to compute than to fetch.

    Problem: Reproduce the cache-aside stale-set race step by step, then prevent it with a version check.

    Solution 
    package com.handbook.microservices.caching.race;

import java.util.HashMap;
import java.util.Map;

/** Coding challenge: a slow reader puts a stale value into the cache after a writer invalidated it. */
public class StaleSetRaceDemo {

    record Versioned(long pricePaise, long version) { }

    static final Map<String, Versioned> DB = new HashMap<>();
    static final Map<String, Versioned> CACHE = new HashMap<>();

    /** Naive set: whatever the reader loaded wins. */
    static void naiveSet(String key, Versioned v) {
        CACHE.put(key, v);
    }

    /** Fix: only replace if the incoming version is newer than what the cache saw last (like SET with a version check). */
    static final Map<String, Long> HIGHEST_SEEN = new HashMap<>();

    static void versionedSet(String key, Versioned v) {
        long highest = HIGHEST_SEEN.getOrDefault(key, -1L);
        if (v.version() >= highest) {
            CACHE.put(key, v);
            HIGHEST_SEEN.put(key, v.version());
        }
    }

    static void invalidate(String key, long newVersion) {
        CACHE.remove(key);
        HIGHEST_SEEN.merge(key, newVersion, Math::max);
    }

    static Versioned run(boolean versioned) {
        DB.put("ONION", new Versioned(4_000, 1));
        CACHE.clear();
        HIGHEST_SEEN.clear();
        Versioned readerLoaded = DB.get("ONION");          // 1. reader misses, loads v1 (then pauses: GC, slow network)
        DB.put("ONION", new Versioned(9_000, 2));          // 2. writer updates DB to v2
        invalidate("ONION", 2);                             // 3. writer deletes cache key
        if (versioned) {
            versionedSet("ONION", readerLoaded);            // 4. reader resumes and sets v1
        } else {
            naiveSet("ONION", readerLoaded);
        }
        return CACHE.get("ONION");
    }

    public static void main(String[] args) {
        System.out.println("=== Challenge: The Cache-Aside Stale-Set Race ===");
        System.out.println("Naive set     -> cache holds " + run(false) + " while DB has v2 (stale until TTL)");
        System.out.println("Versioned set -> cache holds " + run(true) + " (stale write ignored; next read loads v2)");
    }
}

    Output:

    === Challenge: The Cache-Aside Stale-Set Race ===
Naive set     -> cache holds Versioned[pricePaise=4000, version=1] while DB has v2 (stale until TTL)
Versioned set -> cache holds null (stale write ignored; next read loads v2)

    Key points to say: the race needs a slow reader between load and set; the invalidation records the newest version so a late set with an older version is ignored. In Redis, implement the check atomically with a Lua script or WATCH/MULTI.

    Behavioural tie-in (STAR) for experienced candidates

    • S: Festival sale listings showed old prices because racing SETs left stale values in Redis.
    • T: Make listing prices correct within seconds without losing the cache's benefit.
    • A: Switched writers to DEL-only, added versioned sets and jittered 10-minute TTLs, moved invalidation to CDC events, and made checkout read prices from the database.
    • R: Zero price-mismatch tickets in the next sale; database load stayed below 30% with a 97% hit ratio.

    13. Quick Revision Card¶

    Remember in 30 seconds

    • Read: cache → miss → DB → SET with TTL.
    • Write: update DB → DEL key.
    • Always a TTL; jitter it; coalesce hot misses.
    • Write-through = safe & synchronous; write-behind = fast & lossy.
    • Never trust the cache for money or stock decisions.
