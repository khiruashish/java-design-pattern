    Advanced Data Microservices

    Transactional Outbox¶

    🔴 Advanced Microservices Interview frequency ⭐⭐⭐⭐

    TL;DR

    To publish an event reliably when your data changes, insert the event into an outbox table in the same local database transaction as the data change. A separate relay (a polling job or CDC such as Debezium) reads the outbox and publishes to the broker. The data change and the event become atomic: no lost events, no events for changes that never happened. Delivery is at-least-once, so consumers deduplicate.

    1. Intent & Problem It Solves¶

    The problem in plain English, the "dual write":

    orderRepository.save(order);                 // 1. commit to the database
kafkaTemplate.send("orders", orderPlaced);   // 2. publish
    • Crash or broker blip between 1 and 2 → the order exists, but nobody hears about it (no invoice, no fraud check).
    • Publish first, then the DB commit fails → consumers act on an order that doesn't exist.
    • You can't put Kafka and Postgres in one ACID transaction (no XA support in Kafka, and 2PC is undesirable anyway).

    Definition (microservices.io, Chris Richardson):

    A service that uses a relational database inserts messages/events into an outbox table as part of the local transaction. A separate message relay process publishes the events inserted into the database to a message broker.

    2. Real-World Analogy¶

    The office outbox tray

    A clerk files a contract and drops the notification letter into the outbox tray in one motion before going home. The mail room collects letters from the tray later. If the mail van breaks down, the letters wait in the tray; nothing is lost, and no letter goes out for a contract that was never filed.

    3. Structure¶

    flowchart LR
    subgraph Service["order-service (one local transaction)"]
      A[Business logic] --> T[(orders)]
      A --> OB[(outbox)]
    end
    OB --> R[Relay<br/>polling or CDC] --> K[[Kafka topic]]
    K --> C1[Billing]
    K --> C2[Notifications]
    Participant Responsibility
    Service Writes business rows + outbox row in one transaction
    Outbox table id, aggregate_id (message key), type, payload, created_at, published_at
    Relay Reads unpublished rows in order, publishes, marks published (or CDC tails the DB log)
    Consumers Idempotent: deduplicate by event ID

    4. Naive Approach (Without the Pattern)¶

    See section 1: save then publish, or publish then save. Both have a failure window, and those windows are hit at scale every day. Example 2 below reproduces it.

    5. Three Real-World Examples¶

    Example 1: Order + OrderPlaced Atomically (Grocery)¶

    Scenario: Placing an order writes the orders row and an OrderPlaced row in the outbox within one JDBC transaction (real H2 database). A duplicate submit violates the primary key, so both writes roll back. The relay polls while Kafka is down: nothing is lost, and the events stay in the outbox. When Kafka returns, both events are published in order.

    Design:

    sequenceDiagram
    participant S as OrderService
    participant DB as orders_db
    participant R as Relay
    participant K as Kafka
    S->>DB: BEGIN, INSERT orders, INSERT outbox, COMMIT
    R->>DB: SELECT unpublished ORDER BY id
    R->>K: publish ✘ (down) — rows stay
    R->>DB: SELECT unpublished
    R->>K: publish ✔
    R->>DB: UPDATE outbox SET published = TRUE

    Full Code:

    package com.handbook.microservices.outbox.grocery;

import javax.sql.DataSource;
import java.sql.Connection;
import java.sql.PreparedStatement;
import java.sql.SQLException;

/**
 * Writes the order AND the event describing it in ONE local transaction.
 * Either both are committed or neither is, so no event is ever lost or invented.
 */
public final class OrderService {

    public static final String[] SCHEMA = {
            "CREATE TABLE orders (id VARCHAR PRIMARY KEY, customer VARCHAR, total_paise BIGINT)",
            "CREATE TABLE outbox (id BIGINT AUTO_INCREMENT PRIMARY KEY, aggregate_id VARCHAR, "
                    + "type VARCHAR, payload VARCHAR, published BOOLEAN DEFAULT FALSE)"
    };

    private final DataSource db;

    public OrderService(DataSource db) {
        this.db = db;
    }

    public void placeOrder(String orderId, String customer, long totalPaise) throws SQLException {
        try (Connection c = db.getConnection()) {
            c.setAutoCommit(false); // (1)!
            try (PreparedStatement order = c.prepareStatement("INSERT INTO orders VALUES (?, ?, ?)");
                 PreparedStatement event = c.prepareStatement(
                         "INSERT INTO outbox (aggregate_id, type, payload) VALUES (?, ?, ?)")) {
                order.setString(1, orderId);
                order.setString(2, customer);
                order.setLong(3, totalPaise);
                order.executeUpdate();

                event.setString(1, orderId);
                event.setString(2, "OrderPlaced");
                event.setString(3, "{\"orderId\":\"" + orderId + "\",\"total\":" + totalPaise + "}");
                event.executeUpdate(); // (2)!

                c.commit();
            } catch (SQLException e) {
                c.rollback(); // (3)!
                throw e;
            }
        }
    }
}
    1. One local transaction: the only kind the database guarantees.
    2. The event row is just another insert, so it commits or rolls back with the order.
    3. On any failure, neither the order nor the event exists.
    package com.handbook.microservices.outbox.grocery;

import javax.sql.DataSource;
import java.sql.Connection;
import java.sql.PreparedStatement;
import java.sql.ResultSet;
import java.sql.SQLException;
import java.util.function.BiConsumer;

/**
 * Polls unpublished outbox rows in insertion order, publishes each to the broker, then marks it
 * published. If publishing fails, the row stays and is retried on the next poll (at-least-once).
 */
public final class OutboxRelay {

    private final DataSource db;
    private final BiConsumer<String, String> broker; // (topic key, payload)

    public OutboxRelay(DataSource db, BiConsumer<String, String> broker) {
        this.db = db;
        this.broker = broker;
    }

    /** Returns how many events were published in this poll. */
    public int poll(int batchSize) throws SQLException {
        int published = 0;
        try (Connection c = db.getConnection();
             PreparedStatement select = c.prepareStatement(
                     "SELECT id, aggregate_id, payload FROM outbox WHERE published = FALSE ORDER BY id LIMIT ?");
             PreparedStatement mark = c.prepareStatement("UPDATE outbox SET published = TRUE WHERE id = ?")) {
            select.setInt(1, batchSize);
            try (ResultSet rs = select.executeQuery()) {
                while (rs.next()) {
                    try {
                        broker.accept(rs.getString("aggregate_id"), rs.getString("payload")); // (1)!
                    } catch (RuntimeException brokerDown) {
                        System.out.println("  relay: broker unavailable (" + brokerDown.getMessage() + "), will retry");
                        return published; // (2)!
                    }
                    mark.setLong(1, rs.getLong("id"));
                    mark.executeUpdate();
                    published++;
                }
            }
        }
        return published;
    }
}
    1. The aggregate ID becomes the message key, so all events for one order go to the same Kafka partition, in order.
    2. Stop at the first failure to preserve ordering; the next poll resumes from the same row.
    package com.handbook.microservices.support;

import org.h2.jdbcx.JdbcDataSource;

import javax.sql.DataSource;
import java.sql.Connection;
import java.sql.SQLException;
import java.sql.Statement;
import java.util.concurrent.atomic.AtomicInteger;

/** Creates in-memory H2 databases so the examples use real JDBC transactions without a server. */
public final class Db {

    private Db() {
    }

    private static final AtomicInteger COUNTER = new AtomicInteger();

    /** A fresh in-memory database (unique per call) that lives until the JVM exits. */
    public static DataSource inMemory(String name, String... ddl) {
        JdbcDataSource ds = new JdbcDataSource();
        ds.setURL("jdbc:h2:mem:" + name + "_" + COUNTER.incrementAndGet() + ";DB_CLOSE_DELAY=-1");
        try (Connection c = ds.getConnection(); Statement s = c.createStatement()) {
            for (String sql : ddl) {
                s.execute(sql);
            }
        } catch (SQLException e) {
            throw new IllegalStateException(e);
        }
        return ds;
    }

    public static long count(DataSource ds, String sql) {
        try (Connection c = ds.getConnection(); Statement s = c.createStatement(); var rs = s.executeQuery(sql)) {
            rs.next();
            return rs.getLong(1);
        } catch (SQLException e) {
            throw new IllegalStateException(e);
        }
    }
}

    package com.handbook.microservices.outbox.grocery;

import com.handbook.microservices.support.Db;

import javax.sql.DataSource;
import java.sql.SQLException;
import java.util.concurrent.atomic.AtomicBoolean;

public class OrderOutboxDemo {

    public static void main(String[] args) throws SQLException {
        DataSource db = Db.inMemory("orders", OrderService.SCHEMA);
        var orders = new OrderService(db);
        AtomicBoolean brokerUp = new AtomicBoolean(false);
        var relay = new OutboxRelay(db, (key, payload) -> {
            if (!brokerUp.get()) {
                throw new IllegalStateException("connection refused");
            }
            System.out.println("  kafka: orders.events key=" + key + " " + payload);
        });

        System.out.println("=== Grocery: order + OrderPlaced event in one transaction ===");
        orders.placeOrder("ORD-1", "CUST-42", 79_800);
        orders.placeOrder("ORD-2", "CUST-77", 64_900);
        try {
            orders.placeOrder("ORD-1", "CUST-42", 79_800); // duplicate submit: primary key violation
        } catch (SQLException e) {
            System.out.println("Duplicate ORD-1 rejected; transaction rolled back (no order, no event)");
        }
        status(db);

        System.out.println("-- relay polls while Kafka is down --");
        System.out.println("published " + relay.poll(10));
        status(db);

        System.out.println("-- Kafka is back --");
        brokerUp.set(true);
        System.out.println("published " + relay.poll(10));
        status(db);
    }

    private static void status(DataSource db) {
        System.out.println("orders=" + Db.count(db, "SELECT COUNT(*) FROM orders")
                + " outbox=" + Db.count(db, "SELECT COUNT(*) FROM outbox")
                + " unpublished=" + Db.count(db, "SELECT COUNT(*) FROM outbox WHERE published = FALSE"));
    }
}

    Output:

    === Grocery: order + OrderPlaced event in one transaction ===
Duplicate ORD-1 rejected; transaction rolled back (no order, no event)
orders=2 outbox=2 unpublished=2
-- relay polls while Kafka is down --
  relay: broker unavailable (connection refused), will retry
published 0
orders=2 outbox=2 unpublished=2
-- Kafka is back --
  kafka: orders.events key=ORD-1 {"orderId":"ORD-1","total":79800}
  kafka: orders.events key=ORD-2 {"orderId":"ORD-2","total":64900}
published 2
orders=2 outbox=2 unpublished=0

    Why an outbox here:

    • Atomicity of state change and event, using only the database's own transaction.
    • Broker outages delay events; they never lose them.
    • Ordering per aggregate is preserved.

    Example 2: Dual Write vs. Outbox (Insurance claims)¶

    Scenario: Every submitted claim must trigger a fraud check. With a dual write, a broker timeout at exactly the wrong moment means CLM-2 is saved but never checked, and would be paid out. With the outbox, the same broker failure only delays CLM-2's event; the next relay poll delivers it.

    Full Code:

    package com.handbook.microservices.outbox.insurance;

import javax.sql.DataSource;
import java.sql.Connection;
import java.sql.PreparedStatement;
import java.sql.SQLException;
import java.util.function.Consumer;

/** The same claim submission written twice: with a dual write, and with an outbox. */
public final class ClaimServices {

    public static final String[] SCHEMA = {
            "CREATE TABLE claims (id VARCHAR PRIMARY KEY, policy VARCHAR, amount BIGINT)",
            "CREATE TABLE outbox (id BIGINT AUTO_INCREMENT PRIMARY KEY, aggregate_id VARCHAR, "
                    + "type VARCHAR, payload VARCHAR, published BOOLEAN DEFAULT FALSE)"
    };

    private ClaimServices() {
    }

    /** ❌ Commit to the database, then publish. A failure in between loses the event. */
    public static void submitWithDualWrite(DataSource db, Consumer<String> broker, String claimId,
                                           String policy, long amount) throws SQLException {
        try (Connection c = db.getConnection();
             PreparedStatement ps = c.prepareStatement("INSERT INTO claims VALUES (?, ?, ?)")) {
            ps.setString(1, claimId);
            ps.setString(2, policy);
            ps.setLong(3, amount);
            ps.executeUpdate(); // auto-commit: the claim is saved now
        }
        broker.accept("ClaimSubmitted " + claimId); // (1)!
    }

    /** ✅ The claim and the event row commit together; a relay publishes later. */
    public static void submitWithOutbox(DataSource db, String claimId, String policy, long amount)
            throws SQLException {
        try (Connection c = db.getConnection()) {
            c.setAutoCommit(false);
            try (PreparedStatement claim = c.prepareStatement("INSERT INTO claims VALUES (?, ?, ?)");
                 PreparedStatement event = c.prepareStatement(
                         "INSERT INTO outbox (aggregate_id, type, payload) VALUES (?, 'ClaimSubmitted', ?)")) {
                claim.setString(1, claimId);
                claim.setString(2, policy);
                claim.setLong(3, amount);
                claim.executeUpdate();
                event.setString(1, claimId);
                event.setString(2, "ClaimSubmitted " + claimId);
                event.executeUpdate();
                c.commit(); // (2)!
            } catch (SQLException e) {
                c.rollback();
                throw e;
            }
        }
    }
}
    1. The failure window: the claim is already committed; if this line fails, the event is gone forever.
    2. Claim and event commit together.
    package com.handbook.microservices.outbox.insurance;

import com.handbook.microservices.outbox.grocery.OutboxRelay;
import com.handbook.microservices.support.Db;

import javax.sql.DataSource;
import java.sql.SQLException;
import java.util.ArrayList;
import java.util.List;
import java.util.function.Consumer;

public class DualWriteDemo {

    public static void main(String[] args) throws SQLException {
        List<String> fraudCheckInbox = new ArrayList<>();
        Consumer<String> flakyBroker = event -> {
            if (event.endsWith("CLM-2")) {
                throw new IllegalStateException("broker timeout"); // a blip at exactly the wrong moment
            }
            fraudCheckInbox.add(event);
        };

        System.out.println("=== Insurance: claim submitted -> fraud check must always run ===");
        System.out.println("-- dual write (save, then publish) --");
        DataSource naive = Db.inMemory("claims_naive", ClaimServices.SCHEMA);
        for (String id : List.of("CLM-1", "CLM-2", "CLM-3")) {
            try {
                ClaimServices.submitWithDualWrite(naive, flakyBroker, id, "POL-9", 250_000);
            } catch (IllegalStateException e) {
                System.out.println("  " + id + ": saved, but publish failed: " + e.getMessage());
            }
        }
        System.out.println("claims saved: " + Db.count(naive, "SELECT COUNT(*) FROM claims")
                + ", fraud checks received: " + fraudCheckInbox);
        System.out.println("CLM-2 will be paid without a fraud check.");

        System.out.println("-- transactional outbox --");
        fraudCheckInbox.clear();
        DataSource db = Db.inMemory("claims_outbox", ClaimServices.SCHEMA);
        for (String id : List.of("CLM-1", "CLM-2", "CLM-3")) {
            ClaimServices.submitWithOutbox(db, id, "POL-9", 250_000);
        }
        OutboxRelay relay = new OutboxRelay(db, (key, payload) -> flakyBroker.accept(payload));
        relay.poll(10); // CLM-1 published; CLM-2 fails, so the relay stops and keeps order
        new OutboxRelay(db, (key, payload) -> fraudCheckInbox.add(payload)).poll(10); // next poll, broker healthy
        System.out.println("claims saved: " + Db.count(db, "SELECT COUNT(*) FROM claims")
                + ", fraud checks received: " + fraudCheckInbox);
    }
}

    Output:

    === Insurance: claim submitted -> fraud check must always run ===
-- dual write (save, then publish) --
  CLM-2: saved, but publish failed: broker timeout
claims saved: 3, fraud checks received: [ClaimSubmitted CLM-1, ClaimSubmitted CLM-3]
CLM-2 will be paid without a fraud check.
-- transactional outbox --
  relay: broker unavailable (broker timeout), will retry
claims saved: 3, fraud checks received: [ClaimSubmitted CLM-1, ClaimSubmitted CLM-2, ClaimSubmitted CLM-3]

    Why an outbox here:

    • In regulated domains, a missing event is a compliance and fraud risk, not just a bug.
    • The fix needs no new infrastructure: one table and a relay.

    Example 3: At-Least-Once and Consumer Dedupe (Ride-hailing)¶

    Scenario: The relay publishes TripCompleted TRIP-1, then crashes before marking the row. On restart it publishes TRIP-1 again. The billing consumer keeps processed event IDs (the outbox row ID), so the rider gets one receipt per trip.

    Full Code:

    package com.handbook.microservices.outbox.ridehailing;

import java.util.HashSet;
import java.util.Set;

/**
 * Outbox relays are at-least-once: if the relay crashes after publishing but before marking the
 * row, the event is published again. Consumers deduplicate by event ID.
 */
public final class TripEventsConsumer {

    private final Set<Long> processedEventIds = new HashSet<>(); // a processed_events table in real life
    private int fareReceiptsSent;

    public void onEvent(long eventId, String payload) {
        if (!processedEventIds.add(eventId)) { // (1)!
            System.out.println("  billing: duplicate event " + eventId + " ignored");
            return;
        }
        fareReceiptsSent++;
        System.out.println("  billing: receipt sent for " + payload);
    }

    public int fareReceiptsSent() {
        return fareReceiptsSent;
    }
}
    1. In production, insert the event ID into a processed_events table in the same transaction as the consumer's own update (see Idempotent Consumer).
    package com.handbook.microservices.outbox.ridehailing;

import com.handbook.microservices.support.Db;

import javax.sql.DataSource;
import java.sql.Connection;
import java.sql.PreparedStatement;
import java.sql.ResultSet;
import java.sql.SQLException;
import java.sql.Statement;

public class CrashingRelayDemo {

    public static void main(String[] args) throws SQLException {
        DataSource db = Db.inMemory("trips",
                "CREATE TABLE outbox (id BIGINT AUTO_INCREMENT PRIMARY KEY, payload VARCHAR, published BOOLEAN DEFAULT FALSE)",
                "INSERT INTO outbox (payload) VALUES ('TripCompleted TRIP-1 ₹212'), ('TripCompleted TRIP-2 ₹96')");
        var billing = new TripEventsConsumer();

        System.out.println("=== Ride-hailing: relay crashes between publish and mark ===");
        relay(db, billing, true);
        System.out.println("-- relay restarts --");
        relay(db, billing, false);
        System.out.println("Events delivered: 3, receipts sent: " + billing.fareReceiptsSent() + " (exactly once per trip)");
    }

    /** A relay that publishes with the row ID as the event ID; optionally crashes before marking. */
    private static void relay(DataSource db, TripEventsConsumer consumer, boolean crashAfterFirstPublish)
            throws SQLException {
        try (Connection c = db.getConnection(); Statement s = c.createStatement();
             ResultSet rs = s.executeQuery("SELECT id, payload FROM outbox WHERE published = FALSE ORDER BY id");
             PreparedStatement mark = c.prepareStatement("UPDATE outbox SET published = TRUE WHERE id = ?")) {
            while (rs.next()) {
                consumer.onEvent(rs.getLong("id"), rs.getString("payload"));
                if (crashAfterFirstPublish) {
                    System.out.println("  relay: CRASH before marking event " + rs.getLong("id"));
                    return;
                }
                mark.setLong(1, rs.getLong("id"));
                mark.executeUpdate();
            }
        }
    }
}

    Output:

    === Ride-hailing: relay crashes between publish and mark ===
  billing: receipt sent for TripCompleted TRIP-1 ₹212
  relay: CRASH before marking event 1
-- relay restarts --
  billing: duplicate event 1 ignored
  billing: receipt sent for TripCompleted TRIP-2 ₹96
Events delivered: 3, receipts sent: 2 (exactly once per trip)

    Why dedupe is part of the pattern:

    • The outbox guarantees at-least-once, not exactly-once: "publish" and "mark published" can't be atomic.
    • Outbox + idempotent consumer = exactly-once effect.
    Unit Tests: TransactionalOutboxTest.java 
    package com.handbook.microservices;

import com.handbook.microservices.outbox.grocery.OrderService;
import com.handbook.microservices.outbox.grocery.OutboxRelay;
import com.handbook.microservices.support.Db;
import org.junit.jupiter.api.Test;

import javax.sql.DataSource;
import java.util.ArrayList;
import java.util.List;

import static org.assertj.core.api.Assertions.assertThat;
import static org.assertj.core.api.Assertions.assertThatThrownBy;

class TransactionalOutboxTest {

    @Test
    void orderAndEventCommitOrRollBackTogether() throws Exception {
        DataSource db = Db.inMemory("t_outbox", OrderService.SCHEMA);
        var orders = new OrderService(db);
        orders.placeOrder("O1", "C", 100);
        assertThatThrownBy(() -> orders.placeOrder("O1", "C", 100)).isInstanceOf(java.sql.SQLException.class);
        assertThat(Db.count(db, "SELECT COUNT(*) FROM orders")).isEqualTo(1);
        assertThat(Db.count(db, "SELECT COUNT(*) FROM outbox")).isEqualTo(1);
    }

    @Test
    void relayPublishesInOrderAndMarksRows() throws Exception {
        DataSource db = Db.inMemory("t_relay", OrderService.SCHEMA);
        var orders = new OrderService(db);
        orders.placeOrder("O1", "C", 100);
        orders.placeOrder("O2", "C", 200);
        List<String> published = new ArrayList<>();
        assertThat(new OutboxRelay(db, (k, p) -> published.add(k)).poll(10)).isEqualTo(2);
        assertThat(published).containsExactly("O1", "O2");
        assertThat(new OutboxRelay(db, (k, p) -> published.add(k)).poll(10)).isZero();
    }
}

    6. Variations & Modern Java Take¶

    Spring Boot (compiled in the spring-reference module):

    package com.handbook.springref.outbox;

import org.springframework.jdbc.core.JdbcTemplate;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

/** The business write and the outbox insert share one @Transactional boundary. */
@Service
public class PlaceOrderHandler {

    private final JdbcTemplate jdbc;

    public PlaceOrderHandler(JdbcTemplate jdbc) {
        this.jdbc = jdbc;
    }

    @Transactional
    public void placeOrder(String orderId, String customerId, long totalPaise) {
        jdbc.update("INSERT INTO orders (id, customer_id, total_paise) VALUES (?, ?, ?)",
                orderId, customerId, totalPaise);
        jdbc.update("INSERT INTO outbox (topic, aggregate_id, payload) VALUES (?, ?, ?)",
                "orders.placed", orderId,
                "{\"orderId\":\"" + orderId + "\",\"totalPaise\":" + totalPaise + "}");
    }
}

    package com.handbook.springref.outbox;

import org.springframework.jdbc.core.JdbcTemplate;
import org.springframework.kafka.core.KafkaTemplate;
import org.springframework.scheduling.annotation.Scheduled;
import org.springframework.stereotype.Component;
import org.springframework.transaction.annotation.Transactional;

import java.util.List;
import java.util.Map;

/**
 * A polling outbox relay with JdbcTemplate and KafkaTemplate (requires @EnableScheduling).
 * FOR UPDATE SKIP LOCKED (PostgreSQL, MySQL 8) lets several relay instances run without
 * publishing the same row; .get() waits for the broker's ack before the row is marked.
 */
@Component
public class OutboxRelayJob {

    private final JdbcTemplate jdbc;
    private final KafkaTemplate<String, String> kafka;

    public OutboxRelayJob(JdbcTemplate jdbc, KafkaTemplate<String, String> kafka) {
        this.jdbc = jdbc;
        this.kafka = kafka;
    }

    @Scheduled(fixedDelay = 500)
    @Transactional
    public void relay() throws Exception {
        List<Map<String, Object>> rows = jdbc.queryForList(
                "SELECT id, topic, aggregate_id, payload FROM outbox "
                        + "WHERE published_at IS NULL ORDER BY id LIMIT 100 FOR UPDATE SKIP LOCKED");
        for (Map<String, Object> row : rows) {
            kafka.send((String) row.get("topic"), (String) row.get("aggregate_id"), (String) row.get("payload"))
                    .get(); // at-least-once: if we crash after this, the row is published again
            jdbc.update("UPDATE outbox SET published_at = now() WHERE id = ?", row.get("id"));
        }
    }
}

    CREATE TABLE outbox (
  id           BIGSERIAL PRIMARY KEY,
  topic        TEXT        NOT NULL,
  aggregate_id TEXT        NOT NULL,           -- message key (ordering per aggregate)
  payload      JSONB       NOT NULL,
  created_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
  published_at TIMESTAMPTZ
);
CREATE INDEX outbox_unpublished ON outbox (id) WHERE published_at IS NULL;

    9. Pitfalls & Anti-Patterns¶

    Publishing from inside the transaction

    Calling kafkaTemplate.send() inside @Transactional doesn't make it transactional with the DB. If the DB commit fails afterwards, the event is already out.

    Multiple relays without claiming

    Two relay instances reading the same unpublished rows publish everything twice. Use FOR UPDATE SKIP LOCKED, leader election, or atomic claims (see the coding challenge).

    Never cleaning the outbox

    Millions of published rows slow the relay's query. Delete or archive published rows (e.g. older than 7 days) on a schedule, or partition by date.

    Breaking ordering with parallel publishing

    Publishing rows in parallel or with retries out of order can deliver OrderCancelled before OrderPlaced. Keep per-aggregate order (the key) and publish sequentially per key.

    10. Senior / Architect Deep Dive (10–15 yrs)¶

    Polling vs. CDC. Polling is the pragmatic default: easy to understand, monitor and debug. CDC (Debezium) is better at high volume or when you also need the database's change stream for other consumers, at the cost of running Kafka Connect and managing connector offsets and schema changes.

    Event payload design. Outbox payloads are a public contract: version them, prefer business events (OrderPlaced with the needed fields) over raw row dumps, and avoid leaking internal schema. CDC on raw tables couples consumers to your schema; the outbox decouples them.

    The inbox counterpart. On the consumer side, a transactional inbox (processed-message table) gives exactly-once effect. Together: outbox (producer) + inbox (consumer).

    Production checklist¶

    • Outbox insert in the same transaction as the state change (@Transactional covers both).
    • Relay: ordered by ID, keyed by aggregate ID, waits for broker ack before marking.
    • Multiple relays coordinated (SKIP LOCKED, leader election, or CDC).
    • Consumers idempotent (event ID dedupe).
    • Metrics: outbox lag (oldest unpublished age), relay errors; alert when lag grows.
    • Housekeeping job for published rows; versioned payload schemas.

    Explain it in 2 minutes (system design round)¶

    "Every service that changes state and publishes events writes the event into an outbox table in the same local transaction. A relay (polling with SKIP LOCKED, or Debezium CDC at higher volume) publishes rows to Kafka keyed by aggregate ID, so per-entity order is preserved, and marks them published after the broker acks. That's at-least-once, so every consumer deduplicates by event ID in its own transaction. We alert on outbox lag and clean up published rows daily. This removes the dual-write problem without distributed transactions."

    War story: the missing invoices

    A B2B platform saved orders, then published OrderPlaced to RabbitMQ in the same method. During a 4-minute broker failover, the publish calls failed after the DB commits. About 1,800 orders were saved but never invoiced. Nobody noticed for a month, until the quarterly revenue reconciliation came up short. Fix: a transactional outbox with a polling relay and a lag alert; a one-time reconciliation job compared orders with invoices and backfilled the missing events. Lesson: dual writes fail silently. Make the event part of the same transaction, and reconcile.

    12. Interview Corner¶

    Q1. What is the dual-write problem?

    Writing to a database and publishing to a broker as two separate operations: if one succeeds and the other fails, the systems become inconsistent.

    Q2. What is the transactional outbox pattern?

    Save the event into an outbox table in the same DB transaction as the business data, then a separate relay publishes it to the broker.

    Q3. Does it guarantee exactly-once delivery?

    No: at-least-once. Consumers must handle duplicates.

    Q4. What is Debezium?

    A change data capture tool that reads the database's transaction log and publishes changes (including outbox rows) to Kafka.

    Q5. Why not publish to Kafka inside @Transactional?

    Kafka isn't part of the database transaction; the event could be sent even if the DB commit later fails.

    Q1. Polling relay vs. CDC?

    Polling: simple, adds query load and latency. CDC: low latency, no polling, but needs Kafka Connect/Debezium infrastructure.

    Q2. How do you preserve event order?

    Relay in ID order and use the aggregate ID as the message key, so all events for one entity land in one partition.

    Q3. How do multiple relay instances avoid duplicates?

    SELECT ... FOR UPDATE SKIP LOCKED, atomic claim updates, or a single active relay via leader election.

    Q4. How do consumers handle duplicates?

    Store processed event IDs (unique constraint) in the same transaction as their own update and skip IDs already seen.

    Q5. What do you monitor?

    Outbox lag (age of the oldest unpublished row), relay error rate, and table size.

    Q1. "Design reliable event publishing for 50k writes/second."

    CDC (Debezium) from the WAL instead of polling, outbox partitioned by time, events keyed by aggregate, consumers idempotent; capacity for connector lag; schema registry for payloads.

    Q2. "Outbox vs. event sourcing?"

    The outbox adds events alongside state; event sourcing makes events the state. The outbox is far easier to adopt in an existing CRUD service.

    Q3. "What if the relay publishes, the broker acks, and the DB update to mark published fails?"

    The event is republished on the next poll, which is expected under at-least-once. Consumers deduplicate. Never try to make it exactly-once at the producer.

    Q4. "Should the outbox contain the full entity or a minimal event?"

    A business event with the fields consumers need (and a version). Thin events ("OrderPlaced id=1") force consumers to call back (coupling and load); full row dumps leak internals. Design them as public contracts.

    Q5. "How do you migrate a service with dual writes to the outbox safely?"

    Add the outbox table and write to it in the transaction, run the relay to a shadow topic and compare, switch consumers, remove the direct publish, and run a reconciliation job for the past window.

    Problem: Run three relay instances concurrently over 500 outbox rows. No row may be published twice and none may be missed. (PostgreSQL would use SKIP LOCKED; implement it with an atomic conditional UPDATE.)

    Solution 
    package com.handbook.microservices.outbox.claiming;

import javax.sql.DataSource;
import java.sql.Connection;
import java.sql.PreparedStatement;
import java.sql.ResultSet;
import java.sql.SQLException;
import java.util.ArrayList;
import java.util.List;
import java.util.function.LongConsumer;

/**
 * Coding challenge: several relay instances (for availability) must not publish the same row.
 * Each relay atomically claims a batch with a conditional UPDATE, then publishes only its claim.
 * (On PostgreSQL you would use SELECT ... FOR UPDATE SKIP LOCKED instead.)
 */
public final class ClaimingRelay {

    private final DataSource db;
    private final String relayId;

    public ClaimingRelay(DataSource db, String relayId) {
        this.db = db;
        this.relayId = relayId;
    }

    public int pollOnce(int batchSize, LongConsumer publish) throws SQLException {
        try (Connection c = db.getConnection()) {
            c.setAutoCommit(false);
            List<Long> claimed = new ArrayList<>();
            try (PreparedStatement select = c.prepareStatement(
                    "SELECT id FROM outbox WHERE claimed_by IS NULL ORDER BY id LIMIT ?");
                 PreparedStatement claim = c.prepareStatement(
                         "UPDATE outbox SET claimed_by = ? WHERE id = ? AND claimed_by IS NULL")) {
                select.setInt(1, batchSize);
                try (ResultSet rs = select.executeQuery()) {
                    while (rs.next()) {
                        claim.setString(1, relayId);
                        claim.setLong(2, rs.getLong(1));
                        if (claim.executeUpdate() == 1) { // 0 rows means another relay won this one
                            claimed.add(rs.getLong(1));
                        }
                    }
                }
                c.commit();
            } catch (SQLException e) {
                c.rollback();
                throw e;
            }
            claimed.forEach(publish::accept);
            return claimed.size();
        }
    }
}

    package com.handbook.microservices.outbox.claiming;

import com.handbook.microservices.support.Db;

import javax.sql.DataSource;
import java.util.Map;
import java.util.concurrent.ConcurrentHashMap;
import java.util.concurrent.CountDownLatch;
import java.util.concurrent.atomic.AtomicInteger;

public class ClaimingRelayDemo {

    public static void main(String[] args) throws Exception {
        DataSource db = Db.inMemory("claiming",
                "CREATE TABLE outbox (id BIGINT AUTO_INCREMENT PRIMARY KEY, claimed_by VARCHAR)",
                "INSERT INTO outbox (claimed_by) SELECT NULL FROM SYSTEM_RANGE(1, 500)");

        Map<Long, AtomicInteger> publishCount = new ConcurrentHashMap<>();
        CountDownLatch start = new CountDownLatch(1);
        Thread[] relays = new Thread[3];
        for (int r = 0; r < relays.length; r++) {
            ClaimingRelay relay = new ClaimingRelay(db, "relay-" + r);
            relays[r] = Thread.ofPlatform().start(() -> {
                try {
                    start.await();
                    while (relay.pollOnce(20, id -> publishCount.computeIfAbsent(id, k -> new AtomicInteger())
                            .incrementAndGet()) > 0) {
                        // keep polling until nothing is left
                    }
                } catch (Exception e) {
                    throw new IllegalStateException(e);
                }
            });
        }
        start.countDown();
        for (Thread t : relays) {
            t.join();
        }

        System.out.println("=== Challenge: 3 relay instances, 500 outbox rows ===");
        System.out.println("Rows published      : " + publishCount.size());
        System.out.println("Published twice     : " + publishCount.values().stream().filter(c -> c.get() > 1).count());
        System.out.println("Every row claimed   : " + (Db.count(db, "SELECT COUNT(*) FROM outbox WHERE claimed_by IS NULL") == 0));
    }
}

    === Challenge: 3 relay instances, 500 outbox rows ===
Rows published      : 500
Published twice     : 0
Every row claimed   : true

    Key points to say: UPDATE ... WHERE claimed_by IS NULL is atomic per row, so only one relay's update returns 1. Also add a claim timeout (if a relay dies after claiming, the rows must be re-claimable), and remember that cross-relay ordering per aggregate needs partitioning rows by key.

    13. Quick Revision Card¶

    Remember in 30 seconds

    • Dual write = lost or phantom events.
    • Business row + outbox row in one local transaction.
    • Relay: polling (SKIP LOCKED) or CDC (Debezium); key = aggregate ID.
    • At-least-once → idempotent consumers.
    • Monitor outbox lag; clean up published rows.

    Practice¶

    • Add a created_at column and a cleanup job that deletes published rows older than 7 days.
    • Add a claim timeout to ClaimingRelay so rows claimed by a dead relay become available again.
    • Change OutboxRelay to continue with other aggregates when one aggregate's event fails (per-key ordering only).
