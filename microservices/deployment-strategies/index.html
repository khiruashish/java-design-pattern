    Deployment Strategies: Blue-Green, Canary & Feature Toggles¶

    🟡 Intermediate Microservices Interview frequency ⭐⭐⭐⭐⭐

    TL;DR

    Separate deploying code from releasing it, and make every release reversible. Blue-green switches all traffic between two full environments; canary shifts traffic gradually and rolls back automatically on bad metrics; feature toggles turn features on per user, percentage or segment without redeploying. Use all three: canary or blue-green for every deploy, toggles for risky features, and expand/contract migrations so old and new versions can run side by side.

    See It in Motion¶

    Press Play to watch the calls travel between components, or step through with Next and Back. Open the full explorer with all 66 patterns

    1. Intent & Problem It Solves¶

    The problem in plain English: the team deploys checkout v42 on Friday evening by replacing v41 on every server. A bug for coupon users appears at once, for everyone. Rolling back means another full deploy (15 minutes) while orders fail. Next time, people deploy less often, batches get bigger, and each release gets riskier.

    The strategies:

    Strategy How Blast radius Rollback Cost
    Recreate / big bang Stop old, start new 100% Redeploy Low, but has downtime
    Rolling Replace instances a few at a time Grows over time Roll forward/back gradually Low (Kubernetes default)
    Blue-green Two full environments; switch the router 100% at switch Instant (switch back) 2× capacity during release
    Canary Small % of traffic to the new version, then increase 1% → 100% Instant (route back) Needs good metrics
    Feature toggles Code deployed dark; enabled by configuration Any segment / % Instant (flip flag) Flag debt to clean up

    2. Real-World Analogy¶

    Opening a new restaurant menu

    Blue-green: a second, fully staffed kitchen prepares the new menu; at 7 pm all orders switch to it, and if something's wrong, orders switch back. Canary: the new dish is offered to one table in a hundred first, and the manager watches whether plates come back. Feature toggle: the dish is on the menu card but hidden for most guests, shown to staff and regulars first, and can be removed instantly if a supplier fails.

    3. Structure¶

    flowchart LR U[Users] --> R{Router / gateway / mesh} R -->|"blue-green: 100% to live colour"| B[Blue v41] R -.-> G[Green v42] R -->|"canary: 95%"| S[Stable v41] R -->|"canary: 5%"| C[Canary v42] C --> M[(Metrics: errors, latency, business KPIs)] M -->|"bad → rollback"| R F[(Flag service)] -->|"isOn(feature, user)"| S & C
    Element Responsibility
    Router Load balancer, gateway, ingress or service mesh that controls traffic split
    Environments / versions Blue + green, or stable + canary
    Analysis Compares canary vs baseline metrics and decides continue / rollback
    Flag service Evaluates toggles per request (LaunchDarkly, Unleash, OpenFeature providers)
    Compatible data Schemas and messages that both versions can read and write (expand/contract)

    4. Naive Approach (Without the Pattern)¶

    1. Stop all v41 instances
2. Run DB migration (rename column)
3. Start v42 everywhere
4. Bug? → revert code, but the column was renamed → v41 can't start either
    • Every user hits every bug immediately.
    • Rollback is a new deploy, and may be impossible after a breaking migration.
    • Releases become rare, big and scary.

    5. Three Real-World Examples¶

    Example 1: Blue-Green Checkout Release (E-commerce)¶

    Scenario: The checkout service runs as two identical environments behind the load balancer. v42 is deployed to the idle (green) environment and smoke-tested with no customer traffic. The router then switches all traffic to green. A coupon bug appears; switching back to blue (still running v41, warm and unchanged) is one step.

    Design:

    sequenceDiagram autonumber participant Ops participant R as Router participant B as Blue (v41) participant G as Green (v42) Ops->>G: deploy v42 + smoke test Ops->>R: switch → green R->>G: 100% of traffic Note over G: coupon bug! Ops->>R: switch → blue (rollback in seconds) R->>B: 100% of traffic

    Full Code:

    package com.handbook.microservices.deployment.bluegreen;

import java.util.function.Function;

/** Two full environments; the router points ALL traffic at one of them. Switching (and rolling back) is one step. */
public final class BlueGreenRouter {

    private Function<String, String> blue;
    private Function<String, String> green;
    private String live = "blue";

    public BlueGreenRouter(Function<String, String> blue) {
        this.blue = blue;
    }

    public void deployToIdle(Function<String, String> newVersion) { // (1)!
        if (live.equals("blue")) {
            green = newVersion;
        } else {
            blue = newVersion;
        }
    }

    public String smokeTestIdle(String request) { // (2)!
        return (live.equals("blue") ? green : blue).apply(request);
    }

    public void switchTraffic() { // (3)!
        live = live.equals("blue") ? "green" : "blue";
    }

    public String handle(String request) {
        return live + ": " + (live.equals("blue") ? blue : green).apply(request);
    }
}
    1. Deploy to the idle colour: customers are unaffected while it starts and warms up.
    2. Smoke-test the idle environment with synthetic requests before any customer sees it.
    3. The release (and the rollback) is a single router change: a DNS weight, a load-balancer target group, a Kubernetes Service selector.
    package com.handbook.microservices.deployment.bluegreen;

public class BlueGreenDemo {

    public static void main(String[] args) {
        System.out.println("=== E-commerce: Blue-Green Release of the Checkout Service ===");
        BlueGreenRouter router = new BlueGreenRouter(cart -> "total INR 1,240 (v41)");
        System.out.println("Before release   -> " + router.handle("cart-1"));

        router.deployToIdle(cart -> cart.equals("cart-with-coupon") ? "500 NullPointerException (v42)" : "total INR 1,240 (v42)");
        System.out.println("Smoke test green -> " + router.smokeTestIdle("cart-1") + " (no customer traffic yet)");

        router.switchTraffic();
        System.out.println("After switch     -> " + router.handle("cart-1"));
        System.out.println("Coupon user      -> " + router.handle("cart-with-coupon") + "  <- bug found in production");

        router.switchTraffic(); // rollback = flip back; blue is still running v41, warm and unchanged
        System.out.println("Rollback (1 step)-> " + router.handle("cart-with-coupon"));
    }
}

    Output:

    === E-commerce: Blue-Green Release of the Checkout Service ===
Before release   -> blue: total INR 1,240 (v41)
Smoke test green -> total INR 1,240 (v42) (no customer traffic yet)
After switch     -> green: total INR 1,240 (v42)
Coupon user      -> green: 500 NullPointerException (v42)  <- bug found in production
Rollback (1 step)-> blue: total INR 1,240 (v41)

    Why blue-green here:

    • Instant rollback to a warm, known-good environment.
    • The new version is fully started and verified before taking traffic.
    • Simple mental model; good for stateful edge services and big-bang changes that can't be split.

    Example 2: Canary with Automated Analysis (Ride-hailing)¶

    Scenario: A new fare engine is rolled out in steps: 1% → 5% → 25% → 50% of rides, then promoted. At each step, the canary's error rate is compared with the stable baseline (10,000 rides per step); if the canary is worse by more than 0.5 percentage points, the rollout stops and traffic returns to stable. Release 7.3 is healthy; release 7.4 breaks fares for airport pickups.

    Design:

    flowchart LR S1["1%"] -->|"canary − baseline ≤ 0.5pp"| S2["5%"] --> S3["25%"] --> S4["50%"] --> P["PROMOTE 100%"] S1 -->|"worse"| RB["ROLLBACK to stable"] S2 --> RB S3 --> RB S4 --> RB

    Full Code:

    package com.handbook.microservices.deployment.canary;

import java.util.ArrayList;
import java.util.List;
import java.util.Random;

/** Progressive delivery: shift traffic in steps and compare canary vs baseline error rates before each step. */
public final class CanaryAnalysis {

    public record StepResult(int percent, double baselineErrorPct, double canaryErrorPct, String decision) { }

    private final int[] steps;
    private final double maxErrorIncreasePct;

    public CanaryAnalysis(int[] steps, double maxErrorIncreasePct) {
        this.steps = steps;
        this.maxErrorIncreasePct = maxErrorIncreasePct;
    }

    /** Simulates 10,000 requests per step with the given true error probabilities (seeded, so reproducible). */
    public List<StepResult> run(double baselineErrorRate, double canaryErrorRate, long seed) {
        Random random = new Random(seed);
        List<StepResult> results = new ArrayList<>();
        for (int percent : steps) {
            int canaryRequests = 10_000 * percent / 100;
            int baselineRequests = 10_000 - canaryRequests;
            double b = errors(random, baselineRequests, baselineErrorRate) * 100.0 / Math.max(1, baselineRequests);
            double c = errors(random, canaryRequests, canaryErrorRate) * 100.0 / Math.max(1, canaryRequests);
            boolean healthy = c - b <= maxErrorIncreasePct; // (1)!
            boolean last = percent == steps[steps.length - 1];
            results.add(new StepResult(percent, b, c, healthy ? (last ? "PROMOTE to 100%" : "continue") : "ROLLBACK"));
            if (!healthy) {
                break; // (2)!
            }
        }
        return results;
    }

    private static int errors(Random random, int requests, double rate) {
        int n = 0;
        for (int i = 0; i < requests; i++) {
            n += random.nextDouble() < rate ? 1 : 0;
        }
        return n;
    }
}
    1. Compare canary to the baseline at the same time, not to last week: both see the same traffic mix and incidents.
    2. Stop at the first bad step. Argo Rollouts / Flagger do this with Prometheus queries as "analysis templates".
    package com.handbook.microservices.deployment.canary;

import com.handbook.microservices.deployment.canary.CanaryAnalysis.StepResult;

public class CanaryDemo {

    public static void main(String[] args) {
        System.out.println("=== Ride-hailing: Canary Rollout of a New Fare Engine (steps 1% -> 5% -> 25% -> 50%, then promote) ===");
        CanaryAnalysis analysis = new CanaryAnalysis(new int[] {1, 5, 25, 50}, 0.5);

        System.out.println("Release 7.3 (healthy):");
        for (StepResult r : analysis.run(0.004, 0.0045, 11)) {
            print(r);
        }
        System.out.println("Release 7.4 (bug: fares fail for airport pickups, ~3% of rides):");
        for (StepResult r : analysis.run(0.004, 0.034, 11)) {
            print(r);
        }
        System.out.println("The bad release was stopped at 1% of rides, automatically, instead of reaching everyone.");
    }

    private static void print(StepResult r) {
        System.out.printf("  %3d%% canary: baseline %.2f%% errors, canary %.2f%% -> %s%n",
                r.percent(), r.baselineErrorPct(), r.canaryErrorPct(), r.decision());
    }
}

    Output:

    === Ride-hailing: Canary Rollout of a New Fare Engine (steps 1% -> 5% -> 25% -> 50%, then promote) ===
Release 7.3 (healthy):
    1% canary: baseline 0.32% errors, canary 0.00% -> continue
    5% canary: baseline 0.20% errors, canary 0.00% -> continue
   25% canary: baseline 0.37% errors, canary 0.44% -> continue
   50% canary: baseline 0.30% errors, canary 0.54% -> PROMOTE to 100%
Release 7.4 (bug: fares fail for airport pickups, ~3% of rides):
    1% canary: baseline 0.32% errors, canary 4.00% -> ROLLBACK
The bad release was stopped at 1% of rides, automatically, instead of reaching everyone.

    Why canary here:

    • A bad release reaches 1% of rides, not 100%.
    • The decision is automatic and metric-driven, not "someone was watching the dashboard".
    • Real traffic finds bugs that tests and staging don't (airport pickups!).

    Example 3: Feature Toggles for Instant Loans (Banking)¶

    Scenario: A bank ships "instant loan offers" code to production weeks before launch, switched off. Employees see it first (dogfooding), then 10% of customers, then 50%. Each customer's experience must be sticky (the same answer on every visit). When the credit-risk team spots a scoring issue, a kill switch turns it off for everyone in seconds, with no deploy.

    Design:

    flowchart LR Req["isOn('instant-loans', user, segment)"] --> K{kill switch?} K -- on --> Off[false] K -- off --> Seg{segment targeted?} Seg -- employees --> On[true] Seg -- no --> B{"hash(feature:user) % 100 < percent?"} B -- yes --> On B -- no --> Off

    Full Code:

    package com.handbook.microservices.deployment.toggles;

import java.nio.charset.StandardCharsets;
import java.util.HashMap;
import java.util.Map;
import java.util.Set;
import java.util.zip.CRC32;

/** Release toggles decoupled from deploys: segment targeting, sticky percentage rollout, and a kill switch. */
public final class FeatureToggles {

    public record Rule(boolean killSwitchOn, Set<String> segments, int percent) { }

    private final Map<String, Rule> rules = new HashMap<>();

    public void set(String feature, Rule rule) {
        rules.put(feature, rule);
    }

    public boolean isOn(String feature, String userId, String segment) {
        Rule r = rules.get(feature);
        if (r == null || r.killSwitchOn()) { // (1)!
            return false;
        }
        if (r.segments().contains(segment)) { // (2)!
            return true;
        }
        return bucket(feature, userId) < r.percent(); // (3)!
    }

    /** Stable 0..99 bucket per (feature, user): the same user always gets the same answer. */
    static int bucket(String feature, String userId) {
        CRC32 crc = new CRC32();
        crc.update((feature + ":" + userId).getBytes(StandardCharsets.UTF_8));
        return (int) (crc.getValue() % 100);
    }
}
    1. The kill switch is checked first and overrides everything.
    2. Segment targeting: employees, beta testers, one city, one tenant.
    3. Sticky percentage rollout: a stable hash puts each user in a bucket 0–99, so raising 10% → 50% keeps everyone who already had it.
    package com.handbook.microservices.deployment.toggles;

import com.handbook.microservices.deployment.toggles.FeatureToggles.Rule;

import java.util.Set;

public class TogglesDemo {

    public static void main(String[] args) {
        System.out.println("=== Banking: Rolling Out 'Instant Loan Offers' with Feature Toggles ===");
        FeatureToggles toggles = new FeatureToggles();
        toggles.set("instant-loans", new Rule(false, Set.of("employees"), 10)); // code already deployed to everyone

        System.out.println("Employee (dogfooding)  : " + toggles.isOn("instant-loans", "emp-17", "employees"));
        System.out.println("Customers enabled at 10%: " + count(toggles) + " of 10,000");
        System.out.println("cust-123 asks 3 times   : " + toggles.isOn("instant-loans", "cust-123", "retail") + ", "
                + toggles.isOn("instant-loans", "cust-123", "retail") + ", " + toggles.isOn("instant-loans", "cust-123", "retail") + " (sticky)");

        toggles.set("instant-loans", new Rule(false, Set.of("employees"), 50));
        System.out.println("Raised to 50%           : " + count(toggles) + " of 10,000 (everyone from the 10% still has it)");

        toggles.set("instant-loans", new Rule(true, Set.of("employees"), 50)); // credit-risk team spots a scoring issue
        System.out.println("Kill switch flipped     : " + count(toggles) + " of 10,000, employee=" + toggles.isOn("instant-loans", "emp-17", "employees")
                + " (no deploy needed)");
    }

    private static int count(FeatureToggles toggles) {
        int on = 0;
        for (int i = 0; i < 10_000; i++) {
            on += toggles.isOn("instant-loans", "cust-" + i, "retail") ? 1 : 0;
        }
        return on;
    }
}

    Output:

    === Banking: Rolling Out 'Instant Loan Offers' with Feature Toggles ===
Employee (dogfooding)  : true
Customers enabled at 10%: 1038 of 10,000
cust-123 asks 3 times   : false, false, false (sticky)
Raised to 50%           : 4908 of 10,000 (everyone from the 10% still has it)
Kill switch flipped     : 0 of 10,000, employee=false (no deploy needed)

    Why feature toggles here:

    • Deploy ≠ release: code ships continuously; business decides when users see it.
    • Gradual exposure by segment and percentage, with consistent experiences.
    • Fastest possible rollback for a feature (seconds), independent of the deploy pipeline.
    Unit Tests: DeploymentStrategiesTest.java 
    package com.handbook.microservices;

import com.handbook.microservices.deployment.bluegreen.BlueGreenRouter;
import com.handbook.microservices.deployment.canary.CanaryAnalysis;
import com.handbook.microservices.deployment.toggles.FeatureToggles;
import com.handbook.microservices.deployment.toggles.FeatureToggles.Rule;
import org.junit.jupiter.api.Test;

import java.util.Set;

import static org.assertj.core.api.Assertions.assertThat;

class DeploymentStrategiesTest {

    @Test
    void rollbackRestoresTheOldVersionInOneStep() {
        BlueGreenRouter r = new BlueGreenRouter(x -> "old");
        r.deployToIdle(x -> "new");
        r.switchTraffic();
        assertThat(r.handle("x")).isEqualTo("green: new");
        r.switchTraffic();
        assertThat(r.handle("x")).isEqualTo("blue: old");
    }

    @Test
    void badCanaryIsRolledBackEarly() {
        var results = new CanaryAnalysis(new int[] {1, 5, 25, 100}, 0.5).run(0.001, 0.2, 1);
        assertThat(results.get(results.size() - 1).decision()).isEqualTo("ROLLBACK");
        assertThat(results.get(results.size() - 1).percent()).isLessThan(100);
    }

    @Test
    void togglesAreStickyAndKillSwitchWins() {
        FeatureToggles t = new FeatureToggles();
        t.set("f", new Rule(false, Set.of("beta"), 30));
        boolean first = t.isOn("f", "u1", "x");
        assertThat(t.isOn("f", "u1", "x")).isEqualTo(first);
        assertThat(t.isOn("f", "u2", "beta")).isTrue();
        t.set("f", new Rule(true, Set.of("beta"), 100));
        assertThat(t.isOn("f", "u2", "beta")).isFalse();
    }
}

    Variation Notes
    Rolling update Kubernetes maxSurge/maxUnavailable; relies on readiness probes (Health Check)
    Shadow / dark launch Mirror real traffic to the new version and discard its responses; compare outputs
    A/B testing Toggles + experiment analysis on business metrics (conversion), not just errors
    Ring deployments Internal users → one region → all regions
    Toggle types Release (short-lived), ops/kill switches (long-lived), experiments, permissions

    7. Where It Lives in Real Frameworks¶

    Where Deployment strategies
    Kubernetes Rolling updates, readiness-gated rollout, kubectl rollout undo
    Argo Rollouts / Flagger Canary and blue-green with automated analysis (Prometheus, Datadog)
    Istio / Linkerd / Envoy Weighted routing, header-based routing, traffic mirroring
    Spring Cloud Gateway Weight route predicates for canaries (see API Gateway)
    Feature flags OpenFeature SDK, Unleash, LaunchDarkly, FF4J, Togglz
    Databases Flyway / Liquibase migrations written in expand/contract style

    8. Pros, Cons & Trade-offs¶

    ✅ Pros ❌ Cons
    Small blast radius and fast rollback Both versions must be compatible (APIs, schemas, messages)
    Release decisions driven by metrics, not hope Canary needs reliable, low-noise metrics and enough traffic
    Frequent, small, low-stress releases Blue-green doubles capacity during releases
    Toggles let business control exposure Toggle sprawl and untested flag combinations

    9. Pitfalls & Anti-Patterns¶

    Breaking schema changes in the same release

    Renaming or dropping a column while old instances still run (or might be rolled back to) causes outages and blocks rollback. Use expand → migrate → contract across several releases (coding challenge).

    Canary metrics that can't see the bug

    Error rate alone won't catch "fares are 10% too low". Include business metrics (average fare, conversion) and compare against the baseline, not a fixed threshold.

    Toggles that never die

    Every release toggle doubles test paths. Give each an owner and an expiry date; delete the flag and the dead branch after full rollout.

    Sticky sessions and caches across versions

    Users bouncing between v41 and v42 (non-sticky routing) can see inconsistent behaviour; caches written by v42 in a new format can break v41 after rollback. Version cache keys and message formats.

    10. Senior / Architect Deep Dive (10–15 yrs)¶

    Compatibility is the real constraint. Any strategy that runs two versions at once (all of them except recreate) requires N and N−1 to coexist: backward-compatible APIs, tolerant readers for messages, additive schema changes, and dual-reading caches. Make "can we roll back?" a release checklist item.

    Statistics matter. At 1% of 10,000 requests you only see 100 requests: a 0.4% error rate is noise. Use enough traffic per step, longer bake times for low-volume services, and statistical tests (Kayenta's Mann-Whitney) rather than eyeballing.

    Data migrations are releases too. Backfills run as throttled jobs; dual-writes are verified with reconciliation queries before cutting reads over; the contract step is delayed until rollback past it is no longer needed.

    War story: the rollback that couldn't roll back

    A grocery team released v42 with a Flyway migration that renamed mobile to phone_e164. v42 had a checkout bug; they rolled back to v41, which crashed on startup because its queries referenced mobile. Checkout was down for 34 minutes while engineers wrote and deployed a reverse migration under pressure. Fix: migrations reviewed for expand/contract; CI runs the previous app version's integration tests against the new schema; renames take three releases. Lesson: a deployment strategy is only as reversible as your database changes.

    12. Interview Corner¶

    Q1. What is blue-green deployment?

    Two identical environments; deploy to the idle one, then switch all traffic; switch back to roll back.

    Q2. What is a canary release?

    Send a small percentage of traffic to the new version, watch metrics, then increase gradually or roll back.

    Q3. What is a feature toggle?

    A configuration switch that turns a feature on or off at runtime without redeploying.

    Q4. Rolling update vs blue-green?

    Rolling replaces instances gradually in one environment; blue-green switches between two complete environments at once.

    Q5. Why separate deploy from release?

    So code can ship often and safely, while exposure to users is controlled independently.

    Q1. How do you make a percentage rollout sticky?

    Hash a stable key (user id + feature name) into buckets; enable buckets below the percentage.

    Q2. What metrics would you watch during a canary?

    Error rate, latency percentiles, saturation, and business KPIs, compared with the baseline.

    Q3. How do you rename a column with zero downtime?

    Expand (add new), deploy dual-write, backfill, switch reads, deploy new-only, then contract (drop old).

    Q4. What's the downside of blue-green?

    Double capacity, and the switch exposes everyone at once (use a canary-style gradual switch if possible).

    Q5. What happens if the flag service is down?

    Use cached values and safe defaults (usually off); never block requests on the flag service.

    Q1. "Design the release process for 300 microservices."

    GitOps + Argo Rollouts canaries with automated analysis on standard SLIs; compatibility checks (contract tests, schema linting); OpenFeature for risky features with flag expiry; region rings; one-click rollback.

    Q2. "Canary looked fine but the release broke something. Why?"

    Low-traffic paths not exercised, metrics not covering the failure mode, bake time too short, or the bug only appears at scale (cache/DB load).

    Q3. "How do you canary a Kafka consumer?"

    Run the new version as a separate consumer group on mirrored data (shadow), or split partitions between versions; compare outputs before cutting over.

    Q4. "How do you manage toggle debt?"

    Typed toggles with owners and expiry, lint rules failing builds on expired flags, dashboards of flag age, and deletion as part of the feature's definition of done.

    Q5. "Blue-green with a database?"

    Usually one shared database with expand/contract migrations; separate databases per colour require data sync and are rarely worth it.

    Problem: Rename customers.mobile to customers.phone_e164 while rolling deploys run old and new app versions side by side. Show why a single RENAME causes an outage and which sequence keeps every running version working.

    Solution 
    package com.handbook.microservices.deployment.migration;

import java.util.LinkedHashMap;
import java.util.List;
import java.util.Map;
import java.util.Set;

/** Coding challenge: rename customers.mobile -> customers.phone_e164 without breaking old or new app versions. */
public class ExpandContractDemo {

    /** Columns that exist at each step, and which app versions are running during it. */
    record Step(String description, Set<String> columns, List<String> appsRunning) { }

    static boolean appWorks(String app, Set<String> columns) {
        return switch (app) {
            case "v1" -> columns.contains("mobile");                                   // reads/writes mobile
            case "v2" -> columns.contains("mobile") && columns.contains("phone_e164"); // writes both, reads new
            case "v3" -> columns.contains("phone_e164");                               // only the new column
            default -> throw new IllegalArgumentException(app);
        };
    }

    static void check(String title, List<Step> steps) {
        System.out.println(title);
        for (Step s : steps) {
            Map<String, Boolean> ok = new LinkedHashMap<>();
            s.appsRunning().forEach(a -> ok.put(a, appWorks(a, s.columns())));
            boolean safe = !ok.containsValue(false);
            System.out.printf("  %-45s apps %s -> %s%n", s.description(), ok, safe ? "ok" : "OUTAGE");
        }
    }

    public static void main(String[] args) {
        System.out.println("=== Challenge: Zero-Downtime Column Rename (rolling deploys run old + new together) ===");
        check("Big-bang rename:", List.of(
                new Step("ALTER TABLE ... RENAME mobile TO phone_e164", Set.of("phone_e164"), List.of("v1", "v3"))));
        check("Expand / migrate / contract:", List.of(
                new Step("1. expand: ADD COLUMN phone_e164", Set.of("mobile", "phone_e164"), List.of("v1")),
                new Step("2. deploy v2 (dual-write, read new) + backfill", Set.of("mobile", "phone_e164"), List.of("v1", "v2")),
                new Step("3. deploy v3 (new column only)", Set.of("mobile", "phone_e164"), List.of("v2", "v3")),
                new Step("4. contract: DROP COLUMN mobile", Set.of("phone_e164"), List.of("v3"))));
    }
}

    Output:

    === Challenge: Zero-Downtime Column Rename (rolling deploys run old + new together) ===
Big-bang rename:
  ALTER TABLE ... RENAME mobile TO phone_e164   apps {v1=false, v3=true} -> OUTAGE
Expand / migrate / contract:
  1. expand: ADD COLUMN phone_e164              apps {v1=true} -> ok
  2. deploy v2 (dual-write, read new) + backfill apps {v1=true, v2=true} -> ok
  3. deploy v3 (new column only)                apps {v2=true, v3=true} -> ok
  4. contract: DROP COLUMN mobile               apps {v3=true} -> ok

    Key points to say: at every step, check the schema against all versions that might be running (including the rollback target). Expand first, dual-write and backfill, switch reads, and only contract once nobody can roll back to a version that needs the old column.

    Behavioural tie-in (STAR) for experienced candidates

    • S: A rollback failed because the release had renamed a column; checkout was down 34 minutes.
    • T: Make every release reversible and reduce release risk.
    • A: Introduced Argo Rollouts canaries with error-rate and fare-amount analysis, expand/contract migration reviews, CI testing of N−1 against the new schema, and kill switches for risky features.
    • R: Deploys went from weekly to 15 per day; two bad releases in the next quarter were auto-rolled back at 1% traffic with no customer-visible incident.

    13. Quick Revision Card¶

    Remember in 30 seconds

    • Deploy ≠ release. Make every release reversible.
    • Blue-green: two environments, one switch, instant rollback.
    • Canary: 1% → 5% → 25% → 50% → 100%, compare to baseline, auto-rollback.
    • Toggles: kill switch, segments, sticky % buckets; delete when done.
    • Expand → migrate → contract so N and N−1 always coexist.
