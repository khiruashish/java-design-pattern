    Leader Election¶

    🔴 Advanced Microservices Interview frequency ⭐⭐⭐⭐

    TL;DR

    When several identical instances run but some work must be done by exactly one of them (a scheduled job, a partition owner, a coordinator), they elect a leader, usually by competing for a time-limited lease. Others stand by and take over when the lease expires. Combine it with fencing tokens so a leader that was paused or partitioned can't keep acting after it lost leadership.

    See It in Motion¶

    Press Play to watch the calls travel between components, or step through with Next and Back. Open the full explorer with all 66 patterns

    1. Intent & Problem It Solves¶

    The problem in plain English: the grocery service runs on three pods. At 02:00 a job builds the "substitution report" and emails 800 stores. If every pod runs it, stores get three emails and the database does triple work. If only pod-1 is configured to run it, the job silently stops when pod-1 is rescheduled. You need "exactly one, and always one".

    Definition (Azure Architecture Center, Leader Election pattern):

    Coordinate the actions performed by a collection of collaborating instances by electing one instance as the leader that assumes responsibility for managing the others or for doing work that must not be duplicated.

    Building blocks:

    Mechanism How Examples
    Lease A record with holder + expiry, acquired/renewed atomically Kubernetes Lease, DB row, DynamoDB conditional write, Redis SET NX PX
    Ephemeral sequential nodes Lowest sequence wins; session loss deletes the node ZooKeeper, etcd (revision-based)
    Consensus Raft/Paxos elect a leader with majority votes etcd, Consul, Kafka KRaft, CockroachDB
    Bully / ring algorithms Message-based election among known peers Classic textbook algorithms (coding challenge)

    2. Real-World Analogy¶

    The baton in a relay race

    Only the runner holding the baton may run. The baton is handed over explicitly or, if a runner collapses, the official declares the leg forfeited after a timeout and gives the next runner a new numbered baton. A runner who wakes up with an old baton number isn't allowed back on the track (fencing).

    3. Structure¶

    sequenceDiagram autonumber participant P1 as pod-1 participant P2 as pod-2 participant L as Lease store P1->>L: acquire (holder=pod-1, expires=t+15s) ✅ P2->>L: acquire ❌ (held) loop every 5s P1->>L: renew ✅ end Note over P1: crash P2->>L: acquire ❌ (until expiry) P2->>L: acquire after expiry ✅ → pod-2 is leader
    Participant Responsibility
    Candidates Identical instances that try to acquire leadership
    Coordination store Provides an atomic compare-and-set or consensus (DB, etcd, ZooKeeper, Kubernetes API)
    Lease / term Time-bounded leadership; renewed by the leader; expiry enables failover
    Fencing token Monotonic number per term, checked by downstream resources

    4. Naive Approach (Without the Pattern)¶

    @Scheduled(cron = "0 0 2 * * *")
public void substitutionReport() { ... }   // runs on EVERY replica: 3 emails per store

if (System.getenv("POD_NAME").equals("grocery-0")) { ... }   // stops forever when grocery-0 is down
    • Duplicated work (and duplicated side effects).
    • A hard-coded "leader" is a single point of failure.
    • Home-made "check then claim" races let two pods become leader.

    5. Three Real-World Examples¶

    Example 1: A Database Lease for a Nightly Job (Grocery)¶

    Scenario: Three pods of the grocery service all try to acquire the substitution-report lease every 5 seconds. The lease lasts 15 seconds and is renewed by the holder. When the leader pod is killed without releasing, another pod takes over after the lease expires, never before, so there is never more than one leader.

    Design:

    flowchart LR P1[pod-1] -->|"UPDATE ... WHERE holder = me OR expired"| T[(lease table)] P2[pod-2] --> T P3[pod-3] --> T T -->|"1 row updated = leader"| R[run report]

    Full Code:

    package com.handbook.microservices.leaderelection.lease;

import com.handbook.microservices.support.Db;

import javax.sql.DataSource;
import java.sql.Connection;
import java.sql.PreparedStatement;
import java.sql.SQLException;
import java.sql.Timestamp;
import java.time.Clock;
import java.time.Duration;

/** Leader election with a lease row: whoever holds an unexpired lease is the leader. */
public final class DbLease {

    private final DataSource ds = Db.inMemory("leases",
            "CREATE TABLE lease (name VARCHAR PRIMARY KEY, holder VARCHAR, expires_at TIMESTAMP)",
            "INSERT INTO lease VALUES ('substitution-report', NULL, TIMESTAMP '1970-01-01 00:00:00')");
    private final Clock clock;
    private final Duration ttl;

    public DbLease(Clock clock, Duration ttl) {
        this.clock = clock;
        this.ttl = ttl;
    }

    /** Acquire if free/expired, or renew if we already hold it. One atomic UPDATE: no race. */
    public boolean tryAcquireOrRenew(String pod) {
        String sql = "UPDATE lease SET holder = ?, expires_at = ? "
                + "WHERE name = 'substitution-report' AND (holder = ? OR expires_at < ?)"; // (1)!
        try (Connection c = ds.getConnection(); PreparedStatement ps = c.prepareStatement(sql)) {
            Timestamp now = Timestamp.from(clock.instant());
            ps.setString(1, pod);
            ps.setTimestamp(2, Timestamp.from(clock.instant().plus(ttl)));
            ps.setString(3, pod);
            ps.setTimestamp(4, now);
            return ps.executeUpdate() == 1; // (2)!
        } catch (SQLException e) {
            throw new IllegalStateException(e);
        }
    }
}
    1. Acquire and renew in one conditional UPDATE: it succeeds only if we already hold the lease or it has expired. The database serializes concurrent attempts.
    2. Exactly one pod sees "1 row updated". No read-then-write race.
    package com.handbook.microservices.leaderelection.lease;

import com.handbook.microservices.support.FakeClock;

import java.time.Duration;
import java.util.ArrayList;
import java.util.List;

public class LeaseDemo {

    public static void main(String[] args) {
        System.out.println("=== Grocery: One of Three Pods Runs the Substitution Report ===");
        FakeClock clock = FakeClock.at("2026-09-01T02:00:00Z");
        DbLease lease = new DbLease(clock, Duration.ofSeconds(15));
        List<String> pods = new ArrayList<>(List.of("pod-1", "pod-2", "pod-3"));

        for (int tick = 0; tick < 6; tick++) {
            if (tick == 2) {
                pods.remove("pod-1");
                System.out.println("t=" + tick * 5 + "s pod-1 is killed (no graceful release)");
            }
            List<String> leaders = new ArrayList<>();
            for (String pod : pods) {
                if (lease.tryAcquireOrRenew(pod)) {
                    leaders.add(pod);
                }
            }
            System.out.println("t=" + tick * 5 + "s leader(s): " + (leaders.isEmpty() ? "none (lease not yet expired)" : leaders));
            clock.advance(Duration.ofSeconds(5));
        }
    }
}

    Output:

    === Grocery: One of Three Pods Runs the Substitution Report ===
t=0s leader(s): [pod-1]
t=5s leader(s): [pod-1]
t=10s pod-1 is killed (no graceful release)
t=10s leader(s): none (lease not yet expired)
t=15s leader(s): none (lease not yet expired)
t=20s leader(s): none (lease not yet expired)
t=25s leader(s): [pod-2]

    Why a lease here:

    • Uses infrastructure you already have (the service's database); ShedLock does exactly this.
    • Failover is automatic, bounded by the lease TTL.
    • The gap with no leader (t=10s to t=20s) is the price of never having two.

    Example 2: Fencing Tokens for the Payout Writer (Payments)¶

    Scenario: A payout service writes settlement batches to the bank's SFTP drop folder. Writer A holds leadership, then freezes in a 40-second GC pause. Its lease expires, B becomes leader and writes batch 2. A wakes up, unaware anything happened, and tries to write batch 2 again, which would pay merchants twice. Each lease grant carries an increasing fencing token; the storage rejects writes with an older token.

    Design:

    sequenceDiagram autonumber participant A as Writer A participant Lk as Lock service participant B as Writer B participant S as Payout storage A->>Lk: acquire → token 34 A->>S: write(batch-1, 34) ✅ Note over A: GC pause 40 s, lease expires B->>Lk: acquire → token 35 B->>S: write(batch-2, 35) ✅ (highest = 35) A->>S: write(batch-2, 34) ❌ rejected: 34 < 35

    Full Code:

    package com.handbook.microservices.leaderelection.fencing;

import java.util.ArrayList;
import java.util.List;

/** The storage side of fencing: it rejects writes carrying a token older than one it has already seen. */
public final class FencedStorage {

    private long highestToken;
    private final List<String> written = new ArrayList<>();

    public synchronized boolean write(long fencingToken, String line) {
        if (fencingToken < highestToken) { // (1)!
            return false;
        }
        highestToken = fencingToken;
        written.add(line);
        return true;
    }

    public synchronized List<String> written() {
        return List.copyOf(written);
    }

    /** The lock service: every grant gets a strictly increasing token. */
    public static final class LockService {
        private long nextToken = 33;

        public synchronized long grant(String holder) { // (2)!
            return ++nextToken;
        }
    }
}
    1. The resource enforces safety: a token lower than one it has already accepted means the writer's leadership is over.
    2. Every grant gets a strictly higher token (ZooKeeper's zxid, etcd's revision, a DB sequence).
    package com.handbook.microservices.leaderelection.fencing;

import com.handbook.microservices.leaderelection.fencing.FencedStorage.LockService;

public class FencingDemo {

    public static void main(String[] args) {
        System.out.println("=== Payments: Fencing Tokens Stop a Zombie Leader ===");
        LockService locks = new LockService();
        FencedStorage payoutFile = new FencedStorage();

        long tokenA = locks.grant("payout-writer-A");
        System.out.println("A becomes leader with token " + tokenA + ", writes batch 1: " + payoutFile.write(tokenA, "batch-1 by A"));
        System.out.println("A pauses for 40s (stop-the-world GC); its lease expires");

        long tokenB = locks.grant("payout-writer-B");
        System.out.println("B becomes leader with token " + tokenB + ", writes batch 2: " + payoutFile.write(tokenB, "batch-2 by B"));

        boolean zombie = payoutFile.write(tokenA, "batch-2 by A (duplicate payouts!)");
        System.out.println("A wakes up, still thinks it's leader, writes with token " + tokenA + ": accepted=" + zombie);
        System.out.println("Payout file: " + payoutFile.written());
    }
}

    Output:

    === Payments: Fencing Tokens Stop a Zombie Leader ===
A becomes leader with token 34, writes batch 1: true
A pauses for 40s (stop-the-world GC); its lease expires
B becomes leader with token 35, writes batch 2: true
A wakes up, still thinks it's leader, writes with token 34: accepted=false
Payout file: [batch-1 by A, batch-2 by B]

    Why fencing here:

    • A lease guarantees at most one leader at a time only if every holder notices expiry instantly, and GC pauses, network partitions and clock drift break that.
    • Fencing moves the check to the place where damage happens.
    • Martin Kleppmann's critique of Redlock is exactly this: locks without fencing aren't safe for correctness.

    Example 3: Sequential Nodes Without a Herd (Logistics)¶

    Scenario: Four route-optimizer instances need one leader to assign delivery zones. With ZooKeeper, each creates an ephemeral sequential znode under /election; the lowest sequence is the leader. Instead of everyone watching the leader (and stampeding when it dies), each node watches only its predecessor, so each failure wakes exactly one node.

    Design:

    flowchart LR A["n_0 optimizer-a (LEADER)"] --- B["n_1 optimizer-b<br/>watches n_0"] --- C["n_2 optimizer-c<br/>watches n_1"] --- D["n_3 optimizer-d<br/>watches n_2"]

    Full Code:

    package com.handbook.microservices.leaderelection.sequential;

import java.util.ArrayList;
import java.util.List;
import java.util.Map;
import java.util.Optional;
import java.util.TreeMap;

/** ZooKeeper recipe: ephemeral sequential znodes; lowest sequence leads; each node watches its predecessor only. */
public final class SequentialElection {

    private final TreeMap<Integer, String> znodes = new TreeMap<>(); // seq -> member
    private int nextSeq;
    private final List<String> notifications = new ArrayList<>();

    public int join(String member) {
        int seq = nextSeq++;
        znodes.put(seq, member); // (1)!
        return seq;
    }

    /** Session ends (crash or close): its ephemeral znode disappears and only its watcher is notified. */
    public void sessionExpired(String member) {
        Integer seq = znodes.entrySet().stream().filter(e -> e.getValue().equals(member)).map(Map.Entry::getKey).findFirst().orElseThrow();
        Map.Entry<Integer, String> watcher = znodes.higherEntry(seq); // (2)!
        znodes.remove(seq);
        if (watcher != null) {
            boolean nowLeader = znodes.firstKey().equals(watcher.getKey());
            notifications.add(watcher.getValue() + " notified (predecessor " + member + " gone) -> "
                    + (nowLeader ? "now LEADER" : "watches " + znodes.lowerEntry(watcher.getKey()).getValue()));
        }
    }

    public Optional<String> leader() {
        return znodes.isEmpty() ? Optional.empty() : Optional.of(znodes.firstEntry().getValue());
    }

    public List<String> drainNotifications() {
        List<String> out = List.copyOf(notifications);
        notifications.clear();
        return out;
    }
}
    1. Ephemeral sequential znodes: the sequence orders candidates; the node disappears when the session dies.
    2. Only the next node is notified, which checks whether it's now the lowest (leader) or should watch a new predecessor.
    package com.handbook.microservices.leaderelection.sequential;

public class DispatchLeaderDemo {

    public static void main(String[] args) {
        System.out.println("=== Logistics: Electing the Route-Optimizer Leader with Sequential Nodes ===");
        SequentialElection election = new SequentialElection();
        for (String node : new String[] {"optimizer-a", "optimizer-b", "optimizer-c", "optimizer-d"}) {
            System.out.println(node + " created /election/n_" + String.format("%010d", election.join(node)));
        }
        System.out.println("Leader: " + election.leader().orElseThrow());

        election.sessionExpired("optimizer-c"); // a follower dies
        election.drainNotifications().forEach(n -> System.out.println("  " + n));
        election.sessionExpired("optimizer-a"); // the leader dies
        election.drainNotifications().forEach(n -> System.out.println("  " + n));
        System.out.println("Leader: " + election.leader().orElseThrow() + " (each death woke exactly one node: no herd effect)");
    }
}

    Output:

    === Logistics: Electing the Route-Optimizer Leader with Sequential Nodes ===
optimizer-a created /election/n_0000000000
optimizer-b created /election/n_0000000001
optimizer-c created /election/n_0000000002
optimizer-d created /election/n_0000000003
Leader: optimizer-a
  optimizer-d notified (predecessor optimizer-c gone) -> watches optimizer-b
  optimizer-b notified (predecessor optimizer-a gone) -> now LEADER
Leader: optimizer-b (each death woke exactly one node: no herd effect)

    Why sequential nodes here:

    • Leadership order is deterministic and fair (first come, first lead).
    • No herd effect: N candidates don't all hit ZooKeeper when the leader dies.
    • Session expiry gives failure detection for free.

    package com.handbook.microservices;

import com.handbook.microservices.leaderelection.fencing.FencedStorage;
import com.handbook.microservices.leaderelection.lease.DbLease;
import com.handbook.microservices.leaderelection.sequential.SequentialElection;
import com.handbook.microservices.support.FakeClock;
import org.junit.jupiter.api.Test;

import java.time.Duration;

import static org.assertj.core.api.Assertions.assertThat;

class LeaderElectionTest {

    @Test
    void onlyOneHolderUntilTheLeaseExpires() {
        FakeClock clock = FakeClock.at("2026-01-01T00:00:00Z");
        DbLease lease = new DbLease(clock, Duration.ofSeconds(10));
        assertThat(lease.tryAcquireOrRenew("a")).isTrue();
        assertThat(lease.tryAcquireOrRenew("b")).isFalse();
        clock.advance(Duration.ofSeconds(11));
        assertThat(lease.tryAcquireOrRenew("b")).isTrue();
        assertThat(lease.tryAcquireOrRenew("a")).isFalse();
    }

    @Test
    void staleTokensAreFencedOff() {
        FencedStorage s = new FencedStorage();
        assertThat(s.write(5, "x")).isTrue();
        assertThat(s.write(6, "y")).isTrue();
        assertThat(s.write(5, "z")).isFalse();
    }

    @Test
    void lowestSequenceLeadsAndSuccessionIsOrdered() {
        SequentialElection e = new SequentialElection();
        e.join("a");
        e.join("b");
        e.sessionExpired("a");
        assertThat(e.leader()).contains("b");
    }
}

    8. Pros, Cons & Trade-offs¶

    ✅ Pros ❌ Cons
    Exactly-one execution without a dedicated special instance A coordination dependency to run and secure
    Automatic failover Failover gap (up to the lease TTL) with no leader
    Simple mental model for coordinators and schedulers Leader can become a bottleneck or single point of slowness
    Works with infrastructure you have (DB, Kubernetes) Correctness needs fencing; clocks and pauses break naïve leases

    9. Pitfalls & Anti-Patterns¶

    Locks without fencing for correctness-critical work

    A paused or partitioned ex-leader can still act. If duplicates cost money, the downstream resource must check a fencing token (or the work must be idempotent).

    Check-then-claim

    if (lease.holder == null) lease.holder = me; as two operations lets two pods win. Use one atomic conditional write.

    TTL too short or too long

    Too short: GC pauses and slow renewals cause flapping leadership. Too long: slow failover. Renew at ~1/3 of the TTL and size the TTL from observed pauses.

    Leader does all the work

    If the leader also processes every request, you've built a single-node system with extra steps. Let the leader coordinate (assign work), and the followers do it.

    10. Senior / Architect Deep Dive (10–15 yrs)¶

    Time is the enemy. Leases rely on the holder noticing expiry before others act. Process pauses (GC, VM migration), clock drift and network delays violate that. Defences: renew early, stop acting when a renewal fails (not when the lease "should" expire), use monotonic clocks locally, and fence every write.

    Choose the right store. For correctness (payouts, partition ownership), use a linearizable store with revisions: etcd, ZooKeeper, a single-primary SQL database. Redis single-node SET NX PX is fine for efficiency (avoid duplicate work) but not for safety under failover.

    Prefer not needing a leader. Idempotent jobs, partitioned work (each pod owns a hash range), or a queue with competing consumers often remove the need for a global leader and its failover gap.

    War story: two payout files on a Monday

    A payout service used a Redis lock with a 30-second TTL. One Monday a full GC paused the leader for 41 seconds; the standby acquired the lock and generated the payout file; the old leader resumed and uploaded its own copy a minute later. The bank processed both: INR 2.3 crore paid twice to 600 merchants. Fix: etcd-based election with revisions as fencing tokens; the upload step writes the token into the file header and the bank-side importer rejects older tokens; payouts also got idempotency keys per merchant per date. Lesson: a lock tells you who should act; only fencing stops who shouldn't.

    12. Interview Corner¶

    Q1. What is leader election?

    Choosing one instance among many to perform a task that must not be duplicated, with automatic replacement if it fails.

    Q2. How do you run a @Scheduled job only once across replicas?

    ShedLock (a lock row in the DB) or Kubernetes CronJob, or leader election.

    Q3. What is a lease?

    Leadership that expires unless renewed, so a crashed leader is replaced automatically.

    Q4. What happens if the leader crashes?

    After its lease expires, another instance acquires it and becomes leader.

    Q5. Name tools that provide leader election.

    ZooKeeper, etcd, Consul, the Kubernetes Lease API, databases.

    Q1. Why must acquisition be atomic?

    Otherwise two instances can both see "free" and both claim it.

    Q2. What's a fencing token?

    A monotonically increasing number issued with each leadership grant; resources reject requests with older tokens.

    Q3. How do you choose the lease TTL?

    Longer than worst-case pauses + renewal latency; short enough for acceptable failover time; renew at about a third of the TTL.

    Q4. What's the herd effect in ZooKeeper elections?

    All candidates watching the leader node and stampeding when it disappears; avoided by watching the predecessor.

    Q5. Is Redis SET NX PX safe for leader election?

    For efficiency, yes; for correctness, not without fencing, especially across failover.

    Q1. "Design partition ownership for 1,000 partitions across 20 workers."

    A coordinator (elected via etcd) assigns partitions; workers hold per-partition leases with revisions as fencing tokens; reassign on lease loss; writes carry the token.

    Q2. "Explain split brain and how to prevent it."

    Two nodes both believe they lead (partition, pauses). Prevent with majority quorums (Raft), leases with fencing, and stepping down on failed renewal.

    Q3. "How does Raft elect a leader?"

    Followers time out, become candidates for a new term, request votes; a majority makes a leader; terms act as fencing; randomized timeouts avoid split votes.

    Q4. "Leader election vs designing it away?"

    Prefer idempotent or partitioned work to avoid the failover gap and bottleneck; use election for true coordinators.

    Q5. "The leader is slow but alive. What happens?"

    Nothing, by default: a gray failure. Add health-based step-down (leader resigns if its own checks fail) and monitor leader-specific SLIs.

    Problem: Implement the Bully algorithm: node 5 (the coordinator) crashed; node 2 notices and starts an election among nodes 1–5. Print the messages and the winner.

    Solution 
    package com.handbook.microservices.leaderelection.bully;

import java.util.ArrayList;
import java.util.List;
import java.util.Set;
import java.util.TreeSet;

/** Coding challenge: the Bully algorithm. The highest-id live node always wins. */
public class BullyDemo {

    static final Set<Integer> ALIVE = new TreeSet<>();
    static final List<String> LOG = new ArrayList<>();

    static int elect(int starter, Set<Integer> all) {
        List<Integer> higher = all.stream().filter(id -> id > starter).toList();
        LOG.add("node " + starter + " sends ELECTION to " + higher);
        List<Integer> answered = higher.stream().filter(ALIVE::contains).toList();
        if (answered.isEmpty()) {
            LOG.add("no answer: node " + starter + " broadcasts COORDINATOR");
            return starter;
        }
        LOG.add("OK from " + answered + "; node " + starter + " backs off");
        return elect(answered.get(0), all); // the lowest higher live node continues the election
    }

    public static void main(String[] args) {
        System.out.println("=== Challenge: Bully Election Among 5 Inventory Nodes ===");
        Set<Integer> all = Set.of(1, 2, 3, 4, 5);
        ALIVE.addAll(all);
        ALIVE.remove(5); // the old coordinator crashed
        int leader = elect(2, new TreeSet<>(all)); // node 2 noticed the missing heartbeat
        LOG.forEach(l -> System.out.println("  " + l));
        System.out.println("New coordinator: node " + leader);
    }
}

    Output:

    === Challenge: Bully Election Among 5 Inventory Nodes ===
  node 2 sends ELECTION to [3, 4, 5]
  OK from [3, 4]; node 2 backs off
  node 3 sends ELECTION to [4, 5]
  OK from [4]; node 3 backs off
  node 4 sends ELECTION to [5]
  no answer: node 4 broadcasts COORDINATOR
New coordinator: node 4

    Key points to say: a node sends ELECTION to all higher ids; any live higher node answers OK and takes over; a node with no higher live nodes declares itself COORDINATOR. It's O(n²) messages in the worst case and assumes reliable failure detection, which is why production systems use Raft or a coordination service instead.

    • S: A GC pause let two payout writers both upload a payout file; 600 merchants were paid twice.
    • T: Guarantee one payout file per day even under pauses and failovers.
    • A: Moved election to etcd, used revisions as fencing tokens embedded in the file header, had the importer reject stale tokens, and added idempotency keys per merchant per date.
    • R: No duplicate payouts since; failover time dropped from 60 s to 15 s with safe TTLs.

    13. Quick Revision Card¶

    Remember in 30 seconds

    • One instance leads; others stand by; lease expiry = failover.
    • Acquire/renew with one atomic conditional write.
    • Leases alone aren't safe: add fencing tokens.
    • Watch predecessors, not the leader (no herd).
    • Often better: idempotent or partitioned work, no leader at all.
    UPDATE lease SET holder = :me, expires_at = :now + ttl WHERE name = :job AND (holder = :me OR expires_at < :now);
