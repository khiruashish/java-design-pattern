    Intermediate Microservices Observability

    Distributed Tracing¶

    🟡 Intermediate Microservices Interview frequency ⭐⭐⭐⭐

    TL;DR

    Give each request a trace ID at the edge, propagate it (with the current span ID) to every service it touches via headers such as W3C traceparent, and record a span per unit of work. A tracing backend assembles the spans into a tree showing where the time went and where it failed. Logs tell you what happened in one service; traces tell you where in the call chain it happened.

    1. Intent & Problem It Solves¶

    The problem in plain English: checkout takes 1.5 s sometimes. The request touches the gateway, order, inventory, payment and an external bank. Each service's logs say "OK" and its average latency looks fine. Which hop is slow, for this request? Without a shared ID, correlating logs across five services by timestamp is guesswork.

    Definition (OpenTelemetry):

    Traces give us the big picture of what happens when a request is made to an application. A trace is made of one or more spans; each span represents a unit of work.

    Concept Meaning
    Trace The whole journey of one request (one trace ID)
    Span One operation: name, start, duration, attributes, status, parent span ID
    Context propagation Passing trace ID + parent span ID across process boundaries (HTTP headers, message headers)
    traceparent W3C header: 00-<trace-id 32 hex>-<parent-id 16 hex>-<flags>
    Sampling Recording only a share of traces to control cost

    2. Real-World Analogy¶

    A parcel's tracking number

    The parcel gets one tracking number at pickup. Every hub scans it on arrival and departure, so you can see it spent 14 hours stuck at the Pune sort centre. The tracking number is the trace ID; each scan pair is a span.

    3. Structure¶

    flowchart LR
    C[Client] --> G[Gateway<br/>starts trace]
    G -->|traceparent| O[Order svc]
    O -->|traceparent| I[Inventory svc]
    O -->|traceparent| P[Payment svc]
    P -->|traceparent| K[[Kafka<br/>headers]] --> B[Billing svc]
    G & O & I & P & B -.->|spans via OTLP| COL[Collector] --> BE[(Jaeger / Tempo / Zipkin)]
    Participant Responsibility
    Instrumentation (OTel agent, Micrometer) Creates spans for HTTP, DB, messaging; injects/extracts headers
    Propagator Serializes context into headers (W3C, B3)
    Collector Receives, batches, samples and exports spans
    Backend Stores and visualizes traces; links to logs and metrics

    4. Naive Approach (Without the Pattern)¶

    order-service    19:00:00.112 INFO placing order ORD-1
payment-service  19:00:00.140 INFO charging...
payment-service  19:00:01.561 INFO charged
(800 other requests logged in the same second; which "charging..." belongs to ORD-1?)

    5. Three Real-World Examples¶

    All examples use a small tracer and the W3C header format:

    package com.handbook.microservices.tracing.core;

import java.util.Random;

/**
 * The W3C Trace Context carried between services in the {@code traceparent} header:
 * {@code 00-<32 hex trace-id>-<16 hex parent span-id>-<flags>} (flags 01 = sampled).
 */
public record TraceContext(String traceId, String spanId, boolean sampled) {

    public static TraceContext parse(String traceparent) {
        String[] parts = traceparent.split("-"); // (1)!
        if (parts.length != 4 || !parts[0].equals("00") || parts[1].length() != 32 || parts[2].length() != 16) {
            throw new IllegalArgumentException("bad traceparent: " + traceparent);
        }
        return new TraceContext(parts[1], parts[2], parts[3].equals("01"));
    }

    public String toTraceparent() {
        return "00-" + traceId + "-" + spanId + "-" + (sampled ? "01" : "00");
    }

    public static TraceContext newRoot(Random ids) {
        return new TraceContext(hex(ids, 16), hex(ids, 8), true);
    }

    public TraceContext newChild(Random ids) { // (2)!
        return new TraceContext(traceId, hex(ids, 8), sampled);
    }

    static String hex(Random ids, int bytes) {
        StringBuilder sb = new StringBuilder();
        for (int i = 0; i < bytes; i++) {
            sb.append(String.format("%02x", ids.nextInt(256)));
        }
        return sb.toString();
    }
}
    1. Strict parsing: a malformed header should start a new trace rather than corrupt one.
    2. A child keeps the trace ID and gets a new span ID; the old span ID becomes its parent.
    package com.handbook.microservices.tracing.core;

import java.time.Clock;
import java.util.ArrayList;
import java.util.Comparator;
import java.util.List;
import java.util.Random;
import java.util.function.Function;
import java.util.function.Supplier;

/** A tiny tracer: creates spans, records them when they end, and prints a trace as a tree. */
public final class Tracer {

    public record Span(String traceId, String spanId, String parentId, String service, String name,
                       long startMillis, long endMillis) {
        long duration() {
            return endMillis - startMillis;
        }
    }

    private final Clock clock;
    private final Random ids;
    private final List<Span> finished = new ArrayList<>(); // what a collector (Jaeger, Tempo) receives

    public Tracer(Clock clock, Random ids) {
        this.clock = clock;
        this.ids = ids;
    }

    /** Runs work inside a new span. {@code parent} may be null to start a new trace. */
    public <T> T inSpan(TraceContext parent, String service, String name,
                        Function<TraceContext, T> work) {
        TraceContext ctx = parent == null ? TraceContext.newRoot(ids) : parent.newChild(ids);
        long start = clock.millis();
        try {
            return work.apply(ctx);
        } finally {
            synchronized (finished) {
                finished.add(new Span(ctx.traceId(), ctx.spanId(), parent == null ? null : parent.spanId(),
                        service, name, start, clock.millis()));
            }
        }
    }

    public <T> T inSpan(TraceContext parent, String service, String name, Supplier<T> work) {
        return inSpan(parent, service, name, ctx -> work.get());
    }

    public List<Span> spans() {
        synchronized (finished) {
            return List.copyOf(finished);
        }
    }

    public void printTree(String traceId) {
        List<Span> trace = spans().stream().filter(s -> s.traceId().equals(traceId)).toList();
        long t0 = trace.stream().mapToLong(Span::startMillis).min().orElse(0);
        long t1 = trace.stream().mapToLong(Span::endMillis).max().orElse(t0);
        double msPerChar = Math.max(1, (t1 - t0) / 40.0); // the whole trace fits in 40 characters
        trace.stream().filter(s -> s.parentId() == null).forEach(root -> print(root, trace, t0, msPerChar, 0));
    }

    private void print(Span span, List<Span> trace, long t0, double msPerChar, int depth) {
        int offset = (int) ((span.startMillis() - t0) / msPerChar);
        int width = (int) Math.max(1, Math.round(span.duration() / msPerChar));
        System.out.printf("  %-50s %5d ms |%s%n", "  ".repeat(depth) + span.service() + ": " + span.name(),
                span.duration(), " ".repeat(offset) + "#".repeat(width));
        trace.stream().filter(s -> span.spanId().equals(s.parentId()))
                .sorted(Comparator.comparingLong(Span::startMillis))
                .forEach(child -> print(child, trace, t0, msPerChar, depth + 1));
    }
}

    Example 1: Finding the Slow Hop in Checkout (Grocery)¶

    Scenario: One checkout request crosses the gateway, order, inventory and payment services. Each service parses the incoming traceparent, creates a child span and passes its own span ID downstream. The trace tree (with a timeline bar per span) makes the answer obvious: 1.4 s of the 1.5 s is the bank authorization call inside payment-service.

    Full Code:

    package com.handbook.microservices.tracing.grocery;

import com.handbook.microservices.support.FakeClock;
import com.handbook.microservices.support.Http.Request;
import com.handbook.microservices.tracing.core.TraceContext;
import com.handbook.microservices.tracing.core.Tracer;

import java.util.Map;
import java.util.Random;

/**
 * One checkout request crosses four services. Each service reads the incoming traceparent header,
 * creates a child span, and passes its own span ID downstream. The collector stitches the tree.
 */
public class CheckoutTraceDemo {

    static FakeClock clock = FakeClock.at("2026-10-13T19:00:00Z");
    static Tracer tracer = new Tracer(clock, new Random(7));

    public static void main(String[] args) {
        System.out.println("=== Grocery: tracing one slow checkout across services ===");
        Request incoming = Request.get("/checkout", Map.of()); // no traceparent: the gateway starts the trace
        String traceId = tracer.inSpan(null, "api-gateway", "POST /checkout", gw -> {
            clock.advanceMillis(5);
            orderService(incoming.withHeader("traceparent", gw.toTraceparent())); // (1)!
            clock.advanceMillis(3);
            return gw.traceId();
        });
        System.out.println("trace-id " + traceId);
        tracer.printTree(traceId);
        System.out.println("The tree shows where the time went: payment-service waiting on the bank.");
    }

    static void orderService(Request req) {
        TraceContext parent = TraceContext.parse(req.header("traceparent")); // (2)!
        tracer.inSpan(parent, "order-service", "placeOrder", ctx -> {
            clock.advanceMillis(10);
            tracer.inSpan(ctx, "inventory-service", "reserve", () -> {
                clock.advanceMillis(40);
                return null;
            });
            paymentService(req.withHeader("traceparent", ctx.toTraceparent()));
            clock.advanceMillis(15);
            return null;
        });
    }

    static void paymentService(Request req) {
        TraceContext parent = TraceContext.parse(req.header("traceparent"));
        tracer.inSpan(parent, "payment-service", "charge", ctx -> {
            clock.advanceMillis(20);
            tracer.inSpan(ctx, "payment-service", "HTTP POST bank /authorize", () -> {
                clock.advanceMillis(1_400); // the slow external call
                return null;
            });
            return null;
        });
    }
}
    1. Inject: the gateway sends its context downstream in the traceparent header.
    2. Extract: each service continues the trace from the incoming header.

    Output:

    === Grocery: tracing one slow checkout across services ===
trace-id bba3bf02597de5beb5915af31e40d9b2
  api-gateway: POST /checkout                         1493 ms |########################################
    order-service: placeOrder                         1485 ms |########################################
      inventory-service: reserve                        40 ms |#
      payment-service: charge                         1420 ms | ######################################
        payment-service: HTTP POST bank /authorize    1400 ms |  ######################################
The tree shows where the time went: payment-service waiting on the bank.

    Why tracing here:

    • Latency is attributed to a specific hop for a specific request.
    • The tree also shows structure: inventory and payment run sequentially, so parallelizing them is a possible optimization.

    Example 2: Across Kafka (Ride-hailing)¶

    Scenario: Completing a trip publishes TripCompleted; billing consumes it 2 seconds later on another machine. The producer puts traceparent into the message headers; the consumer extracts it and continues the same trace, so the invoice insert appears under the original HTTP request.

    Full Code:

    package com.handbook.microservices.tracing.async;

import com.handbook.microservices.support.FakeClock;
import com.handbook.microservices.tracing.core.TraceContext;
import com.handbook.microservices.tracing.core.Tracer;

import java.util.ArrayDeque;
import java.util.Map;
import java.util.Queue;
import java.util.Random;

/**
 * Traces cross asynchronous boundaries too: the producer puts traceparent into the message headers,
 * and the consumer, possibly seconds later on another machine, continues the same trace.
 */
public class KafkaTracePropagationDemo {

    record Message(String topic, Map<String, String> headers, String payload) {
    }

    public static void main(String[] args) {
        FakeClock clock = FakeClock.at("2026-10-13T22:00:00Z");
        Tracer tracer = new Tracer(clock, new Random(11));
        Queue<Message> topic = new ArrayDeque<>();

        System.out.println("=== Ride-hailing: trip completion -> async billing, one trace ===");
        String traceId = tracer.inSpan(null, "trip-service", "POST /trips/TRIP-5/complete", ctx -> {
            clock.advanceMillis(25);
            tracer.inSpan(ctx, "trip-service", "kafka send trips.completed", producer -> {
                topic.add(new Message("trips.completed",
                        Map.of("traceparent", producer.toTraceparent()), "TripCompleted TRIP-5")); // (1)!
                clock.advanceMillis(4);
                return null;
            });
            return ctx.traceId();
        });

        clock.advanceMillis(2_000); // consumer lag
        Message m = topic.poll();
        TraceContext fromHeaders = TraceContext.parse(m.headers().get("traceparent")); // (2)!
        tracer.inSpan(fromHeaders, "billing-service", "kafka receive " + m.topic(), consumer -> {
            clock.advanceMillis(30);
            tracer.inSpan(consumer, "billing-service", "INSERT invoice", () -> {
                clock.advanceMillis(12);
                return null;
            });
            return null;
        });

        System.out.println("message headers: " + m.headers());
        tracer.printTree(traceId);
        System.out.println("billing-service joined trace " + traceId.substring(0, 8) + "... 2 s after the HTTP request ended.");
    }
}
    1. Message headers carry the context just like HTTP headers do.
    2. The consumer extracts it; OpenTelemetry may model this as a child or as a span link for batch consumers.

    Output:

    === Ride-hailing: trip completion -> async billing, one trace ===
message headers: {traceparent=00-bab66d36a16606e830490b8d6f70abfb-2d5a670a88b89bb4-01}
  trip-service: POST /trips/TRIP-5/complete             29 ms |#
    trip-service: kafka send trips.completed             4 ms |#
      billing-service: kafka receive trips.completed    42 ms |                                       #
        billing-service: INSERT invoice                 12 ms |                                       #
billing-service joined trace bab66d36... 2 s after the HTTP request ended.

    Why propagate through messages:

    • Async flows (sagas, outbox relays) are where "where did it get stuck?" is hardest to answer.
    • Consumer lag becomes visible as a gap in the trace.

    Example 3: Keeping Context Across Threads (Streaming)¶

    Scenario: The home-screen service fetches three rows in parallel. The current trace lives in a ThreadLocal, so work on a plain executor loses it, and those spans become orphan traces. A context-propagating executor captures the context at submit time and restores it in the worker.

    Full Code:

    package com.handbook.microservices.tracing.threads;

import com.handbook.microservices.tracing.core.TraceContext;

import java.util.concurrent.Executor;

/**
 * The current trace context usually lives in a ThreadLocal. Work submitted to another thread loses
 * it unless the executor captures the context at submit time and restores it in the worker.
 */
public final class ContextPropagatingExecutor implements Executor {

    public static final ThreadLocal<TraceContext> CURRENT = new ThreadLocal<>();

    private final Executor delegate;

    public ContextPropagatingExecutor(Executor delegate) {
        this.delegate = delegate;
    }

    @Override
    public void execute(Runnable task) {
        TraceContext captured = CURRENT.get(); // (1)!
        delegate.execute(() -> {
            TraceContext previous = CURRENT.get();
            CURRENT.set(captured); // (2)!
            try {
                task.run();
            } finally {
                CURRENT.set(previous); // (3)!
            }
        });
    }
}
    1. Capture on the submitting thread.
    2. Restore on the worker thread for the task's duration.
    3. Always restore the previous value. Pooled threads are reused, and leaking context into the next task corrupts traces.
    package com.handbook.microservices.tracing.threads;

import com.handbook.microservices.tracing.core.TraceContext;

import java.util.List;
import java.util.Random;
import java.util.concurrent.CompletableFuture;
import java.util.concurrent.Executor;
import java.util.concurrent.Executors;

public class ThreadContextDemo {

    public static void main(String[] args) {
        TraceContext request = TraceContext.newRoot(new Random(3));
        ContextPropagatingExecutor.CURRENT.set(request);

        try (var pool = Executors.newVirtualThreadPerTaskExecutor()) {
            System.out.println("=== Streaming: parallel home-screen fetches keep the trace ===");
            System.out.println("request thread trace: " + request.traceId().substring(0, 8) + "...");
            System.out.println("plain executor      : " + fetchAll(pool));
            System.out.println("propagating executor: " + fetchAll(new ContextPropagatingExecutor(pool)));
        } finally {
            ContextPropagatingExecutor.CURRENT.remove();
        }
    }

    private static List<String> fetchAll(Executor executor) {
        List<CompletableFuture<String>> rows = List.of("continue-watching", "trending", "for-you").stream()
                .map(row -> CompletableFuture.supplyAsync(() -> {
                    TraceContext ctx = ContextPropagatingExecutor.CURRENT.get();
                    return row + "=" + (ctx == null ? "NO TRACE" : ctx.traceId().substring(0, 8));
                }, executor))
                .toList();
        return rows.stream().map(CompletableFuture::join).toList();
    }
}

    Output:

    === Streaming: parallel home-screen fetches keep the trace ===
request thread trace: bb8f12ce...
plain executor      : [continue-watching=NO TRACE, trending=NO TRACE, for-you=NO TRACE]
propagating executor: [continue-watching=bb8f12ce, trending=bb8f12ce, for-you=bb8f12ce]

    Why this matters:

    • Async code (CompletableFuture, @Async, reactive) is the most common place traces break.
    • OpenTelemetry's Context.taskWrapping(executor) and Micrometer's ContextExecutorService do exactly this.
    Unit Tests: DistributedTracingTest.java 
    package com.handbook.microservices;

import com.handbook.microservices.tracing.core.TraceContext;
import com.handbook.microservices.tracing.sampling.RatioSampler;
import org.junit.jupiter.api.Test;

import java.util.Random;

import static org.assertj.core.api.Assertions.assertThat;
import static org.assertj.core.api.Assertions.assertThatThrownBy;

class DistributedTracingTest {

    @Test
    void traceparentRoundTripsAndChildKeepsTraceId() {
        TraceContext root = TraceContext.newRoot(new Random(1));
        TraceContext parsed = TraceContext.parse(root.toTraceparent());
        assertThat(parsed).isEqualTo(root);
        TraceContext child = parsed.newChild(new Random(2));
        assertThat(child.traceId()).isEqualTo(root.traceId());
        assertThat(child.spanId()).isNotEqualTo(root.spanId());
    }

    @Test
    void rejectsMalformedHeaders() {
        assertThatThrownBy(() -> TraceContext.parse("00-abc-def-01")).isInstanceOf(IllegalArgumentException.class);
    }

    @Test
    void samplingIsDeterministicPerTraceId() {
        RatioSampler sampler = new RatioSampler(0.5);
        String traceId = TraceContext.newRoot(new Random(9)).traceId();
        assertThat(sampler.shouldSampleRoot(traceId)).isEqualTo(sampler.shouldSampleRoot(traceId));
    }
}

    6. Variations & Modern Java Take¶

    Spring Boot 3 with Micrometer Tracing (compiled in the spring-reference module):

    package com.handbook.springref.tracing;

import io.micrometer.observation.Observation;
import io.micrometer.observation.ObservationRegistry;
import org.springframework.stereotype.Service;
import org.springframework.web.client.RestClient;

/**
 * With micrometer-tracing-bridge-otel on the classpath, Spring Boot instruments incoming HTTP
 * requests and the auto-configured RestClient.Builder, so traceparent is propagated for free.
 * Custom spans for business steps use the Observation API.
 */
@Service
public class TracedCheckoutService {

    private final RestClient payments;
    private final ObservationRegistry observations;

    public TracedCheckoutService(RestClient.Builder builder, ObservationRegistry observations) {
        this.payments = builder.baseUrl("http://payment-service").build(); // builder carries tracing
        this.observations = observations;
    }

    public String checkout(String orderId) {
        long total = Observation.createNotStarted("checkout.price-cart", observations)
                .lowCardinalityKeyValue("channel", "app") // becomes a span tag and a metric dimension
                .observe(() -> priceCart(orderId));
        return payments.post().uri("/charges/{id}", orderId)
                .body(total)
                .retrieve()
                .body(String.class); // child span + traceparent header added automatically
    }

    private long priceCart(String orderId) {
        return 79_800;
    }
}

management:
  tracing:
    sampling.probability: 0.1          # 10% head sampling
  otlp:
    tracing.endpoint: http://otel-collector:4318/v1/traces
logging.pattern.level: "%5p [${spring.application.name},%X{traceId:-},%X{spanId:-}]"  # IDs in every log line

    OpenTelemetry Java agent Zero-code instrumentation (-javaagent:opentelemetry-javaagent.jar) for HTTP, JDBC, Kafka and more
    Micrometer Tracing (Spring Boot 3) Observation API; bridges to OTel or Brave
    Head sampling Decide at the root (cheap; may miss rare errors)
    Tail sampling The collector decides after seeing the whole trace (keep errors and slow traces)
    Exemplars Link a metric spike to example trace IDs

    7. Where It Lives in Real Frameworks¶

    Where Tracing
    OpenTelemetry The standard API/SDK, OTLP protocol and collector
    Jaeger, Grafana Tempo, Zipkin Open-source backends
    Spring Boot 3 Micrometer Tracing + ObservationRegistry auto-instrumentation
    Service meshes Proxies emit spans per hop (apps still forward headers)
    W3C Trace Context traceparent/tracestate header standard

    8. Pros, Cons & Trade-offs¶

    ✅ Pros ❌ Cons
    Pinpoints slow or failing hops per request Instrumentation gaps break traces
    Shows real dependency graphs Storage cost; requires sampling at scale
    Correlates logs, metrics and traces by ID Context propagation across async code needs care
    Standardized (W3C, OTel) Sensitive data can leak into span attributes

    9. Pitfalls & Anti-Patterns¶

    Broken propagation

    One service that doesn't forward traceparent (a hand-built HTTP client, a thread pool, a message without headers) splits every trace in two. Test propagation end to end.

    High-cardinality or sensitive attributes

    Putting card numbers, emails or full request bodies into span attributes leaks PII into the tracing backend. Use allow-lists for attributes.

    Sampling inconsistently

    If each service samples independently at 10%, only 1% of traces are complete. Use parent-based sampling (see the coding challenge).

    Tracing without logs correlation

    Put trace and span IDs in every log line (MDC), so you can jump from a trace to the exact logs.

    10. Senior / Architect Deep Dive (10–15 yrs)¶

    Three pillars, one ID. Metrics tell you that something is wrong (error rate up), traces tell you where (which hop), logs tell you why (the exception). Wire them together: exemplars on metrics, trace IDs in logs, and service graphs from traces.

    Sampling strategy. Head sampling at 1–10% for volume; tail sampling in the collector to always keep errors and slow traces; higher rates for low-traffic critical paths. Budget storage per day.

    Baggage. W3C Baggage can carry business context (tenant ID, experiment) across services. It's sent on every hop and visible to every service, so keep it small and non-sensitive.

    Production checklist¶

    • OpenTelemetry agent or Micrometer Tracing in every service; W3C propagation everywhere (HTTP, gRPC, Kafka).
    • Context propagation through executors, @Async, reactive and virtual threads verified.
    • Trace/span IDs in logs (MDC); exemplars on latency metrics.
    • Parent-based head sampling + tail sampling for errors/slow requests.
    • Attribute allow-list; no PII in spans.
    • Collector deployed with batching and back-pressure; backend retention set.

    Explain it in 2 minutes (system design round)¶

    "Every service runs the OpenTelemetry agent. The gateway starts a trace and propagates W3C traceparent over HTTP, gRPC and Kafka headers, so a checkout produces one trace across all services and async consumers. Spans go via OTLP to a collector that does tail sampling (keep all errors and requests over 1 s, plus 5% of the rest) and exports to Tempo. Trace IDs are in every log line and metrics have exemplars, so from a latency spike we can click straight to a slow trace and then to its logs."

    War story: the trace that ended at the thread pool

    A payments team adopted tracing, but traces for refunds always stopped at refund-service. The refund flow used a custom ExecutorService for parallel ledger updates; the context stayed on the request thread. For months, slow refunds were blamed on the ledger database, which looked fine. Fix: wrapped the executor with context propagation; the now-complete traces showed the real culprit: a synchronous call to a fraud-scoring API inside the parallel tasks, with no timeout. Lesson: a trace that stops early hides the actual problem. Verify propagation across every async boundary.

    12. Interview Corner¶

    Q1. What is distributed tracing?

    Following a single request across multiple services using a shared trace ID, recording a span for each operation.

    Q2. What is a span?

    A timed unit of work (e.g. an HTTP call or DB query) with a name, start time, duration, attributes and a parent span.

    Q3. How is the trace ID passed between services?

    In headers, typically the W3C traceparent header (or older B3 headers).

    Q4. Name some tracing tools.

    OpenTelemetry (standard), Jaeger, Zipkin, Grafana Tempo; Spring Boot uses Micrometer Tracing.

    Q5. Trace ID vs. correlation ID?

    A correlation ID only groups logs; a trace ID plus span IDs builds a timed tree of operations.

    Q1. Explain the traceparent header.

    version-traceid-parentid-flags: 00, a 32-hex trace ID, the 16-hex span ID of the caller, and flags (01 = sampled).

    Q2. How do traces cross Kafka?

    The producer injects context into message headers; the consumer extracts it and creates a child span or a span link.

    Q3. Why do traces break in async code?

    Context is stored in thread-locals; work on other threads loses it unless executors propagate it.

    Q4. What is sampling and why is it needed?

    Recording only a fraction of traces to control overhead and storage; head-based (at the start) or tail-based (after completion).

    Q5. How do you connect logs to traces?

    Put trace/span IDs into the logging MDC and log pattern; backends link from a trace to its logs.

    Q1. "Design observability for 300 microservices."

    OTel everywhere (agents + SDK for custom spans), W3C propagation, collectors per cluster with tail sampling, a trace backend with 7–14 days retention, metrics with exemplars, structured logs with trace IDs, service maps and SLOs per service.

    Q2. "Head vs. tail sampling trade-offs?"

    Head: cheap and simple, but may drop the rare error traces. Tail: keeps interesting traces, but the collector must buffer whole traces (memory, routing by trace ID).

    Q3. "How do you measure the overhead of tracing?"

    Load-test with and without instrumentation; watch CPU, allocation and p99; tune sampling, batch export and attribute counts.

    Q4. "A trace shows a gap of 300 ms between two spans. What could it be?"

    Uninstrumented work (local computation, a library call), queueing in a thread pool or connection pool, GC pauses, network/proxy time, or consumer lag for async hops.

    Q5. "How would you trace a request through a legacy system that can't be instrumented?"

    Use a sidecar or proxy to create spans around it, or log the incoming trace ID and correlate; propagate the trace ID through its message fields if possible.

    Problem: Sample about 10% of traces, but every service must make the same decision for a given trace, so sampled traces are complete. Downstream services should honour the caller's decision.

    Solution 
    package com.handbook.microservices.tracing.sampling;

import com.handbook.microservices.tracing.core.TraceContext;

/**
 * Coding challenge: keep ~10% of traces, and make every service agree on WHICH traces, so sampled
 * traces are complete. The root decides from the trace ID; downstream services honour the sampled
 * flag in traceparent (OpenTelemetry's ParentBased(TraceIdRatioBased) sampler).
 */
public final class RatioSampler {

    private final long threshold;

    public RatioSampler(double ratio) {
        this.threshold = (long) (ratio * Long.MAX_VALUE);
    }

    /** Root decision: a deterministic function of the trace ID (its last 16 hex chars). */
    public boolean shouldSampleRoot(String traceId) {
        long lower = Long.parseUnsignedLong(traceId.substring(16), 16) >>> 1; // non-negative 63 bits
        return lower < threshold;
    }

    /** Downstream decision: follow the parent. */
    public boolean shouldSample(TraceContext parent) {
        return parent.sampled();
    }
}

    package com.handbook.microservices.tracing.sampling;

import com.handbook.microservices.tracing.core.TraceContext;

import java.util.Random;

public class SamplingDemo {

    public static void main(String[] args) {
        RatioSampler sampler = new RatioSampler(0.10);
        Random ids = new Random(2026);
        int sampled = 0;
        int disagreements = 0;
        for (int i = 0; i < 10_000; i++) {
            TraceContext root = TraceContext.newRoot(ids);
            boolean rootDecision = sampler.shouldSampleRoot(root.traceId());
            sampled += rootDecision ? 1 : 0;
            TraceContext sent = new TraceContext(root.traceId(), root.spanId(), rootDecision);
            boolean downstream = sampler.shouldSample(TraceContext.parse(sent.toTraceparent()));
            boolean recomputed = sampler.shouldSampleRoot(root.traceId()); // another service, same rule
            if (downstream != rootDecision || recomputed != rootDecision) {
                disagreements++;
            }
        }
        System.out.println("=== Challenge: consistent 10% trace sampling ===");
        System.out.println("traces sampled: " + sampled + " of 10,000");
        System.out.println("services disagreeing on a trace: " + disagreements + " (every sampled trace is complete)");
    }
}

    Output:

    === Challenge: consistent 10% trace sampling ===
traces sampled: 994 of 10,000
services disagreeing on a trace: 0 (every sampled trace is complete)

    Key points to say: the decision is a pure function of the trace ID (random bits), so any service computes the same answer; downstream services just follow the sampled flag (parent-based). This mirrors OpenTelemetry's ParentBased(TraceIdRatioBased(0.1)).

    Behavioural tie-in (STAR) for experienced candidates

    • S: Our p99 checkout latency doubled after a release, and each team's dashboard showed their service as healthy.
    • T: Find the cause within the incident window.
    • A: We had just rolled out OpenTelemetry; filtering traces over 2 s showed every slow trace contained a new synchronous call from pricing to a promotions service with no cache.
