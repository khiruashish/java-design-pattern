    Advanced Data Microservices

    Sharding¶

    🔴 Advanced Microservices Interview frequency ⭐⭐⭐⭐⭐

    TL;DR

    Sharding splits one large dataset across several databases (shards) by a shard key, so each shard holds only part of the data and takes only part of the load. Use it when a single database can't keep up with writes or storage even after indexing, caching, read replicas and vertical scaling. Choose the shard key from your main access path, because everything else becomes harder.

    See It in Motion¶

    Press Play to watch the calls travel between components, or step through with Next and Back. Open the full explorer with all 66 patterns

    1. Intent & Problem It Solves¶

    The problem in plain English: a payments ledger grows by 20 million rows a day. One PostgreSQL primary handles reads with replicas, but writes all go to one machine; it's at 85% CPU, vacuum can't keep up, and the next bigger instance doesn't exist. You need more than one primary.

    Definition (Azure Architecture Center, Sharding pattern):

    Divide a data store into a set of horizontal partitions or shards. Each shard has the same schema but holds its own distinct subset of the data, and runs on its own server.

    Three ways to pick a shard:

    Strategy How Good at Bad at
    Hash hash(key) % N or consistent hashing Even spread of writes Range queries; resharding with % N moves most keys
    Range Key ranges (A–F, dates) per shard Range scans Hot spots on sequential keys
    Directory / lookup A table maps key (tenant, city) → shard Moving or splitting individual tenants Directory is a dependency to cache and protect

    Sharding vs partitioning vs replication: partitioning splits a table within one database (PostgreSQL declarative partitions); sharding puts partitions on different servers; replication copies the same data for availability and read scaling. Real systems combine all three.

    2. Real-World Analogy¶

    Exam halls by roll number

    A university with 30,000 students doesn't seat everyone in one hall. Roll numbers 1–5,000 go to Hall A, 5,001–10,000 to Hall B (range sharding). To find a student you only check one hall. A question like "who scored highest across all halls" needs every hall's results combined (scatter-gather).

    3. Structure¶

    flowchart LR C[Service] --> R{"Shard router<br/>shard = f(shard key)"} R --> S0[(Shard 0<br/>primary + replica)] R --> S1[(Shard 1<br/>primary + replica)] R --> S2[(Shard 2<br/>primary + replica)] D[(Directory / config)] -.-> R
    Participant Responsibility
    Shard key The field that decides placement (account id, customer id, tenant id, city)
    Router Maps a key to a shard: in the app, a library (Vitess, Citus, ShardingSphere) or the database itself
    Shards Independent databases with the same schema, each usually replicated
    Directory (optional) Lookup table for directory-based schemes; cached aggressively
    Scatter-gather layer Runs queries without the shard key on all shards and merges results

    4. Naive Approach (Without the Pattern)¶

    Bigger instance → bigger instance → largest instance (still 85% CPU)
Add read replicas → reads fine, writes still on one primary
Archive old rows → buys months, not years
    • Vertical scaling has a hard ceiling and a steep price curve.
    • Replicas don't help write throughput.
    • One huge database means huge backups, slow migrations and a single blast radius.

    5. Three Real-World Examples¶

    Example 1: Hash-Sharded Ledger (Banking)¶

    Scenario: A neobank has 40 million accounts and peaks at 15,000 ledger writes per second. Accounts are hash-sharded across databases by account id. Transfers between accounts on the same shard are a normal local transaction. Transfers that cross shards can't use one ACID transaction, so they go through a saga (debit, then credit, with compensation).

    Design:

    flowchart LR T["transfer(ACC-1001 → ACC-1004)"] --> R{"same shard?"} R -- yes --> L["one local transaction on shard 1"] R -- no --> S["Transfer saga: debit on shard A,<br/>credit on shard B, compensate on failure"]

    Full Code:

    package com.handbook.microservices.sharding.banking;

import com.handbook.microservices.support.Db;

import javax.sql.DataSource;
import java.sql.Connection;
import java.sql.PreparedStatement;
import java.sql.ResultSet;
import java.sql.SQLException;
import java.util.ArrayList;
import java.util.List;

/** Hash sharding: each account lives in exactly one of N databases, chosen from its id. */
public final class ShardedLedger {

    private final List<DataSource> shards = new ArrayList<>();

    public ShardedLedger(int shardCount) {
        for (int i = 0; i < shardCount; i++) {
            shards.add(Db.inMemory("ledger_shard" + i,
                    "CREATE TABLE account (id VARCHAR PRIMARY KEY, balance_paise BIGINT CHECK (balance_paise >= 0))"));
        }
    }

    public int shardOf(String accountId) { // (1)!
        return Math.floorMod(accountId.hashCode(), shards.size());
    }

    public void open(String accountId, long paise) {
        exec(shards.get(shardOf(accountId)), c -> update(c, "INSERT INTO account VALUES (?, ?)", accountId, paise));
    }

    public long balance(String accountId) {
        try (Connection c = shards.get(shardOf(accountId)).getConnection();
             PreparedStatement ps = c.prepareStatement("SELECT balance_paise FROM account WHERE id = ?")) {
            ps.setString(1, accountId);
            ResultSet rs = ps.executeQuery();
            rs.next();
            return rs.getLong(1);
        } catch (SQLException e) {
            throw new IllegalStateException(e);
        }
    }

    /** Same shard: one local ACID transaction. Different shards: refuse, a saga is needed. */
    public String transfer(String from, String to, long paise) {
        if (shardOf(from) != shardOf(to)) { // (2)!
            return "cross-shard (" + shardOf(from) + "->" + shardOf(to) + "): start a transfer saga instead";
        }
        exec(shards.get(shardOf(from)), c -> {
            update(c, "UPDATE account SET balance_paise = balance_paise - ? WHERE id = ?", paise, from);
            update(c, "UPDATE account SET balance_paise = balance_paise + ? WHERE id = ?", paise, to);
        });
        return "local transaction on shard " + shardOf(from);
    }

    private interface Work { void run(Connection c) throws SQLException; }

    private static void exec(DataSource ds, Work work) {
        try (Connection c = ds.getConnection()) {
            c.setAutoCommit(false);
            try {
                work.run(c);
                c.commit();
            } catch (SQLException e) {
                c.rollback();
                throw new IllegalStateException(e);
            }
        } catch (SQLException e) {
            throw new IllegalStateException(e);
        }
    }

    private static void update(Connection c, String sql, Object... args) throws SQLException {
        try (PreparedStatement ps = c.prepareStatement(sql)) {
            for (int i = 0; i < args.length; i++) {
                ps.setObject(i + 1, args[i]);
            }
            ps.executeUpdate();
        }
    }
}
    1. Routing is a pure function of the shard key. % N is simplest but moves most keys when N changes; production systems use consistent hashing or many fixed virtual shards (e.g. 1,024 logical shards mapped onto 8 servers).
    2. The router knows when an operation spans shards and refuses to pretend it's atomic.
    package com.handbook.microservices.sharding.banking;

public class LedgerShardingDemo {

    public static void main(String[] args) {
        System.out.println("=== Banking: Accounts Hash-Sharded Across 3 Databases ===");
        ShardedLedger ledger = new ShardedLedger(3);
        String[] accounts = {"ACC-1001", "ACC-1002", "ACC-1003", "ACC-1004", "ACC-1007"};
        for (String a : accounts) {
            ledger.open(a, 100_000);
            System.out.println(a + " -> shard " + ledger.shardOf(a));
        }
        System.out.println("ACC-1001 -> ACC-1004: " + ledger.transfer("ACC-1001", "ACC-1004", 25_000));
        System.out.println("  balances now " + ledger.balance("ACC-1001") + " / " + ledger.balance("ACC-1004"));
        System.out.println("ACC-1001 -> ACC-1002: " + ledger.transfer("ACC-1001", "ACC-1002", 10_000));
    }
}

    Output:

    === Banking: Accounts Hash-Sharded Across 3 Databases ===
ACC-1001 -> shard 1
ACC-1002 -> shard 2
ACC-1003 -> shard 0
ACC-1004 -> shard 1
ACC-1007 -> shard 1
ACC-1001 -> ACC-1004: local transaction on shard 1
  balances now 75000 / 125000
ACC-1001 -> ACC-1002: cross-shard (1->2): start a transfer saga instead

    Why hash sharding here:

    • Writes spread evenly; each shard takes about 1/N of the load.
    • Each account's rows live together, so single-account operations stay simple.
    • Cross-shard operations are explicit and handled with sagas, not hidden distributed locks.

    Example 2: City Shards and a Hot-City Split (Ride-hailing)¶

    Scenario: A ride-hailing platform keeps driver locations and trip state per city, because matching only ever looks within one city. Bengaluru on a Friday evening generates 6× the load of the next city. A directory maps each city to a shard, and a hot city can be split by zone range without touching anyone else.

    Design:

    flowchart LR D[(Directory)] -->|"bengaluru zones 0-99"| S1[shard-south-1] D -->|"bengaluru zones 100+"| S3[shard-south-3] D -->|chennai, mysuru| S2[shard-south-2] D -->|delhi| N1[shard-north-1]

    Full Code:

    package com.handbook.microservices.sharding.geo;

import java.util.LinkedHashMap;
import java.util.Map;
import java.util.NavigableMap;
import java.util.TreeMap;

/** Directory-based sharding: a lookup table maps city (and, for hot cities, a zone range) to a shard. */
public final class GeoShardDirectory {

    private final Map<String, NavigableMap<Integer, String>> directory = new LinkedHashMap<>(); // city -> (zoneFrom -> shard)

    public void assign(String city, String shard) {
        directory.put(city, new TreeMap<>(Map.of(0, shard)));
    }

    /** Split a hot city: zones >= fromZone move to a new shard. Only that city's mapping changes. */
    public void split(String city, int fromZone, String newShard) { // (1)!
        directory.get(city).put(fromZone, newShard);
    }

    public String route(String city, int zone) {
        NavigableMap<Integer, String> ranges = directory.get(city);
        if (ranges == null) {
            throw new IllegalArgumentException("no shard for " + city);
        }
        return ranges.floorEntry(zone).getValue(); // (2)!
    }
}
    1. Splitting changes one entry in the directory. With hash % N, adding a shard would move every city.
    2. floorEntry finds the range a zone falls into, like range sharding within a city.
    package com.handbook.microservices.sharding.geo;

import java.util.Map;
import java.util.TreeMap;

public class GeoShardingDemo {

    public static void main(String[] args) {
        System.out.println("=== Ride-hailing: City-Based Shards and Splitting a Hot City ===");
        GeoShardDirectory dir = new GeoShardDirectory();
        dir.assign("bengaluru", "shard-south-1");
        dir.assign("chennai", "shard-south-2");
        dir.assign("mysuru", "shard-south-2");
        dir.assign("delhi", "shard-north-1");

        System.out.println("Bengaluru zone 12 -> " + dir.route("bengaluru", 12) + ", zone 140 -> " + dir.route("bengaluru", 140));
        Map<String, Integer> load = new TreeMap<>();
        for (int zone = 0; zone < 200; zone++) {
            load.merge(dir.route("bengaluru", zone), 1, Integer::sum);
        }
        System.out.println("Before split, Bengaluru's 200 zones: " + load);

        dir.split("bengaluru", 100, "shard-south-3"); // Friday-evening surge: move zones 100+ to a new shard
        load.clear();
        for (int zone = 0; zone < 200; zone++) {
            load.merge(dir.route("bengaluru", zone), 1, Integer::sum);
        }
        System.out.println("After split,  Bengaluru's 200 zones: " + load);
        System.out.println("Chennai and Delhi routing unchanged: " + dir.route("chennai", 5) + ", " + dir.route("delhi", 5));
    }
}

    Output:

    === Ride-hailing: City-Based Shards and Splitting a Hot City ===
Bengaluru zone 12 -> shard-south-1, zone 140 -> shard-south-1
Before split, Bengaluru's 200 zones: {shard-south-1=200}
After split,  Bengaluru's 200 zones: {shard-south-1=100, shard-south-3=100}
Chennai and Delhi routing unchanged: shard-south-2, shard-north-1

    Why directory sharding here:

    • The access pattern is naturally per city, so queries hit one shard.
    • Uneven tenants (Bengaluru vs Mysuru) need individual placement, not a uniform hash.
    • Data can be placed near users (data residency, latency).

    Example 3: Scatter-Gather for a Cross-Shard Report (Grocery)¶

    Scenario: A grocery platform shards orders by customer id, so "my orders" hits one shard. But the merchandising dashboard asks "top-selling SKUs today", which has no shard key and must query every shard and merge. A common bug is merging each shard's local top-N, which can miss the real winner.

    Design:

    sequenceDiagram autonumber participant Dash as Dashboard participant G as Scatter-gather participant S0 as orders-0 participant S1 as orders-1 participant S2 as orders-2 Dash->>G: top 2 SKUs today par in parallel G->>S0: totals per SKU G->>S1: totals per SKU G->>S2: totals per SKU end G->>G: merge totals, then take top 2 G-->>Dash: EGGS 133, ATTA 112

    Full Code:

    package com.handbook.microservices.sharding.scatter;

import java.util.ArrayList;
import java.util.Comparator;
import java.util.HashMap;
import java.util.List;
import java.util.Map;
import java.util.concurrent.CompletableFuture;
import java.util.concurrent.ExecutorService;

/** A query without the shard key must ask EVERY shard and merge the partial results. */
public final class ScatterGather {

    public record SkuSales(String sku, long units) { }

    /** One shard's local data: orders of the customers that hash to it. */
    public record Shard(String name, List<SkuSales> orderLines) {
        List<SkuSales> topN(int n) { // (1)!
            Map<String, Long> totals = new HashMap<>();
            orderLines.forEach(l -> totals.merge(l.sku(), l.units(), Long::sum));
            return totals.entrySet().stream().map(e -> new SkuSales(e.getKey(), e.getValue()))
                    .sorted(Comparator.comparingLong(SkuSales::units).reversed().thenComparing(SkuSales::sku))
                    .limit(n).toList();
        }

        Map<String, Long> totals() {
            Map<String, Long> totals = new HashMap<>();
            orderLines.forEach(l -> totals.merge(l.sku(), l.units(), Long::sum));
            return totals;
        }
    }

    public static List<SkuSales> globalTopN(List<Shard> shards, int n, ExecutorService pool) {
        List<CompletableFuture<Map<String, Long>>> partials = new ArrayList<>();
        for (Shard s : shards) {
            partials.add(CompletableFuture.supplyAsync(s::totals, pool)); // (2)!
        }
        Map<String, Long> merged = new HashMap<>();
        partials.forEach(f -> f.join().forEach((sku, units) -> merged.merge(sku, units, Long::sum))); // (3)!
        return merged.entrySet().stream().map(e -> new SkuSales(e.getKey(), e.getValue()))
                .sorted(Comparator.comparingLong(SkuSales::units).reversed().thenComparing(SkuSales::sku))
                .limit(n).toList();
    }

    /** Wrong shortcut: merging each shard's local top-N can miss the true global top-N. */
    public static List<SkuSales> mergeOfLocalTopN(List<Shard> shards, int n) {
        Map<String, Long> merged = new HashMap<>();
        shards.forEach(s -> s.topN(n).forEach(x -> merged.merge(x.sku(), x.units(), Long::sum)));
        return merged.entrySet().stream().map(e -> new SkuSales(e.getKey(), e.getValue()))
                .sorted(Comparator.comparingLong(SkuSales::units).reversed().thenComparing(SkuSales::sku))
                .limit(n).toList();
    }
}
    1. Each shard can compute a local aggregate cheaply...
    2. ...queried in parallel, so latency is the slowest shard, not the sum.
    3. Merge complete partial aggregates, then rank. Ranking before merging is the classic bug.
    package com.handbook.microservices.sharding.scatter;

import com.handbook.microservices.sharding.scatter.ScatterGather.Shard;
import com.handbook.microservices.sharding.scatter.ScatterGather.SkuSales;

import java.util.List;
import java.util.concurrent.Executors;

public class ScatterGatherDemo {

    public static void main(String[] args) {
        System.out.println("=== Grocery: 'Top 2 SKUs Today' Across Customer-Sharded Order Databases ===");
        List<Shard> shards = List.of(
                new Shard("orders-0", List.of(new SkuSales("MILK", 50), new SkuSales("BREAD", 40), new SkuSales("EGGS", 39))),
                new Shard("orders-1", List.of(new SkuSales("ATTA", 60), new SkuSales("MILK", 45), new SkuSales("EGGS", 44))),
                new Shard("orders-2", List.of(new SkuSales("BREAD", 55), new SkuSales("ATTA", 52), new SkuSales("EGGS", 50))));
        try (var pool = Executors.newVirtualThreadPerTaskExecutor()) {
            System.out.println("Scatter-gather of full totals : " + ScatterGather.globalTopN(shards, 2, pool));
        }
        System.out.println("Merging each shard's top 2    : " + ScatterGather.mergeOfLocalTopN(shards, 2)
                + "  <- EGGS (133 units, the real #1) missed: never in a local top 2");
        System.out.println("A query with the shard key (one customer's orders) would touch exactly 1 of 3 shards.");
    }
}

    Output:

    === Grocery: 'Top 2 SKUs Today' Across Customer-Sharded Order Databases ===
Scatter-gather of full totals : [SkuSales[sku=EGGS, units=133], SkuSales[sku=ATTA, units=112]]
Merging each shard's top 2    : [SkuSales[sku=ATTA, units=112], SkuSales[sku=BREAD, units=95]]  <- EGGS (133 units, the real #1) missed: never in a local top 2
A query with the shard key (one customer's orders) would touch exactly 1 of 3 shards.

    Why scatter-gather here:

    • Some queries legitimately span all data; parallel fan-out keeps them possible.
    • It's expensive (N queries, tail latency of the slowest shard), so frequent ones should move to a materialized view or analytics store.
    • Correct merging requires mergeable aggregates (sums, counts), not ranks.
    Unit Tests: ShardingTest.java 
    package com.handbook.microservices;

import com.handbook.microservices.sharding.banking.ShardedLedger;
import com.handbook.microservices.sharding.geo.GeoShardDirectory;
import com.handbook.microservices.sharding.scatter.ScatterGather;
import com.handbook.microservices.sharding.scatter.ScatterGather.Shard;
import com.handbook.microservices.sharding.scatter.ScatterGather.SkuSales;
import org.junit.jupiter.api.Test;

import java.util.List;
import java.util.concurrent.Executors;

import static org.assertj.core.api.Assertions.assertThat;

class ShardingTest {

    @Test
    void routingIsStableAndLocalTransfersAreAtomic() {
        ShardedLedger l = new ShardedLedger(3);
        assertThat(l.shardOf("ACC-1")).isEqualTo(l.shardOf("ACC-1"));
        l.open("ACC-1001", 100);
        l.open("ACC-1004", 0);
        assertThat(l.shardOf("ACC-1001")).isEqualTo(l.shardOf("ACC-1004"));
        l.transfer("ACC-1001", "ACC-1004", 40);
        assertThat(l.balance("ACC-1001") + l.balance("ACC-1004")).isEqualTo(100);
    }

    @Test
    void splittingAHotCityMovesOnlyThatCity() {
        GeoShardDirectory d = new GeoShardDirectory();
        d.assign("a", "s1");
        d.assign("b", "s1");
        d.split("a", 50, "s2");
        assertThat(d.route("a", 49)).isEqualTo("s1");
        assertThat(d.route("a", 50)).isEqualTo("s2");
        assertThat(d.route("b", 99)).isEqualTo("s1");
    }

    @Test
    void scatterGatherFindsTheTrueGlobalTop() {
        List<Shard> shards = List.of(new Shard("0", List.of(new SkuSales("A", 10), new SkuSales("C", 9))),
                new Shard("1", List.of(new SkuSales("B", 10), new SkuSales("C", 9))));
        try (var pool = Executors.newVirtualThreadPerTaskExecutor()) {
            assertThat(ScatterGather.globalTopN(shards, 1, pool)).containsExactly(new SkuSales("C", 18));
        }
    }
}

    6. Variations & Modern Java Take¶

    Variation Notes
    Logical (virtual) shards 1,024 logical shards mapped to a few physical servers; rebalance by moving logical shards, never rehashing keys
    Consistent hashing Adding a node moves ~1/N of keys (LLD: consistent hashing)
    Distributed SQL CockroachDB, YugabyteDB, Google Spanner, TiDB: automatic range sharding and cross-shard transactions
    Sharded PostgreSQL Citus (distributed tables, co-location by tenant), Vitess for MySQL
    App-level routing in Spring AbstractRoutingDataSource picks a DataSource per request from a shard key in context
    NoSQL DynamoDB/Cassandra partition keys: sharding is built in, so the key design rules still apply

    7. Where It Lives in Real Frameworks¶

    Where Sharding
    Spring AbstractRoutingDataSource, Apache ShardingSphere-JDBC (driver-level sharding)
    PostgreSQL ecosystem Citus create_distributed_table('orders', 'customer_id'); native partitioning on each shard
    MySQL Vitess (YouTube, Slack), ProxySQL
    Kafka Topic partitions: hash(key) % partitions: same rules, same hot-partition problem
    Elasticsearch / OpenSearch Index shards; routing by _routing key
    DynamoDB / Cassandra Partition key = shard key; avoid hot partitions with high-cardinality keys

    8. Pros, Cons & Trade-offs¶

    ✅ Pros ❌ Cons
    Write throughput and storage scale horizontally Cross-shard queries need scatter-gather
    Smaller databases: faster backups, migrations, vacuum Cross-shard transactions need sagas or distributed SQL
    Failure of one shard affects only part of the users Resharding is hard and risky
    Data can live near users (residency, latency) Operational overhead: N databases to monitor, upgrade, back up

    9. Pitfalls & Anti-Patterns¶

    Sharding too early

    Most services never need it. Exhaust indexing, query fixes, caching, read replicas, partitioning and a bigger instance first. Sharding is a one-way door.

    Monotonic shard keys

    Range-sharding on timestamps or auto-increment ids sends every new write to the last shard (coding challenge). Hash them, or prefix with a high-cardinality component.

    hash % N with no plan for N+1

    Adding a shard moves ~(N)/(N+1) of keys. Use logical shards or consistent hashing from day one.

    Shard key that doesn't match the main query

    If 80% of queries filter by store_id but you shard by customer_id, 80% of queries become scatter-gather.

    10. Senior / Architect Deep Dive (10–15 yrs)¶

    Choosing the key. High cardinality, even distribution, present in nearly every query, and stable (never changes for a row). Co-locate data that's queried or updated together under the same key (Citus "co-location": orders, order lines and payments all keyed by customer_id).

    Resharding without downtime. Dual-write or CDC-copy a logical shard to its new home, verify, switch the directory entry, then drain and delete. Logical shards make each move small and reversible. Rehearse it before you need it.

    Hot keys. A celebrity seller or a viral product can overload one shard regardless of strategy. Split the key (product#1..#8 for counters), cache reads, queue writes, or give that tenant a dedicated shard via the directory.

    War story: the last shard that took every write

    An e-commerce team range-sharded orders by created_at month, reasoning that old months could be archived easily. Every new order went to the current month's shard; at the Diwali sale it hit 100% CPU while the other 11 shards idled at 3%. Checkout errors peaked at 30% for two hours. Fix: re-shard by hashed customer_id into 256 logical shards on 8 servers; time-based archiving moved to PostgreSQL partitioning inside each shard. Lesson: shard keys must spread writes, and time is the worst key for that.

    Sharding Read Replicas Partitioning (in one DB) Database per Service

    12. Interview Corner¶

    Q1. What is sharding?

    Splitting data across multiple databases by a key so each database stores and serves only part of it.

    Q2. Sharding vs replication?

    Sharding splits data; replication copies it. Sharding scales writes; replication scales reads and availability.

    Q3. What is a shard key?

    The field used to decide which shard a row lives on.

    Q4. Name three sharding strategies.

    Hash, range, directory (lookup).

    Q5. What's a hot shard?

    One shard receiving far more traffic than the others, usually due to a poor key or a very popular entity.

    Q1. Why is hash % N problematic?

    Changing N remaps most keys, forcing massive data movement.

    Q2. How do you query across shards?

    Scatter-gather in parallel and merge results; or maintain a read model/analytics store.

    Q3. How do you handle a transaction across shards?

    Avoid it via co-location; otherwise a saga, or a distributed SQL database with distributed transactions.

    Q4. How do you generate unique ids across shards?

    UUIDv7, Snowflake-style ids (timestamp + node + sequence) or per-shard ranges.

    Q5. Why not shard by date?

    All new writes go to the newest shard.

    Q1. "Design sharding for an orders database at 50k writes/s."

    Hash by customer_id into 1,024 logical shards on N Citus/Vitess nodes; co-locate order lines/payments; Snowflake ids; CQRS read models for store/merchant views; CDC to an analytics store for reports.

    Q2. "How do you reshard live?"

    Logical shards; copy via CDC; verify checksums; flip directory entries per shard; keep the old copy for rollback; throttle to protect production.

    Q3. "A single seller generates 40% of writes."

    Dedicated shard via the directory, sub-sharding that seller's key, write queues, and caching their catalog reads.

    Q4. "When would you choose Spanner/CockroachDB instead?"

    When you need cross-shard ACID transactions and SQL across regions and can accept higher write latency and cost.

    Q5. "What are the operational costs?"

    N× backups, upgrades, schema migrations (must be backward compatible and rolled out per shard), monitoring per shard, and runbooks for shard failover.

    Problem: Route today's 100,000 new orders with (a) range-by-quarter on order date and (b) a hash of the order id across 4 shards. Show the distribution and explain the trade-off.

    Solution 
    package com.handbook.microservices.sharding.hotspot;

import java.time.LocalDate;
import java.util.Map;
import java.util.TreeMap;

/** Coding challenge: why "range by order date" is a terrible shard key for writes. */
public class ShardKeyDemo {

    static final int SHARDS = 4;

    static int byDateRange(LocalDate day) {
        int quarter = (day.getMonthValue() - 1) / 3;
        return quarter; // Q1 -> shard 0, Q2 -> shard 1, ...
    }

    static int byHashedOrderId(String orderId) {
        return Math.floorMod(orderId.hashCode() * 0x9E3779B1, SHARDS); // spread similar ids
    }

    public static void main(String[] args) {
        System.out.println("=== Challenge: Picking a Shard Key (today's 100,000 new orders) ===");
        LocalDate today = LocalDate.of(2026, 5, 14);
        Map<Integer, Integer> range = new TreeMap<>();
        Map<Integer, Integer> hashed = new TreeMap<>();
        for (int i = 0; i < SHARDS; i++) {
            range.put(i, 0);
            hashed.put(i, 0);
        }
        for (int i = 0; i < 100_000; i++) {
            range.merge(byDateRange(today), 1, Integer::sum);
            hashed.merge(byHashedOrderId("ORD-" + (20260514_000_000L + i)), 1, Integer::sum);
        }
        System.out.println("Range by date  : " + range + "  <- every write hits one hot shard");
        System.out.println("Hash of orderId: " + hashed + "  <- writes spread evenly");
        System.out.println("But 'orders between two dates' now needs scatter-gather: pick the key for your main access path.");
    }
}

    Output:

    === Challenge: Picking a Shard Key (today's 100,000 new orders) ===
Range by date  : {0=0, 1=100000, 2=0, 3=0}  <- every write hits one hot shard
Hash of orderId: {0=24998, 1=24998, 2=25002, 3=25002}  <- writes spread evenly
But 'orders between two dates' now needs scatter-gather: pick the key for your main access path.

    Key points to say: range-by-time sends every write to one shard; hashing spreads writes but turns date-range queries into scatter-gather. Pick the key for the dominant access path and serve the other paths with read models.

    Behavioural tie-in (STAR) for experienced candidates

    • S: Date-range sharding sent all Diwali-sale writes to one shard; checkout errors reached 30%.
    • T: Spread writes evenly without losing cheap archiving.
    • A: Re-sharded by hashed customer_id into 256 logical shards on 8 nodes via CDC copy and per-shard cut-over; kept monthly partitions inside each shard for archiving.
    • R: Peak per-shard CPU fell from 100% to 38% the next sale; resharding a logical shard now takes 20 minutes with no downtime.

    13. Quick Revision Card¶

    Remember in 30 seconds

    • Split rows across servers by a shard key; scales writes and storage.
    • Strategies: hash (even), range (scans, hotspots), directory (flexible).
    • Key: high cardinality, in most queries, stable; co-locate related data.
    • Cross-shard: scatter-gather reads, sagas for writes.
    • Use logical shards or consistent hashing; shard last, not first.
    int shard = Math.floorMod(hash(customerId), LOGICAL_SHARDS);   // then logical → physical via directory
