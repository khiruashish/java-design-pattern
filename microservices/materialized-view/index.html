    Data Intermediate Microservices

    Materialized View¶

    🟡 Intermediate Microservices Interview frequency ⭐⭐⭐⭐

    TL;DR

    A Materialized View stores the precomputed result of an expensive query (aggregates, joins, data from several services) so reads become a single cheap lookup. It's refreshed on a schedule or kept up to date incrementally from events. Use it when the same expensive question is asked far more often than the underlying data changes, or when the data needed lives in several services or shards.

    See It in Motion¶

    Press Play to watch the calls travel between components, or step through with Next and Back. Switch to Without it to see what goes wrong without the pattern, or press a Break it button to make something fail while the pattern is in place. Open the full explorer with all 66 patterns

    1. Intent & Problem It Solves¶

    The problem in plain English: the store manager's dashboard shows today's orders and revenue. Computing it means SUM over millions of order lines, run every time 400 managers refresh their screens. The tracking page needs shipment, driver and ETA data that live in three different services; joining them over HTTP on every page view is slow and fragile.

    Definition (Azure Architecture Center, Materialized View pattern):

    Generate prepopulated views over the data in one or more data stores when the data isn't ideally formatted for required query operations. The view is a disposable cache: it can always be rebuilt from the source of truth.

    Refresh strategies:

    Strategy How Freshness Cost
    Full refresh Recompute everything on a schedule (REFRESH MATERIALIZED VIEW) Minutes / hours Proportional to all data
    Incremental Apply each change (event, CDC row) to the view Seconds Proportional to changes
    On read, cached Compute on miss, keep with TTL Varies See Cache-Aside

    2. Real-World Analogy¶

    The cricket scoreboard

    Nobody recounts every ball of the match to know the score. The scorer updates the board after each ball (incremental view). The board can always be reconstructed from the ball-by-ball scorebook (source of truth) if someone suspects a mistake.

    3. Structure¶

    flowchart LR subgraph Sources of truth O[(Orders DB)] D[(Delivery service)] P[(Payments service)] end O -->|"events / CDC / scheduled query"| B[View builder] D --> B P --> B B --> V[(Materialized view<br/>denormalized, query-shaped)] Q[Dashboard / page] -->|"one lookup"| V
    Participant Responsibility
    Source of truth Normalized data owned by its service; never modified by the view
    View builder Scheduled job, stream processor or CDC consumer that computes/updates the view
    Materialized view Denormalized, query-shaped storage (table, document, Redis hash, search index)
    Readers Query the view only; accept its staleness

    4. Naive Approach (Without the Pattern)¶

    // Dashboard: full scan on every refresh by every manager
jdbc.queryForObject("SELECT COUNT(*), SUM(amount_paise) FROM order_line WHERE store = ? AND sales_day = ?", ...);

// Tracking page: three synchronous calls and an in-memory join per view
var s = shipmentClient.get(awb); var d = driverClient.get(s.driverId()); var e = etaClient.get(awb);
    • Repeating expensive work for identical answers.
    • Page latency = sum of three services' latencies; any one down breaks the page.
    • Heavy analytical queries slow down the transactional database.

    5. Three Real-World Examples¶

    Example 1: Store Sales Summary with Full Refresh (Grocery)¶

    Scenario: 400 dark-store managers refresh a sales dashboard all evening. The raw order_line table gets 2 million rows a day. A summary table, refreshed every 5 minutes in one transaction, answers each dashboard request with a single primary-key lookup. A few minutes of staleness is acceptable for a dashboard.

    Design:

    flowchart LR L[(order_line: 21k+ rows)] -->|"every 5 min: GROUP BY store, day"| MV[(mv_store_daily_sales)] M[400 managers] -->|"SELECT ... WHERE store = ? AND day = ?"| MV

    Full Code:

    package com.handbook.microservices.materializedview.sales;

import com.handbook.microservices.support.Db;

import javax.sql.DataSource;
import java.sql.Connection;
import java.sql.Date;
import java.sql.PreparedStatement;
import java.sql.ResultSet;
import java.sql.SQLException;
import java.sql.Statement;

/** A summary table rebuilt on a schedule: the dashboard reads one row instead of scanning every order line. */
public final class StoreSalesView {

    private final DataSource ds = Db.inMemory("mv_sales",
            "CREATE TABLE order_line (store VARCHAR, sales_day DATE, amount_paise BIGINT)",
            "CREATE TABLE mv_store_daily_sales (store VARCHAR, sales_day DATE, orders BIGINT, revenue_paise BIGINT,"
                    + " PRIMARY KEY (store, sales_day))");

    public void insertLines(String store, String day, int count, long paiseEach) {
        try (Connection c = ds.getConnection();
             PreparedStatement ps = c.prepareStatement("INSERT INTO order_line VALUES (?, ?, ?)")) {
            for (int i = 0; i < count; i++) {
                ps.setString(1, store);
                ps.setDate(2, Date.valueOf(day));
                ps.setLong(3, paiseEach);
                ps.addBatch();
            }
            ps.executeBatch();
        } catch (SQLException e) {
            throw new IllegalStateException(e);
        }
    }

    /** Equivalent of PostgreSQL REFRESH MATERIALIZED VIEW: recompute in one transaction. */
    public void refresh() { // (1)!
        try (Connection c = ds.getConnection(); Statement s = c.createStatement()) {
            c.setAutoCommit(false);
            s.execute("DELETE FROM mv_store_daily_sales");
            s.execute("INSERT INTO mv_store_daily_sales SELECT store, sales_day, COUNT(*), SUM(amount_paise)"
                    + " FROM order_line GROUP BY store, sales_day");
            c.commit(); // (2)!
        } catch (SQLException e) {
            throw new IllegalStateException(e);
        }
    }

    public String dashboard(String store, String day) {
        try (Connection c = ds.getConnection(); PreparedStatement ps = c.prepareStatement(
                "SELECT orders, revenue_paise FROM mv_store_daily_sales WHERE store = ? AND sales_day = ?")) {
            ps.setString(1, store);
            ps.setDate(2, Date.valueOf(day));
            ResultSet rs = ps.executeQuery();
            return rs.next() ? rs.getLong(1) + " orders, INR " + rs.getLong(2) / 100 : "no data yet";
        } catch (SQLException e) {
            throw new IllegalStateException(e);
        }
    }

    public long rawLines() {
        return Db.count(ds, "SELECT COUNT(*) FROM order_line");
    }
}
    1. A full refresh: rebuild the summary from the source of truth. PostgreSQL has this built in (CREATE MATERIALIZED VIEW ...; REFRESH MATERIALIZED VIEW CONCURRENTLY ...).
    2. In one transaction, so readers see either the old or the new summary, never a half-built one.
    package com.handbook.microservices.materializedview.sales;

public class SalesViewDemo {

    public static void main(String[] args) {
        System.out.println("=== Grocery: Store Sales Dashboard on a Refreshed Summary Table ===");
        StoreSalesView view = new StoreSalesView();
        view.insertLines("BLR-HSR", "2026-07-01", 12_000, 41_500);
        view.insertLines("BLR-KORA", "2026-07-01", 9_000, 38_000);
        view.refresh(); // nightly / every 5 minutes
        System.out.println("Raw order lines: " + view.rawLines() + "; dashboard reads 1 precomputed row:");
        System.out.println("  BLR-HSR  2026-07-01 -> " + view.dashboard("BLR-HSR", "2026-07-01"));

        view.insertLines("BLR-HSR", "2026-07-01", 500, 41_500); // evening orders after the last refresh
        System.out.println("Before next refresh -> " + view.dashboard("BLR-HSR", "2026-07-01") + " (stale by design)");
        view.refresh();
        System.out.println("After refresh       -> " + view.dashboard("BLR-HSR", "2026-07-01"));
    }
}

    Output:

    === Grocery: Store Sales Dashboard on a Refreshed Summary Table ===
Raw order lines: 21000; dashboard reads 1 precomputed row:
  BLR-HSR  2026-07-01 -> 12000 orders, INR 4980000
Before next refresh -> 12000 orders, INR 4980000 (stale by design)
After refresh       -> 12500 orders, INR 5187500

    Why a materialized view here:

    • Read load is hundreds of times the write rate for this question.
    • Staleness is explicit and bounded by the refresh interval.
    • The transactional workload no longer runs aggregate scans.

    Example 2: Incremental Balance View (Banking)¶

    Scenario: A banking app shows the balance every time it opens (8 million opens a day). The source of truth is an append-only ledger. Summing the ledger per open is too expensive; a balance view is updated by each ledger event. The broker delivers at least once, so the view must ignore duplicates.

    Design:

    flowchart LR LG[(Ledger, append-only)] -->|"LedgerEntry events (at-least-once)"| C[View consumer] C -->|"dedupe by eventId, then balance += delta"| V[(balances)] App -->|"GET balance"| V

    Full Code:

    package com.handbook.microservices.materializedview.balances;

import java.util.HashSet;
import java.util.Map;
import java.util.Set;
import java.util.TreeMap;

/** Incrementally maintained view: each ledger event updates the running balance once. */
public final class BalanceView {

    public record LedgerEntry(String eventId, String account, long deltaPaise) { }

    private final Map<String, Long> balances = new TreeMap<>();
    private final Set<String> applied = new HashSet<>(); // in production: a processed_events table

    public boolean apply(LedgerEntry e) {
        if (!applied.add(e.eventId())) { // (1)!
            return false;
        }
        balances.merge(e.account(), e.deltaPaise(), Long::sum); // (2)!
        return true;
    }

    public long balance(String account) {
        return balances.getOrDefault(account, 0L);
    }

    public Map<String, Long> all() {
        return Map.copyOf(balances);
    }
}
    1. Idempotency: a redelivered event is detected and ignored (Idempotent Consumer). In SQL, insert the event id and the balance update in the same transaction.
    2. Incremental update: the cost is proportional to the change, not to the history.
    package com.handbook.microservices.materializedview.balances;

import com.handbook.microservices.materializedview.balances.BalanceView.LedgerEntry;

import java.util.List;
import java.util.TreeMap;

public class BalanceViewDemo {

    public static void main(String[] args) {
        System.out.println("=== Banking: Account Balances Maintained Incrementally from Ledger Events ===");
        BalanceView view = new BalanceView();
        List<LedgerEntry> stream = List.of(
                new LedgerEntry("e1", "SB-1", 500_000),
                new LedgerEntry("e2", "SB-2", 120_000),
                new LedgerEntry("e3", "SB-1", -75_000),
                new LedgerEntry("e3", "SB-1", -75_000), // redelivered by the broker
                new LedgerEntry("e4", "SB-2", -20_000));
        int ignored = 0;
        for (LedgerEntry e : stream) {
            ignored += view.apply(e) ? 0 : 1;
        }
        System.out.println("Applied " + (stream.size() - ignored) + " events, ignored " + ignored + " duplicate");
        System.out.println("Balances: " + new TreeMap<>(view.all()));
        System.out.println("Balance lookup is O(1): no SUM over millions of ledger rows per app open.");
    }
}

    Output:

    === Banking: Account Balances Maintained Incrementally from Ledger Events ===
Applied 4 events, ignored 1 duplicate
Balances: {SB-1=425000, SB-2=100000}
Balance lookup is O(1): no SUM over millions of ledger rows per app open.

    Why an incremental view here:

    • Freshness in seconds without recomputing history.
    • The ledger stays the auditable source of truth; the view is a derived convenience.
    • Shown to customers, but payments still validate against the ledger, not the view.

    Example 3: Tracking Page from Three Services (Logistics)¶

    Scenario: A courier's tracking page needs the shipment's city (shipping service), the driver (fleet service) and the ETA (routing service). Instead of three calls per page view, a view builder consumes all three event streams into one denormalized document per AWB. Events from different services can arrive in any order, and the same source can deliver an older update late.

    Design:

    sequenceDiagram autonumber participant F as Fleet participant S as Shipping participant R as Routing participant V as TrackingView F->>V: DriverAssigned v1 (before Shipped!) S->>V: Shipped v1 R->>V: EtaUpdated v2 (14:40) R->>V: EtaUpdated v1 (14:25, late) → ignored Note over V: page = {city, driver, eta 14:40}

    Full Code:

    package com.handbook.microservices.materializedview.tracking;

import java.util.HashMap;
import java.util.Map;

/** A denormalized view assembled from three services' events; tolerates out-of-order delivery per source. */
public final class TrackingView {

    public sealed interface Event permits Shipped, DriverAssigned, EtaUpdated {
        String awb();
        long version(); // per-source sequence number
    }

    public record Shipped(String awb, String city, long version) implements Event { }

    public record DriverAssigned(String awb, String driver, long version) implements Event { }

    public record EtaUpdated(String awb, String eta, long version) implements Event { }

    public record Page(String awb, String city, String driver, String eta) { }

    private final Map<String, Page> pages = new HashMap<>();
    private final Map<String, Long> lastVersion = new HashMap<>(); // key: awb + source

    public void on(Event e) {
        String source = e.getClass().getSimpleName();
        String key = e.awb() + "/" + source;
        if (e.version() <= lastVersion.getOrDefault(key, 0L)) { // (1)!
            return;
        }
        lastVersion.put(key, e.version());
        Page p = pages.getOrDefault(e.awb(), new Page(e.awb(), "?", "?", "?"));
        pages.put(e.awb(), switch (e) { // (2)!
            case Shipped s -> new Page(p.awb(), s.city(), p.driver(), p.eta());
            case DriverAssigned d -> new Page(p.awb(), p.city(), d.driver(), p.eta());
            case EtaUpdated t -> new Page(p.awb(), p.city(), p.driver(), t.eta());
        });
    }

    public Page page(String awb) {
        return pages.get(awb);
    }
}
    1. Keep the last applied version per source, so a late, older event can't overwrite newer data.
    2. Each event type updates only its fields: arrival order between sources doesn't matter.
    package com.handbook.microservices.materializedview.tracking;

import com.handbook.microservices.materializedview.tracking.TrackingView.DriverAssigned;
import com.handbook.microservices.materializedview.tracking.TrackingView.EtaUpdated;
import com.handbook.microservices.materializedview.tracking.TrackingView.Shipped;

public class TrackingViewDemo {

    public static void main(String[] args) {
        System.out.println("=== Logistics: One Tracking Page Built from Three Services ===");
        TrackingView view = new TrackingView();
        view.on(new DriverAssigned("AWB-77", "Ravi (KA-01-AB-1234)", 1)); // arrives before Shipped
        System.out.println("After driver event : " + view.page("AWB-77"));
        view.on(new Shipped("AWB-77", "Bengaluru", 1));
        view.on(new EtaUpdated("AWB-77", "14:40", 2));
        view.on(new EtaUpdated("AWB-77", "14:25", 1)); // older ETA delivered late
        System.out.println("After all events   : " + view.page("AWB-77"));
        System.out.println("The late, older ETA (v1) was ignored; the page answers with one key lookup, no joins across services.");
    }
}

    Output:

    === Logistics: One Tracking Page Built from Three Services ===
After driver event : Page[awb=AWB-77, city=?, driver=Ravi (KA-01-AB-1234), eta=?]
After all events   : Page[awb=AWB-77, city=Bengaluru, driver=Ravi (KA-01-AB-1234), eta=14:40]
The late, older ETA (v1) was ignored; the page answers with one key lookup, no joins across services.

    Why a materialized view here:

    • The page works even if the routing service is down (it shows the last ETA).
    • One key lookup instead of three network calls.
    • The pattern behind CQRS read models and API composition replacements.
    Unit Tests: MaterializedViewTest.java 
    package com.handbook.microservices;

import com.handbook.microservices.materializedview.balances.BalanceView;
import com.handbook.microservices.materializedview.balances.BalanceView.LedgerEntry;
import com.handbook.microservices.materializedview.sales.StoreSalesView;
import com.handbook.microservices.materializedview.tracking.TrackingView;
import com.handbook.microservices.materializedview.tracking.TrackingView.EtaUpdated;
import org.junit.jupiter.api.Test;

import static org.assertj.core.api.Assertions.assertThat;

class MaterializedViewTest {

    @Test
    void summaryReflectsDataOnlyAfterRefresh() {
        StoreSalesView v = new StoreSalesView();
        v.insertLines("S", "2026-01-01", 2, 100);
        assertThat(v.dashboard("S", "2026-01-01")).isEqualTo("no data yet");
        v.refresh();
        assertThat(v.dashboard("S", "2026-01-01")).isEqualTo("2 orders, INR 2");
    }

    @Test
    void duplicateEventsDoNotDoubleCount() {
        BalanceView v = new BalanceView();
        v.apply(new LedgerEntry("e1", "A", 100));
        v.apply(new LedgerEntry("e1", "A", 100));
        assertThat(v.balance("A")).isEqualTo(100);
    }

    @Test
    void olderEventsFromTheSameSourceAreIgnored() {
        TrackingView v = new TrackingView();
        v.on(new EtaUpdated("X", "10:00", 2));
        v.on(new EtaUpdated("X", "09:00", 1));
        assertThat(v.page("X").eta()).isEqualTo("10:00");
    }
}

    6. Variations & Modern Java Take¶

    CREATE MATERIALIZED VIEW mv_store_daily_sales AS
  SELECT store, sales_day, COUNT(*) AS orders, SUM(amount_paise) AS revenue_paise
  FROM order_line GROUP BY store, sales_day;
CREATE UNIQUE INDEX ON mv_store_daily_sales (store, sales_day);  -- required for CONCURRENTLY
REFRESH MATERIALIZED VIEW CONCURRENTLY mv_store_daily_sales;      -- readers aren't blocked
    Variation Notes
    Database materialized views PostgreSQL, Oracle (with fast refresh), SQL Server indexed views
    Stream-processed views Kafka Streams KTable / state stores, Flink, Materialize, RisingWave: incremental SQL views over streams
    CDC-fed views Debezium → consumer → Elasticsearch/Redis/another DB
    Search index as a view OpenSearch documents built from several services for full-text and faceted queries
    Blue/green rebuild Build view_v2 alongside view_v1, verify, switch readers, drop old (coding challenge)

    7. Where It Lives in Real Frameworks¶

    Where Materialized views
    PostgreSQL CREATE MATERIALIZED VIEW, REFRESH ... CONCURRENTLY (schedule with pg_cron)
    Kafka Streams groupByKey().aggregate(...) → KTable with interactive queries
    Spring @Scheduled refresh jobs; Spring Kafka listeners building projections
    Axon Event-handling projections (@EventHandler updating query models)
    Cloud BigQuery / Snowflake materialized views; DynamoDB Streams → aggregates

    8. Pros, Cons & Trade-offs¶

    ✅ Pros ❌ Cons
    Expensive queries become cheap lookups Data is stale (by refresh interval or event lag)
    Combine data from several services/shards Extra storage and a builder to operate
    Reads keep working when sources are down Incremental logic must handle duplicates and ordering
    Offloads the transactional database Views drift if events are lost; need rebuild tooling

    9. Pitfalls & Anti-Patterns¶

    Making decisions from a stale view

    Approving a payment from a balance view that lags the ledger allows overdrafts. Use views for display; check the source of truth for decisions.

    Non-idempotent incremental updates

    At-least-once delivery + balance += delta without dedupe = double counting. Track applied event ids or versions.

    Full refresh that blocks readers

    PostgreSQL's plain REFRESH MATERIALIZED VIEW takes an exclusive lock. Use CONCURRENTLY (needs a unique index) or swap tables.

    No way to rebuild

    If the view can't be recomputed from the source of truth (events retained, or source tables queryable), a single bug corrupts it permanently.

    10. Senior / Architect Deep Dive (10–15 yrs)¶

    Treat views as disposable. Keep enough history (Kafka retention, event store, CDC from source tables) to rebuild any view from scratch. Build new versions side by side and switch readers atomically. This makes schema changes to views low-risk.

    Lag is a product metric. Measure "event time → visible in view" and alert on it. Expose freshness to users where it matters ("updated 2 minutes ago").

    Ordering. Per-key ordering (Kafka partition by aggregate id) handles most cases; across sources, apply per-source versions or "last-writer-wins by event time" carefully, and design fields so each source owns its own part of the document.

    War story: the balance that was off by one payment

    A wallet's balance view consumer crashed after updating the balance but before committing its Kafka offset. On restart it re-applied the event: thousands of users saw a refund twice. Some spent it, because the payment check used the same view. Fix: event id stored in a processed_events table in the same transaction as the balance update; payments validated against the ledger; nightly rebuild-and-compare job that alerts on drift. Lesson: incremental views need idempotency, decisions need the source of truth, and drift needs a detector.

    12. Interview Corner¶

    Q1. What is a materialized view?

    A stored, precomputed query result that is refreshed periodically or incrementally.

    Q2. View vs materialized view in SQL?

    A view is a saved query run every time; a materialized view stores the result.

    Q3. Why is it stale?

    It only changes when refreshed or when updates are applied.

    Q4. When would you use one?

    For expensive, frequently repeated queries like dashboards and reports.

    Q5. What happens if it gets corrupted?

    Rebuild it from the source data; it's derived.

    Q1. Full vs incremental refresh?

    Full recomputes everything (simple, expensive); incremental applies changes (fresh, needs idempotency and ordering).

    Q2. How do you refresh without blocking readers in PostgreSQL?

    REFRESH MATERIALIZED VIEW CONCURRENTLY with a unique index, or build a new table and swap.

    Q3. How do you handle duplicate events?

    Store processed event ids or per-key versions, updated in the same transaction as the view.

    Q4. Materialized view vs cache?

    A view is built proactively and query-shaped; a cache-aside entry is filled on demand and mirrors the source.

    Q5. How do views help with database-per-service?

    They let one service hold a read-only, denormalized copy of others' data built from their events, avoiding synchronous joins.

    Q1. "Design a seller dashboard for 1M sellers with near-real-time numbers."

    Order events → Kafka (partition by seller) → stream processor aggregating per seller per day → key-value store; lag SLO of 30 s; nightly batch rebuild for correction.

    Q2. "How do you change a view's schema safely?"

    Build v2 alongside v1 from retained history, compare, switch reads behind a flag, then retire v1.

    Q3. "Events from three services arrive out of order."

    Each source owns its own fields; track per-source versions; ignore older versions; never let one source overwrite another's fields.

    Q4. "How do you detect drift?"

    Periodic rebuild-and-compare (or checksums per partition) against the source of truth, alerting on differences.

    Q5. "When not to use one?"

    Rapidly changing data needing strong consistency (stock reservations, balances for authorisation), or queries already cheap with an index.

    Problem: A live balance view silently missed one event months ago. Write a job that rebuilds the view from the ledger and reports which accounts drifted.

    Solution 
    package com.handbook.microservices.materializedview.rebuild;

import com.handbook.microservices.materializedview.balances.BalanceView;
import com.handbook.microservices.materializedview.balances.BalanceView.LedgerEntry;

import java.util.ArrayList;
import java.util.List;
import java.util.Map;
import java.util.TreeMap;

/** Coding challenge: detect drift by rebuilding the view from the source of truth and comparing. */
public class RebuildCheckDemo {

    public static void main(String[] args) {
        System.out.println("=== Challenge: Rebuild and Compare to Catch View Drift ===");
        List<LedgerEntry> ledger = new ArrayList<>();
        for (int i = 0; i < 1_000; i++) {
            ledger.add(new LedgerEntry("e" + i, "SB-" + (i % 3), i % 2 == 0 ? 10_000 : -4_000));
        }

        BalanceView live = new BalanceView();
        for (LedgerEntry e : ledger) {
            if (!e.eventId().equals("e501")) { // a consumer crash skipped one event months ago
                live.apply(e);
            }
        }

        BalanceView rebuilt = new BalanceView();
        ledger.forEach(rebuilt::apply); // replay from the beginning into a fresh view

        Map<String, String> drift = new TreeMap<>();
        rebuilt.all().forEach((acc, expected) -> {
            long actual = live.balance(acc);
            if (actual != expected) {
                drift.put(acc, "live=" + actual + " expected=" + expected);
            }
        });
        System.out.println("Accounts checked: " + rebuilt.all().size() + ", drifted: " + drift);
        System.out.println("Fix: swap in the rebuilt view (blue/green tables), then alert on any future drift.");
    }
}

    Output:

    === Challenge: Rebuild and Compare to Catch View Drift ===
Accounts checked: 3, drifted: {SB-0=live=1006000 expected=1002000}
Fix: swap in the rebuilt view (blue/green tables), then alert on any future drift.

    Key points to say: the ledger is the source of truth, so the view can be replayed into a fresh copy and compared; swap tables to fix; run the comparison on a schedule and alert. At scale, compare per-partition checksums instead of every row.

    13. Quick Revision Card¶

    Remember in 30 seconds

    • Precomputed, query-shaped, disposable copy of data.
    • Full refresh (simple) vs incremental (fresh, idempotent).
    • Combine services/shards without runtime joins.
    • Stale by design: display, don't decide.
    • Keep history so you can rebuild and compare.
