    Advanced Data Microservices

    CQRS (Command Query Responsibility Segregation)¶

    🔴 Advanced Microservices Interview frequency ⭐⭐⭐⭐

    TL;DR

    CQRS splits a system into a write side (commands that enforce business rules) and one or more read sides (query models shaped for specific screens). The read models are updated from the write side's events, often asynchronously. Each side can use its own model, schema, database and scaling. The price is eventual consistency and more moving parts.

    1. Intent & Problem It Solves¶

    The problem in plain English: a single normalized products table must enforce pricing rules on writes and answer "cheapest organic fruit in Bengaluru, sorted by discount, with ratings" in 20 ms for millions of shoppers. The write model wants normalization and invariants; the read side wants denormalized, pre-joined, indexed data. One model serves both badly. In microservices it's worse: the data for one screen lives in several services.

    Definition (Greg Young, building on Bertrand Meyer's CQS):

    CQRS is simply the creation of two objects where there was previously only one. The separation occurs based upon whether the methods are a command or a query.

    Levels of CQRS:

    1. Separate command and query classes in one service (same DB).
    2. Separate read tables/views in the same DB (materialized views).
    3. Separate read databases (Elasticsearch, Redis, Cassandra) fed by events, which is the microservices form.

    2. Real-World Analogy¶

    A restaurant's kitchen and menu board

    Orders go into the kitchen (write side), which enforces the rules: no dish without ingredients. The menu board (read side) is a separate, simplified display, updated when the kitchen runs out of something. For a few seconds the board may still show "Mango lassi" after the last mango is used (eventual consistency), and that's acceptable.

    3. Structure¶

    flowchart LR
    U[Client] -->|commands| CMD[Command side<br/>validates, enforces rules]
    CMD --> W[(Write store)]
    CMD -->|events| BUS[[Event stream]]
    BUS --> P1[Projector] --> R1[(Search view<br/>Elasticsearch)]
    BUS --> P2[Projector] --> R2[(Dashboard view<br/>Redis/SQL)]
    U -->|queries| Q[Query side] --> R1
    Q --> R2
    Participant Responsibility
    Command handler / write model Validates commands, enforces invariants, emits events
    Event stream Carries changes (outbox + Kafka, or an event store)
    Projector Updates read models from events; idempotent; tracks a checkpoint
    Read model Denormalized, query-shaped, disposable (rebuildable from events)

    4. Naive Approach (Without the Pattern)¶

    -- Every page view runs this against the transactional database
SELECT p.*, AVG(r.stars), MIN(o.price), s.qty FROM products p
JOIN reviews r ON ... JOIN offers o ON ... JOIN stock s ON ...
WHERE p.category = 'fruit' GROUP BY ... ORDER BY MIN(o.price) LIMIT 20;
-- Reads slow down writes (locks, CPU); indexes for reads slow inserts;
-- and in microservices, reviews/offers/stock aren't even in this database.

    5. Three Real-World Examples¶

    Example 1: Catalog Writes vs. Search Reads (Grocery)¶

    Scenario: The write side validates product commands (no duplicates; price cuts over 50% need approval). The search view keeps denormalized rows answering "cheapest in a category". A price change is visible in search only after the projector catches up, a stale read that the demo shows on purpose.

    Design:

    sequenceDiagram
    participant A as Admin
    participant C as CatalogCommands
    participant V as CatalogSearchView
    participant S as Shopper
    A->>C: changePrice(APPLE, ₹59)
    C-->>V: PriceChanged (queued)
    S->>V: cheapest(fruit) → old price (stale)
    V->>V: catchUp()
    S->>V: cheapest(fruit) → new price

    Full Code:

    package com.handbook.microservices.cqrs.catalog;

import java.util.HashMap;
import java.util.Map;
import java.util.function.Consumer;

/**
 * The write side: validates commands against the current state and emits events.
 * It is optimised for correctness, not for queries; it can't even list products by category.
 */
public final class CatalogCommands {

    public sealed interface Event permits ProductAdded, PriceChanged {
    }

    public record ProductAdded(String sku, String name, String category, long pricePaise) implements Event {
    }

    public record PriceChanged(String sku, long oldPaise, long newPaise) implements Event {
    }

    private final Map<String, Long> prices = new HashMap<>();
    private final Consumer<Event> publish;

    public CatalogCommands(Consumer<Event> publish) {
        this.publish = publish;
    }

    public void addProduct(String sku, String name, String category, long pricePaise) {
        if (prices.containsKey(sku)) {
            throw new IllegalArgumentException(sku + " already exists");
        }
        prices.put(sku, pricePaise);
        publish.accept(new ProductAdded(sku, name, category, pricePaise));
    }

    public void changePrice(String sku, long newPaise) {
        Long old = prices.get(sku);
        if (old == null) {
            throw new IllegalArgumentException("unknown " + sku);
        }
        if (newPaise < old / 2) { // (1)!
            throw new IllegalArgumentException("price cut over 50% needs approval");
        }
        prices.put(sku, newPaise);
        publish.accept(new PriceChanged(sku, old, newPaise));
    }
}
    1. Invariants live on the write side only. The read side never needs to know about approval rules.
    package com.handbook.microservices.cqrs.catalog;

import com.handbook.microservices.cqrs.catalog.CatalogCommands.Event;
import com.handbook.microservices.cqrs.catalog.CatalogCommands.PriceChanged;
import com.handbook.microservices.cqrs.catalog.CatalogCommands.ProductAdded;

import java.util.ArrayDeque;
import java.util.Comparator;
import java.util.HashMap;
import java.util.List;
import java.util.Map;
import java.util.Queue;

/**
 * The read side: a denormalised view shaped for "cheapest products in a category" (think an
 * Elasticsearch index or a Redis sorted set). It is updated asynchronously from events.
 */
public final class CatalogSearchView {

    public record Row(String sku, String name, String category, long pricePaise) {
    }

    private final Map<String, Row> rows = new HashMap<>();
    private final Queue<Event> inbox = new ArrayDeque<>();

    public void enqueue(Event event) { // (1)!
        inbox.add(event);
    }

    /** The projector: applies queued events. In production this runs continuously off Kafka. */
    public int catchUp() {
        int applied = 0;
        for (Event e; (e = inbox.poll()) != null; applied++) {
            switch (e) { // (2)!
                case ProductAdded a -> rows.put(a.sku(), new Row(a.sku(), a.name(), a.category(), a.pricePaise()));
                case PriceChanged p -> rows.computeIfPresent(p.sku(),
                        (k, r) -> new Row(r.sku(), r.name(), r.category(), p.newPaise()));
            }
        }
        return applied;
    }

    public List<String> cheapest(String category, int limit) { // (3)!
        return rows.values().stream()
                .filter(r -> r.category().equals(category))
                .sorted(Comparator.comparingLong(Row::pricePaise))
                .limit(limit)
                .map(r -> r.name() + " ₹" + r.pricePaise() / 100)
                .toList();
    }
}
    1. Events arrive asynchronously (here, an inbox queue; in production, a Kafka consumer).
    2. A sealed event hierarchy + pattern-matching switch: the compiler checks every event type is handled.
    3. The query is shaped for one screen; a real implementation would use a sorted index.
    package com.handbook.microservices.cqrs.catalog;

public class CatalogCqrsDemo {

    public static void main(String[] args) {
        var view = new CatalogSearchView();
        var commands = new CatalogCommands(view::enqueue);

        System.out.println("=== Grocery: catalog writes vs. search reads ===");
        commands.addProduct("MANGO-1KG", "Alphonso mangoes 1 kg", "fruit", 39_900);
        commands.addProduct("BANANA-12", "Robusta bananas x12", "fruit", 6_900);
        commands.addProduct("APPLE-1KG", "Shimla apples 1 kg", "fruit", 9_900);
        System.out.println("applied " + view.catchUp() + " events -> cheapest fruit: " + view.cheapest("fruit", 2));

        commands.changePrice("APPLE-1KG", 5_900); // apple season sale
        System.out.println("Price changed, projection not yet caught up -> " + view.cheapest("fruit", 2) + "  (stale read)");
        System.out.println("applied " + view.catchUp() + " event  -> cheapest fruit: " + view.cheapest("fruit", 2));

        try {
            commands.changePrice("MANGO-1KG", 9_900);
        } catch (IllegalArgumentException e) {
            System.out.println("Command rejected by the write model: " + e.getMessage());
        }
    }
}

    Output:

    === Grocery: catalog writes vs. search reads ===
applied 3 events -> cheapest fruit: [Robusta bananas x12 ₹69, Shimla apples 1 kg ₹99]
Price changed, projection not yet caught up -> [Robusta bananas x12 ₹69, Shimla apples 1 kg ₹99]  (stale read)
applied 1 event  -> cheapest fruit: [Shimla apples 1 kg ₹59, Robusta bananas x12 ₹69]
Command rejected by the write model: price cut over 50% needs approval

    Why CQRS here:

    • Reads outnumber writes about 1000:1 in catalogs; the read side scales independently (search cluster, caches).
    • Write rules stay simple and consistent; search shape changes don't touch them.
    • The stale-read window is acceptable for browsing; checkout re-validates price on the write side.

    Example 2: One Write Model, Two Read Models (Banking)¶

    Scenario: The account write model enforces "no overdraft". Two projections serve two screens: a balance tile (one key lookup) and a mini statement (last 3 transactions, pre-formatted). Here they're updated synchronously in the same process, which shows CQRS doesn't require separate databases or async messaging.

    Full Code:

    package com.handbook.microservices.cqrs.banking;

import java.util.ArrayDeque;
import java.util.ArrayList;
import java.util.Deque;
import java.util.HashMap;
import java.util.List;
import java.util.Map;
import java.util.function.Consumer;

/** One write model, two read models, each shaped for one screen. */
public final class AccountCqrs {

    public record Transacted(String account, String description, long amountPaise, long balanceAfter) {
    }

    /** Write side: enforces the no-overdraft rule. */
    public static final class AccountCommands {
        private final Map<String, Long> balances = new HashMap<>();
        private final List<Consumer<Transacted>> projections = new ArrayList<>();

        public void subscribe(Consumer<Transacted> projection) {
            projections.add(projection);
        }

        public void deposit(String account, long paise, String description) {
            apply(account, paise, description);
        }

        public void withdraw(String account, long paise, String description) {
            if (balances.getOrDefault(account, 0L) < paise) { // (1)!
                throw new IllegalStateException("insufficient funds");
            }
            apply(account, -paise, description);
        }

        private void apply(String account, long delta, String description) {
            long after = balances.merge(account, delta, Long::sum);
            Transacted event = new Transacted(account, description, delta, after);
            projections.forEach(p -> p.accept(event));
        }
    }

    /** Read model 1: the balance tile on the app home screen (one key lookup). */
    public static final class BalanceView implements Consumer<Transacted> {
        private final Map<String, Long> balances = new HashMap<>();

        @Override
        public void accept(Transacted e) {
            balances.put(e.account(), e.balanceAfter());
        }

        public String balance(String account) {
            return String.format("₹%,.2f", balances.getOrDefault(account, 0L) / 100.0);
        }
    }

    /** Read model 2: the last N transactions, already formatted for the mini-statement. */
    public static final class MiniStatementView implements Consumer<Transacted> {
        private final Map<String, Deque<String>> lines = new HashMap<>();
        private final int size;

        public MiniStatementView(int size) {
            this.size = size;
        }

        @Override
        public void accept(Transacted e) {
            Deque<String> d = lines.computeIfAbsent(e.account(), k -> new ArrayDeque<>());
            d.addFirst(String.format("%-14s %+,10.2f", e.description(), e.amountPaise() / 100.0)); // (2)!
            if (d.size() > size) {
                d.removeLast();
            }
        }

        public List<String> statement(String account) {
            return List.copyOf(lines.getOrDefault(account, new ArrayDeque<>()));
        }
    }
}
    1. The rule is checked on the write side against authoritative state.
    2. The read model stores data already formatted for its screen.
    package com.handbook.microservices.cqrs.banking;

import com.handbook.microservices.cqrs.banking.AccountCqrs.AccountCommands;
import com.handbook.microservices.cqrs.banking.AccountCqrs.BalanceView;
import com.handbook.microservices.cqrs.banking.AccountCqrs.MiniStatementView;

public class AccountCqrsDemo {

    public static void main(String[] args) {
        var commands = new AccountCommands();
        var balance = new BalanceView();
        var statement = new MiniStatementView(3);
        commands.subscribe(balance);
        commands.subscribe(statement);

        System.out.println("=== Banking: one write model, two read models ===");
        commands.deposit("ACC-1", 5_000_000, "Salary");
        commands.withdraw("ACC-1", 1_250_000, "Rent");
        commands.withdraw("ACC-1", 89_900, "Groceries");
        commands.withdraw("ACC-1", 45_000, "Electricity");
        try {
            commands.withdraw("ACC-1", 9_999_900, "New laptop");
        } catch (IllegalStateException e) {
            System.out.println("Withdraw ₹99,999 rejected: " + e.getMessage());
        }
        System.out.println("Balance tile   : " + balance.balance("ACC-1"));
        System.out.println("Mini statement :");
        statement.statement("ACC-1").forEach(line -> System.out.println("  " + line));
    }
}

    Output:

    === Banking: one write model, two read models ===
Withdraw ₹99,999 rejected: insufficient funds
Balance tile   : ₹36,151.00
Mini statement :
  Electricity       -450.00
  Groceries         -899.00
  Rent           -12,500.00

    Why CQRS here:

    • The most frequent queries (balance, mini statement) become O(1) lookups.
    • New screens = new projections, without changing the write model.
    • Synchronous projections give read-your-writes where the UX needs it.

    Example 3: Patient Dashboard from Three Services (Healthcare)¶

    Scenario: Appointments, lab results and prescriptions are owned by three services. The doctor's dashboard needs all three, instantly, during a consultation. A projection subscribes to events from all three and maintains one denormalized row per patient: next appointment, abnormal labs only, and active medications.

    Full Code:

    package com.handbook.microservices.cqrs.healthcare;

import java.util.ArrayList;
import java.util.HashMap;
import java.util.List;
import java.util.Map;

/**
 * A read model fed by events from three services (appointments, lab, pharmacy). The doctor's
 * dashboard becomes one key lookup instead of three remote calls and an in-memory join.
 */
public final class PatientDashboardView {

    public sealed interface ClinicalEvent permits AppointmentBooked, LabResultReady, PrescriptionIssued, PrescriptionEnded {
        String patientId();
    }

    public record AppointmentBooked(String patientId, String when, String doctor) implements ClinicalEvent {
    }

    public record LabResultReady(String patientId, String test, double value, double upperLimit) implements ClinicalEvent {
    }

    public record PrescriptionIssued(String patientId, String drug) implements ClinicalEvent {
    }

    public record PrescriptionEnded(String patientId, String drug) implements ClinicalEvent {
    }

    public record Dashboard(String nextAppointment, List<String> abnormalLabs, List<String> activeMedications) {
    }

    private static final class Row {
        String nextAppointment = "none";
        final List<String> abnormalLabs = new ArrayList<>();
        final List<String> meds = new ArrayList<>();
    }

    private final Map<String, Row> rows = new HashMap<>();

    public void on(ClinicalEvent event) {
        Row row = rows.computeIfAbsent(event.patientId(), k -> new Row());
        switch (event) {
            case AppointmentBooked a -> row.nextAppointment = a.when() + " with " + a.doctor();
            case LabResultReady l -> {
                if (l.value() > l.upperLimit()) { // (1)!
                    row.abnormalLabs.add(l.test() + " " + l.value() + " (max " + l.upperLimit() + ")");
                }
            }
            case PrescriptionIssued p -> row.meds.add(p.drug());
            case PrescriptionEnded p -> row.meds.remove(p.drug());
        }
    }

    public Dashboard dashboard(String patientId) { // (2)!
        Row r = rows.getOrDefault(patientId, new Row());
        return new Dashboard(r.nextAppointment, List.copyOf(r.abnormalLabs), List.copyOf(r.meds));
    }
}
    1. The projection does work once, at write time (filtering abnormal results), not on every dashboard load.
    2. The query is a single lookup, with no calls to three services during the consultation.
    package com.handbook.microservices.cqrs.healthcare;

import com.handbook.microservices.cqrs.healthcare.PatientDashboardView.AppointmentBooked;
import com.handbook.microservices.cqrs.healthcare.PatientDashboardView.LabResultReady;
import com.handbook.microservices.cqrs.healthcare.PatientDashboardView.PrescriptionEnded;
import com.handbook.microservices.cqrs.healthcare.PatientDashboardView.PrescriptionIssued;

public class PatientDashboardDemo {

    public static void main(String[] args) {
        var view = new PatientDashboardView();

        System.out.println("=== Healthcare: doctor's dashboard built from three services' events ===");
        view.on(new PrescriptionIssued("PAT-5", "Metformin 500 mg"));        // pharmacy service
        view.on(new PrescriptionIssued("PAT-5", "Amoxicillin 250 mg"));      // pharmacy service
        view.on(new LabResultReady("PAT-5", "HbA1c %", 7.9, 6.5));           // lab service
        view.on(new LabResultReady("PAT-5", "TSH mIU/L", 2.1, 4.5));         // lab service (normal)
        view.on(new AppointmentBooked("PAT-5", "2026-10-20 10:30", "Dr. Iyer")); // appointments service
        view.on(new PrescriptionEnded("PAT-5", "Amoxicillin 250 mg"));       // course finished

        var d = view.dashboard("PAT-5");
        System.out.println("Next appointment  : " + d.nextAppointment());
        System.out.println("Abnormal labs     : " + d.abnormalLabs());
        System.out.println("Active medication : " + d.activeMedications());
        System.out.println("Unknown patient   : " + view.dashboard("PAT-404"));
    }
}

    Output:

    === Healthcare: doctor's dashboard built from three services' events ===
Next appointment  : 2026-10-20 10:30 with Dr. Iyer
Abnormal labs     : [HbA1c % 7.9 (max 6.5)]
Active medication : [Metformin 500 mg]
Unknown patient   : Dashboard[nextAppointment=none, abnormalLabs=[], activeMedications=[]]

    Why CQRS here:

    • Cross-service queries without API composition at request time (faster and more available).
    • The dashboard keeps working if the lab service is down (it shows the last known data).
    • In a clinical setting, show "last updated" timestamps so staleness is visible.

import com.handbook.microservices.cqrs.catalog.CatalogCommands;

import static org.assertj.core.api.Assertions.assertThat;

class CqrsTest {

    @Test
    void readModelIsEventuallyConsistent() {
        var view = new CatalogSearchView();
        var commands = new CatalogCommands(view::enqueue);
        commands.addProduct("A", "Apple", "fruit", 100);
        assertThat(view.cheapest("fruit", 5)).isEmpty();

        var p = new TopSellersProjection();

    }
}

    // Spring: a projector as a Kafka listener (reference)
@KafkaListener(topics = "catalog.events", groupId = "search-projection")
public void on(ProductEvent event, @Header(KafkaHeaders.OFFSET) long offset) {
    searchRepository.apply(event);          // idempotent upsert into Elasticsearch

    Variation Notes
    Same DB, separate models Command and query services/classes over the same tables; simplest
    Materialized views DB-maintained read models (PostgreSQL materialized views, Oracle MVs)
    Separate read stores Elasticsearch for search, Redis for counters, Cassandra for timelines
    CQRS + Event Sourcing Write side stores events; projections build every read model (Axon)
    GraphQL on read models Query side exposed through GraphQL

    Handling eventual consistency in the UI: return the new version from the command and poll the read model until it catches up; use optimistic UI updates; or route the user's own reads to the write side for a few seconds ("read-your-writes").

    7. Where It Lives in Real Frameworks¶

    Where CQRS
    Axon Framework @CommandHandler, @EventHandler projections, @QueryHandler
    Spring Data Separate repositories / read-only replicas for queries
    Kafka Streams / ksqlDB Materialized views from event streams
    Elasticsearch + CDC Common read model for search

    8. Pros, Cons & Trade-offs¶

    ✅ Pros ❌ Cons
    Read and write sides scale and evolve independently Eventual consistency visible to users
    Fast, screen-shaped queries More infrastructure: event pipeline, projectors, read stores
    Cross-service queries without runtime joins Projection bugs require replays/rebuilds
    New read models added by replaying events Overkill for simple CRUD

    9. Pitfalls & Anti-Patterns¶

    CQRS everywhere

    Most screens in most services are fine with simple CRUD. Apply CQRS to the parts with real read/write asymmetry or cross-service queries.

    Validating commands against the read model

    The read model is stale. "Is this username taken?" checked against a projection lets duplicates through. Enforce invariants on the write side (unique constraints).

    Non-idempotent projectors

    Events are redelivered. count = count + 1 on redelivery double counts. Track checkpoints or event IDs (see the coding challenge).

    Ignoring rebuild time

    If rebuilding a projection from 2 billion events takes 3 days, schema changes become impossible. Plan snapshots, parallel replays and blue/green projections.

    10. Senior / Architect Deep Dive (10–15 yrs)¶

    Read models are caches with a contract. They're derived and disposable. Version them (search_v2), build the new one alongside the old by replaying, switch reads, then drop the old one: blue/green projections.

    Consistency budgets. Agree on acceptable staleness per screen (search: seconds; balance after transfer: read-your-writes; analytics: minutes). Monitor projection lag (event time vs. applied time) and alert on it.

    Ordering and partitioning. Projectors usually need per-aggregate ordering: key events by aggregate ID, process partitions independently, and handle cross-aggregate projections (e.g. totals) carefully.

    Production checklist¶

    • Clear reason for CQRS (read/write asymmetry, cross-service views), not fashion.
    • Events published reliably (outbox) and keyed by aggregate.
    • Projectors idempotent, with checkpoints; dead-letter handling.
    • Projection lag metrics + alerts; "last updated" in sensitive UIs.
    • Rebuild procedure tested (blue/green projections).
    • Commands validated only against the write model.

    Explain it in 2 minutes (system design round)¶

    "Product writes go through the catalog service, which enforces pricing and stock rules in PostgreSQL and publishes events via the outbox. A projector consumes them and updates an Elasticsearch index shaped for search and listing pages, which take 99% of traffic and scale separately. Read models are rebuildable from Kafka (with compaction) or a full export. Staleness is a few hundred milliseconds; checkout re-validates price and stock against the write side, so stale reads can't cause wrong charges. We monitor projection lag."

    War story: the leaderboard that counted twice

    A fantasy-sports app built its leaderboard projection with points += event.points. After a Kafka consumer-group rebalance, a batch of events was reprocessed, and during the final minutes of a big match, thousands of users saw inflated scores. Prizes were almost paid on wrong rankings. Fix: the projection stores the last applied offset per partition in the same transaction as the score update and skips already-applied events; a nightly job recomputes scores from the event log and compares. Lesson: a projector must be idempotent before it's fast.

    CQRS Event Sourcing Cache-aside API Composition

    12. Interview Corner¶

    Q1. What is CQRS?

    Separating the model that changes data (commands) from the model that reads data (queries).

    Q2. What's the difference between a command and a query?

    A command changes state and returns little or nothing; a query returns data and changes nothing.

    Q3. Does CQRS require two databases?

    No. It can be separate classes on one database; separate read stores are an option for scale.

    Q4. What is eventual consistency?

    After a write, read models are updated shortly afterwards, so reads may briefly return old data.

    Q5. Is CQRS the same as event sourcing?

    No. They're often used together, but CQRS works with a normal database on the write side.

    Q1. How are read models kept up to date?

    A projector consumes events (from Kafka, via the outbox or CDC) and updates the read store idempotently.

    Q2. How do you handle a user who doesn't see their own change?

    Read-your-writes techniques: return the new data from the command, poll until the read model's version catches up, optimistic UI, or read from the write side briefly.

    Q3. How do you add a new read model later?

    Create a new projector and replay historical events (event store, compacted topic, or a bootstrap from the write DB), then switch reads to it.

    Q4. Where are business rules validated?

    Only on the write side, against authoritative state.

    Q5. When is CQRS a bad idea?

    Simple CRUD domains, small teams, or when users can't tolerate any staleness and there's no read/write asymmetry.

    Q1. "Design the product listing for an e-commerce site with 50M products and 100k QPS reads."

    Write side per domain (catalog, pricing, inventory) → outbox → Kafka → projector into a search cluster with denormalized documents; CDN/edge caching for hot listings; projection lag SLO; checkout re-validates against the write side.

    Q2. "How do you rebuild a projection without downtime?"

    Blue/green: build v2 from the start of the log while v1 serves; when v2 catches up to live, switch the query side; then retire v1.

    Q3. "Projections need data from multiple aggregates. Ordering issues?"

    Events for different aggregates may arrive out of order across partitions. Design projections to tolerate it (upserts with versions, buffering, or reprocessing on missing references).

    Q4. "How does SAP S/4HANA's approach relate to CQRS?"

    S/4HANA moved many aggregates and indexes into in-memory columnar tables and computes analytics on the fly, which reduces the need for separate read models. CQRS remains useful across service boundaries.

    Q5. "What metrics prove CQRS is working?"

    Read p99 latency, write throughput unaffected by read load, projection lag distribution, rebuild duration, and error/dead-letter rates in projectors.

    Problem: Months after launch, product asks for a "top sellers" screen. Build a new projection by replaying stored OrderPlaced events, then keep it live. It must ignore redelivered events.

    Solution 
    package com.handbook.microservices.cqrs.rebuild;

import java.util.HashMap;
import java.util.List;
import java.util.Map;

/**
 * Coding challenge: product asks for a new "top sellers this week" screen months after launch.
 * Because the read models are derived data, we build a new projection and replay the stored
 * event history into it. No migration of the write model is needed.
 */
public final class TopSellersProjection {

    public record OrderPlaced(long sequence, String sku, int qty) {
    }

    private final Map<String, Integer> unitsBySku = new HashMap<>();
    private long lastSequence; // checkpoint: where to resume after a restart

    public void apply(OrderPlaced e) {
        if (e.sequence() <= lastSequence) {
            return; // already applied (replays and redeliveries are safe)
        }
        unitsBySku.merge(e.sku(), e.qty(), Integer::sum);
        lastSequence = e.sequence();
    }

    public List<String> top(int n) {
        return unitsBySku.entrySet().stream()
                .sorted(Map.Entry.<String, Integer>comparingByValue().reversed().thenComparing(Map.Entry.comparingByKey()))
                .limit(n)
                .map(e -> e.getKey() + "=" + e.getValue())
                .toList();
    }

    public long checkpoint() {
        return lastSequence;
    }
}

    package com.handbook.microservices.cqrs.rebuild;

import com.handbook.microservices.cqrs.rebuild.TopSellersProjection.OrderPlaced;

import java.util.List;

public class RebuildDemo {

    public static void main(String[] args) {
        List<OrderPlaced> history = List.of(
                new OrderPlaced(1, "MANGO-1KG", 2), new OrderPlaced(2, "RICE-5KG", 1),
                new OrderPlaced(3, "MANGO-1KG", 3), new OrderPlaced(4, "MILK-1L", 6),
                new OrderPlaced(5, "RICE-5KG", 1), new OrderPlaced(6, "MILK-1L", 2));

        System.out.println("=== Challenge: add a new read model by replaying history ===");
        var topSellers = new TopSellersProjection();
        history.forEach(topSellers::apply);
        System.out.println("Rebuilt from " + history.size() + " stored events -> top 2: " + topSellers.top(2)
                + ", checkpoint=" + topSellers.checkpoint());

        System.out.println("Live events continue; event 6 is redelivered by the broker:");
        topSellers.apply(new OrderPlaced(6, "MILK-1L", 2));
        topSellers.apply(new OrderPlaced(7, "MANGO-1KG", 4));
        System.out.println("top 2: " + topSellers.top(2) + ", checkpoint=" + topSellers.checkpoint());
    }
}

    Output:

    === Challenge: add a new read model by replaying history ===
Rebuilt from 6 stored events -> top 2: [MILK-1L=8, MANGO-1KG=5], checkpoint=6
Live events continue; event 6 is redelivered by the broker:
top 2: [MANGO-1KG=9, MILK-1L=8], checkpoint=7

    Key points to say: the checkpoint (last applied sequence) makes replays and redeliveries safe, and lets a restarted projector resume. Persist it atomically with the view's data. With Kafka, use offsets per partition.

    13. Quick Revision Card¶

    Remember in 30 seconds

    • Commands (write, rules) vs. queries (read, shaped views).
    • Read models updated from events by idempotent projectors.
    • Eventual consistency; validate commands only on the write side.
    • Read models are disposable: replay to rebuild.
    • Use where reads and writes differ a lot, not everywhere.
