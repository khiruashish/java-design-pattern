    Intermediate Structural

    Decorator¶

    🟡 Intermediate Structural Interview frequency ⭐⭐⭐⭐⭐

    TL;DR

    Decorator wraps an object in another object with the same interface, adding behavior before or after delegating to it. Wrappers can be stacked. Use it to add cross-cutting features (logging, retries, caching, encryption, pricing rules) without subclassing and without touching the original class.

    1. Intent & Problem It Solves¶

    The problem in plain English: a payment processor needs logging, retries and fraud checks, but not always all of them, and not always in the same order. Subclassing gives you LoggingRetryingFraudCheckedProcessor, LoggingProcessor, RetryingFraudCheckedProcessor... one subclass per combination. With decorators you write each feature once and compose them at runtime.

    Formal definition (GoF):

    Attach additional responsibilities to an object dynamically. Decorators provide a flexible alternative to subclassing for extending functionality.

    2. Real-World Analogy¶

    Dressing for the weather

    You're still you. On a cold day you put on a sweater, then a jacket, then a raincoat. Each layer adds something (warmth, wind protection, waterproofing) and you can add or remove layers in any combination. Nobody needs to manufacture a "you-with-sweater-and-raincoat" person.

    3. Structure¶

    classDiagram
    class Component {
        <<interface>>
        +operation()
    }
    class ConcreteComponent {
        +operation()
    }
    class Decorator {
        <<abstract>>
        #Component inner
        +operation()
    }
    class DecoratorA {
        +operation()
    }
    class DecoratorB {
        +operation()
    }
    Component <|.. ConcreteComponent
    Component <|.. Decorator
    Decorator o--> Component : wraps
    Decorator <|-- DecoratorA
    Decorator <|-- DecoratorB
    Participant Responsibility
    Component The interface clients use (PaymentProcessor)
    Concrete component The real work (FlakyGatewayProcessor)
    Decorator Implements Component and holds a Component; forwards by default
    Concrete decorators Add behavior before/after forwarding, or instead of it (RetryingProcessor, FraudCheckProcessor)

    The key trick: a decorator is-a Component and has-a Component, so decorators can wrap decorators.

    4. Naive Approach (Without the Pattern)¶

    class PaymentProcessor { String pay(...) { /* gateway call */ } }
class LoggingPaymentProcessor extends PaymentProcessor { ... }
class RetryingPaymentProcessor extends PaymentProcessor { ... }
class LoggingRetryingPaymentProcessor extends RetryingPaymentProcessor { ... }       // logging copied
class FraudLoggingRetryingPaymentProcessor extends LoggingRetryingPaymentProcessor { ... }
// 3 features = up to 7 subclasses; a 4th feature doubles it. Order is fixed at compile time.
    • Subclass explosion (2ⁿ combinations).
    • Fixed at compile time: can't turn retries on for one merchant only.
    • Code duplication of each feature across subclasses.

    5. Three Real-World Examples¶

    Example 1: Stacking Payment Concerns (Payments)¶

    Scenario: A payment gateway call sometimes times out under load. The payments team wants fraud screening (block orders above a limit before calling the gateway at all), retries (up to 3 attempts on timeouts), and logging of every attempt for incident analysis. Different merchants get different stacks (some have no fraud rule), so the composition must be decided at runtime, from configuration.

    Design:

    flowchart LR
    C[Checkout] --> F[FraudCheckProcessor<br/>limit INR 50,000]
    F --> R[RetryingProcessor<br/>3 attempts]
    R --> L[LoggingProcessor]
    L --> G[FlakyGatewayProcessor<br/>real gateway call]

    Full Code:

    package com.handbook.structural.decorator.payments;

/** Base decorator: implements the interface and forwards to the wrapped processor. */
public abstract class PaymentDecorator implements PaymentProcessor {

    protected final PaymentProcessor inner; // (1)!

    protected PaymentDecorator(PaymentProcessor inner) {
        this.inner = inner;
    }

    @Override
    public String pay(String orderId, int amountInr) {
        return inner.pay(orderId, amountInr);
    }
}
    1. The decorator implements the interface and holds an instance of it. Because the field's type is the interface, it can hold the real processor or another decorator.
    package com.handbook.structural.decorator.payments;

public class FraudCheckProcessor extends PaymentDecorator {

    private final int limitInr;

    public FraudCheckProcessor(PaymentProcessor inner, int limitInr) {
        super(inner);
        this.limitInr = limitInr;
    }

    @Override
    public String pay(String orderId, int amountInr) {
        if (amountInr > limitInr) {
            return "BLOCKED " + orderId + " (fraud rule: amount > INR " + limitInr + ")"; // (1)!
        }
        return super.pay(orderId, amountInr);
    }
}
    1. A decorator can short-circuit: it answers without calling inner at all. That's why fraud screening sits outermost: blocked orders never reach the gateway.
    package com.handbook.structural.decorator.payments;

public class RetryingProcessor extends PaymentDecorator {

    private final int maxAttempts;

    public RetryingProcessor(PaymentProcessor inner, int maxAttempts) {
        super(inner);
        this.maxAttempts = maxAttempts;
    }

    @Override
    public String pay(String orderId, int amountInr) {
        for (int attempt = 1; ; attempt++) {
            try {
                return super.pay(orderId, amountInr);
            } catch (IllegalStateException e) {
                if (attempt == maxAttempts) {
                    throw e;
                }
                System.out.println("  [retry] attempt " + attempt + " failed (" + e.getMessage() + "), retrying");
            }
        }
    }
}

    package com.handbook.structural.decorator.payments;

public class LoggingProcessor extends PaymentDecorator {

    public LoggingProcessor(PaymentProcessor inner) {
        super(inner);
    }

    @Override
    public String pay(String orderId, int amountInr) {
        System.out.println("  [log] -> pay " + orderId + " INR " + amountInr);
        try {
            String result = super.pay(orderId, amountInr);
            System.out.println("  [log] <- " + result);
            return result;
        } catch (RuntimeException e) {
            System.out.println("  [log] <- FAILED: " + e.getMessage());
            throw e;
        }
    }
}

    package com.handbook.structural.decorator.payments;

public interface PaymentProcessor {

    String pay(String orderId, int amountInr);
}

    package com.handbook.structural.decorator.payments;

/** Concrete component: the real gateway call. Fails the first N attempts to simulate timeouts. */
public class FlakyGatewayProcessor implements PaymentProcessor {

    private int failuresLeft;

    public FlakyGatewayProcessor(int failuresBeforeSuccess) {
        this.failuresLeft = failuresBeforeSuccess;
    }

    @Override
    public String pay(String orderId, int amountInr) {
        if (failuresLeft-- > 0) {
            throw new IllegalStateException("gateway timeout");
        }
        return "PAID " + orderId;
    }
}

    package com.handbook.structural.decorator.payments;

public class PaymentsDemo {

    public static void main(String[] args) {
        System.out.println("=== Payments: Stacking Cross-Cutting Concerns ===");

        PaymentProcessor processor =
                new FraudCheckProcessor(                // outermost: cheapest check first
                        new RetryingProcessor(
                                new LoggingProcessor(   // logs every attempt
                                        new FlakyGatewayProcessor(2)),
                                3),
                        50_000);

        System.out.println("Order 1:");
        System.out.println("Result: " + processor.pay("ORD-1", 1_200));
        System.out.println("Order 2:");
        System.out.println("Result: " + processor.pay("ORD-2", 75_000));
    }
}

    Output:

    === Payments: Stacking Cross-Cutting Concerns ===
Order 1:
  [log] -> pay ORD-1 INR 1200
  [log] <- FAILED: gateway timeout
  [retry] attempt 1 failed (gateway timeout), retrying
  [log] -> pay ORD-1 INR 1200
  [log] <- FAILED: gateway timeout
  [retry] attempt 2 failed (gateway timeout), retrying
  [log] -> pay ORD-1 INR 1200
  [log] <- PAID ORD-1
Result: PAID ORD-1
Order 2:
Result: BLOCKED ORD-2 (fraud rule: amount > INR 50000)

    Because logging sits inside the retry decorator, every attempt is logged. Put it outside and you'd see one log line per order. Order is a design decision.

    Why Decorator here:

    • Each concern is one small class, testable on its own.
    • Stacks are composed at runtime, per merchant, from config.
    • The checkout code sees only PaymentProcessor; it doesn't know what's stacked.

    Example 2: Patient Record Storage Pipeline (Healthcare)¶

    Scenario: A hospital stores ECG traces and clinical notes in object storage. Regulations require encryption at rest and an audit trail of every read and write; ECG traces are long and repetitive, so compression cuts storage cost. Some record types (small notes) skip compression; test environments skip encryption. Each concern must be pluggable, and the order matters: compress before encrypting, because encrypted data looks random and doesn't compress.

    Design:

    sequenceDiagram
    autonumber
    participant D as Doctor app
    participant A as AuditingStore
    participant C as CompressingStore
    participant E as EncryptingStore
    participant S as Storage
    D->>A: write("P-1001/ecg", 93 chars)
    A->>A: audit "dr.mehta WRITE"
    A->>C: write(...)
    C->>C: run-length encode
    C->>E: write(compressed)
    E->>E: encrypt + Base64
    E->>S: write(44 chars)

    Full Code:

    package com.handbook.structural.decorator.healthcare;

import java.util.regex.Matcher;
import java.util.regex.Pattern;

/** Decorator: run-length encoding, e.g. "AAAB" <-> "3A1B". Real code would use GZIP. */
public class CompressingStore implements RecordStore {

    private static final Pattern RUN = Pattern.compile("(\\d+)(\\D)");
    private final RecordStore inner;

    public CompressingStore(RecordStore inner) {
        this.inner = inner;
    }

    @Override
    public void write(String key, String data) {
        if (data.chars().anyMatch(Character::isDigit)) {
            throw new IllegalArgumentException("demo RLE does not support digits");
        }
        StringBuilder out = new StringBuilder();
        for (int i = 0; i < data.length(); ) {
            int j = i;
            while (j < data.length() && data.charAt(j) == data.charAt(i)) {
                j++;
            }
            out.append(j - i).append(data.charAt(i));
            i = j;
        }
        inner.write(key, out.toString());
    }

    @Override
    public String read(String key) {
        Matcher m = RUN.matcher(inner.read(key));
        StringBuilder out = new StringBuilder();
        while (m.find()) {
            out.append(m.group(2).repeat(Integer.parseInt(m.group(1))));
        }
        return out.toString();
    }
}

    package com.handbook.structural.decorator.healthcare;

import java.nio.charset.StandardCharsets;
import java.util.Base64;

/** Decorator: toy XOR cipher + Base64 to keep the demo readable. Use AES-GCM in real systems. */
public class EncryptingStore implements RecordStore {

    private final RecordStore inner;
    private final byte[] key;

    public EncryptingStore(RecordStore inner, String key) {
        this.inner = inner;
        this.key = key.getBytes(StandardCharsets.UTF_8);
    }

    @Override
    public void write(String id, String data) {
        inner.write(id, Base64.getEncoder().encodeToString(xor(data.getBytes(StandardCharsets.UTF_8))));
    }

    @Override
    public String read(String id) {
        return new String(xor(Base64.getDecoder().decode(inner.read(id))), StandardCharsets.UTF_8);
    }

    private byte[] xor(byte[] in) {
        byte[] out = new byte[in.length];
        for (int i = 0; i < in.length; i++) {
            out[i] = (byte) (in[i] ^ key[i % key.length]);
        }
        return out;
    }
}

    package com.handbook.structural.decorator.healthcare;

import java.util.ArrayList;
import java.util.List;

/** Decorator: records who touched which record, then delegates. */
public class AuditingStore implements RecordStore {

    private final RecordStore inner;
    private final String user;
    private final List<String> auditLog;

    public AuditingStore(RecordStore inner, String user, List<String> auditLog) {
        this.inner = inner;
        this.user = user;
        this.auditLog = auditLog;
    }

    public void write(String key, String data) {
        auditLog.add(user + " WRITE " + key);
        inner.write(key, data);
    }

    public String read(String key) {
        auditLog.add(user + " READ " + key);
        return inner.read(key);
    }

    public static List<String> newLog() {
        return new ArrayList<>();
    }
}

    package com.handbook.structural.decorator.healthcare;

public interface RecordStore {

    void write(String key, String data);

    String read(String key);
}

    package com.handbook.structural.decorator.healthcare;

import java.util.HashMap;
import java.util.Map;

/** Concrete component: stores exactly what it is given (think: object storage). */
public class InMemoryRecordStore implements RecordStore {

    private final Map<String, String> data = new HashMap<>();

    public void write(String key, String value) { data.put(key, value); }

    public String read(String key) { return data.get(key); }

    public String raw(String key) { return data.get(key); }
}

    package com.handbook.structural.decorator.healthcare;

import java.util.List;

public class RecordsDemo {

    public static void main(String[] args) {
        System.out.println("=== Healthcare: Patient Record Storage Pipeline ===");
        InMemoryRecordStore disk = new InMemoryRecordStore();
        List<String> audit = AuditingStore.newLog();

        // audit -> compress -> encrypt -> disk  (compress BEFORE encrypt: encrypted data does not compress)
        RecordStore store = new AuditingStore(
                new CompressingStore(new EncryptingStore(disk, "k3y")), "dr.mehta", audit);

        String ecg = "ECG:" + "N".repeat(40) + "V" + "N".repeat(40) + ";BP:high"; // long runs, like real traces
        store.write("P-1001/ecg", ecg);

        System.out.println("Original      (" + ecg.length() + " chars): " + ecg);
        System.out.println("Stored on disk(" + disk.raw("P-1001/ecg").length() + " chars): " + disk.raw("P-1001/ecg"));
        System.out.println("Read back     : " + store.read("P-1001/ecg"));
        System.out.println("Round trip OK : " + ecg.equals(store.read("P-1001/ecg")));
        System.out.println("Audit log     : " + audit);
    }
}

    Output:

    === Healthcare: Patient Record Storage Pipeline ===
Original      (93 chars): ECG:NNNNNNNNNNNNNNNNNNNNNNNNNNNNNNNNNNNNNNNNVNNNNNNNNNNNNNNNNNNNNNNNNNNNNNNNNNNNNNNNN;BP:high
Stored on disk(44 chars): WnZIKAI+WglNW31IPQdJJQJCWnFIOwJDWltIAgIeWls=
Read back     : ECG:NNNNNNNNNNNNNNNNNNNNNNNNNNNNNNNNNNNNNNNNVNNNNNNNNNNNNNNNNNNNNNNNNNNNNNNNNNNNNNNNN;BP:high
Round trip OK : true
Audit log     : [dr.mehta WRITE P-1001/ecg, dr.mehta READ P-1001/ecg, dr.mehta READ P-1001/ecg]

    Toy algorithms on purpose

    The run-length encoding and XOR cipher keep the output readable. In production use GZIPOutputStream (or Zstandard) and AES-GCM via javax.crypto with keys from a KMS. The structure stays exactly the same.

    Why Decorator here:

    • This is exactly how java.io works: new GZIPOutputStream(new CipherOutputStream(new FileOutputStream(...))).
    • Each concern is a separate, certifiable unit, which auditors like.
    • Bidirectional decorators: write transforms on the way in, read reverses on the way out, in mirror order.

    Example 3: Pricing Rules (Grocery)¶

    Scenario: A grocery app applies a member discount (10%), a festival offer (INR 100 off above INR 500) and GST (5%). Marketing changes the active rules weekly. Finance has one firm requirement: GST is charged on the discounted price. In an earlier version someone applied rules in the wrong order, and customers were charged INR 5 too much per order. Here each rule is a functional decorator built with Java default methods.

    Design:

    flowchart LR
    S["Subtotal<br/>INR 1000"] --> M["Member -10%<br/>INR 900"] --> F["Festival -INR 100<br/>INR 800"] --> G["GST +5%<br/>INR 840"]

    Full Code:

    package com.handbook.structural.decorator.pricing;

/** Component. Amounts in paise to avoid floating-point money. */
@FunctionalInterface
public interface PriceCalculator {

    long price(long subtotalPaise);

    static PriceCalculator base() {
        return subtotal -> subtotal;
    }

    // ---- decorators as small functions that wrap another calculator ----

    default PriceCalculator thenMemberDiscount(int percent) { // (1)!
        return subtotal -> {
            long p = price(subtotal);
            return p - p * percent / 100;
        };
    }

    default PriceCalculator thenFlatOff(long paiseOff, long minimumPaise) {
        return subtotal -> {
            long p = price(subtotal);
            return p >= minimumPaise ? p - paiseOff : p;
        };
    }

    default PriceCalculator thenGst(int percent) {
        return subtotal -> {
            long p = price(subtotal);
            return p + Math.round(p * percent / 100.0);
        };
    }
}
    1. Each then... default method returns a new calculator that wraps this: it calls the current pipeline, then applies its rule. That's a decorator written as a lambda, the functional-programming form of the pattern.
    package com.handbook.structural.decorator.pricing;

public class PricingDemo {

    public static void main(String[] args) {
        System.out.println("=== Grocery: Pricing Rules as Decorators ===");
        long cart = 1_000_00; // INR 1000.00

        PriceCalculator correct = PriceCalculator.base()
                .thenMemberDiscount(10)        // INR 1000 -> 900
                .thenFlatOff(100_00, 500_00)   // festival: INR 100 off above INR 500 -> 800
                .thenGst(5);                   // tax on the discounted price -> 840

        PriceCalculator wrongOrder = PriceCalculator.base()
                .thenGst(5)                    // tax first -> 1050
                .thenMemberDiscount(10)        // -> 945
                .thenFlatOff(100_00, 500_00);  // -> 845

        PriceCalculator plain = PriceCalculator.base().thenGst(5);

        System.out.println("No offers           : INR " + inr(plain.price(cart)));
        System.out.println("Discounts, then GST : INR " + inr(correct.price(cart)));
        System.out.println("GST, then discounts : INR " + inr(wrongOrder.price(cart)) + "  <- same rules, different order");
    }

    private static String inr(long paise) {
        return "%d.%02d".formatted(paise / 100, paise % 100);
    }
}

    Output:

    === Grocery: Pricing Rules as Decorators ===
No offers           : INR 1050.00
Discounts, then GST : INR 840.00
GST, then discounts : INR 845.00  <- same rules, different order

    Why Decorator here:

    • Rules are independent, stackable, and reorderable, and the order changes the result.
    • Functional decorators (lambdas + default methods) remove the class boilerplate entirely.
    • New rules (a bank-card offer) are one method; existing rules don't change.
    Unit Tests: DecoratorTest.java (all three examples + challenge) 
    package com.handbook.structural.decorator;

import com.handbook.structural.decorator.caching.CachingCatalog;
import com.handbook.structural.decorator.healthcare.CompressingStore;
import com.handbook.structural.decorator.healthcare.EncryptingStore;
import com.handbook.structural.decorator.healthcare.InMemoryRecordStore;
import com.handbook.structural.decorator.healthcare.RecordStore;
import com.handbook.structural.decorator.payments.FlakyGatewayProcessor;
import com.handbook.structural.decorator.payments.FraudCheckProcessor;
import com.handbook.structural.decorator.payments.RetryingProcessor;
import com.handbook.structural.decorator.pricing.PriceCalculator;
import org.junit.jupiter.api.Test;

import java.util.concurrent.atomic.AtomicInteger;

import static org.assertj.core.api.Assertions.assertThat;
import static org.assertj.core.api.Assertions.assertThatThrownBy;

class DecoratorTest {

    @Test
    void retrySucceedsWithinLimitAndGivesUpAfter() {
        assertThat(new RetryingProcessor(new FlakyGatewayProcessor(2), 3).pay("O", 1)).isEqualTo("PAID O");
        assertThatThrownBy(() -> new RetryingProcessor(new FlakyGatewayProcessor(5), 3).pay("O", 1))
                .hasMessage("gateway timeout");
    }

    @Test
    void fraudCheckShortCircuitsBeforeTheGateway() {
        var neverCalled = new FlakyGatewayProcessor(Integer.MAX_VALUE);
        assertThat(new FraudCheckProcessor(neverCalled, 100).pay("O", 500)).startsWith("BLOCKED");
    }

    @Test
    void storeDecoratorsRoundTripInEitherOrder() {
        String data = "AAAABBBCCD;x";
        RecordStore a = new CompressingStore(new EncryptingStore(new InMemoryRecordStore(), "k"));
        RecordStore b = new EncryptingStore(new CompressingStore(new InMemoryRecordStore()), "k");
        a.write("1", data);
        assertThat(a.read("1")).isEqualTo(data);
        assertThatThrownBy(() -> b.write("1", data)) // encrypted Base64 may contain digits
                .isInstanceOf(IllegalArgumentException.class);
    }

    @Test
    void pricingOrderMatters() {
        long discountFirst = PriceCalculator.base().thenMemberDiscount(10).thenGst(5).price(10_000);
        long taxFirst = PriceCalculator.base().thenGst(5).thenMemberDiscount(10).price(10_000);
        assertThat(discountFirst).isEqualTo(9_450);
        assertThat(taxFirst).isEqualTo(9_450); // percentages commute...
        long flatThenTax = PriceCalculator.base().thenFlatOff(1_000, 0).thenGst(5).price(10_000);
        long taxThenFlat = PriceCalculator.base().thenGst(5).thenFlatOff(1_000, 0).price(10_000);
        assertThat(flatThenTax).isNotEqualTo(taxThenFlat); // ...flat amounts do not
    }

    @Test
    void cachingCallsTheSourceOncePerKey() {
        AtomicInteger calls = new AtomicInteger();
        CachingCatalog c = new CachingCatalog(sku -> sku + calls.incrementAndGet());
        c.describe("a");
        c.describe("a");
        assertThat(calls).hasValue(1);
        assertThat(c.stats()).isEqualTo("hits=1 misses=1");
    }
}

    6. Variations & Modern Java Take¶

    Form Example
    Classic class-based with an abstract base decorator Example 1
    Direct implementation (no base class) Example 2: each decorator implements the interface and holds a field
    Functional (lambdas, Function.andThen, default methods) Example 3; also UnaryOperator<String> pipeline = trim.andThen(lower)
    Dynamic proxies / AOP Spring @Transactional, @Cacheable, @Retryable: decorators generated at runtime
    Resilience4j Decorators.ofSupplier(call).withRetry(..).withCircuitBreaker(..).withBulkhead(..).decorate()

    Decorators and Spring. Spring AOP proxies are decorators: @Transactional wraps your bean with "begin, call, commit or roll back". You can also write decorators manually with @Primary beans that take the original bean as a constructor argument.

    Equality and identity. A decorated object is a different object. decorated.equals(original) is usually false, and instanceof ConcreteComponent fails on the wrapper. Don't rely on concrete types once you decorate.

    8. Pros, Cons & Trade-offs¶

    ✅ Pros ❌ Cons
    Add behavior without modifying the class (OCP) Many small objects; stack traces get deep
    Combine features at runtime in any order Order matters and is easy to get wrong
    Each concern in one class (SRP), testable on its own Removing a decorator from the middle of a stack is awkward
    Avoids 2ⁿ subclasses Identity and instanceof checks break on wrapped objects
    Big interfaces mean every decorator must forward every method (use a base class)

    9. Pitfalls & Anti-Patterns¶

    Wrong order

    Encrypt-then-compress (no compression), retry-outside-circuit-breaker (retries hammer an open circuit), tax-before-discount (wrong prices). Write down the intended order and test it (see pricingOrderMatters).

    Retrying non-idempotent operations

    A retry decorator around "charge card" can double-charge. Retry only idempotent calls, or send an idempotency key.

    Forgetting to forward some methods

    In interfaces with many methods, a decorator that only overrides one and forgets the others breaks behavior silently. Extend a forwarding base class that delegates everything.

    Decorators with hidden state

    A caching decorator that never evicts is a memory leak; a retry decorator with a shared counter isn't thread-safe. Decorators are real components; give them the same care.

    10. Senior / Architect Deep Dive (10–15 yrs)¶

    Resilience stacks are decorator stacks, and the order is documented. Resilience4j's recommended order (outermost to innermost) is roughly: Retry ( CircuitBreaker ( RateLimiter ( TimeLimiter ( Bulkhead ( call ) ) ) ) ). Reasoning: retries should see the circuit breaker's "open" error and stop; time limits apply per attempt; the bulkhead limits concurrent calls. Be ready to defend whichever order you choose.

    Decorators vs. AOP vs. middleware. All three wrap behavior around calls. Use explicit decorators when the composition is part of the domain (pricing rules) or changes per tenant; use AOP for uniform infrastructure (transactions, metrics) across many beans; use middleware/filters (servlet filters, gateway filters) at process or network boundaries.

    Observability. With deep stacks, name each layer in logs and metrics (payment.retry.attempts, payment.fraud.blocked) so you can tell which layer acted.

    Performance. Each layer is a virtual call; the JIT usually inlines small, monomorphic stacks. Deep or megamorphic stacks (many decorator types at one call site) can hurt hot paths. Measure before collapsing layers.

    War story: the retry that DDoS'ed our own database

    A team added a retry decorator (5 attempts, no backoff) around a repository call, then a second team added a retry decorator at the service layer (3 attempts), and an HTTP client retried too (3 attempts). When the database slowed down, each user request turned into up to 45 queries. The slowdown became an outage. Fix: one retry layer only (at the edge), exponential backoff with jitter, a retry budget, and a circuit breaker inside the retry so retries stop when the database is clearly down. Lesson: decorators compose multiplicatively. Draw the whole stack before adding a layer.

    12. Interview Corner¶

    Q1. What is the Decorator pattern?

    A structural pattern that adds responsibilities to an object dynamically by wrapping it in an object of the same interface. Decorators can be stacked.

    Q2. Give a Java example.

    Java I/O: new BufferedReader(new InputStreamReader(new FileInputStream("a.txt"))). Each wrapper adds a feature (buffering, decoding) to the stream it wraps.

    Q3. Why not just use inheritance?

    Inheritance is static and leads to a subclass for every combination. Decorators are composed at runtime, in any combination, with one class per feature.

    Q4. Decorator vs. Proxy?

    Same structure; different intent. Decorator adds behavior; Proxy controls access (lazy loading, security, remote calls, caching).

    Q5. Which principle does Decorator follow?

    Open/Closed (extend without modifying) and Single Responsibility (each decorator does one thing).

    Q1. Does the order of decorators matter?

    Yes: compress before encrypting, logging inside or outside retry, discounts before tax. Order changes behavior and results.

    Q2. How does Spring use decorators?

    AOP proxies wrap beans for @Transactional, @Cacheable, @Async, @Retryable. Also BeanPostProcessors that wrap beans, and HttpServletRequestWrapper in filters.

    Q3. How do you write a decorator for an interface with 20 methods?

    Extend an abstract forwarding base class that delegates all 20 by default; override only what you change.

    Q4. How do you test decorators?

    Each one in isolation with a fake inner component (assert it adds its behavior and forwards correctly), plus one test for the composed stack's order.

    Q5. Write a functional decorator.

    Function<String,String> pipeline = String::trim; pipeline = pipeline.andThen(String::toLowerCase);, or default methods returning wrapping lambdas (Example 3).

    Q1. "Design a resilient client for a flaky downstream service."

    Decorators: timeout per attempt, retry with exponential backoff and jitter for idempotent calls, circuit breaker, bulkhead to cap concurrency, fallback (cached response or degraded mode), metrics at each layer. State the order and why, and mention retry budgets to prevent retry storms.

    Q2. "Multiple layers retry and we had an outage. Explain and fix."

    Retries multiply across layers (5 × 3 × 3 = 45). Keep one retry layer, add backoff and jitter, a retry budget (for example 10% extra load), circuit breakers, and propagate deadlines so inner layers don't retry past the caller's timeout.

    Q3. "Decorator vs. AOP: when would you choose explicit decorators?"

    When composition is domain-specific or per tenant (pricing rules, merchant-specific payment stacks) and should be visible in code and tests. AOP suits uniform, infrastructure-level concerns across many beans.

    Q4. "How would you add per-tenant encryption to an existing storage service without touching its code?"

    An EncryptingStore decorator that looks up the tenant's key (envelope encryption: data key encrypted by a tenant KMS key), wraps the existing store, adds key-version metadata for rotation, and is composed in configuration.

    Q5. "What are the performance implications of deep decorator stacks?"

    Mostly negligible (JIT inlining). Watch megamorphic call sites, extra allocations per call (e.g. wrapper objects in streams), and buffer copies in I/O stacks. Measure with JFR; collapse layers only if profiling shows it matters.

    Problem: The product catalog database is slow. Add a read-through cache in front of any ProductCatalog without changing the catalog or its callers. Count hits and misses, and support evicting a SKU when its price changes.

    Solution 
    package com.handbook.structural.decorator.caching;

import java.util.Map;
import java.util.concurrent.ConcurrentHashMap;
import java.util.concurrent.atomic.AtomicInteger;

/** Challenge solution: transparent read-through cache in front of any catalog. */
public class CachingCatalog implements ProductCatalog {

    private final ProductCatalog inner;
    private final Map<String, String> cache = new ConcurrentHashMap<>();
    private final AtomicInteger hits = new AtomicInteger();
    private final AtomicInteger misses = new AtomicInteger();

    public CachingCatalog(ProductCatalog inner) {
        this.inner = inner;
    }

    @Override
    public String describe(String sku) {
        String cached = cache.get(sku);
        if (cached != null) {
            hits.incrementAndGet();
            return cached;
        }
        misses.incrementAndGet();
        return cache.computeIfAbsent(sku, inner::describe);
    }

    public void evict(String sku) {
        cache.remove(sku);
    }

    public String stats() {
        return "hits=" + hits + " misses=" + misses;
    }
}

    package com.handbook.structural.decorator.caching;

/** Challenge: component interface. */
public interface ProductCatalog {

    String describe(String sku);
}

    package com.handbook.structural.decorator.caching;

import java.util.List;

public class CachingDemo {

    public static void main(String[] args) {
        ProductCatalog slowDb = sku -> {
            System.out.println("  (db query for " + sku + ")");
            return sku + ": Salted Butter 500g, INR 285";
        };
        CachingCatalog catalog = new CachingCatalog(slowDb);

        for (String sku : List.of("BUTTER-500", "BUTTER-500", "BUTTER-500")) {
            System.out.println(catalog.describe(sku));
        }
        catalog.evict("BUTTER-500"); // price changed
        System.out.println(catalog.describe("BUTTER-500"));
        System.out.println(catalog.stats());
    }
}

    Output:

      (db query for BUTTER-500)
BUTTER-500: Salted Butter 500g, INR 285
BUTTER-500: Salted Butter 500g, INR 285
BUTTER-500: Salted Butter 500g, INR 285
  (db query for BUTTER-500)
BUTTER-500: Salted Butter 500g, INR 285
hits=2 misses=2

    Key points to say: same interface, so callers don't change; ConcurrentHashMap.computeIfAbsent makes concurrent misses for the same SKU load once; eviction keeps the cache correct after price changes. Production follow-ups: size limit and TTL (use Caffeine), and don't cache nulls or errors.

    Behavioural tie-in (STAR) for experienced candidates

    • S: A retry storm across three layers turned a slow database into a two-hour outage.
    • T: Make the client stack safe by design.
    • A: Mapped every decorator layer, removed two retry layers, added backoff with jitter, a retry budget and a circuit breaker inside the remaining retry; documented the stack order in an ADR and in tests.
    • R: The next database slowdown caused 4 minutes of degraded responses instead of an outage.
