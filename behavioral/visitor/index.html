    Visitor¶

    🔴 Advanced Behavioral Interview frequency ⭐⭐⭐

    TL;DR

    Visitor lets you add new operations to a stable class hierarchy without changing those classes. Each operation is a "visitor" with one method per element type. In Java 21, sealed interfaces + pattern-matching switch often give the same benefit with far less code. Know both.

    1. Intent & Problem It Solves¶

    The problem in plain English: a cart has books, electronics and fresh produce. Finance wants GST per category, logistics wants shipping cost, marketing wants loyalty points, and next quarter someone wants carbon footprint. If each operation becomes a method on every item class (gst(), shipping(), points(), carbon()), item classes grow forever and mix tax rules with logistics rules. The item types rarely change; the operations keep coming.

    Formal definition (GoF):

    Represent an operation to be performed on the elements of an object structure. Visitor lets you define a new operation without changing the classes of the elements on which it operates.

    Double dispatch: item.accept(visitor) calls visitor.visit(this). The right visit method is chosen by both the element's runtime type (first dispatch, via accept) and the visitor's type (second dispatch). That's how Java, with only single dispatch, picks "GST rule for Electronics".

    2. Real-World Analogy¶

    Inspectors visiting a building

    A building has flats, shops and a parking lot (stable element types). Different inspectors visit: fire safety, electrical, tax assessment. Each inspector knows what to check for each kind of unit. Adding a new kind of inspection doesn't require rebuilding the units; you just send a new inspector.

    Participant Responsibility

    4. Naive Approach (Without the Pattern)¶

    double gst(Item item) {
    if (item instanceof Book) return 0;
    else if (item instanceof Electronics e) return e.price() * 0.18;
    else if (item instanceof FreshProduce) return 0;
    throw new IllegalArgumentException();   // a new item type compiles fine and fails at runtime
}
int shipping(Item item) { /* the same instanceof chain again */ }
    • instanceof chains repeated per operation.
    • A new element type compiles fine and fails at runtime when a branch is missing.
    • Or, the alternative: every operation added as a method to every class, mixing unrelated concerns.

    5. Three Real-World Examples¶

    Example 1: Tax and Shipping over a Mixed Cart (E-commerce) — classic double dispatch¶

    Scenario: An Indian marketplace sells books (GST-exempt), electronics (18% GST, fragile items need careful packing) and fresh produce (exempt, chilled items need a cold-chain bag). Tax rules are owned by finance; shipping rules by logistics. Neither team should edit the item classes, which are shared by catalog, search and orders.

    Design:

    sequenceDiagram
    autonumber
    participant C as Cart loop
    participant E as Electronics (element)
    participant G as GstVisitor
    C->>E: accept(gst)
    E->>G: visit(this as Electronics)
    G->>G: gst += price * 0.18
    C->>E: accept(shipping)
    E->>G: (ShippingVisitor) visit(this): weight + fragile surcharge

    Full Code:

    package com.handbook.behavioral.visitor.cart;

/** Element hierarchy (stable) + visitor interface (operations grow). Classic double dispatch. */
public final class CartItems {

    private CartItems() {
    }

    public interface CartVisitor { // (1)!
        void visit(Book b);
        void visit(Electronics e);
        void visit(FreshProduce f);
    }

    public interface Item {
        void accept(CartVisitor v); // (2)!
    }

    public record Book(String title, int priceInr, int grams) implements Item {
        public void accept(CartVisitor v) { v.visit(this); }
    }

    public record Electronics(String name, int priceInr, int grams, boolean fragile) implements Item {
        public void accept(CartVisitor v) { v.visit(this); }
    }

    public record FreshProduce(String name, int priceInr, int grams, boolean chilled) implements Item {
        public void accept(CartVisitor v) { v.visit(this); }
    }
}
    1. One visit overload per element type. Adding an element type means adding a method here, and the compiler then forces every visitor to handle it.
    2. accept is identical in every element (v.visit(this)), but it must be written in each class: inside Book, this has static type Book, so the compiler picks visit(Book).
    package com.handbook.behavioral.visitor.cart;

import com.handbook.behavioral.visitor.cart.CartItems.*;

/** Operation 1: GST per category. Rates live here, not in the item classes. */
public class GstVisitor implements CartVisitor {

    private double gst;

    public void visit(Book b) { gst += 0; }                          // books exempt
    public void visit(Electronics e) { gst += e.priceInr() * 0.18; }
    public void visit(FreshProduce f) { gst += 0; }                  // unprocessed produce exempt

    public double total() { return gst; }
}

    package com.handbook.behavioral.visitor.cart;

import com.handbook.behavioral.visitor.cart.CartItems.*;

/** Operation 2: shipping cost. Each item type has its own rule. */
public class ShippingVisitor implements CartVisitor {

    private int grams;
    private int surcharges;

    public void visit(Book b) { grams += b.grams(); }

    public void visit(Electronics e) {
        grams += e.grams();
        if (e.fragile()) {
            surcharges += 40; // bubble wrap and careful handling
        }
    }

    public void visit(FreshProduce f) {
        grams += f.grams();
        if (f.chilled()) {
            surcharges += 25; // cold-chain bag
        }
    }

    public int costInr() {
        return 30 + (grams / 1000) * 10 + surcharges;
    }
}

    package com.handbook.behavioral.visitor.cart;

import com.handbook.behavioral.visitor.cart.CartItems.*;

import java.util.List;

public class CartDemo {

    public static void main(String[] args) {
        System.out.println("=== E-commerce: Tax and Shipping over a Mixed Cart ===");
        List<Item> cart = List.of(
                new Book("Clean Code", 650, 700),
                new Electronics("Bluetooth Speaker", 2_999, 900, true),
                new FreshProduce("Alphonso Mangoes 1kg", 450, 1_100, true));

        GstVisitor gst = new GstVisitor();
        ShippingVisitor shipping = new ShippingVisitor();
        for (Item item : cart) {
            item.accept(gst);
            item.accept(shipping);
        }
        System.out.printf("GST      : INR %.2f%n", gst.total());
        System.out.println("Shipping : INR " + shipping.costInr() + " (2.7 kg + fragile + chilled)");
    }
}

    Output:

    === E-commerce: Tax and Shipping over a Mixed Cart ===
GST      : INR 539.82
Shipping : INR 115 (2.7 kg + fragile + chilled)

    Why Visitor here:

    • Stable element types, a growing list of operations owned by different teams.
    • Each operation's rules are together in one class (all GST rules in GstVisitor).
    • Visitors can accumulate results across the whole cart.

    Example 2: Claim Adjudication (Health Insurance) — sealed types + pattern matching¶

    Scenario: A health insurer processes consultation, surgery and pharmacy claims. Two operations run on every claim: adjudication (approve, reject or review, with rules like "surgery needs pre-authorization" and "cap at sum insured") and fraud scoring. More operations (reserve estimation, reinsurance split) are planned. The claim types are fixed by regulation and rarely change.

    Design:

    flowchart LR
    C{{"sealed interface Claim"}} --> A[Consultation]
    C --> S[Surgery]
    C --> P[Pharmacy]
    O1["decide(Claim) — switch"] -.-> C
    O2["fraudScore(Claim) — switch"] -.-> C

    Full Code:

    package com.handbook.behavioral.visitor.claims;

/** Sealed hierarchy: Java 21 pattern matching gives Visitor-style dispatch without accept(). */
public sealed interface Claim {

    String id();

    int amountInr();

    record Consultation(String id, int amountInr, String doctorRegNo) implements Claim { }

    record Surgery(String id, int amountInr, boolean preAuthorized, int daysAdmitted) implements Claim { }

    record Pharmacy(String id, int amountInr, boolean hasPrescription) implements Claim { }
}

    package com.handbook.behavioral.visitor.claims;

import com.handbook.behavioral.visitor.claims.Claim.*;

/** Each operation is one method with an exhaustive switch: a "visitor" without boilerplate. */
public final class ClaimOperations {

    private ClaimOperations() {
    }

    public static String decide(Claim c) {
        return switch (c) { // (1)!
            case Consultation x when x.amountInr() <= 2_000 -> "AUTO-APPROVE";
            case Consultation x -> "REVIEW (consultation above INR 2000)";
            case Surgery s when !s.preAuthorized() -> "REJECT (no pre-authorization)";
            case Surgery s -> "APPROVE " + Math.min(s.amountInr(), 300_000) + " (sum insured cap)";
            case Pharmacy p when !p.hasPrescription() -> "REJECT (no prescription)";
            case Pharmacy p -> "AUTO-APPROVE";
        };
    }

    public static int fraudScore(Claim c) {
        return switch (c) {
            case Consultation x -> x.doctorRegNo().isBlank() ? 70 : 5;
            case Surgery s -> s.daysAdmitted() == 0 && s.amountInr() > 100_000 ? 60 : 10;
            case Pharmacy p -> p.amountInr() > 20_000 ? 40 : 5;
        };
    }
}
    1. The modern Visitor: a switch over a sealed type is checked for exhaustiveness (add Dental to Claim and both operations stop compiling, exactly like a visitor interface), with guards (when) for rule conditions. No accept() methods, no visitor interfaces.
    package com.handbook.behavioral.visitor.claims;

import com.handbook.behavioral.visitor.claims.Claim.*;

import java.util.List;

public class ClaimsDemo {

    public static void main(String[] args) {
        System.out.println("=== Health Insurance: Claim Adjudication ===");
        List<Claim> claims = List.of(
                new Consultation("CL-1", 1_200, "KMC-55123"),
                new Consultation("CL-2", 3_500, ""),
                new Surgery("CL-3", 420_000, true, 4),
                new Surgery("CL-4", 150_000, false, 0),
                new Pharmacy("CL-5", 2_400, true),
                new Pharmacy("CL-6", 26_000, false));

        for (Claim c : claims) {
            System.out.printf("%s %-12s INR %,7d -> %-38s fraud score %d%n", c.id(), c.getClass().getSimpleName(),
                    c.amountInr(), ClaimOperations.decide(c), ClaimOperations.fraudScore(c));
        }
    }
}

    Output:

    === Health Insurance: Claim Adjudication ===
CL-1 Consultation INR   1,200 -> AUTO-APPROVE                           fraud score 5
CL-2 Consultation INR   3,500 -> REVIEW (consultation above INR 2000)   fraud score 70
CL-3 Surgery      INR 420,000 -> APPROVE 300000 (sum insured cap)       fraud score 10
CL-4 Surgery      INR 150,000 -> REJECT (no pre-authorization)          fraud score 60
CL-5 Pharmacy     INR   2,400 -> AUTO-APPROVE                           fraud score 5
CL-6 Pharmacy     INR  26,000 -> REJECT (no prescription)               fraud score 40

    Why this form here:

    • The hierarchy is closed (sealed) and owned by the same codebase, which is ideal for pattern matching.
    • Rules read like a decision table, which reviewers in insurance appreciate.
    • Same benefit as Visitor (new operations without touching claim classes), and the compiler still catches missing cases.

    Example 3: One Document, Many Exports (Docs SaaS) — visitor with return values¶

    Scenario: A docs product stores documents as a list of elements: headings, paragraphs, images, tables. Users export to Markdown and HTML; the editor shows a word count; PDF and Google-Docs export are planned. Element classes are part of a stable, versioned document model; exporters are added by different teams.

    Design:

    classDiagram
    class Visitor~R~ {
        <<interface>>
        +heading(Heading) R
        +paragraph(Paragraph) R
        +image(Image) R
        +table(Table) R
    }
    class Markdown["Markdown : Visitor<String>"]
    class Html["Html : Visitor<String>"]
    class WordCount["WordCount : Visitor<Integer>"]
    Visitor <|.. Markdown
    Visitor <|.. Html
    Visitor <|.. WordCount

    Full Code:

    package com.handbook.behavioral.visitor.docs;

import java.util.List;

/** Document elements with a generic visitor that returns a value. */
public final class Doc {

    private Doc() {
    }

    public interface Visitor<R> {
        R heading(Heading h);
        R paragraph(Paragraph p);
        R image(Image i);
        R table(Table t);
    }

    public interface Element {
        <R> R accept(Visitor<R> v);
    }

    public record Heading(int level, String text) implements Element {
        public <R> R accept(Visitor<R> v) { return v.heading(this); }
    }

    public record Paragraph(String text) implements Element {
        public <R> R accept(Visitor<R> v) { return v.paragraph(this); }
    }

    public record Image(String url, String alt) implements Element {
        public <R> R accept(Visitor<R> v) { return v.image(this); }
    }

    public record Table(List<String> header, List<List<String>> rows) implements Element {
        public <R> R accept(Visitor<R> v) { return v.table(this); }
    }
}

    package com.handbook.behavioral.visitor.docs;

import com.handbook.behavioral.visitor.docs.Doc.*;

import java.util.stream.Collectors;

/** New operations = new visitors. The element classes never change. */
public final class Exporters {

    private Exporters() {
    }

    public static class Markdown implements Visitor<String> {
        public String heading(Heading h) { return "#".repeat(h.level()) + " " + h.text(); }
        public String paragraph(Paragraph p) { return p.text(); }
        public String image(Image i) { return "![" + i.alt() + "](" + i.url() + ")"; }
        public String table(Table t) {
            String head = "| " + String.join(" | ", t.header()) + " |";
            String sep = "|" + " --- |".repeat(t.header().size());
            String body = t.rows().stream().map(r -> "| " + String.join(" | ", r) + " |").collect(Collectors.joining("\n"));
            return head + "\n" + sep + "\n" + body;
        }
    }

    public static class Html implements Visitor<String> {
        public String heading(Heading h) { return "<h%d>%s</h%d>".formatted(h.level(), h.text(), h.level()); }
        public String paragraph(Paragraph p) { return "<p>" + p.text() + "</p>"; }
        public String image(Image i) { return "<img src=\"" + i.url() + "\" alt=\"" + i.alt() + "\">"; }
        public String table(Table t) { return "<table>(" + t.rows().size() + " rows)</table>"; }
    }

    public static class WordCount implements Visitor<Integer> {
        private static int words(String s) { return s.isBlank() ? 0 : s.trim().split("\\s+").length; }
        public Integer heading(Heading h) { return words(h.text()); }
        public Integer paragraph(Paragraph p) { return words(p.text()); }
        public Integer image(Image i) { return 0; } // alt text doesn't count
        public Integer table(Table t) { return t.rows().stream().flatMap(r -> r.stream()).mapToInt(WordCount::words).sum(); }
    }
}

    package com.handbook.behavioral.visitor.docs;

import com.handbook.behavioral.visitor.docs.Doc.*;

import java.util.List;

public class DocsDemo {

    public static void main(String[] args) {
        System.out.println("=== Docs SaaS: One Document, Many Exports ===");
        List<Element> doc = List.of(
                new Heading(2, "Q3 Launch Plan"),
                new Paragraph("We launch in Pune and Jaipur on 1 November."),
                new Image("pune.png", "Pune dark store"),
                new Table(List.of("City", "Stores"), List.of(List.of("Pune", "12"), List.of("Jaipur", "7"))));

        System.out.println("--- Markdown ---");
        doc.forEach(e -> System.out.println(e.accept(new Exporters.Markdown())));
        System.out.println("--- HTML ---");
        doc.forEach(e -> System.out.println(e.accept(new Exporters.Html())));
        int words = doc.stream().mapToInt(e -> e.accept(new Exporters.WordCount())).sum();
        System.out.println("--- Word count: " + words + " ---");
    }
}

    Output:

    === Docs SaaS: One Document, Many Exports ===
--- Markdown ---
## Q3 Launch Plan
We launch in Pune and Jaipur on 1 November.
![Pune dark store](pune.png)
| City | Stores |
| --- | --- |
| Pune | 12 |
| Jaipur | 7 |
--- HTML ---
<h2>Q3 Launch Plan</h2>
<p>We launch in Pune and Jaipur on 1 November.</p>
<img src="pune.png" alt="Pune dark store">
<table>(2 rows)</table>
--- Word count: 16 ---

    Why Visitor here:

    • Generic Visitor<R> lets each operation return its own type (String for exports, Integer for counts) without casts or accumulator fields.
    • Exporters are independent plug-ins; the document model stays clean.
    • This is how compilers and document processors (ASTs, Markdown parsers) are typically structured.

    package com.handbook.behavioral.visitor;

import org.junit.jupiter.api.Test;

import java.util.List;

import static org.assertj.core.api.Assertions.assertThat;

class VisitorTest {

    @Test
    void gstOnlyOnElectronics() {
        GstVisitor v = new GstVisitor();
        new Book("b", 100, 1).accept(v);
        new Electronics("e", 100, 1, false).accept(v);
        assertThat(v.total()).isEqualTo(18.0);
    }

    @Test
    void shippingAddsSurcharges() {
        ShippingVisitor v = new ShippingVisitor();
        new Electronics("e", 1, 500, true).accept(v);
        assertThat(v.costInr()).isEqualTo(70);
    }

    @Test
    void claimRulesWithGuards() {
        assertThat(ClaimOperations.decide(new Claim.Surgery("x", 500_000, true, 3))).isEqualTo("APPROVE 300000 (sum insured cap)");

    }

    @Test
    void wordCountIgnoresImages() {
        List<Doc.Element> doc = List.of(new Doc.Heading(1, "Two words"), new Doc.Image("a", "many alt words here"));
        assertThat(doc.stream().mapToInt(e -> e.accept(new Exporters.WordCount())).sum()).isEqualTo(2);
    }
}

    6. Variations & Modern Java Take¶

    Form When to use
    Classic visitor (Example 1) Element types in another module/library you can't make sealed; visitors that keep state
    Generic Visitor<R> (Example 3, challenge) Operations that return values; no mutable accumulators
    Sealed + pattern-matching switch (Example 2) Closed hierarchies in your own code (Java 21+); usually the simplest choice today
    Reflective/dynamic visitors Avoid; you lose compile-time safety
    Visitor over a Composite Elements call accept on their children (tree traversal inside or outside the visitor)

    The expression problem

    OOP makes it easy to add types (new class) and hard to add operations (edit every class). Visitor flips that: easy to add operations, hard to add types (edit every visitor). Choose based on which side changes more often. This is a favourite senior-level discussion.

    7. Where It Lives in Real Frameworks¶

    Where Visitor
    JDK java.nio.file.FileVisitor with Files.walkFileTree
    JDK javax.lang.model.element.ElementVisitor (annotation processors), javax.lang.model.type.TypeVisitor
    Compilers javac's tree visitors, ASM ClassVisitor/MethodVisitor (bytecode), ANTLR parse-tree visitors
    Spring BeanDefinitionVisitor (resolving placeholders in bean definitions)
    Hibernate / JPA Criteria/HQL AST walkers that render SQL
    Jackson JsonFormatVisitor (schema generation)

    8. Pros, Cons & Trade-offs¶

    ✅ Pros ❌ Cons
    Add operations without changing element classes (OCP for operations) Adding an element type breaks every visitor
    Related logic grouped per operation Boilerplate (accept everywhere, visitor interfaces)
    Visitors can accumulate state across a structure Visitors may need access to element internals (weaker encapsulation)
    Compile-time completeness (every type handled) Harder for beginners to follow (double dispatch)

    9. Pitfalls & Anti-Patterns¶

    Using Visitor on an unstable hierarchy

    If new element types arrive every sprint, every visitor must change every sprint. Use plain polymorphic methods instead.

    default branches that hide new types

    A visitor base class with no-op defaults, or a switch with default, silently ignores new element types: the tax visitor returns 0 GST for a new "Jewellery" type. Prefer exhaustive handling.

    Visitors with too much state

    A visitor that both accumulates totals and mutates elements is hard to reason about. Keep visitors focused, or return values (Visitor<R>).

    Reusing a stateful visitor

    GstVisitor accumulates a total; reusing the same instance for two carts adds them together. Create one per traversal.

    10. Senior / Architect Deep Dive (10–15 yrs)¶

    Where Visitor shines: ASTs. Compilers, query engines, rule engines and document processors have stable node types and many passes (type check, optimize, generate code, pretty-print). That's the textbook Visitor use case. The Interpreter page's ASTs could get a ToSqlVisitor this way.

    Choosing in modern Java. Inside one codebase with a closed hierarchy, sealed + switch wins: less code, exhaustive, readable. Use classic visitors across module boundaries (public APIs where you can't seal types and want third parties to add operations), or when you need double dispatch over two hierarchies.

    Traversal ownership. Decide whether the structure controls traversal (elements call children's accept) or the visitor does. For trees, letting the visitor control traversal enables pruning (skip a subtree) and different orders.

    War story: the missing jewellery tax

    A marketplace added a Jewellery item type. Their tax code used a visitor base class with no-op default methods "for convenience". GstVisitor didn't override visit(Jewellery), so jewellery was charged 0% GST instead of 3% for two months, and the company paid the shortfall plus interest. Fix: removed default implementations (every visitor must handle every type); migrated tax rules to a sealed hierarchy with an exhaustive switch; added a test that runs every visitor over one instance of every element type. Lesson: Visitor's main safety feature is the compiler forcing every case. Don't turn it off with defaults.

    12. Interview Corner¶

    Q1. What is the Visitor pattern?

    A behavioral pattern that lets you add new operations to a set of classes without modifying them, by moving each operation into a separate visitor class.

    Q2. What is double dispatch?

    The method called depends on two runtime types: element.accept(visitor) dispatches on the element, and visitor.visit(this) dispatches on the visitor, so the right combination runs.

    Q3. When should you use Visitor?

    When the element types are stable but you keep adding operations (tax, shipping, export).

    Q4. Main disadvantage?

    Adding a new element type requires changing every visitor.

    Q5. Give a Java example.

    Files.walkFileTree(path, FileVisitor) and compiler/AST visitors.

    Q1. Why must every element implement accept itself?

    Because overload resolution is compile-time: inside each class, this has that class's static type, so v.visit(this) selects the right overload.

    Q2. How do Java 21 features change Visitor?

    Sealed interfaces + pattern-matching switch give exhaustive type-based dispatch without accept/visitor boilerplate (Example 2).

    Q3. How do you return values from visitors?

    Make the visitor generic: interface Visitor<R> { R visitX(X x); } and <R> R accept(Visitor<R> v) (Example 3).

    Q4. Visitor vs. Strategy?

    Strategy swaps one algorithm for one context type; Visitor defines an operation across many element types.

    Q5. How do you visit a tree?

    Composite nodes call accept on their children (structure-driven), or the visitor recurses into children (visitor-driven, which allows pruning).

    Q1. "Explain the expression problem and how you'd choose a design."

    Adding types is easy with OOP polymorphism, adding operations is easy with Visitor/pattern matching; neither makes both easy. Choose based on which axis changes more; in Java 21, sealed + switch for operations, open interfaces for types.

    Q2. "Design a SQL query builder that supports Postgres, MySQL and BigQuery."

    Build an AST of the query (Composite), then dialect visitors render it (quoting, limits, functions); add optimizer passes as visitors; tests per dialect with golden outputs.

    Q3. "A visitor-based tax engine must support 30 countries. Structure?"

    Stable item categories as elements; one visitor per jurisdiction (or a visitor parameterized by rate tables); effective-dated rules; exhaustive handling; golden-file tests per country.

    Q4. "How would you add a new element type to a public visitor API without breaking third parties?"

    Add visit(NewType) as a default method that falls back to a generic visitOther(Element) (or throws UnsupportedOperationException), document it, and version the API. Accept the safety trade-off consciously.

    Q5. "When would you choose a classic visitor over pattern matching in 2026?"

    When element types live in a library you don't control (can't seal), when you need two-hierarchy double dispatch, or when third parties add operations via a published interface.

    Problem: Shapes (circle, rectangle, triangle) need area and perimeter, and more operations later (bounding box, SVG). Implement a generic ShapeVisitor<R> so operations return values and shape classes never change.

    Solution 
    package com.handbook.behavioral.visitor.shapes;

import java.util.List;

/** Challenge solution: area and perimeter as visitors over a closed shape hierarchy. */
public class ShapesDemo {

    interface ShapeVisitor<R> {
        R circle(Circle c);
        R rectangle(Rectangle r);
        R triangle(Triangle t);
    }

    interface Shape {
        <R> R accept(ShapeVisitor<R> v);
    }

    record Circle(double r) implements Shape {
        public <R> R accept(ShapeVisitor<R> v) { return v.circle(this); }
    }

    record Rectangle(double w, double h) implements Shape {
        public <R> R accept(ShapeVisitor<R> v) { return v.rectangle(this); }
    }

    record Triangle(double a, double b, double c) implements Shape {
        public <R> R accept(ShapeVisitor<R> v) { return v.triangle(this); }
    }

    static final ShapeVisitor<Double> AREA = new ShapeVisitor<>() {
        public Double circle(Circle c) { return Math.PI * c.r() * c.r(); }
        public Double rectangle(Rectangle r) { return r.w() * r.h(); }
        public Double triangle(Triangle t) { // Heron's formula
            double s = (t.a() + t.b() + t.c()) / 2;
            return Math.sqrt(s * (s - t.a()) * (s - t.b()) * (s - t.c()));
        }
    };

    static final ShapeVisitor<Double> PERIMETER = new ShapeVisitor<>() {
        public Double circle(Circle c) { return 2 * Math.PI * c.r(); }
        public Double rectangle(Rectangle r) { return 2 * (r.w() + r.h()); }
        public Double triangle(Triangle t) { return t.a() + t.b() + t.c(); }
    };

    public static void main(String[] args) {
        for (Shape s : List.of(new Circle(1), new Rectangle(3, 4), new Triangle(3, 4, 5))) {
            System.out.printf("%-30s area=%6.2f perimeter=%6.2f%n", s, s.accept(AREA), s.accept(PERIMETER));
        }
    }
}

    Output:

    Circle[r=1.0]                  area=  3.14 perimeter=  6.28
Rectangle[w=3.0, h=4.0]        area= 12.00 perimeter= 14.00
Triangle[a=3.0, b=4.0, c=5.0]  area=  6.00 perimeter= 12.00

    Key points to say: <R> R accept(ShapeVisitor<R> v) gives typed results; visitors are stateless constants (safe to reuse); the triangle uses Heron's formula. Then mention the sealed + switch alternative: double area(Shape s) { return switch (s) { case Circle c -> ...; ... }; }.

    • Add operations without changing element classes; one visitor per operation.

    • Easy: new operations. Hard: new element types (the expression problem).

    • Avoid no-op defaults; they hide missing cases.
