    Behavioral Intermediate

    Command¶

    🟡 Intermediate Behavioral Interview frequency ⭐⭐⭐⭐

    TL;DR

    Command turns a request ("do this") into an object. Once it's an object, you can queue it, log it, retry it, send it over the network, replay it later, and undo it. Use it for undo/redo, job queues, scheduled operations, offline-first apps, macros and audit trails.

    1. Intent & Problem It Solves¶

    The problem in plain English: when a button directly calls doc.delete(0, 7), the action is gone the moment it runs. You can't undo it (what was deleted?), you can't queue it for later, and you can't send it to a server when the network comes back. If the action is instead an object (new Delete(doc, 0, 7)) holding everything needed to run it, and to reverse it, all of those become easy.

    Formal definition (GoF):

    Encapsulate a request as an object, thereby letting you parameterize clients with different requests, queue or log requests, and support undoable operations.

    2. Real-World Analogy¶

    A restaurant order slip

    The waiter writes your order on a slip (command) and puts it on the kitchen rail (queue). The chef (receiver) cooks orders in sequence. The slip can be read again for the bill (log), corrected (undo: "cancel the dessert"), or re-made if dropped (retry). The waiter (invoker) never needs to know how to cook.

    4. Naive Approach (Without the Pattern)¶

    deleteButton.onClick(() -> doc.delete(selectionStart, selectionLength));   // can't undo: what was deleted?
payButton.onClick(() -> ledger.debit(acc, amount));                         // runs now or never; no queue, no retry
    • No undo: nothing remembers what happened.
    • No queueing or scheduling: the action is a method call, not data.
    • UI tied to business logic: buttons know how operations are done.

    5. Three Real-World Examples¶

    Example 1: Undo / Redo in a Document Editor (SaaS)¶

    Scenario: A Google-Docs-style editor supports unlimited undo and redo. Each edit is a command that knows how to reverse itself: an insert is undone by deleting the inserted text; a delete is undone by re-inserting the text it removed (which it must remember). A new edit after an undo clears the redo history, as every editor does.

    Design:

    stateDiagram-v2
    direction LR
    state "undo stack" as U
    state "redo stack" as R
    [*] --> U : run(cmd) / execute, push, clear redo
    U --> R : undo() / pop, cmd.undo(), push to redo
    R --> U : redo() / pop, cmd.execute(), push to undo

    Full Code:

    package com.handbook.behavioral.command.editor;

/** Command: an edit as an object, with enough information to reverse itself. */
public interface EditCommand {

    void execute();

    void undo();

    String label();

    record Insert(Document doc, int position, String text) implements EditCommand {
        public void execute() { doc.insert(position, text); }
        public void undo() { doc.delete(position, text.length()); }
        public String label() { return "insert '" + text + "'"; }
    }

    final class Delete implements EditCommand {
        private final Document doc;
        private final int position;
        private final int length;
        private String removed; // (1)!

        public Delete(Document doc, int position, int length) {
            this.doc = doc;
            this.position = position;
            this.length = length;
        }

        public void execute() { removed = doc.delete(position, length); }
        public void undo() { doc.insert(position, removed); }
        public String label() { return "delete " + length + " chars"; }
    }
}
    1. The command remembers what it removed during execute() so undo() can put it back. Commands often need a little state like this.
    package com.handbook.behavioral.command.editor;

import java.util.ArrayDeque;
import java.util.Deque;

/** Invoker: runs commands and keeps the undo/redo history. */
public class Editor {

    private final Deque<EditCommand> undoStack = new ArrayDeque<>();
    private final Deque<EditCommand> redoStack = new ArrayDeque<>();

    public void run(EditCommand command) {
        command.execute();
        undoStack.push(command);
        redoStack.clear(); // (1)!
    }

    public String undo() {
        if (undoStack.isEmpty()) {
            return "nothing to undo";
        }
        EditCommand c = undoStack.pop();
        c.undo();
        redoStack.push(c);
        return "undid " + c.label();
    }

    public String redo() {
        if (redoStack.isEmpty()) {
            return "nothing to redo";
        }
        EditCommand c = redoStack.pop();
        c.execute();
        undoStack.push(c);
        return "redid " + c.label();
    }
}
    1. A new edit invalidates the redo history: redoing an old edit on top of a new one would corrupt the document.
    package com.handbook.behavioral.command.editor;

/** Receiver: knows how to change text; knows nothing about undo. */
public class Document {

    private final StringBuilder text = new StringBuilder();

    public void insert(int position, String s) {
        text.insert(position, s);
    }

    public String delete(int position, int length) {
        String removed = text.substring(position, position + length);
        text.delete(position, position + length);
        return removed;
    }

    public int length() {
        return text.length();
    }

    @Override
    public String toString() {
        return '"' + text.toString() + '"';
    }
}

    package com.handbook.behavioral.command.editor;

import com.handbook.behavioral.command.editor.EditCommand.Delete;
import com.handbook.behavioral.command.editor.EditCommand.Insert;

public class EditorDemo {

    public static void main(String[] args) {
        System.out.println("=== Docs SaaS: Undo / Redo ===");
        Document doc = new Document();
        Editor editor = new Editor();

        editor.run(new Insert(doc, 0, "Hello world"));
        System.out.println("type           -> " + doc);
        editor.run(new Insert(doc, 5, ", dear"));
        System.out.println("insert         -> " + doc);
        editor.run(new Delete(doc, 0, 7));
        System.out.println("delete         -> " + doc);

        System.out.println(editor.undo() + " -> " + doc);
        System.out.println(editor.undo() + " -> " + doc);
        System.out.println(editor.redo() + " -> " + doc);
        editor.run(new Insert(doc, doc.length(), "!"));
        System.out.println("new edit       -> " + doc);
        System.out.println(editor.redo());
    }
}

    Output:

    === Docs SaaS: Undo / Redo ===
type           -> "Hello world"
insert         -> "Hello, dear world"
delete         -> "dear world"
undid delete 7 chars -> "Hello, dear world"
undid insert ', dear' -> "Hello world"
redid insert ', dear' -> "Hello, dear world"
new edit       -> "Hello, dear world!"
nothing to redo

    Why Command here:

    • Undo needs objects that remember what they did.
    • The Editor (invoker) manages history without knowing what an insert or delete is.
    • New edit types (format bold, insert image) plug in with their own undo().

    Example 2: Nightly Batch of Scheduled Payments (Banking)¶

    Scenario: A bank lets customers schedule transfers, bill payments and mobile recharges. At night, a batch job executes them. Commands are data (records), so they can be stored in a database, audited and replayed. Mobile clients sometimes resend the same instruction after a timeout, so each command has an ID, and duplicates are skipped. Failed commands (insufficient funds) go to a dead-letter queue for customer notification, without stopping the batch.

    Design:

    flowchart LR
    App[Mobile / net banking] -->|submit| Q[(Command queue)]
    Q --> P[CommandProcessor<br/>de-duplicate by id]
    P -->|execute| L[Ledger]
    P -->|failure| D[(Dead-letter queue)]
    P -->|audit| A[(Audit log)]

    Full Code:

    package com.handbook.behavioral.command.banking;

import com.handbook.behavioral.command.banking.PaymentCommand.*;

import java.util.ArrayDeque;
import java.util.ArrayList;
import java.util.HashSet;
import java.util.List;
import java.util.Queue;
import java.util.Set;

/** Invoker: queues commands, executes them later, audits, de-duplicates and dead-letters. */
public class CommandProcessor {

    private final Ledger ledger;
    private final Queue<PaymentCommand> queue = new ArrayDeque<>();
    private final Set<String> processed = new HashSet<>();
    private final List<String> deadLetters = new ArrayList<>();

    public CommandProcessor(Ledger ledger) {
        this.ledger = ledger;
    }

    public void submit(PaymentCommand command) {
        queue.add(command); // (1)!
    }

    public void runBatch() {
        while (!queue.isEmpty()) {
            PaymentCommand c = queue.poll();
            if (!processed.add(c.id())) { // (2)!
                System.out.println("  skip duplicate " + c.id());
                continue;
            }
            try {
                execute(c);
                System.out.println("  done " + c);
            } catch (IllegalStateException e) {
                deadLetters.add(c.id() + ": " + e.getMessage());
                System.out.println("  FAILED " + c.id() + " -> dead-letter queue");
            }
        }
    }

    private void execute(PaymentCommand c) {
        switch (c) { // (3)!
            case Transfer t -> { ledger.debit(t.from(), t.amountInr()); ledger.credit(t.to(), t.amountInr()); }
            case PayBill b -> { ledger.debit(b.from(), b.amountInr()); ledger.credit("BILLER:" + b.biller(), b.amountInr()); }
            case MobileRecharge r -> { ledger.debit(r.from(), r.amountInr()); ledger.credit("TELCO:" + r.phone(), r.amountInr()); }
        }
    }

    public List<String> deadLetters() {
        return deadLetters;
    }
}
    1. Submit now, execute later: the request is stored as an object. In production this queue is a database table or a Kafka topic.
    2. Idempotency: the command's ID makes a resent command harmless. This matters far more than undo in real payment systems.
    3. Commands here are pure data, and the processor dispatches with an exhaustive switch over a sealed interface. This "commands as data + handler" style is how CQRS command handlers and job queues usually look.
    package com.handbook.behavioral.command.banking;

/** Commands as plain data: easy to persist, queue, audit and replay. */
public sealed interface PaymentCommand {

    String id();

    record Transfer(String id, String from, String to, long amountInr) implements PaymentCommand {
    }

    record PayBill(String id, String from, String biller, long amountInr) implements PaymentCommand {
    }

    record MobileRecharge(String id, String from, String phone, long amountInr) implements PaymentCommand {
    }
}

    package com.handbook.behavioral.command.banking;

import java.util.HashMap;
import java.util.Map;

/** Receiver: the actual money movement. */
public class Ledger {

    private final Map<String, Long> balances = new HashMap<>(Map.of("ACC-1", 10_000L, "ACC-2", 500L));

    public void debit(String account, long amount) {
        long balance = balances.getOrDefault(account, 0L);
        if (balance < amount) {
            throw new IllegalStateException("insufficient funds in " + account);
        }
        balances.put(account, balance - amount);
    }

    public void credit(String account, long amount) {
        balances.merge(account, amount, Long::sum);
    }

    public long balance(String account) {
        return balances.getOrDefault(account, 0L);
    }
}

    package com.handbook.behavioral.command.banking;

import com.handbook.behavioral.command.banking.PaymentCommand.*;

public class BankingDemo {

    public static void main(String[] args) {
        System.out.println("=== Banking: Nightly Batch of Scheduled Payments ===");
        Ledger ledger = new Ledger();
        CommandProcessor processor = new CommandProcessor(ledger);

        processor.submit(new Transfer("CMD-1", "ACC-1", "ACC-2", 2_000));
        processor.submit(new PayBill("CMD-2", "ACC-1", "ELECTRICITY-BESCOM", 1_450));
        processor.submit(new MobileRecharge("CMD-3", "ACC-2", "98450-00001", 3_000));
        processor.submit(new Transfer("CMD-1", "ACC-1", "ACC-2", 2_000)); // resent by a retrying client

        System.out.println("Running batch:");
        processor.runBatch();
        System.out.println("ACC-1 balance: INR " + ledger.balance("ACC-1"));
        System.out.println("ACC-2 balance: INR " + ledger.balance("ACC-2"));
        System.out.println("Dead letters : " + processor.deadLetters());
    }
}

    Output:

    === Banking: Nightly Batch of Scheduled Payments ===
Running batch:
  done Transfer[id=CMD-1, from=ACC-1, to=ACC-2, amountInr=2000]
  done PayBill[id=CMD-2, from=ACC-1, biller=ELECTRICITY-BESCOM, amountInr=1450]
  FAILED CMD-3 -> dead-letter queue
  skip duplicate CMD-1
ACC-1 balance: INR 6550
ACC-2 balance: INR 2500
Dead letters : [CMD-3: insufficient funds in ACC-2]

    Why Command here:

    • Requests must be stored, scheduled, audited and replayed, so they need to be data.
    • De-duplication by command ID makes retries safe.
    • Failures are isolated per command (dead-letter), not per batch.

    Example 3: Offline Driver App (Ride-hailing)¶

    Scenario: Drivers lose signal in tunnels, basements and rural roads. The driver app must keep working: "start trip" and "end trip" are recorded as commands with their original timestamps and IDs, queued in an outbox while offline, and replayed in order when the network returns. Flaky networks sometimes deliver the same action twice, so the server applies each action ID only once. Fares must use the real trip times, not the replay time.

    Design:

    sequenceDiagram
    autonumber
    participant D as Driver
    participant A as DriverApp (invoker)
    participant O as Outbox
    participant S as TripServer (receiver)
    D->>A: StartTrip (09:09)
    Note over A: offline
    A->>O: queue
    D->>A: EndTrip (09:31)
    A->>O: queue
    Note over A: back online
    A->>S: replay StartTrip @09:09
    A->>S: replay EndTrip @09:31
    S->>S: ignore duplicates by id

    Full Code:

    package com.handbook.behavioral.command.offline;

import java.util.ArrayList;
import java.util.List;
import java.util.function.Consumer;

/** Invoker on the phone: sends immediately when online, queues when offline, replays in order. */
public class DriverApp {

    private final Consumer<DriverAction> server;
    private final List<DriverAction> outbox = new ArrayList<>();
    private boolean online = true;

    public DriverApp(Consumer<DriverAction> server) {
        this.server = server;
    }

    public void setOnline(boolean online) {
        this.online = online;
        System.out.println(online ? "[network] back online, replaying " + outbox.size() + " action(s)" : "[network] lost signal");
        if (online) {
            outbox.forEach(server); // (1)!
            outbox.clear();
        }
    }

    public void perform(DriverAction action) {
        if (online) {
            server.accept(action);
        } else {
            outbox.add(action);
            System.out.println("  queued offline: " + action.getClass().getSimpleName() + " at " + action.at());
        }
    }
}
    1. Replay in the original order, so the server sees start before end. Real apps persist the outbox to local storage (SQLite) so it survives an app restart.
    package com.handbook.behavioral.command.offline;

/** Commands recorded on the phone while offline. Each carries an id and the time it happened. */
public sealed interface DriverAction {

    String id();

    String at();

    record AcceptTrip(String id, String at, String tripId) implements DriverAction {
    }

    record ArrivedAtPickup(String id, String at, String tripId) implements DriverAction {
    }

    record StartTrip(String id, String at, String tripId, String otp) implements DriverAction {
    }

    record EndTrip(String id, String at, String tripId, double km) implements DriverAction {
    }
}

    package com.handbook.behavioral.command.offline;

import com.handbook.behavioral.command.offline.DriverAction.*;

import java.util.HashSet;
import java.util.Set;

/** Receiver on the server: applies actions idempotently using the action id. */
public class TripServer {

    private final Set<String> seen = new HashSet<>();

    public void apply(DriverAction action) {
        if (!seen.add(action.id())) {
            System.out.println("  server: ignored duplicate " + action.id());
            return;
        }
        String what = switch (action) {
            case AcceptTrip a -> "trip " + a.tripId() + " accepted";
            case ArrivedAtPickup a -> "driver at pickup for " + a.tripId();
            case StartTrip s -> "trip " + s.tripId() + " started (OTP " + s.otp() + " verified)";
            case EndTrip e -> "trip " + e.tripId() + " ended, " + e.km() + " km, fare INR " + Math.round(50 + 14 * e.km());
        };
        System.out.println("  server @" + action.at() + ": " + what);
    }
}

    package com.handbook.behavioral.command.offline;

import com.handbook.behavioral.command.offline.DriverAction.*;

public class OfflineDemo {

    public static void main(String[] args) {
        System.out.println("=== Ride-hailing: Driver App Through a Tunnel ===");
        TripServer server = new TripServer();
        DriverApp app = new DriverApp(server::apply);

        app.perform(new AcceptTrip("A1", "09:00", "TRIP-77"));
        app.perform(new ArrivedAtPickup("A2", "09:07", "TRIP-77"));
        app.setOnline(false);
        app.perform(new StartTrip("A3", "09:09", "TRIP-77", "4821"));
        app.perform(new EndTrip("A4", "09:31", "TRIP-77", 8.4));
        app.setOnline(true);
        server.apply(new EndTrip("A4", "09:31", "TRIP-77", 8.4)); // a flaky network re-sends A4
    }
}

    Output:

    === Ride-hailing: Driver App Through a Tunnel ===
  server @09:00: trip TRIP-77 accepted
  server @09:07: driver at pickup for TRIP-77
[network] lost signal
  queued offline: StartTrip at 09:09
  queued offline: EndTrip at 09:31
[network] back online, replaying 2 action(s)
  server @09:09: trip TRIP-77 started (OTP 4821 verified)
  server @09:31: trip TRIP-77 ended, 8.4 km, fare INR 168
  server: ignored duplicate A4

    Why Command here:

    • Actions must outlive the moment they happen: queued, persisted, replayed.
    • Each command carries its own context (time, IDs), so replays are accurate.
    • The same command objects travel from phone to server, which is the basis of offline-first sync.

    package com.handbook.behavioral.command;

import com.handbook.behavioral.command.banking.CommandProcessor;
import com.handbook.behavioral.command.banking.Ledger;
import com.handbook.behavioral.command.banking.PaymentCommand.Transfer;
import com.handbook.behavioral.command.cart.CartCommands.*;
import com.handbook.behavioral.command.editor.Document;
import com.handbook.behavioral.command.editor.EditCommand.Delete;
import com.handbook.behavioral.command.editor.EditCommand.Insert;
import com.handbook.behavioral.command.editor.Editor;
import org.junit.jupiter.api.Test;

import java.util.List;

import static org.assertj.core.api.Assertions.assertThat;

class CommandTest {

    @Test
    void undoRestoresEveryPreviousState() {
        Document doc = new Document();
        Editor editor = new Editor();
        editor.run(new Insert(doc, 0, "abc"));
        editor.run(new Delete(doc, 1, 1));
        assertThat(doc).hasToString("\"ac\"");
        editor.undo();
        assertThat(doc).hasToString("\"abc\"");
        editor.undo();
        assertThat(doc).hasToString("\"\"");
        assertThat(editor.undo()).isEqualTo("nothing to undo");
    }

    @Test
    void newEditClearsRedo() {
        Document doc = new Document();
        Editor editor = new Editor();
        editor.run(new Insert(doc, 0, "a"));
        editor.undo();
        editor.run(new Insert(doc, 0, "b"));
        assertThat(editor.redo()).isEqualTo("nothing to redo");
    }

    @Test
    void duplicateCommandsExecuteOnce() {
        Ledger ledger = new Ledger();
        CommandProcessor p = new CommandProcessor(ledger);
        p.submit(new Transfer("X", "ACC-1", "ACC-2", 100));
        p.submit(new Transfer("X", "ACC-1", "ACC-2", 100));
        p.runBatch();
        assertThat(ledger.balance("ACC-1")).isEqualTo(9_900);
    }

    @Test
    void macroUndoIsAllOrNothing() {
        Cart cart = new Cart();
        Macro m = new Macro(List.of(new AddItem(cart, "A", 1), new AddItem(cart, "B", 2)));
        m.execute();
        m.undo();
        assertThat(cart).hasToString("{}");
    }
}

    6. Variations & Modern Java Take¶

    Variation Notes
    Lambdas as commands Runnable, Callable, Supplier are commands without undo: executor.submit(() -> sendEmail(order))
    Commands as data + handler (Example 2) Records + sealed interface + switch; serializable; the CQRS style
    Undoable commands (Example 1) execute() + undo(); commands store what they need to reverse
    Macro commands (coding challenge) A composite command that runs steps in order and undoes them in reverse
    Compensating commands When undo is impossible (an email was sent), issue a new command that compensates (send a correction); see Saga

    7. Where It Lives in Real Frameworks¶

    Where Command
    JDK Runnable, Callable submitted to ExecutorService; TimerTask
    Swing Action / AbstractAction (one action used by a menu item, a toolbar button and a shortcut) and UndoManager / UndoableEdit
    Spring Batch Tasklet, Step
    Spring Shell / picocli CLI commands as objects
    Axon Framework @CommandHandler with command objects (CQRS)
    Message queues Kafka/RabbitMQ messages carrying commands ("ReserveStock") to handlers
    Hystrix (legacy) HystrixCommand: every remote call wrapped as a command object

    8. Pros, Cons & Trade-offs¶

    ✅ Pros ❌ Cons
    Undo/redo, queueing, scheduling, logging and retries More classes (one per operation) unless you use lambdas or records
    Decouples who asks from who does Undo logic can be hard (or impossible for external side effects)
    Commands can be composed (macros) Command history uses memory; bound it
    Serializable commands enable distributed and offline processing Replaying old commands after schema changes needs versioning

    9. Pitfalls & Anti-Patterns¶

    Non-idempotent replays

    Queued commands get retried and duplicated. Without an ID and de-duplication (Examples 2 and 3), retries double-charge customers.

    Undo that doesn't really undo

    "Undo send email" is impossible. Be honest: offer compensation (send a correction) or a delay before executing (Gmail's "Undo send" just waits a few seconds).

    Commands that capture mutable state

    A command holding a reference to a mutable Cart may see different data when it runs later. Capture values (IDs, amounts) at creation time.

    Unbounded history

    Infinite undo stacks in long editing sessions eat memory. Limit them, or compact old commands into snapshots (see Memento).

    10. Senior / Architect Deep Dive (10–15 yrs)¶

    Commands vs. events. A command is a request that may be rejected ("ReserveStock", imperative). An event is a fact that already happened ("StockReserved", past tense). CQRS systems receive commands, validate them against the current state, and emit events. Mixing the two up leads to confusing systems; be precise in design reviews.

    Command queues at scale. Persist commands before acknowledging (transactional outbox), process with at-least-once delivery, make handlers idempotent, partition by entity (account ID) to keep per-entity ordering, and route poison commands to a dead-letter queue with alerting.

    Collaborative editing. Undo in a multi-user editor is hard: Alice's undo must not revert Bob's later edits. Real editors (Google Docs, Figma) use Operational Transformation or CRDTs, transforming commands against concurrent ones. Mentioning this shows depth.

    Versioning. Stored commands outlive code. Include a schema version in each command and keep handlers able to read old versions, or migrate the queue during deploys.

    War story: the batch that paid twice

    A bank's scheduled-payments batch crashed halfway through. The operator re-ran the whole batch. Commands had no IDs, so the first half executed again: about 8,000 customers paid their bills twice, and refunds took a week. Fix: every command got a unique ID stored with a "processed" marker in the same database transaction as the ledger update; the processor skips processed IDs; re-running a batch became safe by design. Lesson: if a command can be stored, it can be replayed. Idempotency isn't optional.

    12. Interview Corner¶

    Q1. What is the Command pattern?

    A behavioral pattern that encapsulates a request as an object, so requests can be parameterized, queued, logged and undone.

    Q2. Name the participants.

    Command (interface), Concrete command (holds receiver + parameters), Receiver (does the work), Invoker (runs commands), Client (creates them).

    Q3. How do you implement undo?

    Each command implements undo() that reverses execute(); the invoker keeps a stack of executed commands and pops one to undo.

    Q4. Give Java examples.

    Runnable/Callable in ExecutorService, Swing Action, and UndoManager.

    Q5. Advantage over calling methods directly?

    Decoupling (the invoker doesn't know the receiver), and requests become data you can store, delay, retry or undo.

    Q1. How would you implement redo?

    Two stacks: undo pops from the undo stack, calls undo(), pushes to the redo stack; redo does the reverse; a new command clears the redo stack.

    Q2. What is a macro command?

    A command made of other commands (Composite); execute() runs them in order and undo() undoes them in reverse order.

    Q3. How do you make queued commands safe to retry?

    Give each command a unique ID and make handlers idempotent (record processed IDs atomically with the effect).

    Q4. Command vs. Strategy?

    A command represents what to do (a request, often with its data); a strategy represents how to do something (an interchangeable algorithm).

    Q5. How do lambdas relate to Command?

    A lambda is a command with only execute(). Use lambdas for fire-and-forget tasks; use classes or records when you need undo, IDs, serialization or logging.

    Q1. "Design a job scheduling system (like a distributed cron) for millions of jobs."

    Jobs as persisted commands (type, payload, schedule, idempotency key); time-partitioned storage or a delay queue; leasing workers with heartbeats; at-least-once execution with idempotent handlers; retries with backoff; dead-letter queues; per-tenant fairness; observability per job type.

    Q2. "Commands vs. events in CQRS: walk me through a 'place order' flow."

    PlaceOrder command goes to a handler that validates against the aggregate state and emits OrderPlaced (event), stored in an event store or table plus an outbox; projections update read models; other services react to the event. Commands can fail; events are facts.

    Q3. "How would you implement undo in a collaborative editor?"

    Per-user undo stacks of operations; undo generates an inverse operation that is transformed (OT) or merged (CRDT) against concurrent operations from others; don't revert other users' work.

    Q4. "Stored commands from last year fail to deserialize after a refactor. Prevent it."

    Schema versioning in every command; tolerant readers; upcasters that convert old versions; contract tests with stored samples of every version; never reuse field meanings.

    Q5. "An offline-first mobile app syncs commands to the server. What can go wrong?"

    Duplicates (use IDs), ordering (sequence numbers per device), conflicts (server state changed meanwhile; need conflict resolution rules), clock skew (server validates times), stale permissions, and very old queued commands (expire them).

    Problem (grocery): "Reorder my usual" adds several items to the cart in one tap. Implement it as a macro command whose undo removes exactly what it added, leaving items that were already in the cart untouched.

    Solution 
    package com.handbook.behavioral.command.cart;

import java.util.ArrayList;
import java.util.LinkedHashMap;
import java.util.List;
import java.util.Map;

/** Challenge solution: "Reorder my usual" as a macro command with all-or-nothing undo. */
public final class CartCommands {

    private CartCommands() {
    }

    public static class Cart {
        private final Map<String, Integer> lines = new LinkedHashMap<>();

        void add(String sku, int qty) { lines.merge(sku, qty, Integer::sum); }

        void remove(String sku, int qty) {
            lines.computeIfPresent(sku, (k, v) -> v - qty <= 0 ? null : v - qty);
        }

        @Override
        public String toString() { return lines.toString(); }
    }

    public interface Command {
        void execute();
        void undo();
    }

    public record AddItem(Cart cart, String sku, int qty) implements Command {
        public void execute() { cart.add(sku, qty); }
        public void undo() { cart.remove(sku, qty); }
    }

    public static final class Macro implements Command {
        private final List<Command> steps;

        public Macro(List<Command> steps) {
            this.steps = List.copyOf(steps);
        }

        public void execute() {
            steps.forEach(Command::execute);
        }

        public void undo() {
            List<Command> reversed = new ArrayList<>(steps);
            java.util.Collections.reverse(reversed);
            reversed.forEach(Command::undo); // undo in reverse order
        }
    }
}

    package com.handbook.behavioral.command.cart;

import com.handbook.behavioral.command.cart.CartCommands.*;

import java.util.List;

public class MacroDemo {

    public static void main(String[] args) {
        Cart cart = new Cart();
        new AddItem(cart, "BANANA-6", 1).execute();
        System.out.println("Cart before        : " + cart);

        Macro usual = new Macro(List.of(
                new AddItem(cart, "MILK-1L", 2), new AddItem(cart, "BREAD-WW", 1), new AddItem(cart, "BANANA-6", 1)));
        usual.execute();
        System.out.println("After 'my usual'   : " + cart);
        usual.undo();
        System.out.println("After undo         : " + cart);
    }
}

    Output:

    Cart before        : {BANANA-6=1}
After 'my usual'   : {BANANA-6=2, MILK-1L=2, BREAD-WW=1}
After undo         : {BANANA-6=1}

    Key points to say: the macro is a Composite of commands; undo runs in reverse order; each AddItem undoes only its own quantity, so the banana that was already there stays. Follow-up: if a step fails halfway, undo the steps that already ran (transactional macro).

    Behavioural tie-in (STAR) for experienced candidates

    • S: Re-running a failed payments batch double-paid 8,000 bills.
    • T: Make batch re-runs safe and restore customer trust.
    • A: Introduced command IDs with processed markers written in the same transaction as ledger entries, a dead-letter queue for failures, and a runbook that says "re-run freely".
    • R: Zero duplicate payments in the 18 months since, including 3 more batch crashes that were simply re-run.
