    Interpreter¶

    🔴 Advanced Behavioral Interview frequency ⭐⭐

    TL;DR

    Interpreter represents the grammar of a small language as a tree of objects, where each node knows how to evaluate itself. Use it for small, stable domain-specific languages (DSLs): promo rules, pricing formulas, search filters, schedules. Business people write the rules; your code runs them.

    1. Intent & Problem It Solves¶

    The problem in plain English: marketing changes promotion rules every week: "carts over INR 999 in electronics, or for gold members, except in Leh". If every rule is Java code, every change needs a developer, a review and a deployment. If rules are text in a small language that your system can interpret, marketing can change them through an admin screen.

    Formal definition (GoF):

    Given a language, define a representation for its grammar along with an interpreter that uses the representation to interpret sentences in the language.

    How it works:

    1. Parse the text into an abstract syntax tree (AST): one object per grammar construct.
    2. Interpret: call eval() / matches() on the root; each node evaluates its children and combines the results.
    Grammar part Node type Example
    Terminal (no children) A value or a leaf test cart_total >= 999, a number, a variable
    Non-terminal (has children) Combines other expressions AND, OR, +, max(a, b)

    2. Real-World Analogy¶

    Musical notation

    Sheet music is a small language. Notes are terminals; bars, repeats and chords combine them. A musician (the interpreter) reads the score and produces sound. Composers write new pieces without changing the musician.

    Expression interpret(context)
    Terminal expression Leaf of the grammar (a comparison, a number)

    Context Input data (cart fields, variables, date and time)
    Parser Turns text into the AST (not part of GoF's pattern, but always needed in practice)

    The AST is a Composite; the interpreter is a recursive walk over it.

    4. Naive Approach (Without the Pattern)¶

    boolean offerApplies(Cart c) {
    // Changed every week by a developer, after a ticket from marketing:
    return c.total() >= 999 && (c.category().equals("electronics") || c.tier().equals("gold"))
            && !c.city().equals("Leh");
}
    • Every rule change is a code change and a deployment.
    • Business users can't see, test or own the rules.
    • Rules can't vary per country or campaign without more ifs.

    5. Three Real-World Examples¶

    Example 1: Promo Rules Written by Marketing (E-commerce)¶

    Scenario: An e-commerce site's promotions team defines eligibility rules in an admin UI using a tiny language: comparisons (>=, ==), AND, OR, NOT and parentheses. Rules are stored as text, parsed once when saved (so typos are rejected immediately), and evaluated against every cart. AND must bind tighter than OR, as in every programming language, or rules will silently mean something else.

    Design:

    flowchart TB
    A1[AND] --> A2[AND]
    A1 --> N[NOT]
    A2 --> C1["cart_total >= 999"]
    A2 --> O[OR]
    O --> C2["category == 'electronics'"]
    O --> C3["member_tier == 'gold'"]
    N --> C4["city == 'Leh'"]

    Full Code:

    package com.handbook.behavioral.interpreter.promo;

import java.util.Map;

/** Abstract syntax tree for promo rules. Each node interprets itself against a cart context. */
public sealed interface Rule {

    boolean matches(Map<String, Object> cart); // (1)!

    record And(Rule left, Rule right) implements Rule {
        public boolean matches(Map<String, Object> c) { return left.matches(c) && right.matches(c); }
        public String toString() { return "(" + left + " AND " + right + ")"; }
    }

    record Or(Rule left, Rule right) implements Rule {
        public boolean matches(Map<String, Object> c) { return left.matches(c) || right.matches(c); }
        public String toString() { return "(" + left + " OR " + right + ")"; }
    }

    record Not(Rule inner) implements Rule {
        public boolean matches(Map<String, Object> c) { return !inner.matches(c); }
        public String toString() { return "NOT " + inner; }
    }

    record Compare(String field, String op, Object value) implements Rule { // (2)!
        public boolean matches(Map<String, Object> c) {
            Object actual = c.get(field);
            if (actual == null) {
                return false;
            }
            if (value instanceof Double expected) {
                double a = ((Number) actual).doubleValue();
                return switch (op) {
                    case ">" -> a > expected;
                    case ">=" -> a >= expected;
                    case "<" -> a < expected;
                    case "<=" -> a <= expected;
                    case "==" -> a == expected;
                    default -> throw new IllegalStateException(op);
                };
            }
            return switch (op) {
                case "==" -> actual.toString().equals(value);
                case "!=" -> !actual.toString().equals(value);
                default -> throw new IllegalArgumentException("Operator " + op + " needs a number");
            };
        }

        public String toString() { return field + " " + op + " " + (value instanceof String ? "'" + value + "'" : value); }
    }
}
    1. The interpreter method. Every node evaluates itself against the cart context; non-terminals delegate to their children.
    2. The terminal expression: a single comparison. A missing field means "no match" rather than an error, which is a deliberate rule-language decision.
    package com.handbook.behavioral.interpreter.promo;

import java.util.ArrayList;
import java.util.List;
import java.util.regex.Matcher;
import java.util.regex.Pattern;

/**
 * Recursive-descent parser. Grammar:
 * <pre>
 *   expr    := term ( OR term )*
 *   term    := factor ( AND factor )*
 *   factor  := NOT factor | '(' expr ')' | compare
 *   compare := IDENT OP ( NUMBER | 'string' )
 * </pre>
 */
public final class RuleParser {

    private static final Pattern TOKEN = Pattern.compile(
            "\\s*(?:(\\d+(?:\\.\\d+)?)|'([^']*)'|(>=|<=|==|!=|>|<|\\(|\\))|([A-Za-z_][A-Za-z_0-9]*))");

    private final List<String> tokens = new ArrayList<>();
    private int pos;

    private RuleParser(String text) {
        Matcher m = TOKEN.matcher(text);
        int end = 0;
        while (m.lookingAt()) {
            if (m.group(2) != null) {
                tokens.add("'" + m.group(2)); // mark strings with a leading quote
            } else {
                tokens.add(m.group().strip());
            }
            end = m.end();
            m.region(end, text.length());
        }
        if (!text.substring(end).isBlank()) {
            throw new IllegalArgumentException("Unexpected input at: " + text.substring(end));
        }
    }

    public static Rule parse(String text) {
        RuleParser p = new RuleParser(text);
        Rule rule = p.expr();
        if (p.pos != p.tokens.size()) {
            throw new IllegalArgumentException("Unexpected token: " + p.tokens.get(p.pos));
        }
        return rule;
    }

    private Rule expr() {
        Rule left = term();
        while (accept("OR")) {
            left = new Rule.Or(left, term());
        }
        return left;
    }

    private Rule term() {
        Rule left = factor();
        while (accept("AND")) {
            left = new Rule.And(left, factor());
        }
        return left;
    }

    private Rule factor() {
        if (accept("NOT")) {
            return new Rule.Not(factor());
        }
        if (accept("(")) {
            Rule inner = expr();
            expect(")");
            return inner;
        }
        String field = next();
        String op = next();
        String raw = next();
        Object value = raw.startsWith("'") ? raw.substring(1) : Double.valueOf(raw);
        return new Rule.Compare(field, op, value);
    }

    private boolean accept(String token) {
        if (pos < tokens.size() && tokens.get(pos).equalsIgnoreCase(token)) {
            pos++;
            return true;
        }
        return false;
    }

    private void expect(String token) {
        if (!accept(token)) {
            throw new IllegalArgumentException("Expected " + token);
        }
    }

    private String next() {
        if (pos >= tokens.size()) {
            throw new IllegalArgumentException("Unexpected end of rule");
        }
        return tokens.get(pos++);
    }
}

    package com.handbook.behavioral.interpreter.promo;

import java.util.List;
import java.util.Map;

public class PromoDemo {

    public static void main(String[] args) {
        System.out.println("=== E-commerce: Promo Rules Written by Marketing ===");
        String text = "cart_total >= 999 AND (category == 'electronics' OR member_tier == 'gold') AND NOT city == 'Leh'";
        Rule rule = RuleParser.parse(text);
        System.out.println("Rule text : " + text);
        System.out.println("Parsed AST: " + rule);

        List<Map<String, Object>> carts = List.of(
                Map.of("cart_total", 1499, "category", "electronics", "member_tier", "silver", "city", "Pune"),
                Map.of("cart_total", 1200, "category", "fashion", "member_tier", "gold", "city", "Delhi"),
                Map.of("cart_total", 650, "category", "electronics", "member_tier", "gold", "city", "Pune"),
                Map.of("cart_total", 5000, "category", "electronics", "member_tier", "gold", "city", "Leh"));
        for (Map<String, Object> cart : carts) {
            System.out.printf("total=%-5s category=%-12s tier=%-7s city=%-6s -> %s%n",
                    cart.get("cart_total"), cart.get("category"), cart.get("member_tier"), cart.get("city"),
                    rule.matches(cart) ? "OFFER APPLIES" : "no offer");
        }
        try {
            RuleParser.parse("cart_total >= ");
        } catch (IllegalArgumentException e) {
            System.out.println("Bad rule rejected: " + e.getMessage());
        }
    }
}

    Output:

    === E-commerce: Promo Rules Written by Marketing ===
Rule text : cart_total >= 999 AND (category == 'electronics' OR member_tier == 'gold') AND NOT city == 'Leh'
Parsed AST: ((cart_total >= 999.0 AND (category == 'electronics' OR member_tier == 'gold')) AND NOT city == 'Leh')
total=1499  category=electronics  tier=silver  city=Pune   -> OFFER APPLIES
total=1200  category=fashion      tier=gold    city=Delhi  -> OFFER APPLIES

total=5000  category=electronics  tier=gold    city=Leh    -> no offer

    The printed AST makes precedence visible: the parser grouped OR inside the parentheses and AND everywhere else, exactly as written.

    Why Interpreter here:

    • Rules change weekly and belong to business users.
    • A small grammar (4 constructs) is easy to parse, document and test.
    • Parsing on save gives immediate feedback; evaluation per cart is a cheap tree walk.

    Example 2: Tariff Formulas (Telecom)¶

    Scenario: A telecom operator's pricing team defines postpaid bills as formulas: rental, plus extra minutes beyond the free allowance, plus extra data beyond the free GB, and roaming capped at a maximum. Tariffs change with every marketing campaign and regulatory update. Formulas are stored in the product catalogue and evaluated for millions of customers at month-end, so they're parsed once and the AST is reused.

    Design:

    flowchart TB
    P1["+"] --> P2["+"]
    P1 --> M2["*"]
    P2 --> R[rental]
    P2 --> M1["*"]
    M1 --> MX1["max(minutes - free_minutes, 0)"]
    M1 --> PM[per_min]
    M2 --> MX2["max(data_gb - free_gb, 0)"]
    M2 --> PG[per_gb]

    Full Code:

    package com.handbook.behavioral.interpreter.billing;

import java.util.Map;

/** Arithmetic expression AST: numbers, variables, + - * /, and max/min functions. */
public sealed interface Formula {

    double eval(Map<String, Double> vars);

    record Num(double value) implements Formula {
        public double eval(Map<String, Double> v) { return value; }
    }

    record Var(String name) implements Formula {
        public double eval(Map<String, Double> v) {
            Double value = v.get(name);
            if (value == null) {
                throw new IllegalArgumentException("Unknown variable: " + name);
            }
            return value;
        }
    }

    record BinOp(char op, Formula left, Formula right) implements Formula {
        public double eval(Map<String, Double> v) {
            double a = left.eval(v), b = right.eval(v);
            return switch (op) {
                case '+' -> a + b;
                case '-' -> a - b;
                case '*' -> a * b;
                case '/' -> a / b;
                default -> throw new IllegalStateException();
            };
        }
    }

    record Call(String fn, Formula a, Formula b) implements Formula {
        public double eval(Map<String, Double> v) {
            return switch (fn) {
                case "max" -> Math.max(a.eval(v), b.eval(v));
                case "min" -> Math.min(a.eval(v), b.eval(v));
                default -> throw new IllegalArgumentException("Unknown function: " + fn);
            };
        }
    }
}

    package com.handbook.behavioral.interpreter.billing;

/**
 * expr   := term (('+'|'-') term)*
 * term   := factor (('*'|'/') factor)*
 * factor := NUMBER | IDENT | IDENT '(' expr ',' expr ')' | '(' expr ')'
 */
public final class FormulaParser {

    private final String s;
    private int i;

    private FormulaParser(String s) {
        this.s = s.replace(" ", "");
    }

    public static Formula parse(String text) {
        FormulaParser p = new FormulaParser(text);
        Formula f = p.expr();
        if (p.i != p.s.length()) {
            throw new IllegalArgumentException("Unexpected '" + p.s.charAt(p.i) + "' at " + p.i);
        }
        return f;
    }

    private Formula expr() {
        Formula f = term();
        while (i < s.length() && (s.charAt(i) == '+' || s.charAt(i) == '-')) {
            char op = s.charAt(i++);
            f = new Formula.BinOp(op, f, term());
        }
        return f;
    }

    private Formula term() {
        Formula f = factor();
        while (i < s.length() && (s.charAt(i) == '*' || s.charAt(i) == '/')) {
            char op = s.charAt(i++);
            f = new Formula.BinOp(op, f, factor());
        }
        return f;
    }

    private Formula factor() {
        if (s.charAt(i) == '(') {
            i++;
            Formula f = expr();
            i++; // ')'
            return f;
        }
        int start = i;
        if (Character.isDigit(s.charAt(i))) {
            while (i < s.length() && (Character.isDigit(s.charAt(i)) || s.charAt(i) == '.')) {
                i++;
            }
            return new Formula.Num(Double.parseDouble(s.substring(start, i)));
        }
        while (i < s.length() && (Character.isLetterOrDigit(s.charAt(i)) || s.charAt(i) == '_')) {
            i++;
        }
        String name = s.substring(start, i);
        if (i < s.length() && s.charAt(i) == '(') {
            i++;
            Formula a = expr();
            i++; // ','
            Formula b = expr();
            i++; // ')'
            return new Formula.Call(name, a, b);
        }
        return new Formula.Var(name);
    }
}

    package com.handbook.behavioral.interpreter.billing;

import java.util.Map;

public class BillingDemo {

    public static void main(String[] args) {
        System.out.println("=== Telecom: Tariff Formulas Configured by the Pricing Team ===");
        // Stored in the product catalogue, not in code:
        String postpaid = "rental + max(minutes - free_minutes, 0) * per_min + max(data_gb - free_gb, 0) * per_gb";
        String roaming = "min(minutes * intl_rate, cap)";
        Formula bill = FormulaParser.parse(postpaid);
        Formula roam = FormulaParser.parse(roaming);

        Map<String, Double> light = Map.of("rental", 399.0, "minutes", 250.0, "free_minutes", 300.0,
                "per_min", 1.0, "data_gb", 18.0, "free_gb", 20.0, "per_gb", 50.0);
        Map<String, Double> heavy = Map.of("rental", 399.0, "minutes", 420.0, "free_minutes", 300.0,
                "per_min", 1.0, "data_gb", 26.5, "free_gb", 20.0, "per_gb", 50.0);

        System.out.printf("Light user bill : INR %.2f%n", bill.eval(light));
        System.out.printf("Heavy user bill : INR %.2f%n", bill.eval(heavy));
        System.out.printf("Roaming 30 min  : INR %.2f%n", roam.eval(Map.of("minutes", 30.0, "intl_rate", 25.0, "cap", 999.0)));
        System.out.printf("Roaming 90 min  : INR %.2f (capped)%n", roam.eval(Map.of("minutes", 90.0, "intl_rate", 25.0, "cap", 999.0)));
    }
}

    Output:

    === Telecom: Tariff Formulas Configured by the Pricing Team ===
Light user bill : INR 399.00
Heavy user bill : INR 844.00
Roaming 30 min  : INR 750.00
Roaming 90 min  : INR 999.00 (capped)

    Heavy user: 399 + (420 − 300) × 1 + (26.5 − 20) × 50 = 399 + 120 + 325 = INR 844.

    Money and double

    The demo uses double to keep the grammar small. A real billing interpreter evaluates with BigDecimal and an explicit rounding rule per tariff.

    Why Interpreter here:

    • Pricing is data owned by the pricing team, not code.
    • Parse once, evaluate millions of times: the AST is built at load time.
    • New functions (ceil, if) are new node types; existing formulas keep working.

    Example 3: Warehouse Receiving Hours (Logistics)¶

    Scenario: A logistics network has hundreds of warehouses and hubs, each with receiving hours like MON-FRI 09:00-18:00, SAT 10:00-14:00, or night hubs with FRI-MON 22:00-23:59 (wrapping around the weekend). Trucks are routed only to sites that will accept them on arrival. Hours are edited by site managers as text, and the routing engine must interpret them.

    Design:

    flowchart LR
    S["schedule"] --> W1["window: MON-FRI 09:00-18:00"]
    S --> W2["window: SAT 10:00-14:00"]
    Q["isOpen(SATURDAY, 15:00)?"] --> S
    S -->|"any window contains it?"| A[false: wait]

    Full Code:

    package com.handbook.behavioral.interpreter.hours;

import java.time.DayOfWeek;
import java.time.LocalTime;
import java.util.ArrayList;
import java.util.EnumSet;
import java.util.List;
import java.util.Set;

/**
 * Interprets expressions like "MON-FRI 09:00-18:00, SAT 10:00-14:00".
 * Grammar: schedule := rule (',' rule)* ; rule := days ' ' time '-' time ; days := DAY | DAY '-' DAY
 */
public final class OpeningHours {

    private record Window(Set<DayOfWeek> days, LocalTime from, LocalTime to) { // terminal-level expression
        boolean contains(DayOfWeek day, LocalTime t) {
            return days.contains(day) && !t.isBefore(from) && t.isBefore(to);
        }
    }

    private final List<Window> windows = new ArrayList<>(); // non-terminal: OR of windows

    private OpeningHours() {
    }

    public static OpeningHours parse(String text) {
        OpeningHours h = new OpeningHours();
        for (String rule : text.split(",")) {
            String[] parts = rule.strip().split(" ");
            String[] times = parts[1].split("-");
            h.windows.add(new Window(days(parts[0]), LocalTime.parse(times[0]), LocalTime.parse(times[1])));
        }
        return h;
    }

    private static Set<DayOfWeek> days(String spec) {
        String[] range = spec.split("-");
        DayOfWeek from = day(range[0]);
        DayOfWeek to = range.length == 2 ? day(range[1]) : from;
        Set<DayOfWeek> result = EnumSet.noneOf(DayOfWeek.class);
        for (DayOfWeek d = from; ; d = d.plus(1)) {
            result.add(d);
            if (d == to) {
                return result;
            }
        }
    }

    private static DayOfWeek day(String abbrev) {
        for (DayOfWeek d : DayOfWeek.values()) {
            if (d.name().startsWith(abbrev)) {
                return d;
            }
        }
        throw new IllegalArgumentException("Unknown day: " + abbrev);
    }

    public boolean isOpen(DayOfWeek day, LocalTime time) {
        return windows.stream().anyMatch(w -> w.contains(day, time));
    }
}

    package com.handbook.behavioral.interpreter.hours;

import java.time.DayOfWeek;
import java.time.LocalTime;

public class HoursDemo {

    public static void main(String[] args) {
        System.out.println("=== Logistics: Warehouse Receiving Hours ===");
        OpeningHours bhiwandi = OpeningHours.parse("MON-FRI 09:00-18:00, SAT 10:00-14:00");
        OpeningHours nightHub = OpeningHours.parse("FRI-MON 22:00-23:59");

        Object[][] arrivals = {
                {DayOfWeek.WEDNESDAY, "11:30"}, {DayOfWeek.SATURDAY, "15:00"},
                {DayOfWeek.SUNDAY, "10:00"}, {DayOfWeek.SUNDAY, "22:30"}};
        for (Object[] a : arrivals) {
            DayOfWeek day = (DayOfWeek) a[0];
            LocalTime t = LocalTime.parse((String) a[1]);
            System.out.printf("Truck %-9s %s -> Bhiwandi: %-6s Night hub: %s%n", day, t,
                    bhiwandi.isOpen(day, t) ? "accept" : "wait", nightHub.isOpen(day, t) ? "accept" : "wait");
        }
    }
}

    Output:

    === Logistics: Warehouse Receiving Hours ===
Truck WEDNESDAY 11:30 -> Bhiwandi: accept Night hub: wait
Truck SATURDAY  15:00 -> Bhiwandi: wait   Night hub: wait
Truck SUNDAY    10:00 -> Bhiwandi: wait   Night hub: wait
Truck SUNDAY    22:30 -> Bhiwandi: wait   Night hub: accept

    Why Interpreter here:

    • A familiar notation (like OpenStreetMap's opening_hours) that site managers already understand.
    • The grammar is tiny: windows (terminals) combined by "any of" (a non-terminal).
    • Edge cases (week wrap-around, exclusive end times) are handled once, in the interpreter, and tested.

    @Test
    void andBindsTighterThanOr() {
        var rule = RuleParser.parse("a == 'x' OR b == 'y' AND c == 'z'");
        assertThat(rule.matches(Map.of("a", "x", "b", "n", "c", "n"))).isTrue();
        assertThat(rule.toString()).isEqualTo("(a == 'x' OR (b == 'y' AND c == 'z'))");

    @Test

        assertThat(RuleParser.parse("total > 1").matches(Map.of())).isFalse();
    }

    @Test
    void formulaRespectsPrecedenceAndFunctions() {
        assertThat(FormulaParser.parse("2 + 3 * 4").eval(Map.of())).isEqualTo(14.0);
        assertThat(FormulaParser.parse("(2 + 3) * 4").eval(Map.of())).isEqualTo(20.0);
        assertThat(FormulaParser.parse("max(x - 10, 0)").eval(Map.of("x", 4.0))).isEqualTo(0.0);
        assertThatThrownBy(() -> FormulaParser.parse("y + 1").eval(Map.of())).hasMessageContaining("Unknown variable");
    }

    @Test
    void openingHoursWrapAroundTheWeek() {
        var h = OpeningHours.parse("SAT-MON 08:00-10:00");
        assertThat(h.isOpen(DayOfWeek.SUNDAY, LocalTime.of(9, 0))).isTrue();
        assertThat(h.isOpen(DayOfWeek.TUESDAY, LocalTime.of(9, 0))).isFalse();
        assertThat(h.isOpen(DayOfWeek.MONDAY, LocalTime.of(10, 0))).isFalse(); // end is exclusive
    }

    @Test
    void romanNumerals() {
        assertThat(Roman.interpret("XIV")).isEqualTo(14);
        assertThatThrownBy(() -> Roman.interpret("ABC")).isInstanceOf(IllegalArgumentException.class);

    6. Variations & Modern Java Take¶

    • Sealed interfaces + records for ASTs (all examples): concise, immutable nodes with exhaustive pattern matching.
    • Separate evaluation from the tree with a Visitor or switch: eval(node) as a switch over sealed node types lets you add operations (pretty-print, optimize, translate to SQL) without touching the nodes.
    • Compile instead of interpret: turn the AST into a lambda tree once (Predicate<Cart>), and evaluation becomes plain method calls.
    • Don't write a parser for big languages: use ANTLR for real grammars, or embed an existing expression engine: Spring Expression Language (SpEL), MVEL, JEXL, or a rules engine (Drools). For JSON-friendly rules, consider JSONLogic or CEL (Common Expression Language).

    Never eval untrusted code

    Embedding a general-purpose scripting engine (Nashorn, Groovy, full SpEL with type access) for business rules lets a rule author run arbitrary code on your servers. A small custom grammar or a sandboxed language (SpEL SimpleEvaluationContext, CEL) is far safer.

    8. Pros, Cons & Trade-offs¶

    ✅ Pros ❌ Cons
    Business users own the rules; changes without deployments Grammars grow; large languages become hard to maintain as hand-written classes
    Each grammar rule is one small class (easy to extend) Performance: tree walking is slower than compiled code for hot paths
    ASTs can be analysed: validated, explained, translated to SQL You now maintain a language: docs, error messages, versioning, tooling
    Natural fit with Composite and Visitor Security risk if the language can do too much

    9. Pitfalls & Anti-Patterns¶

    Accidental general-purpose language

    Rules start simple, then someone needs loops, then variables, then functions. Stop early: keep the grammar declarative and small, or adopt an established engine.

    Silent precedence bugs

    A OR B AND C must mean A OR (B AND C). Test precedence explicitly (see andBindsTighterThanOr) and show users the parsed tree.

    Parsing on every evaluation

    Parse once (on save or load), cache the AST, and evaluate many times.

    Unhelpful errors

    "Parse error" isn't enough for business users. Report position and expected token, and validate fields against a known schema at save time.

    10. Senior / Architect Deep Dive (10–15 yrs)¶

    Rules platforms. At scale, rule DSLs grow into platforms: an editor with autocomplete, validation against a schema of available fields, versioning with effective dates, simulation ("how many of last week's orders would this rule have matched?"), audit of who changed what, and a kill switch. Interviews for SAP-style or fintech roles love this discussion.

    Rules → SQL. Because the AST is data, you can translate it with a visitor: evaluate in memory for one cart, or generate a WHERE clause to find all matching customers in the database. Use bind parameters, never string concatenation.

    Performance. For millions of evaluations, compile the AST into lambdas or bytecode once (SpEL has a compiler mode). Order AND operands by cost and selectivity so cheap checks short-circuit first.

    Safety. Bound evaluation (depth limits, maximum expression size, timeouts), and whitelist functions. Treat rules as code: review, test and stage them.

    War story: the OR that gave everything away

    A rule meant "electronics AND (gold OR platinum)" was typed as category == 'electronics' AND tier == 'gold' OR tier == 'platinum'. The interpreter correctly parsed it as (electronics AND gold) OR platinum, so every platinum customer got 20% off everything, including gold coins. The promo ran for 6 hours before finance noticed. Fix: the editor now displays the parsed tree with explicit parentheses before saving, requires parentheses when AND and OR are mixed, and runs a simulation against yesterday's orders showing how many would match. Lesson: a correct interpreter isn't enough. Make the meaning visible to the people writing rules.

    12. Interview Corner¶

    Q1. What is the Interpreter pattern?

    A behavioral pattern that defines a grammar as classes and evaluates sentences of that language by walking a tree of those objects.

    Q2. Terminal vs. non-terminal expressions?

    Terminal expressions are leaves (a number, a variable, a comparison). Non-terminal expressions combine others (AND, OR, +).

    Q3. Give real examples.

    Regex (Pattern), SpEL, SQL/JPQL parsing, cron expressions, calculators.

    Q4. When should you use it?

    For a simple, stable grammar that needs to be evaluated often, especially when non-developers write the sentences.

    Q5. Main disadvantage?

    Complex grammars produce many classes and are hard to maintain; performance can suffer compared with compiled code.

    Q1. How do you parse text into an AST?

    Tokenize, then a recursive-descent parser with one method per grammar rule (expr, term, factor); precedence comes from the call hierarchy.

    Q2. How do you add a new operation (pretty-print, to-SQL) without changing nodes?

    Use a Visitor, or with sealed node types, a switch with pattern matching in a separate class.

    Q3. How do you make evaluation fast?

    Parse once and cache the AST; compile to lambdas; short-circuit AND/OR; order cheap checks first.

    Q4. Interpreter vs. Specification pattern?

    Specification composes rule objects in code (isGold().and(totalAbove(999))); Interpreter parses text into such objects.

    Q5. What are the risks of user-written rules?

    Wrong meaning (precedence), invalid fields, expensive or infinite evaluation, and code execution if the engine is too powerful. Validate, sandbox and limit.

    Q1. "Design a promotions engine where marketing writes rules."

    A small DSL or JSON rules with a schema of fields; parse-on-save with errors; versioned rules with effective dates; simulation on historical data; conflict resolution between promos (priority, stacking rules); compiled evaluation for checkout latency; audit and a kill switch; a/b tests.

    Q2. "Build your own DSL or use an existing engine (SpEL, CEL, Drools)?"

    Custom: tight control, small surface, better error messages, but you maintain it. CEL/SpEL (sandboxed): proven, fast, but you must restrict features. Drools: complex rule sets with inference, at the cost of a steep learning curve. Choose based on rule complexity, who writes rules, and security.

    Q3. "How would you evaluate a rule against 50 million customers?"

    Translate the AST to SQL or a Spark predicate (visitor) and push it down to the data, instead of loading each customer into memory.

    Q4. "Protect the system from a malicious or careless rule."

    Limits on expression size and depth, evaluation timeouts, whitelisted functions only, no reflection or I/O, and staged rollout with monitoring.

    Q5. "How do you evolve a rule language without breaking stored rules?"

    Version the grammar; keep old parsers or migrate stored rules with automated rewriters; deprecate constructs with warnings; test with a corpus of real stored rules.

    Problem: Interpret Roman numerals (MCMXCIV = 1994). Each symbol is a terminal with a value; a smaller symbol before a larger one is subtracted.

    Solution 
    package com.handbook.behavioral.interpreter.roman;

import java.util.Map;

/** Challenge solution: each symbol is a terminal expression; subtraction rule is the grammar. */
public final class Roman {

    private static final Map<Character, Integer> VALUE =
            Map.of('I', 1, 'V', 5, 'X', 10, 'L', 50, 'C', 100, 'D', 500, 'M', 1000);

    private Roman() {
    }

    public static int interpret(String numeral) {
        int total = 0;
        for (int i = 0; i < numeral.length(); i++) {
            Integer current = VALUE.get(numeral.charAt(i));
            if (current == null) {
                throw new IllegalArgumentException("Not a Roman numeral: " + numeral);
            }
            boolean subtract = i + 1 < numeral.length() && VALUE.getOrDefault(numeral.charAt(i + 1), 0) > current;
            total += subtract ? -current : current;
        }
        return total;
    }
}

    package com.handbook.behavioral.interpreter.roman;

public class RomanDemo {

    public static void main(String[] args) {
        for (String n : new String[] {"III", "IX", "XLII", "MCMXCIV", "MMXXVI"}) {
            System.out.println(n + " = " + Roman.interpret(n));
        }
    }
}

    Output:

    III = 3
IX = 9
XLII = 42
MCMXCIV = 1994
MMXXVI = 2026

    Key points to say: symbols are terminals; the subtraction rule is the grammar; single left-to-right pass, O(n). Follow-up: validate canonical form (IIII and IC are invalid) with a stricter grammar.
